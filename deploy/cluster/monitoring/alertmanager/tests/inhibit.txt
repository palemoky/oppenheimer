# 抑制的核对表（scripts/cluster/monitoring.sh inhibit-test）：每行是“期望 | 告警的标签”。
# 脚本把这些告警一次塞进集群上的 Alertmanager（另加 synthetic=true、run、case 三个标签，4 分钟后自己过期），
# 再从它的 API 读每一条是不是被抑制了、被谁抑制的。不动任何组件；critical 的那些先加了静默，不发 Telegram。
#
#   inhibited  应当被抑制
#   active     不该被抑制（源告警，以及每条抑制规则的对照：equal 里的标签对不上的那一个）
#
# 标签照规则真实产生的写（2026-11-23 从 Prometheus 里取的：mysql_up 带 cluster 和 instance，实例名是 Pod 名；
# 节点的 instance 是 地址:9100）。equal 的坑是“两边都没有这个标签也算相同”，所以标签要写全，不能只写规则里匹配的那几个。
# 改了 alertmanager.yaml 的 inhibit_rules，或者改了这些规则的标签，就在这里加一行再跑一遍。

# ---- chart 自带的：同名、同命名空间，重的压轻的；InfoInhibitor 压同命名空间的 info ----
active    | alertname=SyntheticTiered severity=critical namespace=synthetic-a
inhibited | alertname=SyntheticTiered severity=warning namespace=synthetic-a
active    | alertname=SyntheticTiered severity=warning namespace=synthetic-b

# InfoInhibitor 自己被“任何告警”压住（chart 的第四条规则没有源的条件），所以它是 inhibited；
# 它照样能当源（抑制不连锁的另一面：被抑制的告警仍然是有效的源）。
inhibited | alertname=InfoInhibitor severity=none namespace=synthetic-c
inhibited | alertname=SyntheticInfo severity=info namespace=synthetic-c
active    | alertname=SyntheticInfo severity=info namespace=synthetic-d
