## 分配理由

- **集群放在 Ubuntu**：核心数最多，x86_64 镜像兼容性最好。用虚拟机而不是单机多容器节点，是为了能真实地关掉一个节点、切断节点间网络。
- **压测机与集群分离**：压测工具和被测系统抢资源会让数据失真，所以由 Mac mini 发起。
- **GTX 1660 不用于模型推理**：6GB 显存跑不了对诊断有用的模型，Agent 使用 Claude API。
- **Mac mini 不加入集群**：混合架构会让每个镜像都要多架构构建，增加的麻烦与学习目标无关。

## 内存预算（粗估）

2026-11-17 宿主机从 32GB 加到 48GB（系统认到 46.96 GiB，差的约 1 GiB 是内核的页记账和固件保留），虚拟机从 6、11、11 GiB 改成 10、16、16 GiB，合计 42 GiB。改规格用 `scripts/cluster/on-host.sh vm.sh resize <名字>`，一次一台。下面的预算表是按原来的 28GB 写的，各项预估没有变，变的是余量：约 6GB 变成约 20GB。

内存是整个项目最紧的资源，原来总可分配约 28GB：

| 组件 | 预估 |
|---|---|
| K8s 系统组件 | 2GB |
| MySQL：2 分片 × 一主一从 | 4GB |
| Redis Cluster：6 节点 | 1.5GB |
| Kafka：3 broker | 4.5GB |
| Prometheus、Grafana、Alertmanager、Loki | 4GB |
| Tempo（单体模式，链路；ADR-0024 之前这里是 SkyWalking OAP 加 BanyanDB 的 4GB） | 1GB（粗估，阶段 3a 实测） |
| OpenTelemetry Collector | 0.5GB |
| Chaos Mesh | 0.5GB |
| 业务服务（多副本，含 CDC） | 3GB |
| 归档 MySQL 实例 | 1GB |
| 余量 | 约 6GB |

不够时的处理顺序：缩短监控数据保留期并下调采样率 → 把 Tempo 或 Loki 的存储挪到 NAS 或 Mac mini → 降低中间件副本规格。

## 网络

局域网是 192.168.50.0/24。网关、DNS、DHCP 都在 R2S（192.168.50.2，OpenWrt），不在 RT-AC5300 上。DHCP 池是 .100 到 .249，集群用池外的地址（定义在 `scripts/cluster/cluster.env`）：

| 地址 | 用途 |
|---|---|
| 192.168.50.2 | R2S：网关、DNS、出网代理 |
| 192.168.50.3 | DS218+（`ssh nas`，端口 5022） |
| 192.168.50.14 | 3900X 的 Wi-Fi，管理用的备用通道（`ssh ubt`） |
| 192.168.50.19 | 3900X 的网桥 `br0`（有线，上联口是 PCIe 网卡 `eno1`；R2S 上按网卡 MAC 绑定了同一个地址，换网卡后绑定和白名单要跟着换） |
| 192.168.50.40 到 .42 | k3s-server、k3s-agent-1、k3s-agent-2 |
| 192.168.50.43、.44 | 已在代理白名单里，留给以后加节点 |
| 192.168.50.50 到 .59 | MetalLB 地址池（只接收进来的访问，不需要进代理白名单）。.50 是镜像仓库（端口 5000），.51 是对外入口（Envoy Gateway，端口 80），其余未分配 |

.1 到 .32 是 R2S 上给各设备的静态绑定，不要占用。

- **虚拟机用桥接**：网卡接在宿主机的 `br0` 上，直接拿局域网地址。Wi-Fi 网卡不能接进网桥，所以宿主机必须走有线。
- **节点不接受 IPv6 的路由通告**（`accept-ra: false`）：通告里带的 IPv6 DNS 不经过代理，返回被污染的地址，节点和 Pod 会连不上镜像源（2a 设计文档第 11 节）。集群只用 IPv4。
- **NAS 的 NFS**：共享文件夹 `k8s`（`/volume1/k8s`），只对 192.168.50.40/29 开放，Squash 是“无映射”。子目录由 `scripts/cluster/addons.sh nfs` 建，要直接挂子目录。
- **出网要进 R2S 的白名单**：R2S 上的代理（nikki）是 fake-ip 模式，带按 IP 和 MAC 的局域网白名单。不在名单里的设备解析域名拿到的是 198.18.0.0/16 的假地址，但连接不被代理接管，表现是所有按域名的出网都连不上，而 ping 真实 IP 是通的。新加的设备（宿主机的有线网卡、每台虚拟机）都要进名单。
- 2026-11-15 实测有线链路只有 100 Mbit/s，换过一根网线后仍然如此。内核日志是 `Downshift occurred from negotiated speed 1Gbps to actual speed 100Mbps`：两端都同意千兆，但千兆要用的四对线里有不通的，网卡退到只用两对线的百兆。让网卡只通告千兆时链路起不来，别的电脑接同一个路由器口是千兆，所以是板载网口的硬件问题。2026-11-17 换成了 PCIe 网卡（RTL8126，`10ec:8126`，内核自带的 r8169 驱动，接口名 `eno1`），协商到 1Gbps 全双工；路由器的口只有千兆，所以到不了 2.5G 或 5G。板载的 `enp39s0` 不再使用，也不要再插网线：它回到了安装器写的 DHCP 配置，插上会和网桥抢地址。
- 上联断开时（拔网线、换网卡）宿主机从 IPv4 连不上，包括 Wi-Fi 的地址：虚拟机的端口让 `br0` 保持有载波，发往局域网的包仍然走网桥。这时走 Wi-Fi 网卡的 IPv6 链路本地地址。
- 宿主机是双系统。GRUB 菜单显示 5 秒，默认进 Ubuntu，另有一项 `Windows Boot Manager`（2026-11-17 手工加在宿主机的 `/etc/grub.d/40_custom`，不在仓库的脚本里）。
