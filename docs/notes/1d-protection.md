# 1d 笔记：让系统在过载和依赖故障时表现得可预期

这份笔记整理 1d 里值得在面试中讲的点，按主题组织，不按开发步骤。每条按“面试官会怎么问 → 要点 → 本项目里怎么做、量到什么数、踩过什么坑”来写。设计全文见 [design/1d-protection.md](../design/1d-protection.md)（下文简称“设计”，引用章节号），取舍见 [ADR-0017](../adr/0017-keyed-concurrent-consume.md)、[0018](../adr/0018-async-stock-deduction.md)、[0019](../adr/0019-gateway-rate-limiting.md)、[0020](../adr/0020-service-protection.md)、[0021](../adr/0021-degradation-and-lifecycle.md)、[0022](../adr/0022-reconciliation-hash-tree.md)、[0023](../adr/0023-instrumentation.md)，另有 [ADR-0004](../adr/0004-opentelemetry.md)（OpenTelemetry）和 [ADR-0011](../adr/0011-admission-backpressure.md)（受理背压，和限流的关系见 4.1）。

1d 做的事分六步：还吞吐的欠账（落库并发、轮询先读闸门、商家索引按批写、开环压测）；库存扣减在 MySQL 一侧异步化；网关限流；服务侧保护（Envoy 边车、时限逐跳收紧、重试规范）；降级预案和优雅启停；基于哈希树的对账；OpenTelemetry 埋点。本机的绝对数字不可靠（OrbStack 的端口转发偶发 200 毫秒停顿，1b 起就如此），文中的数用来看相对变化和瓶颈在哪，吞吐结论要到阶段 2 的集群上才算数。

## 1. 消费者吞吐

### 1.1 消费者吞吐上不去，先看什么

**问**：Kafka 消费者吞吐不够，怎么办？

**要点**：先定位瓶颈在哪一层，再选手段。一个分区一个 worker、一条处理完才取下一条时，吞吐上限是“分区数 ÷ 单条耗时”，和下游有多少余量无关；资源都很空闲而吞吐上不去，说明瓶颈在消费的结构上。手段分两层：

| 手段 | 解决什么 | 代价 |
|---|---|---|
| 加分区 | 把负载分到更多消费者实例上 | 分区数只能加不能减；key 到分区的映射变，同一个 key 的新旧消息可能进不同分区；每个分区在 broker 上有开销，再平衡随分区数变慢 |
| 加实例 | 同上，上限是分区数 | 要有实例可加 |
| 分区内并发（按 key 分 lane） | 单个实例内的并行度 | 位点提交变复杂；重复投递变常态；占用的下游资源按并发度倍增 |
| 按批处理 | “每条消息各自提交一次”的开销（见 1.7） | 批内失败要隔离；同 key 多版本要合并 |

关键的区分：**分区数由“要分给多少个实例”决定，实例内的并行度由“下游能承受多少并发”决定**。把两件事绑在一个数上，调一个就动了另一个。

**本项目**（设计 2.1、ADR-0017）：1b 压测落库只有约 410 单/秒，4 个分区、每条约 10 毫秒（一次 Redis、一次 gRPC、两个事务），而 MySQL 约 60%、inventory 0.1 核，都没用满。商家索引同样结构，约 2000 行/秒，500 万行要追 40 分钟。没有直接加分区：本机只有一个 order 实例，缺的是实例内并行度；分区数留到阶段 2 有多实例时按实例数定。

### 1.2 分区内按 key 并发：怎么保序

**问**：分区内并发处理，怎么保证同一个订单的消息仍然有序？

**要点**：按 key 的哈希分到固定的 lane，lane 内串行，lane 之间并行。同一个 key 永远进同一条 lane，所以“同 key 按位点顺序”仍然成立；不同 key 之间本来就没有顺序要求。这是它和“开一个协程池随便处理”的区别：协程池里同一个订单的两条消息可能同时被处理，每个 handler 都得自己处理并发。

**本项目**：`kafkax.ConsumerConfig.Concurrency`，默认 1（旧行为）。order 落库开 8，orderindex 开 16（后来被按批写取代，见 1.7）。落库并发 8 乘 4 个分区，同时在途 32 个订单，要和订单库连接池（每库 25）一起定，order 启动时比较两个数并告警（设计 2.2）。

### 1.3 位点只能提交连续前缀

**问**：并发处理时消息不按顺序完成，位点怎么提交？

**要点**：Kafka 一个分区的已提交位点是一个**数**，不是一个集合；提交 8 的含义是“0 到 7 都处理完了”。偏移量 7 做完了而 5 还在重试，只能提交到 5，提交到 8 的话重启后 5 就丢了。所以可提交的位点是“最小的未完成偏移量”，没有在途消息时是“最后分发的偏移量加一”。后果：前缀之后已经完成的消息在重启或再平衡后会被重新投递，**并发消费把重复投递从偶发变成常态，handler 幂等是前提**。

**本项目**：`pkg/kafkax/inflight.go` 的 `prefixTracker`，按偏移量二分查找，不用“offset 减首个 offset”当下标，因为压缩过的 topic 和事务控制记录会让偏移量有空洞。实测一次**正常停止**：处理了 923 条、提交了 661 条，重启后 262 条重做。停止时每条 lane 只做完手上的一条，前缀之后已完成的都要重来，量出来比预想的多（设计 2.10）。这部分是“提交错了就丢消息”的代码，带 `-race` 测试：乱序完成时提交的位点、卡住一条时窗口生效、再平衡时不提交未完成的、同一个 key 不并发。

### 1.4 在途窗口

**问**：一条消息卡住，别的 lane 一直在处理，会怎样？

**要点**：位点被卡住的那条拖着不动，“已处理未提交”的跨度会无限增长：内存里的完成表无限长，一次重启要重放全部。所以加窗口：分发的偏移量领先最小未完成偏移量超过窗口就停止分发。到这一步行为和串行时一样（分区停住），窗口只是让短暂的重试不拖住其他订单。窗口也限定了最坏的重放量，以及 lag 告警要留的余量（已提交位点可能落后实际进度最多一个窗口）。

**本项目**：窗口 `MaxUncommitted` 默认 1024，且不小于 lane 数（窗口比 lane 数还小，有的 lane 永远轮不到）。一条 lane 被慢消息拖住时，哈希到同一条 lane 的其他订单也在等：落库重试上限约 26 秒，并发度 8 时约八分之一的订单被连累，并发度越大受连累的比例越小（ADR-0017 后果）。

### 1.5 lane 的哈希为什么不能和生产者分区用同一个

**问**：按 key 分 lane，用哪个哈希？

**要点**：不能用生产者分区那个哈希（Kafka 默认 murmur2）。一个分区里的 key 本来就是“哈希取模分区数后相等”的一批，再用同一个哈希对 lane 数取模，lane 数和分区数有公因数时它们会挤进少数几条 lane，并发度白开。

**本项目**：`laneOf` 用带随机种子的 `maphash`。种子每个进程不同没有关系，lane 的分配不需要跨重启稳定（设计 2.10、`pkg/kafkax/consumer.go`）。

### 1.6 哪些消费者不该开并发

**问**：什么消费者能开并发，什么不能？

**要点**：判据是“消息的 key 和它处理时锁的数据是不是同一个维度”。key 是订单号、处理时碰的也只是这个订单的数据，才能开。key 是订单、处理时锁的是 SKU 行（同一个 SKU 的不同订单并发处理只会在行锁上排队，还会让死锁重试变多），开了没收益。依赖“分区内按时间有序、队首没到期就等”的延迟队列，并发会破坏它的假设，不允许。

**本项目**（设计 2.2 的表）：开并发的是 order 的落库（key 是订单号）；inventory 的订单事件（key 是订单号，碰的是 SKU 行）不开，它也不是瓶颈；支付结果、payment 的订单事件量小不开；延迟关单消费者 `Concurrency > 1` 时构造函数直接报错。

**另一个后果**（ADR-0017）：不同 key 之间原来“碰巧有”的先后没有了。同一个用户用同一个幂等键先后受理两个订单（幂等键在 Redis 里过期后的重放），以前同一分区里按位点先受理的赢，并发后谁先插入谁赢，先受理的订单号可能变成不存在。两种结果都满足“一个幂等键只有一个订单”，跨分区时本来就如此。

### 1.7 按批消费和坏消息隔离

**问**：按 key 并发和按批处理各针对什么瓶颈？一批里有一条坏消息怎么办？

**要点**：并发针对“每条消息各自等下游往返”（落库：Redis、gRPC、事务各自的往返，合不成一条语句）；按批针对“每条消息各自提交一次”（写一行的投影，一条多行语句写几百行）。批内失败的隔离办法：**整批先重试几次（暂时性错误），仍失败或错误本身标为不可重试，就退回逐条处理**，每条单独走原有的重试和死信，这样坏消息被隔离，handler 不需要报告“是哪一条”。只做“失败就直接逐条”时，数据库抖一下，第一条重试到恢复后其余几百条各自提交一次，正确但按批的意义没了。多行 upsert 拿不到逐行结果时，统计只能是估计值：精确的是写了几行、批内合并掉几个映像，“改了几行”取受影响行数和写入行数的较小者，是上界，日志字段名带 `_est` 提醒这一点。

**本项目**（设计 2.11、ADR-0017 补充）：

- `kafkax.NewBatchConsumer`，不设“攒多久”：取本地队列里现成的，至多 `MaxBatch`（默认 500），没有积压时一批就是一条，延迟不变。整批最多尝试 3 次（`batchAttempts`）。与 `Concurrency` 互斥，延迟消费者不支持。
- orderindex 一批里：解不了的消息返回 `Permanent` 触发逐条回退；同一订单只留版本最高的映像；每张索引表一条多行 `INSERT ... AS new ON DUPLICATE KEY UPDATE`，版本比较不变（版本列最后赋值）；两个索引库是两个事务，不是原子的，一个成功一个失败时整批重做，成功那半是空操作。
- 语句内的行按主键排序再写，不同分区的批并发写同一张表时加锁顺序一致，减少死锁。
- 实测：按 key 并发在约 9000 行/秒见顶（一行一个事务、每次约 1.2 毫秒刷盘，靠组提交合并，合到头就是这个数，从 4 路加到 64 路到 32 路后就平了）；按批写，批 500 行在 4 路并行下不带 `-race` 7.9 万行/秒、带 `-race` 4.8 万；批 1 行 2100 行/秒。印证瓶颈是提交次数。
- 流程：先决定“商家索引先用并发消费，达不到 1 万行/秒再做按批写”，实测 9000 低于门槛才做，没有一上来就做最复杂的方案。

## 2. 热点行与库存扣减异步化

### 2.1 瓶颈是一层一层露出来的

**问**：压测里怎么一步步找到瓶颈？

**要点**：瓶颈不是一次找全的：解掉一层，下一层才露出来，每一层都要量了才知道，不能靠猜。本项目落库路径依次是：消费者串行（1b）→ 热门 SKU 的行锁 → 每个订单三次提交的刷盘 → 剩下的往返次数乘以每次往返的代价（见 9.9）。找瓶颈的办法：让数据库自己说，清空 `performance_schema` 的语句统计，跑一次，按总耗时排序。

**本项目**（设计 2.10、3.9）：

| 阶段 | 落库吞吐（单/秒，开环 3000/s、10 个 SKU） | 怎么看出下一个瓶颈 |
|---|---|---|
| 并发度 1 | 316 | 刷盘是主要成本（放宽刷盘后 571） |
| 并发度 16 | 686 | `UPDATE sku_stock` 平均 48.4 毫秒，几乎全是等行锁，累计 1192 秒；其余语句都在 0.3 毫秒以下 |
| 异步合并更新，并发 16 | 870（32 时 985） | 热点行锁消失，下一个是 `COMMIT` 每次约 9 毫秒，一个订单提交三次约 27 毫秒；每秒约 2600 次提交是这个实例的上限 |
| 同上、放宽刷盘 | 约 1050 | MySQL 不再是瓶颈，剩下 54 毫秒在 MySQL 外，用链路才拆开（9.9） |

并发度加到 8 以后收益递减：8 到 16 只多 7%。

### 2.2 热点行更新的几种解法

**问**：秒杀时所有订单扣同一个 SKU 的库存行，怎么办？

**要点**：

| 方案 | 做法 | 代价 |
|---|---|---|
| 分桶 | 一个 SKU 的库存拆成 N 行，不同订单扣不同的行 | “某个桶没货、别的桶有货”要换桶或借调；读可售数变成求和；桶数要按热度定。适合 MySQL 仍是防超卖关口的系统 |
| 合并更新 | 把一批对同一个 SKU 的增量合成一次扣减（先记增量，后台一批一条 UPDATE） | 计数落后一个应用周期；防超卖的判断要挪走 |
| 异步汇总 | 预占只写流水，可售数异步汇总 | 同上 |
| 缩短持锁时间 | 放宽刷盘、把更新放事务最后一步 | 实测只把并发 16 的吞吐从 686 提到 848，且拿持久性换的 |
| 靠多个 SKU 分散 | | 压测里 10 个 SKU 到 100 个只从 686 到 800；秒杀恰恰是所有人买同一个 SKU |

**本项目**（ADR-0018）：选合并更新。理由是防超卖的关口已经在 Redis 闸门，MySQL 这一步只是第二道检查，不值得为它付分桶的复杂度。

### 2.3 库存异步化之后，防超卖靠什么

**问**：MySQL 不再在预占时检查可售数，还怎么保证不超卖？

**要点**：**缓存（Redis）里的原子扣减成了唯一关口，数据库从“阻止”变成“发现”**。这是最大的代价：闸门和 MySQL 对不上时（有人直接改库、Redis 丢数据后装载有误、对账修正有缺陷），以前是订单创建失败，以后是订单成功、应用者在把增量加到 `sku_stock` 时被 CHECK 约束拒绝并报错。兜底没有消失，只是变成事后发现：应用者的 CHECK、闸门和 MySQL 的周期对账、`load verify` 的第 22 项（静止后增量都已应用）。

**本项目**（设计 3.4、3.8）：

- 恒等式 `available + reserved + sold = 入库总量` 在任何时刻仍成立（每个增量自身三项之和为零）；“加上未应用增量之后三个数都不为负”才是新的不变量。
- **“发现”对持续的超卖是确定的，对短暂的不确定**：一批之内先求和再更新，预占超过库存但它的释放落在同一批里，合计不为负就报不出来，分在两批才会。
- 读“真实的数”（`sku_stock` 加全部未应用增量）要在一个一致性读里，一条语句一个快照：闸门预热和闸门对账必须这样读，`GetStock` 也统一返回真实的数，不分“判断的读”和“展示的读”，免得有人误用落后的那个。
- 为什么增量放库里的一张表而不经 Kafka（设计 3.2，方案 A 对 B）：未应用的增量必须能和计数在同一个快照里读到，否则装载闸门时不知道还有多少在路上，装进去的数偏大，正是超卖的方向；“改计数”和“标记已应用”要在一个事务里，Kafka 是至少一次，仍要靠预占记录去重，等于在消费端把方案 A 的事务再做一遍。主人决定方案 B 先不做。

### 2.4 队列表的坑

**问**：用数据库表当队列（取一批、处理、删除），有哪些经典的坑？

**要点和本项目**（设计 3.3、3.7、3.10）：

1. **不能用自增 id 做“已处理到哪”的水位。** 自增 id 在插入时分配，不是提交时：id 小的事务可能后提交，水位已经越过它，它就永远不被应用。取“当前看得见的行”再删掉没有这个问题。这和 outbox 的结论（1b 笔记 1.2）是同一个原因。
2. **`SKIP LOCKED` 在有先后依赖的队列里有害。** 同一个订单的增量有先后：先预占（`reserved +n`）后释放（`reserved -n`）。跳过被锁住的行会让后面的先应用，`reserved` 瞬间为负，撞上 CHECK。`SKIP LOCKED` 适合“任意一行都行”的场景（多个工作者抢可互换的任务），不适合有依赖的。本项目改坏验证时发现它的害处是**误报，不是算错**：最终的数仍正确，但每次都是一条“超卖”的错误日志，而这条日志是发现真超卖的唯一途径，不能有假阳性。第一版并发测试只看了最终的数和恒等式，改坏之后照样通过，补上“库存充足时应用者不应报告任何卡住的 SKU”才抓得到。
3. **`REPEATABLE READ` 下带 `LIMIT` 的加锁读会锁住索引末尾的间隙。** 行数不足一批时它一直扫到索引末尾并锁住末尾的间隙，而所有新增量都插在末尾，预占、确认、释放被应用者的事务挡到它提交。所以应用者用 `READ COMMITTED`。归档的删除同理。
4. **按 id 顺序加锁扫描不是快照**（CI 上才抓到的设计漏洞，设计 3.10）。原设计写“按 id 顺序、不跳过，就不会乱序”，这个论断是错的：`SELECT ... ORDER BY id LIMIT n FOR UPDATE` 是一行一行加锁往前走的，中途会在别人锁着的行上等，不是一个瞬间的快照。较早分配 id、较晚提交的预占可以出现在游标已走过的位置后面，游标继续往前就取到这个订单后来的释放，一批里有释放没有预占，应用者报“超卖”。本机连跑 40 遍复现不了，CI 失败了一次。修法不再依赖先后：这一批的合计被拒绝时，锁住这个 SKU 的全部未应用增量重算；还不行就用一次普通一致性读（真正的快照）算真实值，为负才报。两个应用者现在可能互相死锁，数据库回滚一个，应用者重试。**教训两条**：论证“某种交错不会发生”时问清每条语句看到的是不是一个时间点的状态（一致性读是，加锁读不是）；并发测试在本机通过说明不了什么，这个测试在本机连跑五遍、做过改坏验证，CI 第二次运行就失败了（CI 机器更慢、别的包的测试同时在跑，交错的分布不同）。
5. **合计为零的批也要执行更新**：同一订单先预占后释放，三个增量加起来都是零，仍执行并确认行存在，否则“SKU 不存在”的增量会被当成已应用而删掉。
6. **卡住的 SKU 要绕开**：它的增量留在表头，不绕开会把每一批占满，别的 SKU 轮不到；应用者记着卡住的 SKU，平时排除，每秒带上重试一次。

### 2.5 CHECK 约束、取值范围变了要查所有读者

**问**：有没有“一个假设变了，下游读者没跟着变”的例子？

**要点**：约束失败的范围要清楚：CHECK 失败只回滚那一条语句，不是整个事务。一个值的取值范围变了，要把它所有的读者过一遍。

**本项目**（设计 3.8）：异步化之后“可售数”可能为负（超卖时），测试铺开时发现两个产品代码缺陷：超卖时预热把负数原样传给闸门，被当参数错误拒绝，对外成了“闸门不可用，请重试”，调用方对一个数据问题无休止地重试（改成按 0 装载并记错误日志）；超卖时对账把负的 MySQL 可售数当上限传给闸门而报错，闸门装多了导致超卖时对账是唯一能收紧闸门的机制，却恰好此时失效（改成上限取 0）。约定：`GetStock` 照实返回（可为负），面向买家的展示由 gateway 截到 0。

### 2.6 读路径上“先查哪里”由数据的生命周期决定

**问**：轮询订单状态拖垮了落库，怎么改？

**要点**：非终态订单不缓存，每次轮询都读 MySQL，和落库共用连接池。把查询顺序按数据的生命周期倒过来：刚受理的订单只在 Redis 的占用里，MySQL 里不可能有行，先读占用就不用白读两次库。

**本项目**（设计 2.4）：`GetOrder` 先读占用：未认领（落库还没开始，行不可能在）直接合成 `CREATING`；已认领读主库；没有占用才读订单行（从库，没有再由主库确认，再走冷库）；Redis 读失败退回旧顺序，Redis 故障不应让已落库的订单也查不到。**先读占用让原来“行、占用、行”的三步变成一次行读**：原来多读的那一次是为了排除“两次读之间订单落库并走完终态、占用被归还”，先读占用后占用没有只可能是没受理、已回收、或已终态，最后一种行一定已提交。未认领时返回 `CREATING` 可能比真实状态旧一瞬间，展示读可接受。测试 `TestQueuedOrderIsAnsweredWithoutTheOrderDB` 把订单库关掉也能答。实测有查询压力（每秒约 4600 次查询）时落库 617 对无压力的 821，剩下的 25% 来自已落库待支付订单的轮询，交给限流（4.1）。

### 2.7 组提交和刷盘

**要点**：每个事务提交要刷盘（`sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`），串行时刷盘是主要成本；并发时靠组提交把多个事务的刷盘合并。所以一个订单的提交次数就是吞吐的天花板，要提高就得减少每个订单的提交次数（本项目落库三次：订单库两次加 inventory 一次）。链路里 MySQL 自己统计的提交 10.2 毫秒和链路里的数一致，而单个连接串行提交只要 1.3 毫秒，那 10 毫秒是每秒两千多次提交并发时排队等刷盘。放宽刷盘（`sync_binlog=0`、`flush=2`）量过但那是拿持久性换的，量完改回。

## 3. 压测方法

### 3.1 闭环和开环，协调遗漏

**问**：压测工具怎么写才能量出过载下的行为？

**要点**：

- **闭环**：每个虚拟用户发一个、等返回、再发下一个。系统变慢时请求也跟着变少，**量不出过载**，而且慢的时候采样变稀。
- **开环**：按固定时间表发请求（每秒 N 个，均匀间隔），不管上一个有没有返回。系统卡住时请求照来，才能看到限流该不该触发、触发后延迟是否稳住。要给在途请求设上限（否则卡住时耗尽本机连接），超过时这个时刻的请求记为“未发出”单独计数，不悄悄跳过。
- **协调遗漏（coordinated omission）**：延迟要从“计划发出的时刻”算起，不是从实际发出的时刻。系统卡住 1 秒时，这 1 秒里本该发出的请求都在排队，它们的延迟要算上排队时间；只从实际发出算，会把最坏的样本漏掉，表现是 p99 好看得离谱。

**本项目**（设计 2.6）：`load run -mode open -rate N`；压测期间不轮询，结束后有收尾阶段把已受理订单的终态查出来写进账本，`load verify` 照常能用。之前的“开环”是用 1 毫秒轮询超时凑出来的近似。闭环模式保留作默认。开环模式没有量落库延迟（网关响应里没有落库时刻、压测期间不轮询），报告里写“未测”，落库吞吐从库里算。

### 3.2 为什么先还吞吐的欠账，再做限流和熔断

**问**：限流阈值怎么定？

**要点**：限流、熔断、背压的阈值都要对着“系统实际能处理多少”来定。在一个由结构缺陷造成的瓶颈上定下的阈值（落库串行约 400 单/秒），瓶颈改完就全部作废。另外没有开环的压测，过载下的行为量不出来，限流和降级的验收都要靠它。所以 1d 把吞吐放第一步，对账放最后（它和前几步无依赖，放最后正好用来验证前几步改动之后数据仍然一致）。

**本项目**（设计第 1 节）：`ADMIT_MAX_QUEUE` 保持 1 万，按 640 到 820 单/秒是排 12 到 16 秒，仍小于 1 分钟宽限期；落库吞吐提高后要重新设定，“静态上限和吞吐绑定”是 ADR-0011 就记着的代价。

### 3.3 几条压测上的经验

- **基线要先确认它自己没被写慢**：全量归并的第一版按 18.6 小时一个节点、一张表一条语句地读，4096 行的数据发了 2.9 万条语句，对比不公平，改成按 198 天分段（设计 7.15）。
- **压测配置要和被测机制对齐**：压测、chaos、e2e 都是从一个地址用很多用户号打网关，默认限流会把它们限住，忘了关时现象是“吞吐突然上不去”，容易误判成性能问题（ADR-0019 后果）。
- **一致性检查全绿不等于可用**，这条在 1b 笔记里，1d 的故障注入和 `load verify` 延续同样的做法：看比例，不只看不变量。
- **全量采样压测会撑爆后端**：`otel-lgtm` 容器上限 1.5 GiB，全量采样压测一轮后 1.26 到 1.33 GiB（设计 8.16）。

## 4. 限流

### 4.1 限流和背压的区别

**问**：已经有背压了，为什么还要限流？

**要点**：两者问的问题不同。

| | 背压 | 限流 |
|---|---|---|
| 问的问题 | 系统现在还吃得下吗 | 这个调用方是不是要得太多了 |
| 依据 | 队列长度（系统自己的状态） | 谁在调、调哪个接口、多快 |
| 被拒绝的是谁 | 所有人，不分来源 | 超出配额的那个用户或地址 |

只有背压：一个用户用脚本每秒下 1000 单，队列被占满，其他人全被拒绝，系统没垮但不公平。只有限流：每个人都守规矩但总量超过容量，系统照样被压垮。两个都要。对外要让客户端能区分：429 加 `BACKLOGGED`（系统忙，所有人退避）和 429 加 `RATE_LIMITED`（你自己太快）。

**本项目**（设计 4.1、4.10）：背压在 order 的闸门脚本里（ADR-0011，按队列长度，不是最老订单的排队时长，见 1b 笔记 2.7）；限流在网关最外层。ADR-0011 里还有一个可以单独讲的点：**背压的信号不能放在会被别的任务清掉的数据里**。第一版“排队超时的占用数”会被回收任务还掉占用而降回阈值以下，受理重新打开，循环发生；补充的第 3 条信号是消费者自己留下的心跳（`gate:claim_at`），落库没有动静时只放最多 `ADMIT_MAX_STALE` 个订单当探测，探测被认领就恢复。这和熔断器半开是同一个思路，区别是不需要单独的状态，心跳的新旧就是状态。它的边界（心跳只能说明消费者在取消息，不能说明订单写进了库）由 6.3 的落库健康补上。

### 4.2 限流算法对比

**问**：限流算法有哪些？为什么选令牌桶？

**要点**：

| 算法 | 做法 | 问题 |
|---|---|---|
| 固定窗口计数 | 每个窗口一个计数器，边界清零 | 边界上能通过两倍：上一窗口最后一刻和下一窗口第一刻各打满一次 |
| 滑动窗口日志 | 记每个请求的时间戳，数最近一个窗口内的 | 精确，但每个键要存和限额一样多的时间戳 |
| 滑动窗口计数 | 当前窗口计数加上一窗口按比例折算 | 近似，够用；表达不了“平时慢、允许偶尔突发” |
| 漏桶 | 请求进队列，以固定速率流出 | 输出平滑，突发要排队，增加延迟；网关不适合替客户端排队。当计量器用（不排队，只判断）时和令牌桶等价，GCRA 是它只存一个时间戳的写法 |
| 令牌桶 | 以固定速率攒令牌，最多攒到容量，有令牌就过 | 允许不超过容量的突发 |

**令牌桶的两个参数各表达什么**：`rate` 是长期平均速率，`burst`（桶容量）是允许的突发。用户连点两下、客户端超时后立刻重试、页面同时发几个请求都是正常突发，应放过；持续超过速率才拒绝。**不需要后台任务补令牌**：状态只有“令牌数、上次计算的时刻”两个数，补充在取的时候按流逝的时间算出来（取令牌数和容量的较小者）。**`Retry-After`** 由“缺的令牌数除以速率”算出来，向上取整到秒、至少 1 秒；一次判断里几个桶都不够时取最长的那个。

**本项目**（设计 4.2、4.3；ADR-0019）：三个维度各防一样东西：

| 维度 | 键 | 防什么 | 默认 |
|---|---|---|---|
| IP | 客户端地址 | 没有身份的洪水，在识别用户之前就拒绝，最便宜 | 每秒 200，桶 400 |
| 用户 | 用户号加接口 | 一个用户占用过多：脚本刷单、过快的轮询 | 下单、支付、取消 5/10；查订单、查支付 20/40；列表 10/20；查库存 50/100 |
| 接口 | 接口 | 总量超过下游承受 | 默认不设（等有指标） |

按 IP 默认值比按用户的高得多，因为一个地址后面可能是一个公司或运营商出口。用户身份取自 `X-User-Id`，本项目没有做认证，这个头可以伪造，按用户限流在有真实认证之前挡不住故意换用户号的人，那是按 IP 那一层要挡的。e2e：一个用户 9 毫秒内并发 30 个下单，受理 10 个、20 个 429，`Retry-After` 是 1 秒，另一个用户不受影响。开环压测 20 个用户、每秒 1000 单、20 秒：受理 2180（算出来 20 × (10 + 5 × 20) = 2200），89.1% 被限流，受理延迟 p99 从 17.0 毫秒降到 3.6 毫秒，被限流的请求在网关就返回，没碰 order、闸门和 Kafka。

### 4.3 限流状态放哪

**问**：多个网关实例，限流状态放进程里还是 Redis？

**要点**：

- **放进程里**：没有网络往返、不依赖任何东西；N 个实例各限各的，总限额是 N 倍，同一用户的请求落在哪个实例随机。
- **放 Redis**：所有实例共用，限额精确；每个请求多一次往返，Redis 不可用要有对策。
- 按维度分：**按 IP 在进程里**（第一道闸，要最便宜；N 倍的误差对“挡洪水”无所谓；不能依赖 Redis，否则打垮 Redis 就等于关掉限流）；**按用户和接口在 Redis**（用户配额很小，N 倍误差就是限了个寂寞；接口总量保护下游，必须全局算）。
- **放缓存实例还是数据实例**：限流状态的要求是“快、丢了无所谓”（丢一个桶等于那个桶满了，宽松一次），这正是缓存实例（`allkeys-lru`、不持久化）的特性；闸门实例的要求是“不能丢、不能慢”，把每个请求都加到它上面是拿下单的可用性换限流的精确，闸门实例上跑一个慢脚本会直接卡住下单。

**本项目**：用户和接口的桶放 `redis-cache`；网关因此新增一个依赖。进程内的表要处理两个问题：**键无界**（容量上限默认 10 万加淘汰）和**并发**（分片加锁）。淘汰不需要“最近使用”的顺序：**补满的桶和不存在的桶没有任何区别，丢掉它不改变行为**，所以先找补满的丢，找不到再随机丢；每个桶多记一个“什么时候补满”，换掉了每次请求都要挪动的链表。一次调用里的几个桶可能在不同分片，按分片号升序加锁，不会死锁。自己写而不用 `golang.org/x/time/rate`：它是单个桶，按键管理、淘汰、和 Redis 版行为对齐都要自己包一层，剩下只有几十行算术；好处是进程内和 Redis 两个实现是同一个算法、过同一组测试，退回时行为一致。

### 4.4 多个桶怎么原子地判断，Redis 脚本里的时间

**问**：用户桶和接口桶两个要同时判断，怎么保证原子？

**要点**：分两次调用时，用户桶扣了、接口桶拒绝，这个请求没被处理却消耗了用户配额，两次调用之间还可能插进别的请求。**一个 Lua 脚本里先都看一遍，都够再都扣**，原子，也只有一次往返。**脚本里用 Redis 的 `TIME`，不用调用方传入的时间**：各网关实例时钟有偏差，时钟快的实例会多补令牌，时钟慢的会把时间戳往回写。Redis 7 起脚本按效果复制，脚本里调 `TIME` 才是允许的。键的过期时间取“从空到满要多久”再加一点：过期的桶等于满桶，和自然补满的结果一样，所以过期不改变行为，只是回收不活跃的键；被内存淘汰同理。

**本项目**（`pkg/ratelimit/redis.go`，设计 4.5）：每个桶一个 hash（`tokens`、`ts`），键 `rl:u:{用户号}:{接口}` 和 `rl:r:{接口}`，网关调用带 20 毫秒时限。限制：脚本一次处理多个键，它们必须在同一个节点，Redis Cluster 下用户桶和接口桶没法靠哈希标签放进同一个槽，用不了；到需要集群时要么拆成两次调用并接受不原子，要么把接口总量改成进程内按实例数均分（设计 4.15）。**改坏验证纠正了一个错误假设**（设计 4.15）：写脚本时我以为 Lua 数字转字符串只保留 14 位有效数字，微秒时间戳（16 位）写进 hash 会丢位，于是加了显式整数格式化并写了测试“钉住”；改坏验证去掉格式化，测试照样通过，因为 Redis 把脚本里的数字参数写入时对整数值本来就按整数格式化，Lua 自己的 `tostring` 确实只有 14 位但没走那条路。结论：格式化保留（不依赖没写进文档的行为），错误的测试和注释删掉。**改坏验证能发现“测试钉住的是一个不存在的问题”。**

### 4.5 Redis 挂了怎么办

**问**：限流用的 Redis 挂了，放行还是拒绝？

**要点**：三种选择，各有后果：

| 选择 | 后果 |
|---|---|
| 放行 | 限流在最需要的时候消失（Redis 往往就是被流量打垮的） |
| 拒绝 | 给网关加了一个单点，Redis 一挂网关全不可用 |
| 退回本地限流器 | 每个实例各算各的，限额变宽（实例数倍）但没有消失，网关也不受牵连 |

连续失败时不要每个请求都去撞一次超时：失败后一小段时间内直接走本地，到时再试一次。这其实就是一个最小的熔断器。

**本项目**（设计 4.6；`pkg/ratelimit/fallback.go`）：选退回本地，失败后 1 秒内不再试 Redis。`Fallback` 一次失败就打开，不数失败率（退回的代价只是限额变宽，不值得为少退回几次去多等几个超时）；调用方自己取消不算主限流器的故障。设计 4.6 预告步骤三会把这个“最小熔断器”换成正式的，实际做出来的是可复用的 `pkg/breaker`（6.4），`Fallback` 至今仍是自己的一次失败即打开（代码里没有引用 `pkg/breaker`）。

### 4.6 客户端地址怎么取

**问**：按 IP 限流，客户端地址从哪来？怎么防伪造？

**要点**：直接面向客户端时用连接的远端地址。前面有代理时远端地址是代理的，真实地址在 `X-Forwarded-For`，但这个头客户端可以随便写。规则：**只有远端地址属于受信任的代理，才看 `X-Forwarded-For`，并且从右往左**，找第一个不属于受信任代理的地址。每一级代理把它看到的对端地址追加在最右边，所以右边的可信，第一个不受信任的地址是“受信任链条之外”的那一跳，它左边都可能是伪造的。取最左边是常见的错误，那正是客户端可以随便写的位置。配错的两个方向：该信没信，所有请求都算在代理地址上，一下就被限住；不该信却信了，攻击者每个请求写一个不同的地址，限流形同虚设还会撑满桶表。IPv6 按 /64 限：运营商通常给一个用户分一整个 /64，主机在里面自己选地址，按单个地址限会被轻易绕开并撑满表。

**本项目**（设计 4.9；`services/gateway/internal/httpapi/clientaddr.go`）：`TRUSTED_PROXIES`（CIDR 列表，默认空）。头里遇到解析不了的值时退回远端地址（链条上有不按规矩写头的一环，它左边不可信）；IPv4 映射的 IPv6 还原成 IPv4，同一个客户端只有一种写法。IPv6 按 /64 这一条只在代码里，设计文档没有写。

### 4.7 客户端库自动重试带来的缺陷

**问**：有没有“客户端库的默认行为和你以为的不一样”造成过问题？

**要点**：命令会不会被重试、时限从哪里来，要去读客户端源码确认，不能假设。go-redis 在读超时后默认自动重试命令（最多 3 次），Lua 脚本也不例外；并且默认不遵守 ctx 的截止时间（要开 `ContextTimeoutEnabled`）。非幂等的脚本被重试，第一次已执行成功只是回复没收到时，第二次看到的是自己刚写的状态。**让操作在语义上幂等，比指望它只被执行一次可靠。**

**本项目**（设计 4.16，1b 起就有的缺陷）：受理的 `Hold` 脚本第一次执行成功、回复丢了，重试看到自己刚写下的幂等键，返回“重复”，带的订单号是这次调用自己的；order 把它当成“以前受理过”，返回订单、**不发落库消息**。用户拿到 202，占用等不到落库，宽限期一过被回收，之后查询 404：订单凭空消失，而且恰好在网络抖动（1 秒的停顿撞上 Redis 读超时）时发生。修法：闸门返回“重复”且订单号等于这次调用刚生成的订单号，按受理成功处理、照常发消息（订单号由发号器保证每次不同，所以相等只可能是自己的占用）。没有去改“客户端不重试”：重试对连接断开有用，而且调用方自己重试时是同样的情形。过了一遍其他脚本：闸门的认领、释放、装载本来就幂等；闸门修正多修一次，之后几轮对账反向修回；分布式锁加锁第二次看到锁被（自己）占着，返回“没拿到”，只影响可用性（leader 晚一个租期才有人接，没改）；令牌桶多扣一个令牌，网关的客户端关掉了重试。

**两个连带的教训**：

- `pkg/redisx` 开了 `ContextTimeoutEnabled` 之后，所有带时限的 Redis 调用行为都变了。`pkg/lock` 的看门狗每 TTL/3 续期、续期的超时也是 TTL/3，这个超时以前不起作用；生效之后测试里 300 毫秒的租期只剩 100 毫秒，CI 上连续超时，锁被判丢，`TestLockOutlivesAcquireContext` 失败。**让一个一直没生效的超时开始生效，等于改了所有带时限的调用的行为**，要预期有这种后果（测试租期放宽到 900 毫秒）。
- 限流时限 20 毫秒不开这个选项的话，Redis 卡住时每个请求要等客户端的 1 秒读超时才退回本地。是子 Agent 用一个只接受连接、从不回应的假服务器验证出来的。

## 5. 熔断与隔离

### 5.1 熔断放进程里的库，还是独立的代理

**问**：熔断和隔离放在业务进程里的库，还是边车、网格？各自能看到什么？

**要点**：

| | 进程里的库（Sentinel、Resilience4j、Hystrix、Polly、gobreaker） | 独立的代理（Envoy、Linkerd、网关） |
|---|---|---|
| 位置 | 调用方进程内 | 服务之间的调用都经过它 |
| 看得到 | 业务含义（哪个 SKU、哪类错误算失败）、进程内部资源（连接池） | 请求的状态码、延迟、连接 |
| 看不到 | 其他调用方的情况 | 不经过它的东西（Redis、MySQL 协议、Kafka、进程内的争用）、业务含义 |
| 好处 | 能做错误比例、慢调用比例、半开单个探测；降级逻辑就在旁边 | 是配置不是代码，所有语言一套，改阈值不重新发布；每个调用方有自己的统计 |
| 代价 | 每个服务、每种语言都要接一遍 | 多一跳（本机每个代理约 0.5 到 1.3 毫秒）；排查多一层；判断粗 |

**本项目**（设计 5.2、ADR-0020）：阶段计划原写 sentinel-go，查证最新正式版 v1.0.4 发布于 2021 年 12 月，五年无正式版，主人不想引入停更的库。在维护的 Go 库（failsafe-go、gobreaker、cep21/circuit）都没有热点参数限流。决定：**服务之间的熔断和并发隔离用 Envoy v1.40.2 边车，每个服务一个**；代理看不到的留在进程里：时限逐跳收紧（只有应用知道上游还剩多少时间）、order 里展示读和落库对连接池的隔离（不是 RPC）、冷库的时限和并发上限（MySQL 协议）、热点参数限流、取消和超时的错误映射、降级逻辑（熔断之后退回哪是业务决定）、Kafka 消费者重试（不经过代理）。边车的位置（调用方一侧出站、被调用方一侧入站）见 5.3。

### 5.2 Envoy 的 circuit breakers 和 outlier detection

**问**：Envoy 的熔断是什么？

**要点**：名字有误导性。**`circuit_breakers` 其实是并发上限**（`max_requests` 是同时在途请求数，超了立刻拒绝），它是隔离/舱壁，不是“根据失败打开”的熔断。真正的熔断是 **`outlier_detection`**：连续 N 次失败把这个实例摘除一段时间。

**本项目的实测**（设计 5.3，Envoy v1.40.2，用镜像加可控的 gRPC 上游实际跑的）：

- 上限 128、发 400 个慢请求：恰好 128 个通过，其余几毫秒内返回 `UNAVAILABLE`（`reset reason: overflow`），尾部带 `x-envoy-overloaded: true`。计在 `upstream_rq_active_overflow` 上，不是 `upstream_rq_pending_overflow`：HTTP/2 下一条连接跑很多流，超的是在途数，不是排队数。（第一版文档和脚本写错了统计项，故障注入脚本第一次运行就失败。）
- 连续 5 次 `INTERNAL`/`UNAVAILABLE` 后摘除，之后 0.2 毫秒返回 `UNAVAILABLE`（`no healthy upstream`），5 秒后放回；杀掉上游同样 5 次连接失败后摘除。
- 业务错误不触发：连续 50 次 `NOT_FOUND` 原样返回，不摘除（gRPC 状态码按对应的 HTTP 状态归类）。

**为什么每个调用方要有自己的统计**：并发上限和摘除的统计是按集群的。所有调用方共用一个代理、按下游分集群，一个调用方把额度用完别的调用方跟着被拒绝。出站放在调用方的边车上，各有各的额度和判断：gateway 查库存把它对 inventory 的额度用完，不影响 order 落库时的预占。这就是服务网格里“目标规则作用在客户端边车”的做法。入站放在被调用方的边车上，只做一件事：这个服务总共同时处理多少的上限，不做摘除（后面只有本机一个进程）。

### 5.3 单实例下摘除不生效，以及另外两个坑

**问**：用 Envoy 做熔断踩过什么坑？

**要点和本项目**（设计 5.3，三个“不查就会踩”的坑，都是实测的）：

1. **每个服务只有一个实例时，默认配置下摘除不生效。** 两个默认值挡着：`max_ejection_percent` 默认 10%（一个实例的 10% 是 0 个）；健康实例低于 50% 时进入“恐慌模式”，无视摘除照常转发。要设 `max_ejection_percent: 100` 和 `healthy_panic_threshold: 0`。默认值是为“很多实例里坏了几个”设计的：那种情况宁可继续往坏实例发，也不要把流量全压到剩下的几个上；只有一个实例时摘除就是熔断，要的正是全部拒绝。将来有了多个实例这两个参数要改回去，否则全部实例都被摘时没有恐慌模式兜底（ADR-0020 后果）。
2. **慢下游只有路由的固定超时能熔断。** 试了三种：只靠调用方自己的截止时间，Envoy 看到的是调用方主动断开，不算上游的错，30 个请求每个都等满 300 毫秒，不摘除；让 Envoy 按调用方的 `grpc-timeout` 头提前超时（`max_stream_duration`），超时生效但同样不计入摘除；**只有路由上写死的 `timeout` 到期才算一次网关错误**，连续 5 次后摘除、快速失败。
3. **`split_external_local_origin_errors` 不能开。** 它把代理自己产生的错误（超时、连接失败）和上游返回的错误分开统计，开着时 30 次连续路由超时一次都没触发摘除，关掉后 5 次就摘。

另外：摘除时间是基数乘以被摘除的次数（实测第二次 10 秒），默认上限按文档 300 秒，杀进程测试里服务被反复杀，所以基数和上限都设 5 秒。路由超时到期时调用方看到的是 `UNAVAILABLE`（`upstream request timeout`），不是 `DEADLINE_EXCEEDED`，区分“下游超时”和“下游不可用”不能只看状态码。**这是“探测出来的行为文档里没有”的典型：每个数都是在本机跑出来的，不是照文档抄的。**

实测验收（设计 5.14，`make fault`）：inventory 被 `kill -STOP` 挂住，查库存前 5 次各约 3 秒返回 503，之后 7 次在 1 到 2 毫秒返回 503，摘除 1 次，期间查订单 20 次全 200、延迟同基线、新订单被受理，`kill -CONT` 后 5.5 秒恢复；并发上限场景同时 300 个请求、上限 128，恰好 172 个被立刻拒绝（不到 500 毫秒），没有一个等满 5 秒；30 次查不存在的 SKU 都是 404，摘除 0 次。前 5 次是 503 不是 504，说明边车的路由超时先到。一个没解释的现象：“杀掉再重启”场景紧跟在“挂住”后跑时，重启后约 30 毫秒就成功了而统计里摘除仍是 1，单独跑是预期的 5.5 秒，可能是提前放回或统计滞后（设计 5.13）。

### 5.4 熔断按什么判断，半开探测

**问**：按连续失败、错误比例、慢调用比例熔断各针对什么？半开怎么做？

**要点**：

- **连续失败 N 次**：针对“整体坏”（连不上、挂起），几毫秒到几秒就数得到，实现最简单；对“偶尔失败”（30% 的请求失败）不敏感，连续失败总被成功打断。
- **错误比例**（滑动窗口内错误数占比）：针对部分失败；要维护窗口，要有最小请求数避免小样本误判。
- **慢调用比例**：针对“没报错但很慢”（拖住调用方的协程和连接），要设“慢”的阈值。
- **半开**：冷却时间到后不是整个放回，而是**只放一个（或少数）探测请求**，成功则关闭，失败则回到打开。好处是对“恢复的一瞬间所有等着的请求一起涌上去”的依赖（比如 Redis）不会被再次压垮。

**本项目**：Envoy 的 `outlier_detection` 单实例下只有连续失败一种，**没有半开时的单个探测**（到时间整个放回，还坏就再连续失败 5 次才再次摘除，摘除时间逐次加长），按错误比例的检测要多个实例互相比较。对“一个下游整体坏了”够用，对部分失败不敏感，这条写进 ADR-0020 后果；若以后需要，在进程里补（备选 gobreaker、failsafe-go）。进程里的熔断器 `pkg/breaker` 自己写了，见 6.4。

### 5.5 超时预算为什么逐跳收紧

**问**：全链路超时怎么设？

**要点**：只有入口一个总时限（如 5 秒）时，中间哪一跳都可以把它用完：order 等 inventory 等满 5 秒时 gateway 也刚好超时，谁都来不及补救，客户端等 5 秒拿到一个 504。规则：总时限只在入口设一次，经 ctx 往下传；**每一跳给下一跳单独设一个更短的时限，从上游剩下的时间里取，不超过它**，让上一跳在下一跳超时之后还有时间处理。没有上游截止时间的调用（消费者、周期任务）自己设总时限。

**本项目**（设计 5.1、5.6）：现状是 gateway 5 秒、gRPC 客户端兜底 3 秒（只在调用方没带截止时间时才加，经 gateway 进来的都带着 5 秒，所以不起作用）。改后：gateway 到任一下游最多 3 秒；order 到 inventory 1 秒；payment 到 order 1 秒；order 到 Redis 闸门 300 毫秒；冷库 1 秒；从库最多 500 毫秒（超时退回主库）；周期任务的 Guard 1 秒。有测试把每一跳的数排出来检查都短于上一跳，并和 Envoy 配置里的路由超时核对。

**两处设时限，但不是同一个数**（本项目一个值得讲的设计缺陷，设计 5.6、5.13）：Envoy 的路由超时是这一跳的预算，进程里（`grpcx.WithHopTimeout`）的时限比它长 500 毫秒（`grpcx.SidecarMargin`），只做兜底，保证边车不在（直连）或卡住时调用方仍会放手。第一版设计写的是“两处同一个数”，这是错的：进程里的计时器先启动，两个数相等时总是调用方先放手，边车看到的是“调用方断开”，不计入异常检测，慢下游永远不被摘除（和 5.3 的坑 2 是同一件事，设计时没连起来，是 gateway 的子 Agent 指出的）。后果：下游超时时调用方正常看到边车返回的 `UNAVAILABLE`（gateway 映射 503），只有边车不在时才是进程里的 `DEADLINE_EXCEEDED`（504）。

**注意**：`AGENTS.md` 的工程规范里仍写着“同一个数也写在 Envoy 边车的出站路由上，两处要一致”，和上面的结论（进程里 = 边车 + 500 毫秒）不一致，面试时以设计 5.6 和代码为准。

**时限收紧带出来的问题**（设计 5.13）：闸门调用的时限 300 毫秒，比原来实际生效的 1 秒（Redis 客户端的读超时）紧得多，一次 TCP 重传（约 200 毫秒）之内能过，连丢两个包或突发时等连接池就会超，超时的下单返回 503、客户端带同一个幂等键重试；`Hold` 超时后的清理和 `Hold` 本身可能乱序（`Hold` 的包在重传，清理走另一条连接先到，看到“没有占用”，随后 `Hold` 成功），留下一个没有落库消息的占用，要靠回收任务收走，修法要改闸门（清理时写短期“已放弃”标记），没做；预热被这一跳的 1 秒封顶了（它原来是 3 秒）。

### 5.6 重试放大、重试规范、退避

**问**：重试有什么风险？怎么规范？

**要点**：每层重试 3 次，三层就是 27 次，下游刚恢复就被重试的洪水再次打垮（**重试风暴**）。规则：

1. 只重试幂等的操作；不幂等的要么先改成幂等，要么不重试。
2. 一条调用链上只有一层重试。
3. 退避加抖动，否则同时失败的请求会同时重试。
4. 重试要有上限，耗尽后的去向要明确（死信、返回错误、留给周期任务）。
5. 客户端库可能自己重试，要先确认（4.7）。

**本项目**（设计 5.6，写进了 `AGENTS.md`）：同步链路上不重试（进程里不重试，Envoy `max_retries: 0`），由客户端带幂等键重试；异步的由消费者重试。系统里的重试逐处：Kafka 消费者原地重试（指数退避，原来没有抖动，加上）；数据库死锁重试（`pkg/retry`，带抖动）；Redis 客户端自动重试（步骤二查明）。重试上限的例外见 6.3（消费者对普通错误不设上限，因为每条消息都有终点）。

### 5.7 取消、超时、本跳超时怎么区分，499

**问**：调用方取消和超时怎么区分？为什么客户端断开记 499？

**要点**：**判断依据是 ctx 的状态，不是错误的类型**：驱动在超时后返回的错误五花八门（Redis 客户端返回网络层的 `i/o timeout`，MySQL 驱动连接被关掉时返回 `invalid connection`）。每一跳自己的时限用带原因的超时（`context.WithTimeoutCause`），事后看 `context.Cause` 是不是这一跳自己的时限；请求自己的 ctx 出了错则以它为准。三种情况对外：调用方取消 → `Canceled`（不记日志）；到了截止时间 → `DeadlineExceeded`（WARN）；本跳的时限（依赖慢）→ `Unavailable`（WARN）。**客户端主动断开用 499**（Nginx 的约定，不是标准状态码）：它不是服务端的错误，不记 ERROR，统计可用性时排除（ADR-0020 后果）。这样按错误级别告警不被客户端的行为淹没。

**本项目**（设计 5.9、5.13）：1b 遗留的“调用方取消被记成 ERROR、返回 `Internal`”（order、payment）和 gateway 对客户端断开返回 500 并记 ERROR 在这里一起改掉。**合并回源时别人的取消不能当成自己的结果**：查询缓存把同一订单的并发回源合并成一次，发起回源的调用被取消时，搭便车的调用靠 `errors.Is(err, context.Canceled)` 认出“这是别人的取消”并自己重新回源，所以 order 返回的取消错误必须还能解包出 `context.Canceled`，只返回一个普通 gRPC 状态错误的话它们会把别人的取消当成自己的结果。没改的：`grpcx` 服务端日志拦截器对 `DeadlineExceeded`、`Unavailable` 仍记 ERROR，按错误级别告警时调用方超时仍会响。

### 5.8 舱壁隔离，热点参数限流

**问**：什么是舱壁隔离？热点参数限流和按接口限流有什么区别？

**要点**：**舱壁**（名字取自船的水密隔舱）：给一类调用单独划一份资源上限，同时最多 N 个，多出来的**立刻拒绝而不排队**（排队等于把上限从“同时在用的”变成“在用的加在等的”，后者没有上限）；一个舱进水不淹到别的舱。典型用法：给写路径留数据库连接，让展示读和后台扫描不能把连接池占满。**热点参数限流**：按接口限流是一个接口一个桶，热点参数限流是这个接口下**每个参数值**一个桶（某个 SKU 被集中访问、某个大商家的订单列表被集中翻），能防“一个 SKU 把整个接口的容量占满”，接口级的限流看不到。

**本项目**（设计 5.7、5.8、5.13）：

- `pkg/bulkhead`：不排队的计数信号量，原子加一后判断，超了就退回去（不用“先读、够再加”，两步之间别的协程也在加）。order 展示读对每个订单库的并发上限 16（连接池 25，给落库留 9 个）；冷库并发上限 8（连接池 10）加 1 秒时限。冷库没有熔断器（走 MySQL 协议不经过 Envoy），时限加并发上限已经把它能占用的资源封了顶，不值得单独写熔断器（步骤四又给冷库加了熔断器，让旧订单查询在冷库不可用时快速失败，见设计 6.8、6.16）。名额满返回 429、原因码 `READ_BUSY`，没有 `Retry-After`。**上限只限主库不限从库**：目的是给写路径留主库连接；从库读超时退回主库的那次占主库名额，所以坏掉的从库不会把主库的查询推过上限。
- 热点参数限流在 gateway，复用 `ratelimit.Local`：`getStock` 按 `sku_id` 每个 SKU 每秒 500、桶 1000；`listMerchantOrders` 按 `merchant_id` 每个商家每秒 50、桶 100；可给个别值单独设阈值；状态在进程里，热点保护要的是“别让一个 SKU 把这个实例占满”，不需要跨实例精确。下单按 SKU 的热点限流不做：闸门已经按 SKU 原子放行。路径里的 ID 接受 `007`、`+7`，所以限流按解析后的整数计数，不能靠改写法绕过。

### 5.9 雪崩的传导过程

**问**：一个下游变慢，怎么演变成整个系统雪崩？怎么防？

**要点**：传导链是：下游变慢 → 调用方每个请求等满超时，占着协程和连接 → 调用方的线程池/连接池耗尽，连它自己的其他接口也不可用 → 调用方的调用方同样被拖住 → 重试放大流量（5.6）→ 下游一恢复就被洪水打垮。防线对应每一环：时限逐跳收紧（别等满）、并发上限（别把资源占满，舱壁）、熔断（已经知道它坏了就快速失败）、降级（快速失败之后给用户什么）、重试规范（别放大）、限流和背压（别让入口流量压垮）。**只有时限没有熔断时，坏掉的下游每个请求都要等满超时**，所以 `make fault` 的验收是“前 5 个请求各花 3 秒，之后毫秒级失败，别的接口完全不受影响，恢复不需要人干预”。

**本项目**：设计 5.1 的三个问题（没有预算只有总数、一个下游变慢拖住每个调用它的请求、没有按参数的保护）正是上面这条链上的三环。

## 6. 降级

### 6.1 降级和熔断是什么关系

**问**：降级和熔断的区别？

**要点**：熔断是**机制**，依据失败统计自动判断“这个依赖现在不能用”，目的是保护调用方，别再为一个坏的依赖每次等满超时；降级是**策略**，回答“不能用之后，这个接口对用户是什么表现”。熔断打开之后可以降级（返回缓存、返回部分结果、拒绝），也可以什么都不做（直接报错）。降级的触发也不只有熔断：人工开关、过载保护都可以。降级的结果要么精确、要么明说不完整，不悄悄返回可能有错的数据。

**本项目**（设计 6.2 的六条原则）：不受理落不了库的订单；依赖不可用时消息留在分区里等，不进死信；坏掉的依赖只付一次超时；可选依赖不挡启动；降级的结果精确或明说不完整；自动降级和人工开关走同一条路。

### 6.2 闸门（Redis）不可用：为什么拒绝下单，不退回数据库扣减

**问**：库存缓存挂了，为什么不退回数据库扣减？

**要点**：退回数据库听上去稳妥，难点在切回来。

1. **扣减有了两个权威。** 退回期间卖掉的数量闸门不知道，恢复后闸门里的数是旧的，必须先按 MySQL 重新装载才能再用；恢复的 Redis 里还可能留着故障前受理、没落库的占用，装载时要算进去。做错就是超卖。
2. **“Redis 不可用”是每个实例各自的判断。** 一个实例连不上 Redis（网络分区）、别的实例正常，前者在 MySQL 同步扣减、后者继续用闸门，同一份库存卖两次。要避免就得有所有实例一致的模式开关，切换还要围栏，这是另一个一致性问题。
3. 本项目 MySQL 已经不阻止超卖（2.3），退回要恢复同步条件更新，还要先把未应用增量应用完。
4. 退回的路容量很小（同步扣减是几百单/秒，热门 SKU 上是行锁排队），秒杀流量下即使退回成功，绝大部分请求还是要被拒绝。
5. **让 Redis 高可用是更直接的办法**：主从加自动切换把不可用压到十几秒，这段时间拒绝下单，为此维护第二条扣减路径不划算。

真实系统里两种做法都有：有独立降级扣减路径的，通常是配置中心下发的全局开关加切换预案（停受理、排空、切模式、重新预热），是**人工的全局开关，不是自动的**。这里作为备选记在 ADR-0021。

**本项目**（设计 6.4、6.18，ADR-0021）：阶段计划原写“退回数据库扣减并收紧限流”，2026-11-14 改成“拒绝下单，其余照常，已受理的订单等 Redis 恢复后继续落库”。各路径：受理在熔断器打开后立刻 503（`STOCK_GATE_UNAVAILABLE`，带 `Retry-After`），打开前几个请求各等一次 300 毫秒；排队的订单留在 Kafka，落库消费者停在 `Claim` 上重试；已落库订单的查询照常，没落库的 503（分不清排队还是不存在）；取消、支付、关单照常；闸门对账不跑（它的正确性依赖互斥，宁可不跑）。故障注入：暂停 Redis 30 秒，52 次下单头 8 次之后 44 次全 503，p50 3 毫秒；慢的 5 次是每 5 秒一次的半开探测（最大 313 毫秒）；156 次已落库订单的查询全部 200；恢复后 4.1 秒下单成功，暂停前受理的订单全部落库，死信 0，被回收的占用 0。代价（ADR-0021）：闸门的 Redis 是下单的单点；故障时间会吃掉支付窗口，超过支付时限的直接失败。

**恢复的次序问题**（设计 6.4、6.16）：Redis 恢复后，**回收任务和消费者会抢同一批订单**。回收按“受理了多久还没被认领”判断孤儿，故障期间这个时钟一直在走而消费者一直认领不了；不等这一下，回收任务抢赢了订单就没了。所以闸门恢复后的半个宽限期（30 秒）内不回收，队列上限 1 万、落库每秒 600 到 800 单，够排空。这个等待有两个来源：闸门熔断器恢复的时刻，以及回收任务自己上一轮列占用失败后第一次成功的那一轮（熔断器是被调用喂出来的，一个只跑周期任务的实例每 10 秒才访问一次 Redis，短于 50 秒的故障数不到连续 5 次熔断器不会打开）；两个来源都是本进程的见闻，消费者在别的实例而只有那个实例连不上 Redis 时，回收所在实例看不到，不会等。另一个次序问题是**故障期间没写上的标记留下的空白**：读己之写的标记写不进去只记日志（1c 的决定），Redis 恢复后这些订单的展示读会被当成“没有标记”而去读从库，所以熔断器恢复后的一段时间内（标记最长保留时间）展示读一律读主库；`window` 模式等 pin 的 3 秒，`gtid` 模式等 1 分钟，也就是 `gtid` 模式下闸门每恢复一次有 1 分钟展示读全落主库（受每库 16 的并发上限约束）。

### 6.3 不受理落不了库的订单，死信该收什么

**问**：为什么受理端要知道下游的健康？死信队列该收什么？

**要点**：用户拿到 202 之后订单消失或必然失败，比一开始就拿到 503 糟糕：前者用户以为下单成功了。受理之前就知道落不了库（闸门不可用、落库在持续失败），直接拒绝。

**死信该收“消息本身有问题的”**。死信的用处是把坏消息挪开让分区继续；依赖不可用时每条消息都会失败，挪开一条没用，后面照样失败，全部挪进死信之后，一次会自己恢复的故障变成了要人逐条重放的数据问题，而重放之前数据是不一致的（比如闸门里的占用没人归还）。所以依赖不可用时消息留在分区里等，让分区停住等依赖恢复。**代价**：没识别出来的坏消息会一直挡住分区，只能靠消费积压告警发现。判定方向要选对：让 handler 把“数据本身不对、重试也不会成功”标成不可重试（`Permanent`）直接进死信，比反过来枚举“哪些错误算依赖不可用”更安全，后者漏掉一种就是把正常消息送进死信，涉及资金和库存的消息宁可挡住分区。

**本项目**（设计 6.5、6.16，ADR-0021）：

- **落库健康**：order 每个订单库一个熔断器，由落库结果喂它；打开时订单号落在这个库的下单在 `Hold` 之前就 503（`ORDER_LANDING_UNAVAILABLE`）。inventory 坏了所有库都打开，一个订单库坏了只有它的用户受影响。半开的探测不用另外发（消费者本来就在重试排队的消息）；没有排队消息时放一个下单请求进来当探测。每个实例自己的判断，没分到分区的实例看不到落库结果，兜底仍是闸门里的背压。场景 L：inventory 挂住期间持续下单 20 秒，56 次下单只有头 8 次里的 7 个 202，之后 49 次都是 503，最大 6 毫秒，恢复后那 7 个全部落库；不再出现“202 之后失败”。
- **什么算“落库成功”要收紧**：第一版写“处理完成算成功”，但 inventory 坏着时被 sweeper 置为失败的订单，它的消息下一次重试会正常结束（看到终态什么都不做），这算成功会把熔断器错误关上，受理放开，新订单接着失败。改成只有这次处理真的调用了 inventory 并得到回答才报告成功。
- **闸门的故障不记到落库健康上**：闸门有自己的熔断器，两个都记，对外原因码取决于谁先检查，而且 Redis 恢复后还要多等一次探测。
- **探测的结果不一定回得来**：多实例时探测消息的分区可能在别的实例上，熔断器会一直停在半开。做法：探测发出后一个冷却时间内没有失败报上来就当它成功；失败会重新打开，之后“当它成功”不再起作用（熔断器的代号机制，见 6.4）；第一版用定时器，改成下一次受理时顺带检查，没有新的下单请求时停在半开也没影响。
- **落库的重试不设上限**（原来 10 次约 26 秒后进死信）：不设上限不等于永远重试，每条消息都有终点（认领不了的等闸门恢复；订单行已写、一直预占不了的由 sweeper 在 1 分钟创建超时后置为失败，消费者下一次重试看到终态结束；认领了而订单行写不进去的订单库恢复后写入）。原来的做法下最后一种进死信，占用已认领却没有订单行，回收任务不会自动归还，用户看到 `CREATING` 持续到支付时限的两倍。inventory 和 payment 的订单事件消费者同样改了。
- **不设上限的前提是标出 `Permanent`**：子 Agent 逐个检查两个消费者的普通错误，找出重试永远不会成功的几种，以前最多挡 5 分钟（inventory）或 1.5 秒（payment）后进死信，现在会永久挡住。inventory 的两种（预占的状态值不认识、已预占却没有明细）已改成直接进死信。没改的（设计 6.17）：闸门 Lua 脚本运行时出错和“Redis 连不上”分不开，数据损坏时会一直重试；payment 读支付单的扫描错误同样。

### 6.4 熔断器状态机

**问**：讲一下熔断器的状态机。半开为什么只放一个探测？

**要点**：

```
        连续失败 N 次                 冷却时间到
关闭 ───────────────→ 打开 ───────────────→ 半开
 ↑                      ↑                     │
 │                      └──── 探测失败 ───────┤
 └──────────────────── 探测成功 ──────────────┘
```

- **关闭**：放行，数连续失败，成功一次清零。
- **打开**：不放行，调用方立刻拿到 `ErrOpen` 去走降级。
- **半开**：只放一个请求去探测，其余仍不放行；成功回关闭，失败回打开。只放一个是因为依赖刚恢复时可能还很脆弱，所有等着的请求一起涌上去会再次打垮它。
- **过期的结果怎么作废**：每次状态变化换一个代号（generation），`Allow` 放行时记下当时的代号，结果回来时代号变了就丢弃：那是上一个状态里发出去的调用，它的结果不该影响现在的状态。
- **哪些错误不计入失败**：依赖返回的错误和本跳的超时算；调用方自己取消、上游的截止时间先到了不算（那是调用方的事，说明不了依赖的状态，和 5.7 判断取消的规则相同）；业务结果（库存不足、订单不存在）不算。探测如果是“不算”的结果，要把探测名额让出来。
- 一个丢失的探测不能把熔断器永远卡在半开：探测超过一个冷却时间没有结果就再放一个。

**本项目**（设计 6.3、6.14；`pkg/breaker/breaker.go`）：自己写，约 150 行（实现 330 行含指标），默认连续 5 次、冷却 5 秒，和边车摘除参数一致；理由是状态机本身是考点，需要的只有连续失败和半开单个探测，现成库（failsafe-go、gobreaker）功能更全但用不上。按连续失败不按比例：这里保护的依赖坏起来是整体坏（连不上、挂起），连续失败几毫秒到几秒就数得到；按比例要维护滑动窗口，对付的是“30% 失败”，这里没遇到。用 `testing/synctest` 控制时间测试，半开时并发 100 个请求只有 1 个被放行。

### 6.5 降级的错误为什么不能用 UNAVAILABLE

**问**：降级时返回什么错误码？怎么区分“我不行了”和“我的依赖不行了”？

**要点**：**调用方的熔断/边车会把 `UNAVAILABLE` 算成这个服务自己的失败**。闸门的 Redis 坏了，下单请求全部被 order 拒绝，如果拒绝用的是 `UNAVAILABLE`，秒杀流量下连续 5 个下单请求之后 gateway 的边车就把 order **整个摘掉**5 秒，查询、取消、支付跟着快速失败：“拒绝下单、其余照常”变成了全挂，而且是保护机制自己造成的。区分“这个服务不行了”（`UNAVAILABLE`、`INTERNAL`，被摘掉是对的）和“这个服务是好的，它的一个依赖不行了或功能被关掉”（用 `FAILED_PRECONDITION` 加降级原因码，边车归为 4xx 不计入摘除）。网关按**原因码**而不是状态码映射成 503 加 `Retry-After`。

**本项目**（设计 6.16，`errx.Degraded`，已写进 `AGENTS.md`）：这个问题在这一步之前就存在（`Hold` 超时本来返回 `UNAVAILABLE`），设计时只想了“对客户端返回 503”，没想服务之间的状态码。payment 调 order 失败原来回 `UNAVAILABLE`，同样改成降级错误（`ORDER_UNAVAILABLE`），否则 order 坏了会连累 payment 被 gateway 摘掉。**“FAILED_PRECONDITION 不计入摘除”是按 Envoy 的状态码映射推断的**（5.3 实测过的只有 `NOT_FOUND`），要由故障注入证实：场景 F、G 里闸门不可用、持续下单的同时，查订单全部成功，gateway 边车上 order 的摘除次数增量是 0。同理，背压和限流用 429 不用 503，是有意的削峰不是故障，`grpcx` 把 `UNAVAILABLE` 记为 ERROR 会淹没真正的下游故障（1b 笔记 2.7）。

### 6.6 人工开关和自动降级走同一条路径

**问**：降级开关怎么设计？

**要点**：**人工关掉一个功能，等于把它的熔断器强制打开**，自动降级和人工开关走同一条代码路径，这样降级路径平时就有人走，不会到用的时候才发现是坏的。

**本项目**（设计 6.9、6.16；`pkg/degrade`）：每个服务一组有名字的开关，取值 `auto`（默认，是否降级由熔断器或探测决定）和 `off`（强制降级）。第一版还有 `on`（强制不降级），实现时去掉了：它要求每个调用点多一条绕过熔断器的路径，而“依赖坏着却强制去用”没有实际用处。开关：order 的 `admission`、`cache`、`replica_read`、`archive_read`，inventory 的 `cache`，gateway 的 `merchant_orders`、`user_orders`、`stock_query`（返回 503 加 `FEATURE_DISABLED`）。初始值从 `DEGRADE` 环境变量读，名字写错拒绝启动；运行中通过服务内部端口 `GET/PUT /degrade` 修改，只在本进程生效、不持久化。gateway 的开关接口没有鉴权，不能挂在对外端口上，另开只在本机监听的 `ADMIN_ADDR`（默认 `127.0.0.1:8089`）。开关的判断排在所有限流之前，被关掉的请求不消耗用户配额。`GET /degrade` 在有指标之前是唯一能看到“现在哪些东西降级了”的地方，故障注入脚本靠它做断言。局限：多实例要逐个改；缓存没开时不登记 `cache` 开关，`DEGRADE=cache=off` 会让服务拒绝启动。**一个写测试时查出的竞态**（设计 8.15）：开关的指标“先报后改”，两个并发的 `SetMode` 会让指标和实际状态相反，一直错到下一次改动，并发用例约 300 次里失败 1 次，改成在同一把锁里改值和报指标。

### 6.7 部分结果，从库延迟怎么量

**问**：什么时候可以返回部分结果？从库延迟怎么监控？

**要点**：**降级时返回部分结果的条件：返回的每一行都精确，并且明说不完整**。冷库不可用时，按用户列订单：订单号晚于冷热分界（`MinHotAge`，30 天）的行不可能在冷库里，这一段只看热库就是精确的，返回这一段加游标和 `archive_unavailable = true`，客户端可以显示“更早的订单暂时无法查看”，之后用游标接着取；总是带游标，因为冷库不可用时不知道后面还有没有订单，不能说“没有更多了”。这一段为空时返回 503。

**从库延迟**：不要用 `Seconds_Behind_Source`，它是用从库正在回放的事件的时间戳算的，IO 线程断了或落后时它是 0 或 NULL，看上去一切正常。要量读者真正关心的东西：**主库刚才的位置，从库多久能追上**——在主库读当前 GTID 集合，在从库上 `WAIT_FOR_EXECUTED_GTID_SET(集合, 最大延迟)`，追上了就健康，没追上、出错、超时就不健康（也复用了读己之写已有的机制）。

**本项目**（设计 6.7、6.8、6.16）：每个从库一个健康标记，后台每秒探测一次；连续两次通过才恢复，避免在阈值附近来回切；不健康时展示读直接读主库、sweeper 同样；请求路径上读从库出错也立刻标不健康。最大延迟默认 1 秒，**要小于 `window` 模式下 pin 的时长**（延迟超过 pin 时长，`window` 模式会读到自己刚写数据的旧版本）；而且“最大延迟小于 pin”不够，探测每秒一次，延迟在两次探测之间还会涨，所以启动校验改成 `ORDER_READ_MAX_LAG + 探测间隔 < ORDER_READ_PIN_TTL`（1 秒加 1 秒小于 3 秒）。故障注入：停止从库回放 1.2 秒后 `/degrade` 显示不健康，恢复回放 1.8 秒回到健康；暂停一个从库，33 次查询全 200，p50 5 毫秒、最大 6 毫秒。局限：探测量的是 GTID 位置，主库没有新写入时停了回放的从库不会被判为不健康（也没有东西会读旧），场景 I 要停止回放后写一笔才触发。初始状态是不健康：刚启动的实例在连续两次探测通过前（约 1 到 2 秒）展示读全读主库。

### 6.8 缓存的 Redis 挂了

**要点和本项目**（设计 6.6、6.18）：`pkg/cache` 里加熔断器，打开期间读和写都跳过 Redis 直接回源，order 的订单缓存和 inventory 的库存缓存都经过它，不用各改一遍。回源的压力由展示读的并发上限（5.8）挡住，超出的 429；“缓存没了，能打到数据库的查询数不变，多出来的被拒绝”。**故障注入发现并修掉的一个问题**：缓存的 Redis 挂住时熔断器打开之前的每个请求多等约 1 到 2 秒，因为缓存读没有自己的时限，等的是客户端的读超时（1 秒），熔断器要数到连续 5 次才打开；给进入缓存的那次读加了 200 毫秒时限，复测最大延迟从约 1030 毫秒降到约 210 毫秒。闸门调用在步骤三就有 300 毫秒时限，缓存漏了。**教训：熔断器打开之前的那几次调用的耗时，也要受时限约束**，否则熔断只是少付后面的，前面的每个请求仍等满。


### 6.9 熔断器把一次抖动放大成几秒的故障

**问**：你们的熔断器误触发过吗？怎么发现、怎么改的？

**要点**：熔断器要回答的是“依赖是不是坏了”，两类失败不是这个意思，却很容易被算进去。

- **本地排队造成的超时**。连接池满了之后，等连接的时间算在调用的时限里，超时的样子和“依赖没响应”一模一样。排队应该由并发上限挡在前面，不该喂给熔断器。
- **一次性的抖动**。“连续 N 次失败”在高并发下不等于“持续失败”：一次几百毫秒的停顿会让在途的几十个调用同时超时，N 次发生在同一毫秒。光数次数，一次抖动就打开一个冷却期，故障被放大十几倍。解法是给次数加上时间的条件（失败要持续一段时间），或者改成按一段时间里的错误比例。

共用一个连接池的调用方里，只要有一个的量不受控（客户端轮询的查询），就要给它单独的份额，否则它能饿死别人。

**本项目**（设计 8.18，ADR-0021 的补充）：这是埋点做完之后靠指标查出来的，很适合讲“可观测性换来了什么”。

- **现象**：开环每秒 2000 个下单请求，12 次运行里 5 次闸门的熔断器打开，落库在熔断期间重试 380 到 750 次，那一轮吞吐低 15% 到 25%，订单没丢。Redis 的慢日志是干净的。
- **原因一**：order 的闸门 Redis 连接池是默认的 32，受理、落库、回收、查询共用。连接池指标显示在用数一直顶在 32，每轮 3 万到 6.8 万次调用在排队。压测结束后工具集中轮询订单状态，每个查询读一次占用，排队超过 300 毫秒的时限，被算成闸门失败。**查询多了让落库停摆**。步骤三给订单库的连接做了隔离（展示读每库 16 个），闸门的连接漏了。
- **修一**：展示读读占用前先占名额（`READ_GATE_MAX_CONCURRENCY`，默认 16），占不到就只读订单行，不经过熔断器；连接池可配置（`REDIS_POOL_SIZE`），默认 128。修完池子不再打满，但 5 次里仍有 2 次打开。
- **原因二**：剩下的是受理的 `Hold`，十几个调用在同一毫秒一起超时，池子没满，另一个 Redis 容器同时也超时。是一次约 300 毫秒的整体停顿（来自容器网络还是进程没查到）。熔断器数“连续 5 次”，这一下就够了，打开 5 秒。
- **修二**：`pkg/breaker` 加 `MinFailureSpan`，连续失败还要从第一次起持续这么久才打开，闸门设 1 秒。真的不可用时 1 秒后照样打开，代价是这 1 秒里每个调用各自等满时限。
- **结果**：再跑 6 次，停顿还在（每次 0 到 54 个调用超时），熔断器一次没打开，重试每次 0 到 5 次。
- **追问**：为什么不把冷却缩短？那样仍然会打开，只是每次停得短。为什么不改成错误比例？更准，但要维护滑动窗口，这里一个时间条件就够。Envoy 的异常摘除也是数连续次数，多实例之后同样的问题会在那里出现。
- 一个教训：第一次只看了“超时的大多是查询”就下结论说是连接池，修完重跑才发现还有第二个原因。**修复之后要用同样的办法再量一次**。

## 7. 启停

### 7.1 就绪和存活

**问**：K8s 的就绪探测和存活探测有什么区别？就绪探测该不该检查依赖？

**要点**：**存活**回答“进程还活着吗”，失败则重启；**就绪**回答“现在能接请求吗”，失败则从服务的端点里摘掉，不重启。分开的原因是有些状态是“活着但暂时不该接流量”（启动中、正在停止）。**就绪探测不该检查共享的依赖**：Redis 一坏，所有实例同时变成未就绪，负载均衡把它们全摘掉，本来还能提供的查询和支付也没了。就绪只表达这个进程自己的状态，依赖的状态另外暴露（降级状态、指标）。存活探测同理，检查共享依赖会让依赖故障变成整个服务集体重启。

**本项目**（设计 6.11；`pkg/app`）：`/healthz`（存活，进程能响应就 200）和 `/readyz`（所有组件启动之后才 200，开始停止的那一刻起 503，gRPC 健康检查跟着走）。依赖降级不影响就绪，状态在 `/degrade` 里看。gateway 的 `/readyz` 在两个端口上都有，负载均衡要打对外的那个。

### 7.2 优雅停止为什么先摘流再停

**问**：优雅停止怎么做？为什么要先摘流再停？要等多久？

**要点**：K8s 里“给进程发 SIGTERM”和“把这个实例从服务的端点里摘掉”是**同时发生的两件事**，后者要经过端点控制器、各节点上的代理才生效，通常要几秒。进程收到信号就立刻关监听，这几秒里发过来的请求会被拒绝。所以顺序是：收到 SIGTERM → 就绪变 503（继续正常处理请求，留给负载均衡发现）→ 等 `DRAIN_DELAY` → 再按启动的相反顺序停各组件（先把 gRPC 健康状态置为不可用并等在途调用；消费者等在途 handler、提交位点；中继最后发一轮）。**等多久**：比端点传播时间长一点（通常 5 到 10 秒），且 `DRAIN_DELAY` 加停止时限要小于 `terminationGracePeriodSeconds`，否则被 SIGKILL。另外：第二次信号立刻退出，开发时停止过程中再按 Ctrl-C 不该等满超时。

**本项目**（设计 6.11、6.18）：`DRAIN_DELAY` 本机默认 0（单实例没有别处可去，等只是让重启变慢），阶段 2 设成 5 到 10 秒，停止总时限 20 秒；第二次信号取消组件 ctx 立刻放弃。**诚实的局限**：单实例下验证不了摘流，只有 `pkg/app` 的测试（就绪时序：启动完成前 503、收到信号后 503 而请求仍被处理、等待结束后才停止）；零失败的滚动发布要两个以上实例和会看就绪的负载均衡，留给阶段 2。场景 M：带流量给 order 发 SIGTERM，不到 1 秒退出、退出码 0，期间受理的 20 单全部落库，被回收的占用 0。**应用者最后停**（gRPC 的预占、消费者的确认和释放收尾时还在写增量），停了之后再收一次尾，没应用完的留到下次启动也对（读库存的地方都会加上增量）。

### 7.3 哪些依赖坏了该启动失败

**问**：启动时依赖不可用，该失败还是带着降级启动？

**要点**：判据：**运行中坏了能降级的，启动时坏着也应该能起来**；没有它什么都做不了的才启动失败。否则 Redis 故障期间重启或发布的实例起不来，连不依赖 Redis 的查询和支付结果也跟着没了。

| 依赖 | 启动时不可用 |
|---|---|
| 自己的主库、Kafka | 启动失败 |
| 闸门的 Redis（order、inventory） | 启动，受理处于降级状态 |
| 锁的 Redis（payment） | 启动，锁 `FailOpen` |
| 缓存的 Redis、从库、冷库 | 启动，对应功能降级（冷库的建表在后台重试） |
| 下游 gRPC 服务 | 启动（连接本来就是惰性的） |

**本项目**（设计 6.10；`redisx.OpenLazy`、`mysqlx.OpenLazy`）：不因 PING 失败而返回错误，记一条 WARN，连接池在后台建。1b 留下的不一致（payment 运行中 Redis 不可用能放行，启动时却失败）由此消除。场景 N：Redis 暂停时启动 payment 和 order，都能启动（`/readyz` 200），查询 200、下单 503，恢复后 4.9 秒下单成功。**可观测性同样是可选依赖**：见 9.8。

## 8. 对账

### 8.1 要解决什么，Merkle 树省的是什么

**问**：两份各 500 万行的数据，怎么找出不一样的那几行？Merkle 树的优势在哪？

**要点**：直接办法是两边按主键读出来归并着比，代价和差异多少无关，每次要把每一行传过来。Merkle 树的想法是先比摘要，只在摘要不同的地方往下看。但**摘要本身要扫全表才算得出来，所以它省的不是扫描，是传输和比较**；省不省得下来取决于摘要在哪里算：

- 对账工具把行读过来再算摘要：扫描、传输一样没少，还多了一次哈希，**没有任何好处**。
- 数据库自己算，只把摘要传出来：扫描还在，传输从“全部行”变成几千行摘要。

Dynamo、Cassandra 的反熵修复就是这个结构：每个副本在本地建树，副本之间只交换树。应用场景：副本修复、数据校验、对账。要问清楚的是**它在什么数据量和差异率下才有优势**。

**本项目的实测**（设计 7.2、7.12，ADR-0022；`index` 这一对，两侧各 490.8 万行，工具和数据库同机）：

| 差异 | 做法 | 合计（不含复查） | 读回的行（每侧） |
|---|---|---|---|
| 0 | 树 | 4.8 秒 | 0 |
| 0 | 全量归并 | 7.8 秒，545 MB | 490.8 万 |
| 1 行 | 树 | 5.0 秒 | 1495 |
| 93 行，散布 | 树 | 6.6 秒 | 14.1 万 |
| 9612 行，散布（0.2%） | 树 | 10.7 秒 | 464 万 |

- 没有差异时树是归并的六成时间，传输是三千分之一；时间差得不多，因为两边都要扫全表，树还多一次 SHA-256，本机没有网络，传输省下来的不显眼。
- **交叉点取决于差异落在多少个节点里，不是差异有多少行。** 第一遍在 18.6 小时一个节点的层上，共 3231 个非空节点，每个约 1500 行，不超过逐行比的阈值（2000），所以摘要不同的节点整个读回来；9612 行散布的差异打中其中 3053 个，等于把 95% 的行又读了一遍，比归并慢。按这个数推，均匀散布的差异超过约 2000 行（万分之四）树就不如归并。
- **真实的故障很少均匀散布**：消费者漏了一段时间、一次发布写坏了一批，差异集中在几个节点里，代价接近“1 行”那一行。均匀散布的大量差异意味着整份数据要重建，那时不该用对账去找。
- 树的好处要到工具和数据库之间隔着网络、或者一份数据有多个副本要两两比时才显出来。设计里没有预设结论，**量出来的是“本机同机时优势不大，随差异分散度反转”**，面试里这样讲比“树一定更快”可信。
- 行哈希的代价（冷库 482 万行单条语句）：`COUNT(*)` 3.1 秒，`CRC32` 聚合 5.0 秒，SHA-256 聚合 8.5 秒。

### 8.2 为什么摘要用行哈希的和，不是 H(子节点)

**问**：教科书的 Merkle 树和你们的有什么不同？为什么用和，不用 XOR？

**要点**：教科书里父节点 = H(子节点哈希拼接)，给的是**防篡改和包含证明**（改任何一片叶子根一定变，能给出一条路径证明某叶子在树里），代价是摘要和结构绑死：必须先有子节点才能算父节点，两边必须按同样方式切分。对账要的是另外三条，用“节点摘要 = 它下面所有行哈希的和（外加行数）”得到：

1. **与顺序无关**：数据库按什么顺序扫、分几次扫，结果一样。
2. **可以跨分片相加**：两边分片方式不同（订单按用户分 4 个库 8 个 slot，商家索引按商家分 2 个库 4 个 slot，冷库不分片，支付单一个库），同一段订单号的摘要，一边 8 张表各算再加起来，另一边 4 张表加起来；“热库加冷库”只是再加一项。H(子节点) 做不到，它要求两边的行先凑到一起排好序。
3. **任何一层的节点都能直接算**，不需要先有子节点，所以可以从上往下、只在不同的地方才向数据库要下一层。
4. 可以增量维护：加一行加它的哈希，删一行减掉（这一步没用到）。

**和 XOR 的区别**：XOR 下同一行出现两次会互相抵消，和不会（行数也能发现，两道保险好过一道）。pt-table-checksum 用的是 `BIT_XOR`。**放弃的是防篡改**：行哈希的和不抗有意构造的碰撞，也给不出包含证明。对账面对的是程序缺陷和运维失误，不是攻击者；128 位下偶然碰撞概率可忽略；如果以后要和不可信的一方对账（比如外部支付渠道），要重新选摘要。所以 `pkg/merkle` 不是教科书意义上的 Merkle 树，包文档里写明了。

**CRC32 和 SHA-256 做行哈希**：CRC32 快（5.0 秒对 8.5 秒）但只有 32 位，一行改动恰好不被发现的概率是四十亿分之一，乘以几百万行和反复运行后不能忽略。本项目行哈希取规范字符串 SHA-256 的前 128 位，拆成两个 64 位各自对 2^64 取模求和；MySQL 里是 `SHA2(CONCAT_WS('|', ...), 256)`，MySQL 对无符号 64 位整数求和返回精确的 DECIMAL，取模在工具里做。（设计 7.15：MySQL 9.7 已经没有 `MD5()`。）

### 8.3 分桶键怎么选

**问**：叶子按什么分桶？

**要点**：两条路：按主键区间，或按键的哈希。区间的好处：每个节点是主键上的一段，一次主键范围扫描就能算摘要或读出行，**旧数据的节点不再变**（水位线就是“右边若干节点不比”，存下来的旧节点摘要可以一直用），范围条件能裁掉分区。哈希的好处是桶大小均匀；代价是取一个桶的行要扫全表，每个桶里新旧数据混着。区间的代价：**桶大小不均**，所以树不能定深度。

**本项目**（设计 7.3）：订单号是 `41 位毫秒时间 | 6 位机器 | 10 位序号 | 6 位基因`，时间在最高位，树是订单号上的 16 叉基数树，节点是订单号的一个前缀（shift 48 约 18.6 小时、44 约 70 分钟、40 约 4.4 分钟、36 约 16 秒、32 约 1 秒）。造的 500 万单摊在近 7 年里，一分钟不到 2 单；压测时一秒 800 单，差四个数量级，固定大小的叶子要么在旧数据上碎成几百万个一两行的桶，要么在新数据上一个桶几百万行。所以**树不定深度**：摘要不同的节点行数不超过阈值（默认 2000）就逐行比，超过再分 16 份，稀的地方停得早，密的地方走得深。**第一遍不从根开始**：从根开始每下一层都要把不同的区间重扫一遍，差异分散时上面几层每层都近似一次全表扫描，所以直接在 shift 48 上聚合，一次全表扫描、约 3000 个节点，之后只对不同的节点往下走。

### 8.4 一侧没有索引时怎么下钻

**要点**：按键分桶的树要求两边都能按该键的范围取数；一侧没有这个键的索引（商家索引的主键是 `(merchant_id, order_id)`，按订单号的范围取数是全表扫描）时，下钻不能一个节点一条语句，要把**同一层所有不同的节点合成一条语句**（`WHERE order_id >> ? IN (...)`），一层一次全表扫描。数据源自己声明“按键的范围扫描有没有索引”，比对过程据此选做法。

**本项目**（设计 7.5、7.12、7.16、7.17）：第一遍本来就是全表扫描（一张 205 万行的索引表 3 秒）；往下每一层是 4 张表各一次全表扫描（约 3 秒），所以调小阈值不划算。窗口只有 26 小时时 `index` 仍要 0.27 秒（窗口条件只能在全表扫描里过滤，省的是每行的 SHA-256 不是扫描）。给 `merchant_orders_N` 加 `KEY (order_id)` 能全部变成按索引取，代价是索引写入变慢（现在按批写 4.8 万行/秒），没量过没加。另一个坑（设计 7.15）：按订单号删索引行是带锁的全表扫描，修复第一版对每个订单在 4 张表上各发一条 `DELETE ... WHERE order_id = ?`，`REPEATABLE READ` 下给扫过的每一行加锁，CDC 消费者期间写不进这张表；改成先用不加锁的读找出现有的索引行（一批 1000 个订单号一次全表扫描），再按主键逐行删。

### 8.5 两边结构不同的数据怎么对账

**问**：订单和支付单、订单明细和库存预占，结构完全不同，怎么比？

**要点**：**各自投影成同一个集合**。写投影就是把不变式写出来：投影后两边是同样的键加同样的列，不一致就是不变式被破坏。“已释放”投影成“没有这一行”，这样没预占过就失败的订单不会被报成差异。投影里只放整数和状态码，不放时间和浮点（两边精度、时区不一样就白比了）。**拼接的歧义**：`CONCAT_WS` 会跳过 `NULL`，`(1, NULL, 2)` 和 `(1, 2, NULL)` 拼成同一个串；字符串内容里可能出现分隔符。所以 `NULL` 写成一个不会和数字混淆的标记，字符串写成十六进制。投影写错，对账就会漏报或误报。

**本项目**（设计 7.7、7.4；`pkg/merkle/canon.go`）：五对：`replica`（订单主库对从库）、`index`（订单对商家索引）、`payment`（`PAID` 的订单对 `SUCCEEDED` 的支付单，键是订单号，比 `payment_id`、金额、币种）、`stock`（待支付/已付的订单明细对 `RESERVED`/`CONFIRMED` 的预占明细，键订单号加 SKU）、`archive`（热库加冷库对归档前存下来的一棵树，“热加冷”这个集合在归档前后应当不变）。`archive` 的右边是文件，只有节点摘要没有行，所以只能定位到节点（一段时间里的若干订单）不能定位到行；要定位到行得有另一份数据，有商家的订单可以再跑 `index`。`replica` 发现不了主库自己的重复（两侧摘要相同），要靠 `index`、`payment` 这类对面不会重复的对。验收演练：`payment` 一笔金额加 1，报出那个订单 `mismatch`（12900 对 12901）；`stock` 把一个已确认的预占改成已释放，报出该订单明细 `only_left`；`archive` 归档 20717 个订单后三棵树的根都没变，再把冷库一个订单金额加 1，`archive/orders` 报出 1 个节点（1566 行）。

### 8.6 对账遇到变动中的数据

**问**：两边不是同一时刻读的，在途的变化会被看成差异，怎么办？为什么不用一致性快照？

**要点**：三层：

1. **水位线**：只比时间早于 `now - settle` 的数据，过了这个时间绝大多数已是终态不再变。
2. **复查**：水位线以内仍有会变的行，逐行比出来的差异不直接报告，等一段时间把这些键在两边重读，**两次结果相同的才算差异**（和库存对账“连续几轮偏差相同才修”同理）。
3. 主从对比前等从库追上。

**为什么没有一致性快照**：`START TRANSACTION WITH CONSISTENT SNAPSHOT` 只管一个库，对不上两个库的同一时刻。**pt-table-checksum 的办法**是让校验语句本身经复制在从库上重放，天然在同一个位置上执行，要求语句格式的 binlog；CDC 需要行格式，用不了。

**本项目**（设计 7.6、7.15、7.16）：水位线默认 30 分钟（支付时限 15 分钟的两倍），是订单号上的一个上界，纯计算两边用同一个数；复查等 5 秒。第 3 层**没有做**（水位线以内的行很少再变，从库落后的几行由复查过滤）。局限：复查只看第一次报出来的行；**和文件比（`archive`）没有复查**（右边没有行可重读），所以它的热库读主库，并且存快照和比对都要在归档任务不在跑时做，两次扫描之间被搬走的订单会被数两次或一次都没数到。修复时先读热库再读冷库：归档是先写冷库再删热库，这个顺序下正在被搬的订单至少在一边读得到，不会被当成“订单库里没有”而删掉索引行。

### 8.7 增量对账和全量对账

**问**：对账每次都全量比吗？

**要点**：通常的对账只比新数据（T+1 的日切对账就是这样），全量是偶尔做的兜底。**增量防什么**：同步出的错（消息丢了、消费者有缺陷）发生在写入的时候，一个时间段比过一次相等，以后不用再比。**全量防什么**：窗口之前的数据后来被改坏（手工改库、归档搬坏、存储损坏）没有任何信号，只有全量扫描能发现，所以全量不能取消，只能降低频率。**窗口要互相重叠**而不是记“上次比到哪”：重叠的窗口不依赖上一次运行成功，漏跑一次也不会留下没比过的时间段，代价是每段数据被比两三次。**窗口由时间决定，不由树决定**：树解决的是“在给定范围里怎么少传数据找到不同的行”，范围取多大是另一个旋钮；两者配得上是分桶键选得巧（时间窗口就是主键上的一段），按哈希分桶的树做不到，每个桶里新旧数据都有。

**本项目**（设计 7.17，主人提出，补了下界）：`-since 26h` 表示窗口 `[now - since, now - settle)`，`since` 取运行间隔的两倍以上，不记任何状态。建议：每小时 `-since 3h`；每天 `-since 50h`；每周或每月不带 `-since` 做全量。实测：`index` 全量 490.8 万行 4.7 秒，30 天窗口 6.6 万行 0.29 秒，26 小时 9221 行 0.27 秒（受无索引限制，见 8.4）；`archive` 不支持下界。

**把行哈希存进表里的风险**（设计 7.17，讨论过三种，都没做）：应用在终态时算行哈希写进一列，省每行的 SHA-256，但**哈希成了行的一份拷贝，有人直接改了金额而哈希没跟着变时，两边存的哈希仍相等，对账恰好漏掉这种差异**，不要这样做；**生成列（`STORED`）**没有这个问题（哈希永远跟着行走），但一列只对应一个投影，五对投影各不相同，数据到几十亿行、SHA-256 代价显眼时可以给 `replica` 这类同构的对用；存节点摘要（旧时间段不再重扫）和下界是同一个取舍，下界不需要存任何东西；增量维护的树（写入路径或 CDC 更新摘要表）能把扫描也省掉，但摘要表本身是又一份要保证不丢更新的派生数据。

### 8.8 谁是准，能不能自动修

**问**：对账发现差异，自动修吗？

**要点**：**派生数据可以按源重写，钱和库存只报告**。派生数据（索引表）以源（订单库）为准，修就是重写；涉及钱和库存的没有哪一边天然正确，自动修可能把错的覆盖成另一个错的；从库被改坏说明有人绕过了只读保护或复制出了问题，正确处理是查原因、重建从库。修复要带条件（“源此刻的版本号不低于派生表里的”），修复期间源又变了不会把派生表写回旧值。

**本项目**（设计 7.8）：默认只报告；只有 `index` 能 `-repair`，缺的和不同的按订单库的映像重写，多出来的删除，只对复查后仍不同的键、逐行、带版本号条件。1 行 0.35 秒，93 行 1.2 秒，9612 行 41 秒（每个订单约 4 毫秒，主要是在 8 张热表和冷库里逐个按主键重读）。版本号写入条件是“不低于”，索引里版本号比订单库还高时修不动，留在“未修好”里要人看。

### 8.9 对账放哪，和 `reconcile`、`load verify` 的关系

**要点和本项目**（设计 7.1、7.7、7.9、7.10）：

- `pkg/merkle` 纯计算，不碰数据库；`services/recon` 是单独的批处理命令，要连所有服务的库，不属于任何一个服务，阶段 2 是 CronJob。
- **闸门（Redis）对 MySQL 的库存不用这个工具**：键只有 SKU 那么多，逐个比代价本来就小；数一直在变，没有“已定型”的部分，水位线用不上；它现在的做法（逐个比、连续 3 轮偏差相同才修）是对的，套树是为了用而用。阶段计划把它列在对账对象里，这是和计划不一致的有意决定。
- `load verify` 是压测后、系统静止时的全面检查，带客户端账本，不合并；`recon` 是运行中对全量数据比对；`scripts/chaos.sh` 在 `load verify` 之后加跑一次 `recon`，两套检查互相印证。
- 仍是每张表一次全表扫描，**跑在从库上**（订单库默认连从库），没有从库的库（冷库、索引库、支付库、库存库）直接承受；第一遍按订单号分段执行，不在一个库上开几十秒的长查询。取订单号范围用 `ORDER BY ... LIMIT 1` 不用 `MIN`/`MAX`（`stock` 的数据源是连接，`MIN`/`MAX` 会把整个连接算一遍）。

## 9. 可观测

### 9.1 链路上下文怎么传播

**问**：跨服务的链路怎么串起来？

**要点**：W3C `traceparent` 头四段：版本、trace-id、parent-id（上游 span）、标志位（含**采样位**），固定 55 个字符，如 `00-<32 位十六进制>-<16 位十六进制>-01`。传播靠在调用方把当前 span 的上下文注入请求头（gRPC 的元数据、HTTP 头、Kafka 的消息 header），被调用方取出来当作父。`tracestate` 带厂商私有信息，`baggage` 带跨服务的业务键值。中间的代理要原样转发。

**本项目**（设计 8.3、8.4）：全局传播器是 W3C `traceparent` 加 `baggage`；资源属性 `service.name`、`service.instance.id`、`service.version`；导出只用 OTLP（gRPC），地址和采样用 OTel 规范的标准环境变量，不自己发明名字。**经过两个 Envoy 边车**没配链路追踪时 `traceparent`、`tracestate`、`baggage` 原样转发（实测：自己起一个 gRPC 服务端打印收到的元数据，经 gateway 和 inventory 两个边车，三个头都在，只多出 `x-request-id` 和 `x-forwarded-proto`），这是实现的第一件事，决定 gRPC 这一跳的做法成不成立。`otelgrpc` v0.72 已经没有拦截器的接法，只有 `NewServerHandler`、`NewClientHandler`，加在 `grpcx.Listen`、`grpcx.Dial` 里；MySQL 用 `otelsql`、Redis 用 `redisotel`，所有客户端构造集中在 `pkg/` 所以接入点很少。

### 9.2 异步一跳：父子还是 link

**问**：经过消息队列的一跳，消费者的 span 是生产者的子 span，还是 link？

**要点**：

- **父子**：一条链路看到一个业务动作的全过程，在 Kafka 里排了多久是两个 span 之间的空隙。
- **link**：消费者开一条新链路，只带一个指向生产者 span 的引用；每条链路都短、都很快结束，要看全过程得在后端里跳转。
- 判据：**是不是同一个业务动作的延续**。同一动作的延续用父子；批处理（一个 span 只能有一个父，批里有很多消息）和延迟触发（给一条早已结束的链路在 15 分钟后再添 span，后端按“链路已结束”做的处理——尾部采样、聚合——都会出错）用 link。

**本项目**（设计 8.5、ADR-0023）：受理到落库、订单事件、支付结果用父子；延迟关单用 link；orderindex 按批消费一个 span link 到各条消息（上限 32 个），实际上这些消息来自 CDC 本来就不带上下文；进死信的消息原样带着 header，死信里还能找回它的链路。CDC 的一跳不传递（binlog 里没有地方放上下文，除非给每张表加一列）。

### 9.3 链路怎么穿过本地消息表

**问**：outbox 的中继是后台循环，链路在这里断开怎么办？

**要点**：中继发消息时的 ctx 和当初写这一行的请求毫无关系，上下文**只能跟着数据走**，而数据在表里：给 outbox 加一列存 `traceparent`，写业务变更时在同一个事务里写入，中继发布时原样放进消息 header，消费者看到的父 span 就是写 outbox 的那个 span，中继的延迟表现为空隙。不加列的替代办法是靠 span 上的 `order_id` 属性在后端搜，能找到同一订单的几条链路但没有先后和因果，也没法自动算“从下单到完结”的耗时。**没有采样的也要写**：采样位就在 `traceparent` 里，不写的话下游会各自重新抽签，低采样率下多出一批只有后半段的链路。

**本项目**（设计 8.6）：`outbox` 加 `trace_context VARCHAR(64) NULL`，`outbox.Add` 从 ctx 取。代价：一次表结构变更（order 每库一张、payment 一张，加可空列是 INSTANT 的）；MySQL 没有 `ADD COLUMN IF NOT EXISTS`，迁移里先查 `information_schema` 再决定 `ALTER`，中途被杀可重跑；原来“迁移文件里的建表语句和 `outbox.Schema` 逐字一致”的测试改成比数据库里实际的表结构。每行多 55 字节。**支付结果的链路要自己开头**（设计 8.15）：e2e 第一次跑出来，支付结果的链路是从“中继发消息”才开始的，因为出结果的是 payment 的后台处理器，ctx 里没有 span，`outbox.Add` 存不下上下文；处理器在出结果的地方开一条链路（`payment.complete`）。规则：后台循环里的一步如果是一个业务动作的起点，就在那里开头；这是业务代码里唯一手工建 span 的地方。所以**一个订单是三条链路**，不是一条：下单（约 70 个 span）、发起支付、支付结果，延迟关单是第四条用 link 指回下单，靠 span 上的 `app.order_id` 关联。

### 9.4 重试时的 span

**问**：消息重试时，一条消息一个 span 还是每次尝试一个？

**要点**：**每次尝试一个 span**。span 结束了才会被导出，整条消息一个 span 的话，分区停住的那段时间里什么也看不到，恰好是最需要看的时候。每次尝试的属性带第几次、消息在 Kafka 里排了多久。

**本项目**（设计 8.4、8.5）：ADR-0021 之后消费者对普通错误不设重试上限，一条消息可以重试几分钟，所以必须如此。

### 9.5 采样

**问**：头部采样和尾部采样的区别？为什么尾部采样只能在 Collector 里做？`ParentBased` 是什么？

**要点**：**头部采样**在链路开头（入口）按比例决定，写在 `traceparent` 的标志位里，后面每一跳跟着这个决定；便宜，缺点是出错的那条恰好没采到。**尾部采样**等一条链路的 span 到齐再决定留不留（只留出错的和慢的），**必须在能看到整条链路所有 span 的地方做**，各服务进程只看得到自己那段，所以只能在 Collector（或后端）里做，要缓存整条链路直到判定。**`ParentBased` 采样器**：有父 span 时跟随父的采样决定，没有父才用根采样器（如按比例）；于是**一条链路要么完整要么没有**，不会出现只有后半段的链路。

**本项目**（设计 8.7、8.16）：`ParentBased(TraceIDRatioBased(r))`，gateway 在入口决定；本机 `make run` 默认 100%，`bench.sh` 默认 1%；没被采样的请求仍有 trace id、仍传播，只是不记录属性、不导出；尾部采样是阶段 3 的事。**一个自定义采样器**（设计 8.4）：Redis 和 MySQL 的后台循环每秒都在查，不加处理会产生一堆孤立的根 span。MySQL 用 `otelsql` 的 `SpanFilter`（没有父 span 的语句不出 span）；`redisotel` 的过滤器拿不到 ctx，做不到，改由采样器：`otelx` 在环境变量选出的采样器外面包一层，没有父 span 的 CLIENT span 一律丢弃，代价是采样器环境变量由 `otelx` 自己解析、只认规范里的六个名字（SDK 只在没有显式传采样器时才读）。

### 9.6 对外入口为什么不信任外面带来的 traceparent

**问**：入口服务收到带 `traceparent` 的请求，应该接着用吗？

**要点**：对外的入口**不能信任**：任何人都能把自己的 span 接到你的链路上，还能用采样位（标志位）强制你对他的请求全量采样，等于给外部一个放大你的存储和开销的把手。所以不当成父 span，只记成 link，入口自己决定采样；响应里返回 `X-Trace-Id`，压测工具和排查时用它找链路。内部服务之间则必须信任并接上。

**本项目**（设计 8.4、ADR-0023）：gateway 的 `traceEntry` 中间件自己建入口 span，span 名用路由模板（`POST /api/v1/orders`，不带订单号），没匹配路由的叫 `GET unmatched`。**为什么没有用 `otelgin`**（起草时写的是用，读 v0.72.0 源码后去掉，四处对不上且没有选项可改）：没有“公共入口”的选项，外面来的 `traceparent` 一律当父；它的指标带 `server.port` 标签，值取自请求的 Host 头，客户端随便写一个端口就多一条时间序列（**取自请求的值进标签 = 基数被客户端控制**）；`client.address` 用 gin 的 `ClientIP()`，默认信任所有代理；所有 5xx 和所有被取消的请求都标 Error，降级的 503 和客户端断开的 499 也在内。绕开四处之后它只剩“建一个 span”，所以自己建，几十行。降级响应靠 `writeDegraded` 在 gin 的 context 里设的键来认，不靠状态码猜（下游真的不可用时也是 503，那个要标 Error）。

### 9.7 指标的标签基数

**问**：指标标签能放用户号、订单号吗？

**要点**：**不能**。指标的每一种标签组合是一条独立的时间序列，在进程里和后端里各占一份内存；按用户号打标签，序列数就等于用户数（高基数会撑爆后端）。标签只能是有限的枚举（结果、原因码、规则名、topic）。高基数的东西放 span 上：链路里每个 span 是独立的记录，没有这个问题，而且按订单号找链路是最常用的入口。同类陷阱：路由未匹配的请求用原始路径当标签（扫描器能造无数种路径），取自请求头的值（Host 里的端口）进标签。**直方图的桶边界要对着被量的东西定**：SDK 默认的边界是给秒级的 HTTP 请求定的，Redis 一次调用不到 1 毫秒，全落在第一个桶里；本项目用 View 给耗时类仪表统一设一组 0.5 毫秒到 10 秒的边界，不用指数直方图（阶段 3 后端的支持要另外验证，不引入这个变数）。

**本项目**（设计 8.8、`AGENTS.md`）：订单号、用户号、SKU、IP、请求路径原文、trace id 一律不进标签；span 上放 `order_id`、`user_id`（`otelx.SetOrder`、`otelx.SetUser`）。所以阶段计划里的“库存扣减数”是总数不分 SKU。HTTP 指标标签只有方法、路由模板、状态码。加指标的规则：不改业务行为，不为了指标新增数据库或 Redis 查询（所以 `order.gate.unclaimed_holds`、`inventory.stock_pending.backlog` 两个指标没做），热路径上的标签组合预先建好。

### 9.8 什么算错误；可观测是可选依赖

**要点**：**只有服务端故障才把 span 标成 Error**；业务拒绝（库存不足）、限流的 429、降级是正常结果，不标 Error，原因码记成属性（`otelx.SetReason`），否则错误率被业务拒绝淹没。**可观测性是可选依赖**：后端不在时不能挡启动、不能阻塞业务：OTLP 导出器建连接是惰性的；批处理队列满了就丢 span 不阻塞业务 goroutine；`shutdown` 有时限（5 秒），在所有组件停止之后调用，把缓冲里的 span 和最后一次指标发出去。没配地址时仍建 `TracerProvider` 只是不挂导出器，span 照常产生，日志里有 trace id 可以串起来（`make test`、e2e、chaos 默认如此），这样量不出代价（见 9.9），所以没有改成“不记录”：不记录会把“不采样”传给下游，下游即使配了地址也收不到这些链路。

**本项目**（设计 8.3、8.4、8.15）：规则和 `grpcx.isServerFault` 同一条。日志不走 OTLP，仍是标准输出的 JSON，`logx.New` 的 handler 在 ctx 里有 span 时加 `trace_id`、`span_id`（只有带 ctx 的调用才有，所以规范是手边有 ctx 就用 `InfoContext`；`sloglint` 的强制还没打开）。`redisotel` 默认给每个 span 记调用位置（每条命令一次 `runtime.Caller`，位置总落在我们自己的封装里），已关掉。MySQL 的 span 名按空格取第一个词时多行语句带着换行、以注释开头的叫 `mysql /*`，改成只认十来个动词其余叫 `mysql query`。

### 9.9 埋点的开销怎么量，用链路拆一次请求的时间

**问**：埋点有多大开销？怎么用链路定位一次请求的耗时？

**要点**：**开销的测法**：同一负载下对比几种配置（基线、采样 0、采样 1%、采样 100%），每种多跑几次，不预设通过线；注意**基线怎么选**：用 `always_off` 而不是埋点之前的二进制，它仍包含传播和生成 trace id 的开销，所以量到的是“记录和导出”的代价，不是埋点的全部代价。**拆一次请求的时间**：看 handler 的 span 里被子 span 覆盖的部分和没覆盖的部分；子 span 覆盖不到的才是进程内的等待。**平均值和中位数差很多时看长尾**：平均值被少数极慢的调用拉高。**200 毫秒整数倍的长尾是 TCP 重传的特征**（丢一个包等约 200 毫秒重发，Linux 最小 RTO）。最后落到**往返次数乘以每次往返的代价**。

**本项目的实测**（设计 8.16；开环每秒 2000 单、20 秒、落库并发 16，每种配置 3 次）：

| 配置 | 落库吞吐（单/秒） | 受理 p50（毫秒） |
|---|---|---|
| 不导出，`always_off` | 736、751、611\* | 6.2 到 7.6 |
| 不导出，默认采样 | 623\*、725\*、726 | 6.2 到 7.5 |
| 导出，采样 1% | 793、728、737 | 5.8 到 7.4 |
| 导出，采样 100% | 562\*、687、553\* | 8.5 到 9.4 |

带 \* 的几次出现了落库重试，不能用来比。结论：**1% 采样的开销量不出来；全量采样有可见代价（唯一没有重试的一次低约 7%，p50 多约 2 毫秒），只适合看单个请求**。另见：过载时闸门的调用会成批超时（12 次运行里 5 次，认领的 Redis 调用超过 300 毫秒时限，闸门熔断器打开，几百条消息被拒绝重试，那一轮落库吞吐低 15% 到 25%，订单没丢），不是埋点引起的（`always_off` 的一次也出现了），以前没注意是因为没有 `kafkax.consumer.retries` 这个数。原因后来查到并修了，见 6.9。

**回答 3.9 的悬案：放宽刷盘后落库停在约 1050 单/秒，每个订单在途约 60 毫秒，其中 54 毫秒不在 MySQL 里，在哪？**（放宽刷盘、采样 2%，取 120 条落库链路，同时读 MySQL 的语句统计）

| 一次落库里 | p50（毫秒） | 平均 | 最大 |
|---|---|---|---|
| 整个 handler | 26.8 | 55.3 | 632 |
| 调 inventory 的 `Reserve`（客户端看到的） | 14.9 | 26.4 | 423 |
| 其中 inventory 服务端 | 9.8 | 21.4 | 419 |
| order 自己的 MySQL 语句（不含提交） | 8.1 | 22.0 | 219 |
| order 的提交（两次） | 1.6 | 3.9 | 110 |
| Redis | 0.6 | 0.8 | 5.5 |
| 没有被任何子 span 覆盖的时间 | 0.15 | 2.2 | 204 |

- **不在 order 进程里**：没覆盖的中位数 0.15 毫秒，猜的“进程内某处等待”不存在。
- **不是一个 54 毫秒，是一个 27 毫秒的中位数加一条长尾**；平均值被拉到 55。64 个在途除以平均 55 毫秒约每秒 1160 单，和 1050 对得上。
- **长尾是 200 毫秒的整数倍**（最大值 219、419、423），TCP 重传的特征，打在谁身上是随机的，所以“语句”“提交”“Reserve”的最大值都是这种数。
- **中位数的 27 毫秒花在往返次数上**：MySQL 自己统计每条语句 0.2 到 0.5 毫秒、提交 1.5 毫秒，客户端看到每条约 1 毫秒；一次落库在 order 里有 18 个子 span，inventory 里还有十来条语句，每次往返经过容器端口转发多出大半毫秒；`Reserve` 经过两个边车另外多 5 毫秒。
- 结论：MySQL 不再是瓶颈之后，剩下的是**往返次数乘以这台机器上每次往返的代价，再加偶发的 200 毫秒重传**；前一半在集群上会小得多，后一半是 OrbStack 的问题。这支持把吞吐结论挂到阶段 2，也说明方案 B（经 Kafka、order 不再同步调 `Reserve`）在本机上能省的是那 15 毫秒，在集群上未必值得。
- 严格刷盘（默认）同样的拆法：handler p50 51 毫秒，其中 order 的两次提交 18、`Reserve` 21（里面一次提交约 9）、order 的语句 8；MySQL 统计的提交每次 10.2 毫秒和链路一致，而单个连接串行提交只要 1.3 毫秒，那 10 毫秒是并发时排队等刷盘。
- 过载时消息从写入 Kafka 到开始处理的中位数是 1.7 到 10 秒，大部分是进程内排队（`kafkax.queue_ms`），不是 broker：背压放进来的积压，符合设计。`kafkax.queue_ms` 是进程内排队，`kafkax.delivery_ms` 是从写入 Kafka 算起的总等待，两者的差是 broker 和网络上的时间。

**设计取舍**：业务代码不手工建 span（客户端 span 覆盖不到的只有“等待”，最主要的是 `kafkax` 消费者里消息从拉到进程里到 handler 开始之间的排队）；Kafka 的传播和消费 span 自己写在 `kafkax` 里而不用 franz-go 的 `kotel` 插件（它的 span 对应“消息进出客户端缓冲”，而我们关心的处理过程——按 key 分 lane、排队、重试、按批、延迟等到期——在 `kafkax` 自己的代码里，`kotel` 看不到）；指标经 OTLP 推不开 `/metrics`（和 ADR-0004 一致，链路和指标同一条路，代价是不起后端没法直接 `curl`）；本机后端用 `grafana/otel-lgtm`（0.41.0，只用来看），SkyWalking 的 OTLP 够不够用是 ADR-0004 留给阶段 3a 的验证项。

## 10. 1d 的已知缺口汇总

- **热门 SKU 之后的下一个瓶颈**：本机落库是每个订单三次提交的上限（约 790 到 985 单/秒），不是数量级的提升；吞吐结论挂到阶段 2 的集群（2.1、9.9）。
- **MySQL 一侧只“发现”超卖**；对短暂的超卖不确定，持续的一定发现（2.3）。`inventory.oversell.detected` 依赖每个应用者内存里的“已知卡住”集合，重启或多副本时同一 SKU 会重复计数。
- **Envoy 只有连续失败一种判断**，没有错误比例、慢调用比例、半开单探测（5.4）。
- **`Hold` 超时后的清理和 `Hold` 本身可能乱序**，留下没有落库消息的占用，靠回收任务收走（5.5）。
- **闸门的 Redis 是下单的单点**；Redis 重启后数据丢了的恢复留给阶段 4（6.2）。
- **一条没识别出来的坏消息会永久挡住分区**，要靠消费积压告警，阶段 3 才有；闸门脚本运行时出错和连不上分不开（6.3）。
- **落库健康是每个实例自己的判断**；`Retry-After` 固定 5 秒；标记和闸门共用一个熔断器；inventory 进程里的闸门调用没有熔断器（设计 6.17）。
- **`DRAIN_DELAY` 在单实例下验证不了**（7.2）。
- **对账**：商家索引没有订单号索引，每一层下钻是全表扫描；`archive` 只能定位到节点，没有自动存树；主从对比前不等从库追上；`replica` 没有在开发库上演练；增量维护的树、定时调度、指标没做（8.4、8.6、8.7）。
- **埋点**：`sloglint` 没打开；两个指标没做；没验证后端容器停掉时长时间不涨内存；CDC 一跳不传递；压测工具没用 `X-Trace-Id`；过载时那个约 300 毫秒的停顿本身来自容器网络还是进程没查到（熔断器对它的放大已修，见 6.9）。
- **限流**：按 IP 和 Redis 退回只有网关集成测试覆盖，没在整套服务上验证；429 的访问日志仍每个记一条，洪水来时会是下一个问题；限流维度只在错误文字里，没有结构化字段（设计 4.17）。
- `make fault` 没进 CI（耗时约 5 分钟，会暂停本机共享的 Redis 和从库）。
