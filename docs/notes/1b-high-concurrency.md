# 1b 笔记：把下单链路改成能扛峰值，同时不放松一致性

这份笔记整理 1b 里值得在面试中讲的点，按主题组织，不按开发步骤。每条按“面试官会怎么问 → 要点 → 本项目里怎么做、踩过什么坑”来写。设计全文见 [design/1b-high-concurrency.md](../design/1b-high-concurrency.md)（下文简称“设计”，引用章节号），取舍见 ADR-0007 到 ADR-0010。

1b 做的事：用 outbox 加 Kafka 替换 1a 的“同步调用加轮询重试”；用 Redis 库存闸门加异步下单削峰；超时关单改为延迟消息；周期任务用分布式锁单实例运行；查询加缓存。

## 1. 消息与最终一致性

### 1.1 为什么不用 XA / 2PC

**问**：跨服务的订单和库存，为什么不用分布式事务？

**要点**：2PC 有协调者单点；准备阶段参与者持锁等待，任何一方变慢，所有参与者都被拖住；协调者在第二阶段前崩溃会让参与者一直悬着。互联网业务普遍用最终一致换可用性。这是 `AGENTS.md` 里的既定约束，不是临时决定。

**本项目**：1a 用“本地事务加幂等下游加后台重试”，1b 把重试换成 outbox 加 Kafka（ADR-0008）。代价要讲清楚：一致性从“调用成功时立即一致”变为**始终最终一致**，订单已支付到库存显示已售之间有一小段延迟，读接口和测试都要接受。

### 1.2 outbox 与事务消息

**问**：改了库还要发消息，怎么保证两件事要么都做要么都不做？

**要点**：先提交再发会在崩溃时丢消息，先发再提交会通知一件没发生的事。outbox 把“要发的事件”和业务变更写在同一个本地事务里，再由中继异步发到 Kafka。

| 方案 | 做法 | 取舍 |
|---|---|---|
| outbox + 轮询中继 | 事件进本库的表，中继扫表发送 | 通用，不依赖中间件能力；多写一行、多一个组件、空闲时也在查库 |
| 事务消息（RocketMQ） | 先发半消息，本地事务提交后确认，broker 回查未确认的 | 不需要 outbox 表；需要中间件支持，Kafka 没有。Kafka 的事务解决的是“消费、处理、再生产”的原子性，不是数据库与消息之间的 |
| CDC（读 binlog） | 不轮询，延迟低，业务不用写 outbox | 要额外部署运维一套 CDC。1c 会做，届时和轮询中继对比（压测结果待补） |

**本项目的坑和设计点**（设计 3.4）

- **为什么按 `published_at IS NULL` 扫，而不是记一个已发到哪个 id 的游标**：自增 id 在插入时分配，不是提交时。事务 A 拿到 id 5，事务 B 拿到 id 6，B 先提交，中继看到 6 看不到 5；游标推到 6 之后，5 永远发不出去。按状态扫描没有这个问题。这是考 outbox 的经典追问。
- 发送成功但标记前崩溃会重发，所以是**至少一次**。`Send` 返回失败也不代表没写入（broker 写入后、回复前超时），重发同样产生重复。
- 事务里不能发 Kafka：事务时长取决于网络，发送成功后事务还可能回滚。
- 提交后 `Kick()` 唤醒中继降低延迟，轮询只是兜底。

### 1.3 Kafka 的投递语义

**问**：Kafka 是 exactly-once 吗？

**要点**：三种语义取决于“处理”和“提交位点”的先后。先提交后处理是至多一次（可能丢）；先处理后提交是至少一次（可能重复）。Kafka 的“精确一次”指幂等生产者加事务，覆盖 Kafka 到 Kafka 的读、处理、写。一旦副作用在外部系统（数据库），端到端只能是**至少一次加消费端幂等**，不存在免费的 exactly-once。

**本项目**：生产者 `acks=all` 加幂等；消费者处理成功后才提交位点。每个消费逻辑自己保证幂等，且一律用业务唯一键，不建通用去重表（ADR-0008）：预占记录以 `order_id` 为主键，支付结果以 `payment_id` 为主键，状态转换带前置条件。出现没有业务键的消费逻辑时才引入去重表。

### 1.4 顺序性

**问**：Kafka 怎么保证顺序？

**要点**：只保证单个分区内有序；同一个 key 进同一个分区，所以按业务键保序。分区数变化会改变 key 到分区的映射。生产者重试可能乱序，幂等生产者解决这个问题；消费者并行处理同一分区内的消息也会破坏顺序。

**本项目**：同一订单的两次状态变更由订单行锁串行，outbox 的 id 递增，中继按 id 升序发，key 是订单号。**但仍然不依赖严格有序**：失败重发可能让旧事件排到新事件后面。消费者全部以状态机前置条件判断，而不是假设先来的先发生。设计 5.6 的表逐格论证了重复、延迟、乱序三种情况，并有测试。分区内 handler 失败时原地重试、分区不前进，宁可慢也保序。

### 1.5 再平衡与消费积压

**问**：消费者组再平衡会带来什么问题？积压了怎么办？

**要点（再平衡）**：分区被收回时，旧消费者可能还在处理在途消息，而新持有者已经开始处理同一分区，造成重复处理。缓解：收回分区前先提交已处理完的位点；handler 要遵守 ctx 并有自己的超时；使用增量（协作式）再平衡避免全组停顿。

**要点（积压）**：先定位是生产突增还是消费变慢；加消费者实例（上限是分区数）；加分区（key 的映射会变，要考虑顺序）；优化 handler，批量处理，去掉慢依赖；极端时降级，丢弃可丢的消息或另起一个跳过的消费者组。积压是症状，要先查根因。

**本项目**（设计 3.3）：

- 实现 `kafkax.Consumer` 后确认的限制：handler 卡住超过再平衡超时（默认 60 秒）会被踢出组，两边并发处理同一条消息，所以幂等不是可选的。
- **死信发不出去时分区会一直停住**，不会跳过，有意为之（不能丢），靠积压告警发现。
- 积压在本项目里有真实的后果：落库时支付时限已经过了就直接转 `FAILED`（`CREATE_TIMEOUT`），否则订单进入待支付又立刻被关，用户没时间支付，库存白占一轮（设计 6.3）。
- 库存服务处理事件先改 MySQL 再改 Redis，Redis 不可用时如果按默认 5 次重试就进死信，会造成 MySQL 已释放而占用没归还，对账看不出来。所以该消费者重试调到 60 次（约 5 分钟），宁可停住等 Redis 恢复（设计 6.6）。

### 1.6 消费者被 kill -9 后，分区要停多久

**问**：消费者进程被 `kill -9` 或机器掉电，它名下的分区多久能恢复消费？

**要点**：被杀的成员来不及发 LeaveGroup，broker 只能等**会话超时**（`session.timeout.ms`）内没有心跳才把它踢出组、触发再平衡，这段时间分区没人消费。心跳间隔通常取会话超时的三分之一。重启的新实例**也要等旧成员被踢掉**才能拿到分区，所以重启得再快也没用。会话超时取小，恢复快，但 GC 停顿、网络抖动会误踢；取大则相反。静态成员（`group.instance.id`）让重启的实例直接接回原来的分区、不触发再平衡，代价是每个副本要有稳定的身份（K8s 上用 StatefulSet 或按 Pod 名），且实例真的下线后要等会话超时才会重新分配。

**本项目踩过的坑**（设计 7.3.4，杀进程测试里最有价值的两个发现）：

- **会话超时没设，用了 franz-go 默认的 45 秒**。被杀的消费者名下分区整整停摆 45 秒：库存一直不归还（库存小的运行里前 2 秒卖完，之后释放的库存再没回到闸门，结束时闸门里还有二三十件可售，不超卖但一直少卖）；下单消息没人消费，5 秒的回收宽限期一到占用就被回收，受理的订单有 28% 到 33% 就这样消失。修复：`SessionTimeout` 默认 10 秒，心跳三分之一，静止等待从 10 到 43 秒降到 2 到 13 秒。静态成员留到阶段 2 上 K8s 再评估。
- **依赖方重启几秒，消息就进了死信**。分区不再停摆之后才看得见：order 落库调 inventory 的 `Reserve`，默认重试 5 次合计约 1.5 秒，短于 inventory 重启的 1 到 3 秒，一次运行有 12 条下单消息进死信。数据仍然一致（订单由 sweeper 置为失败），但用户的订单因为对方抖了一下就没了。修复：重试调到 10 次（约 26 秒）。

**各种超时之间有约束，不是各自拍脑袋定的**：

- **回收宽限期 > 会话超时 + 重启耗时**。否则消费者一被杀，消息还没来得及被接手，占用就被回收。默认宽限 1 分钟在 45 秒的会话超时下只剩 15 秒余量；改成 10 秒后才充足。杀进程测试把宽限期调成 5 秒，小于 10 秒的会话超时，所以修复后仍有订单被回收（一次 180 个，一次 7 个），这是预期内的正确行为。
- **消费者的重试预算 > 依赖方一次重启的耗时**（见上，1.5 秒对 1 到 3 秒）。
- **回收宽限期 > 可接受的最大积压排空时间**：见 2.7。

### 1.7 消费幂等

见 1.3。再强调一个观点：幂等记录要和业务变更在同一个事务里（1a 笔记第 3 节）；1b 里订单消费 `payment.events` 时，`payment_results` 去重、状态转换、答复事件的 outbox 在同一个事务提交。订单不存在时没有订单行锁可以排队，并发的同一 `payment_id` 会在插入时撞主键，这种冲突按可重试处理，重做事务时读到已有记录走“已处理”分支（设计 5.1）。

**“第一次答复为准”**（实现时发现的设计缺陷，设计 5.2）：支付服务处理订单答复时，退款语句原设计没有 `notified = 0` 的前置条件。于是一条 `ACCEPTED`（订单已付清）之后再来一条矛盾的 `REFUND_REQUIRED`，会把已付清订单的钱退掉。订单服务按 `payment_id` 去重，正常不会给出两个答复，但退款不可逆，不能把正确性押在对方没有缺陷上。教训：**消费端对涉及资金的动作要自己设防，不信任上游“不会重复、不会矛盾”**。

### 1.8 Saga 与 TCC

**问**：Saga 和 TCC 有什么区别？

| | Saga | TCC |
|---|---|---|
| 每步 | 本地事务直接提交 | Try 只预留资源，之后 Confirm 或 Cancel |
| 失败处理 | 反向执行补偿 | 对预留的资源执行 Cancel |
| 隔离性 | 没有，中间状态对外可见 | 预留状态在业务上就是隔离手段 |
| 实现成本 | 补偿逻辑 | 每个接口拆成三个，还要处理空回滚、悬挂、幂等 |
| 编排 | 协同式（事件驱动）或编排式（中心协调） | 通常有协调者 |

**本项目**：库存的 `Reserve / Confirm / Release` 就是 TCC 形状，空回滚与悬挂见 1a 笔记第 6 节。订单、支付、库存之间靠事件推进，是**协同式 Saga**：各服务订阅事件各自反应。只有两三步时够用；出现步骤多、有先后依赖的流程时再评估编排式（ADR-0008）。

## 2. 削峰：Redis 预扣与异步下单

### 2.1 Lua 预扣

**问**：秒杀怎么扛？Redis 里扣库存怎么保证不超卖？

**要点**：热点商品的瓶颈是 1a 里同一行的行锁排队。把“买不到的请求”挡在入口：Redis 里一段 Lua 脚本原子地完成幂等检查、库存检查、限购检查、扣减。Redis 单线程执行脚本，脚本执行期间没有别的命令插入，所以它能代替锁。脚本里**先做完所有检查，再做所有修改**，所以中途拒绝不需要回滚（多 SKU 订单要么全扣要么都不扣）。

**追问：Redis Cluster 怎么办？** 脚本访问的 key 必须在同一个槽。本项目的脚本在内部拼 key，没有通过 `KEYS` 声明，只能用单实例。上集群要么只支持单 SKU 下单并用 hash tag，要么把闸门按 SKU 分片（设计 6.2）。这是有意识的限制。

### 2.2 两个存储之间没有事务，操作顺序怎么定

**问**：Redis 和 MySQL 都要改，没有事务，先改哪个？

**要点**：先想清楚“哪个方向的偏差可以接受”。本项目里 MySQL 是唯一事实来源，Redis 只决定放不放进来，**允许偏小（少卖），不允许偏大**（偏大不会超卖，MySQL 条件更新兜底，但会放进一批注定失败的订单）。所以：让 Redis 变小的操作先做 Redis，让 Redis 变大的操作后做 Redis。扣减先扣 Redis 再扣 MySQL；归还先还 MySQL 再还 Redis。任何一步崩溃，中间状态只会少卖不会多放。

### 2.3 占用（hold）与幂等归还

整套设计的核心是 `gate:hold:<order_id>`：以订单号为主键、记录“闸门为这个订单扣过什么”的记录。它存在归还才生效，归还时删除，所以**归还天然幂等**。它不设过期时间：让它自己过期等于不归还就丢掉记录，数量永远少一块。它要活到订单终态，因为之后的取消、关单还要靠它做幂等归还和限购回退。

### 2.4 受理路径的不一致窗口与回收

**问**：为什么受理路径不用 outbox？

**要点**：outbox 要在受理时写一次 MySQL，而不碰 MySQL 正是削峰的目的。代价是“Redis 扣了、消息没发出去就崩溃”没有本地事务兜底，留下孤儿占用。这个窗口只会让库存暂时偏小，由回收任务收敛。

**本项目踩过的坑**（设计 6.3、6.4，都值得单独讲）：

1. **发送失败不等于没发出去，不能无条件归还。** `Send` 失败时消息可能已经写进 Kafka、消费者可能已经认领。无条件归还会把一个即将在 MySQL 预占成功的订单的占用还掉，还会删掉幂等键让用户重试时下出第二单。所以用 `ReturnIfUnclaimed`：归还成功才算没受理；已被认领按成功作答；占用已不存在说明订单已走完，查一次状态作答。`Hold` 本身超时（结果未知）也要先尽力撤销，否则重试会命中幂等键，拿到一个永远不会落库的订单号。
2. **“回收”和“落库”必须互斥，只靠宽限期不够。** 消费积压时消息还在 Kafka 里排队，超过宽限期没被消费，回收任务这时把占用还了，稍后消费者又把订单建出来并在 MySQL 预占成功，Redis 就比 MySQL 多一份，且不会自己恢复。解法是一次原子的认领：消费者落库前先 `Claim`，回收只还未认领的，两个脚本在 Redis 里原子执行，同一笔占用只有一方得手。回收先赢，用户看到订单消失（404），库存已归还。
3. **已认领的占用要和未认领的分开放（实现时由子 Agent 用测试复现出来）。** 最初认领后仍留在同一个列表里，它要活到订单结束，会一直排在最前面，数量超过回收一批的大小后，后面的孤儿永远轮不到。修正：认领时移到 `gate:claimed`，回收只扫 `gate:holds`。
4. 幂等键在 Redis 里过期后的重放：订单库的 `(user_id, idempotency_key)` 唯一键是最后一道防线。落库时撞唯一键而订单号不同，先把幂等键补回指向原订单，再 `Abort` 这笔占用。**顺序保证任何一步失败后重试都能接着做完**。

**已知缺口**：认领后消息进死信的占用不会自动归还（不知道 MySQL 里有没有预占），只记 error 日志等人工；重放的用户会先拿到新订单号的 202 随后查到 404；重放一个已失败的订单返回 `FAILED` 订单而不是当初的错误。

### 2.7 削峰的队列也要有上限：受理端背压

**问**：异步下单受理远快于落库时，队列无限长会怎样？怎么限流？

**要点**：队列不限长，积压就没有上界，延迟也没有上界。对本项目更糟：回收任务把超过宽限期仍未认领的占用当孤儿还掉（它分不清“没人发消息”和“消息排在很后面”），所以积压一旦超过宽限期，已受理的订单会被回收，用户先拿到 202，之后查询变成 404。回收本身是对的，错在让队列长过了宽限期。

**为什么按队列长度，而不是按最老订单的排队时长**（利特尔定律：等待 = 长度 / 速率）：最老订单的排队时长衡量的是过去，新订单要等多久取决于它前面排了多少。

- **第一版只看排队时长，仍然丢单**：受理 4900 单/秒、落库 400 单/秒，最老订单排到 30 秒的那一刻，后面已经排了 13 万单，要 5 分钟才落得完，照样被回收。一次压测受理 15 万、落库 12.6 万，**丢了 2.3 万单**。
- **加上长度上限后**：同样的压测受理 3.2 万、落库 3.2 万，零回收，积压 25 秒排空。
- 排队时长那条没删，留着发现“队列不动了”（落库停住，长度没到上限）：排队超过宽限期一半的占用多于 100 个就拒绝。按个数而不是看最老的一个，是为了容忍零星真孤儿，否则一个孤儿就能让受理停摆半分钟。

**设计取舍**（设计 6.4.1，ADR-0011）：

- **上限是静态的**（`ADMIT_MAX_QUEUE` 默认 1 万 ≈ 本机落库约 400/s × 25 秒，小于 1 分钟宽限）。按最近认领速率自适应更准，但冷启动速率为零、速率会抖、要多维护计数器。代价：落库吞吐变了（加分区、换机器）要手动调。
- **拒绝而不是排队等**：在网关排队只是把队列从 Kafka 挪到内存，请求挂着还占连接；秒杀里明确告诉用户“稍后重试”更好。
- **用 429（`RESOURCE_EXHAUSTED`）而不是 503（`UNAVAILABLE`）**：这是有意的削峰，不是故障。`grpcx` 把 `UNAVAILABLE` 记为 ERROR，积压时每秒上百条，会淹没真正的下游故障。
- **卖完优先于积压**：积压检查放在库存检查之后，卖完的请求得到“卖完”而不是“稍后重试”，否则用户会对注定买不到的商品反复重试。
- 检查放在 `Hold` 脚本里、任何修改之前，拒绝时什么都没发生，可用同一个幂等键重试；检查和写入在一个 Lua 脚本里原子完成，这是不按 Kafka lag 限流的原因之一（要查 Kafka，引入依赖，lag 还是条数，换算时间仍要速率）。
- 边界：消费者完全停住超过宽限期时，已在队列里的订单仍会被回收，背压救不了，所以宽限期要大于“会话超时加重启耗时”（见 1.6）。

### 2.8 突发流量下的冷连接池与预热

**问**：秒杀开始瞬间，为什么会有一批请求同时超时？连接池怎么配？

**要点**：连接池启动时是空的，突发的几百个请求让客户端同时新建几十上百个连接。**新连接没有往返时间（RTT）样本，丢一个包要等 1 秒的初始重传超时（RTO）才重发**；已建立的连接重传只要约 200 毫秒（Linux 最小 RTO）。1 秒的重传恰好撞上 1 秒的读超时，于是同一时刻一批请求一起失败。对策：固定大小的池、启动时建满（预热），突发的请求排队等现成连接，而不是各自去新建；池大小按“每次调用耗时 × 并发”估，Lua 调用几十微秒，32 个连接每秒就能处理十几万次。

**本项目踩过的坑**（设计 7.3.4，“e2e 偶发失败”）：

- 现象：`make e2e` 并发提交时个别请求 503。在步骤四之前的提交上连跑 30 次失败 8 次，不是步骤四引入的。Redis 慢日志是空的，服务端并不慢。
- 失败有两种，同一个根因：`inventory unavailable`（新 SKU 第一批几百个并发下单都发现“未装载”，各调一次 `WarmUp`，inventory 里的 Redis 调用超时）；`stock gate unavailable`（order 自己调 `Hold` 超时）。日志里 25 次超时落在同一个 5 毫秒窗口，都在服务启动后第一波并发中。特征很明确：同一时刻、全是新连接、恰好 1 秒。
- 丢包本身没有拿到计数证实（推测是本机 OrbStack 端口转发在高包速率下丢包，和压测里约 23% 的提交卡在 200 毫秒是同一类现象）。但修复不依赖这个前提，生产上同样成立。
- **修复两处**：`pkg/redisx` 改固定大小池，默认 `PoolSize` 32、`MinIdleConns` 等于 `PoolSize`，`Open` 等连接建满再返回（最多 2 秒）；order 按 SKU 用 `singleflight` 合并并发的预热调用，合并后的调用用独立时限，发起者被取消时搭便车的请求不跟着失败。
- **单飞为什么只解决了预热路径**：只做 `singleflight` 时 20 次失败 2 次，剩下的全是 `Hold` 超时。`Hold` 每单一次，不能合并，只能靠池里有现成连接。两处缺一不可。结果：连跑 25 次全部通过（失败从 30 次 8 次降到 25 次 0 次）。
- 追问可以答：惊群（同一个 SKU 的预热被几百个请求同时触发）用 `singleflight` 合并，和 5.3 的击穿处理是同一类思路。

### 2.5 对账

**问**：Redis 和 MySQL 的库存如何对账、修正？

**要点**：先找出稳定状态下的恒等式：`Redis avail + held == MySQL available + reserved`（都等于“还没卖掉的数量”）。偏差持续存在才认定为真，修正用**增量**而不是覆盖。

**本项目**（设计 6.6）：

- **增量而不是覆盖**：读 MySQL 和读 Redis 不是同一时刻，直接覆盖会抹掉期间发生的扣减。
- **连续 3 轮相同才修**：瞬时偏差（例如 Confirm 已提交、Settle 还没执行）不能修。“连续”指相邻的轮次，丢过 leader 或偏差值变了都要重新计数。
- **修正后的 `avail` 不超过 MySQL 的 `available`**：Redis 丢数据重新装载后，在途订单的占用丢了，若不设上限，对账会把 `avail` 调高放进一批注定失败的订单。
- **对账必须单实例**：增量修正执行两次就是两倍，所以对账用 leader 锁，且锁不可用时停下（见 4.5）。
- **汇总量对账发现不了的偏差**：“占用该还没还”这一类，恒等式两边都没变。逐单核对占用与预占留给 1d。
- 已知缺口：上限不够紧（没扣掉已受理未预占的占用）；“连续 3 轮相同”理论上可能是巧合，误修后会被反向修回。
- Redis 必须 `noeviction`：`gate:sku:*` 被淘汰而占用还在时，归还和结清会跳过这个 SKU，数量就丢了。

### 2.6 异步下单后的读己之写

下单改为 202 加轮询后，受理后落库前订单库里没有这一行。`GetOrder` 查不到订单行时再查占用，存在就合成一个 `CREATING` 的订单；两边都没有才是 404（设计 6.3）。这影响缓存：见 5.3。

## 3. 延迟消息的几种实现

**问**：15 分钟未支付自动关单，怎么做？

| 方案 | 优点 | 问题 |
|---|---|---|
| 定时扫表 | 最简单 | 延迟等于扫描间隔，负载和间隔成反比；分库分表后要扫每个分片 |
| 进程内时间轮 | O(1)，精度高 | 只在内存里，重启就丢，要另做持久化和恢复；多副本要决定任务归谁。适合做“最后一段” |
| Redis ZSET | 任意时长，可取消 | 取出即删则崩溃丢任务，要自己实现确认和重新入队；可靠性取决于持久化；单 key 是热点 |
| Kafka 固定时长延迟 topic | 复用已有的持久化、至少一次、重试、死信 | 不支持任意时长；不能取消；延迟期间位点不前进，保留时间要远大于延迟 |
| 支持延迟的 MQ（RocketMQ 5、RabbitMQ 插件、Pulsar） | 功能最贴合 | 为一个需求引入第二套消息系统 |

**本项目选择**（ADR-0009）：Kafka 固定时长延迟 topic，扫表降为 30 秒一次的兜底。几个可以讲的点：

- **只看队首为什么成立**：同一个 topic 里延迟时长相同，分区内天然按到期时间有序。这也是限制：不同时长要不同 topic。
- **不能取消怎么办**：处理到期消息时本来就以“仍是待支付且已过期”为前置条件做条件更新，已支付的订单自然是空操作。用消息量换数据库扫描。
- **时钟**：到期时间以发送方的时钟为准，处理方时钟慢时按本机还没过期，要返回错误让消费者重试，不能当作不需要关闭而跳过。
- **为什么还要保留扫表**：延迟消息和 `order.submit` 一起发，不是原子的，可能只成功一条，也可能进死信。有了兜底，延迟消息只需“大多数时候准时”，不需要“绝对不丢”。**不要让一个“尽力而为”的机制承担“必须发生”的责任。**
- **饥饿问题**：一个按时间排序的列表里混入长期不出队的元素，会挡住后面的元素（和已认领占用挡住孤儿同一个模式，见 2.4）。延迟消费者只看队首，所以延迟时长必须统一。
- 任意时长要求出现时再评估 ZSET 或支持延迟的 MQ。

## 4. 分布式锁

### 4.1 正确实现

**问**：用 Redis 怎么实现一把分布式锁？

**要点**（`pkg/lock`，设计 3.5）：

- 加锁 `SET key token NX PX ttl`，token 是随机值。NX 保证互斥，PX 保证持有者崩溃后能自动释放，不能分成 `SETNX` 加 `EXPIRE` 两步（中间崩溃锁永不过期）。
- 解锁用 Lua 脚本先比较 token 再删除，两步必须在同一个脚本里。直接 `DEL` 会在锁已过期并被别人拿走后删掉别人的锁。
- 续期（看门狗）：按 `ttl/3` 间隔用脚本校验 token 后延长，续期失败要通知持有者（会被取消的 context）。

**本项目的细节**：加锁和 `INCR` 取 fencing token 在同一个脚本里。分开的话，A 加锁后卡住，锁过期，B 加锁拿到 1，A 醒来再 `INCR` 拿到 2，后加锁的 B 反而拿到更小的 token，fencing 就颠倒了。计数器 key 不设过期，否则重置后新 token 比旧持有者的还小；因此锁名数量必须有限，不能按订单号加锁。

### 4.2 过期与续期

**问**：锁过期了但业务还没做完怎么办？

**要点**：看门狗续期只能缩短窗口，不能消除。持有者暂停（GC、虚拟机迁移、被调度走、网络卡住）超过 TTL，锁在它不知情时过期并被别人拿走，它醒来后继续做“持锁期间”的事，两个持有者同时存在。判定丢锁有滞后，最坏要到 TTL 之后再约 TTL/3。

**本项目**：两个刻意制造失效的测试：持锁方停顿超过 TTL 后旧持有者解锁不影响新持有者；旧 token 的写入被拒绝。

### 4.3 fencing token

**问**：怎么防止“僵尸持有者”？

**要点**：锁服务每次授予锁返回单调递增的序号，持锁者访问资源时带上，**资源侧**拒绝比已见过的更小的序号。防线在资源侧，因为只有资源能在“最后一刻”判断。前提是资源支持这种检查（例如带版本号的条件更新）。

**本项目的边界**：`pkg/lock` 提供 token，但本项目的锁都用在“重复执行无害”的任务上，没有哪个资源真的去校验它。要讲清楚：这是能力，不是已经全面使用的东西。`Guard` 只回答“这一轮能不能跑”，这一轮期间丢了锁任务不知道，所以只能用在重复执行无害的任务上（设计 3.5）。

### 4.4 Redlock 的争议，以及与 etcd、ZooKeeper 锁的对比

**问**：Redlock 是什么？为什么有争议？单实例 Redis 锁和它有什么区别？

**Redlock 是什么**：在 N 个（通常 5 个）互相独立的 Redis 主节点上依次加锁，在远小于 TTL 的时间内拿到多数就算成功，有效时间是 TTL 减去加锁耗时（再扣除时钟漂移）。目的是解决单实例的问题：主从异步复制时，主节点宕机、锁没复制到从节点，从节点升主后第二个持有者就能加锁。

**Kleppmann 的论点**（2016 年《How to do distributed locking》）：

- 锁有两种用途。只为效率（避免重复做事）时，单实例 Redis 就够，Redlock 太重；为正确性时，Redlock 不够安全。
- Redlock 依赖时间假设：进程暂停、网络延迟、时钟跳变都不会超过某个界。真实系统里这些假设会被打破（暂停发生在拿到锁之后、使用资源之前，没有任何办法察觉）。
- 它不产生 fencing token。多个独立节点各自计数，没有一个能给出全局单调的数。没有 token，就没法在资源侧挡住僵尸持有者。
- 要正确性应该用有共识协议支撑的系统（ZooKeeper 之类）加 fencing token。

**antirez 的回应**（《Is Redlock safe?》）：

- 时钟跳变：Redlock 只需要各节点时钟走速大致一致（有界漂移），可以通过运维手段避免时间被大幅调整，不需要同步的时钟。
- 进程暂停：Redlock 在拿到多数之后会再检查耗时，暂停发生在加锁过程中能被发现；暂停发生在检查之后则是**任何**锁（包括带 fencing 的）都面对的问题。
- fencing：随机 token 配合资源侧的比较并设置也能达到类似效果；并且如果资源侧已经能做这种检查，锁在正确性上就不再是必须的了。

**一个中立的结论**（面试里这样收尾比站队稳）：双方在“持有者暂停会导致两个持有者”这一点上其实没有分歧，分歧是 Redlock 的时间假设能不能接受，以及它是不是适合“正确性”场景。工程上的共识：**锁只是效率优化时，单实例加幂等就够；锁要保护正确性时，要么资源侧做 fencing 检查，要么直接用资源自己的原子操作（条件更新）。** 本项目单实例锁的取舍和这个共识一致：只用于“重复执行无害”的任务。

**与 etcd、ZooKeeper 锁的对比**

| | Redis 单实例锁 | Redlock | etcd | ZooKeeper |
|---|---|---|---|---|
| 一致性基础 | 单节点（主从异步复制，切换可能丢锁） | 多数独立节点，依赖时间假设 | Raft，线性一致 | ZAB，写经过 leader 顺序提交 |
| 锁的载体 | key 加 TTL | 同左，多个节点 | 绑定 lease 的 key，lease 靠客户端续约 | 临时顺序节点，绑定会话 |
| 排队 | 无，自旋重试 | 无 | 按 key 的创建 revision 排队，监听前一个 | 按顺序号排队，监听前一个节点 |
| fencing 序号 | 自己用 `INCR` 实现 | 无自然的全局序号 | key 的 revision 单调递增，天然可用 | 节点的序号或 zxid 可用 |
| 持有者崩溃 | TTL 到期 | TTL 到期 | lease 到期 | 会话超时，临时节点被删 |
| 性能 | 最高 | 较高，多次往返 | 写走共识，较低 | 写走共识，较低 |

要点和容易说错的地方：

- etcd 和 ZooKeeper 的锁**同样存在租约过期**：持有者暂停超过 lease 或会话超时，锁照样被别人拿走。它们的优势不是“消除了暂停问题”，而是（1）数据由共识协议保证，不会因主从切换丢锁；（2）自带单调序号，用来做 fencing 很自然；（3）有排队和监听前一个的机制，避免惊群。
- 代价是写要经过共识，延迟和吞吐不如 Redis；多引入一套要运维的系统。
- ZooKeeper 的客户端能感知断连和会话过期，比“靠 TTL 猜”更早知道可能丢锁，但仍不能覆盖暂停发生在检查之后的情况。

这一小节的“与 etcd/ZK 对比”和 Redlock 论点是按公开资料整理的，设计文档里没有对应内容。具体参数、版本相关的行为细节我没有写，面试前最好对照原文复习一遍。

### 4.5 锁不可用时放行还是停下

**问**：Redis 挂了，靠锁单实例运行的任务怎么办？

**要点**：分两种，取决于**正确性是否依赖锁**。

- 必须互斥（对账：增量修正执行两次是两倍）：fail-closed，锁不可用就停。
- 互斥只为省事（outbox 中继、sweeper、回收、支付处理器，重复执行只是浪费）：fail-open，退化成每个副本都跑。否则 Redis 一挂，事件链路就停摆，等于凭空加了一个单点。

**本项目**（设计 7.1）：`lock.FailOpen(guard, logger)` 把 `Allow` 的错误变成放行并限频记 warn。每个任务一把固定名字的锁，不共用，一个任务卡住不会连带其他任务丢锁。中继 TTL 5 秒（崩溃空窗内事件延迟最多 5 秒），其余 15 秒；正常退出主动释放，没有空窗。

**加锁后事件延迟变了**：`Kick()` 在非 leader 副本上会被 `Guard` 挡掉，消息要等 leader 的下一次轮询，延迟从几乎为零变成最坏一个轮询间隔。可接受，消除它要让 Kick 跨进程传递，不值得。

**实现后记下的缺口**（子 Agent 评审时提出，没有改）：

- **锁只防崩溃，不防卡住**：leader 卡在某一轮里（中继等 Kafka 确认）时，看门狗照常续期，其他副本拿到“没抢到”而不是错误，`FailOpen` 不放行，任务一直没人跑。要解决得让续期依赖任务进展，留到阶段 4 故障实验。
- 主动释放假设 Loop 真的停了；超时仍在跑的 Loop 下一轮会把刚释放的锁抢回来。
- Redis 变慢时 `Allow` 会拖慢每一轮（没有单独超时）。
- payment 启动时 Redis 不可用会启动失败，和运行中可放行不一致。

### 4.6 什么时候不该用锁

**问**：什么时候不该用分布式锁？

**要点**：操作本身能做成原子的“检查并修改”时。锁只会把并发变成串行，并引入一个会过期的外部依赖，以及“锁过期了但操作还在进行”的新问题。

**本项目里不用锁的地方**：库存扣减（条件更新、Lua）、订单状态转换（`WHERE status = ?`）、占用的认领与回收（Lua）。

**为什么中继不用 `SKIP LOCKED` 多实例并行**（设计 7.1）：同一订单的两条事件可能被不同实例取走，分区内顺序没有保证；行锁要持有到 Kafka 确认，事务时长取决于网络。能保序时没必要放弃。

## 5. 缓存

### 5.1 什么数据适合缓存

**问**：什么数据适合放缓存？

**要点**：读多写少，且能容忍旧数据；或者永远不会再变。本项目的规则更严：**缓存里只放两类数据：不会再变的，和旧了也无所谓的**（ADR-0010、设计 7.2.1）。

| 数据 | 缓存 | 理由 |
|---|---|---|
| 终态订单 | 是，10 分钟，不失效 | 终态不再变，永远不会不一致 |
| 库存数量 | 是，1 秒，写时不删 | 只用于展示，下单以闸门为准；秒杀时每秒扣减成百上千次，每次删缓存则永远是冷的 |
| 创建中、待支付订单，支付单 | 否 | 旧值有后果（重复支付） |

一个附带的好处：payment 创建支付单前读订单，读到缓存也安全（缓存里只有终态，终态本来就不能支付），所以接口不需要“是否允许读缓存”的开关。

**坑**：订单以后加了发货、退款，`PAID` 就不再是终态。用 `cacheable(status)` 集中判断，并写测试枚举所有状态必须明确归入缓存或不缓存，新增状态时测试失败，逼着做决定。

### 5.2 先更新库再删缓存，及其窗口

**问**：缓存和数据库怎么保持一致？

**要点**：旁路缓存，写时**先更新数据库再删缓存**。

- 不是先删再更新：删除之后、提交之前进来的读会把旧值写回。
- 不是更新缓存：两个并发写，后提交的可能先写缓存。
- 仍有两个窗口：读请求在提交前读到旧行、在删除之后才写入缓存；提交后、删除前进程崩溃。所以必须有 TTL 兜底，**TTL 的长度就是最坏的不一致时长**。
- 进一步缩小：延迟双删、消费自己的事件来删、订阅 binlog 来删。大致分工（通用知识，不是本项目实测）：延迟双删主要针对第一个窗口（过一会儿再删一次，把那个迟到写回的旧值清掉，延迟取多久是猜的）；消费事件或订阅 binlog 删除，是把“删缓存”变成可重试的异步动作，主要针对第二个窗口（提交后删除前崩溃），不会因为进程崩溃而丢。

**本项目**：没有采用。缓存非终态订单需要这套失效逻辑，窗口的后果是用户付完款仍看到“待支付”。省下的只是一次主键查询，不值得。选择了“数据本身决定缓存策略”，从根上绕开失效问题。代价：非终态订单的轮询仍读库；压测若显示这成为瓶颈再重新评估（压测结果待补）。

### 5.3 穿透、击穿、雪崩

| 问题 | 含义 | 本项目的做法 |
|---|---|---|
| 穿透 | 查不存在的数据，每次落库 | 空值缓存（订单 2 秒、SKU 1 秒）；没用布隆过滤器：订单号持续新增，过滤器要持续维护，SKU 数量少 |
| 击穿 | 热点 key 过期瞬间大量请求回源 | 进程内 `singleflight` 加 Redis 互斥（`SET NX PX`），等待有上限（20ms 重读，最多 200ms），超过自己回源但不写缓存 |
| 雪崩 | 大量 key 同时过期或缓存整体不可用 | TTL 加 ±20% 抖动；Redis 不可用时直接回源，错误只记日志 |

可以展开的点：

- **空值缓存的弱点**：攻击者用大量不同的 key 占满缓存，要靠限流和淘汰策略。
- **空值与“已受理未落库”的冲突**（本项目的坑）：受理后落库前 MySQL 没有这一行，若直接写空值，客户端接下来 2 秒都看 404，以为订单丢了。所以写空值之前必须先看闸门占用，有占用就不是“不存在”，且不写缓存。闸门 Redis 不可用时返回 `UNAVAILABLE`、什么也不缓存（不能把“不知道”缓存成“不存在”），代价是此时空值缓存失效，对不存在订单号的查询会打到 MySQL，靠 1d 限流兜底。
- **击穿互斥为什么不用 `pkg/lock`**：它每把锁有个不过期的 fencing 计数器，不能用在无上限的名字上；重建互斥也不需要看门狗和 fencing，锁丢了只是多回源一次。
- **等待上限的意义**：不让“持锁的实例卡住”变成“所有实例一起卡住”。
- 实现时补的细节：等待方每轮重读缓存的同时也重新抢锁（持锁方回源结果可能不写缓存，只等缓存会白等）；拿到锁后先再读一次缓存，否则排队的实例会一个接一个回源；`load` 出错不写缓存。
- 订单缓存关闭了进程间互斥（`DisableLock`）：按订单号的 key 没有热点，互斥让每次未命中多两次往返，而非终态的结果又不写缓存。
- 没采用逻辑过期（值里带过期时间，物理上不过期，过期后只让一个请求去重建，其余直接返回旧值）：它完全不阻塞，适合能接受短暂旧值的热点展示数据；本项目库存 TTL 只有 1 秒，互斥加有上限的等待已够用，少一套机制更容易理解和测试。
- 没用布隆过滤器：适合要过滤的合法 key 集合相对固定、能预先装进去的场景。本项目 SKU 少，订单号每秒都在新增，过滤器要持续维护，空值缓存加限流更合适。
- 已知缺口：Redis 拒绝连接时 go-redis 默认重拨 5 次、每次 100 毫秒，“直接回源”前仍要多等约半秒，要靠熔断消除（1d）。

### 5.4 缓存和不可淘汰数据为什么分实例

**问**：缓存和库存闸门为什么不放同一个 Redis？

**要点**：两者对内存满的要求相反。闸门是系统状态，必须 `noeviction`，内存满了宁可写入报错，因为 key 被淘汰就丢库存；缓存是可重建的副本，内存满了应该淘汰（`allkeys-lru`），也不需要持久化。放在一起，缓存涨满内存会让闸门写入报错，下单失败。**可丢的东西不能和不可丢的东西共享故障域和淘汰策略。**

**本项目**：`CACHE_REDIS_ADDR` 不设时退回 `REDIS_ADDR`；compose 里的 `redis-cache` 实例不开 AOF、`maxmemory 256mb`、`allkeys-lru`。锁仍放在闸门实例上：锁的 key 被淘汰等于凭空释放。

## 6. 压测对比同步与异步接口

**问**：怎么证明异步下单比同步快了一个数量级？怎么比才公平？

**要点**：1a 的提交接口同步返回 201，订单已落库；1b 返回 202，订单只是被受理。直接比每秒请求数比的不是同一件事。要报三个数（设计 7.3.1）：

1. 1a 的下单吞吐（同一个工具打 1a 代码，工具同时接受 201 和 202）。
2. 1b 的**受理吞吐**：用户感知到“抢到了没有”的速度，数量级提升指的是它。
3. 1b 的**落库吞吐**（真正进入 `pending_payment` 的速度）：受 MySQL 限制，预期和 1a 同一量级。

第 2 个远大于第 3 个，差出来的部分排在 Kafka 里，这就是削峰。还要记积压排空耗时。同时记机器、并发数、库存量，本机数据只用于前后对比。

其他可以讲的点：

- **自己写压测工具**（`test/load`）：场景需要“提交、轮询到落库、按比例支付或取消”，还要记下客户端看到的每个结果做对账，用通用工具反而绕。
- **客户端账本对账**：压测同时输出每个请求的结果，事后与服务端核对。“告诉用户成功的事不能丢”（客户端见过 `paid`，库里必须是 `PAID`）；“结果未知”的请求不做断言，只统计。
- **5xx 不等于没执行**：网关调下游超时，订单可能已经落库。账本把 `http_error` 和“结果未知”同样对待，不做断言；提交重试用尽后客户端没有订单号，服务端却可能有这个订单，对账要按用户加幂等键去找。支付和取消没有幂等键，不重试，结果未知的支付直接去轮询订单。
- **杀进程测试**（设计 7.3.2、7.3.3）：压测中随机 `kill -9` 四个服务，结束后等系统静止，再逐条核对 18 项（库存恒等式、订单与预占、订单与支付、闸门与库存、账本、outbox 与死信）。**关键细节：对账期间闸门对账照常开着，但要检查日志里没有出现过修正**，否则兜底机制会掩盖主流程的问题。设计里预先写下了预期会暴露的问题（认领之后被杀、Confirm 已提交 Settle 未执行、宽限期调短后回收与落库竞争更频繁），测试时对照。

**压测结果**（2026-11-12，`scripts/bench.sh`，`make bench`）

机器：Apple M5，10 核（4 性能核 + 6 能效核），32 GiB；四个服务和压测工具跑在 macOS 上，MySQL、Redis、Kafka 跑在 OrbStack 的容器里。**本机数据只用于前后对比**，不代表线上容量。

参数（两边相同）：每档 30 秒，10 个 SKU，每个库存 1 亿（不会卖完），不限购，用户 id 取 [1, 100000]，每单 1 件，`-pay 0 -cancel 0`（只比下单），`PAYMENT_TIMEOUT=1h`，`LOG_LEVEL=warn`，每轮从空库开始。1a 是合并 PR #2 的提交（`732f9ab`），用 `bench1a_*` 库。每格是两次运行的数字（第 1 次 / 第 2 次）。

1b 跑了两种客户端模式。工具的虚拟用户是闭环的：提交、轮询到落库，再下一单（`closed`）。这样 1b 的“受理吞吐”被落库速度卡住，等于落库吞吐，测不出削峰。所以另加 `fire` 模式：轮询时限设为 1ms，提交后只查一次就下一单，近似开环；落库吞吐和 drain 改从库里 `orders.updated_at` 统计。1a 返回 201 不轮询，两种模式一样。

| 并发 | 1a 下单 /s | 1a p50 / p99 ms | 1b 受理 /s（fire） | 1b 受理 p50 / p99 ms | 倍数 | 1b 落库 /s（库） | 1b drain s |
|---|---|---|---|---|---|---|---|
| 50 | 1303 / 1299 | 30.8 / 189；30.2 / 220 | 4750 / 4824 | 2.5 / 8.3；2.5 / 11.1 | 3.7× | 421 / 418 | 311 / 316 |
| 200 | 1256 / 1266 | 123 / 589；123 / 579 | 2146 / 2175 | 4.8 / 245；4.6 / 220 | 1.7× | 408 / 408 | 128 / 130 |
| 800 | 1206 / 1221 | 477 / 2811；475 / 2713 | 3875 / 3818 | 161 / 439；162 / 420 | 3.2× | 377 / 338 | 279 / 310 |

解读：

- **受理吞吐没有达到数量级提升**，最好是 3.7 倍（并发 50），并发 200 时只有 1.7 倍。落库吞吐约 410/s，只有 1a 的三分之一，和设计预期的“同一量级”相符但偏低。削峰本身成立：30 秒受理了 14 万单，之后用 5 分钟排空，没有丢单（库里落库数等于受理数）。
- **1a 卡在 MySQL**：MySQL 容器 CPU 135%–160%，四个服务各自不到 1 核。三档并发吞吐基本不变（约 1250/s），延迟随并发线性上涨，是排队；10 个 SKU 的库存行是热点行，每次预占都要在一次带 fsync 的事务里持有行锁。
- **1b 落库卡在消费并行度**：`eventx.Partitions = 4`，每个分区的消息串行处理，410/s 折合每条约 9.7ms（认领占用、带 outbox 的落库事务）。这时 inventory 只用 0.1 核、MySQL 约 60%，资源都没用满。要提速得加分区，或者在分区内按订单并发处理。
- **1b 受理在并发 50 时主要卡在压测工具的结构**：fire 模式每单还要多一次 1ms 的等待和一次查询，每个虚拟用户一轮约 10.5ms，提交请求本身平均只占 4.3ms。这时 gateway 0.96 核、order 1.44 核、压测工具 0.64 核，10 核的机器还空着一大半，不是 CPU 瓶颈。
- **并发 200、800 时受理反而变慢，而且不是资源耗尽**：gateway 降到 0.33 核，主机一半 CPU 空闲。提交延迟是双峰的：p50 4.8ms，p90 202ms，约 23% 的提交落在 150–260ms。单独测依赖：不压服务时，主机到 Kafka 同步发两条（acks=all），200 并发下 p50 0.5ms、p99 1.2ms、37 万条/s；Redis 跑闸门同类的 Lua 脚本 6.4 万次/s。都远超所需，所以 Redis 往返和 Kafka 同步等待都不是瓶颈。但压测进行时，另开连接、以 4 并发探测 Redis 和 Kafka，p50 仍是 0.15ms 和 0.4ms，最大值却都在 200–210ms。两个不同的容器同时出现约 200ms 的停顿，正好是 Linux TCP 的最小重传超时，推测是 OrbStack 主机到虚拟机的端口转发在连接多、包速率高时丢包重传。这一条没有拿到丢包计数直接证实。它属于本机环境的问题，到集群上应重测。
- **轮询会把落库拖垮**（closed 模式）：非终态订单不缓存，每次轮询都要查一次 MySQL（行不存在）再读一次闸门，和消费者共用 order 服务的连接池和同一个 MySQL。并发 800、每 50ms 轮询一次时约 1 万次/s 查询，落库从 410/s 跌到 43/s，落库 p50 18 秒，MySQL 95%。轮询间隔调到 500ms 后恢复到 340/s。这正是 5.2 节预留的“压测若显示这成为瓶颈再重新评估”：至少应该先读闸门，有占用就直接返回 `creating`，不去查库。
- **积压与回收的冲突**（已修，见 2.7）：受理是落库的 5–11 倍，30 秒的峰值就排出 5 分钟的积压，而占用回收的默认宽限 `HOLD_REAP_GRACE` 只有 1 分钟，排队超过 1 分钟的已受理订单会被当作孤儿回收，用户先看到 202，之后查询变成 404。压测里先把宽限设成了 1 小时绕过。后来在受理端按队列长度做背压（ADR-0011），同样负载零回收；宽限仍要大于可接受的最大积压，并对消费滞后告警。

**杀进程对账结果**（2026-11-12，`make chaos`，每次约 60 秒、杀 14 到 28 次进程；设计 7.3.4）

- 先跑了 5 次，19 项检查（18 条加“日志里没有修正”）全过、死信为零，但暴露了分区停摆 45 秒。把会话超时改成 10 秒后，第一次复跑反而有 12 条下单消息进了死信（分区不停摆了，inventory 重启的空窗才显露出来）；把下单消费者的重试预算调大后，之后每次都全过、死信为零。
- **一致性检查全部通过不等于系统可用。** 45 秒的分区停摆期间，少卖（闸门里剩二三十件一直没人买）、受理的订单被回收（28% 到 33%）都不违反任何一条不变量，检查全绿。第 15 条（受理后被回收）只计数、没有阈值，比例到三分之一也判通过。可用性问题要靠**看比例**发现，检查本身不会报。修复和约束见 1.6。
- 预期的三个问题里，“认领之后被杀”和“Confirm 已提交、Settle 未执行”没有出现（读代码确认重投幂等、重放会补 Settle），但随机杀进程不能证明这两个窗口真被命中过，要证明得做定点注入（阶段 4）；“回收与落库的竞争”出现且量很大，真正的驱动不是重启耗时而是会话超时。
- 局限：库存小的运行很快卖完，在途订单少，覆盖的并发场景有限；库存大的运行更有说服力。
- 没修的小问题：gateway 被杀后，下游把 `context canceled` 记成 ERROR、返回 `Internal`，会干扰按错误级别告警，应映射为 `Canceled` 并降到 info。

## 1b 的已知缺口汇总

- 支付单“已出结果但长期 `notified = 0`”没有任何任务扫描，靠死信和积压告警（对账在 1d）。
- 订单侧不再有库存的兜底（`stock_settled` 已删），库存是否跟上完全取决于事件被消费。
- 认领之后进死信的占用不会自动归还；闸门对账只比汇总量。
- 幂等键过期后重放的用户会看到订单消失。
- 锁只防崩溃不防卡住；Redis 变慢时 Guard 拖慢每一轮（仍未解决，阶段 4 故障实验）。
- Redis 不可用时缓存层每个请求仍多等约半秒，缓存与闸门故障期间对数据库没有限流熔断保护（1d）。
- Redis 丢数据后对账上限不够紧，恢复期会多放订单（不会超卖）。
- 闸门脚本只支持单实例 Redis。
- 落库是串行的（4 个分区，每条约 10ms），落库吞吐只有 1a 的三分之一；轮询会拖垮落库；压测工具是闭环的。这三项挂到 1d；“数量级提升”的验收结论和本机网络丢包的怀疑挂到阶段 2，在集群上重测。
- 静态的 `ADMIT_MAX_QUEUE` 和落库吞吐绑定，落库优化后要重新设定。
- 取消请求被记成内部错误（`context canceled` 记 ERROR、返回 `Internal`），未修。

**已解决**（步骤四）：

- 受理端背压：积压超过回收宽限期导致已受理订单被回收，已按队列长度限流，压测同负载零回收（2.7，ADR-0011）。
- e2e 偶发失败：冷连接池加新连接丢包等 1 秒 RTO，已改固定大小预热的池并合并预热调用，30 次失败 8 次变为 25 次全过（2.8）。
- 会话超时：消费者被杀后分区停摆 45 秒，已设为 10 秒；下单消费者重试预算从约 1.5 秒调到约 26 秒（1.6）。
