# 4a：故障实验的准备，结论和教训

2026-11-24。这份笔记把 4a 学到的东西收成一处，供复习和面试时讲。它不产生新的数，数的出处在设计文档 [4a-chaos-prep.md](../design/4a-chaos-prep.md)（下文“设计”，“设计 6”指第 6 节“实现中的发现和量到的数”）和 [ADR-0041](../adr/0041-two-fault-injection-paths.md)。面试考点在[阶段计划](../plan/phase-4-chaos.md)里以“4a ”开头的三段。

**文档之间不一致的地方，这里采用更晚写的那个**：

- 设计 3.2 以为实验对象建在 `chaos-mesh` 命名空间里，目标命名空间就没有痕迹。不对：NetworkChaos、IOChaos 会在目标 Pod 旁边留下 `PodNetworkChaos`、`PodIOChaos` 对象和事件（设计 6“第 1 步”）。
- 设计 3.3 写的是“一个要传下去的开关集合”“平时的构建里开关永远是关的”，实现是包级的登记表、平时的构建里根本没有这个函数（设计 6“第 2 步”）。
- 设计 3.5 写 Agent 的工具“拒绝” `chaos-mesh`、权限也收掉。实现是“当它不存在”，权限没有收，Prometheus 的工具也筛（设计 6“第 5 步”）。
- ADR-0041 和设计第 2 节写镜像 tag 带 `-faults` 后缀、故障文件叫 `x_variant.go`。走通之后都改了：后缀是 `-p4`，文件按代码在做什么起名（设计 6“第 6 步”的问题 1、2）。

## 1. 结论

1. **4a 的产出**是一套能重复做实验的东西，不是实验本身：
   - 两条注入的路：Chaos Mesh 管从外面造得出来的（杀 Pod、网络、CPU 和内存压力、磁盘、时钟、DNS），`pkg/fault` 管只能预埋的代码缺陷。
   - 场景目录 `chaos/scenarios/<编号>/`（元数据、注入的清单、答案），编号不透明。
   - `chaos-run.sh`（抽场景、密封答案、注入、恢复、对账、揭晓、总闸）和 `chaos-steady.sh`（一条固定速率的压测和“现在是不是稳态”的检查）。
   - 诊断 Agent 多了 `pprof_capture`，并且看不到注入工具。
2. **在长期运行的那一套上走通了两个场景**（设计 6“第 6 步”）：杀 `inventory` 的一个 Pod、打开 `gateway` 的一个故障开关。脚本没有改就通过了，两次对账差异都是 0。
3. **这一步真正难的不是把系统弄坏，是不把答案漏出去。** 盲测和 Agent 的评测都要求“排查的人只看得到症状”。答案漏出去的渠道比预想的多，第 3 节列了走到现在发现的全部。
4. **没有验证的**放在第 6 节，最要紧的三条：盲测那条路一次都没有真的跑过；mutex、block 采样没有打开；只有三个场景。

## 2. 两条注入的路，各自为什么是这样

| | Chaos Mesh | 故障开关（`pkg/fault`） |
|---|---|---|
| 造什么 | 进程之外的：Pod 没了、网络慢了断了、资源被抢、磁盘慢、时钟跳、DNS 坏 | 进程之内的：goroutine 泄漏、无上限的缓存、加锁顺序不一致 |
| 在哪一层动手 | 目标 Pod 的网络命名空间、cgroup、卷、vDSO | 业务包里的一个接缝函数的另一份实现 |
| 怎么保证平时没有 | 命名空间没有注解就不能被注入 | 构建标签：平时的二进制里没有这些代码，`go tool nm` 核对 |
| 怎么保证会结束 | 对象的 `duration` | 开关的 ttl，进程自己关 |
| 留下什么痕迹 | 一部分类型在目标命名空间里留对象和事件 | 调用栈里的文件名和函数名；镜像的 tag |

三个决定值得会讲：

- **为什么不用“常量为 false 的分支”而用构建标签。** 依赖编译器把死分支删掉是一个没有人保证的优化；构建标签是文件根本不参加编译。而且可以检查：对比带标签和不带标签的二进制的符号表。
- **检查要“反过来确认一次”。** `check-faults.sh` 第一版就空转了（`pipefail` 加 `grep -q` 的 SIGPIPE），是“带标签的二进制里应该找得到”那一半先报出来的。只有正向那一半的话它会一直是绿的。
- **开关必须自己会关。** 注入的一方（开发机、脚本）可能在撤销之前死掉。Chaos Mesh 的 `duration` 和开关的 ttl 都是“故障自己带着到期时间”，不依赖注入方还活着。

## 3. 答案从哪些地方漏出去

按发现的先后。前四条是装的时候和写脚本的时候想到或者看到的，后四条是走通时才看到的。

1. **注入工具自己的日志和 Pod。** `chaos-controller-manager` 的日志里写着每一次注入。处理：Agent 的工具把这个命名空间当成不存在；日志采集不收它。
2. **目标命名空间里的 `Pod*Chaos` 对象和事件。** 处理：Agent 的事件工具按 API 组筛掉；人这一侧靠约定。
3. **命名空间的注解。** 只有 Chaos Mesh 的场景才加的话，看有没有注解就能猜出方式。处理：所有注入方式都加。
4. **密封文件的摘要可以穷举。** 场景只有几十个，光对场景编号做 SHA-256，把每个编号算一遍就对出来了。处理：密封的内容里放 128 位随机数。
5. **只有一个服务有 `/fault` 接口。** 处理：五个服务都挂，不管有没有故障点。
6. **镜像 tag 的 `-faults` 后缀。** 它在 Pod 的事件和 describe 里，Agent 第一次走通时读到了，还写进了报告。处理：后缀换成 `-p4`。
7. **故障文件统一的后缀。** `stock_variant.go` 出现在 pprof 的调用栈里，每个故障点都这样叫，见过一次就认得出。处理：按代码在做什么起名。
8. **稳态的压测本身。** Agent 不知道有一条压测在跑，把它当成了“流量涨了 100 倍”，并把原因归到了它上面。这一条不是泄漏，是反过来的：缺了一条该给的背景。给不给，是评测设计要定的事。

**规律**：凡是“只在做实验时才出现”或者“每个故障点都一样”的东西，都是信号。要么让它平时也在（注解、`/fault` 接口），要么让它每次都不一样（文件名），要么让排查的一方读不到（命名空间、日志）。

**挡的是谁要想清楚。** 这里所有的处理挡的都是“无意中读到”，不是一个存心绕过的调用方：Agent 的权限没有收（RBAC 没有拒绝规则），聚合掉命名空间标签的查询仍然把 `chaos-mesh` 算在里面，人这一侧 `kubectl` 什么都看得到。对一个不作弊的被评测者够了；要防作弊得换一套做法（分集群、在查询进后端之前改写）。

**“拒绝”本身是信息。** 指名去读隐藏的命名空间，得到的回答要和它不存在时一字不差。一句“不允许读”等于告诉对方这里有东西，而且是演练用的。和登录接口不区分“用户不存在”“密码错”是同一个道理。

## 4. 走通时量到的和学到的

数都在设计 6“第 6 步”，这里只留结论。

- **正常地杀一个 Pod，什么都不会发生。** `pod-kill` 发的是 TERM，优雅停止加边车把在途的请求做完了：0 个 5xx，没有告警。这说明之前做的优雅停止是管用的，也说明这个场景练不到东西。要练“实例突然没了”得不给宽限期。
- **goroutine 泄漏没有任何告警。** 8 分钟里每个副本从 88 涨到 239，504 占那个接口的约 0.3%，SLO 一条都没有动。这类故障靠告警发现不了，要么等它拖到内存出事，要么有人看运行时指标。要不要补一条“goroutine 数持续上涨”的规则，是 4b 做完这一批实验之后复盘时定的事，不在这里先补（先补就看不到“没有它时会怎样”了）。
- **Agent 拿到了证据，讲错了故事。** 它自己决定抓 goroutine 剖析，找到了停在 `chan send` 的那一处，建议也对路（select 上 `ctx.Done()`）。但它把阻塞的发送理解成了排队，把原因归到了流量上。**工具给对了证据不等于结论对**：评测要分开打“找没找到关键证据”和“根因说没说对”两个分，`truth.md` 本来就是这样分栏的。
- **只抓一次剖析证明不了泄漏。** 泄漏的定义是“只涨不降”，要隔一会儿再抓一次比。Agent 把这一步列在了“下一步”而没有做。工具支持（`base` 参数），是模型没有用。
- **刚恢复就查稳态会 1 秒通过。** 稳态看的是 3 到 5 分钟窗口的比例，刚撤掉注入、刚滚动重启时它还没有反应。处理：恢复动作之后先等 180 秒。同一类问题在 3e 遇到过一次（`increase` 的窗口里不够两个点）：**按窗口算的指标，对“刚刚发生的事”是瞎的**。
- **有负载时逐行对账慢了一个数量级**（8 分钟的窗口 160 秒，没有负载时 24 分钟的窗口约 15 秒）。每次实验收尾 6 到 12 分钟，排实验的节奏时要算进去。

## 5. 脚本里值得记的几个做法

- **命名空间用白名单，不用黑名单。** 能被注入的只有 `oppenheimer` 和 `oppenheimer-e2e`。“拒绝那四个”的写法在第五个出现时就漏了。
- **总闸不依赖运行的状态。** `recover --all` 不看哪个运行在进行中，直接删所有实验对象、关所有副本上的所有开关、去注解。状态文件坏了、脚本被 `kill -9` 了，它仍然能用。
- **注入完就返回，恢复才阻塞。** 注入的脚本不等故障到期：故障自己会结束，脚本一直挂着反而多一个会死的东西。
- **故障开关只对注入那一刻的副本生效。** 之后扩容或者重启出来的副本没有开关，故障会悄悄变弱。泄漏类的场景要么钉住副本数，要么改成启动时读配置。4b 写这类场景时定。

## 6. 没有做的、留给后面的

- `blind`（随机抽、终端不打印内容）没有真的跑过；`recover --all --restart`、注入中途失败的撤销、开关到 ttl 自己关，也没有。
- `istio`、`script` 两种注入方式没有样例场景；`s003`（网络）没有跑过；经边车的 gRPC 那条路上 NetworkChaos 的延迟是什么样没有量。
- mutex、block 采样没有打开（要用 3b 的压测量开销）；`pprof_capture` 的 `cpu`、`heap`、`base` 没有对着真的故障用过。
- `mysql-main` 的 `MALLOC_ARENA_MAX=4` 没有验证（走通时连接最多 97 个，要到 200 以上才看得出）。
- 关于 `chaos-mesh` 自己的告警发给 Agent 时没有筛。
- 带 `-p4` 后缀和改了文件名的镜像还没有部署（集群上是改之前的 `9dda461-faults`）。
- 3c、3e 留下的告警验证（计划文件“4a 准备”的最后一项）在 4b 对应的实验里做。

## 7. 面试时怎么讲

- **“你们怎么做故障演练的”**：两条路（外部注入和预埋开关）各管什么、为什么需要第二条；每个场景一份清单加一份答案；注入前检查稳态，结束后对账；答案密封，排查的人和 Agent 都看不到。然后讲第 3 节：最费劲的是不漏答案，举镜像 tag 和文件名两个例子。
- **“故障代码怎么保证不上生产”**：构建标签加符号表的对比，加“反过来确认一次”的故事。
- **“演练发现了什么”**：正常杀 Pod 没有任何影响（优雅停止管用）；goroutine 泄漏没有告警；窗口型的指标对刚发生的事是瞎的。
- **“AI 诊断靠不靠谱”**：用 `s001` 那一次：它找到了证据、给了对路的建议、讲错了原因。所以要把“证据”和“根因”分开评，也所以它现在只读、只给人看。
