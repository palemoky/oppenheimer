# 3b：容量结论

2026-11-22。设计文档 [3b-load-testing.md](../design/3b-load-testing.md) 3.6 节要的那份结论。它不产生新的数，只把 [3b-rounds/](3b-rounds/) 里十份记录的结果收成一处；每个数后面标了出处（“R4 1.1”指 round-4 的第 1.1 节），要核对或者要看条件时去那里。记录里标了“推断”“没有验证”“每组只跑一次”的，这里保持同样的说法。

**和设计 3.6 不一致的地方**：3.6 要“每个服务单副本的能力”和“1、2、4 个副本的扩容系数”。前一个按原样的问法量不出来（先到顶的始终是节点，不是某个服务，R6 3.4），这里改成“每个请求的 CPU 开销”；后一个量了，答案是 1.0 和 0.8，也就是没有收益。计划文件里这一条的措辞 2026-11-22 已经改过。

## 1. 结论

1. **这套硬件上有三个限制，哪一个先到取决于请求的组合和持续的时间。**
   - 写入：**盘的同步刷盘**。持续 125 到 150 单/秒（普通下单的组合）。
   - 其余的一切：**两个工作节点的 16 个 vCPU**。读多写少时 1907 请求/秒，售罄的秒杀在 4000 到 8000 请求/秒之间。
   - 持续几个小时以上：**磁盘的空间**。上限由 binlog 和 Kafka 的保留期决定，不由吞吐决定。
2. **没有哪一个服务是瓶颈。** 到顶的是节点，所有东西一起慢。所以“某个服务单副本能扛多少”在这里没有答案，能给的是每个请求花多少 CPU（第 4 节）。
3. **节点不变时，加副本不加能力，还要多花 CPU**：1 个和 2 个副本的拐点相同，4 个副本低一档。读从库也一样：主库省下的 CPU 原样出现在同一批节点的从库上。扩容必须带着节点一起加，而这套硬件只有两个工作节点，加节点时的扩容系数量不了。
4. **HPA 的机制验证过（扩容期间 69 万个请求 0 失败），但在这两个节点上是关着的**：上限和下限都是 2。requests 按实测写了之后第三个副本放不下，这是调度器在说同一件事。
5. **`GOALS.md` 的五个目标**：零超卖和对账两项做到了（3b 里对账过的每一轮都是 0 差异）；受理 p99 低于 200 毫秒在拐点以下做到了；“5000 QPS 的秒杀”要拆成两句话才能答（第 8 节）；1 亿数据量不做（第 8 节，主人 2026-11-22 定）。

## 3. 各个场景的上限

拐点的判据是设计 3.3：受理 p99 超过 200 毫秒、5xx 超过 0.1%、`BACKLOGGED` 持续出现、积压单调上涨，任何一条出现就算过了，拐点记作上一档。

| 场景 | 拐点 | 先到顶的 | 拐点上的延迟 | 过了拐点先出现什么 | 出处 |
|---|---|---|---|---|---|
| 普通下单（每单带轮询、五成支付、两成取消） | 持续 **125 到 150 单/秒**（入口上约 565 到 680 请求/秒） | 盘的同步刷盘 | 受理 p99 45 毫秒，落库延迟 p99 2.4 到 3.2 秒（125 单/秒，4 小时） | 落库延迟上涨，之后 `429 BACKLOGGED` | R0、R2 第 10 节、R9 |
| 同上，盘在快的一档 | 约 240 单/秒，只能当几分钟的突发 | 节点的 CPU（92%、98%） | | | R2 第 3 节 |
| 只下单不支付（秒杀有货时的落库） | 落库 287 单/秒 | 盘 | 落库延迟 p99 27 秒（过载中量的） | | R4 2.2 |
| 混合读写（读九成） | **1907 请求/秒**（其中下单 148 单/秒） | 两个工作节点的 CPU（87% 到 97%）；下单那一份同时走到了落库的拐点 | 各接口 p99 在 100 毫秒内；受理 p99 在 94 到 191 毫秒之间晃（同样的配置多次量的范围） | 全部接口一起慢五到八倍；gateway 到 inventory 的并发上限溢出（503） | R4 第 1 节、R6、R8 |
| 秒杀，售罄之后 | 4000 请求/秒很轻（p99 不到 20 毫秒）；7986 请求/秒已经过了（下单 p99 368 毫秒，入口每秒 20 个 `503 UO`）。**拐点在两者之间，没有再细分** | 入口的 Envoy（单个 Pod，2.08 核）和 gateway 的 CPU | | 入口 `503 UO` | R4 第 2 节 |
| 秒杀，有货 | **低于 500 次迭代/秒**（量的最低一档已经过了） | 节点的 CPU，是“等落库的订单的轮询”推上去的 | | 入口 `503 UO`、`READ_BUSY`、受理 p99 0.9 秒 | R4 第 2 节 |

另外几个单项的数：

- **支付出结果**：改成并发之后每秒 76 笔（R1）。它和落库抢同一块盘，上面“普通下单”的数已经含着它。
- **闸门 Redis 的内存**：每持续 1 单/秒稳态约占 1.5 MiB（幂等键留 1 小时），768 MiB 的上限对应约 500 单/秒。线性外推，没有实测（R9 2.2）。它不是当前的限制，离盘的上限有三倍多的余量。
- **受理的队列上限 2500**：125 单/秒 4 小时里一次没有碰到（R9 2.3）。

**所以“这个系统能扛多少”没有一个数。** 要先问请求的组合，再问持续多久。

## 4. 每个请求的 CPU 开销

代替“单副本能力”的那个数。单位是毫核·秒（一个请求用掉的 CPU 时间，等于“核数 ÷ 每秒请求数”）。

**按场景，整套服务合计（2 个副本）**

| 场景 | 业务容器加边车 | MySQL | 出处 |
|---|---|---|---|
| 混合读写，每个到达入口的请求（1907 请求/秒时） | 4.0（7.63 核） | 1.2（2.31 核） | R6 2.1、R8 第 3 节 |
| 普通下单，每一单（100 单/秒时；一单是入口上约 5.4 个请求） | 35（3.50 核） | 15（1.49 核） | R6 2.2 |
| 普通下单，每一单（125 单/秒 4 小时的平均） | 34（4.30 核） | | R9 2.1 |
| 售罄的秒杀，每个请求，只算 gateway 加它的边车 | 0.59 | 不碰数据库 | R4 2.2 |

**按服务，每个到达 gateway 的请求（混合读写 1907 请求/秒，1 个副本，R6 3.4）**

| 服务 | 业务容器 | 边车 |
|---|---|---|
| gateway | 0.61 | 0.33 |
| order | 0.61 | 0.18 |
| inventory | 0.38 | 0.17 |

这几个数怎么用、有多不稳：

- **随请求的组合变两倍多**。gateway 自己看：混合读写 1.56、普通下单 2.0（2 个副本，含边车，R8 第 2 节）；order 按 gRPC 请求算是 3.1 和 4.2。
- **随副本数变四成**。同样的 1907 请求/秒，业务容器加边车在 1、2、4 个副本时是 5.1、7.6、8.4 核（第 5 节）。
- **边车约是业务容器的三分之一到一半**（R6 2.1 的各档）。没有做“有边车对没边车”的对照。
- **全量导出链路占业务容器 CPU 的 14% 上下**，头部采样 10% 就能拿回几乎全部（设计第 6 节“第 5 步的对照”）。
- 粗算整个系统：混合读写在拐点上两个工作节点用了约九成，折下来每个请求约 7 到 8 毫核·秒，其中服务和边车占一半，其余是 MySQL、Kafka、Redis、入口、监控的采集和内核。这一条是用节点使用率折的，使用率里含不含等 IO 的时间没有核对，只当量级用。

## 5. 水平扩容和读从库都没有收益

**加副本（R6）。** 五个服务一起钉到 1、2、4 个副本，别的都不动，跑同一个混合读写的阶梯：

| 副本数 | 拐点（请求/秒） | 相对上一组 | 1907 档业务容器加边车的 CPU（核） |
|---|---|---|---|
| 1 | 1907 | | 5.1 |
| 2 | 1907 | 1.0 | 7.6 |
| 4 | 1526 | 0.8 | 8.4 |

- 写入和副本数无关：三组的落库都是 99 单/秒上下，由盘决定。
- 为什么没有用：先到顶的是节点的 CPU，不是哪个进程。Go 的服务本身用得上多核（1 个副本的 order 在 1907 档只用 1.2 核），拆成两个进程，CPU 一核没多，活一点没少。
- 为什么还要倒贴：pprof 里多出来的主要是调度和系统调用。“流量分散后每个进程更闲、批处理被摊薄”是推断，没有单独验证。
- 修掉了入口“连接上限被空闲连接占满”的缺陷之后重跑，4 个副本的拐点仍是 1526（R6 第 7 节）：那个缺陷让 4 个副本更难看，但不是它更差的原因。

**读从库（R7）。** `window`、`gtid` 两种模式都把七成多的订单读分到从库，主库 CPU 降三分之一，三组的拐点都是 1907。主从在同一批节点上，到顶的是节点。集群上保持 `primary`。

**这两条结论管不到的地方**：

- 加节点时的扩容系数没有量（只有两个工作节点）。那时瓶颈会移到共享的部分：MySQL（1907 档已经用 2.3 到 2.4 核）、Kafka、入口的单个 Pod。
- 单个服务被框住时的上限没有量。
- 每组只跑了一次；节点 95% 时 p99 自己就能晃出一倍。

**2 个副本留着的理由只剩可用性**（滚动、节点故障时不断），不是容量。

## 6. requests 和 HPA 现在的数，以及依据

**CPU requests**（R8 6.1）：取的是 2 个副本、混合读写 1526 请求/秒（拐点的八成）时每个 Pod 的实测用量，再统一乘 0.9（不乘的话滚动时多出来的那个 Pod 放不下）。CPU limits 不设。

| | requests |
|---|---|
| gateway | 700m 加边车 400m |
| order | 700m 加边车 250m |
| inventory | 450m 加边车 250m |
| payment、orderindex、cdc | 150m |
| 入口的 Envoy | 700m |
| `mysql-main` | 550m |
| 订单库（主从同一个数） | 400m |
| Kafka 的 broker | 400m |
| redis-cache、redis-gate | 100m |

两个工作节点的 requests 合计 5.75、6.10 核（可分配各 7.5）。服务和中间件必须一起按实测调：只调服务的那一步，节点满时中间件分到的 CPU 权重少了将近一半，过载时入口多拒一个数量级（R8 第 3 节）。

**HPA**（gateway、order，KEDA，请求速率和 CPU 两个触发器取大的）：

| | 现在 | 依据 |
|---|---|---|
| 副本数的下限和上限 | 2 和 2 | 第三个副本加滚动多出的一个放不下；加了也不加能力 |
| CPU 触发点 | requests 的 70% | requests 按实测写了之后这个百分比才有意义 |
| 每副本的请求速率（`perReplica`） | gateway 450、order 200 | CPU 触发点 ÷ 混合读写时每个请求的 CPU（便宜的那种组合）；组合变贵时由 CPU 那一项接住 |

上限是 2 的时候这些阈值不起作用。机制是在上限 3、阈值 500 和 220 时验证的（R8 第 4 节）：600 升到 1221 请求/秒，从负载上升到新 Pod 接到流量约 75 秒，690972 个请求 0 失败，落库不受影响。**加节点之后要做的是把上限改回去，并且重量一次拐点**，不是照抄现在的阈值。

**随副本数漂的几处配置**（R6 第 4 节、R4 2.2），改副本数时要一起看：

- 边车的并发上限、连接池、订单读的名额是按 Pod 给的，总量跟着副本数走。
- 热点限流（每个 SKU 500 次/秒）的桶在 gateway 的进程里，2 个副本实际是 1000。
- order 的连接池每库 40，是按“(HPA 上限 + 1) × 连接池 ≤ `max_connections` − 40”倒推的，上限改了要重算。

## 7. 持续负载：上限由保留期决定

长稳那一轮（R9）之前，每一轮压测只有几分钟，看不到这一条。

- 125 单/秒持续时，agent-2 的盘每小时少 4.4 GiB，其中 3.9 是日志：`mysql-main` 的 binlog 每小时 1.4 GiB，订单库每个实例 0.83，Kafka 每个 broker 0.78。原来的保留期（binlog 30 天、Kafka 7 天不限大小）都是没人配过的默认值，按它算稳态要上千 GiB，而盘只有 150。
- 2026-11-22 改成 binlog 1 天、Kafka 24 小时（每分区 4 GiB 兜底）、死信 7 天。按量到的速率算，125 单/秒持续时 agent-2 上这几样的稳态是 93 GiB，可用的约 124 GiB。**改完之后没有再跑长稳验证磁盘走平。**
- 由此推出来的两个数（**都是线性外推，没有实测**）：
  - 日志这一项撑得住的持续速率约 165 单/秒（125 × 124 ÷ 93）。它和盘的刷盘上限（125 到 150）碰巧在同一个量级：再把写入的上限往上推，先撞上的会是磁盘的空间。
  - 日志走平之后，表数据和压缩保留的 `cdc.order.orders` 仍然跟着订单数涨。agent-2 上量到的 4.4 减去日志的 3.9，每小时约 0.5 GiB，一天约 12 GiB；余量 30 GiB 上下，也就是**持续 125 单/秒大约能跑两到三天**。这个差值是两个量出来的数相减，误差大。
- 保留期缩短的代价是可回溯的时间变短（CDC 停超过 1 天要重做全量；一个分区被挡住超过 24 小时会丢消息），3c 的告警按它来设（计划文件 3c 已经写了）。

容量的三样东西各有各的公式：吞吐看瓶颈资源的速率，内存看“速率 × TTL × 单个大小”，磁盘看“写入速率 × 保留期 × 副本数”。前两样在短的压测里看得到，第三样只有长稳看得到。

## 8. 对 `GOALS.md` 的修正

| 原来的目标 | 量到的 | 修正 |
|---|---|---|
| 下单接口峰值 5000 QPS（秒杀场景） | 售罄之后：4000 请求/秒很轻，约 8000 请求/秒已经过了拐点。有货时：受理被背压限制在落库的速率上，只下单不支付时落库 287 单/秒，带支付和取消时持续 125 到 150 | 拆成两条，见下 |
| 下单 P99 延迟低于 200 毫秒（受理） | 普通下单 125 单/秒：45 毫秒。混合读写的拐点上：94 到 191 毫秒。过了拐点不保证 | 保留，加上“在拐点以下” |
| 订单数据量灌入 1 亿级 | 灌了 1000 万；这套负载下数据量不是变量（R5） | 不做，见下 |
| 零超卖 | 3b 里对账过的每一轮都是零超卖，包括过载的几轮 | 不变 |
| 对账最终一致 | `recon` 每一轮差异 0 | 不变 |

**“5000 QPS 的秒杀”为什么要拆。** 这句话把两件不同的事说成了一件：

- **到达速率**（有多少请求打到入口）。售罄之后每个请求在闸门上就被拒了，不碰数据库，系统很轻：4000 请求/秒没有问题，到顶的是入口的单个 Envoy Pod 和 gateway 的 CPU。5000 落在量过的两档之间，没有直接量过；按 4000 档的余量看多半过得去，但这是估计。
- **受理速率**（有多少单真的被接下来）。这个数由落库决定，和到达速率无关：背压把受理压在落库速率加一个队列（2500 单）的量上。5000 单/秒的受理在这块盘上做不到，差一个半数量级。

而且有货时的难点不在下单本身：500 次迭代/秒就把节点打满了，因为每个被受理的订单都有人在轮询等落库，请求量被放大到到达的五倍（R4 2.2）。更高的到达速率下有货的秒杀会怎样，没有量过（库存要给到 50 万以上，R4 2.3）。

**1 亿数据量不做（主人 2026-11-22 定，按下面的建议）。** 理由：

1. **现有的负载量不出它的影响。** 下单、查最新的订单、取列表的第一页只碰索引的右边缘和一小块热数据，空表和 1000 万量不出差别（R5）；1 亿多半也一样。要量“数据量大了哪里会慢”，得先加一个随机读历史订单和深翻页的 k6 场景，这是 1 亿之前就该做的事，在 1000 万上就能看到缓冲池（订单库 1 G）放不下的效果。
2. **现在的盘放不下，要先扩盘。** 按 1000 万时的大小乘十：订单库每个实例 34 到 43 GB，`mysql-main` 约 30 GB，agent-2 上（`mysql-main` 加两个订单库实例）要 100 GB 以上，现在剩 89 GiB；灌数当天的 binlog 和 `cdc.order.orders`（现在约 1470 万单占每个 broker 5.5 GiB，按比例 1 亿是近 40 GiB）还没有算。宿主机的卷组还有约 240 GB 没有分，`vm.sh resize` 能扩（一次一台，对运行中的节点有什么影响没有查）。以上都是按比例估的。
3. **耗时按小时算**：5000 单/秒灌 9000 万单要 5 小时；逻辑备份的恢复按比例是一小时的量级，要换物理备份才合理（设计第 6 节第 4 步）。

如果以后要做，合适的位置是阶段 4 的备份恢复实验（那里本来就要面对“逻辑备份到多大就不能用了”），前提是先扩盘、先有随机读的场景。分片方案本身 1c 已经在功能上验证过，1 亿验证的是它在数据量下的运维代价，不是它对不对。

**再往上要付什么（估算，不做）。** 主人 2026-11-21 定了接受现在的写入拐点（R2 第 10 节末尾）。记下各条路能换来多少：

| 做什么 | 能换来多少 | 依据 |
|---|---|---|
| 换有掉电保护的盘（刷盘不再是 4 到 11 毫秒） | 写入到约 240 单/秒，然后撞上节点的 CPU | 盘在快的一档时量到过 239 单/秒，当时节点 CPU 92%、98%（R2 第 3 节） |
| 每单的提交次数减半（改受理到支付的事务边界） | 同上：盘上的数翻一倍，同样撞上 CPU | 没有量，按“落库一单两次提交”推的 |
| 加工作节点 | 不知道。读路径应该能涨，共享的 MySQL、Kafka、入口会成为下一个限制 | 没有量（R6 3.4） |
| 链路改头部采样 10% | 业务容器的 CPU 省一成多 | 设计第 6 节“第 5 步的对照” |
| 入口多个 Pod 分担（MetalLB 换 BGP 或者前面再加一层） | 只对售罄的秒杀有用 | 没有量；入口的单个 Pod 在 8000 请求/秒时用 2.08 核 |

前两条加起来也只到 240：这套硬件上盘和 CPU 两堵墙离得很近，推开一堵马上是另一堵。

## 9. 没有量的

结论里没有、以后有人问起要老实说“没有量”的：

- 加节点时的扩容系数；单个服务的上限。
- 有货的秒杀在 500 次/秒以上的表现；售罄的秒杀在 4000 到 8000 之间的拐点；有货那一档落库延迟为什么到 27 秒（按队列上限算应该在 9 秒内）。
- 随机读历史订单、深翻页；1 亿数据量。
- 改完保留期之后磁盘是不是真的走平；混合读写的长稳（跑的是普通下单）；文件描述符、MySQL 的 undo 和临时表。
- 长稳里没有查原因的三件小事：gateway 的堆每个 Pod 每小时涨约 1.5 MiB；闸门 Redis 的内存在键数走平后还涨了约 20 MiB；读的舱壁几乎只拒 `read_db_1`。
- 中间件的 requests 调完之后，拐点以上 MySQL 的查询耗时和落库延迟为什么没有回到改之前（R8 6.2）。
- 绝大多数对照每组只跑了一次。

## 10. 面试时怎么说

- **“你这个系统能扛多少 QPS”**：没有一个数。普通下单持续 125 到 150 单/秒，读多写少 1900 请求/秒，售罄的秒杀四千以上；先到顶的分别是盘、节点的 CPU、入口。先说组合，再说先到顶的是什么、是怎么确认的（拐点那一档从外往里看每种资源的使用率和饱和度）。
- **“单个服务能扛多少”**：这个问法在这套硬件上答不了，因为单个服务从来不是瓶颈。能答的是每个请求花多少 CPU，以及它随请求的组合变两倍、随副本数变四成，所以按请求速率定的阈值只对一种组合成立。
- **“加副本为什么没用”**：加副本加能力有前提，副本带来了新的资源，或者单个进程有自己扩不上去的瓶颈。两条都不满足时，拆进程只是多付调度和边车的开销。量到的扩容系数是 1.0 和 0.8。
- **“那 HPA 还有什么用”**：机制是对的（扩容期间不丢请求验证过），收益要等有新节点。requests 按实测写了之后调度器放不下第三个副本，比放上去之后大家一起变慢要好。
- **“5000 QPS 的秒杀做到了吗”**：先分清到达和受理。到达几千没有问题，因为售罄的请求在 Redis 上就结束了；受理由落库决定，这块盘上是一两百。秒杀最难的是有货的那一段：削峰压平了写入，没有压平“等结果”的读。
- **“瓶颈是硬件还是软件”**：两堵墙都是硬件（一块没有掉电保护的消费级盘，16 个 vCPU），但各有一半是软件决定的：落库一单提交两次；边车和全量的链路导出占了服务 CPU 的一大块。知道每一项值多少，决定不去做，也是结论的一部分。
- **容量不只是吞吐**：持续负载下的上限是磁盘的保留期决定的，而保留期是没人配过的默认值。短的压测看不到，长稳才看得到。
