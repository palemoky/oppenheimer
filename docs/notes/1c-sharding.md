# 1c 笔记：订单数据怎么分、怎么复制、怎么查、怎么扩、怎么归档

这份笔记整理 1c 里值得在面试中讲的点，按主题组织，不按开发步骤。每条按“面试官会怎么问 → 要点 → 本项目里怎么做、量到了什么数、踩过什么坑”来写。设计全文见 [design/1c-sharding.md](../design/1c-sharding.md)（下文简称“设计”，引用章节号），取舍见 [ADR-0002](../adr/0002-app-level-sharding.md)、[ADR-0012](../adr/0012-shard-layout.md) 到 [ADR-0016](../adr/0016-cold-archive.md)。

1c 做的事：订单按 `user_id` 分成 8 个逻辑分片、2 个库（后来演练扩到 4 个）；每个库一主一从，读写分离加读己之写；自研 Go CDC 把 binlog 同步到按商家分片的索引表，支持商家维度的查询；造 500 万订单量分片均匀度和各类查询的延迟；在有流量时把 2 个库扩成 4 个；终态的老订单归档到独立的压缩冷库。

“本项目”里的数字都是本机（Apple M5，OrbStack 里的容器）上量的，只用于前后对比，不代表线上容量。标了“通用知识”的段落是设计文档里没有的，来自公开资料，面试前对照官方文档核对一遍。

## 1. 分片键与布局

### 1.1 分片键怎么选

**问**：订单分库分表，分片键选什么？为什么？

**要点**：好的分片键要同时满足：

- 最常见的查询条件里都有它，这样大多数查询只落一个分片。
- 取值分布够散，不会把流量集中到少数分片。
- 一条数据的归属在创建后不变，否则一次更新就变成跨分片的“删加插”，没有事务保证。
- 事务涉及的数据都能带上它，这样本地事务够用，不需要跨库事务。

订单的候选是订单号、用户号、商家号。按订单号哈希最均匀，但“我的订单”要扫全部分片；按商家号分片，大商家会把一个分片压垮，而且一个商家的数据不可拆；按用户号分，C 端的主要查询（我的订单、下单、支付、取消）都落一个分片，单个用户的数据量有限，倾斜小。代价是商家维度的查询没有分片键（见第 5 节）。

**本项目**（ADR-0002、设计 2.1）：`slot = user_id & 7`。数据实测印证了倾斜的判断（设计 5.11）：用户按 Zipf 分布，最重的用户有 5.4 万单（占 1%），但被 8 个 slot 稀释之后，订单行数最多的 slot 与最少的之比只有 1.22，两个库之比 1.01。同一批订单如果按商家分，最大的商家一家就占全部订单的 28%（136 万单），独占商家索引一个 slot 的七成，最多与最少之比 3.37。**倾斜来自“一个键下的数据量不可拆”，加 slot 稀释不了，要么把大商家单独放，要么在商家之下再拆。**

### 1.2 基因法

**问**：按用户分片后，只有订单号时怎么知道去哪个分片查？

**要点**：三种办法：（1）维护“订单号到分片”的映射表，多一次查询，而且这张表自己要高可用、要分片；（2）按订单号再哈希，但这样订单号和用户号的分片不一致，两种查询只能二选一；（3）**基因法**：生成订单号时把分片键的低几位嵌进订单号，只凭订单号就能算出分片，不需要任何查询。要求分片数是 2 的幂且不超过基因位数，否则取模对不上。限制是：基因位数决定了最多支持多少个 slot，以后要超过只能改 ID 的格式。

**本项目**：订单号最低 6 位是 `user_id` 的低 6 位（`idgen.GeneOf`），所以对任何不超过 64 的 2 的幂 N，`order_id % N == user_id % N`。`ForOrder(id) == ForUser(user)` 对 idgen 生成的订单号恒成立（设计 2.2）。订单号来自外部输入（HTTP 路径、Kafka 消息）时，按它算出的 slot 里查不到就是不存在，不用去别的分片找。

两处校验把“基因不一致”变成明确的错误（设计 2.4、2.6）：`store.InsertOrder` 要求订单号的 slot 与 `user_id` 的 slot 一致，否则返回错误（写进去之后按用户和按订单号会找到两个不同的分片）；落库消费者要求完整的 6 位基因都相等，不等就当毒消息处理（记 ERROR、不重试、在认领占用之前拒绝）。前者是“写进去就找不到”的硬约束，后者是“上游有缺陷”的信号，所以后者更严。

### 1.3 slot 与库的两级映射

**问**：为什么不直接把分片键哈希到库，而要中间加一层逻辑分片？

**要点**：分片数固定、库数可变，中间用一层逻辑分片（slot）隔开：路由只算 slot（纯计算），slot 在哪个库是另一张映射。扩容时 slot 整个搬走，行落在哪个 slot 永远不变，不需要重新计算每一行的归属。对比：

| 方案 | 扩容时 | 问题 |
|---|---|---|
| 直接 `hash % 库数` | 库数变，几乎所有行的归属都变，要重新洗牌 | 搬迁量接近全量 |
| 一致性哈希 | 只搬一部分 | 适合节点频繁增减、数据能重算的缓存；订单迁移代价高，扩容是计划内的低频操作，成倍加固定 slot 数更简单，搬迁量能精确算出 |
| 固定 slot 加 slot 到库的映射（本项目） | 整个 slot 搬走 | 只能成倍扩容（取模映射下）；slot 数是上限 |

**本项目的具体选择**（ADR-0012、设计 2.1）：

- 8 个 slot（基因有 6 位，最多可到 64）。现在用 8 个，以后表太大可以把 slot 数翻倍：`orders_k` 里 `user_id & 15` 为 `k + 8` 的行拆到新表，只涉及一张表内的行。
- `db = slot % 库数`，不是 `slot / 4`。取模映射下 2 库扩 4 库，slot `s` 从 `s % 2` 号库搬到 `s % 4` 号库：旧库 0 的一半（2、6）去新库 2，旧库 1 的一半（3、7）去新库 3，每个旧库只拆给一个新库，库的编号不变。区间映射下要给旧库重新编号。
- 表名带**全局** slot 号（`orders_3`），不是库内表号。表名全局唯一，搬 slot 时表原样搬走不用改名，路由只算一次 slot，不是先库后表两步。
- `payment_results` 也按 slot 拆：它只在“锁住订单行”的事务里读写，必须和订单在同一个库；按 slot 拆则搬 slot 时整表搬走，不用从一张表里挑行。
- slot 数、库数必须是 2 的幂，库数不超过 slot 数，`pkg/sharding` 构造时校验。
- 没选 64 个 slot：每个库 32 组表，测试和本机的建表开销偏大。
- 只拆 order，payment、inventory 保持单库：1c 要学的东西在 order 上都能覆盖，再拆是重复劳动。

### 1.4 分片后的全局唯一和分片内唯一

**问**：分片之后，原来靠主键、唯一索引做的检查还成立吗？

**要点**：唯一索引只在**一张表内**有效。分片后同一个逻辑表的数据散在多张物理表里，唯一约束只能保证分片内唯一。要么让唯一值本身带上分片键（订单号里有基因，所以订单号全局唯一由“分片内唯一加基因”推出），要么放弃全局的数据库级保证，改由别处负责。自增 id 也是：各库各自的自增列会重复，不能直接当全局 id。

**本项目**：

- `payment_results` 的主键只在 slot 内唯一。1a 里有个防御检查“同一个 `payment_id` 已经记在另一个订单上”，分片后只有两个订单恰好在同一个 slot 才查得出来，基本失效（设计 2.6）。它本来只防上游缺陷（payment 保证一笔支付只对应一个订单号），失效的代价可以接受，`GetPaymentResult` 的注释里写明了。真要全局查，得在 payment 一侧做（它是单库）。
- outbox 行的 id 是各库自己的自增列，两个库都会有 id 为 1 的行（见 3.1）。
- 订单号的全局唯一：基因加时间戳加节点号加序号（见第 2 节）。

## 2. 分布式 ID

### 2.1 方案对比和雪花算法

**问**：分布式 ID 有哪些方案？雪花算法有什么问题？

**要点**（通用知识）：

| 方案 | 优点 | 问题 |
|---|---|---|
| 数据库自增，各库设不同步长 | 简单，严格递增 | 每次要访问数据库，扩容时步长要改，难以带分片信息 |
| 号段模式（一次从数据库领一段） | 数据库压力小，趋势递增 | 发号服务要高可用，重启会丢一段（有空洞） |
| UUID | 无中心，随机 | 128 位、无序，作 InnoDB 主键会让 B+ 树页随机分裂，索引占空间 |
| Redis `INCR` | 快 | 持久化和主从切换可能回退，发号退回成一个必须高可用的依赖 |
| 雪花算法 | 无中心，趋势递增，64 位 | 依赖时钟，节点号要分配，时钟回拨要处理 |

雪花的几个固有问题：（1）**时钟回拨**会生成重复 ID，必须检测，小幅回拨可以等，大幅回拨只能拒绝服务；（2）**节点号分配**：同一个节点号同时只能有一个生成器在用，否则重复，实例多了要有分配机制；（3）同一毫秒的序号用完了要等下一毫秒；（4）时间戳位数决定可用年限；（5）趋势递增而不是严格递增，同一毫秒内不同节点的先后不严格，用时间顺序做业务判断时不可靠。

**本项目**（`pkg/idgen`，设计 5.3）：63 位有效位，自高到低：41 位毫秒时间戳（相对 `Epoch`，约 69 年）、6 位节点号（最多 64 个）、10 位序号（每节点每毫秒 1024 个）、6 位分片基因。基因放在**最低位**，所以 `id % N == 分片键 % N`；时间戳在最高位，同一节点的 ID 随时间严格递增，对 B+ 树主键友好（造数时订单号按时间递增生成，主键顺序插入，页不分裂）。

- 时钟回拨：回拨不超过 5 毫秒（`maxBackwardWait`）时原地等待，等完仍然落后或超过 5 毫秒返回 `ErrClockMovedBackwards`，拒绝发号。序号用完时等到下一毫秒。
- 订单号里的时间是真的，所以它可以拿来做别的用途：分页游标（高位是毫秒时间戳，按订单号倒序就是按创建时间倒序）、冷热判断（第 8 节）、按时间分区（`idgen.LowerBound(t)` 把“早于某个时间”换成主键范围）。**把业务含义放进 ID 就要承担它的约束**：ID 的时间必须可信，格式一旦发号就不能改。
- 对外接口里 64 位整数用 JSON 字符串（1a 的考点，浏览器的数字是 double，超过 2^53 丢精度）。

### 2.2 Epoch 为什么不能改

**问**：雪花 ID 的起始时间能不能改？

**要点**：不能（有数据之后）。`Epoch` 是时间戳的零点，改了以后旧 ID 解出的时间全部错位；新旧 ID 之间不会重复（代码注释的结论），但“越晚生成越大”的顺序被破坏，按 ID 排序不再等于按时间排序，依赖这个顺序的分页、冷热判断、分区边界都会错。

**本项目**：这一条在 1c 里被“实操”了一次，是个反面教材。造数工具需要生成 2020 年起的订单，而 Epoch 是 2026-01-01，订单号造不出更早的时间。设计 5.3 比较了三个办法：（A）把 Epoch 提前到 2020-01-01，本机开发库清空重建；（B）Epoch 不动，数据只铺满 2026 年到今天；（C）往未来灌。选了 A，**理由只有一个：这是练习项目，没有不能丢的数据**。代码注释（`idgen.Epoch`）和设计都明确写了“一旦有 ID 生成就不能再改”，真实系统里这样做不可行。面试里可以这样说：我知道规则，也知道自己在什么前提下破了一次例。

## 3. 分片之后的周边问题

### 3.1 outbox 每库一个中继，中继名为什么必须不同

**问**：分库之后，outbox 怎么办？

**要点**：outbox 的作用是“和业务写在同一个本地事务里”，所以它必须和业务表在同一个库，每个库一张。每个库要有自己的中继。同一订单的事件仍然有序：同一订单的所有状态变更都在同一个库，经过同一个中继、同一个消息 key，到同一个 Kafka 分区。

**本项目**（设计 2.4）：中继名分别是 `order-0`、`order-1`，各有自己的 leader 锁（`order:outbox-relay:0`、`:1`）。**名字必须不同**：event-id 是 `<中继名>:<outbox 行 id>`，行 id 是各库自己的自增列，两个库都会有 id 为 1 的行。名字相同时两条不同的事件 id 相同，按 event-id 去重的下游会丢掉其中一条。事务提交后只踢事务所在库的中继。

outbox 不按 slot 拆，是因为它的行很短暂（发布后保留 1 小时），扩容搬 slot 时不用搬它，只要先把旧库的 outbox 发完（见 7.5）。

### 3.2 CHECK 约束名是库级唯一的

**问**：分表后建表脚本有什么坑？

**要点**：MySQL 里**索引名是表级唯一，CHECK 约束名是库（schema）级唯一**。同一个库里放多张同构的表，约束名不带分片号，第二组表就建不出来。

**本项目**（设计 2.6）：迁移是 `text/template`，为本库每个 slot 渲染一组表，约束名带 slot 号（`chk_orders_{{.}}_total`、`chk_order_items_{{.}}_quantity`），索引名不用带。扩容时搬表、建表的工具也要遵守。

### 3.3 迁移：多实例同时启动的互斥，DDL 隐式提交与可重入

**问**：多个实例同时启动，都跑迁移怎么办？迁移进程中途被杀怎么办？

**要点（互斥）**：

| 方案 | 做法 | 取舍 |
|---|---|---|
| `GET_LOCK` 会话锁 | 在一条专用连接上拿命名锁，迁移完释放 | 简单，不需要额外的表。会话级：连接断开（含进程被杀）时服务端自动释放，不会留下死锁。锁名要带库名，否则多个库互相阻塞。要占住一个连接；不适用于经过连接池代理、会话不固定的场景 |
| 锁表加租约 | 在表里写一行，带过期时间，持有者续租 | 不依赖会话，能跨代理；要建表、要心跳、要处理租约过期后旧持有者还在跑 |

**要点（可重入）**：MySQL 的 **DDL 隐式提交**，不能放进事务里回滚。一个迁移版本里有多条 DDL，进程在中间被杀就留下“前几条做了、后几条没做、版本号没记”的状态。所以迁移必须写成**可重入**：`CREATE TABLE IF NOT EXISTS`；没有 `IF NOT EXISTS` 的语句（`ALTER TABLE ... ADD COLUMN`、加索引）先查 `information_schema` 判断是否已做过。

**本项目**（设计 2.6.1、4.2、5.2）：

- goose v3.30.0 的 MySQL 没有会话锁（只有 Postgres 的，和一个要建锁表带租约的表锁），所以 `mysqlx` 自己用 `GET_LOCK` 实现了 goose 的 `SessionLocker`：锁名带库名，两个分库互不阻塞，等锁最多 60 秒。原来代码里的注释说 goose 用咨询锁，实际没有配置，评审时发现的。
- 分片后一个版本里有 13 条建表语句，所以 `00001_init.sql` 的建表全改成了 `IF NOT EXISTS`。
- **每个 `ADD COLUMN` 前先查**：`00002` 给 8 张 `orders_N` 各一条 `ALTER`（`merchant_id` 和 `version` 两列放在同一条里，单条 DDL 原子），每条前面用 `information_schema.columns` 判断列在不在，在就用预处理语句执行 `DO 0` 跳过（`SET @ddl = IF(...)`、`PREPARE`、`EXECUTE`）。goose 在同一个连接上执行一个版本里的所有语句，所以会话级的用户变量能用。`00003` 的索引变更同样先查 `information_schema.statistics`。一个版本里最多放一条这样的语句，这是规则。
- **一个测试的教训**：“多个实例同时在空库上迁移”去掉锁也能通过，因为 goose 建版本表失败后会等 1 秒重试，恰好把几个实例错开。能暴露问题的场景是“版本表已存在、有一个待应用的版本”。测试要能在去掉被测机制时失败，否则钉住的是一个不存在的问题。
- 扩容时这个要求变成必须（设计 5.7）：新库是从旧库拷贝来的，没有 goose 的版本记录，order 启动时所有迁移会在它上面重跑一遍，建表是 `IF NOT EXISTS`，加列加索引先查后做，都会跳过，只新建一张空的 `outbox`。
- 局限：inventory 的 `00001`（3 条建表）和 payment 的 `00002`（建表后跟一条 `ALTER`）有同样的问题，没有改。
- 测试里另一个发现：迁移续跑测试假设只有两个版本，加了 `00003` 之后 goose 报“出现了比库里版本号更低的未执行迁移”，测试要把之后的版本记录一起去掉（设计 5.11）。

### 3.4 连接池预算

**问**：分库之后连接池怎么配？

**要点**：每个库一个池，总连接数 = 副本数 × 库数 × 每个池的上限，要和每个 MySQL 实例的 `max_connections` 对着算。分库后同一个服务的连接总数按库数成倍增长；加从库又是一组池。池太大把数据库压垮，太小则请求排队。

**本项目**（设计 2.6.1）：本机所有服务连同一个 MySQL，`max_connections` 默认 151，分片前 order、inventory、payment 各 50，刚好 150。分片后 order 仍用 50，两个库就是 100，合计 200，超上限后新连接被拒（Too many connections）。所以 `MYSQL_MAX_OPEN_CONNS` 改成**每个库的上限**，默认 25，两个库合计 50 与分片前持平。步骤二把库拆到各自的实例上之后，每个池只占自己那个实例的预算，可以调大；从库另有一个池，上限沿用同一个配置。

### 3.5 后台扫描按分片设超时

**问**：后台任务要扫所有分片，一个库挂了怎么办？

**要点**：驱动没有设读超时时，一个“连得上但不响应”的库会让查询一直等，整轮卡在它上面，其他库的数据也扫不到。每个分片单独设时限，超时记日志并跳过，下一轮再来；不能让一个分片拖住全部。

**本项目**（设计 2.4、2.6.1、3.9）：sweeper 每个 slot 一个时限（`SlotTimeout`，默认 10 秒），某个库不可用时跳过它的 slot 并记日志。sweeper 读从库时只用一半的时限：从库挂起时不能把整个时限耗光，否则退回主库时已经没有时间，兜底任务会跟着从库一起停摆。后台扫描是明确豁免的全分片扫描（任务本来就要看所有数据，逐个 slot 扫，不需要合并排序）。

### 3.6 事务绑定在一个 slot 上

**问**：分库后不能跨库事务，业务怎么保证？

**要点**：让事务的边界天然落在一个分片内（以一个订单为中心），把“不允许跨分片”变成运行时检查，而不是靠约定。跨分片的一致性靠本地消息表加补偿（工程规范：不用 XA，见 1b 笔记 1.1）。

**本项目**（设计 2.4）：`store.InTx(ctx, orderID, fn)` 返回的 `Tx` 记住自己的 slot，`LockOrder`、`MarkPaid` 等只操作这个 slot 的表；传入不属于这个 slot 的订单号时返回错误，而不是悄悄去查别的表。有测试覆盖。

## 4. 主从复制与读写分离

### 4.1 主从延迟的成因

**问**：主从为什么会延迟？

**要点**（通用知识）：异步复制下，从库收到 binlog 的 IO 线程和应用 binlog 的 SQL 线程是分开的，延迟可以出现在任一环节：

- **网络**：主库到从库的带宽或往返时延。
- **从库回放慢**：早期的 SQL 线程是单线程，主库并发写、从库串行放；8.0 之后有基于组提交的多线程回放，仍然受并行度影响。从库的机器规格、磁盘比主库差，或者从库上还跑着查询占用 IO 和 CPU。
- **大事务**：一个大事务在主库提交后才进 binlog，在从库上要整体回放，期间后面的事务都排队。大批量删除、大批量更新是典型来源。
- **从库上的锁等待**：从库上的长查询阻塞回放线程的 DDL 或某些语句。
- **DDL**：从库上重放同样要执行一遍。

延迟变大往往恰好出现在系统出问题的时候，所以“靠延迟小”不能作为正确性依赖。

**本项目**：本机主从没有出现自然的延迟，验证用的是人为制造（在从库上 `STOP REPLICA SQL_THREAD`，停着就是延迟无限大，启动就是追上）。归档大批量删除时是真实的延迟来源，这一点在 8.5 里：实测每 10 秒采样一次，四个从库延迟最大 1 秒，因为归档任务拿复制延迟做反馈限速。没有自然延迟的量化数据，要如实说。

### 4.2 读写分离按用途划分，不按语句类型

**问**：读写分离怎么做？哪些读能走从库？

**要点**：中间件或驱动按“是不是 SELECT”自动路由，应用不用改，但会把事务里的读、写后马上的读、用来做决定的读都送到从库，要再用注解或提示一条条拉回来。**哪些读能容忍旧数据是业务知识**，放在方法名上比放在路由规则里清楚。原则：**用来做决定的读走主库，只用来展示的读可以走从库。** 走从库的读的结果不能成为任何写的前提。

**本项目**（ADR-0013、设计 3.2）：

| 读 | 走哪里 | 理由 |
|---|---|---|
| `GetOrder`（对外查询） | 从库，受读己之写规则约束 | 只展示，读流量主体 |
| sweeper 的两类扫描 | 从库 | 只是找候选，真正的转换是主库上带前置条件的更新，从库旧了只会晚一轮发现 |
| `CancelOrder` 之后的复查 | 主库 | 据此告诉用户取消是否成功 |
| 落库时订单号重复后的读取、`dropReplay` | 主库 | 写路径上的决定 |
| 延迟关单消费者读订单 | 主库 | 读到的状态决定重试还是放弃 |
| 受理时幂等键重复后的查询 | 主库 | 用户刚提交过，最容易读到旧数据 |
| 事务内的所有读 | 主库 | 事务在主库上 |
| 用户订单列表 | 主库 | 见 4.6 |

`store` 的接口分两类：现有方法都读主库，展示读是单独的方法（读从库），不做透明路由。

### 4.3 从库旧了会出什么问题

**问**：读到从库的旧数据具体会造成什么后果？

**本项目**（设计 3.3）：三种，严重程度不同：

1. **订单凭空消失**（最严重）：订单落库前，`GetOrder` 靠 Redis 闸门里的占用合成一个 `CREATING` 的订单；走到终态后占用被归还，如果这时从库还没有这一行，查询返回 404，而且“不存在”还会被缓存 2 秒。订单明明存在。
2. **状态倒退**：取消返回了 `CANCELLED`，紧接着查询看到 `PENDING_PAYMENT`。
3. **状态停滞**：已经从 `CREATING` 进入待支付，查询还是 `CREATING`。轮询的客户端晚一点看到可以接受，但实现上和第 2 种分不开。

后两种是“读己之写”问题：用户（或代表他的系统）刚写过，随后的读必须看到这次写。别的用户晚一点看到没关系，订单只有它的主人能查。

### 4.4 读己之写的几种做法

**问**：怎么保证用户写完立刻读到自己的写？

**要点**：

| 做法 | 原理 | 失效条件 | 代价 |
|---|---|---|---|
| 一律读主库 | 最简单 | 无 | 没有分离，主库读压力不降 |
| 固定窗口 | 写之后一段时间内（几秒）这个订单的读走主库 | 复制延迟超过窗口时，标记过期了从库还没追上，读到旧数据；窗口取长了更多读压在主库。**窗口靠猜，而延迟变大恰恰是出故障的时候** | 一次 Redis 写 |
| GTID 等待 | 写完记下主库的 GTID 位置，读时先在从库上等它追到这个位置（`WAIT_FOR_EXECUTED_GTID_SET`，带超时），追到才读，超时读主库 | 标记（记录的位置）过期后从库仍然落后；Redis 不可用时没有位置可等 | 每次写多一次取 GTID 的主库查询加一次标记写；每次带标记的读多一次等待 |
| 客户端带位置 | 写的响应里带回位置，读的请求带上它 | 服务端不存状态也不依赖缓存，但要改对外接口；而且订单的状态变更有一半不是用户的请求触发的（落库、支付结果、超时关单），客户端拿不到那些写的位置 | 接口和客户端都要改 |
| 按用户而不是按订单打标记 | 一个标记覆盖用户所有订单 | 读主库的范围更大 | 对列表有用 |

**本项目**（ADR-0013、设计 3.4）：`ORDER_READ_MODE` 在 `primary`、`window`、`gtid` 三种间切换，便于对比。标记放在**闸门那个 Redis 实例**上（不淘汰），放缓存实例的话标记被淘汰等于悄悄读到旧数据。

- `window`：写之前打标记，保留 3 秒，有标记读主库。
- `gtid`：写之前打 pin 标记，提交后另外记下主库此刻的 `gtid_executed`，保留 1 分钟。读时：有 pin 读主库；否则有 GTID 就在从库上等它追到（默认最多 100 毫秒），追到读从库，超时读主库。所以 `gtid` 等于“窗口内读主库，窗口过后按 GTID 等”，窗口可以配得比 `window` 模式短。
- 两个 key：`order:rw:pin:<订单号>`（写前打，到期自己消失）、`order:rw:gtid:<订单号>`。
- **GTID 取 `@@global.gtid_executed`**，是“到此刻为止主库执行过的全部事务”，比“我这次事务”多，所以等它追上是偏保守的但一定正确。更精确的是用 `session_track_gtids` 让服务端在应答里带回本次事务的 GTID，但 go-sql-driver/mysql v1.10.1 没有把它暴露出来。
- **GTID 只往前更新**：同一订单可能有两个写的一方交错（支付结果和超时关单）：甲先提交、先读到 GTID，乙后提交、后读到，但甲写 Redis 比乙晚，就会用较旧的集合盖掉较新的。所以读 GTID 时一并读出主库的时间，Redis 里用脚本比较，只接受更晚读到的那个（较晚读到的集合一定包含较早的）。
- **只在确实写了数据之后记 GTID**：条件更新没有生效（被别人抢先）的事务不记，抢先的一方自己会记（设计 3.9）。
- 实测（设计 3.10，e2e 用停 SQL 线程制造延迟，两个分片各跑一遍）：从库里有旧行、主库上已取消、标记已过期时，`gtid` 模式读到已取消，那次查询耗时 104 到 115 毫秒，就是等满 `ORDER_READ_GTID_WAIT` 后退回主库；`window` 模式读到旧的待支付，耗时约 5 毫秒。`window` 的已知局限被用例记录下来，不是判为失败。
- 没做的：不同延迟下三种模式读主库比例、对落库吞吐的影响。没有指标统计读走了哪里，本机吞吐测量在 1b 已被证明不可靠，挪到阶段 3。要如实说“对比实验没做完”。

### 4.5 为什么标记要在写之前打，“不存在”只由主库确认

**问**：标记什么时候打？订单查不到时返回什么？

**要点（写前打标记）**：提交之后才打标记，“已提交、标记还没写上”的那一小段读会走从库；进程恰好在这里崩溃，这个订单在标记本该存在的整个时间里都可能读到旧数据。先打标记再写，最坏是写失败、标记白打，代价只是几次读走了主库。**宁可多读主库，不冒读到旧数据的风险**——这是不确定时的默认方向。

**要点（“不存在”）**：从库的“没有这一行”有两种含义：真不存在，或者还没复制过来。所以“订单不存在”这个结论只能由主库给出。这一条不依赖标记：标记过期、Redis 出错、延迟再大，都不会把一个存在的订单答成 404。代价是查询不存在的订单要读一次主库，“不存在”的结果有 2 秒缓存挡着。

**本项目**（设计 3.4、3.9）：`GetOrder` 在从库查不到行、闸门里也没有占用时，最后一次复查读主库。进一步：**占用已被认领时，展示读改读主库**。原来从库查不到行、闸门里有占用时，直接从占用合成 `CREATING`，从库落后时主库上已经待支付的订单会被答成 `CREATING`，状态倒退。认领发生在写订单行之前，所以“已认领”说明主库上可能已经有行；未认领说明落库还没开始，照旧合成。这样从库“缺一行”在任何情况下都不会给出错误的答案，剩下的局限只有一种：标记过期之后，从库里**有**这一行但状态是旧的。

其他退回主库的情形：从库不可用、等待超时、Redis 读标记失败。写的一方打标记失败则继续写，不因为 Redis 抖动拒绝业务写入，这是一个已知缺口。

### 4.6 为什么用户列表读主库

**问**：用户订单列表能走从库吗？

**本项目**（设计 5.2）：不能（实现时改的，原来打算走从库）。读己之写的标记是按订单打的，列表是“这个用户的一组订单”：要读从库，得证明这个用户最近写过的每个订单都已经复制过去，而刚落库的新订单正是从库上没有、读的一方也不知道该去查哪个标记的那一行。按“不确定就退回主库”读主库。查询只扫一个分片里 `idx_orders_user` 的一小段，主库多承担的代价不大。以后要分流，需要在写订单的每个地方按用户再打一份标记，没做。

### 4.7 `WAIT_FOR_EXECUTED_GTID_SET` 的超时为 0 是无限等待

**问**：用 GTID 等待有什么坑？

**本项目**（设计 3.8，MySQL 9.7 官方文档加本机实测）：`WAIT_FOR_EXECUTED_GTID_SET(集合, 超时)` 返回 0 是追上，1 是超时。超时的单位是秒，实测接受小数（0.1 约 100 毫秒）。**超时为 0 表示一直等下去**，不是立即返回，所以 `store.WaitReplica` 拒绝不大于 0 的超时（这是能把请求挂死的坑）。它只看这台服务器上已经应用了哪些 GTID，不管复制线程开着还是停着：线程停着时就是等到超时。

### 4.8 半同步复制解决的是什么

**问**：半同步复制能解决读到旧数据吗？

**要点**：不能。半同步复制保证的是**主库提交前，至少一个从库已经收到（写入中继日志）这个事务的日志**，所以主库宕机时不会丢已提交的事务（解决的是“不丢数据”）。但“收到”不等于“已应用”：从库的 SQL 线程可能还没回放，这时读从库仍然读到旧数据。异步复制下，主库宕机可能丢掉最后几个已提交的事务；半同步（`AFTER_SYNC` 模式）让这个窗口基本关闭，代价是每次提交多等一次往返，从库慢或断开时会退化回异步（超时后）。

**本项目**：ADR-0013 把半同步列为“考虑过但与读到旧数据无关”，设计 3.1 明确半同步和主库故障切换都不在 1c 做（放到阶段 4）。异步复制下主库宕机可能丢掉已提交的事务这一点，直接影响了 CDC 该读哪里（见 5.5）。

### 4.9 容器重建后复制起不来：中继日志名

**问**：主从复制遇到过什么环境类的问题？

**本项目**（设计 4.13，步骤二留下的缺陷，步骤三才暴露）：给 MySQL 加 `--binlog-row-metadata` 要重建容器，重建后两个从库的复制线程都启动失败（错误 1872）。原因是从库没有设 `--relay-log`，**中继日志的文件名默认取主机名**，而容器的主机名是容器 ID，每次重建都变；复制元数据里记着旧文件名，新实例找不到。`make down` 再 `make up` 同样触发，步骤二验证时没走过这条路径。MySQL 启动日志里其实有一条警告说的就是这件事。

修了两处：compose 里固定 `--relay-log=relay-bin`；复制脚本在 `START REPLICA` 失败时执行 `RESET REPLICA ALL` 再重新配置。**为什么重置复制元数据是安全的**：用的是 GTID 自动定位（`SOURCE_AUTO_POSITION = 1`），位置不来自复制元数据，而来自从库自己的 `gtid_executed`，主库按它补发，所以重新配置既不丢也不重复。修完后核对过主从的 GTID 集合一致，又做了一次 `make down`、`make up`，复制自己恢复。

另外两个环境细节（设计 3.8）：MySQL 9 默认认证插件是 `caching_sha2_password`，连接不是 TLS 时从库必须指定 `GET_SOURCE_PUBLIC_KEY = 1`，主库才给出 RSA 公钥（没有校验主库身份，生产应当用 TLS 加证书校验）；`super_read_only` 不能写在 compose 启动参数里（官方镜像首次启动要写系统表，会失败），改为复制建立后由脚本 `SET PERSIST`，代价是容器首次启动到脚本跑完之间从库可写。

## 5. 非分片键查询：CDC 加商家索引表

### 5.1 非分片键的查询怎么办

**问**：订单按用户分片，“某个商家的订单列表”怎么查？

**要点**：几种办法：

| 办法 | 说明 | 取舍 |
|---|---|---|
| 全分片扫描加归并 | 每个分片查一遍再合并 | 延迟取决于最慢的分片，分片越多越差，分页要处理（见 6.1） |
| 另存一份按查询维度分片的数据（异构索引） | 本项目的选择 | 要同步，有延迟，多一份存储 |
| 搜索引擎（ES） | 任意条件筛选 | 又一套系统，最终一致 |
| 离线或分析库 | 聚合、任意条件 | 不是在线路径 |

**本项目**（设计 4.1、4.9）：商家索引表 `merchant_index_db_{0,1}`，4 个 slot，`slot = merchant_id & 3`，表名 `merchant_orders_{slot}`，主键 `(merchant_id, order_id)`，另有 `(merchant_id, status, order_id)`。同步靠自研 Go CDC 读 binlog 发到 Kafka，`orderindex` 消费后写索引表。

### 5.2 为什么用 CDC，不用双写，也不用业务事件

**问**：索引表怎么和订单保持同步？为什么不在写订单时顺手写索引？

**要点**：

- **应用层双写**：两个库之间没有事务，写完一个崩溃就不一致，要另做补偿；业务代码每多一条写路径就要记得再写一次索引。
- **消费业务事件**（outbox 发到 Kafka 的 `OrderEvent`）：行得通，事件和状态变更在同一个事务里，不丢。区别在于事件是发布方决定发什么、什么时候发，绕过业务代码的变更（人工修数、归档任务、忘了发事件的新写路径）它看不到；还要让上游为某一个下游改事件格式。
- **CDC（读 binlog）**：binlog 记的是**库里实际发生了什么**，不依赖业务代码配合；后面的归档、对账、人工修数都能被它看到。代价是要多一套组件，位点、全量、表结构变更、主从切换都要处理。

**本项目**（ADR-0014）：选 binlog。这一步的学习目标也是 CDC 本身，ADR 里写明：实际工作里两者都要会评估。ADR-0014 还对比了**用 CDC 替换 outbox 的轮询中继**（Debezium outbox 模式：业务仍在事务里写 outbox 表，由 CDC 读 binlog 来发）：好处是没有轮询间隔的延迟、没有“扫未发布的行”对库的压力（1b 记录的“轮询拖垮落库”正是这个问题）；代价是发布依赖 binlog 保留和 CDC 位点，outbox 表变成只写不读，清理要另外做。只做了书面对比，没有实现。

**自研还是 Canal、Debezium**（ADR-0014）：Canal 约 1 GB，Debezium 约 1 GB 加 Connect，本机放不下；自研是一个 Go 进程，几十 MB。更重要的是位点、全量衔接、表结构、顺序这些问题正是学习目标，用现成工具等于把答案藏在配置项后面。ADR 里也明说：生产环境里没有特别的理由应该用 Debezium，自研要自己承担数据类型、DDL、主从切换的各种边界情况；要同步的表变多、出现需要关联多张表才能生成的下游数据、或需要不停机的大表全量时，应当重新评估。

### 5.3 binlog 格式与 CDC 原理

**问**：CDC 是怎么读到变更的？binlog 有几种格式？

**要点**：CDC 伪装成一个从库：向主库（或从库）发 dump 请求，按 GTID 或文件位置从某个点开始接收 binlog 事件流。binlog 格式：

| 格式 | 记什么 | 对 CDC |
|---|---|---|
| STATEMENT | SQL 语句 | 不可用：只有语句，拿不到行的值，还有非确定性函数的问题 |
| ROW | 每一行改前改后的值 | CDC 的基础 |
| MIXED | 大部分 statement，不安全的语句用 row | 不可靠，CDC 要求 ROW |

ROW 格式下还有 `binlog_row_image`：`FULL` 记整行的前后映像，`MINIMAL` 只记变化的列。CDC 要完整的行映像才能拿到整行数据、判断更新前后的版本号。另外行事件里只有按位置排列的值，没有列名；列名要么去库里查当前的表结构，要么让 MySQL 把列名写进 binlog（`binlog_row_metadata=FULL`）。事务的边界是 XID 事件，GTID 事件在事务开头。

**本项目**（设计 4.3、4.8、4.13）：本机主从都是 `log_bin=ON`、`log_replica_updates=ON`、ROW 格式，binlog 保留 30 天。`binlog_row_metadata=FULL` 的意义：**“查库得到的是现在的表结构”和“产生那条日志时的表结构”有时间差**——CDC 在追旧日志时查到的是“现在”的结构，Debezium 为此专门维护一个表结构历史的 topic。`FULL` 让每个 TABLE_MAP 事件带上当时的列名，CDC 不用查库，也就没有这个时间差。go-mysql v1.16.0 的 `RowsEvent.Table.ColumnNameString()` 对本机的 MySQL 9.7.4 能拿到列名（设计里写明这是动工时第一件事要验证的，取不到就退回查库加 DDL 触发刷新）。

**表结构变更的约定**（设计 4.8）：加列，新列自动出现，消费者忽略不认识的列；删列或改名，消费者需要的列缺失时，这条消息是毒消息，消费停住并报错，不跳过——所以删列要按“先让所有消费者不再依赖它，再改表”的顺序做；8 张表的 DDL 不是同时完成的，中间不同 slot 的消息列不一样，按列名取值的消费者不受影响。

**一个实际踩到的细节**（设计 4.13，有测试钉住）：**全量和增量对同一行必须给出相同的映像，有两处天然不同**：`BINARY(n)` 列，MySQL 写 binlog 时去掉尾部的 `0x00`，`SELECT` 返回的却是补满 n 字节的值，`request_hash` 恰好以 `0x00` 结尾的订单两条路径会给出不同的值，CDC 按 TABLE_MAP 里的列长度补齐；`FLOAT` 列在 binlog 里是 32 位，直接转 64 位和 `SELECT` 的文本对不上（订单表没有浮点列，也对齐了）。`ENUM`、`SET`、`BIT`、`JSON` 两条路径的表示不同，没有处理（订单表里没有）。

### 5.4 位点：为什么记 GTID 集合，什么时候推进

**问**：CDC 的位点怎么存？什么时候推进？

**要点（位点的形式）**：位点可以是“文件名加偏移”，也可以是 GTID 集合。文件名加偏移绑死某一台机器的 binlog 文件，主从切换、换源后就没意义；GTID 标识的是事务本身，和机器无关，换源后仍然有效，所以记 **GTID 集合**。

**要点（什么时候推进）**：两条规则：

1. **只在事务边界推进**（XID 事件）：重启不会从事务中间开始，不会把一个事务切成两半。
2. **先确认消息落盘，再推进位点**：先推进位点、消息还没发成功就崩溃，这批变更永久丢失；先确认再推进，崩溃后从位点重读，最多重发一个间隔内的事务，这是**至少一次**，下游靠幂等去重（见 5.6）。

**本项目**（设计 4.5）：位点存在 Kafka 的压缩 topic `cdc.checkpoint` 里，key 是流水线名。源是只读的从库，没法把位点写回源库；另找一个 MySQL 又多一个依赖；本地文件换机器就丢，阶段 2 上集群后不可用；Redis 那个实例是闸门用的，位点丢了要重做全量，不该放一起（ADR-0014）。每隔 1 秒：等到目前为止发出的消息全部得到确认，再把“最后一个完整发出的事务”对应的 GTID 集合写进位点 topic。生产者开幂等和 `acks=all`，**发送失败不跳过**，遇到重试解决不了的错误进程退出，重启后从位点再来。

- **为什么不用 Kafka 事务把“发消息”和“写位点”做成原子的**：franz-go 支持，但下游无论如何要幂等（它自己的消费位移和写库也不是原子的），有了幂等，上游的恰好一次没有额外收益，只多了事务的开销和超时要处理。
- **位点在源库上已经被清掉**（`gtid_purged` 里有位点之后的事务）时，CDC 拒绝启动并报错，由人决定是否重做全量。自动重做会把“binlog 保留期配短了”这种问题盖住。
- **同时只应有一个实例**读同一个源：两个实例不会出错（下游幂等），只是每条变更发两遍；没有加选主，靠部署保证单实例。

### 5.5 从主库读还是从库读 binlog

**问**：CDC 读主库还是从库？

**要点**：从主库读延迟最低。但异步复制下主库宕机时，可能有已提交但从库没收到的事务：从主库读的 CDC 已经把这些事务发给了下游；切换到从库之后它们在新主库上不存在，下游就比新主库多出数据，而且没有办法自动发现。**从从库读，下游看到的永远不超过从库已有的**，提升这个从库后两边一致。代价：同步延迟叠加了复制延迟，从库停了 CDC 也跟着停；不占主库的连接是次要好处。

**本项目**（ADR-0014、设计 4.3）：从从库读，DSN 可配、能指回主库。**配套的约束**（ADR-0014“后果”里最有深度的一条，是 orderindex 的子 Agent 评审时指出的）：行版本号的正确性依赖“CDC 的源就是将来被提升的那个从库”。如果 CDC 读的是主库，它可能已经把旧主库上的版本 3（比如已支付）发给了下游，这个事务在新主库上不存在；新主库上同一个订单会再长出一个内容不同的版本 3（比如已关闭），下游按“版本更大才接受”把它当成重复丢掉，索引停在一个源库里不存在的状态上，直到这个订单下一次更新。所以读源和版本号这两个决定是配套的；一个分片有多个从库时，切换后要对没被提升的那些源重做全量。主库切换没有演练过，要等阶段 4。

另外 CDC 的源 DSN 必须指向一个固定的实例，不能是负载均衡或虚拟地址（设计 4.13）：全量里“读 G”和“分批读”必须在同一台机器上（见 5.7）。

### 5.6 至少一次投递下的幂等和定序：行版本号

**问**：CDC 至少一次，下游怎么保证不重复、不乱序应用？

**要点**：分区内有序只能保证**正常情况**下的顺序，挡不住**重放**：CDC 从位点重启后，把已经发过的 `v3, v4, v5` 又发了一遍，消费者已经应用到 `v5`，按顺序再应用就是先退回 `v3` 再回到 `v5`，最终结果对，但中间有一段读到旧状态。全量和增量衔接的地方也是同样的问题。所以每条变更要带一个**能比较新旧的版本**，消费者只接受更新的：应用变更变成可交换的，乱序、重复都收敛到版本最高的那个映像。

版本从哪里来：

| | 从日志位置派生（GTID 事务号） | 行上的 `version` 列 |
|---|---|---|
| 业务代码 | 不用改 | 每条更新都要 `version = version + 1` |
| 会不会漏 | 不会 | 新写一条更新忘了加，这次变更就被丢 |
| 换主库之后 | 新主库的事务号从另一个序列开始，不可比 | 不受影响 |
| 全量读到的行 | 行里没有位置，只能用“全量开始时的位置”代替，且全量必须是精确对应某个位置的一致性快照（要短暂加全局读锁） | 行自己带着版本，全量可以是普通的分批读 |
| 还有 | `updated_at`：语句执行时的墙上时钟，不保证递增（回拨、同一微秒） | 触发器维护的 `version`：不会漏，但逻辑藏进库里，也给以后的在线改表工具添麻烦 |

**本项目**（ADR-0014、设计 4.6）：采用行上的 `version` 列（`orders` 加 `version BIGINT NOT NULL DEFAULT 0`，5 条更新语句都在 `store.go` 里加 `version = version + 1`）。它让“全量加增量”和“换源”这两个最容易出错的地方变简单：任何来源的行映像，版本高的赢。弱点（忘了加）用 CDC 自己来补：更新事件里有改之前和改之后的整行，发现前后 `version` 相同就记错误日志并计数，测试里断言这个计数为 0。

**换源时版本号放在行上起了作用**（设计 5.8）：订单从库 0 搬到库 2，binlog 换了一份，GTID 的来源也换了；如果版本号从日志位置派生，换库之后新旧版本没法比较。放在行上的版本号跟着数据走，搬到哪里都连续。另外设计里也提到：从库的 `gtid_executed` 里有两个 uuid（主库的事务，加上从库自己的 5 个本地事务），正是“事务号只在同一个 uuid 内可比”的情况（设计 4.13）。

### 5.7 `ON DUPLICATE KEY UPDATE` 的赋值顺序

**问**：用 upsert 实现“只接受更高版本”，有什么坑？

**要点**：MySQL 的 `ON DUPLICATE KEY UPDATE` 里**赋值从左到右执行，后面的表达式读到的是前面已经改过的值**。写成 `IF(new.src_version > src_version, new.xxx, xxx)` 逐列判断时，`src_version` 这一列必须**放在最后**赋值；如果先赋值，后面每一列的比较都变成“新版本大于新版本”，永远为假，行就只有版本号在涨，其他列都不更新。

**本项目**（设计 4.6）：索引表的写入语句里每一列都是 `IF(new.src_version > src_version, new.列, 列)`，`src_version` 放在最后，设计要求有测试钉住这一点（这是个静悄悄的 bug，不钉住就看不出来）。

### 5.8 全量加增量怎么衔接，有行版本号时为什么不需要一致性快照

**问**：CDC 初始化要先同步存量数据，存量和增量怎么衔接？

**要点**：经典做法是全局读锁加一致性快照加记下 binlog 位置，然后快照读完从该位置接增量，要求快照和位置精确对应；Debezium 有不加锁的增量快照（DBLog 水位线算法）。

**本项目**（设计 4.7）：位点 topic 里没有这条流水线的记录时：（1）在源上读出当前的 `gtid_executed`，记为 G，连同“全量进行中”写进位点；（2）逐张 `orders_N` 按主键分批读（`WHERE order_id > ? ORDER BY order_id LIMIT n`），每行发一条 `op=READ`，每批发完把“读到哪张表的哪个主键”写进位点，中断后从那里继续；（3）全部读完后从 G 开始读 binlog，转入增量。

正确性论证：G 之前提交的状态，分批读一定看得到；G 之后提交的任何变更都在 binlog 里 G 的后面，增量阶段会发出来；分批读期间行被改了、新行插在已读位置之后，都属于后一种。全量读到的映像可能比增量里的某条新，也可能旧，**版本号保证留下的是最新的**。所以不需要一致性快照、不需要全局读锁、没有长事务；代价是 binlog 必须保留到全量读完（现在 30 天）。读 G 和分批读必须在同一台机器上。带全量游标的位点在续传前、全量做完转入增量前各检查一次 G 之后的日志有没有被清掉（全量可能做很久）。实测：扩容后两个新源做全量，260 万行用了约 20 秒（设计 5.11）。

### 5.9 索引表的分片键为什么必须不可变，一个订单只属于一个商家

**问**：商家索引表设计上有什么约束？

**要点**：**索引的分片键如果可变**，一次更新就要变成“旧分片删、新分片插”，两步不在一个事务里，会出现重复或丢失。

**本项目**（设计 4.2）：`merchant_id` 写入后不变（`CREATING → PENDING_PAYMENT` 的那条更新同时写入，之后不改），所以索引行不会从一个索引分片搬到另一个。进一步，**一个订单只属于一个商家**：Reserve 发现订单里的 SKU 属于不同商家时拒绝（`FAILED_PRECONDITION`，reason=`MIXED_MERCHANTS`）。原因在同步这一侧：`merchant_id` 在 `orders` 行上，每条行变更自己带着路由所需的全部信息；如果允许多商家，商家只出现在 `order_items` 上，状态变更只改 `orders` 行，消费者拿到“订单变成已支付”时不知道该更新哪些商家的索引，只能回查源库或自己维护映射，把顺序和幂等变复杂（ADR-0014）。真实电商在结算页就拆单，这里只保证订单模型是“拆完之后”的样子。

- `merchant_id` 为空的订单（还在 `CREATING` 或预占前就失败）不进索引。
- 只同步 `orders_*`，不同步 `order_items_*`。
- **多商家的订单失败在落库之后，不在受理时**（设计 4.13）：受理只看 Redis 闸门，那里没有商家信息，所以会被受理、返回 `creating`，随后在预占时被拒，订单变 `failed`（原因码 `MIXED_MERCHANTS`），闸门占用由 failed 事件归还。要在受理时拒绝，得在装载闸门时把商家也放进 Redis，没做。

### 5.10 索引表只存主键回表，还是带上展示列

**问**：异构索引表存什么？

**要点**：只存主键（订单号）则列表每一行都要回到订单分片读一次，一页 20 条就是分散在各分片的 20 次点查，而且没法按状态筛选；带上列表页要显示的列则不回源，代价是这些列有同步延迟。本项目带上展示列（状态、金额、时间）。

**本项目**（设计 4.9、4.10）：索引表带 `status`、`total_amount`、`created_at`、`paid_at` 等，不回源。**同步延迟怎么应对，按用途划分**：索引只用于展示列表，列表里的状态可能是旧的，新订单可能晚一点出现，商家不是这些订单的写入方，没有“读己之写”的预期；任何做决定的操作（以后的发货、商家退款）都按订单号回到订单分片主库重新读状态，不用索引里的状态做前提；点进详情走 `GetOrder`；不做“列表页回查源库刷新状态”（那会把每次列表查询变回多分片点查）。这和 4.2 的原则相同。

**同步延迟实测**（设计 4.14）：从下单请求返回到订单出现在商家列表里，几次运行量到 50 到 260 毫秒（每 50 毫秒轮询一次），包含订单落库、主从复制、CDC、Kafka 和写索引，是本机空闲时的值。可观测做到日志加 e2e 测量，没有写入时算不出延迟，“没有变更”和“同步卡住了”在日志上分不开（要靠消费组积压和 CDC 进程存活区分），完整做法是在源库上定时写心跳行，放到阶段 3。

### 5.11 用订单号做游标的深分页

**问**：商家有上百万订单，怎么分页？

**要点**：`LIMIT n OFFSET m` 要扫过并丢掉前 m 行，翻得越深越慢。游标分页（keyset pagination）用上一页最后一条的排序键做条件：`WHERE order_id < 游标 ORDER BY order_id DESC LIMIT n`，直接走索引范围扫描，翻多深都是一次范围扫描。局限：只能“下一页”，不能跳页；排序键必须唯一或带上唯一的次级键。

**本项目**（设计 4.9）：订单号的高位是毫秒时间戳，按订单号倒序就是按创建时间倒序，所以订单号本身就是好游标。不同节点的时钟有偏差、同一毫秒内的先后不严格，对列表页足够。接口：`GET /api/v1/merchants/{merchant_id}/orders?status=&cursor=&limit=`，`cursor` 是不透明的。实测：商家列表第一页 p50 0.21 ms、p99 0.29 ms；最大的商家（136 万单）翻到第 500 页（游标）p50 0.21 ms、p99 0.31 ms，延迟和这个商家有多少订单无关。

**`FORCE INDEX` 的坑**（设计 4.13、5.2）：设计里写“直接走主键”，实现时发现优化器两个方向都选错过：带状态筛选时选了主键倒序扫、边扫边过滤，状态稀少时要扫完这个商家的全部订单；不带状态时有一次选了 `idx_merchant_status` 再排序。两条查询的形状固定，所以各自指定索引，测试里用 `EXPLAIN` 断言没有 filesort。用户列表同理：`FORCE INDEX (idx_orders_user)`，带状态筛选时优化器可能改选 `(status, expire_at)`。固定之后索引被删或改名时语句直接报错，**不会悄悄变慢**（这是固定索引的好处，也是代价：要跟着索引演进）。

### 5.12 DELETE 在 CDC 里怎么表示：墓碑，还是带前镜像的普通消息

**问**：Kafka 压缩 topic 里源表的删除怎么表示？

**要点**：压缩 topic 保留每个 key 的最后一条消息。**墓碑**（value 为 null）的语义是“这个 key 不存在了，可以清掉”，压缩后这个 key 会从 topic 里消失；**带前镜像的普通消息**（`op=DELETE`、`before` 是删除前的整行）压缩后留下的是这个 key 的最终映像。选哪个取决于“删除”在业务上是什么意思：真删除（数据不再存在）用墓碑；**“离开热库”**（数据还在，只是搬走了）用带前镜像的普通消息，这样新下游从头消费 topic 仍能拿到全部订单。

**本项目**（ADR-0016、设计 6.7）：归档会删热库的行，CDC 照常发出 `op=DELETE`。约定：`orders` 表的 DELETE 表示“这一行离开了热库”，`before` 是它的最终映像，保持为普通消息，不改墓碑。订单在业务上从不删除，只会归档，所以没有歧义；改成墓碑的话，归档订单会从 topic 里消失，而 CDC 的全量只读热库，新下游就再也看不到它们了。

**连带的几个后果**（设计 6.13）：`cdc.order.orders` 的压缩保留从调优选项变成了**数据约束**（topic 丢了，归档订单对新下游就消失了，只能从冷库另做全量）；“最后一条是 DELETE 就表示已归档”不能当判断依据（CDC 的全量和归档同时进行时，同一行的 `READ` 可能排在它的 DELETE 之后成为最后一条）；压缩保留的是 key 位置**最靠后**的那条，不是版本最高的那条，重放期间（崩溃后重启，或重做全量后从 G 读 binlog）某个 key 的最后一条可能是较旧的版本，新下游要从头消费时同样要按版本号比较。

### 5.13 源表归档后，异构索引保留还是跟着删

**问**：订单归档到冷库后，商家索引里的行怎么处理？

**本项目**（ADR-0016、设计 6.7）：**保留**。索引表是一份独立的数据，带着展示列，商家列表不回源，所以订单归档后商家照样能列出它；点进详情走 `GET /orders/{id}`，由冷热读路径去冷库取。删掉索引行换来的是索引变小，付出的是商家端看不到旧订单，或者要给冷库再建一套商家维度的查询。orderindex 对 DELETE 的处理从“忽略”改成“用 `before` 做一次带版本号的 upsert”：平时它是空操作（索引里已经是这个版本），在索引从头重建时它就是这个订单唯一的来源。索引自己的冷热分离是另一件事，这一步不做。实测：归档完商家索引仍是 490.8 万行，一行没少。

另外的现象：归档的 DELETE 在索引里是空操作，消费者处理它们的速度约 4500 条/秒，是真正写入时（约 2000 行/秒）的两倍多；归档期间索引积压涨到 266 万条，归档结束后约 5 分钟追平，期间在线订单的索引延迟最长约 13 分钟（设计 6.14）。

## 6. 跨分片查询

### 6.1 跨分片分页为什么不能直接做

**问**：要全局按时间倒序，翻到第 p 页，每页 n 条，跨分片怎么做？

**要点**：每个分片各自的第 p 页合起来不是全局的第 p 页：全局的前 `p × n` 条可能全部来自同一个分片。所以用偏移量时，**每个分片都要返回自己的前 `p × n` 条**，协调方归并后丢掉前面的。三种改法：

| 方案 | 做法 | 取舍 |
|---|---|---|
| 禁止跳页，用游标 | 每个分片执行 `order_id < 游标 ORDER BY order_id DESC LIMIT n`，协调方 k 路归并取前 n 条 | 每个分片每次只出 n 行，翻多深代价都一样；只能“下一页” |
| 二次查询法 | 保留跳页：第一次每个分片查 `OFFSET (p × n) / 分片数`，取各分片返回的最小排序键，第二次用这个下界重新查，算出全局偏移 | 两次往返，分片内仍要跳过偏移量，只省网络传输；实现复杂，只在排序键分布均匀时划算 |
| 不做 | 收窄到带分片键，或交给索引表、离线存储 | 在线不支持 |

**本项目**（设计 5.1）：8 个 slot、翻到第 1000 页、每页 20 条，偏移量写法是取回 16 万行只为显示 20 行，而且每个分片自己也要扫过 2 万行。选游标用于“单个分片内的分页”（用户列表、商家列表），选“不做”用于其余。散发加归并只在造数工具的查询测试里实现一次，用来量偏移量和游标的差距，不做成对外接口。实测（设计 5.11，第 500 页、每页 20 条）：

| 场景 | 偏移量 p50 | 游标 p50 | 偏移量取回的行 | 游标取回的行 |
|---|---|---|---|---|
| 单个分片内，一个重度用户 | 5.2 ms | 0.37 ms | 20 | 20 |
| 8 个 slot 散发加归并 | 7.6 ms | 0.64 ms | 80000 | 160 |

单分片内偏移量慢 14 倍，是数据库自己扫过并丢掉前 9980 行的代价；散发时偏移量要从每个分片取回 1 万行，共 8 万行，只为显示 20 行。页越深差距越大，游标的代价不随页码变化。

### 6.2 跨分片聚合哪些能由分片结果合成

**问**：全局统计（订单总数、成交额）怎么在分片上做？

**要点**：`COUNT`、`SUM`、`MIN`、`MAX` 可以每个分片各算一次再合并（相加、取极值）；`AVG` 要拆成 `SUM` 和 `COUNT` 再合并；`COUNT(DISTINCT)`、中位数、`TOP N` **不能**由分片结果直接合成（分片之间的去重集合不同，分位数要全体数据）。在线路径上本项目不做，归宿是离线或分析型存储（数据同样从 CDC 的 topic 来，本项目不搭，只写明出口）。

**本项目**（设计 5.1）：把查询按“落在几个分片上”分类：按订单号、按用户加幂等键、按用户列表（5.2 新增）都落一个 slot；按商家列表落索引表的一个 slot；后台扫描是逐 slot 的豁免；不带用户不带商家的列表、全局聚合、跨用户连接、全局榜单是“在线不支持”——意思是 gateway 和 order 不提供这样的接口，不是做不到。运营后台偶尔要看“全站最近订单”，可以接受慢，用散发加归并就够，不值得为它建索引表。阶段验收“不出现全分片扫描”的证据是每条查询的 `EXPLAIN`。

**`EXPLAIN` 的局限**（设计 5.11）：`ref` 访问给的是索引的平均基数，5 万单的重度用户也显示 7 行，所以“扫描行数与页大小同阶”要看实测延迟，不能看 `EXPLAIN` 的 `rows`；本机 MySQL 9.7 的 `explain_format` 默认是 `TREE`，没有分开的 `key` 列，测试里要写 `EXPLAIN FORMAT=TRADITIONAL`。

### 6.3 造数与实测

**问**：怎么验证分片是均匀的、查询在数据量大时仍然快？

**本项目**（设计 5.3、5.11）：`test/load seed` 直接向主库写，不经过服务（经过服务每单要走 Kafka、Redis、三个服务，灌几百万单要几个小时，而且造不出过去的时间）。设计要点：

- 表要大到缓冲池装不下（order 每个实例缓冲池不到 300 MB，实际 64 MB）。500 万订单、1000 万条明细，时间从 2020-01-01 到 2026-11-13，2 分 57 秒，平均 2.8 万单/秒（开头 8.6 万，表超过缓冲池之后降到 2 万多）。
- **用户和商家按 Zipf 分布取**：均匀分布必然得到均匀分片，量不出东西；真实系统里的不均匀来自少数重度用户和大商家。
- 只造终态订单（已支付约 70%、超时关闭约 20%、已取消约 8%、创建失败约 2%），不造 `CREATING` 和待支付，否则超时关单的后台任务会接手这些订单，去释放并不存在的库存预占。
- 用户号从保留区间取（`2^40` 起），对账工具据此把造出来的订单和真实流量分开。
- 订单号用 `idgen` 配假时钟生成，节点号固定 63；可中断续跑：生成是确定性的，每完成一个“slot 加一天”的块在同一个事务里往 `seed_progress` 表记一行。
- 写入会经过 binlog 流到从库和 CDC，再进商家索引表，不绕开：这正好是一次 CDC 增量同步的吞吐测试。

**查询延迟**（2 个库，每类 2000 次，随机参数）：

| 查询 | p50 | p99 |
|---|---|---|
| 按订单号查一行 | 0.23 ms | 0.46 ms |
| 用户列表第一页 | 0.34 ms | 4.4 ms |
| 用户列表带状态筛选 | 0.48 ms | 15.3 ms |
| 重度用户第 500 页（游标） | 0.21 ms | 1.0 ms |

带状态筛选的尾延迟明显更高：它在用户的索引范围里逐行回表过滤，要找的状态少见时回表的行多，又赶上页不在缓冲池里。“不为状态另建索引”的决定（一个用户的订单通常几十到几千条，商家可以有上百万所以索引表有 `(merchant_id, status, order_id)`）在这个数据量下还成立，但代价是看得见的。

**商家索引追得很慢**：CDC 这一侧没问题（500 万行的变更在灌数期间就全部发进了 Kafka），慢的是索引消费者：逐条写库、4 个分区串行，只有约 2000 行/秒，500 万行要 40 分钟以上，演练结束时还积压约 547 万条。改成按批写是 1d 的事。**教训**：“上游发得快”和“下游追得上”是两回事，压测灌数要同时看积压；对账（`load verify`）要等索引追平，否则会误报缺失。

## 7. 扩容：2 库扩 4 库

### 7.1 成倍扩容有哪几种做法

**问**：分库之后库不够了，怎么扩？

**要点**：

| 方案 | 做法 | 取舍 |
|---|---|---|
| 从库提升 | 给每个旧主库挂新从库，追平后切断复制、提升为新主库，两边各删掉不属于自己的一半 | 数据搬迁由数据库复制完成，应用不写搬数据的代码，保证事务边界；只适合成倍扩容；切换瞬间要处理写入归属 |
| 双写加回填 | 应用同时写新旧两库，后台把历史数据补到新库，校验一致后切读，再停旧库写 | 可用于任意重新分片；双写非原子，两边会不一致，要靠对账修；回填和在线写会更新同一行，要处理先后；应用里长期带着迁移期代码 |
| 用 CDC 搬 | 消费变更流写新库，是一条在线迁移管道 | 同样不限成倍；没选是因为这次是整表搬，MySQL 复制更快更省事；拆表（8 变 16）时应重新考虑 |
| 停机导出导入 | 最简单 | 停机时间和数据量成正比 |

**本项目**（ADR-0015、设计 5.4）：选从库提升。搬迁量和停顿都可预先算出：每个旧库搬走一半，停顿和数据量无关，取决于复制延迟、outbox 和 CDC 追上的时间。不做拆表、非成倍扩容、缩容、多个 order 实例下的滚动切换（阶段 2 上 K8s 再验证）。

### 7.2 库数配置化之后怎么防配错

**问**：库数做成配置后，配错了数据就找不到，怎么防？

**要点**：把“我是第几个库、共几个库、持有哪些 slot”存在**库自己里面**，应用启动时逐库核对配置，不符就拒绝启动。这样配置错误从“悄悄把订单写到找不到的地方”变成“启动失败”。

**本项目**（ADR-0015、设计 5.5）：库数等于 `MYSQL_DSNS` 的个数，必须是 2 的幂且不超过 slot 数（改了 ADR-0012 的“库数是常量”，slot 数仍是常量）。每个库里有一张 `shard_meta`，一行：本库的序号、总库数、本库持有的 slot 列表；order 启动时逐库核对：DSN 列表里第 `i` 个库的 `shard_meta` 必须写着“我是 `i` 号库，共 `len(DSNS)` 个库”。DSN 顺序写反、少写一个库、拿旧配置连上扩容后的库，都会在启动时失败。空库由迁移写入这一行；`shard_meta` 只由迁移（首次）和扩容工具改。另外 `MYSQL_DSN`（旧的单库配置）设了就拒绝启动，防止部署配置没跟上时悄悄连到默认的本机库。分片布局只定义一处（`sharding.OrderSlots` 与 `OrderLayout(dbs)`），对账工具在传入库数与布局不符时报错。

### 7.3 怎么保证一个 slot 只有一个库在写：改表名做围栏

**问**：切换的那一刻，怎么保证搬走的 slot 不会在新旧两个库里都被写？

**要点**：危险在于路由的切换不是瞬时的。进程重启要时间；多实例时滚动升级期间新旧两种路由并存，旧实例会把 slot 继续写进旧库，新实例已在写新库，同一个订单在两边各有一个版本。**围栏（fencing）要放在数据存储里**，不能依赖每个应用实例都及时拿到新配置：围栏之后任何按旧路由来的访问被存储拒绝。

**本项目**（ADR-0015、设计 5.6）：在旧主库上把要搬走的表改名（`orders_2` 改为 `moved_orders_2`），一条 `RENAME TABLE` 对所有表原子，只改元数据，和表多大无关。它提交的那一刻就是精确的分界：之前的写入都在它前面，之后按旧路由来的读写得到“表不存在”（错误 1146），整个事务回滚，包括同一个事务里写 outbox 的那一行。旧实例只会报错，不会写错地方。对比备选：只停 order 再切，单实例是对的（进程没了自然没有写入），多实例就留隐患，而围栏的成本只是一条 `RENAME TABLE`；在应用里给 slot 加“冻结”状态需要配置中心和“所有实例都已生效”的确认机制，本项目没有；库数保持常量则 CI 和 e2e 得跟着跑 4 个库。

**`RENAME TABLE` 的元数据锁**：它要拿元数据锁（MDL），会等这些表上**正在进行的事务**结束。**长事务会让改名一直等，并且把后面所有访问这些表的语句堵在它后面**（MDL 的队列是 FIFO，后来的读写都排在这个等待中的排他锁后面）。所以执行前设 `lock_wait_timeout`（几秒），超时就放弃重试，不能无限等；切换前检查长事务（`expand.sh` 的 `check` 步骤）。这条通用结论也适用于 `OPTIMIZE TABLE`（8.7）。

### 7.4 演练的步骤

**本项目**（设计 5.7，`scripts/expand.sh`，每个阶段一个子命令可单独重跑）：

1. `prepare`：启动新实例，用 **CLONE 插件**从旧主库拷一份数据，然后作为旧主库的从库开始复制，开 `super_read_only`。可以提前很久做，对线上没有影响。CLONE 的好处：接收方是空实例，比导出导入快，而且 GTID 状态一起带过来。
2. 切换前检查：新从库的复制延迟接近 0；没有长事务；行数、`shard_meta` 符合预期。
3. 立围栏：两个旧主库各执行一次改名，记下执行后的 `@@gtid_executed`。
4. 等三件事：新从库执行到第 3 步的 GTID；旧库 outbox 里围栏之前写下的行都已发布；旧的两个 CDC 源的位点越过第 3 步的 GTID。
5. 提升：新实例 `STOP REPLICA`、`RESET REPLICA ALL`、关 `super_read_only`；建库 `order_db_2`，把 `order_db_0.moved_orders_2` 等改名到 `order_db_2.orders_2`；写 `shard_meta`；给 `cdc` 账号补新库名的 `SELECT` 权限。
6. 切路由：用 4 个主库 DSN 重启 order（先不带从库，读模式 `primary`），新主库的从库建好后再重启一次，CDC 增加两个源。
7. `verify`；8. `cleanup`（验证通过后才做，不可回退）。

**跨库 `RENAME TABLE` 只改元数据**：同一个实例内，把表从 `order_db_0` 改名到 `order_db_2` 只改元数据，和表多大无关。**MySQL 没有 `RENAME DATABASE`**（通用知识：5.1.23 曾加后因数据丢失风险移除），所以拷来的库名对不上序号时，只能逐表跨库改名，再删掉旧库名下剩下的东西。

**新主库的从库不在提升那一步建**：CLONE 要重启接收方，每个要 5 到 10 秒，放进窗口会把它拖长一倍；路由切完之后再用 `replicas` 子命令建。

**回退**：第 6 步之前随时可以回退（把表名改回去，新实例丢弃）。第 6 步之后新库上有了新写入，旧库没有，改回表名会丢数据，只能向前修。真实系统里想保留回退的能力，要在切换后立刻建立反向复制（旧库作为新库的从库），本项目不做。

### 7.5 切换要等的三件事

**问**：放开新库写入之前要等什么？为什么？

**要点和本项目**（设计 5.7、5.8）：

1. **新库执行到围栏的 GTID**：改名也会复制到新从库，执行到这条改名对应的 GTID，就拥有了围栏之前的全部数据。
2. **旧库 outbox 里围栏之前的行都已发布**：这些事件必须由旧库的中继先发完，否则同一订单的事件会由新旧两个中继各发一部分，顺序没有保证。**怎么判断“发完了”**：outbox 是每个库一张，没搬走的 slot 还在不停地写，所以不能等“没有未发布的行”（有流量时永远等不到，演练里踩到的坑，设计 5.11）；围栏之后立刻记下 `MAX(id)` 作为**水位**，只等不超过水位的行发完。
3. **旧的 CDC 源越过围栏的 GTID**：变更 topic 是按订单号压缩的，压缩保留的是每个键位置最靠后的那条，不是版本最高的那条。如果旧源还没发完围栏之前的变更，新源就开始发更新的版本，topic 里就可能出现“新版本在前、旧版本在后”。索引的消费者会正确地丢掉旧版本，但压缩之后留下来的是旧版本，以后从头重放 topic 会得到错的结果。判断用 `GTID_SUBSET(围栏的集合, 位点的集合)`，位点用 cdc 二进制的 `-print-checkpoint <流水线名>` 打印。

### 7.6 窗口有多长，预算从哪里来

**问**：被搬的 slot 不可用多久？这段时间的请求怎么办？

**要点**：不可用窗口里的请求会失败，要看每条路径上有没有“重试到窗口结束”的能力。**窗口必须小于最短的那个重试预算**，否则请求就会耗尽重试而被丢弃或进死信。**消费者重试耗尽进死信，对“唯一途径”的消息就意味着丢数据**。

**本项目**（设计 5.7）：读代码确认的预算，当时 `kafkax` 消费者对普通错误原地重试，到 `MaxAttempts` 次后进死信：

- 下单消息：10 次，退避合计约 21 秒，超过后进死信，订单最后由回收任务置为失败（数据一致，但用户的订单没了）。
- **支付结果：默认的 5 次，合计约 1.5 秒**。超过后进死信，而这条消息是订单变成已支付的**唯一途径**，没有任务会重发。钱收了，订单却会超时关闭。**这不只是扩容的问题**：订单库任何超过 1.5 秒的不可用（比如以后的主从切换）都会触发。这是这一步最重要的发现，已改为无限重试，分区停住等库恢复；消息本身有问题的仍由 handler 标成 `Permanent` 直接进死信。
- 延迟关单消息：10 次约 20 秒，超过后由 sweeper 兜底，不受影响。

所以围栏窗口要明显短于 21 秒：`expand.sh` 给第 3 到第 5 步设一个总预算（默认 15 秒），第 4 步等待超出预算就自动回退（把表名改回去，新实例保持从库身份继续追，稍后重试）；回退在第 5 步之前始终安全。**后续**：1d 之后下单消费者的重试也改成了无限（ADR-0021，`kafkax.Permanent` 才进死信），上面“下单消息 10 次约 21 秒”是 1c 写下时的状态。

窗口里其他路径：已受理的订单在 Kafka 里排队，落库失败后重试，路由切换后落到新库——这是 1b 异步下单结构带来的好处，削峰的队列顺便吸收了切换的停顿，前提是落库消费者把“表不存在”当可重试的错误，而不是毒消息，也不能把订单置为失败；取消走 gRPC，这段时间返回错误，由调用方重试；终态订单在缓存里的仍然读得到，其余返回 503；窗口要远小于回收的宽限期。

**实测**（设计 5.11，500 万单上，20 个并发持续下单 150 秒约 55 单/秒，一半支付一半取消，中途切换）：

| 阶段 | 用时 |
|---|---|
| `prepare`：两个新实例各 CLONE 约 1 GB 并开始复制 | 28 秒 |
| 立围栏到新主库可写（数据库层面的窗口） | 7.5 秒 |
| 立围栏到 order 按 4 库路由恢复服务 | 9.3 秒 |
| `replicas`：给两个新主库各建一个从库 | 36 秒 |

窗口里大部分时间花在等待的三项检查上（每项都要起一次容器内的客户端），真正的改名、提升、跨库改名都是毫秒级，order 重启只用了 0.3 秒。期间受理的 8181 个订单全部落库，没有一个进死信；落库延迟 p99 是 1.8 秒，最长 8.5 秒（正是在窗口里排队的那些）；轮询订单状态有 1289 次返回错误（被搬的 slot 上的读），压测工具重试后都拿到了结果；对账通过（4096 个已支付订单对应 4096 笔支付，库存和闸门平衡，死信为空）。

### 7.7 在线校验怎么排除切换后的新写入

**问**：搬完之后怎么验证数据一致？

**要点**：切路由之后新库继续被写，旧库的 `moved_*` 不再变，直接比行数和 `CHECKSUM TABLE` 只在切路由之前成立，而在窗口里做整表校验又会把窗口拖长。所以只比“围栏之后没有动过的行”，两边用**同一个**条件。**校验条件必须建立在“这一列到底什么时候写、写的是什么”之上，不能看列名猜。**

**本项目**（设计 5.7 第 7 步、5.11）：订单表先在新库上取出围栏之后更新过的订单号，两边都排除；明细和支付结果写入后不再改，两边都只取创建时间早于围栏时刻的行；然后比行数和行摘要的聚合值，被排除的行数打印出来，它应当和切换后的流量相称。这样校验可以在流量恢复之后从容做。**踩过的两次坑**：第一版比行数加 `CHECKSUM TABLE`，新库一有写入就不等，改成只比围栏之后没动过的行；改完后又报了三张明细表不一致，查明明细的 `created_at` 取的是订单的**受理时间**，围栏之前受理、切换之后才落库的订单，明细看起来是“围栏之前”的，改成明细和订单表共用同一份排除名单才通过。结果：搬走的 12 张表在新旧两边一致，每张订单表比较了 59 万到 68 万行，排除了围栏之后变动过的 600 多行。

### 7.8 扩容对 CDC 和索引表的影响

**本项目**（设计 5.8）：旧源会读到改名的 DDL，之后读不到 slot 2、6 的行事件；规则按表名整体匹配（`^orders_(\d+)$`），`moved_orders_2` 不匹配，被忽略，DDL 事件只当事务边界。新源（`order-2`、`order-3`）没有位点，第一次启动做全量加增量，把 slot 2、6 的所有行重新发一遍，索引表靠行版本号去重，重发的行版本没有变高，全部被跳过。索引表本身不扩容，它的分片键是商家，和订单库的布局无关。

**过程中还踩到的**（设计 5.11）：`cdc` 账号对新库名没有权限（拷贝来的授权只认旧库名），提升时补授权；CLONE 和复制是实例级的，新实例带上旧实例里所有的库（包括 `e2e_*`），脚本只处理当前前缀的库。

## 8. 冷热归档

### 8.1 冷热怎么划分

**问**：冷数据怎么定义？按下单时间还是完结时间？

**要点**：按完结时间更贴近业务（有退款、售后的系统里，完结可能比下单晚几个月）；代价是 ID 无法推出完结时间，读路径要么对每个没查到的订单号都再去冷库查一次，要么维护一个各方都要读的水位。如果 ID 里带着时间，且“下单到终态”的间隔很短，按 ID 里的时间划分，读路径可以是**纯计算**，扫描也是主键范围扫描，不需要时间索引。

**本项目**（ADR-0016、设计 6.2）：冷 = **终态且订单号里的受理时间早于截止点（默认 90 天）**，不用完结时间（阶段计划原写“完结超过 3 个月”，改了）。终态是 `PAID`、`CANCELLED`、`CLOSED`、`FAILED`，5 条更新语句都带非终态的前置条件，终态订单的行不会再变。本系统从受理到终态最多隔一个支付时限，两者差几分钟，没有理由付元数据的代价。ADR 里明说：有退款、售后的系统里结论会不同。早于截止点但非终态的订单（卡住的）留在热库，archiver 报告数量。

**两个时间常量，保证读和归档对“哪些订单可能在冷库”的看法一致**：`MinHotAge = 30 天`（编译进代码的常量，读路径认为订单号比它新的一定不在冷库）；archiver 的 `-older-than` 默认 90 天，小于 `MinHotAge + 1 天` 时拒绝运行（多出的一天吸收时钟偏差）。常量而不是配置，因为配反的后果是“订单查不到”，和库数配错同一类。`MinHotAge` 一旦有数据归档就不能调大（调大会让读路径不去冷库找已归档的较新订单），调小是安全的。

### 8.2 跨库搬数据不用分布式事务：先写冷、校验、再删热

**问**：冷热在两个库上，没有跨库事务，怎么保证不丢不重？

**要点**：把跨库的原子性换成**每一步可重复执行加一个确定的顺序**：失败的结果是“重复”，不是“丢失”，重复由下一次运行消除。和 outbox 同一个思路。顺序必须是先写目标、校验、再删源。

**本项目**（ADR-0016、设计 6.3）：一批（默认 500 个订单）：

1. **读**：热库主库上按主键范围读一批终态订单及其明细和支付结果（普通快照读，不加锁），对每个订单算一个摘要（三张表的全部列规范化后哈希）。
2. **写冷库**：一个事务里 upsert（`INSERT ... ON DUPLICATE KEY UPDATE`，整行覆盖），重复执行结果相同。
3. **校验冷库**：把刚写的行从冷库读回来、算摘要、和第 1 步比，验证“冷库里存下来的和读出来的一样”（字符集、截断、列对应）。
4. **删热库**：一个事务（`READ COMMITTED`）里：`SELECT ... WHERE order_id IN (...) FOR UPDATE` 按主键顺序加锁；**在锁里重读三张表再算一次摘要**；摘要和第 1 步相同的订单删三张表的行，不同的跳过、下一轮重新处理；提交。

任何一步之后崩溃：第 2 步之后崩，订单在冷热两边各有一份，内容相同，重跑再 upsert 一次、再删，不会出现两边都没有。**不变量**：一个订单在热库、冷库或两边都有，不会两边都没有；两边都有时以热库为准；数据只从热到冷，不回流；冷库里只有终态订单。

**实测**：482 万订单、964 万条明细，8 分 8 秒，约 9900 单/秒（4 个库并行，每个约 2500 单/秒）；跳过 0；**守恒**：归档前热库订单 5,008,181、明细 10,009,030；归档后热库 187,276 + 冷库 4,820,905，明细 366,622 + 9,642,408，三张表都对得上；`load verify` 冷热不相交、冷库只有够旧的终态订单、明细齐全，480 万行用时 84 秒。

### 8.3 删除前只比行版本号为什么不够

**问**：删热库之前怎么确认冷库那份和热库的一致？只比行版本号行不行？

**要点**：行版本号只覆盖它所在的那张表的行。**子表的插入不改主表的行**，主表行版本号不变，只比版本号发现不了。需要一个**一组表的互斥锁**，让“重读到的内容”在提交前不会再变。

**本项目**（ADR-0016、设计 6.3）：终态订单的 `orders` 行不变，但它的 `payment_results` 还可能增加：订单取消之后才到的支付成功结果，会插入一条“要求退款”的记录，这条插入不改 `orders` 行，行版本号不变。处理支付结果的事务第一步就是锁订单行（`LockOrder`），所以**订单行锁就是这个订单三张表的互斥锁**：archiver 拿到锁之后看到的内容，在它提交之前不会再变。锁里的摘要等于第 1 步的摘要，第 1 步的摘要等于冷库的内容，所以删的那一刻热和冷相同。这变成 store 包的一条约定：**写子表之前必须先锁订单行**，以后新增写 `payment_results` 或 `order_items` 的路径都要先 `LockOrder`；删除时逐表核对删掉的行数等于锁内读到的行数，对不上就回滚报错，是兜底不是保证。

**实现中发现，设计原来写错的不变量**（设计 6.13）：原来写“两边都有且内容相同”，不对。一个订单写进冷库之后、删热之前来了一笔支付结果，锁内摘要对不上，订单被跳过、留在热库，冷库里留下一份少一条支付结果记录的旧拷贝，直到下一次运行。改成“两边都有时以热库为准”。也因此冷库的写入只做加法（upsert，不删冷库里多出的子表行）：热库子表只增不改，加法足够；“先删再插”在两个归档任务并发时会删掉另一个刚写进去的记录。

### 8.4 删除用 `READ COMMITTED`

**问**：归档批量删除为什么用 `READ COMMITTED`？

**要点**：`REPEATABLE READ` 下带范围条件的加锁读或删除会加**间隙锁**（gap lock），锁住索引的间隙，挡住相邻位置的插入；`READ COMMITTED` 只锁命中的行，不留间隙锁（要求 binlog 是 ROW 格式）。

**本项目**（设计 6.3、6.13）：有两个作用，设计里原来只写了一个：（1）删子表时不留间隙锁，免得挡住相邻订单的支付结果插入；（2）让锁内的普通读看到最新提交的内容——`REPEATABLE READ` 下拿到锁之后读子表用的可能还是拿锁之前的快照，锁内重读就失去了意义。**死锁**：archiver 先一次拿齐这一批的订单行锁，再碰子表；处理支付结果的事务只锁一个订单行。属于这一批的订单，对方卡在第一步手里什么都没有；不属于这一批的 archiver 不等它。一批的上限是 2000 个订单：一条预处理语句最多 65535 个占位符，订单行 15 列；多行 INSERT 另按 1000 行切开（一个订单的明细行数不受批大小限制）；一批会同时持有这么多订单行锁，这些订单上的支付结果要等这一批提交。

### 8.5 读路径：为什么必须先热后冷，为什么不用水位

**问**：冷热两处的读顺序怎么定？能不能用一个水位来路由？

**要点**：**数据的流向决定查的顺序**。数据从热流向冷，而且写冷在删热之前：先查热没查到，说明要么不存在、要么已经删了，而删之前冷库一定已经有了。反过来先查冷再查热，会在“还没写冷”时查冷、“已经删热”后查热，两边都落空，把一个存在的订单说成不存在。

**水位路由为什么不行**：“早于 W 的已经归档完”能让冷订单的读直接去冷库，但读水位和读数据之间有窗口：读到旧水位、去热库查、行刚被删掉，于是把存在的订单说成不存在。要补上就得在热库落空后再查一次冷库，最后还是“先热后冷”，水位只剩优化作用；而冷订单访问量本来就小，多一次主键查询约 0.2 毫秒，不值得引入一份要保持一致的状态。

**本项目**（ADR-0016、设计 6.6）：`GetOrder` 先查热库；热库主库确认没有、并且订单号早于 `now - MinHotAge` 时才查冷库。订单号新于 `MinHotAge` 的查不到就直接返回不存在，不碰冷库，所以热订单的读路径没有任何额外开销。

**用户列表**：两边各按同样条件取 n+1 条，按订单号归并去重，取前 n 条，游标仍是订单号。加一条判断避免每次都查冷库：**热库这一页之后还有订单，而且这一页最后一条新于 `MinHotAge`，就不查冷库**（冷库里的订单都比它旧，挤不进这一页）；热库刚好一页用完时仍要查冷库（冷库里有没有更旧的决定有没有下一页）。这样做精确，但“近 30 天下单不满一页的用户是多数，他们的第一页都会碰冷库”（造数的用户里占绝大多数，真实比例没量）；常见产品做法是在接口上区分（默认只列近期，“更早的订单”单独请求），用不精确换冷库的清静。

**实测**（设计 6.14，冷库重建后）：按订单号 0.22 / 0.45 ms（落在 1 个分区）；用户列表第一页（无游标）1.35 / 2.21 ms（落在全部 11 个分区）；带游标的一页 0.19 / 1.34 ms（游标所在年份及更早的）。

### 8.6 归档带来的一致性问题

**问**：归档之后，系统里哪些原来成立的假设会失效？

**本项目**（设计 6.6、6.13）：

1. **迟到的支付结果**：这是唯一涉及钱的改动。原来订单不存在而支付成功时答复“要求退款”。归档后一条针对已归档订单的支付结果（重复投递，或消费组位移被重置后重放）会因为热库查不到订单、也查不到当初的处理记录，对一个正常付清的订单要求退款。改成：热库没有、订单号早于 `MinHotAge` 时查冷库：冷库有这条 `payment_id` 的处理记录，是重复投递，什么都不做；冷库有订单没有这条记录，订单是终态，按和热库相同的规则得出答复（支付失败则接受；支付成功则要求退款，订单已不可支付），发答复事件，**不写记录**（冷库不接受在线写入；答复只取决于不会再变的冷数据，重放时得出同样的答复，支付服务以第一次答复为准，所以不写记录也幂等）；冷库也没有，走“订单不存在”；冷库查询失败，返回错误，消费者原地重试（支付结果已是无限重试），**宁可堵住也不猜**。不依赖“Kafka 的保留期比 30 天短”这类巧合。备选“把支付结果写回热库的 `payment_results`”被放弃：会在热库留下订单已经不在的孤儿行。
2. **禁止数据回流比处理回流简单**：落库消费者遇到受理时间早于 `now - MinHotAge` 的消息直接丢弃（记错误日志并计数）。否则一条被重放的陈年消息会在热库里重新插入一个已归档的订单号：行版本号从 0 开始，状态是创建失败，而且先查热库的读路径会返回它，盖住冷库里真正的订单。这也解决了 CDC 留下的“行被删除后用同一个主键再插入，版本从 0 重新开始，下游会把新行当成旧映像丢掉”（设计 4.13）：不处理它，禁止它。正常情况下受理到落库只隔几秒，背压把排队限制在约 25 秒。
3. **幂等键的有效期受数据保留期限制**：归档后 `(user_id, idempotency_key)` 的唯一约束对这个订单不再起作用，同一个幂等键在 90 天后重放会创建新订单。幂等的有效期有上限，等于热数据的保留期，是对外行为的变化，要写进接口文档。
4. **上线顺序是硬约束**：先给所有 order 实例配上 `ARCHIVE_DSN`，再第一次运行归档。没配冷库的实例收到已归档订单的支付结果时走的还是“订单不存在”：往热库写一条没有订单的支付结果记录，并对一个付清的订单要求退款。归档任务检查不到别的进程有没有配。
5. **两个归档任务同时运行会误报**：A 读了热库的旧内容，B 搬走了带新支付结果的版本，A 读回冷库比对时摘要不同，报错停下。不丢数据，但没有必要，所以归档启动时在冷库上取一把 `GET_LOCK`（会话锁，进程崩溃时自动释放），拿不到就退出。**正确性不依赖这把锁**。
6. 对已归档订单调用取消：已取消的返回成功（和热库里重复取消一样），其他终态返回 `ORDER_NOT_CANCELLABLE`；写路径不需要知道冷库，是读回订单时经过了同一个“先热后冷”的出口。
7. 后台任务（sweeper、关单、回收）只看非终态，和归档的数据不相交；查询缓存只缓存终态订单，内容不变；都不受影响。

### 8.7 大批量删除先压垮的是复制，用复制延迟做反馈

**问**：大批量删除数据，怎么避免拖垮线上？

**要点**：一次大批量删除产生大量 binlog，在从库上回放要同样的时间，**从库延迟最先涨**，进而影响读写分离。对策：分小批、限速，并把**复制延迟作为反馈**：每批删完等从库追上主库当前的位置再做下一批。

**本项目**（设计 6.4、6.13、6.14）：限速有两层：固定的速率上限（`-rate`）；每批删除之后等这个库的从库执行到主库当前的 GTID（复用步骤二的 `WaitReplica`）再做下一批。实测每 10 秒采样一次，四个从库最大延迟 1 秒，等从库追上的反馈起了作用，固定限速没用上。**设计和实现的差异**：6.4 写“等超时就放慢”，实现是等满时限（默认 30 秒）就继续下一批：这一批已经为从库等了这么久，再加别的退避没有依据。限速和等从库这条路径没有自动化测试（测试环境没有真的从库），只有这次实际运行。进度不持久化：归档过的行已经从热库删掉，重跑时同样的扫描条件自然只看到剩下的。

### 8.8 删除后空间不归还，`OPTIMIZE TABLE` 是重建表

**问**：归档删了 96% 的行，磁盘用量降了吗？

**要点**：InnoDB 删除后把页标成可复用，**文件不会变小**，表里留下大量半空的页。要还给操作系统要重建表。`OPTIMIZE TABLE` 在 InnoDB 上等价于 `ALTER TABLE ... FORCE`（重建表）：

- 在线 DDL：重建期间表可读写，但开始和结束各需要一次短暂的**元数据锁**，有长事务时会堵住，并堵住它后面的所有语句（和 7.3 改表名是同一个问题）。
- 需要额外的磁盘空间放新表。
- DDL 在从库上重放时同样要重建一遍，期间这个从库的复制延迟上升。

**本项目**（设计 6.8、6.14）：做成 archiver 的显式子命令（`-reclaim`），逐表串行，不自动跟在归档后面。实测四个库数据目录合计：

| 时刻 | 磁盘上 | 说明 |
|---|---|---|
| 归档前 | 2273 MB | 500.8 万订单 |
| 归档后、回收前 | 2273 MB | 行删了 96%，文件一个字节没小 |
| 回收后 | 217 MB | `archiver -reclaim`，24 张表共 8.6 秒，单表最长 1.6 秒 |

`information_schema` 里 `data_length + index_length` 在回收前就已经降到 549 MB（purge 把整段空出来的区还给了表空间内部，但不还给文件系统），**只看这个数会以为空间已经回来了**。重建只要几秒，是因为表里只剩 4% 的行；从库上重放同样快，没有量到延迟。**回收前后查询延迟几乎一样**：空洞多的表对这几类查询没有可见的影响，回收换来的是磁盘空间，不是延迟。

**对延迟的影响在尾部**：点查没有变化（主键查找代价只和树高有关，500 万行和 19 万行的差别在误差内），**归档不会让本来就走主键的查询变快**；列表的 p99 从 0.82 降到 0.30，带状态筛选的从 4.73 降到 0.7 左右——归档前每个实例的缓冲池是 64 MB、数据约 560 MB，尾延迟来自读盘和筛选时回表的行数；归档后数据比缓冲池小，筛选要扫的行也少了。

### 8.9 分区和分片各解决什么问题，分区表的唯一键必须包含分区键

**问**：分区和分库分表有什么区别？

**要点**：**分片**解决写入和容量在多台机器上的分摊；**分区**是同一个库里把一张表按规则拆成多个物理段，解决按范围整段管理数据（裁剪扫描范围、整段删除）。分区不分摊单机的写入。分区表的**唯一键（含主键）必须包含分区键**，因为唯一性检查只在各分区内部做。`DROP PARTITION` 是元数据操作，对比逐行 `DELETE`：直接删掉整个分区文件，不产生逐行的 binlog、不留碎片空间。

**本项目**（ADR-0016、设计 6.5）：冷库按订单号做 RANGE 分区，每年一个（订单号高位是时间，所以按订单号分区就是按时间分区，**分区键就是主键**，不用为了分区把时间列塞进主键）。过了保存期限的整年数据用 `DROP PARTITION` 删，元数据操作，**对照热库上不得不逐行删再重建表**。按订单号点查裁剪到一个分区；带游标的用户列表裁掉游标之后的分区；**不带游标的用户列表要探查全部 11 个分区**（二级索引是分区本地的，条件里没有订单号的范围就没法裁剪，实测慢约 6 倍），这就是分区按年而不是按月的原因。分区后唯一键要含分区键，所以冷库少了 `(user_id, idempotency_key)` 唯一键（也是幂等键失效的原因之一），`payment_results_archive` 的主键改成 `(order_id, payment_id)`。保存期限的到期删除任务没实现，表结构为它留好了。

**冷库不分片**：冷数据没有写入压力，查询量很小，分片解决的问题它没有。容量不够时按时间加库，不是按用户哈希。备选“照热库按 slot 拆 8 张”会把一个不需要分片的库分了片，扩容时冷库也要跟着搬。

### 8.10 热表为什么不适合按时间分区后整区卸掉

**问**：热表直接按时间分区，过期的整个分区卸掉，不就不用逐行删了吗？

**要点**：这是日志类数据的标准做法，没有删除开销、没有空间回收问题。前提是**一个分区里的行全部可以走**。订单不满足：归档的条件里有状态，一个卡住的非终态订单会钉住整个分区；整区卸掉之前还是得先把数据拷到冷库并校验；按用户分片的 8 张表各自再分区，表的数量和迁移、扩容脚本的复杂度也上去了。

**本项目**：写进 ADR-0016 的备选，没选。

### 8.11 压缩：`ROW_FORMAT=COMPRESSED` 对透明页压缩，MySQL 压缩表对 Parquet

**问**：冷数据怎么压缩？压缩比怎么样？

**要点**：

| 方案 | 原理 | 取舍 |
|---|---|---|
| `ROW_FORMAT=COMPRESSED` | 页在磁盘上压缩，缓冲池里压缩页和未压缩页各存一份 | 写入慢，读多一次解压；页分裂时重压缩代价比普通页还高 |
| 透明页压缩（`COMPRESSION='zstd'`） | 在写盘时压缩，靠文件系统打洞（hole punching）释放空间 | 依赖文件系统支持，容器的卷上不一定成立 |
| 归档到对象存储（Parquet） | 列式压缩，压缩比远高于页压缩，存储便宜一个数量级 | 按订单号点查要么全扫、要么另建“订单号到文件”的索引，延迟百毫秒到秒级；“冷订单仍可查”要另做一条慢路径并在接口上体现；适合分析 |

**本项目**（ADR-0016、设计 6.5、6.14）：选 `ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8`；透明页压缩因依赖文件系统打洞没用；Parquet 只在 ADR 里做书面对比，合理的组合是两层：近几年的冷数据放压缩的 MySQL 供在线查，更老的再转成 Parquet 只供离线，本项目只做第一层。

**实测**（设计 6.14）：

| | 订单表 | 明细表 | 数据目录 |
|---|---|---|---|
| 归档刚结束 | 816 MB 数据 + 92 MB 索引 | 481 MB | 1490 MB |
| 重建全部分区之后 | 477 MB + 96 MB | 255 MB | 906 MB |

- 重建之后（只算数据）：订单每行 104 字节（热库 169，压缩比 1.6），明细每行 27.8 字节（热库 56.6，压缩比 2.0）；订单压得差是因为行里有 32 字节的请求哈希和幂等键，都是随机内容。
- 同样的 482 万订单热库里约 2190 MB，冷库 906 MB，是 41%。**省下来的不只来自压缩**：热表有三个二级索引共约 134 字节/行，冷表只留一个约 20 字节/行。**去掉用不上的索引省的空间和压缩差不多。**

### 8.12 归档后冷库的碎片

**问**：压缩表为什么刚归档完几乎没有压缩效果？

**本项目**（设计 6.14）：归档刚结束时订单表数据部分每行 169 字节，和热库归档前一样。原因是**插入顺序**：8 个 slot 分在 4 个库上并行归档，每个 slot 都从 2020 年往后搬，冷库的主键在同一段范围里被几路交错着插入，页不断从中间分裂，留下大量半满的页；压缩页分裂的代价比普通页还高。把分区重建一遍（`ALTER TABLE ... REBUILD PARTITION`，两张表共 150 秒）之后小了 39%。重建冷库分区现在是手工执行的，没做进归档任务（日常的增量归档只往最新的一两个分区追加，问题小得多）；没做的改进是归档任务按全局时间顺序写冷库（先把所有 slot 的 2020 年搬完再搬 2021 年），或归档后自动重建涉及的分区。**教训**：并行加快了归档，却破坏了“主键顺序插入”这个 B+ 树友好的前提。

## 9. 顺带的 SQL 细节

这一节的几条设计文档里没有专门写，部分来自代码里的实际使用，部分是通用知识，面试前对照官方文档核对。

### 9.1 非负约束：CHECK 还是 UNSIGNED

**问**：库存、金额不能为负，用 `UNSIGNED` 还是 `CHECK`？

**要点**（通用知识）：

- **`UNSIGNED` 做减法，结果为负时报错**（`BIGINT UNSIGNED value is out of range`，在 `NO_UNSIGNED_SUBTRACTION` 未开时），**连查询里的中间计算也会**，例如 `available - reserved` 这样的表达式，即使你只是想比较大小。
- **和 Go 的 `int64` 对不上**：`BIGINT UNSIGNED` 的上界超出 `int64`，读进 `int64` 会溢出，要用 `uint64`，整个代码里的金额类型都得跟着变；用不用有符号数是一个全链路的决定（`pkg/merkle` 和 CDC、orderindex 里也专门处理了 `unsigned` 溢出 `int64` 的情况）。
- **CHECK 能表达更多条件**：`quantity > 0`（严格大于）、`available >= 0 AND reserved >= 0`、两列之间的关系，`UNSIGNED` 只能表达“不小于 0”。CHECK 的违反在 8.0.16 之后真正被执行；失败时**只回滚那一条语句**。
- CHECK 是最后一道防线，应用层仍要用条件更新（`WHERE available >= ?`）防超卖。

**本项目**：用的是 CHECK，不用 `UNSIGNED`：`chk_orders_{{.}}_total CHECK (total_amount >= 0)`、`chk_order_items_{{.}}_quantity CHECK (quantity > 0)`（`services/order/migrations/00001_init.sql`），库存的 `chk_sku_stock_available`、`chk_sku_stock_reserved`（`available >= 0`、`reserved >= 0`，`services/inventory/migrations/00001_init.sql`）。金额用整数分（`int64`，ADR-0006）。CHECK 约束名在库级唯一，分表时要带 slot 号（3.2）。

### 9.2 `SKIP LOCKED`：适合什么，不适合什么

**问**：`SELECT ... FOR UPDATE SKIP LOCKED` 什么时候用？

**要点**（通用知识）：它让加锁读**跳过已被别的事务锁住的行**，不等待。适合“**任意一行都行**”的场景：多个工作者抢任务队列里的任务、分配可互换的资源（抢一个空闲的券码）。**不适合**：（1）“必须是这一行”的场景，扣指定 SKU 的库存、改指定订单的状态，跳过就等于没做；（2）要看到全集才能判断的场景（汇总、检查“是否还有未处理的行”），被跳过的行让结果不完整；（3）**有先后依赖的队列**：同一个订单的增量有先后（先预占 +n，后释放 -n），跳过被锁的行会让后面的经常先被应用。

**本项目**：1c 里没有用到，在 1b 和 1d 的相关设计里是明确选择不用：outbox 中继不用 `SKIP LOCKED` 多实例并行，同一订单的两条事件可能被不同实例取走，分区内顺序没有保证，行锁要持有到 Kafka 确认，事务时长取决于网络（1b 笔记 4.6）；inventory 的 `ApplyPending`（`services/inventory/internal/store/pending.go` 的注释）用普通 `FOR UPDATE`，不用 `SKIP LOCKED`，理由是增量有先后。1c 的 archiver 取订单行锁也是“必须是这一批订单”的场景，不能跳过。

### 9.3 CLONE 插件、跨库 `RENAME TABLE`、`RENAME DATABASE`

见 7.4。要点：CLONE 是实例级的物理拷贝（接收方要是空实例，完成后接收方的 mysqld 会重启），GTID 状态一起带过来（拷完之后 `gtid_executed` 被替换成捐赠方的，“有外来 UUID”等于“已经拷过数据”，脚本以此判断是否已拷过）；它带上旧实例里**所有**的库；跨库 `RENAME TABLE` 在同一实例内只改元数据；MySQL 没有 `RENAME DATABASE`（通用知识）。

### 9.4 `ENUM`、`BIT`、`JSON` 在 binlog 里的表示

见 5.3：全量（`SELECT`）和增量（binlog）对同一行的值表示可能不同（`ENUM` 在 binlog 里是序号，`BINARY` 去尾部 `0x00`，`FLOAT` 是 32 位）。做 CDC 要逐类型核对两条路径。

## 10. 什么时候不该分库分表

**问**：你们为什么要分库分表？什么时候不该分？

**要点**（通用知识加本项目的体会）：分库分表的代价是整个系统的复杂度：跨分片查询、分布式事务、分页、聚合、扩容、全局唯一 ID、唯一约束、运维多个实例。**先穷尽更便宜的办法**：

- 加索引、优化 SQL、读写分离、缓存；
- 升级硬件，单机 MySQL 到上亿行、几百 GB 仍可用；
- **冷热分离/归档**：本项目 500 万订单里 96% 是 90 天前的终态订单，归档后热库从 2273 MB 降到 217 MB，而点查的延迟在归档前后没有变（8.8）——数据量大不等于性能问题，主键点查只和树高有关；
- 分区表（按时间管理数据）；
- 换分布式数据库（TiDB 等），ADR-0002 里把它列为备选，没选是因为这个项目要学分片路由、非分片键查询和扩容本身。

**拆之前要想清楚**：是容量问题（单机放不下）还是写入吞吐问题（单机写不动）？分片键能不能让大多数查询落一个分片？事务能不能收敛在一个分片内？能不能接受跨分片查询的限制（在线不支持、走索引表或离线）？本项目的回答是：**数据量上不需要分，是为了练习而分**，这一点面试里要诚实。

## 1c 的已知缺口汇总

- **读写分离**：写的一方打标记失败时继续写，随后的读可能旧；标记过期之后从库有这一行但状态旧，读到旧数据（`gtid` 模式下延迟超过 1 分钟才出现）；对比实验（不同延迟下读主库比例、对吞吐的影响）没做；用户列表固定读主库。
- **CDC**：只跑一个实例，没有选主；主库切换没有演练过；缺列的消息会让它所在分区（四分之一订单）停止同步，只能从日志和积压发现；没有写入时算不出延迟，要在源库上写心跳行（阶段 3）；`ENUM`、`SET`、`BIT`、`JSON` 没有处理；主键必须是整数且不被更新；超过 Kafka 消息上限的行会让流水线反复失败。
- **索引消费者**逐条写、约 2000 行/秒，500 万行要 40 分钟以上，改成按批写挂在 1d；商家索引按商家分片有固有的倾斜（最大的商家占 28%），没有解决。
- **扩容**：只支持成倍；多个 order 实例滚动切换没验证（阶段 2）；切换后不能回退，没有建反向复制；CI 和 e2e 仍只跑 2 个库，4 个库的布局只有本机演练和单元测试覆盖；两个旧库的围栏是先后立的，不是同一时刻；`seed_progress` 不跟着 slot 走。
- **归档**：`GetOrder` 查冷库没有自己的时限，冷库不可用时没有降级；用户列表落到冷库的比例没量；归档任务不按全局时间顺序写冷库，要手动重建分区；归档进行时杀进程的验证只有集成测试里的中断重跑，没有加进 chaos；`load verify` 的第 4 到 15 项只读热库，长期运行的环境里要先限定时间范围；查占用排在查冷库之前，已归档订单若在 Redis 里还留着占用，会被答成 `CREATING`（要求库存消费者卡住 30 天以上）。
- **迁移可重入**：inventory 的 `00001` 和 payment 的 `00002` 还有“多条 DDL 一个版本”的问题，没改。
- **分片后失效的防御检查**：`payment_results` 的“同一个 `payment_id` 已记在另一个订单上”基本失效。
