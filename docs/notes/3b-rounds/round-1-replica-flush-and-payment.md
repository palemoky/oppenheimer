# 3b 第 1 轮：从库不逐次刷盘，支付出结果改成并发

2026-11-19 做的。主人同意按[第 0 轮记录](round-0-first-bottleneck.md)第 7 节的建议做：第 1 轮是第 1 条（从库放松刷盘）加第 6 条（支付的串行循环）。改完用和第 0 轮完全相同的阶梯重跑。

## 1. 改了什么

**从库不逐次刷盘**（ADR-0032）。订单库的两个从库改成 `innodb_flush_log_at_trx_commit=2`、`sync_binlog=0`，主库和 `mysql-main` 不变。几个要点：

- 落盘方式跟着实例当前的角色走，不跟着序号：运行时 `SET PERSIST`，和 `super_read_only` 同一种做法。values 里只写 `replicaDurability: relaxed`；`middleware.sh mysql` 每次对每个 Pod 按角色设一遍（chart 里的 `files/durability.sh`）；核对把“主库不是 1/1”报成 `ANOMALY`。
- 切换手册在提升从库的那一步加了“先设回 1/1 再放开写入”，并新增第三节：从库所在的节点非正常关机之后，这个从库要从主库重建。
- 第 0 轮担心的“CDC 读的是从库的 binlog”想清楚了，不成问题：CDC 的位点是 GTID 集合，从库的 binlog 丢一截或者从库重建，它都按集合续读。细节在 ADR-0032 的理由一节。
- 部署时五个 MySQL 实例滚动重启了一次（chart 的脚本变了）。

**支付出结果改成并发**（`services/payment/internal/processor`）。原来一轮取 100 笔、一笔一笔串行、一笔一个事务；现在一轮里同时处理 16 笔（`PROCESSOR_CONCURRENCY`），每笔仍然是自己的事务。

- 没有改成“几笔合进一个事务”：那样一笔失败要连累同批的其他笔。要的只是不再排队等刷盘，并发就够了：同时提交的事务会被 MySQL 的组提交合进同一次刷盘。
- 取满一批并且这一轮确实出了结果，就不等 200 毫秒的间隔、紧接着再跑一轮。整批都失败时不这样做，否则数据库不可用时会变成不停重试的循环。
- 并发开出去的 goroutine 里自己接 panic：外层 `worker.Loop` 的 recover 接不住另一个 goroutine 的。
- 正确性的依据没有变：一轮里的各笔是不同的行；同一笔被两个实例同时拿到时靠条件更新，只有一个写事件。新加的四个测试（一轮并发、同批里一笔失败不影响别的、取满就接着跑、整批失败不空转）带 `-race` 重复十次通过。

**两个指标缺口**（第 0 轮记下的）：

- 新增 `payment.result.delay`：支付单从创建到出结果等了多久。
- 名字以 `.delay` 结尾的直方图改用到 30 分钟的桶（`otelx.WaitBuckets`）。`order.persist.delay` 原来只到 10 秒，这一轮能看到 112 秒了。

## 2. 条件

和第 0 轮一样的：阶梯（100、125、156、195、244、305、381 单/秒，每档 3 分钟）、场景和参数（50% 支付、20% 取消、每 100 毫秒轮询）、发压机、副本数（gateway、order 钉在 2）、限流和采样、MySQL 的内存。运行号 `l2-order-ladder`，15:30:32 到 15:51:48 UTC，SKU 7054 到 7063。

不一样的：

- 镜像 tag `7980e19-dirty-20261119152743`（提交 `7980e19` 加这一轮没提交的改动）。
- 库里比第 0 轮多了约 25 万单压测留下的订单。
- **两个 order Pod 这次都在 k3s-agent-1 上**（第 0 轮各在一个节点）。这是滚动发布加软约束的结果，开跑之后才发现。agent-1 的 CPU 在 156 到 244 三档是 97%。
- 五个 MySQL 实例在开跑前约 10 分钟重启过，缓冲池是冷的。

每档的数取后 145 秒（`scripts/cluster/loadtest-round.sh stages l2-order-ladder`，这一轮新加的子命令，结果在 `tmp/k6/l2-order-ladder/stages/`，不入库）。

## 4. 结论

**从库延迟没有了。** 七档全是 0（第 0 轮从 52 秒涨到 553 秒）。从库的 CPU 从约 1 核降到 0.15 到 0.26 核：第 0 轮那 1 核确实是协调线程等刷盘时空转出来的。

**支付出结果跟上了。** 需求到 76 笔/秒时出结果也是 76 笔/秒，从创建到出结果 p99 0.5 秒（模拟延迟 100 毫秒加一轮的间隔 200 毫秒）。第 0 轮是不管需求多少都只有约 17 笔/秒。payment 的提交 p99 还是 0.1 到 0.16 秒：单次提交没有变快，变的是同时在提交的笔数。

**落库的上限从约 143 升到 154 到 171 单/秒**（156、195、244 三档），高了 8% 到 20%。这是从库让出刷盘额度的效果：两个 agent 节点的刷盘次数在这三档是每秒 300 到 415 次，和第 0 轮（390 到 440）差不多，但单次耗时从 4.7 到 6.0 毫秒降到 3.4 到 5.5 毫秒。提高得不多，因为落库这一侧的结构没有变：还是一单两次订单库的提交加一次库存库的提交，32 单在途。拐点仍然在 125 和 156 之间：156 这一档落库延迟 p99 是 9.3 秒，积压在涨。

**受理在过载时比第 0 轮差**（195 档起 p99 约 0.9 秒，第 0 轮 0.5 到 0.67 秒）。机制和第 0 轮第 4 节一样（轮询把读路径打满），这一轮更重，因为两个 order Pod 挤在同一个节点上，那个节点的 CPU 到了 97%。这是条件不同造成的，不是这一轮的改动造成的；下一轮开跑前要先把两个 Pod 分开。

## 5. 两件新看到的事

**inventory 消费 `order.events` 跟不上了。** 它的处理速率在各档都停在每秒 102 到 112 条，积压从 3000 条涨到 2 万条（第 0 轮最多 46 条）。第 0 轮它每秒只要处理约 54 条（100 单/秒时），因为支付结果出不来，“已支付”的事件很少；现在支付通了，每单多出一条事件，它就成了下一个最窄的地方。它管的是支付之后把预占变成扣减，落后的后果是库存库里的预占迟迟不结算，订单本身的状态不受影响。它为什么停在约 105 条/秒还没有查。

**最后两档的落库掉到了约 100 单/秒，这两档不能用来对比。** 15:47 UTC 起三台虚拟机的刷盘耗时同时翻倍，并且在停压之后也没有恢复：

| 节点 | 15:46 之前（毫秒/次） | 15:48 之后 |
|---|---|---|
| k3s-server | 2.6 到 3.1 | 5.4 到 6.3 |
| k3s-agent-1 | 3.4 到 3.8 | 7.6 到 8.0 |
| k3s-agent-2 | 5.0 到 5.5 | 9.7 到 11.6 |

三台同时变，所以原因在宿主机那一层，不在某一个 Pod。查到的和没查到的：

- Tempo 在 15:46:18 被 OOMKilled（第 0 轮也是在第 16 分钟前后），时间上只差一分钟。但第 0 轮它被杀之后落库没有掉，server 节点的写入量在它重启之后也没有变大，所以不能说是它造成的。
- 宿主机上两块 NVMe 当时的温度是 37 度和 46 度（其中一个传感器 68 度），不到降速的温度；内核日志里没有盘的报错；没有定时任务（`fstrim`、`e2scrub`）在那个时间。
- 阶梯的第 15 分钟也是最早一批订单的支付超时到期、开始成批关单的时刻，这会多出一批写入。第 0 轮同样有这件事而没有掉。
- 没有查的：这块盘（970 EVO Plus，消费级）在连续写入约 15 分钟后缓存写满而降速的可能。停压、系统静止之后的复测见第 6 节。

## 6. 对账和盘的复测

**对账通过。** 停压后 24 分钟系统静止（第 0 轮 26 分钟），**不用再等从库**（第 0 轮又等了 7 分钟才追平，这一轮从库一直是 0）。`recon -since 90m` 六对数据差异为 0；`verify` 是 `PASS`，库存守恒。终态是已付 43635、取消 17759、关单 108917。

- **退款是 0。** k6 记到 43635 笔支付被受理，库里已付的订单也是 43635 单。第 0 轮同样的阶梯是 43227 笔受理、20876 单已付、22351 笔退款。
- **有 608 个受理了的订单没有落库**（`verify` 的第 15 条：受理过、库里没有、占用已被回收）。第 0 轮没有这种订单。它们出在最后两档：落库延迟的 p99 到了 63 到 112 秒，占用等不到落库，宽限期过了被回收任务归还，消费者再去认领时已经没有了（`order.persists` 的 `hold_missing`，305 档每秒 0.5 个、381 档每秒 3.2 个）。库存和账是对的（占用还回去了），但用户看到的是“下单成功，之后订单不见了”。这是背压没有挡住的情况：背压按积压的条数拒绝（约 5000 到 7500 条），落库只有约 100 单/秒时这么多条要等一分钟以上，超过了回收的宽限期。**背压的水位应该按“积压条数 ÷ 落库速率”折成等待时间来定，或者宽限期要比最坏的落库延迟长**，现在两个数是各自定的。第 3 轮做读路径和过载表现时一起处理。

**盘的复测**（停压 25 分钟、系统静止之后，和第 0 轮一样的 `dd bs=4k count=1000 oflag=dsync`）：

| | 一次同步写 | 第 0 轮空闲时 |
|---|---|---|
| k3s-agent-1（虚拟机里） | 8.9 毫秒 | 12.6 毫秒 |
| k3s-agent-2（虚拟机里） | 7.3 毫秒 | 10.7 毫秒 |
| 宿主机（虚拟机镜像所在的卷） | 5.5 毫秒 | 5.3 毫秒 |

节点上 MySQL 等的刷盘耗时也回到了 2.9 到 4.0 毫秒。所以第 5 节那次翻倍是持续写入期间的暂时状态，静止之后自己恢复了；它是什么触发的仍然没有定。虚拟机里比第 0 轮快，可能是从库不再往同一块盘上刷，没有单独验证。

## 7. 接下来

- 开跑前把两个 order Pod 分到两个节点上，并把“Pod 在哪个节点”记进每一轮的条件（`loadtest.sh conditions`）。
- 弄清楚刷盘耗时翻倍是不是可以复现；可以的话，阶梯要缩短或者每档之间留出让盘恢复的时间，否则后几档量到的是盘的状态。
- 第 2 轮原定是落库消费者的应用层组提交。动手之前先做一个不改代码的对照：把 `SUBMIT_CONCURRENCY` 调大。第 0 轮的记录说“单独调大没有用”，但这一轮支付的结果说明并发的提交会被组提交合并，这个判断要重新量。量完再定第 2 轮怎么做。
- inventory 消费 `order.events` 的上限要定位。

## 8. 面试里这件事的说法

- “从库 CPU 1 核”改掉刷盘之后降到 0.2 核：验证了第 0 轮的判断（等待，不是计算）。先有假设，再用一次改动去证实或者推翻它。
- 串行循环的上限是“1 ÷ 单次耗时”，和负载无关，平时完全看不出来，只有需求超过它时才以“排队”的形式出现；所以要有“等了多久”的指标，只有“处理了多少”不够。
- 修掉一个瓶颈，下一个马上露出来（inventory 的消费者），而且它是被上游的修复“喂”出来的：上游通了，下游的负载才真的到。
- 两轮压测的条件要逐项对：这一轮 Pod 的分布变了，后两档盘的状态变了，这些都要在结论之前说清楚，哪些数能比、哪些不能。
- 主从的落盘方式为什么可以不一样、不一样之后多出来的运维义务是什么（ADR-0032）。
