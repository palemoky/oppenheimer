# 3b 第 2 轮：调大落库的并发，三个串行的消费者改成按订单号并发

2026-11-19 夜里到 20 日做的（UTC 16:20 到 17:40）。**这一轮没有按原计划做“应用层的组提交”**，原因在第 1 节；要不要补做等主人定。

这一轮的数比前两轮乱：节点的盘有“快”和“慢”两种表现，四次对照各碰上了不同的情况，其中一次还把闸门 Redis 写满了。哪些结论站得住、哪些只是迹象，每一节都分开写。

## 1. 为什么没有做应用层的组提交

[第 0 轮的记录](round-0-first-bottleneck.md)第 7 节第 4 条说：“加大落库的并发单独做没有用，盘的刷盘额度已经用掉八成，并发再高只是排队更长。”第 2 条（应用层把几单合进一个事务）是建立在这个判断上的。

[第 1 轮](round-1-replica-flush-and-payment.md)的结果和这个判断矛盾：支付的处理器从串行改成 16 个并发之后，单次提交的耗时没有变，吞吐却从每秒 17 笔到了 76 笔。也就是说同时在等刷盘的提交会被 MySQL 的组提交合进同一次刷盘，“并发高了只是排队”是错的。

所以动手写组提交之前，先做了不改代码的对照：把 `SUBMIT_CONCURRENCY` 从 8 调到 24。结果（第 3 节的对照 A）是落库跟到了 239 单/秒。第 0 轮那条判断错在只看了“盘的繁忙度 76% 到 79%”，没有算一次刷盘能带走几个事务：当时一次只带走 1.5 个，是因为同时在提交的事务本来就少（32 单在途，大部分时间花在等 Reserve 的往返上），不是盘带不动更多。

应用层的组提交要动订单状态的核心路径（一批里一单失败怎么办、幂等、和 Reserve 的配合）。数据库自己已经在做同一件事、而且只要给它足够多的并发提交就够了的时候，不值得再在应用里做一遍。**建议不做，除非盘的问题（第 5 节）弄清楚之后落库仍然是最窄的地方。**

## 2. 改了什么

- `deploy/cluster/services/order.yaml`：`SUBMIT_CONCURRENCY=24`、`MYSQL_MAX_OPEN_CONNS=50`（每个分片两个副本合计 100 个连接，MySQL 的上限 200）。只改了集群的 values，代码里的默认值没有动。
- 三个消费者从分区内串行改成按订单号并发（`kafkax` 的 `Concurrency`，和落库消费者同一个机制，ADR-0017），默认都是 8：
  - inventory 消费 `order.events`（`ORDER_EVENTS_CONCURRENCY`）：把预占确认成扣减，或者释放。
  - order 消费 `payment.events`（`PAYMENT_EVENTS_CONCURRENCY`）：把订单置为已支付，或者要求退款。
  - payment 消费 `order.events`（`ORDER_EVENTS_CONCURRENCY`）：处理订单对支付结果的答复。

  三个都是“一条消息一个事务、分区内串行”，上限是 4 个分区 ÷ 单次提交的耗时，每秒 70 到 150 条，和第 1 轮修掉的支付处理器是同一类问题。第 1 轮之前它们没有暴露，是因为支付出不来结果，下游没有量。

  可以并发的依据（每个常量上的注释里写了）：消息的 key 都是订单号，同一个订单的消息仍然按顺序；每条消息只碰这个订单自己的行；三个 handler 本来就按“不保证先后、至少一次”写的，各自已经有“同一条消息并发处理多次只生效一次”的测试。没有新加测试，因为按 key 分 lane 之后出现的并发，是已有测试覆盖的情形的子集。
- service chart 的副本分散约束加了 `matchLabelKeys: [pod-template-hash]`：只在同一个版本的 Pod 之间算分散。原来滚动时新 Pod 和旧 Pod 一起算，旧的删完之后两个新的常常在同一个节点上（这一夜三次部署里两次如此）。**这一处已入库，还没有部署**（会滚动所有服务，留到下一次部署）。
- 闸门 Redis 的 `maxmemory` 从 192mb 提到 768mb（第 6 节）。
- `pkg/redisx` 的 `TestCommandWithoutParentProducesNoSpan` 改成只数没有父 span 的（PR #16 的 CI 上失败了一次，是它第二次偶发失败；这次打出来的两个多余的 span 是别的用例建连接时的握手，和被测的行为无关）。

## 4. 站得住的结论和只是迹象的

**站得住：调大落库的并发，上限提高了。** A 和第 1 轮比，条件差在并发（8 对 24）和 order 副本的分布（第 1 轮两个都在一个节点上），盘都是快的。195 档从“落 162、延迟 46 秒”变成“落 195、延迟 1 秒”，差得太多，不是副本分布能解释的。机制也看得见：195 档 order 的提交是每秒 498 次，节点上的刷盘次数还是每秒 330 到 390 次，和并发 8 时一样；多出来的提交是搭在同一批刷盘上的。A 的 244 档落了 239，这时两个 agent 节点的 CPU 是 92% 和 98%：**盘快的时候，下一个限制是节点的 CPU，在 240 单/秒上下。**

**站得住：三个消费者改成并发之后不再积压。** B、C、D 三次、盘慢的时候也一样，积压从上万条降到几百条。

**要打折扣：A 的 239 不是整条链路的能力。** A 里下游三个消费者是串行的，压测期间它们欠着 1.4 万到 5 万条没处理（确认扣减、置为已支付、标记答复），这些工作是压完之后才慢慢做完的。落库这一段快，一部分是因为下游把活欠着、没有来抢盘。B、C 里下游跟上了，落库的数就低了。

**C 和 D 互相印证：下游全部跟上时，拐点在 125 和 156 单/秒之间。** 两次条件相同（副本分散、没有残留），数也接近：125 档落库延迟 p99 是 0.5 到 2.5 秒；156 档落得完但延迟 p99 到了 4 到 5 秒，提交的 p99 从 0.1 秒跳到 0.4 秒以上；195 档起落库 176 到 185、在积压；244 档（只有 D）落 215、延迟 55 秒。**所以这一轮之后整条链路稳得住的速率仍然是约 125 到 150 单/秒，和第 0 轮的拐点差不多；变了的是过了拐点之后的表现**：第 0 轮落库死死停在 143，现在过载时能落 176 到 215，下游不再欠活，支付不再排队到退款，从库不再落后。

**B 不能和 A、C 比。** 它叠了三样别的：A 留下的未付订单正好在这 12 分钟里成批超时关单（关单的消费者每秒处理 114 到 160 条，都是写）、order 的两个副本在一个节点上（该节点 CPU 98%）、盘在中途变慢。连着跑两轮而不等上一轮的订单关完，是我安排的失误；之后每一轮开跑前都等到静止。

## 5. 盘的“快”和“慢”：多半是我们自己的写入量触发的

三台虚拟机上的刷盘耗时不是连续变化的，而是在两档之间跳，三台同时跳：

| | k3s-server | k3s-agent-1 | k3s-agent-2 |
|---|---|---|---|
| 快（毫秒/次） | 2.2 到 2.9 | 3.3 到 4.1 | 4.6 到 5.8 |
| 慢 | 5.1 到 6.2 | 6.2 到 9.0 | 7.6 到 11.8 |

慢的时候两个 agent 节点每秒完成的刷盘次数从 330 到 400 降到 175 到 230。

**一开始我把它当成盘自己的状态（会随机变慢），按这个想法查了温度、内核日志、定时任务、Tempo，都对不上。把四次运行排在一起看，更像是负载触发的：**

| 什么时候变慢 | 那一刻发生了什么 |
|---|---|
| 第 1 轮 15:47 | 阶梯升到 305 单/秒，同时最早一批订单开始超时关单 |
| A | 没有变慢。下游三个消费者是串行的，欠着活，总的写入量小 |
| B 16:44 | 升到 195 档 |
| B 之后 16:58（没有压测） | B 的 195 档那批未付订单开始超时关单（16:43 加 15 分钟） |
| C 17:10 到 17:12 | 125 档就半慢，156 档全慢 |
| D 17:43 | 升到 195 档；156 档是过渡（耗时在两档之间） |
| D 之后 17:58（没有压测） | D 的 195 档那批订单开始关单（17:43 加 15 分钟）；17:52 到 17:56 关的是前两档的，量小，是快的 |

除了 C 开头那一段，每一次变慢都落在写入量上一个台阶的时刻；每一次变回快都在写入量降下来之后。所以“慢”更像是这块盘的刷盘被打满之后的表现，不是一个会自己来去的状态。几件支持和不支持这个读法的事：

- 支持：变慢的门槛很稳定，都在两个 agent 节点合计每秒 700 次刷盘上下。快的时候再往上加不上去，然后跳到慢的那一档。
- 支持：慢的时候刷盘次数少了一半，但提交的总数是涨的（D 的 125 档三个服务合计每秒 613 次提交，195 档 816 次）。一次刷盘带走了更多的事务，代价是每个事务等得更久：提交的 p99 从 0.1 秒到 0.45 秒。
- 支持：k3s-server 自己的刷盘次数没有变（每秒 29 次），耗时却跟着翻倍。三台虚拟机的镜像在宿主机的同一块 NVMe 上，别人的刷盘把它的也拖慢了。
- 不支持、没有解释的：为什么是跳变而不是渐变；C 开头为什么 125 档就半慢（它前面 38 分钟里系统有 20 分钟在关单，不算完全静止过）；16:54 到 16:56 agent-2 每秒 350 次刷盘还是快的，两分钟后每秒 250 次却是慢的。

**没有做的验证**：在宿主机上直接看这块盘（`iostat`、`nvme smart-log`、盘的写缓存有没有被写满而降速）。这一夜宿主机的 Wi-Fi 管理通道从 17:21 起连不上（`ssh` 到 192.168.50.8 超时，集群本身不受影响），没有查成。

**对结论的影响**：不管机制是哪一种，量出来的事实是一样的：这块盘能支撑的同步写就这么多，下游全部跟上时系统在 125 到 156 单/秒之间用完它。要再往上，只有两条路：每单少刷几次盘，或者换能更快刷盘的盘（有掉电保护的企业级盘刷盘不用真的清缓存，快一到两个数量级）。第 1 节说“应用层的组提交不值得做”，是在“数据库自己的组提交已经在合并”的意义上说的；如果目标是把拐点本身往上推，减少每单的提交次数（落库的两次订单库提交合成一次、Reserve 和落库的提交错开）仍然是有效的方向，只是要先确认上面这个读法。

## 6. 闸门 Redis 被幂等键写满

C 的最后一档，17:19:41 起 order 对闸门的写命令全部报 `OOM command not allowed when used memory > 'maxmemory'`：

- 闸门（`redis-gate`）的 `maxmemory` 是 192mb，策略是 `noeviction`（闸门里是库存的占用和幂等键，不能被淘汰，这个策略是对的）。
- 写满它的是幂等键：每受理一单写一个，TTL 24 小时（`IDEMPOTENCY_TTL` 的默认值），一个约 220 字节。压测两天下来有 82 万个没过期的，85.9 万个键里占了绝大多数。
- 写满之后的表现：受理被拒（`STOCK_GATE_UNAVAILABLE`，闸门的熔断器随后打开）；落库认领不了占用，消费者停在原地重试，5672 条受理了的订单卡住；回收任务和分布式锁也写不进去（日志里是 `lock unavailable, running without mutual exclusion`）。**不会自己恢复，直到有键过期。**
- 处理：`maxmemory` 提到 768mb、容器 1 Gi（`deploy/cluster/redis/redis-gate.yaml`），`middleware.sh redis` 滚动。滚动时 Sentinel 切了一次主，**现在的主库是 `redis-gate-1`**。约一分半钟后卡住的 5672 条全部落完，没有新的报错。这次提上限没有事先问主人（主人睡了，系统停着，后面的对账也做不了）；它和当晚同意过的 Tempo 提上限是同一类改动，改动已入库。

**这是一条容量约束，提上限没有解决它**：

> 闸门的内存 ≈ 幂等键的 TTL 内受理的订单数 × 220 字节

768mb 大约是 330 万单/24 小时，折成日均 38 单/秒。按这一轮量到的 150 到 240 单/秒持续跑，3 到 6 小时就会写满。长稳测试之前必须先定下面三条里的一条（建议第一条，要一篇 ADR）：

1. 缩短 Redis 里幂等键的 TTL（例如 1 小时）。订单库里 `(user_id, 幂等键)` 的唯一键才是幂等的最终依据，Redis 里的键过期之后重放会走到 `dropReplay`（落库时发现唯一键冲突，把键补回去、撤销新占用），这条路径已经有了、有测试。代价是过期之后的重放要多走一次受理和落库才被挡住。
2. 幂等键挪到另一个可以淘汰的 Redis 上（缓存那一套），闸门里只留占用。要拆 `Hold` 的脚本，它现在在一个脚本里同时写占用和幂等键，靠的就是同一个实例上的原子性。
3. 按峰值算好内存一直给够。最简单，但这是拿内存换，而且闸门是一主一从，内存越大，全量同步和故障切换越慢。

另外两条要补的：**闸门内存的使用率没有告警**（3c）；写满时的表现是“受理的订单卡住不落库”，比“拒绝受理”糟，背压应该把闸门的内存水位也算进去（至少在写满之前先拒绝新的受理，留出余量给认领和回收）。

## 9. 面试里这件事的说法

- 一个被自己推翻的判断：第 0 轮说“并发再高只是排队”，第 1 轮的数据和它矛盾，于是在做大改动之前先花十几分钟做一个不改代码的对照。结论是那个大改动不用做了。**先做便宜的实验，再决定要不要做贵的改动。**
- 组提交为什么在并发低的时候攒不起来：一次刷盘带走的是“刷盘期间到达的提交”，在途的事务大部分时间不在提交上的话，再多的线程数也没用，要看的是同一时刻有几个在提交。
- 修掉一个瓶颈，暴露出来的常常是同一类问题的另外几处（三个串行的消费者）；以及下游欠着活的时候上游的数是虚高的。
- 压测量到的是“系统加环境”，而且环境的表现可能是被系统自己推过去的：我先把盘变慢当成了随机的外部状态，排了四次运行的时间线才看出它每次都发生在写入量上台阶的时候。把现象归给“环境不稳定”之前，先排一遍它和自己负载的时间关系。
- 带 TTL 的键在 `noeviction` 的 Redis 里是一条容量公式（速率 × TTL × 单个大小），不压到那个量、不压够那么久是看不到的；写满之后的行为（写不进、连回收都做不了）要事先想好。
