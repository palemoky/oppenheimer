# 3b：混合读写和秒杀的阶梯

2026-11-21。设计第 4 节第 6 步剩下的两个场景。普通下单的阶梯在第 0 到 3 轮已经做过（拐点在落库，持续 125 到 150 单/秒，瓶颈是盘的同步刷盘）；这两轮的到达速率是它的十倍，看的是那一轮看不到的东西：读路径、gateway 和入口、限流、节点的 CPU。

条件（两轮相同）：提交 `23379d7` 的代码（镜像 tag `1228d9c-dirty-20261121084655`，内容相同）；gateway、order 钉在 2 个副本，其余服务 2 个（cdc 1 个）；按地址的限流关着，其余限流默认；库里 1000 万历史订单加约 144 万压测留下的；发压机是 Mac mini（有线）。两轮都对账通过。

## 1. 混合读写：`m1-mixed-ladder`

09:41 到 10:05 UTC。权重同基线（查库存 50、查订单 25、订单列表 10、商家列表 5、下单 8、支付 2），Zipf 1.1，20 个 SKU（7144 到 7163）。从基线的 500 请求/秒起，每档 1.25 倍、3 分钟，共 8 档。盘第一档在快的一档（一次刷盘 2.2 到 2.9 毫秒），第二档起在慢的一档（5.3 到 11.7 毫秒）。

### 1.2 读法

- **拐点是 1907 请求/秒（其中下单 148 单/秒）。** 这一档所有读接口和受理的 p99 都在 100 毫秒以内、没有 5xx；再加一档，全部接口一起变慢五到八倍。
- **到顶的是节点的 CPU，不是哪一个服务。** 1907 档两个 agent 节点已经是 87% 和 95%，2384 档是 92% 和 99%。没有哪个容器被 CPU 限额节流（节流比例一直是空的），也没有哪个服务单独突出：最高一档 order 两个 Pod 各约 1 核，gateway 各 0.65 到 0.84 核加边车 0.4 到 0.5 核，inventory 各 0.5 到 0.64 核加边车 0.3 核，MySQL 三个主库 0.66 到 1.14 核，Tempo 1 核，入口 0.74 核。所有东西挤在 16 个 vCPU 上，一起慢。这和普通下单场景不一样：那里是盘先到顶、CPU 还有余量。
- **下单这一份（8%）恰好也走到了落库的拐点**：148 单/秒时落库延迟 p99 是 4.2 秒，191 单/秒时 15 秒，和普通下单阶梯的 156、195 档（4.3、9.9 秒）接得上。所以 1907 这个数同时被两样东西顶着，读写比例换一换，先到的会不一样：读更多时先到的是 CPU，写更多时先到的是盘。
- **2384 档的 503 是并发隔离在起作用，位置在 gateway 的边车上。** inventory 变慢（`GetStock` 的 p99 从几毫秒到 0.49 秒）之后，gateway 的每个 Pod 到 inventory 的在途请求超过了 128（`DestinationRule` 的 `http2MaxRequests`），多出来的立刻失败：最后 3 分钟两个 Pod 的 `upstream_rq_active_overflow` 合计 7870 次，k6 整轮记到 9137 个 5xx（其余的在升到这一档的那几秒和窗口之外）。inventory 自己的 `GetStock` 全部是 OK，没有摘除，没有路由超时。被拒的请求约 100 毫秒就返回了（日志里的样本），没有去排队拖慢别的接口：这正是这个上限的用处。128 这个数是 1d 时按“单实例、几毫秒一次”定的，现在看它在节点 CPU 到顶之后才触发，不用改。
- **入口的上限差一点就到了**：在途最高 902，上限 1024。再高一档就会出现 `503 UO`。它也是在 CPU 到顶、耗时涨了几十倍之后才靠近的，符合“在途 = 到达速率 × 耗时”。
- **订单读的保护只在最后两档动过**：`READ_BUSY` 一共 793 个（读名额和按库的读并发上限，1907 档起每秒 1 到 7 次）。
- **订单缓存几乎不命中**（最高一档命中 63 次/秒、未命中 565 次/秒），订单读全部走主库（`mode=primary`）。基线时就看到了，仍然没有查是设计如此还是缺陷；CPU 是这个场景的瓶颈，它值得查。库存缓存命中 950 次/秒、未命中 149、合并 168。

### 1.3 限流在这一轮的样子

- **按用户的限额**拦的是 Zipf 头部的用户：下单被拦 4256 个，查库存和订单列表被拦约 6400 个，从 625 档就有（每秒零点几次），随速率涨到每秒十几次。这是预期内的：100 万个用户里最热的那几个，到达速率超过了单个用户的限额。
- k6 的汇总把读接口的这些 429 记成了 `OTHER=6652`：脚本为了省内存丢弃这几个接口的响应体，读不到原因码。数是用 gateway 的指标对出来的（查库存和订单列表的 429 合计约 6400，加上支付的 409 约 330）。要让汇总自己分得清，得对 429 保留响应体，没有改。
- **按热点参数的限额（每个 SKU 500 次/秒）没有触发**：20 个 SKU，最热的一个在最高档也不到 500 次/秒。它在秒杀那一轮看。
- **限流的 Redis 在最高一档每秒超时 8.6 次**（`evalsha` 超过 20 毫秒的时限），每次退回进程内的桶、放宽 1 秒（ADR-0019）。原因是节点 CPU 到顶，不是 Redis 自己慢。也就是说**系统最忙的时候恰好是限流最松的时候**；这一轮它没有造成后果（被放宽的是按用户的限额），3c 给 `gateway.ratelimit.fallbacks` 配告警。

### 1.4 对账

停压后等了约 17 分钟到静止。`recon -since 60m` 差异 0；`verify` 是 `PASS`：受理 140002 单全部在订单库里，受理了没落库的 0 单，库存守恒。k6 丢了 3643 个迭代（178 万个里，0.2%，都在最后一档），不影响前七档的数。

## 2. 秒杀：`f1-flash-ladder`

10:24 到 10:36 UTC。所有人抢一个 SKU（7164，库存 8 万），每次迭代查一次库存、下一单，受理了的轮询到落库，不支付。到达 500、1000、2000、4000 次迭代/秒各 3 分钟（请求数至少是它的两倍）。`test/k6/flash.js` 为此加了对 `STAGES` 的支持。

**库存给少了，这一轮没有按设计的样子走。** 设计时按“落库约 180 单/秒”算，8 万够卖到第三档中途；实际第一档每秒受理 288 单，第二档开头就卖完了。所以四档其实是：第一档全程有货，第二档大半是售罄，后两档全是售罄。有货的只有 500 这一档，“有货时到达速率再高会怎样”这一轮没有量到（见 2.3）。

| 1000 | 开头卖完 | 2601 | 101 / 323 / 560 | 167 | 438 | 474 | 32 | 0 | 597 | 60% / 67% / 74% | 1.75 + 1.00 | 0.88 |

耗时是 gateway 记的，毫秒。

### 2.2 读法

- **零超卖**：受理恰好 80000，115 万个 `409 INSUFFICIENT_STOCK`。
- **最难的是有货的那一档，而且只有 500 次/秒。** 这一档 gateway 实际收到 2587 请求/秒，其中 1612 是查订单：受理了的订单在排队落库（落库延迟 p99 是 27 秒，超过轮询的 10 秒时限，8 万单里 25706 单轮询超时），每单被轮询好几次。节点 CPU 到了 90% 和 96%，受理和查订单的 p99 接近 0.9 秒，入口的在途和排队都满了，每秒 43 个 `503 UO`；订单读的名额每秒拒绝 182 次（`READ_BUSY`）。第 3 轮给轮询加了退避和 `Retry-After`，把普通下单场景的放大压下去了，这里还是不够：**秒杀有货时每个订单都要等落库的队列，等的人数 = 受理速率 × 落库延迟，退避只能把每个人问的次数降下来，降不了人数。** 要消掉它得让受理的响应带上预计的等待时间（第 3 轮决定不做的那一项），或者换成推送。
- **只落库、不支付时，落库能到 287 单/秒**（盘在慢的一档，一次刷盘 4.8 到 8.9 毫秒），是普通下单场景持续能力（125 到 150）的两倍。普通下单场景里每单后面跟着 0.5 次支付和 0.2 次取消，它们的事务和落库抢同一块盘。所以“落库的上限”不是一个数，要说清是哪种组合；容量结论里按普通下单的组合写，这个数作为“只下单不支付”的上限另记一行。
- **背压在起作用**：第一档每秒 199 个 `BACKLOGGED`（队列上限 2500）。但落库延迟的 p99 仍是 27 秒，远高于 `ADMIT_MAX_WAIT` 想保证的数。按“队列长度 ÷ 落库速率”算，2500 ÷ 287 不到 9 秒，对不上；第 3 轮记录 2.2 最后一条（队列上限是全局一个数，两个分片的落库速率不一样）可能是原因之一，这一轮没有查，只记现象，见 2.3。
- **售罄之后系统很轻**：2000 次/秒（4000 请求/秒）时查库存和下单的 p99 是 17 和 19 毫秒，入口在途 51，没有任何 5xx。售罄的下单在闸门（Redis）上就被拒了，不碰数据库（这两档刷盘降到 1.2 到 1.9 毫秒，盘是闲的）。
- **售罄流量的拐点在 4000 到 8000 请求/秒之间，到顶的是入口和 gateway 的 CPU。** 4000 次/秒（7986 请求/秒）时下单的 p99 到了 368 毫秒，入口每秒 20 个 `503 UO`、在途 802；入口的 Envoy 用了 2.08 核，而且**全部压在一个 Pod 上**（MetalLB 二层模式只有一个节点应答这个地址，基线时就看到了）；gateway 两个 Pod 连边车共 4.7 核；agent-2 的 CPU 94%。每个请求的 CPU（gateway 加边车）约 0.59 毫核·秒（售罄的请求，几乎是最便宜的一种）。
- **热点限流按预期工作，但限额实际是配置的两倍。** 默认每个 SKU 500 次/秒，查库存稳定放行 1000 次/秒、其余全部 429（2000 档拒绝 1002，4000 档拒绝 2993）：这一维的桶在每个 gateway 进程里（`ratelimit.NewLocal`），两个副本就是两倍。**热点参数的限额随 gateway 的副本数变**，HPA 扩到 4 个副本时是 2000。这是 1d 时有意的取舍（热点限流在进程里做，不为它多一次 Redis 往返），但容量结论和重定 HPA 时要记得它。被限流的查库存在 k6 汇总里是 `OTHER=716135`（原因同 1.3）。
- **限流的 Redis 超时又出现了**，而且和负载同涨：四档分别是每秒 6.2、3.3、0.3、15.3 次。500 档和 4000 档是节点 CPU 最高的两档。

### 2.3 这一轮没有回答的

- 有货时更高的到达速率（基线 `b1-flash` 是 2000 次/秒、1 万库存、40 秒）。按这一轮的数，库存够大、有货状态持续几分钟时，500 次/秒就已经把入口打满；更高的速率下会更糟还是因为 `BACKLOGGED` 多而好一些，要专门跑一轮（库存 50 万以上，或者每档换一个 SKU）。
- 第一档的落库延迟为什么到 27 秒（队列上限 2500、落库 287 单/秒时按总数算应该在 9 秒以内）。

### 2.4 对账

停压后等了约 16 分钟到静止（8 万单全部没付款，等支付超时关单）。`recon -since 45m` 差异 0；`verify` 是 `PASS`：受理 80000 单全部在订单库里，受理了没落库的 0 单；SKU 7164 关单之后可售回到 80000，闸门里的数一致。k6 丢了 3320 个迭代（134 万个里，0.25%）。

## 3. 三个场景放在一起

| 场景 | 拐点 | 先到顶的 | 过了拐点最先出现的 |
|---|---|---|---|
| 普通下单（每单带轮询、50% 支付、20% 取消） | 持续 125 到 150 单/秒 | 盘的同步刷盘 | 落库延迟上涨，之后 `BACKLOGGED` |
| 混合读写（读 90%） | 1907 请求/秒（其中下单 148 单/秒） | 两个 agent 节点的 CPU（落库也同时到了拐点） | 全部接口一起变慢；gateway 到 inventory 的并发上限溢出（503）；入口在途接近上限 |
| 秒杀，有货 | 低于 500 次/秒（这一轮最低的一档已经过了） | 节点 CPU，被“等落库的订单的轮询”推上去的 | 入口 `503 UO`、`READ_BUSY`、受理 p99 到 0.9 秒 |
| 秒杀，售罄 | 4000 到 8000 请求/秒之间 | 入口 Envoy（单个 Pod）和 gateway 的 CPU | 入口 `503 UO`、下单 p99 到 0.37 秒 |

- 这套硬件上有两堵墙：**盘**（写入）和 **16 个 vCPU**（其余的一切）。哪一堵先到取决于读写的比例。
- 过了拐点之后，每一层保护都按设计动了，而且动的顺序是从里到外：背压（`BACKLOGGED`）、订单读的名额（`READ_BUSY`）、边车的并发上限、入口的并发上限。没有出现受理了又丢的订单，三轮对账都是 0 差异。
- 两个放大仍然在：**有货的秒杀里轮询把请求量放大成到达的五倍**；**限流的 Redis 在 CPU 到顶时超时、限额放宽**。

## 4. 接下来

- 空表对照（设计第 4 节）。可以不动现有的 1000 万单：集群 e2e 那套环境（`oppenheimer-e2e` 命名空间，`services.sh e2e-up`）用的是同一批 MySQL 实例上的 `e2e_*` 空库，Kafka 和 Redis 用单独的前缀，`make cluster-bench` 就是这样跑的。局限：空库和大库在同一个实例里，共用缓冲池、redo 和盘，量出来的差别只反映“这几张表自己的索引深度”，不反映“实例里没有别的数据”；压测的预检现在在 `oppenheimer-e2e` 存在时拒绝运行，要给它一个开关。另一条路是清库后从 `keep-seed-10m` 恢复，破坏性的，要主人同意。
- 扩容系数（1、2、4 个副本）。这两轮的结论是 CPU 在节点上到顶，不在某个服务上：加副本不加节点的话，扩容系数预计接近 1，要用数验证；入口的 Envoy 压在一个 Pod 上是另一个要量的点。
- 有货的秒杀在更高速率下的表现（2.3）；第一档落库延迟 27 秒的原因。
- 订单缓存几乎不命中、订单读全部走主库：读代码确认是设计如此还是缺陷（基线时就记下了）。CPU 是读路径的瓶颈，这一条现在有了理由。
- 给 3c 的告警清单再加：`envoy_cluster_upstream_rq_active_overflow` 的速率大于 0（服务之间的并发上限在拒绝请求）；节点 CPU 持续高于 85%。

## 5. 面试里这件事的说法

- **“系统能扛多少”没有一个数。** 同一套硬件，普通下单是 150 单/秒，读多写少是 1900 请求/秒，售罄的秒杀是四千以上；先到顶的分别是盘、CPU、入口。容量要按场景给，并且说清每个场景先到顶的是什么。
- **秒杀最难的不是流量最大的时候，是有货的时候。** 售罄之后每个请求在 Redis 上就被拒了，几千请求/秒很轻；有货时每个被受理的订单都要落库、都有人在等结果，五百次/秒就能把系统打满。削峰把写入压平了，但“等结果”的读没有被压平。
- **并发上限（舱壁）触发时，被调用的服务自己看不到任何错误。** inventory 的指标全是 OK，503 是 gateway 的边车在出站一侧拒的。排查这类问题要看调用方一侧的 `upstream_rq_active_overflow`，不是被调用方的错误率。
- **进程内的限流，限额随副本数变。** 每个 SKU 500 次/秒，两个副本就是 1000。它便宜（不用 Redis），代价是限额和扩缩容耦合；要一个全局的数就得放到 Redis 或者按副本数折算。
- **依赖 Redis 的限流在系统最忙的时候最容易退回本地**（超时是 CPU 饿出来的，不是 Redis 慢），退回之后限额变宽。保护机制自己的降级路径要在高负载下看，不能只在“Redis 停了”的故障注入里看。
- **只落库不支付时落库能到 287 单/秒，带支付和取消时是 150。** 瓶颈资源（盘的刷盘次数）是所有写事务共用的，一个环节的上限取决于同时还有谁在用它。
