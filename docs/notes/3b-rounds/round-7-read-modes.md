# 3b：读从库的模式对比（`primary`、`window`、`gtid`）

2026-11-21 23:54 到 2026-11-22 01:36（UTC）。2c 挪到阶段 3 的那一项：订单的展示读走从库，定量上换来什么。

**结论：在这套硬件上读从库不加能力，三种模式的拐点相同（混合读写 1907 请求/秒）。**

- `window` 和 `gtid` 都把七成多的订单读分到了从库，主库的 CPU 降了三分之一。
- 降下来的 CPU 原样出现在从库上：`window` 时四个订单实例合计不变（1.54 对 1.55 核），`gtid` 还多 0.23 核。
- 主库和从库在同一批节点上，到顶的是节点的 CPU，所以把读从一个实例挪到另一个实例没有用。
- `gtid` 比 `window` 贵：每次读从库前多一次“等从库追到位置”的查询，每次写之后多一次读主库的位置。order 多用 0.14 核，MySQL 多用 0.22 核。
- 集群上的默认值不改，仍然是 `primary`。读从库的收益要等从库在别的机器上，或者主库自己先到顶（第 3 节）。

顺带回答了扩容系数那一轮留下的问题：order 的连接池从 50 收到 40 之后够用（第 4 节）。

## 1. 怎么做的

变量只有 order 的 `ORDER_READ_MODE`。三组都是 2 个副本（五个服务钉在 2），同一个阶梯：预热（普通下单 50 单/秒 60 秒，不计），然后混合读写 1221、1526、1907、2384 请求/秒，每档 3 分钟，参数和扩容系数那一轮的 `s1-r2` 相同。每组停压后等静止（约 17 分钟）再对账，然后才切模式。

切模式用的是 `kubectl set env deploy/order ORDER_READ_MODE=<模式>`（临时的，不入库；Pod 上直接写的环境变量盖过 ConfigMap 里的），跑完用 `ORDER_READ_MODE-` 去掉，回到默认的 `primary`。其余参数都是默认值：pin 3 秒，GTID 标记留 1 分钟，等从库最多 100 毫秒。

条件（三组相同）：镜像 `1228d9c-dirty-20261121084655`；大库；按地址的限流关着；入口和连接池是扩容系数那一轮第 7 节改过之后的配置（`maxConnections` 4096、空闲超时 30 秒、order 连接池 40）；盘在慢的一档（1907 档 agent-2 一次刷盘 11.3 到 11.4 毫秒，三组一致）。

**对账三组都通过**：`recon -since 60m` 差异 0，六轮 `verify` 都是 `PASS`。受理的订单（三组各约 10.17 万单，含预热）全部落库。

## 3. 读法

### 3.1 为什么没有用

读写分离要解决的是“主库的 CPU 或连接不够”。这里主库在拐点上只用了 0.6 核，离不够很远；不够的是它所在的节点。从库和另一个分片的主库在同一个节点上（分片 0 的主库在 agent-1、从库在 agent-2，分片 1 反过来），把读从主库挪到从库，是把 CPU 从一个节点挪到另一个节点，两个节点都是满的。

和扩容系数那一轮是同一件事的另一面：到顶的是节点时，在节点之内怎么分都不加能力。

### 3.2 `gtid` 多花的在哪

- 每次读从库之前先对从库执行一次“等到这个 GTID 位置”（`WaitReplica`），从库多一次往返：两个从库合计 0.94 对 0.81 核。
- 每次写提交之后读一次主库的位置并写进 Redis（stamp）：两个主库合计 0.83 对 0.74 核。
- order 自己多 0.14 核（多出来的调用）。

换来的是保证：只要位置标记还在，读不到早于自己写入的数据。`window` 靠的是“从库延迟不超过 3 秒”这个假设。

### 3.3 什么时候它才有用

- 从库在别的机器上（加节点，或者从库单独放）：主库省下的三分之一 CPU 才是真的省下。
- 主库自己先到顶：读多到主库的 CPU、连接或缓冲池不够。这套负载的读只碰一小块热数据（空表对照的结论），离这个情况很远。
- 读的量再大一个数量级时，`gtid` 每次读多一次往返的开销会更显眼，那时要看“等从库”能不能合并或者按会话缓存位置。

### 3.4 这一轮没有量的

- **读到旧数据的次数没有量。** 对账和 `verify` 核的是最终状态，不是每一次读新不新。从库延迟的指标是整秒的，三组的最大值都是 0 到 1 秒，短于 3 秒的 pin，`window` 的假设在这一轮里是成立的；但第 1 轮里从库落后过几十秒（之后改了刷盘才好），那种时候 `window` 会读到旧数据，靠的是从库探测把它标成不健康。这条路径这一轮没有触发。
- **每组只跑了一次。** 延迟的差别在波动范围之内的都没有下结论。
- 只有混合读写一个场景。

## 4. 连接池 40 够不够（扩容系数那一轮第 7.4 节留下的）

`r1-primary` 和昨天的 `s1-r2` 是同一个阶梯、同样 2 个副本、同样读主库，差别是连接池（50 改 40）和入口的配置。

|---|---|---|---|
| 1221 | 0 | 0.33（一个库） | 47 → 48 |
| 1526 | 0.15（一个库） | 0 | 49 → 50 |

## 5. 面试里这件事的说法

- **读写分离省的是主库，不是系统。** 先问主库是不是瓶颈。主从同机、节点到顶时，把七成的读挪到从库，总的 CPU 一点没少。
- **读己之写的两种做法和代价。** 固定窗口（写后几秒读主库）便宜，靠“从库延迟短于窗口”这个假设，要配从库延迟的探测兜底；按位置等（GTID）有保证，代价是每次写多一次读位置、每次读多一次等待，这里量到的是数据库多 14% 的 CPU。
- **用来做决定的读不走从库。** 走从库的只有展示读；状态机、幂等查询、取消之后的复查都读主库。读从库的结果不能成为写的前提。
- **预测要拿数核对。** 开跑前估计“查的都是刚下的单，分流不出多少”，量出来是七成多：客户端的轮询有退避，读和写之间隔了好几秒。
- **满载时的 p99 自己会晃。** 同一个配置重复五次，下单 p99 从 94 到 158 毫秒。两组的差别落在这个范围里时，结论是“没有量出差别”，不是“快了三成”。
