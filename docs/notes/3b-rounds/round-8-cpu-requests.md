2026-11-22 01:45 到 03:48（UTC）。扩容系数那一轮（[round-6](round-6-scaling-factor.md) 第 5 节）留下的三件事，一次做完。

**结论**

- 六个服务的 CPU requests 改成“2 个副本、混合读写拐点的八成”时的实测用量，原来只有实际的两到三成。两个节点放得下 HPA 上限的 3 个副本加滚动多出的 1 个。

## 1. requests 怎么定的

requests 管三件事，每一件都要求它接近实际用量：

1. **调度。** 调度器只看 requests 的合计，不看实际用量。写小了它会认为节点很空。
2. **HPA 的 CPU 百分比。** 分母是 requests。原来 gateway 是 250m 对实际 1.1 核，放开 HPA 在一半的负载下就会扩到上限。
3. **抢 CPU 时的权重。** 不设 limits 时，requests 换算成 cgroup 的 `cpu.weight`。节点有空闲时它不起作用，谁要多少给多少；节点满了，内核按权重的比例分。它是权重，不是上限，也不是预留。

取数的点：2 个副本、混合读写 1526 请求/秒（拐点 1907 的八成），两次独立的阶梯（`s1-r2`、`r1-primary`）里每个 Pod 的用量。普通下单 100 单/秒（写入拐点的八成）作为另一种请求组合核对。

| 服务 | 业务容器实测（核） | 边车实测（核） | 业务容器 requests | 边车 requests |
|---|---|---|---|---|
| gateway | 0.70 到 0.79 | 0.39 到 0.48 | 200m → 750m | 50m → 450m |
| order | 0.75 到 0.78（普通下单时 0.54） | 0.28 到 0.29 | 300m → 750m | 50m → 300m |
| inventory | 0.47 到 0.52 | 0.29 到 0.30 | 200m → 500m | 50m → 300m |
| payment | 0.08 到 0.13（普通下单时 0.14 到 0.19） | 0.03 到 0.06 | 100m → 150m | 50m（默认值） |
| orderindex | 0.12 到 0.13 | 0.04 | 100m → 150m | 50m（默认值） |
| cdc | 0.14 | 没有边车 | 100m → 150m | |

CPU limits 仍然不设。

**放不放得下。** 每个 agent 节点可分配 7.5 核。

| | agent-1 | agent-2 |
|---|---|---|
| 改之前的 requests 合计 | 2.75 核 | 2.65 核 |
| 改之后（各服务 2 个副本） | 5.10 核（68%） | 4.95 核（66%） |
| gateway、order 的第三个副本都落在这个节点 | 7.35 核 | 7.20 核 |

最坏的情况（两个第三副本同在一个节点）还放得下，滚动多出来的那个（最大 1.2 核）落到另一个节点。HPA 到上限时五个服务同时滚动合计要 15.75 核，超过两个节点的 15 核：多出来的 Pod 会先 Pending，等别的服务滚完腾出位置，不会卡死，但会变慢。`services.sh deploy` 是逐个服务滚动的，实际遇不到。

**两个坑**

- **边车的三项要一起写。** Pod 上只要有 `sidecar.istio.io/proxyCPU` 这一类注解中的任何一个，Istio 的注入模板就只用注解里的值，不再用网格的全局默认值，没写的内存 request 和上限会变成不设。所以 values 里 `istio.proxy` 的 `cpu`、`memory`、`memoryLimit` 三项一起给。部署后在 Pod 上核对过三项都在。
- **集群 e2e 那一套不能跟着这次的数。** 它用同一个 chart、同一份 values，和长期运行的一套同时待在同一批节点上，照抄要多 5.85 核，放不下，Pod 会一直 Pending。在 `deploy/cluster/services/e2e/` 里保持了改之前的值；bench、chaos、fault 叠在它上面，也不变。渲染核对过，**没有在集群上实际跑一遍 e2e**。

## 2. HPA 的阈值

两个触发器的关系没有变：请求速率为主，CPU 兜底，取大的。

| 服务 | 每个 Pod 的 requests | CPU 触发点（70%） | 每个请求的 CPU（混合读写 / 普通下单） | `perReplica` |
|---|---|---|---|---|
| gateway | 1200m | 840m | 1.56 / 2.0 毫核·秒 | 180 → 500 |
| order | 1050m | 735m | 3.1 / 4.2 毫核·秒（gRPC 请求，含落库） | 100 → 220 |

每个请求的 CPU 随请求的组合变，所以请求速率的阈值只能对着一种组合定。取的是便宜的那种（混合读写）：840m 对应 534 请求/秒，取 500。组合变贵时请求速率不涨而 CPU 涨，由 CPU 那一项触发，它留着就是为了这个。

2 个副本时 gateway 合计 1000 请求/秒就扩，是拐点的一半多一点。扩了不加能力（round-6 的结论），这个阈值只保证机制在拐点之前动作。

| | requests | 1907 档的实际用量 | 在所在节点 requests 里的占比，前 → 后 |

节点满的时候，中间件能保证拿到的 CPU 少了将近一半，服务排到 CPU 更快、中间件更慢。服务自己的处理耗时没有变差（1907 档查订单的 p99 从 133 到 91 毫秒），变差的是它们等 Redis 和 MySQL 的时间。2384 档入口的 Envoy 自己也排不上 CPU，在途请求堆到 1024 的上限，被拒的请求多了一个数量级。

**没有验证的**：每组只有一次；没有直接读节点上的 `cpu.weight` 和各 cgroup 的 `cpu.pressure`，“是权重造成的”是按数的方向推断的。1907 档下单 p99 的 158 对 188 在这个负载下的波动范围里（同样的配置出现过 94 到 158）。

**对限流的含义**：限流的 Redis 超时一次，那个请求就退回进程里的桶（ADR-0019），限额变宽。1907 档每秒 12 次退回是 0.6% 的请求。这是 3c 要配告警的那个指标（`gateway.ratelimit.fallbacks`）。

## 6. 主人定了 B 之后（2026-11-22 02:50 到 03:48 UTC）

### 6.1 B 按原数做不了：滚动放不下

第 5 节的表漏算了一件事。中间件按原数调上去之后两个节点各剩 0.7 到 0.9 核，而服务的滚动是先起新的再停旧的（`maxSurge: 1`、`maxUnavailable: 0`），gateway 的一个 Pod 要 1.2 核，order 要 1.05 核，业务 Pod 又不许上控制面节点。结果是 gateway、order 以后每次部署都会卡在 Pending。

办法：比例不变，所有的数统一乘 0.9（取整）。权重要的是比例，不是绝对值；调度要的是“最大的一个 Pod 还放得下”。

| | 1526 档的实测（核） | 现在的 requests |
|---|---|---|
| gateway | 0.70 到 0.79 + 边车 0.39 到 0.48 | 700m + 400m |
| order | 0.75 到 0.78 + 0.28 到 0.29 | 700m + 250m |
| inventory | 0.47 到 0.52 + 0.29 到 0.30 | 450m + 250m |
| payment、orderindex、cdc | 0.08 到 0.19 | 150m（没有乘，数太小） |
| 入口的 Envoy | 0.73 到 0.74（接流量的那个） | 100m → 700m |
| mysql-main | 0.57 到 0.61 | 250m → 550m |
| 订单库（主从同一个数） | 主库 0.42 到 0.45，从库 0.15 到 0.19 | 250m → 400m |
| Kafka 的 broker | 0.38 到 0.47 | 250m → 400m |
| redis-cache | 主库 0.12 到 0.13 | 50m → 100m |
| redis-gate | 主库 0.125 | 100m，没有动（已经在这个比例上，不值得为它做一次主从切换） |

节点的 requests 合计：agent-1 5.75 核（76%），agent-2 6.10 核（81%）。滚动多出来的一个（最大 1.1 核）两个节点都放得下；第三个副本加滚动放不下，**HPA 的上限收到 2**（和下限相同，ScaledObject 留着，加节点之后只改一个数）。`perReplica` 按新的 requests 重算成 gateway 450、order 200，上限是 2 的时候不起作用。order 的连接池保持 40。

第 4 节的弹性测试是在第一步的数（上限 3、阈值 500 和 220）下做的，没有重做：机制没有变，现在的配置下它不会触发。

- **我的读法（没有验证）**：入口放进来的请求多了（2384 档到达 gateway 的从 2040 回到 2388），节点上要抢 CPU 的活更多；MySQL 的权重虽然按比例调了，服务合计的权重仍然是它的好几倍，而 MySQL 的线程一被推迟，等它的请求全都跟着慢。也可能只是一次测量的波动：每组只有一次，盘的快慢、落库的延迟在拐点以上本来就晃得厉害。要分清得每组多跑几次，或者直接读节点上各 cgroup 的 `cpu.pressure`。
- **对结论的影响**：拐点和拐点以下不受影响，容量结论照旧。拐点以上的表现是“入口不再误拒，落库更容易欠账”，欠账由背压（2500 的队列上限）接住，这一轮 `backlogged` 每秒 6 个。

### 6.3 顺带发现：Strimzi 的 operator 两天没有调和成功

改 broker 的 requests 之后 broker 没有滚动。`Kafka` 资源的状态是 `NotReady`，从 2026-11-20 16:26 UTC（宿主机重启后 3 分钟）起一直是：

```
IllegalArgumentException: Invalid DNS name: kafka-kafka-bootstrap.kafka.svc.19818.25.232   kubernetes.default
```

operator 启动时用 DNS 查 `kubernetes.default` 来猜集群域名。那一次启动赶在集群 DNS 就绪之前，查询落到了上游，拿到的是代理的假地址（198.18.x.x），猜出来的“域名”是一串垃圾，之后每次调和都在生成证书时失败。broker 不依赖 operator 运行，所以这两天的压测没有受影响，也没有任何东西报出来。

修法：`scripts/cluster/middleware.sh` 里装 operator 时用 `extraEnvs` 把 `KUBERNETES_SERVICE_DNS_DOMAIN=cluster.local` 写死（chart 的 `kubernetesServiceDnsDomain` 取默认值时不渲染这个变量，等于交给探测）。应用之后 operator 恢复调和，三个 broker 逐个滚动完成。

留给 3c：`Kafka` 资源的 `Ready` 条件要有告警。一个控制器静悄悄地坏了两天，是靠一次不相干的改动才发现的。

### 6.4 滚动中间件时的记录

## 7. 面试里这件事的说法

- **requests 是什么。** 不是预留也不是上限。它是调度器记账用的数，是 HPA 算百分比的分母，是节点满了之后内核分 CPU 的权重。三个用处都要求它接近实际用量，所以它应该来自压测，不是来自估计。
- **只调一部分 Pod 的 requests 会改变所有 Pod 的相对权重。** 把服务的 requests 调准、中间件不动，等于在节点满的时候让服务优先于数据库。平时看不出来，过载时才显现。量到的现象是服务自己更快、它们等 Redis 和 MySQL 更慢。
- **诚实的 requests 会让调度器拒绝你。** 全部按实测写，合计就接近节点的容量，再扩一个副本放不下。这是调度器在说“没有 CPU 了”，比 Pod 调度上去之后大家一起变慢要好。
- **滚动更新要占容量。** `maxSurge: 1` 意味着节点上要留得下最大的一个 Pod。requests 写满之后滚动会卡在 Pending：要么留余量，要么改成先停后起（滚动期间少一个副本），要么有空闲节点。
- **控制器坏了不等于它管的东西坏了。** operator 调和失败时 broker 照常跑，所以没有人发现；它的状态条件要单独监控。
- **HPA 的两个信号。** 请求速率不受 requests 写错的影响，和容量结论直接对应；但 `rate()` 的窗口让它不比 CPU 快，而且每个请求的开销随组合变。所以两个一起用：请求速率按便宜的组合定，CPU 接住变贵的情况。
- **扩容期间不丢请求靠什么。** 新 Pod 就绪之后才进端点；消费者组再均衡时分区只是换了主人，没有停；连接池在就绪之前已经是热的。量的是 69 万个请求 0 失败。
