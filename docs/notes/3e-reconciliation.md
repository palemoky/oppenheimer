## 1. 结论

1. **3e 的产出**：三个常驻的核对，各管一类数据，结果都是指标加日志。
   - `recon watch-totals`（3c 就有，这次补了退款一组和下钻）：钱，30 秒一轮。
   - `recon watch-stock`（新）：库存的计数对流水，1 分钟一轮，5 分钟一次完整的。
   - `recon watch-changes`（新）：派生数据，订单每变一次，约 10 秒后去商家索引、从库、冷库核对那一行。
   - 另外：`sku_stock` 加了入库总量 `stocked` 和一条 CHECK；六条新告警；`recon` 能按绝对时刻给窗口（`-from`、`-to`）；`make recon-check FROM= TO=` 给阶段 4 每次实验收尾用。
2. **三类数据的判据都不靠“等一会儿再比”。** 跨库的数据总有在途的，按时间切一刀，容差短了误报、长了发现得晚。这里每一类找了一个不依赖时间的判据：钱用支付单的状态把在途的分出来，库存用同一个库里的一致性快照，派生数据用行的版本号。
3. **原来的逐行对账没有删，变成了下面两层。** 连续的三样管“现在对不对”；每小时的树是不经过 CDC 的独立一路；每天的全量管旧数据事后被改坏。三层各自看不到的东西不一样（第 5 节）。
4. **在集群上验证过的**：
   - `watch-changes` 第一次启动把 topic 从头放了一遍，约 5 分钟核对了约 1670 万个订单的商家索引和从库，全部通过。
   - 九条对账告警里八条在 `oppenheimer-e2e` 里真实触发过，差异改回去后钱和库存的告警自己恢复。
   - 每天的全量 2 分 09 秒，只有探针流量时 gateway 的 p99 没有变。
5. **没有验证的**放在第 6 节，最要紧的两条：有负载时这三个核对的开销没有量；`DerivedDataCheckStalled` 没有真实触发过。

## 2. 三类数据各用什么办法

| | 钱 | 库存 | 派生数据 |
|---|---|---|---|
| 是什么 | 订单和支付单，两个服务各记各的 | 三个计数和它们的流水 | 从库、商家索引、冷库 |
| 在不在一个库里 | 不在 | 在 | 不在 |
| 在途的怎么办 | 用支付单的状态精确分出来 | 同一个快照里没有在途 | 用版本号分开“没追上”和“不一致” |
| 多久出结果 | 30 秒 | 1 分钟（已售 5 分钟） | 变更后约 10 秒 |
| 开销跟着什么走 | 最近 30 分钟的支付单 | SKU 数和流水的行数 | 变更的速率 |
| 对不上时知道什么 | 哪一分钟、差几笔、差多少钱，下钻到哪几笔 | 哪个 SKU、计数和流水各是多少 | 哪张订单、哪一列 |
| 发现不了的 | 同一分钟里一多一少正好抵消；没封口时被在途盖住的 | 流水本身记错了 | 派生端被直接改坏；CDC 自己漏掉的 |

### 2.1 钱：包含关系

订单服务先在自己的事务里写下支付结果，答复才发出去；支付服务收到答复才把支付单标成已答复。所以任何时刻，支付一侧“已答复”的是订单一侧“已记录”的子集。按支付单号一分钟一段：

- 这一分钟里的支付单都到了终态（封口）：两边相等。
- 还没封口：支付一侧不能比订单一侧多。

退款一组的结构一样：支付一侧“已退款”是订单一侧“要求退款”的子集。这是重读两边处理答复的代码核对的，不是照着成功一组类推的。核对时找到一条例外：订单已归档时要求退款不写记录。它够不着这里的窗口（归档至少 30 天，核对只看最近 30 分钟），但这个推理依赖关单在正常工作。

### 2.2 库存：CHECK 管总量，快照管流水

两层管的是不同的缺陷：

- **总量**（`available + reserved + sold = stocked`）由 CHECK 在每次写入时保证。它拦住的是“只改了一个数”。
- **计数对流水**由 `watch-stock` 核对。预占、确认、释放的每条增量自己三项之和是 0，所以“同一条增量应用了两次”“丢了一条增量”“改了状态没记增量”都不破坏总量，CHECK 拦不住，只会让计数和流水对不上。

核对在一个只读的一致性快照事务里做。前提是“改预占的状态”和“记增量”在同一个事务里，这是动工前读代码确认的。并发的测试证明了快照是必需的：把事务改成读已提交，第 2 轮就读到写了一半的状态。

### 2.3 派生数据：版本号的四种情况

v 是变更的版本，d 是派生端那一行的版本：

| 情况 | 判定 |
|---|---|
| d > v | 通过：更晚的那个版本有自己的变更，会被单独核对 |
| d = v，各列相同 | 通过 |
| d = v，有列不同 | 不一致，立刻报 |
| d < v 或者没有这一行 | 没追上：每 5 秒复查，2 分钟后仍然如此报落后 |

没有版本号时，“派生端的值和变更里的不一样”分不清是没追上、已经被更晚的变更覆盖、还是坏了，只能靠等。有了它，延迟取多少只影响复查的次数，不影响对错。

冷库是例外：归档程序先写冷库再删热库，所以看到删除事件时冷库里一定已经有了，没有就是丢了，第一次看到就报。

## 3. 实现和部署里踩到的坑

### 3.1 裸 `go test` 把对着库的用例全跳过了，输出还是 `ok`

第 3 步写完时主会话报了“测试通过”，实际上对着 MySQL 的用例一个都没跑：在模块目录里直接 `go test` 没有 `OPPENHEIMER_TEST_MYSQL_DSN`，用例 `t.Skip`，输出仍然是 `ok`。子 Agent 带着环境变量跑、报出一条失败才发现。

失败的是一条写错的期望值，代码没有错，但它暴露了规则的一个盲区（3.2）。教训有两条：单个模块用 `make test MODULES=$PWD/services/<模块>` 跑（已写进 `AGENTS.md`）；“跳过”和“通过”显示成同一个字时，报告通过之前要确认用例真的跑了。

### 3.2 没封口的那一分钟里，在途的一笔会盖住多出来的一笔

没封口时规则只看“支付一侧多出来的”。同一分钟里订单一侧有一笔在途的，笔数就相等了，支付一侧多的那一笔报不出来，要等封口（最晚到支付时限）。这是规则固有的宽松，3c 就是这样。逐笔比的时候“在途”可以细到每一笔，当时就找得到；但下钻只对合计报了差异的分钟做，所以这个盲区下钻补不上。

### 3.3 下钻为什么没有用现成的树

设计里写的是对那一分钟跑一次逐行的 `payment` 对账。实现时发现三件事：

1. 它比的不是同一件事。树比的是“已支付的订单”对“成功的支付单”，按订单号；合计比的是支付结果对支付单，按支付单号。退款的差异它看不到。
2. 它在那个时刻会误报。下钻发生在那一分钟之后一两分钟，窗口里的订单大半还在途，树没有“在途”的概念。
3. 直接比合计加起来的那两个集合，合计报了差异就一定找得到是哪几笔。

教训：复用现成的工具之前，先确认它比的关系和要解释的那个数是同一个。

### 3.4 新消费组从头读，压缩保留的 topic 等于全量核对

`cdc.order.orders` 是压缩保留的，每个订单留最后一条。kafkax 的新消费组从头读，所以 `watch-changes` 第一次启动把每个订单核对了一遍：约 5 分钟、1670 万个订单、全部通过，两个从库各约 0.3 核。

这是一次便宜的逐行核对，决定保留。问题在于它当时没有 CPU 上限，在控制面节点（4 核，etcd 也在上面）占了约 2.8 核。加了 1 核的上限。位点丢了时它会再来一次。

反过来它也是一个工具：想让它重新核对某一行，不用去动源库，删掉它的消费组就行（造差异验证时就是这么做的）。

### 3.5 主会话把“在重放”看成了“卡死”

看到它占 2.8 核、几次查询里计数器的值没有变，主会话判断它卡住了，把它缩到 0，加了调试端口重新部署去抓剖析。其实指标一直在更新，是连着几次查询落在同一个导出间隔里。教训：用区间查询（`[10m:1m]`）看一条序列有没有在动，不要拿两次瞬时查询的值比。

### 3.6 `increase` 的窗口短于两个导出间隔时没有结果

`recon-check` 用“TO 之后成功的轮数有没有增加”判断核对有没有越过 TO。指标每 60 秒导出一次，TO 在 3 分钟前时窗口只有 60 秒，里面不够两个点，`increase` 没有结果，被读成“没有成功的一轮”。加了最小窗口，不够时明说还量不出。

更稳的做法是让每个核对自己报一个“核对到的时刻”（`watch-changes` 的 `verified_through` 就是），而不是从计数器的增量反推。钱和库存没有做。

### 3.7 “已售”一小时一轮，收尾就要等一小时

完整的一轮要扫全部流水，设计时没有量过耗时，保守定成每小时。部署后量到不到 1 分钟（599 个 SKU），而阶段 4 每次实验收尾要等它越过实验的结束时刻。改成 5 分钟一轮。流水只增不减，它会随总量变慢，到时候要重看。

### 3.8 在 e2e 里验证告警，每次都要另下发一份规则

正式的规则只看命名空间 `oppenheimer`（e2e 里的失败是故意制造的）。所以在 e2e 里造差异，告警不会响，要另下发一份把命名空间换掉的副本，加一个标签用来静默。做法写在 runbook 里，没有做成脚本。

### 3.9 其余几个值得记的

- **“卡住的预占”按订单号里的时间算**，不是 `created_at`。造差异时改 `created_at` 没有用。
- **从库的实例是 e2e 和长期运行的那一套共用的**，不能用停复制的办法在 e2e 里造“没追上”。
- **`go mod tidy` 不读 `go.work`**：`recon` 新引了 `api` 模块之后，`GOWORK=off go build`（镜像里就是这样构建的）失败，要在模块里 tidy。
- **`make deploy` 之前工作区要干净**：有没提交的改动时镜像的 tag 带 `-dirty`，哪怕改的只是文档。

## 4. 核对程序和业务消费者的取舍相反

`watch-changes` 是只读的核对，不是数据通路，所以出错时的选择和业务消费者正好反过来：

| 情况 | 业务消费者 | 核对程序 |
|---|---|---|
| 依赖连不上 | 停住等它恢复 | 一样停住：把“读不到”当成“核对过”等于漏报 |
| 消息本身解不开 | 标成永久错误进死信，否则数据会丢 | 计数、打日志、跳过：它停了只是自己瞎了 |
| 重复消费 | 要幂等 | 没有后果 |
| 没追上的那些 | | 只放在内存里，重启会丢，由每小时的逐行对账盖住 |

最后一条是一个明确的取舍：另一种做法是没追上就不提交位点、原地重试，但一条没追上的变更会挡住整个分区最多 2 分钟。

## 5. 三层各自看不到什么

| 层 | 多久一次 | 看不到的 |
|---|---|---|
| 连续（三个 watch） | 秒到分钟 | 派生端被直接改坏而源库没有变更；CDC 自己漏掉的变更；`order_items`、`payment_results` 的主从（不在 CDC 里） |
| 每小时的树 | 小时 | 窗口之外的旧订单后来被改 |
| 每天的全量 | 天 | 发现得晚 |

`watch-changes` 和商家索引的消费者读同一个 topic，源头错了两边一起错。所以每小时的树要留着：它是唯一一条不经过 CDC 的路。

全量什么时候换办法：单次超过 30 分钟（按现在的速度约 2.4 亿单），或者量到它影响线上。换成“封账加离线”：过了足够久的一天算一次摘要存下来，以后只扫没封的那几天；扫描打在备份恢复出来的副本上。这一步只写了判据，没有实现。

## 6. 没有做的、留给后面的

- **有负载时的开销没有量**：三个核对的 CPU、`watch-changes` 加在从库和索引库上的点查、等着复查的条数能涨到多大、过载时一分钟几万笔支付的下钻要多久。派生端整体落后时复查没有限流，只能靠 `changes_check` 开关关掉。
- **`DerivedDataCheckStalled` 没有真实触发过**：它要“核对停了”同时“订单库有写入”，e2e 里没有流量。登记在阶段 4 的“4a 准备”。
- **从库这个目标没有造过不一致**（从库只读，实例是共用的）。
- **每天全量对线上的影响只在探针流量下量过**。
- **`DerivedDataMismatch` 响过 5 分钟后自己恢复**，和那一行修没修无关：它是按计数器的增量报的。
- **子 Agent 指出的几个归类问题没有处理**（设计 9“第 4 步”的六条）：例如从库对删除分不清“已经应用了删除”和“从来没有过这一行”。
- **钱和库存没有“核对到的时刻”这个指标**（3.6）。
- **封账加离线没有实现**。

## 7. 面试时怎么讲

**一句话**：原来所有数据用同一种办法对账（哈希树逐行比），要等数据定型、按小时跑；我按数据的性质拆成三类，各找了一个不依赖时间容差的判据，把“现在对不对”从小时缩到秒到分钟。

**展开的顺序**：

1. 先讲为什么“等一会儿再比”不行：跨库总有在途的，容差短了误报、长了发现得晚。
2. 再讲三个判据各自凭什么成立：钱靠写入顺序带来的包含关系，库存靠同一个事务加一致性快照，派生数据靠行的版本号。每一个都要说出它依赖的前提，以及前提是怎么核对的（读代码、并发测试）。
3. 然后讲每一类发现不了什么，以及为什么旧的逐行对账要留着。
4. 最后讲验证：在真实的 CDC 输出上核对了 1670 万个订单；造了哪些差异、哪一条告警没有触发过、为什么。

**容易被追问的**：

- CHECK 已经保证了总量，为什么还要对账？（每条增量自己是平的，重复应用和丢失都不破坏总量。）
- 版本号相同内容不同，可能是怎么来的？（派生端被直接改了；消费者把某一列映射错了；归档搬坏了。）
- 核对程序自己挂了怎么办？（每一类都有一条 Stalled 的告警；`recon-check` 把“差异是 0”和“还没核对到”分开。）
- 这套核对在过载时会不会雪上加霜？（会：复查没有限流。现在有开关可以关，开销没有量过，这是没做完的部分。）
