# 2c 笔记：把六个服务部署到 Kubernetes

这份笔记整理 2c 里值得在面试中讲的点，按主题组织，不按开发步骤。每条尽量按“问题是什么、我们怎么做的、为什么、量到的数或踩到的坑、面试时怎么讲”来写。设计全文见 [design/2c-services.md](../design/2c-services.md)（下文简称“设计”，引用章节号；“设计 13”指第 13 节“实现中的发现和量到的数”，其中的“第几步”是实现顺序里的步），取舍见 [ADR-0028](../adr/0028-worker-id-lease.md)（节点号租约）、[ADR-0007](../adr/0007-kafka-and-redis-clients.md) 末尾的补充（不用静态成员）、[ADR-0020](../adr/0020-service-protection.md)（边车和服务保护的设计）。

2c 做的事：把 gateway、order、inventory、payment、orderindex、cdc 六个服务做成镜像，用一个公共 Helm chart 部署到 2a、2b 建好的 k3s 集群上；服务之间的 gRPC 走每个 Pod 里的 Envoy 边车；配好探针、优雅启停、滚动发布和按 CPU 的 HPA；并让阶段 1 的端到端测试和一致性测试对着集群入口通过。

**关于“通用知识”**：文中标注“（通用知识）”的段落，是为了把原理讲清楚而补的 Kubernetes、Linux、Kafka 常识，设计文档和 ADR 里没有出处，面试前要对照官方文档核对。没有标注的内容，事实来自设计文档、ADR 或阶段计划。设计文档里标了“推断”“没有查”“没有量”的地方，这里保持同样的说法，不要在面试时说成确定的结论。数字都是 2026-11-15 在这个集群上量的。

## 1. 镜像

### 1.1 多阶段构建：为什么镜像小，缓存怎么利用

**问**：为什么 Go 服务的镜像可以做到几十 MB 甚至更小？Dockerfile 里的顺序为什么重要？

**我们怎么做的**（设计 4，13 第一步）：一个 Dockerfile，两个阶段，用构建参数选择服务。构建阶段用官方 Go 镜像（`golang:1.27.4`），编译出静态二进制；运行阶段只拷贝这个二进制。构建上下文是整个仓库，因为多模块的 go workspace 里服务依赖 `pkg/` 和 `api/`，要靠 `go.work` 解析；`.dockerignore` 排掉 `bin/`、`tmp/`、`.git`、`docs/`。依赖下载和编译缓存用 BuildKit 的缓存挂载。

**为什么小**：构建阶段里有 Go 工具链、源码、模块缓存，加起来约 1 GB 量级，这些东西运行时一个都不需要。多阶段构建只把最终产物拷进运行阶段，前一个阶段的层不进最终镜像。设计里提到约 1 GB 降到几十 MB，是这条的说法；实测见下。

**量到的数**（设计 13 第一步）：七个镜像（六个服务加 `recon`）本机镜像库报的大小是 4 到 18 MB；全部构建并推送 2 分 20 秒；改一行代码后重新构建一个服务约 3 秒，因为依赖下载那一层走缓存。

**（通用知识）层缓存的规则**：Dockerfile 的每条指令产生一层，某一层的输入变了，它和它后面所有层的缓存都失效。所以要把变化少的放前面：先复制 `go.mod`、`go.sum` 并下载依赖，再复制全部源码并编译。这样改业务代码不会让依赖下载重做。本项目是多模块 workspace，要先复制各个模块的 `go.mod`，再复制代码，写法比单模块复杂，具体顺序以 `deploy/docker/Dockerfile` 为准。设计 13 还记了一个代价：任何一个模块加依赖，七个镜像的依赖层都失效，靠缓存挂载垫着。

**面试时怎么讲**：先说结论“构建环境和运行环境分开”，再说两个收益（体积、攻击面），再提层缓存的顺序。被追问“你们的镜像多大”就说 4 到 18 MB，并说明这是本机镜像库报的大小。

### 1.2 交叉编译，不用 QEMU 模拟

**问**：开发机是 Apple Silicon（arm64），集群是 x86_64，镜像怎么构建？

**我们怎么做的**（设计 4）：构建阶段用 `--platform=$BUILDPLATFORM`，即在 MacBook 上原生按 arm64 运行 Go 编译器，用 `GOOS=linux GOARCH=amd64 CGO_ENABLED=0` 交叉编译出 amd64 的二进制。运行阶段的基础镜像是 amd64 的。

**为什么**：Go 自己带交叉编译，不需要目标架构的机器。另一条路是用 QEMU 模拟 amd64 来跑整个构建，设计里写的是“要慢一个数量级”。这个说法是设计文档里的判断，没有在本项目里单独量过两种做法的耗时对比，面试时讲成“模拟明显更慢”即可，不要报一个具体倍数。

**为什么要 `CGO_ENABLED=0`**：Go 的纯 Go 代码才能无条件交叉编译；一旦启用 cgo，就要有目标平台的 C 编译器和库。关掉 cgo 得到的是不依赖 libc 的静态二进制，这正是能放进 `static` 基础镜像的前提。反例见 1.5：`-race` 要 cgo，就必须换一套做法。

### 1.3 distroless、非 root、没有 shell

**问**：为什么用 distroless 而不是 alpine？

**我们怎么做的**（设计 4）：运行镜像用 `gcr.io/distroless/static-debian13:nonroot`，按多架构清单的摘要固定，版本登记在 `versions.md`。里面只有 CA 证书、时区数据和一个非 root 用户，没有 shell、没有包管理器。

**为什么**：服务不需要别的东西。攻击面小，镜像也小。以非 root 运行是为了即使容器被攻破，进程的权限也有限（（通用知识）再配上只读根文件系统、去掉 capabilities 就更严格；我们做了只读根文件系统，另挂一个 `/tmp`，见设计 13 第二步）。

**代价**：`kubectl exec` 进不去，排查要用 `kubectl debug` 挂临时容器，设计里说这本身是值得练的。设计 13 还记了一个后果：`degrade.sh` 只能走 `kubectl port-forward`，不能 `kubectl exec`。

**一个小坑**（设计 13 第一步）：exec 形式的 `ENTRYPOINT` 不能引用构建参数，而运行镜像里又没有 shell 可以展开变量，所以构建阶段建一个符号链接 `/app/entrypoint -> <服务>`，入口固定写它。order 的镜像里同时有 `order` 和 `archiver` 两个二进制，归档任务的 Pod 用 `command: ["/app/archiver"]` 覆盖入口。

**留下的问题**（设计 13 第一步，如实说）：基础镜像按摘要固定之后不会自己拿到安全更新，要人去换；`-ldflags="-s -w"` 去掉了符号表，panic 堆栈不受影响，用 pprof 时函数名来自另一张表（pclntab），设计里写的是“到时候实际看一眼再确认”，**没有验证**。

### 1.4 tag 为什么用 git 提交号、不重用 tag

**问**：为什么不用 `latest`，为什么不能给不同内容重用同一个 tag？

**我们怎么做的**（设计 4）：tag 是 git 短提交号，工作区有没提交的改动时加 `-dirty-<时间>`；镜像名是 `192.168.50.50:5000/oppenheimer/<服务>:<tag>`。

**为什么**：两点原因，设计里写得很明确。第一，Deployment 里的镜像字段没变，`helm upgrade` 不会产生新的 Pod 模板，就不会滚动。第二，节点上缓存着同名的旧镜像时，（通用知识）默认的拉取策略对已存在的非 `latest` tag 不会重新拉，于是新旧内容无从分辨，出了问题也无法回溯“当时跑的是哪一版”。

**代价**（设计 13 第一步）：工作区不干净时每次构建一个新 tag，仓库会越积越多，没有清理。

### 1.5 带 `-race` 的测试二进制为什么不能放进 static 镜像

**问**：e2e 测试要在集群里跑，为什么测试镜像不能和服务镜像一样用 static 基础镜像？

**我们怎么做的、为什么**（设计 13 第五步前一半）：测试用 `go test -c -race` 编成二进制。Go 的竞态检测器依赖 cgo（`-race` 要 cgo），于是二进制是动态链接的，运行时需要 glibc，放不进 `static` 基础镜像。做法是：构建阶段仍然在原生的 arm64 上，装 Debian 的交叉 gcc 去编 amd64；运行镜像换成带 glibc 的 `distroless/base-debian13`（同样按摘要固定、已登记）。

**量到的数**：第一次构建 39 秒，镜像 29.7 MB。

**面试时怎么讲**：因果链是“`-race` → 要 cgo → 动态链接 → 要 libc → 不能用 static → 交叉编译时还要目标平台的 C 工具链”。这条把“`CGO_ENABLED=0` 的意义”反过来讲了一遍，很容易展示你真的理解静态链接。

## 2. 雪花节点号的租约

这是 2c 里唯一一处不改代码就会出一致性问题的地方，也是设计演变最多的一条，建议当作主讲项目之一准备。

### 2.1 问题是什么

`pkg/idgen` 发的订单号和支付单号是“毫秒时间、6 位节点号、10 位序列号、6 位基因”（设计 1）。唯一性的前提是**同一时刻同一个服务里没有两个进程用同一个节点号**。本机靠 `run-local.sh` 里写死 `WORKER_ID=2`（order）、`3`（payment）。到 2b 为止每个服务只有一个进程，一直没有问题。

一个 Deployment 的所有 Pod 环境变量相同。两个副本用同一个节点号，同一毫秒里各自从序列号 0 开始发，**必然重号**。节点号只有 6 位，一共 64 个。用到发号器的只有 order 和 payment，两者发的是不同的号，所以只要求同一个服务内部不重。

要的性质（设计 5.1）：**任何时刻，一个服务里用同一个节点号发号的进程最多一个**，包括滚动发布时新旧 Pod 同时存在，以及节点失联后旧 Pod 还在跑而新 Pod 已经起来的时候。

### 2.2 三种做法（设计 5.2）

- **A. StatefulSet 的序号**：Pod 名里的序号当节点号，不写代码。放弃的原因见 2.5。
- **B. 从 Redis 租**（`SET NX` 加过期）：Redis 主从异步复制，Sentinel 提升从库时刚写的租约可能丢，另一个进程能租到同一个号，而原持有者要到下一次续租才发现。正确性建立在闸门那套 Redis 的故障切换行为上，所以没选。
- **C. 从 MySQL 租**（选了它）：每个发号的服务在自己的库里放一张 64 行的 `idgen_worker` 表，一行一个号，有 `owner`、`expires_at`、`last_ms` 三个字段。租用条件更新抢：`UPDATE ... SET owner=?, expires_at=NOW(3)+INTERVAL ? SECOND WHERE worker_id=? AND expires_at < NOW(3)`，影响一行才算租到。续租只有 `owner` 还是自己才成功。

ADR-0028 还列了另外几种备选：Kubernetes 的 Lease 对象（服务要有 API 权限，控制面不可用时起不了新副本）、号段模式（号里就没有时间了，而冷热归档按订单号里的时间划分，分片靠号里的基因）、取 Pod IP 低位（6 位只有 64 个值，Pod 网段是 /16 会撞）。

租约放在哪：order 放第一个订单库 `order_db_0`，payment 放 `payment_db`。理由是 order 启动时本来就要连订单库做迁移，没有新增硬依赖。

### 2.3 设计怎么演变：从“持有者自己设限”到“互不重叠的区间”

**第一版**（设计 5.2）：和常见租约一样，持有者在本地记下最后一次续租成功的单调时刻，超过“租期减余量”还没续上就**自己**停止发号。`last_ms` 的含义是“这个号发出过的最大毫秒”，用来防两台机器的时钟差（新持有者等自己的时钟超过它再发号）。

**动手时发现的问题**（设计 5.3）：这个写法的正确性要靠比较两台机器的时钟，还要靠进程不会在“判断租约有效”和“真的用号”之间卡住（虚拟机暂停、长 GC）。判断完有效之后卡一分钟再醒来，号已经被别人租走了。

**改成的做法**（设计 5.3，ADR-0028）：不再依赖“同一时刻只有一个持有者”，而是给每一任持有者划一段**互不重叠的毫秒区间**。

- 表里每个号有一个上界 `last_ms`：历任持有者可能用到的最大毫秒。
- 持有者每次续租把上界抬到“自己的时钟加一个租期”。**数据库确认写入之后**，它才被允许用到那么远。发号时如果毫秒时间超过已确认的上界就拒绝（`ErrLeaseExpired`）。
- 下一任用条件更新接手，租到之后读出上一任留下的上界，只发比它大的毫秒。上一任这时已经不是持有者，续租的条件（`owner = ?`）不成立，再也抬不动上界。
- 于是上一任发的号都在上界以内，下一任发的都在上界以外，中间隔着数据库里的一次条件更新。

这样，租期（30 秒）和续租间隔（10 秒）只影响可用性，不影响唯一性：卡住一分钟后醒来的旧持有者，发号用的毫秒超过自己已确认的上界，会被拒绝；它的时钟慢了，发出来的号仍然落在自己的区间里，不会和接手的人重叠。过期与否只由数据库的 `NOW(3)` 判断，不比较两个进程的时钟。

**测试**（设计 5.3）：有“上一任被接手之后还在发号”“两边时钟差 20 秒”两个用例，还有“去掉这条规则测试会失败”（手工改坏验证过）。这最后一条在面试里值得讲：一个守护不变量的测试，要证明去掉守护它会红。

**顺带发现的一个原有隐患**（设计 5.3）：`Generator.Next` 原来的写法在检查之前就改了序列号。新加的“拒绝发号”路径会把“这一毫秒用到哪了”冲掉，时钟再回到同一毫秒时会重号。已改成检查都通过才写回，有测试。

### 2.4 它和 fencing token 是什么关系

**（通用知识）** fencing token 是 Martin Kleppmann 分析分布式锁时提出的概念：锁服务每次授予锁都给一个单调递增的数字，资源方（存储）记住见过的最大数字，拒绝带着更小数字的请求，这样即使持有者因为暂停而不知道自己的锁已过期，它的写入也会被资源方挡住。要点是**把正确性的检查放到资源方，而不是信任持有者的自我判断**。

我们这里的对应关系，是我自己的类比，设计文档和 ADR 里没有这么写：“资源”是发出去的 ID 的取值空间；“token”是毫秒时间的区间上界；“检查”由发号逻辑在本地对照**数据库已确认的上界**来做，而不是对照持有者自己的钟。和经典 fencing 的区别是：经典做法里拒绝发生在资源方，这里拒绝发生在持有者进程自己的发号函数里，但它依据的是数据库确认过的值，不依据本地计时。面试时可以说“思路同源，是把对时钟和暂停的依赖，换成对一个已经持久化的单调上界的依赖”，不要说成它“就是”fencing token。

### 2.5 为什么没选 StatefulSet 的序号

**问**：StatefulSet 一行代码不用写，保证同一序号最多一个 Pod，为什么不用？

**答**（设计 5.2，ADR-0028）：代价都来自这个保证本身。

- 滚动发布是原地一个一个换（先删 `order-1` 再建 `order-1`），没有“先起新的再停旧的”，发布期间少一个副本的容量。
- 节点失联时，上面的 Pod 停在 Terminating，StatefulSet 不会在别的节点上建替代的（它不能确认旧的已经死了），要人工强制删除。阶段 4 的“关掉一个节点”实验里，order 会一直少一个副本直到人介入。
- 把无状态的服务变成了有身份的。ADR 里记了：主人最初倾向这个方案，讨论后确认它不是生产里无状态服务的常见做法。

选 MySQL 租约保住了 Deployment 的两个能力：滚动时新旧各占一个号，节点失联后控制器在别处重建。集群上的验证（设计 13 第三步）：order 和 payment 改成 2 个副本后，四个 Pod 各租到不同的号（order 2 和 3，payment 2 和 3）；之前单副本的 Pod 用的是 0，滚动时多开的那个短命的 Pod 用过 1。旧 Pod 退出后表里它那一行 `owner` 为空，`last_ms` 是它实际发过的最后一个号的毫秒时间（和那一单的订单号对得上），不是登记的上界。

### 2.6 代价和没有验证的东西（面试被追问时要诚实）

- **扩大了故障面**（设计 5.3，ADR-0028 后果）：设计 5.2 原本写“停止发号没有扩大故障面”，**这句不对**，5.3 已更正。落库健康是按库判断的，订单库 0 不可用时原来只拒绝一半用户；现在租约在订单库 0 上，它不可用超过约 20 秒（租期减续租间隔）之后**所有**用户的下单都被拒绝，按降级处理返回 503（`ORDER_LANDING_UNAVAILABLE`）。数据库回来后第一次续租成功就自动恢复。
- payment 的租约过期时 `Pay` 返回的是内部错误，不是降级（payment 的库是它唯一的存储，本来库不可用时每个接口就都是内部错误）。
- 租约被别人租走是致命错误：续租发现自己不是持有者时，发号永久停止，进程退出由 Kubernetes 重启。
- 主库故障切换可能丢掉最后一次续租：接手的人从“上界加 10 秒”之后才开始发号。丢得更多（复制落后超过 10 秒时主库故障）就没有保证，和那种情况下订单数据本身会丢是同一个问题，留到阶段 4。
- 崩溃的进程占着的号要过 30 秒才能被别人租走；64 个号里几乎总有闲置的，所以新进程不用等。**64 是副本数的硬上限**，用完时启动失败。
- **没有在集群上验证**（设计 13 第三步）：租约所在的库不可用时受理被拒绝再恢复（本机只有单元测试）；进程被 `kill -9` 后那个号 30 秒后才能被租走。
- ADR-0028 里有一句**推断、没有验证**：`idgen_worker` 表恢复出旧值是安全的（上界只会偏小一个备份周期之前的值，而那时的持有者早已不在）。
- 本机和 CI 设了 `WORKER_ID` 就用它、不租；集群上不设。

**面试时怎么讲（一分钟版）**：问题是多副本下节点号会撞；先想到 StatefulSet，但它在节点失联时不会自动换地方、滚动也要原地换；想到的租约通常是“持有者本地判断有效”，但那要靠时钟和进程不卡住；我们改成给每一任划互不重叠的毫秒区间，上界经数据库确认才使用，租期只影响可用性；代价是租约所在的库挂了所有下单都被拒绝，这个我在设计里一开始写错了，后来更正了。

## 3. 边车、gRPC 负载均衡与服务发现

### 3.1 原生 sidecar：解决启动和停止的顺序

**问**：Envoy 边车为什么写成 `initContainers` 里 `restartPolicy: Always` 的容器，而不是普通的第二个容器？

**答**（设计 6.1）：解决的是顺序问题。

- **启动**：边车先起来并就绪，服务容器才启动。否则服务启动时的预热调用（order 预热闸门要调 inventory）会打在还没监听的出站端口上。
- **停止**：服务容器全部退出之后，kubelet 才给边车发 SIGTERM。服务在 `DRAIN_DELAY` 和停止阶段还要处理在途请求、还要调下游，边车必须活到最后。普通的多容器 Pod 里两个容器同时收到 SIGTERM，Envoy 先退出的话在途请求全部失败。

cdc 没有 gRPC 调用，没有边车。gateway 的 HTTP 入站不经过边车（入口的 Envoy 直接连 gateway 的 8080），它的边车只管四个出站。

**实现时的几个细节**（设计 13 第二步）：边车的存活探针用 `/server_info`，不用 `/ready`，因为后者在排空时是 503，用它做存活探针会让排空中的边车被杀；边车和服务容器都以数字 uid 运行（Envoy 的镜像默认是 root）；边车 CPU requests 是 20m。

**（通用知识）** 原生 sidecar 是 Kubernetes 较新的特性（早期版本需要打开特性门控，后来成为默认可用），具体从哪个版本起稳定，面试前查官方文档。

### 3.2 gRPC 长连接为什么在 ClusterIP 后面不均衡

**问**：gRPC 调一个 ClusterIP Service，为什么负载不均？怎么解决？

**要点**（设计 6.2）：

- gRPC 跑在 HTTP/2 上，一条 TCP 连接复用所有请求，而且连接是长的。
- ClusterIP 的负载均衡（kube-proxy）是按**连接**做的：一个调用方进程对一个 Service 只建一条连接，这条连接落在哪个 Pod，之后所有请求都去那个 Pod。下游有两个副本，一个满载一个空闲；扩容出来的新 Pod 一个请求也收不到，直到调用方重连。
- 解法都是把均衡从连接层挪到请求层。三种：(1) 客户端自己做，gRPC 的 `dns:///` 加 `round_robin`，要配 headless Service；(2) 中间放一个懂 HTTP/2 的七层代理按请求分发；(3) 服务网格，本质上是 (2) 自动化加控制面。我们用的是 (2)：服务进程到自己的边车是一条本地连接，边车对每个下游 Pod 各维持连接、按请求选。2d 计划迁到 Istio，即 (3)。

### 3.3 headless Service 加 STRICT_DNS

**怎么做的**（设计 6.2）：每个服务两个 Service。普通的 ClusterIP Service（`order`）给不经过边车的访问用；headless Service（`order-headless`，`clusterIP: None`）的 DNS 返回所有**就绪** Pod 的地址。调用方边车的出站集群指向 `order-headless.oppenheimer.svc.cluster.local:15001`，Envoy 的 `STRICT_DNS` 类型把解析出的**每一个地址**当成独立的上游，定期重新解析，按请求轮流。

**（通用知识）headless Service 是什么**：`clusterIP: None` 的 Service 没有虚拟 IP，也不经过 kube-proxy，DNS 查询直接返回后端 Pod 的 IP 列表。它把“选哪个后端”的权力交还给客户端。

**设计里的配置来源**（设计 6.3）：`deploy/envoy/*.yaml` 仍是唯一来源（本机 compose 在用，Go 的测试还会核对出站路由超时和代码里的时限差 500 毫秒）。部署脚本只替换两处地址（`host.docker.internal` 换成 `127.0.0.1`，`envoy-<服务>` 换成 headless 的域名）再交给 chart，不在 chart 里另存一份。

**和设计不同的地方**（设计 13 第二步）：gateway 没有 headless Service（它的边车没有入站）。

### 3.4 对照实验：直连 ClusterIP 对比经边车（设计 13 第四步）

读两个 inventory Pod 边车的入站计数，各压 30 秒：

| gateway 怎么连 inventory | 两个 inventory Pod 各收到 |
|---|---|
| 经自己的边车（现在的做法） | 770 和 770 |
| 直连一个临时建的 ClusterIP Service（实验后已删） | 1380 和 160 |

直连时那 160 是 order 经它自己的边车发来的一半。gateway 的约 1200 个请求**全部**去了同一个 Pod：两个 gateway 进程各建了一条长连接，kube-proxy 按连接选后端，两条恰好选了同一个。

接着删掉那个满载的 Pod：连接断开时 20 个请求失败（直连没有“下游要走了”这个信号可用，错误是 `remote connection failure`），重连之后两条连接这次恰好各落在一个 Pod 上，分布变成约一半一半。结论：直连时的分布是每次建连接时掷出来的，而且只在重连时才重掷；经边车时是按请求轮流，两边完全相等。

**面试时怎么讲**：先说原理（连接级对请求级），再给这组数字：同样的负载，一边 770 对 770，另一边 1380 对 160。注意诚实表述：这是“先看到问题再解决”的实验，直连是两个 gateway 进程各一条连接的情形，分布每次建连接都可能不同，不要把 1380 对 160 说成固定比例。

### 3.5 为什么 2c 不上服务网格，决定了什么（设计 6.5）

Istio、Linkerd 做的就是这件事的通用版：自动注入边车，端点经 xDS 实时下发（没有 DNS 的延迟），还带 mTLS。2c 先不换的理由：1d 的配置和三个坑是逐项实测过的，时限和代码对着；控制面要多占 1 GB 上下的内存，当时余量放不下；网格会把“端点怎么传到代理、摘流要等多久”这些正要弄明白的事盖住。代价是端点靠 DNS，变化传得慢，要用 `DRAIN_DELAY` 垫；服务多了以后手写配置不可维护。

**主人的决定**：服务网格更贴近真实环境，要做，但分两步：2c 先手写边车，亲手量一遍端点传播和摘流；2d 迁到 Istio，熔断、并发上限、路由超时改写成它的资源，逐项对照 1d 的三个坑重新验证。内存估计控制面加 10 个边车 1.5 到 2 Gi，**设计里写明是估计，没有实测**。还有一个待解决的麻烦：本机 compose 仍是手写的边车，同一个超时要在两处维护，核对时限的 Go 测试要有对应办法。

**DNS 对比 xDS**：我们量到 DNS 路径下端点变化要 2 到 9.5 秒才传到调用方边车（见 4.2），xDS 是控制面推送，设计里的说法是“没有 DNS 的延迟”。**设计没有给出 xDS 下传播时间的实测数**，2d 迁 Istio 之后可以量，现在不要编一个数字。

### 3.6 边车配置在多实例下要重新看的数（设计 6.4）

- `max_ejection_percent: 100`、`healthy_panic_threshold: 0` 保留。两个副本时默认值不行（10% 的 2 是 0 个）。含义变成摘除的是**一个 Pod**，另一个继续接流量；两个都被摘时立刻失败，和单实例一样。
- 并发上限是每个调用方 Pod 各算各的：`max_requests: 128` 是“这一个 gateway Pod 对 inventory 的在途请求数”，两个 gateway 合计 256。数值先不改，设计写“量过再说”。
- 出站路由不重试（ADR-0020：同步链上不重试）。靠的是 Pod 在 `DRAIN_DELAY` 里继续正常服务，而不是出错后重试。

## 4. Pod 被删时：摘流和 DRAIN_DELAY

### 4.1 问题：SIGTERM 和摘端点是同时开始的

**问**：为什么 Pod 收到 SIGTERM 后直接退出，会有请求失败？

**答**（设计 8.1）：API 把 Pod 标成 Terminating 之后，两件事**同时**开始，互相不等：

1. kubelet 给容器发 SIGTERM。
2. 端点控制器把这个 Pod 从 EndpointSlice 里标成不可用，然后各处才陆续知道：入口的 Envoy（经 Envoy Gateway 的 xDS）、调用方的边车（经 DNS）。

所以收到 SIGTERM 的那一刻，别人还在给它发请求。如果进程立刻退出，这些在路上的请求就失败了。

### 4.2 我们的流程和 DRAIN_DELAY 怎么量出来

`pkg/app` 的流程（设计 1、8.1）：收到 SIGTERM → `/readyz` 变 503、gRPC 健康检查变不可用、**继续正常服务 `DRAIN_DELAY`** → 停止接新请求、处理完在途的（最多 20 秒）→ 退出。之后 kubelet 才停边车。`DRAIN_DELAY` 在本机一直是 0，该设多少取决于“一个 Pod 被摘掉这件事传到每个调用方要多久”，这个数只能在集群上量。

**怎么量**（设计 13 第四步）：带着负载（`probe.py`，20 个 worker 从 MacBook 经入口持续发查库存、下单、查订单，约 90 个/秒）删一个 Pod，同时每 0.2 秒读两个 gateway 边车的 `/clusters`，看它们最后一次把请求发给这个 Pod 是什么时候。5 次（inventory 3 次、order 2 次），10 个样本：

| | 最短 | 最长 |
|---|---|---|
| 删除之后调用方的边车还在给它发请求 | 1.7 秒 | 9.3 秒 |
| 它从边车的上游列表里消失 | 2.0 秒 | 9.5 秒 |

样本在 2 到 9.5 秒之间散开，和“headless 记录的 TTL 加 Envoy 的重新解析间隔，各约 5 秒，相位随机”的预期相符。**注意措辞**：这是和预期相符，两个间隔本身没有单独去量，所以不要在面试里说“TTL 是 5 秒、重新解析间隔是 5 秒”。设计 6.4 还记着：CoreDNS 的配置是 `cache 30`、`kubernetes` 插件没有写 `ttl`（读过 ConfigMap），其余几个数“按记忆是 5 秒量级，不照记忆写，在集群上量”。

**定值**：`DRAIN_DELAY` = 15 秒，即最长的 9.5 秒加 5 秒余量；`terminationGracePeriodSeconds` = 45 秒，要大于 `DRAIN_DELAY` 加停止时限 20 秒加边车自己退出的时间（设计 8.1 的起点就是 15 和 45）。这 5 次删除期间 2 万多个请求 0 失败。

### 4.3 对照：DRAIN_DELAY=0，以及两层保护各管一段

只把 inventory 改成 0，删两次 Pod：每次 15、16 个查库存的请求失败（`503 UNAVAILABLE`，`upstream connect error ... connection timeout`），都集中在约 1 秒之内。之后没有再失败，不是因为调用方知道它没了（那要等几秒），而是边车**连续 5 次失败后把它摘除了**。

结论：两层各管一段。`DRAIN_DELAY` 让正常的退出一个请求都不丢；边车的异常摘除给不正常的退出兜底（崩溃、强删）。强删的实测见 9.5：29 个 5xx。

### 4.4 为什么不用 preStop 里 sleep

**问**：社区常见做法是在 `preStop` 里 `sleep 15`，你们为什么不用？

**答**（设计 8.1）：它做的是同一件事（推迟 SIGTERM），但进程在这段时间里不知道自己要走了，就绪探针还是通过的。这里进程自己知道：就绪立刻变 503、gRPC 健康检查置为不可用，日志里看得到摘流开始和结束。另外消费者在停止时提交位点、主动退出消费组，分区马上交给别的副本，不用等会话过期。

**（通用知识）** `preStop` 钩子在 SIGTERM 之前执行，而且它占用的时间算在 `terminationGracePeriodSeconds` 里；使用 distroless 镜像时，没有 shell 就没有 `sleep` 命令可用，需要新版 Kubernetes 提供的 `sleep` 动作，具体版本和写法面试前核对。

## 5. 滚动发布

### 5.1 参数各管什么

**问**：`maxSurge`、`maxUnavailable`、`minReadySeconds`、PDB 分别是什么？

**答**（设计 8.2、7.4）：

- Deployment 用 `maxSurge: 1`、`maxUnavailable: 0`：先起一个新的，就绪了再停一个旧的，任何时刻就绪的副本数不低于期望值。
- `minReadySeconds`：避免“刚就绪就崩”的 Pod 被当成可用。设计只说“给几秒”，具体值以 chart 为准。
- PDB（`maxUnavailable: 1`）：限制**自愿中断**（驱逐，比如节点维护）时同时不可用的数量。设计 13 的盲区一条写明：直接删 Pod 不经过 PDB，只有驱逐才受它约束。
- **（通用知识）** PDB 的 `maxUnavailable` 要算出“应该有几个 Pod”，是经控制器的 scale 子资源；选中了一个没有 scale 子资源的负载（例如 Job 的 Pod）会怎样，见 2b 笔记里的条目，这里不展开。

### 5.2 新旧版本共存的要求

滚动期间新旧版本同时在线，所以 proto 和消息格式要向后兼容；数据库迁移必须是新旧代码都能跑的（先加列、后用列）。设计 8.2 说明：2c 不涉及表结构变更，只把这条写进笔记。

### 5.3 验证零报错（验收项）

**负载**：`scripts/cluster/probe.py`，约 90 请求/秒，记下每一个不该出现的响应和时刻。基线 20 秒 0 失败。

**怎么做的**：带着负载 `make deploy` 换一个新 tag（内容相同），六个服务全部滚一遍，约 1 分 46 秒。做了三次（设计 13 第四步）：

- 第一次 49 个失败，全部是查库存，全部落在 inventory 滚动的那 16 秒里。原因是上面对照实验留下的：被替换掉的旧 Pod 还带着 `DRAIN_DELAY=0`。其余五个服务（包括 gateway 自己）这一次 0 失败。
- 第二次（干净的状态）15000 个请求 0 失败。
- 第三次（改资源 requests 引起的滚动）13500 个请求 0 失败。

阶段计划里写的是“整体滚动两次共 28500 个请求 0 失败”，即第二、三次之和。避开节点后又带负载滚了一遍，13600 个请求 0 失败（见 6.4）。

**没有覆盖到的**（如实说）：支付的同步调用（探针不发 `pay`）；只有约 90 请求/秒，不是压测；强制删除和在节点上直接杀进程两种没有在这轮做（强删在 9.5 的一致性测试里做了）。

**教训**（设计 13）：第一次的 49 个失败是自己的实验污染。对照实验改过的配置要先恢复并等它生效，再做下一个实验；“恢复”和“下一个实验”合成一步时，被换掉的是带着旧配置的那一批。见第 10 节。

### 5.4 把副本数从 1 改成 2 会触发一次滚动

设计 13 末尾记的小事：分布约束只在副本数大于 1 时才渲染，Pod 模板因此变了，所以改副本数会触发滚动，而不只是多起一个 Pod。

## 6. 配置、资源和调度

### 6.1 环境变量形式的配置为什么改了 ConfigMap 不生效

**答**（设计 7.2）：环境变量只在进程启动时读，改了 ConfigMap 不会自己生效。服务的配置入口本来就是环境变量（经 `envFrom` 整个注入），所以不用改代码。解法是 Pod 模板上加一个 ConfigMap 内容的校验和注解，内容一变模板就变，`helm upgrade` 触发滚动更新。这是有意的：配置变更和发版走同一条有摘流、有就绪检查的路径。运行中要改的东西不走这条路，降级开关走管理端口。

**（通用知识）** ConfigMap 挂成文件时，kubelet 会定期同步更新（有延迟），`subPath` 挂载的不会更新；注入成环境变量则永远不更新。Secret 默认只是 base64，etcd 里没有开静态加密（设计里引用 2b 的发现 11，这个细节面试前回 2b 核对）。

**密码**（设计 7.2）：Secret 不能跨命名空间引用。MySQL 的密码在 `mysql` 命名空间，部署脚本把服务需要的几个键复制成服务命名空间里的 Secret，DSN 用 Kubernetes 的变量展开拼出，密码不进 ConfigMap 和 values。服务用只对本实例业务库有权限的 `app` 账号，不用 root。

### 6.2 requests、limits 和 QoS

**怎么定的**（设计 7.4）：QoS 是 Burstable（requests 小于 limits，CPU 不设 limits）。和中间件的选择一致：CPU 不设上限，避免被节流造成延迟的长尾；内存设上限，泄漏时杀的是自己。节点内存紧张时业务服务先于中间件被驱逐，因为中间件有 PriorityClass `middleware`，服务用默认优先级。

**（通用知识）为什么 CPU 限流会造成长尾**：CPU limits 在 Linux 里靠 cgroup 的配额实现，每个计量周期内用完配额就被暂停到下个周期，请求恰好撞上暂停就多出几十毫秒。这是通用的机制说明，设计里只写了“避免被节流造成延迟的长尾”，没有在本项目里量过。

**第一次估的数偏高，量过之后改了**（设计 13 第四步）：约 90 请求/秒时每个容器的实际用量：order 43 到 46 Mi，inventory 27 到 31 Mi，gateway 8 到 26 Mi，payment、orderindex、cdc 8 到 12 Mi，每个 Envoy 边车 15 到 18 Mi；CPU 都在 40m 以下。原来估的 requests（128 到 192 Mi，边车 48 Mi）偏高，改成服务 64 Mi（order 96 Mi）、边车 32 Mi，limits 不变。11 个 Pod 的内存 requests 合计从约 1.9 Gi 降到约 1.1 Gi。**这是轻载下的数，阶段 3 压测时再校。**

**连接数的账**（设计 7.4）：order 每个 Pod 对每个订单实例最多 25 个主库连接、25 个从库连接，4 个 Pod 是 100，在 `max_connections` 200 以内。HPA 的上限由这笔账定，不是随手写的。

### 6.3 GOMEMLIMIT 和 GOMAXPROCS

**问**：容器里的 Go 服务为什么要设 `GOMEMLIMIT`？

**答**（设计 7.4）：设成内存 limits 的约 90%，经 Downward API 从 limits 取。不设的话 Go 的垃圾回收不知道容器的上限，堆涨到被 OOM 杀掉之前不会加紧回收。

**GOMAXPROCS**：设计的说法是“没有 CPU limits 时它等于节点的核数，不用管；实现时用 `go doc runtime` 确认当前版本对 cgroup 的 CPU 上限的行为再写进笔记，不凭记忆”。**设计 13 里没有回头记录这次确认的结果，所以我没有写这个行为的结论**：面试前自己用 `go doc runtime` 查一下当前 Go 版本在 cgroup CPU 限额下对默认值的处理，再决定怎么讲。

### 6.4 副本分布：怎么发现 server 节点内存 86%，怎么处理，代价是什么

**发现**（设计 13 第四步）：`kubectl top` 显示 k3s-server 的内存用到 86%（3927 Mi；它一共 6 GB，可分配约 4.4 Gi）。副本数加到 2 之后有五个业务 Pod 被分布约束放到了它上面，和 etcd、Kafka 的一个 broker、Redis 的两个实例在一起。

**决定**（主人，2026-11-15）：避开，因为加内存太贵。chart 加了 `avoidControlPlane`（默认开，节点亲和要求没有 control-plane 标签），同一服务的副本分散从硬约束改成软的（`ScheduleAnyway`）：能放的只剩两个工作节点，滚动时多开的那个 Pod 必然和某个旧 Pod 同节点，硬约束会让滚动卡住。改完带着负载滚了一遍，13600 个请求 0 失败，11 个业务 Pod 都在两个 agent 上。

**两件要如实说的事**：

1. **软约束的代价当场就出现**：这次滚动之后 inventory 的两个副本都在 k3s-agent-1 上，payment 也是。滚动是“先多开一个、再删一个旧的”，调度器每次只按当时的分布打分，删掉哪个旧 Pod 不由它定，结果可以是两个新 Pod 同节点。agent-1 一挂这两个服务就没有副本了，要等重建。**没有处理**。可选做法：装 descheduler 定期纠正；这类服务改成 `maxSurge: 0`、`maxUnavailable: 1`（原地换，不会挤在一起，但滚动时少一个副本的容量）；或者 3 个副本。阶段 4 做关节点实验之前要定。
2. **server 节点的内存并没有因此松下来**：业务 Pod 走了之后它仍是 82%（3712 Mi）。所以 86% 的主要来源不是业务 Pod，而是本来就在上面的 etcd、k3s、Kafka 的一个 broker、两个 Redis。避开只是不再往上加。阶段 3 装监控时，DaemonSet 类组件在它上面的 requests 要算进去。

### 6.5 入口、限流和降级开关的“乘以副本数”（设计 1、7.6）

多副本会让一批原本隐含的单实例假设暴露出来，设计里逐项记了：

- gateway 按 IP 和热点参数的限流是进程内的令牌桶，N 个副本就是 N 倍的限额；按用户加接口的限流在 Redis 里不受影响。2c 不改，写明限额是每个 gateway 副本的；要精确就得挪进 Redis，而 1d 有意把按 IP 的放在进程内（不让攻击流量压到 Redis 上）。HPA 伸缩时实际限额跟着变，记为已知的不精确。
- 降级开关在每个进程自己的内存里，N 个副本要改 N 次，**新起来的副本不知道别人被改过**。2c 提供 `scripts/cluster/degrade.sh` 对每个 Pod 调一遍，缺口留着，阶段 4 再定共同来源（ConfigMap 加监听，或放 Redis）。
- cdc 只能一个实例（见 9.4），所以是 `Recreate` 策略，不用 PDB；它停着时商家索引落后，不丢（位点在 Kafka 里）。
- 周期任务（outbox 中继、sweeper、reaper、闸门对账）靠 Redis 上的 leader 锁，可以多副本；库存增量应用者靠增量行上的行锁互斥；各服务启动时的迁移靠 `GET_LOCK`。这些在设计 1 里逐个核对过。其中迁移有一个“没查到根因的偶发失败”（`TestMigrateConcurrentOnEmptyDB`，CI 上出现过一次），对应“多个副本同时在空库上第一次启动”，设计说要盯着。**设计 13 没有记第一次部署是否触发了它**，不要在面试里说“已确认没问题”。

## 7. HPA

### 7.1 配置

gateway 和 order 打开：2 到 4 个副本，目标是 CPU requests 的 70%，`behavior` 用默认值（设计 9、13 第六步）。payment、inventory、orderindex 不做 HPA：它们的吞吐由消费的分区数和下游数据库决定，加副本不一定加吞吐。按 QPS 的 HPA 挪到了阶段 3a，因为需要 Prometheus 加适配器（或 KEDA）才有自定义指标 API，为它在 2c 装一套、3a 再重装没有意义。

### 7.2 算式，以及它看到的是什么

**算式**（设计 9）：期望副本数 = 当前副本数 × 当前值 ÷ 目标值（向上取整）。

**（通用知识）** 控制器有一个容忍带，当前值和目标值的比例在约 10% 以内不动；具体数值和公式的细节面试前核对官方文档。

**利用率是按 requests 算的**：所以 requests 写错 HPA 就失真（设计 9）。

**按整个 Pod 算**（设计 13 第六步）：服务容器加边车的用量之和，除以两者 requests 之和（gateway 是 200m 加 20m）。压测时边车用了约 60m，是它自己 requests 的三倍，都摊进了这个比例。只想看服务容器要用 `ContainerResource` 类型的指标，没有换：边车的 CPU 也是随流量涨的，算进去不算错。

**为什么 CPU 对 gateway 是个还行的信号，对卡在下游的服务不是**（设计 9）：order 落库慢的时候 CPU 是低的，请求都堵在等待上，HPA 看不见。

### 7.3 压到扩容的实测

`probe.py --workers 120 --rate 3`，从 MacBook 经入口，实际约 810 请求/秒，持续 200 秒（设计 13 第六步）：

| 时刻（从发压算起） | gateway | order |
|---|---|---|
| 0 秒 | 2 个，18% | 2 个，17% |
| 约 55 秒 | 78%，决定扩到 3；5 秒后第 3 个就绪 | 23% |
| 约 100 秒 | 79%，决定扩到 4；5 秒后就绪 | 79%，决定扩到 3；5 秒后就绪 |
| 约 150 秒 | 4 个，79% | 90%，决定扩到 4；5 秒后就绪 |
| 结束时 | 4 个，79% | 4 个，73% 到 87% |

- **指标滞后**：从发压到第一次扩容约 55 秒，几乎全是指标的滞后。HPA 看到的利用率在负载已经到位之后还爬了近一分钟（18%、23%、58%、78%）。Pod 本身从创建到就绪只要约 5 秒（镜像已经在节点上）。
- **为什么分两步而不是一步扩到 4**：按最终的数倒推，这个负载在 2 个副本上的真实利用率约 158%，一步就该要 5 个；但每次做决定时看到的都是还没爬完的数（78% 只够要 3 个，用算式验算：2 × 78 ÷ 70 ≈ 2.2，向上取整是 3）。扩到 4 之后 gateway 仍是 79%，高于目标，被 `maxReplicas` 挡住。
- **新 Pod 确实接到了流量**：结束时 4 个 gateway 容器各 114m 到 122m，4 个 order 容器各 165m 到 178m。gateway 的流量是入口 Envoy 分的，order 的是 gateway 的边车分的，都是按请求均衡。这就是 3.2 说的：换成直连 ClusterIP，老连接不会挪到新 Pod，扩了也白扩。
- **order 的 CPU 涨得比 gateway 晚约 45 秒**，原因**没有查**，可能是 gateway 扩容之前自己是瓶颈、放过去的请求少。
- **这次负载里 429 很多**（查订单 26406 个、下单 5700 个，都是按用户的限额），order 是被“查订单”的读流量推上去的。所以它只是“把 CPU 推上去”的负载，**不是吞吐的测量**，不要拿 810 请求/秒当系统吞吐讲。

### 7.4 去掉 replicas 字段的那一次发布有一个瞬态

**问**：开了 HPA 之后为什么不能在 Deployment 里写 `replicas`？

**答**（设计 13 第六步）：否则每次 `helm upgrade` 都把副本数改回 values 里的数，和 HPA 打架。

**去掉这个字段的那一次部署的瞬态**：字段从清单里消失，API server 给它补默认值 1，Deployment 立刻缩到 1 个（删掉一个 Pod），HPA 在同一秒发现低于 `minReplicas` 又拉回 2 个（事件里是 `Current number of replicas below Spec.MinReplicas`）。order 和 gateway 各有约 5 秒只有 1 个就绪副本。被删的 Pod 走的是正常的摘流，带着负载做的，15400 个请求 0 失败；但如果当时一个副本扛不住流量，这就是一次事故。避开的办法是**先建 HPA、等它接管，再从清单里去掉 `replicas`（两次发布）**。

### 7.5 缩容

停止发压（12:07:22）之后 5 分 07 秒才开始缩（12:12:29），正是默认的 5 分钟稳定窗口；之后 order 和 gateway 各在 15 秒里从 4 回到 2（每 15 秒一步）。缩容期间挂着约 90 请求/秒的探针，28860 个请求 0 失败。

**（通用知识）稳定窗口的作用**：缩容时取窗口内历史建议的最大值，防止指标抖动造成来回伸缩。扩容的默认窗口很短，所以扩容快、缩容慢。具体默认值面试前核对，我们量到的是缩容窗口 5 分钟。

**缩容时看到的一件事**（设计 13 第六步）：order 的两个多出来的 Pod 相隔 15 秒被删。第一个退出时交出的分区（`order.submit` 的 3、`payment.events` 的 2）被分给了**第二个已经在摘流、15 秒后也要退出的 Pod**，于是这两个分区挪了两次（各停 2.4 秒和 1.3 秒）。原因是在摘流的 Pod 仍然是消费组里的正常成员，协调者不知道它要走。**没有处理**：代价只是多一次一两秒的停顿；要避免得让进程在收到 SIGTERM 时先离组，那样摘流的 15 秒里它就不消费了。

### 7.6 扩容瞬间的 14 个 503：新 Pod 的冷连接池，没有修

**现象**（设计 13 第六步）：扩容时出现了 14 个失败的请求，都是查订单返回 `503 STOCK_GATE_UNAVAILABLE`，落在 order 的第 3 个 Pod 就绪之后的 20 秒里（前 5 个在它就绪的同一秒）；第 4 个 Pod 就绪时没有出现。

**推断**（设计里明确标了只有时间上的吻合，没有直接证据）：新 Pod 一就绪就按轮询拿到四分之一到三分之一的流量（约 200 请求/秒），它到闸门 Redis 的连接池是空的，建连接加上读闸门的 300 毫秒时限，一批请求超时后按降级答复。这和 1b 里“冷连接池遇上突发流量”是同一类问题。

**可选的修法**（设计 13）：就绪之前把连接池预热到一个下限（go-redis 的 `MinIdleConns`）；或者在调用方边车的集群上开 Envoy 的慢启动，让新端点的权重在一个窗口里从低升到满。滚动发布没有暴露它，是因为那时只有约 90 请求/秒。**阶段 3 压测之前要处理，现在没修。**

**两种修法各解决什么**：预热解决的是“这个进程自己的冷资源”（连接池、缓存），在就绪之前把它们准备好；慢启动解决的是“流量一下子压过来”，由上游代理控制新端点的权重爬坡，对进程自己没有要求。两者可以叠加。（这句对比是我按两种机制的作用点归纳的，设计只列了两个选项。）

### 7.7 压测里顺带看到的

order 的新 Pod 打过 `replica lags behind, reading primary`（订单库 0 的从库落后超过 1 秒，读退回主库）：读己之写的降级在集群上第一次被真实的负载触发，行为符合设计，落后了多久**没有量**。

**面试时怎么讲 HPA（一分钟版）**：算式、按 requests、按整个 Pod；实测从发压到第一次扩容 55 秒，几乎全是指标滞后，Pod 本身 5 秒就绪；因为每次决定看到的是没爬完的数，所以分两步扩到 4；开 HPA 要去掉 `replicas`，去的那一次会瞬间缩到 1 再被拉回，要分两次发布；扩容暴露了新 Pod 冷连接池的 14 个 503，我有推断没有证据，修法有两条。

## 8. Kafka 消费者在滚动发布时停多久

### 8.1 先量现状

**怎么量**（设计 13 第七步前一半）：带着约 90 请求/秒的负载 `kubectl rollout restart deploy/payment`（2 个副本，`order.events` 4 个分区，每个成员 2 个），把新旧四个 Pod 的 `kafka partitions revoked`、`assigned` 两种日志按时间排在一起：

| 时刻 | 发生了什么 | 这个分区没有人消费的时间 |
|---|---|---|
| 12:09:13.66 | 新 Pod 加入，旧 Pod 交出分区 2；12:09:14.17 新 Pod 拿到 | 0.5 秒 |
| 12:09:24.67 | 第二个新 Pod 加入，另一个旧 Pod 交出分区 3 | 0.5 秒 |
| 12:09:33.03 | 第一个旧 Pod 摘流 15 秒后退出，交出分区 1；12:09:35.69 被接走 | 2.7 秒 |
| 12:09:43.04 | 第二个旧 Pod 退出，交出分区 0；12:09:46.20 被接走 | 3.2 秒 |

每个分区在一次滚动里只挪一次，停 0.5 到 3.2 秒；没有任何一个分区等会话超时（10 秒）。期间 9500 个请求 0 失败。旧 Pod 在 `DRAIN_DELAY` 的 15 秒里一直在消费，分区是进程真正退出时才交出去的。

### 8.2 两种停顿的来源不同

- **新成员加入：0.5 秒。** 增量再平衡（franz-go 默认的 cooperative-sticky）：只有要挪的那个分区被收回、下一轮分出去，其余分区一直在消费。
- **旧成员退出：2.7 到 3.2 秒。** 旧成员退出时主动发了离组请求，协调者马上开始再平衡，但**剩下的成员要到下一次心跳才知道**；心跳间隔是会话超时的三分之一，即 3.3 秒，所以停顿是 0 到 3.3 秒之间的一个数（量到 2.7 和 3.2）。想再压低，调的是心跳间隔，不是静态成员。

**（通用知识）** 心跳间隔取会话超时的三分之一是 Kafka 消费者配置的常见建议值，这里设计文档用它解释量到的数，没有单独量过心跳间隔本身。会话超时 10 秒是设计 12 和 1b 里的现值。

### 8.3 静态成员为什么在这里帮倒忙

**设想**（设计 12）：用 `group.instance.id`（取 Pod 名）让重启的实例直接接回原来的分区。

**结论：不做**（设计 13 第七步，ADR-0007 补充）：读了 franz-go v1.22.3 的 `InstanceID` 文档和 `consumer_group.go` 里的 `leave`：设了实例号之后，关闭时**不发离组请求**（只有一种例外，增量再平衡里刚交出分区还没重新加入就关闭）。Deployment 滚动出来的新 Pod 名字是新的，对 Kafka 来说是另一个成员；旧 Pod 不离组，它的分区要等会话超时才会被分出去，而文档还建议用静态成员时把会话超时调大到够一次重启。也就是把现在的 3 秒变成 10 秒以上。

它帮得上的只有“同一个名字在会话超时之内回来”：容器在同一个 Pod 里崩溃重启（现在要等 10 秒会话过期，1b 的 chaos 里见过），或者 StatefulSet。前者少见，而且省下的几秒要用每次发布多停几秒来换；后者我们不用（2.5）。所以 `kafkax` 不改。**放弃的是**：进程被杀后原地重启时省掉约 10 秒的等待；阶段 4 做“杀进程”实验时，这 10 秒是预期之内的数。

### 8.4 面试怎么讲

按“先量再决定”讲：滚动一次每个分区只挪一次、停 0.5 到 3.2 秒；停顿上限是心跳间隔不是会话超时；静态成员在关闭时不离组，所以滚动反而变慢；它只对“同名成员快速回来”有用。这是一个“评估后决定不做”的好例子，比做了一个没用的优化更有说服力。

## 9. 测试搬上集群

### 9.1 e2e 怎么搬：选了什么，为什么

**问题**（设计 1 第 6 点）：`test/e2e` 不只是访问入口，还会直连 5 个 MySQL 实例读数据做核对；在订单从库上停复制线程；在测试进程里起 OTLP 接收端收链路；直接运行 `archiver` 的可执行文件。所以需要一套单独配置的服务，和一个能连到集群里 MySQL 的测试进程。

**做法**（设计 10.1、13 第五步前一半）：命名空间 `oppenheimer-e2e`，同一个 chart、同样的镜像，values 叠一层 e2e 的覆盖（缩短的时限、库名前缀、每次运行不同的 `KAFKA_PREFIX` 和 `REDIS_PREFIX` 等）。测试是一个 Job，镜像里是 `go test -c -race` 编的测试二进制加 `archiver`，经 `hostAliases` 把 `e2e.oppenheimer.test` 指到入口地址，流量从入口进。`make cluster-e2e`。

**没选的**：“MacBook 上跑加端口转发”：要转发 5 个 MySQL 和入口，`port-forward` 在连接多时不稳，各服务的链路还要能连回 MacBook（地址是 DHCP 的）。

**量到的数**：第一次执行就通过，19 个用例全部通过，从构建镜像到清理完一共 203 秒。

### 9.2 和设计不同的三处（设计 13 第五步前一半）

1. **Job 先于服务启动**，设计写的是反过来。OTLP 接收端在测试进程里，服务先起而接收端不在，导出器按指数退避重连（最长 120 秒），部署要几分钟，测试开始时 span 可能发不出来。于是 `TestMain` 加了可选的 `E2E_WAIT_READY`：先起接收端，再经入口轮询 `/readyz` 连续 3 次成功才开始。这是 `test/e2e` 唯一的改动，本机不设。
2. **cdc 的 server id 必须和长期那一套不同**（e2e 用 1012、1022），见 9.4。
3. **root 密码的用处比设计写的多**（测试直接读写各个 e2e 库、跑 `archiver`），仍然只进 `oppenheimer-e2e` 命名空间。

### 9.3 “从入口进”要打折扣：Pod 访问 LoadBalancer 地址走哪条路

**问**：集群里的 Pod 访问 LoadBalancer 的外部地址，流量走哪？

**答**（设计 13）：Job 在集群里访问 LoadBalancer 的地址时，kube-proxy 在本节点上直接转给入口 Envoy 的 Pod，**不经过 MetalLB 的 ARP 应答**。所以测到的是入口 Envoy 加 HTTPRoute 加后面的全部，不是从集群外进来的那一段；那一段由 `probe.py` 从 MacBook 覆盖。

**（通用知识）为什么**：kube-proxy 会为 LoadBalancer Service 的外部 IP 也建转发规则，让集群内的流量不必绕出集群再回来。这是 Kubernetes 的通用行为，设计只记了现象；具体机制（iptables 或 IPVS 下的规则）面试前核对。

### 9.4 两个 CDC 实例读同一个 MySQL 为什么 server id 必须不同

**答**（设计 1、13）：cdc 每条流水线用一个固定的 `server-id` 伪装成从库来读 binlog。两个实例用同一个 `server-id` 连同一个源，MySQL 会把先连上的那个踢掉，两边轮流重连。长期那一套和 e2e 的那一套读的是同一个从库，所以 e2e 用不同的 id（1012、1022）。设计 1 因此把 cdc 定为“只能有一个实例”：副本数不能随便加。设计 13 里写这是“设计漏了”的一项，发现的方式是子 Agent 读代码后提出。

### 9.5 一致性测试：删 Pod，判定标准是数据对得上

**做法**（设计 10.2、13 第五步后一半）：`make cluster-chaos`。发压的 Pod 常驻，压测期间每 5 秒随机删一个业务 Pod（名单是 gateway、order、inventory、payment，各 2 个副本），结束后等 Deployment 恢复，再 `wait-quiet`、`recon`（`payment,stock,replica,index` 四对）、`verify`（22 项里除归档外都查，商家索引那一项本机跳过、这里真查）。

**判定标准是数据一致，不是零报错**；另外要求没有意外的容器重启。理由：这个测试要证明的是“故障下数据不丢不重不错”，客户端看到几个 5xx 是可接受的，只要重试后数据一致。

| 运行 | 删了几个 Pod | 受理订单 | 客户端 5xx | verify、recon | 结果 |
|---|---|---|---|---|---|
| 60 秒，正常优雅期 | 11 | 372 | 0 | 通过 | 数据通过；脚本判失败（脚本 bug） |
| 120 秒，正常优雅期 | 22 | 342 | 0 | 通过 | 数据通过；一个 inventory 容器启动时重启过一次 |
| 120 秒，正常优雅期 | 23 | 392 | 0 | 通过 | PASS |
| 120 秒，`CHAOS_FORCE=1`（宽限期 0，相当于 `kill -9`） | 22 | 452 | 29（下单 15、支付 14） | 通过 | PASS |

四次的数据都对得上：受理的订单全部在库里，没有超卖（三个 SKU 各 60 件都恰好卖完），没有进死信的消息，闸门没有做过修正，商家索引和订单表一致，主从一致。

**正常删除和强制删除的差别来自哪里**：正常删除时客户端一个 5xx 都没有看到，强制删除时有 29 个。这又是一次对照，说明零报错是摘流（`DRAIN_DELAY`）换来的。强删时在途的请求被重置，靠客户端带幂等键重试，数据仍然一致。强删那一次落库延迟的 p99 从约 0.7 秒变成 4.7 秒（消费者没有离组，分区要等会话超时）。

**盲区（如实说）**（设计 13）：入口 Envoy、cdc、MySQL、Kafka、Redis 不在名单里；删 Pod 不经过 PDB；负载只有十几单每秒，库存 60 件很快卖完，之后主要是被拒绝的请求；被强删的 inventory Pod 的最后几行日志可能收不到，会让 verify 第 19 项漏看一次闸门修正；脚本被 `kill -9` 时命名空间留着 `running` 标签，要手工 `services.sh e2e-down`。完整的故障实验是阶段 4。

**一次没有解释的重启**（设计 13）：第二次运行里一个 inventory 容器在启动阶段重启过一次，那时用的已经是修过的镜像。脚本收上一个容器日志的写法有 bug（`--all-containers --previous` 在边车没重启过时整条命令报错），日志没有留下；写法已改，之后两次没有再出现。**原因没有查清**，面试时不要说成“已修”。

### 9.6 新建 Kafka topic“建成功了却查不到”：这个测试查出的真缺陷

**现象**（设计 13 第五步后一半）：第一次运行里 order 和 orderindex 各有一个容器在启动时退出、被 kubelet 重启，日志是 `kafkax: dlq topic ... UNKNOWN_TOPIC_OR_PARTITION`。

**原因**：`EnsureTopics` 建完 topic 之后等的是“它问的那个 broker 看得见”，而消费者是另一个客户端，启动时查死信 topic 可能问到另一个元数据还没更新的 broker。本机和 CI 都只有一个 broker，永远不会出现；集群上是三个。

**修法**（`pkg/kafkax`，Fable 改）：`checkDLQTopics` 查不到时最多等 10 秒再下结论。

**教训**：和 2a 里“两个 DNS 上游一好一坏”是同一个教训：有多个副本时，一次检查通过只说明被问到的那一个是好的。设计推测之前的 `make deploy` 和 `make cluster-e2e` 很可能也发生过，只是没有人看重启次数（e2e 脚本不查）。

**（通用知识）** Kafka 里每个 broker 各自缓存集群元数据，更新是异步传播的，因此创建 topic 后不同 broker 在短时间内对它的可见性可能不一致。这是 Kafka 的通用行为，面试前对照官方文档核对。

### 9.7 e2e 的隔离和隔离不了的（设计 13）

隔离的：库名、topic 和消费组、cdc 的位点（在带前缀的 topic 里）、节点号的租约表和迁移锁（跟着库）、Redis 的键。**隔离不了的**：共用从库的复制线程会被停几秒（主从延迟用例会真的停订单从库的复制线程，长期那套的展示读会退回主库、cdc 落后）；两套写进同一个 `gtid_executed`；MySQL 连接数；`redis-cache` 是 LRU，e2e 的键会挤掉一些缓存；节点内存。清理按前缀删，不分运行号，所以同一时刻只能有一次 e2e 在跑（chaos 和 e2e 共用命名空间，靠命名空间上的标签互斥，运行中再启动退出码 3）。

`gtid` 读模式在集群上第一次跑（长期那套是默认的 `primary`），三个主从延迟用例都过了。

**留下的**（设计 13）：cdc 的源写死的是 `mysql-order-N-1` 这个 Pod，主从延迟用例停的是 `-replica` Service 选中的 Pod，现在是同一个，主从切换之后两处要一起改；Job 拉不到镜像时脚本要等到 Job 的时限（40 分钟）才失败；限流用例对时间敏感，这次过了，没有量余量；冷缓存下的镜像构建耗时没有量；没有进 CI（CI 里没有集群）。

## 10. 做对照实验的方法

阶段计划把这条单独列为考点：**没有“去掉保护就失败”的对照，零失败说明不了保护起了作用；对照改过的配置要先恢复干净。** 2c 里做成对照的有三组：

| 保护 | 去掉保护 | 观察到的差别 |
|---|---|---|
| `DRAIN_DELAY` 15 秒 | `DRAIN_DELAY=0` | 每删一个 Pod 失败 15、16 个，集中在约 1 秒；有保护时 2 万多个请求 0 失败（4.3） |
| 边车按请求均衡 | 直连 ClusterIP | 770/770 对 1380/160；删满载 Pod 时 20 个失败（3.4） |
| 正常的优雅期 | `CHAOS_FORCE=1` 强删 | 0 个 5xx 对 29 个；落库 p99 从约 0.7 秒到 4.7 秒（9.5） |

**污染实验的教训**：5.3 里滚动发布第一次的 49 个失败，原因是上一个对照实验给 inventory 留下了 `DRAIN_DELAY=0`，被滚动换掉的旧 Pod 还带着它。结论是改配置的对照做完后，必须先恢复、等到全部 Pod 都换成恢复后的配置，再开始下一个实验。

**面试时怎么讲**：不要只报“我们测了零报错”。讲成“零报错有对照：把摘流关掉就稳定出现 15 个左右的失败，所以我知道零报错是它换来的；边车的异常摘除是第二层，解释了为什么关掉之后失败只出现 1 秒”。

## 12. 速记：每条考点一句话

- **节点号**：多副本下 Pod 的环境变量相同，节点号会撞；用 MySQL 里 64 行的租约表，给每一任持有者划互不重叠的毫秒区间，上界经数据库确认才用，租期只影响可用性。
- **为什么不用 StatefulSet**：节点失联时它不会在别处重建，滚动只能原地换。
- **摘流**：SIGTERM 和摘端点同时开始，进程先变未就绪、继续服务 `DRAIN_DELAY`；量到端点传播 2 到 9.5 秒，定 15 秒；对照 `DRAIN_DELAY=0` 每次失败 15 个左右。
- **原生 sidecar**：启动时边车先就绪，停止时服务全退出后才停边车。
- **gRPC 均衡**：连接级对请求级；直连 ClusterIP 是 1380 对 160，经边车是 770 对 770。
- **滚动发布**：`maxSurge: 1`、`maxUnavailable: 0`；六个服务滚一遍 1 分 46 秒，干净状态下 15000 个请求 0 失败。
- **配置**：环境变量改了不生效，用校验和注解触发滚动。
- **资源**：Burstable，CPU 不设 limits，内存设 limits，`GOMEMLIMIT` 设成约 90%；轻载实测后 requests 从 1.9 Gi 降到 1.1 Gi。
- **镜像**：多阶段、交叉编译、`CGO_ENABLED=0`、distroless nonroot、tag 用提交号；`-race` 要 cgo 所以测试镜像用 base 带 glibc。
- **HPA**：算式、按 requests、按整个 Pod；55 秒才第一次扩容是指标滞后；分两步扩到 4；去掉 `replicas` 要分两次发布；扩容暴露 14 个 503，推断是冷连接池。
- **Kafka**：滚动时每个分区停 0.5 到 3.2 秒；静态成员关闭时不离组，滚动反而更慢，不做。
- **e2e**：搬成集群里的 Job，Job 先于服务起；cdc server id 必须不同；经入口的流量在集群内不经 MetalLB。
- **一致性测试**：判定是数据对得上；正常删 0 个 5xx，强删 29 个；查出 `kafkax` 启动时查死信 topic 的缺陷，三个 broker 才出现。
