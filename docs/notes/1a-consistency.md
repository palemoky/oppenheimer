# 1a 笔记：没有 Redis 和 Kafka 时怎么把下单做对

这份笔记整理 1a 里值得在面试中讲的点。每一条都对应仓库里能运行的代码和测试，讲的时候可以落到具体实现上。设计全文见 [design/1a-order-flow.md](../design/1a-order-flow.md)。

## 1. 防超卖

**问题**：库存 10 件，100 个人同时下单，怎么保证只卖出 10 件。

**做法**：一条条件更新。

```sql
UPDATE sku_stock SET available = available - ?, reserved = reserved + ?
WHERE sku_id = ? AND available >= ?
```

判断和扣减在同一条语句里，InnoDB 的行锁保证它原子执行。受影响 1 行就是扣到了，0 行就是不够。

**对比**

| 方案 | 做法 | 问题 |
|---|---|---|
| 先查后改 | `SELECT` 看够不够，再 `UPDATE` | 两步之间别人可以插进来，一定超卖 |
| 悲观锁 | `SELECT ... FOR UPDATE` 再 `UPDATE` | 正确，但多一次往返，持锁时间更长 |
| 乐观锁 | 带 `version` 更新，失败重试 | 正确，但高并发下大量重试，热点商品几乎都在空转 |
| 条件更新 | 上面那条语句 | 一次往返，无重试 |

表上还加了 `CHECK (available >= 0)`，代码写错时数据库会拒绝，而不是悄悄写出负库存。

**验证**：`TestFlashSaleNeverOversells` 用 300 个并发请求抢 20 件库存，断言成交数恰好是 20。

**追问：这样就够了吗？** 正确性够了，性能不够。所有请求都打到同一行上排队等行锁，热点商品的吞吐上限就是这一行的更新速度。这是 1b 引入 Redis 预扣的原因。

## 2. 库存为什么分成三个量

`available`（可售）、`reserved`（已下单未支付）、`sold`（已售）。

只用一个数的话，下单就扣会导致“下了单不付钱”把库存占死且无法区分；支付才扣又会导致很多人下单成功、付款时才发现没货。预占把“占住”和“卖出”分成两步，中间可以回退。三者之和恒等于入库总量，这个恒等式是对账和测试的抓手：每个测试结束时都断言它。

## 3. 幂等

三种不同的实现，对应三种场景。

**下单接口：客户端幂等键加唯一索引。** `(user_id, idempotency_key)` 上建唯一索引。重复请求插入时撞上唯一键，读出已有订单返回。同时存了请求内容的哈希：同一个键配上不同的内容说明客户端有 bug，返回错误而不是把旧订单当成新请求的结果。

**库存操作：业务主键作幂等键。** Reserve、Confirm、Release 都以 `order_id` 幂等，`reservation` 表每个订单一行，记录当前状态。重复调用时看到状态已经是目标状态，直接返回成功。

**支付回调：去重表。** `payment_results` 以 `payment_id` 为主键，记下处理结果。重复回调直接返回当时的答复。

**共同点**：幂等记录和业务变更在同一个本地事务里提交。分开的话，“业务做了但幂等记录没写上”会导致重复执行。

**追问：为什么不用 Redis 做幂等？** Redis 里的标记和数据库里的业务数据不在一个事务里，总有一个先写。先写标记后写业务，业务失败了标记还在，重试被误判为重复；反过来则可能执行两次。放在同一个库里用同一个事务，这个问题不存在。

## 4. 状态机

所有状态转换都是带前置状态的条件更新：

```sql
UPDATE orders SET status = PAID WHERE order_id = ? AND status = PENDING_PAYMENT
```

**为什么不能先查状态再更新**：和超卖是同一个问题。两个互斥的操作（支付成功、超时关单）都先查到“待支付”，然后各自更新，订单就既被支付又被关闭。条件更新让数据库来裁决谁赢。

**支付与关单撞车**：这是真实系统里一定会发生的事。用户在第 14 分 59 秒付款，关单任务在第 15 分钟触发。两者只有一个能成功。关单赢了的话，钱已经付了但订单不能要，所以订单服务明确答复支付方 `REFUND_REQUIRED`，支付方据此退款。`TestPayRacingCancelEndsConsistent` 让 40 个订单的支付和取消同时发生，断言每个订单的最终状态自洽：要么已支付且库存已售，要么已取消、库存归还且钱已退。

## 5. 没有分布式事务，跨服务怎么保持一致

下单要改订单库和库存库，没有一个事务能同时罩住两边。

**做法**：先在本地事务里完成自己的状态转换，再调用下游；下游接口全部幂等；调用失败的由后台任务重试到成功。

具体到订单：`orders.stock_settled` 标记“库存是否已跟上订单的终态”。订单变成已支付时这个标记是 0，然后调用库存的 Confirm，成功后置 1。调用失败或进程崩溃都没关系，后台任务会扫出标记为 0 的终态订单再调一次。

这实际上是一个手写的、用轮询驱动的 Saga。1b 会把轮询换成 outbox 加 Kafka。

**为什么不用 2PC 或 XA**：协调者单点、同步阻塞、参与者在准备阶段持锁等待。任何一方变慢，所有参与者都被拖住。互联网业务普遍接受最终一致来换可用性。

**为什么先落订单再占库存**：反过来的话，占完库存进程崩溃，库存里就有一份没有任何订单对应的预占，没人知道该不该释放。先落订单，则库存里的每一份预占都能找到一条订单记录，后台任务总能对它做出处理。

## 6. 空回滚与悬挂

订单服务调用 Reserve 超时了。预占到底成功没有？不知道。只能调 Release 兜底。

问题在于 Release 可能比那个还在网络上的 Reserve 先到：

1. Reserve 发出，在网络上卡住
2. 订单服务超时，发 Release
3. Release 到达，库存服务发现没有这个订单的预占
4. Reserve 终于到达，占住了库存
5. 没有人会再来释放它

这叫**悬挂**。解决办法是第 3 步不能什么都不做：Release 对不存在的预占要插入一条“已释放”的记录（**空回滚**），第 4 步的 Reserve 看到这条记录就拒绝。

这是 TCC 模式的经典问题，面试常问。`TestCreateOrderLateReserveAfterTimeout` 和 inventory 里“Release 先于 Reserve”的测试覆盖了它。

## 7. 这个阶段踩过的两个坑

两个都是设计评审没看出来、测试才暴露的问题，也是最值得讲的部分。

### 唯一键冲突后的锁升级死锁

最初 Release 的写法是：先 `INSERT`，撞上唯一键说明记录已存在，再 `SELECT ... FOR UPDATE` 读状态。

并发测试里稳定死锁。原因是 InnoDB 在 `INSERT` 遇到唯一键冲突时，会给已有的那条记录加**共享锁**。两个并发的 Release 都拿到了共享锁，然后都要通过 `FOR UPDATE` 升级为排他锁，都在等对方释放共享锁。

修正：改用 `INSERT ... ON DUPLICATE KEY UPDATE status = status`，冲突时直接加排他锁，并发请求在这里排队。

还剩一种应用层排除不掉的死锁：多个重复的 Reserve 排队等第一个，第一个回滚后，等待者继承了同一个间隙锁又都要插入。所以加了事务级的死锁重试。测试里把重试次数设为 1 来证明其他场景本身不会死锁，而不是靠重试掩盖。

**可以展开的知识**：InnoDB 的锁类型（记录锁、间隙锁、临键锁、插入意向锁），`SHOW ENGINE INNODB STATUS` 里死锁日志怎么读，为什么可重复读比读已提交更容易死锁。

### “这次没占到”不等于“这个订单没占”

最初的设计：Reserve 返回库存不足时，订单直接标为“失败且库存已结清”，因为“库存一定没被占用”。

子 Agent 实现时指出这个推理有漏洞：

1. 客户端重试，同一订单有 A、B 两次推进在并发进行
2. A 的 Reserve 返回库存不足
3. 别的订单取消了，库存被释放出来
4. B 的 Reserve 成功
5. A 抢先把订单标为“失败且已结清”
6. B 占住的库存没有人会释放

修正：拒绝时把订单标为未结清，并调用一次 Release。有预占就释放，没有就留下标记。多一次幂等调用，换来结论不依赖两次推进的先后顺序。

**教训**：“下游告诉我失败了”只说明这一次调用的结果，不能推出下游的状态。在有重试和并发的系统里，要让补偿动作无条件执行且幂等，而不是根据推理跳过它。

## 8. 加锁顺序

订单 A 买 (SKU 1, SKU 2)，订单 B 买 (SKU 2, SKU 1)。A 锁住 1 等 2，B 锁住 2 等 1，死锁。

解决：所有事务都按 `sku_id` 升序加锁。只要全局顺序一致，就不可能形成环。

`pkg/mysqlx` 的测试里有一个故意制造这种死锁的用例，验证能正确识别 MySQL 的死锁错误码（1213）。

## 9. 分布式 ID 与分片基因

订单号是雪花算法的变体，63 位：

| 41 位时间戳 | 6 位节点号 | 10 位序号 | 6 位基因 |
|---|---|---|---|

基因是 `user_id` 的低 6 位，放在订单号的最低位。于是 `order_id % N == user_id % N` 对任何不超过 64 的 2 的幂 N 成立。

**用处**：1c 分库分表时按 `user_id` 分片。按用户查订单自然能定位分片；有了基因，只拿着订单号也能算出分片，不需要额外的映射表。

**时钟回拨**：回拨 5 毫秒以内原地等待，超过则拒绝发号。继续发号可能与回拨前发出的 ID 重复，宁可短暂不可用也不能重复。

**追问：时间戳在高位有什么好处？** ID 随时间递增，作为主键插入时总是追加在 B+ 树的末尾，不会引起页分裂。UUID 做主键的问题正好相反。

## 10. 其他可以提的细节

- **金额用整数分**：浮点数不能精确表示 0.1，累加会出误差。乘法和求和都检查了溢出。
- **订单号在 JSON 里是字符串**：JavaScript 的数字是双精度浮点，只能精确表示到 2^53，订单号超过这个范围，用数字传会丢精度。
- **事务里不发 RPC**：事务持有行锁，RPC 慢了锁就一直占着。所有跨服务调用都在事务提交之后。
- **内部错误不外泄**：gRPC 拦截器把非业务错误统一转成不带细节的 `Internal`，SQL 和堆栈只进日志。
- **业务拒绝不是故障**：库存不足是正常的业务结果，日志打 info 而不是 error，否则秒杀时告警会被刷爆。
- **优雅停止**：收到 SIGTERM 后不取消在途请求的 context，而是停止接新请求、等在途的做完，超过时限才强制中断。
- **后台任务可以多副本同时跑**：所有转换都是条件更新，所有下游调用都幂等，重复执行只是多做无用功，不会出错。

## 1a 的已知限制

- 热点商品的所有请求在同一行上排队，吞吐有限（1b 解决）。
- 后台任务靠轮询，延迟取决于扫描间隔，且每次都要查库（1b 用消息驱动）。
- 支付失败后同一订单不能再次发起支付。
- 支付单的重试退避依赖 `updated_at`，数据量大时索引用不上。
- 订单的补结清扫描在数据量大时需要更合适的索引。
