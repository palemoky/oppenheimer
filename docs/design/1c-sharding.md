# 1c 设计：分库分表与主从

本文是阶段 1c 的实现规格。1b 之后，订单数据仍在一个库的一张表里。1c 先把订单分到多个库、多张表上，再在此之上做主从、非分片键查询、扩容和冷热归档。

分片键和基因法的大方向见 ADR-0002，具体布局见 ADR-0012。

## 1. 分五步走

每一步结束时系统都能运行，`make lint test e2e` 通过。

| 步骤 | 内容 | 对外行为 |
|---|---|---|
| 一 | 分片：`pkg/sharding`、订单表拆成 2 库 × 4 表、order 服务按分片读写 | 不变 |
| 二 | 主从：每个分片一主一从（GTID 复制），读写分离和读己之写 | 不变 |
| 三 | 非分片键查询：Go 实现的 binlog CDC，同步到按商家分片的索引表 | 新增商家维度查询 |
| 四 | 跨分片查询的取舍、造数工具、扩容演练 | 可能新增按用户分页列表 |
| 五 | 冷热分离与归档 | 冷订单仍可查 |

步骤二的设计在第 3 节，步骤三在第 4 节，步骤四在第 5 节。步骤五在第 6 节。

**范围**：只拆 order 服务的数据。inventory 的数据量与 SKU 数相关，不随订单增长；payment 的数据量与订单同阶，但 1c 的学习目标在 order 上都能覆盖，payment 保持单库（理由写进 ADR-0012）。

## 2. 步骤一：分片

### 2.1 布局

- **逻辑分片（slot）8 个**，编号 0 到 7。`slot = user_id & 7`。
- **物理库 2 个**：`order_db_0`、`order_db_1`。`db = slot % 2`，即库 0 放 slot 0、2、4、6，库 1 放 slot 1、3、5、7。
- **每个 slot 一组表**，表名带全局 slot 号：`orders_3`、`order_items_3`、`payment_results_3`。
- **每个库一张 `outbox`**，不按 slot 拆。

几个选择的理由：

1. **为什么按 slot 而不是按“库号 + 库内表号”命名**。表名全局唯一，扩容时一个 slot 的表可以原样从一个库搬到另一个库，不用改名，也不用重新计算行落在哪张表。路由逻辑只认 slot，slot 在哪个库是一张映射。
2. **为什么 `db = slot % 2` 而不是 `slot / 4`**。成倍扩容（2 库变 4 库）时，取模映射下 slot `s` 从 `s % 2` 号库搬到 `s % 4` 号库：旧库 0 的一半 slot（2、6）去新库 2，另一半留下，旧库 1 同理。每个旧库只拆给一个新库，库的编号不变。区间映射（`slot / 4`）下扩容要给旧库重新编号。
3. **为什么 8 个 slot 而基因有 6 位**。基因 6 位最多支持 64 个 slot。现在用 8 个，以后表太大还可以把 slot 数翻倍：`orders_k` 里 `user_id & 15` 为 `k + 8` 的行拆到新表 `orders_{k+8}`，其他行不动。所以 slot 数、库数都必须是 2 的幂，且库数不超过 slot 数，`pkg/sharding` 在构造时校验。
4. **为什么 `payment_results` 也按 slot 拆**。它只在“锁住订单行”的事务里读写（1a 的支付结果处理），必须和订单在同一个库。按库建一张也能满足这一点，但搬 slot 时就要从一张表里挑出属于这个 slot 的行，按 slot 拆则整表搬走。
5. **为什么 `outbox` 按库建**。outbox 的作用是“和业务写同一个本地事务”，它只需要和业务表在同一个库。它的行是短暂的（发布后保留 1 小时），扩容搬 slot 时不需要搬它，只要先把旧库的 outbox 发完。

### 2.2 路由：`pkg/sharding`

纯计算，不碰数据库：

```go
type Config struct {
    Slots int // 逻辑分片数，2 的幂，不超过 64
    DBs   int // 物理库数，2 的幂，不超过 Slots
}

type Router struct{ /* ... */ }

func New(cfg Config) (*Router, error)
func (r *Router) Slots() int
func (r *Router) DBs() int
func (r *Router) ForUser(userID int64) int   // 返回 slot
func (r *Router) ForOrder(orderID int64) int // 返回 slot，依据 idgen.Gene
func (r *Router) DB(slot int) int            // slot 所在的库
func (r *Router) SlotsOf(db int) []int       // 库里有哪些 slot，升序
func Table(base string, slot int) string     // Table("orders", 3) == "orders_3"
```

`ForOrder(id) == ForUser(user)` 对 idgen 生成的订单号恒成立，这是基因法的全部意义。订单号来自外部输入（HTTP 路径参数、Kafka 消息）时，按它算出的 slot 里查不到就是不存在，不用再去别的分片找。

映射暂时只有取模这一种规则，扩容演练（步骤四）需要“部分 slot 已搬走”的中间状态时再改成显式映射表。

### 2.3 表结构与迁移

订单服务的迁移文件改为模板：`migrations/*.sql` 里用 `{{range .Slots}}...{{end}}` 为本库的每个 slot 生成一组表。`mysqlx` 增加一个按模板渲染后再交给 goose 的入口：

```go
// MigrateTemplate 把 fsys 中 dir 下的迁移文件当作 text/template 渲染（数据为 data），再应用到最新版本。
func MigrateTemplate(ctx context.Context, db *sql.DB, fsys fs.FS, dir string, data any) error
```

渲染结果放进内存里的 `fs.FS` 交给 goose，版本号仍按文件名，每个库各自记录。模板数据是 `struct{ Slots []int }`，由 `Router.SlotsOf(db)` 给出。

**迁移历史压缩成一个文件**。原来的 `00001_init.sql`、`00002_outbox.sql` 作用于 `order_db.orders`，新布局下的库名、表名都变了，没有可以原地升级的旧库。新的 `00001_init.sql` 直接建出 1b 结束时的结构（没有 `stock_settled`，有 `outbox`）。旧的 `order_db` 不再使用，本机数据可以丢弃。

迁移只建本库的 slot。扩容时新库要接收的 slot 的表由迁移工具建（步骤四），不由启动迁移建：启动迁移改变不了“一个 slot 只在一个库里”这个约束。

### 2.4 order 服务

**连接**：`MYSQL_DSNS` 取代 `MYSQL_DSN`，逗号分隔，第 i 个是 `order_db_i`。个数必须等于库数，否则启动失败。slot 数和库数暂时写成常量（8 和 2），不开放配置：配置错了数据就找不到了，改它是一次迁移，不是一次重启。

**store**：`store.Store` 持有 `[]*sql.DB` 和 `*sharding.Router`。

- 按订单号的方法（`GetOrder`、`MarkReserved`）用 `ForOrder` 定位；按用户的方法（`GetOrderByIdempotencyKey`）用 `ForUser`；`InsertOrder` 用订单号定位，并校验订单号的基因和 `user_id` 一致，不一致返回错误（这样的订单写进去之后，按用户和按订单号会找到两个不同的分片）。
- 事务绑定在一个 slot 上：`InTx(ctx, orderID, fn)`。`Tx` 记住自己的 slot，`LockOrder`、`MarkPaid` 等方法只操作这个 slot 的表；传入的订单号不属于这个 slot 时返回错误，而不是悄悄去查别的表。这是“不允许跨分片事务”在代码里的体现。
- `AddOutbox` 写入事务所在库的 `outbox`。
- 后台扫描（`ListExpired`、`ListStaleCreating`）带 slot 参数，每次扫一个 slot。它们是明确豁免的全分片扫描：后台任务本来就要看所有数据，按 slot 逐个扫，不需要合并排序。

**outbox 中继**：每个库一个中继，名字分别是 `order-0`、`order-1`，各有自己的 leader 锁（`order:outbox-relay:0`、`order:outbox-relay:1`）。

- **名字必须不同**。event-id 是 `<中继名>:<outbox 行 id>`，行 id 是各库自己的自增列，两个库都会有 id 为 1 的行。名字相同时两条不同的事件 id 相同，按 event-id 去重的下游会丢掉其中一条。
- **同一订单的事件仍然有序**。同一订单的所有状态变更都在它的 slot 所在的库里，经过同一个中继、同一个消息 key，到 Kafka 的同一个分区。
- 事务提交后只踢事务所在库的中继。`service.Config.Relay` 改为按库号取 `Kicker`。

**sweeper、回收任务**：sweeper 每一轮依次扫所有 slot，每个 slot 各取一批。仍然是一把 leader 锁，一个实例在扫。某个库不可用时跳过它的 slot 并记日志，不影响另一个库。回收任务只看 Redis 闸门，不受影响。

**消费的消息**：落库、支付结果、延迟关单三个消费者的消息里都有订单号，按订单号定位。落库消息里的订单号和 `user_id` 基因不一致时当作毒消息处理（记 ERROR、不重试）：正常路径不会出现，出现说明上游有缺陷。

### 2.5 本机运行与测试

- `make up` 在现有的 MySQL 实例里建 `order_db_0`、`order_db_1`，不再建 `order_db`。两个库在同一个实例上，步骤二再拆到各自的主从。
- `scripts/run-local.sh`、`e2e.sh`、`chaos.sh`、`bench.sh` 改为传 `MYSQL_DSNS`，建库时建两个。
- `test/load` 的 `verify` 和 `wait-quiet` 直接读订单表，改为接受 `-order-dsns`（逗号分隔），用 `pkg/sharding` 遍历所有 slot 汇总。这是对账工具，豁免全分片扫描。
- order 服务的测试辅助函数建两个临时库，跑和生产一样的模板迁移。

**测试重点**：

- `pkg/sharding`：订单号和用户落在同一个 slot（对随机用户号和 idgen 生成的订单号）；`SlotsOf` 的并集覆盖全部 slot 且互不相交；非法配置被拒绝。
- 模板迁移：两个库各自只有自己的 4 组表加一张 `outbox`。
- store：订单写进了按用户算出的那张表，别的表里没有；跨 slot 使用 `Tx` 报错；基因不一致的订单插入失败。
- 分布：一批连续的用户号下单后，8 张表的行数相同。
- 原有的并发测试（支付对关单、重复消息、落库重放）在两个库上照常通过。

### 2.6 实现中发现的问题（步骤一完成后补充）

- **CHECK 约束名在 MySQL 里是库级唯一的**，索引名是表级的。模板里约束名必须带 slot 号（`chk_orders_{{.}}_total`），否则同一个库里第二组表建不出来。扩容时搬表、建表的工具也要遵守这一点。
- **`payment_results` 的主键只在 slot 内唯一**。1a 的防御检查“同一个 `payment_id` 已经记在另一个订单上”，只有两个订单恰好在同一个 slot 时才查得出来。正常情况下 payment 保证一笔支付只对应一个订单号，这条检查本来就只防上游缺陷；分片后它基本失效，`GetPaymentResult` 的注释里写明了。真要全局查，得在 payment 一侧做（它是单库）。
- **落库消息的基因检查比 store 更严**：消费者要求完整的 6 位基因相等，store 的 `InsertOrder` 只比 slot。前者是“上游有缺陷”的信号，后者是“写进去就找不到”的硬约束。毒消息在认领占用之前就被拒绝，占用留给回收任务。
- **event-id 变了**：中继名从 `order` 变为 `order-0`、`order-1`。旧库整体废弃，不影响去重。
- **旧的 `MYSQL_DSN`** 设了就拒绝启动，防止部署配置没跟上时悄悄连到默认的本机库。
- **杀进程测试回收数偏高**：两次 `make chaos` 的“已受理但被回收”是 189 和 78，1b 的几次在 0 到 57 之间。复核结论是与分片无关：旧日志里分片前就有过 180；回收只出现在 order 被杀之后，集中在个别几次击杀上；启动耗时分片前后相同。推断的原因是 `kill -9` 后新实例要等旧成员的消费组会话过期（10 秒）才分到分区，超过了 chaos 设的 5 秒回收宽限期。

### 2.6.1 评审后的修正（2026-11-13）

- **迁移加锁，并写成可重入的**。原来的注释说 goose 用咨询锁，实际没有配置，goose v3.30.0 也没有 MySQL 的会话锁（只有 Postgres 的，和一个要建锁表、带租约的表锁）。`mysqlx` 用 `GET_LOCK` 实现了 goose 的 `SessionLocker`：锁名带库名，两个分库互不阻塞；锁是会话级的，进程被杀时服务端自动释放；等锁最多 60 秒。
  - 锁只防并发，不防中途崩溃。MySQL 的 DDL 隐式提交，分片后一个版本里有 13 条建表语句，进程在中间被杀会留下部分表而版本号没记。所以 `00001_init.sql` 的建表都改成了 `IF NOT EXISTS`，重跑能接着做完。
  - 以后的迁移也要可重入。`ALTER TABLE` 没有 `IF NOT EXISTS`，一个版本里只放一条这样的语句。inventory 的 `00001_init.sql`（3 条建表）和 payment 的 `00002_outbox.sql`（建表后跟一条 `ALTER`）还有同样的问题，没有改。
  - 测试里的教训：“多个实例同时在空库上迁移”去掉锁也能通过，因为 goose 建版本表失败后会等 1 秒重试，恰好把几个实例错开了。能暴露问题的是“版本表已存在、有一个待应用的版本”。
- **连接池按库数分摊**。order 每个库一个池，`MYSQL_MAX_OPEN_CONNS` 是每个库的上限，默认 25。本机所有服务连同一个 MySQL，`max_connections` 默认 151，分片前三个服务各 50 刚好放得下，分片后 order 仍用 50 就是 100，合计 200。步骤二加从库时要重新算一次。
- **sweeper 每个 slot 有自己的时限**（`SlotTimeout`，默认 10 秒）。驱动没有设读超时，一个库连得上但不响应时查询会一直等，原来整轮卡在它上面，另一个库的 slot 也扫不到。
- **分片布局只定义一处**：`sharding.OrderSlots`、`sharding.OrderDBs`。order、对账工具和测试都引用它，对账工具在传入的库数与布局不符时报错。

### 2.7 不在步骤一做的

- 主从和读写分离（步骤二）。
- 按用户的分页列表（步骤四，那时一并讨论跨分片的列表和聚合）。
- 显式 slot 映射表和扩容（步骤四）。
- payment、inventory 分库。

## 3. 步骤二：主从与读写分离

状态：主人已确认（2026-11-13）。决定和备选方案见 ADR-0013。

目标是阶段计划里的验收项：人为制造主从延迟时，用户下单后立刻查询仍能看到订单。

### 3.1 拓扑

- order 的两个库各自搬到独立的 MySQL 实例上，每个实例带一个从库，共 4 个容器：`mysql-order-0`、`mysql-order-0-replica`、`mysql-order-1`、`mysql-order-1-replica`。
- 现有的 `mysql` 容器保留，继续放 inventory、payment 和 `make test` 的临时库。
- 复制用 GTID 加 `SOURCE_AUTO_POSITION = 1`，异步复制。从库开 `super_read_only`。
- 从库的初始化由 `make up` 里的一段幂等脚本完成：在主库建复制账号，在从库执行 `CHANGE REPLICATION SOURCE TO` 和 `START REPLICA`，已经在复制就跳过。
- 迁移只在主库上跑，DDL 靠复制到从库。迁移锁（`GET_LOCK`）也在主库上。

内存是要先解决的问题：现在一个 MySQL 容器占约 860 MB，再加 4 个放不下。order 的 4 个实例要调小（缓冲池、关掉 `performance_schema`），目标每个 300 MB 以内，动工时实测。CI 用同一个 compose 文件，runner 的内存也要先确认。

半同步复制、主库故障后的切换不在这一步做。异步复制下主库宕机可能丢掉已提交的事务，这一点记入考点，故障切换放到阶段 4。

### 3.2 哪些读可以走从库

原则：**用来做决定的读走主库，只用来展示的读可以走从库。** 走从库的读拿到的可能是旧数据，所以它的结果不能成为任何写的前提。

| 读 | 走哪里 | 理由 |
|---|---|---|
| `GetOrder`（对外查询） | 从库，受 3.3 的规则约束 | 只展示。读流量的主体。 |
| sweeper 的两类扫描 | 从库 | 扫描只是找候选，真正的转换是主库上带前置条件的更新。从库旧了只会晚一轮发现，或者多做一次不生效的更新。 |
| `CancelOrder` 之后的复查 | 主库 | 要据此告诉用户取消是否成功。 |
| 落库时订单号重复后的读取、`dropReplay` | 主库 | 写路径上的决定。 |
| 延迟关单消费者读订单 | 主库 | 读到的状态决定是重试还是放弃。 |
| 受理时幂等键重复后的查询 | 主库 | 很少发生，而且用户刚提交过，最容易读到旧数据。 |
| 事务内的所有读 | 主库 | 事务在主库上。 |

`store` 的接口相应地分成两类：现有的方法都读主库；新增 `GetOrderForDisplay`（名字待定）读从库。sweeper 的两个扫描方法改为读从库。这样“哪些读允许旧数据”在方法名上就能看出来，而不是藏在一个路由开关里。

### 3.3 从库旧了会出什么问题

1. **订单凭空消失**。订单落库前，`GetOrder` 靠闸门里的占用合成一个 `CREATING` 的订单。订单走到终态后占用被归还，如果这时从库还没有这一行，`GetOrder` 就查不到，返回 404，而且“不存在”会被缓存 2 秒。这是最严重的一种：订单明明存在。
2. **状态倒退**。取消返回了 `CANCELLED`，紧接着查询看到的还是 `PENDING_PAYMENT`；支付成功后查询还是待支付。
3. **状态停滞**。订单已经从 `CREATING` 进入待支付，查询还是 `CREATING`。客户端在轮询，晚一点看到是可以接受的，但它和第 2 种在实现上分不开。

三种都属于“读己之写”：用户（或代表他的系统）刚写过，随后的读必须看到这次写。别的用户晚一点看到没关系，订单只有它的主人能查。

### 3.4 读己之写：两种做法都实现

两种做法共用一个结构：写的一方在 Redis 里给订单留一个标记，`GetOrder` 读从库之前先看标记。没有标记说明这个订单近期没有被写过，放心读从库。标记放在闸门那个 Redis 实例上（不淘汰），放缓存实例的话标记被淘汰等于悄悄读到旧数据。

用配置 `ORDER_READ_MODE` 在三种行为之间切换，便于对比：

| 模式 | 写的一方 | `GetOrder` |
|---|---|---|
| `primary` | 什么都不做 | 一律读主库。没有配置从库时只能是这个模式。 |
| `window` | 写之前给订单打标记，保留一段时间（默认 3 秒） | 有标记读主库，没有读从库 |
| `gtid` | 写之前打标记；提交后另外记下主库此刻的 GTID 集合，保留更久（默认 1 分钟） | 有“写之前”的标记就读主库；否则有 GTID 就在从库上等它追到这个位置（默认最多等 100 毫秒），追到了读从库，超时读主库 |

两种标记是两个 key：`order:rw:pin:<订单号>`（写之前打，到期自己消失，写的一方不删它）和 `order:rw:gtid:<订单号>`。所以 `gtid` 模式等于“窗口内读主库，窗口过后按 GTID 等”，窗口可以配得比 `window` 模式短。

**GTID 只往前更新。** 同一个订单可能有两个写的一方交错（例如支付结果和超时关单）：甲先提交、先读到 GTID，乙后提交、后读到，但甲写 Redis 比乙晚，就会用较旧的集合盖掉较新的。所以读 GTID 时一并读出主库的时间，Redis 里用脚本比较，只接受更晚读到的那个。较晚读到的集合一定包含较早的。

**“订单不存在”只由主库说了算。** `GetOrder` 在从库里查不到行、闸门里也没有占用时，最后的那次复查改为读主库。这样 3.3 的第 1 种问题（订单凭空消失）不依赖标记就被堵住了：标记过期、Redis 出错、延迟再大，都不会把一个存在的订单答成 404。代价是查询不存在的订单要读一次主库，“不存在”的结果有 2 秒缓存挡着。标记要解决的只剩第 2、3 种（状态旧）。

**为什么标记要在写之前打。** 如果在提交之后才打，“已提交、标记还没写上”的那一小段时间里读会走从库。进程恰好在这里崩溃的话，这个订单在标记本该存在的整个时间里都可能被读到旧数据。先打标记再写，最坏的情况是写失败了、标记白打，代价只是几次读走了主库。

**`window` 的弱点**是窗口长度靠猜：复制延迟超过窗口，标记过期了从库还没追上，照样读到旧数据。窗口取长了，更多的读压在主库上。

**`gtid` 的优点**是等的是确切的位置，不靠猜；从库已经追上时等待立即返回，所以标记可以保留得久。代价是每次写多一次主库查询（取 GTID 集合）和一次 Redis 写，每次带标记的读多一次从库上的等待。落库是当前的吞吐瓶颈，这个代价要实测。

**GTID 怎么取。** 提交后在主库上读 `@@global.gtid_executed`。它是“到此刻为止主库执行过的全部事务”，比“我这一次事务”多，等它追上是偏保守的，但一定正确。更精确的做法是让服务端在提交的应答里带回本次事务的 GTID（`session_track_gtids`），但 go-sql-driver/mysql v1.10.1 没有把它暴露出来，所以不用。

**从库不可用或等待超时**一律退回主库并记日志。Redis 读标记失败时也读主库：宁可多读主库，不冒读到旧数据的风险。写的一方打标记失败则继续写，不因为 Redis 抖动拒绝业务写入，这是一个已知的缺口。

### 3.5 连接与配置

- `MYSQL_DSNS` 仍然是主库。新增 `MYSQL_REPLICA_DSNS`，个数和顺序与主库一致；不设表示没有从库，所有读走主库，`ORDER_READ_MODE` 只能是 `primary`。chaos 和 bench 脚本先不改，继续用单实例。
- 每个从库一个连接池，上限沿用 `MYSQL_MAX_OPEN_CONNS`。主从分到不同实例后，每个池只占自己那个实例的连接数预算。
- 一个分片只有一个从库，不做多从库之间的负载均衡。

### 3.6 测试

- **单元和集成测试不需要真的复制。** 测试里把“从库”接到一个没有数据的临时库上，它等价于延迟无限大的从库：有标记的读能看到订单，没有标记的读看不到，这正好能断言路由是否正确。sweeper 读从库也用同样的办法验证“从库旧了只是晚处理，不会做错”。
- **`gtid` 模式要真的复制才能测。** 放在 e2e 里，跑在 compose 的主从上：在从库上 `STOP REPLICA SQL_THREAD` 制造延迟，下单、取消后立刻查询，断言看到的是最新状态；再恢复复制，断言等待能在时限内返回并读到从库。
- **对比实验**（写进笔记）：三种模式下，人为延迟 0、1 秒、10 秒时，读到旧数据的次数、读主库的比例、落库吞吐。

### 3.7 实现顺序

1. compose 的主从拓扑、初始化脚本、内存调优，登记版本和端口。先确认本机和 CI 放得下。
2. `store` 支持从库和 `primary` 模式，sweeper 的扫描改读从库。
3. `window` 模式。
4. `gtid` 模式和 e2e 的延迟用例。
5. 对比实验和笔记。

第 1 步是脚本和 YAML，派给 Sonnet；第 2 到 4 步涉及订单状态的读路径，由 Fable 编写或评审。

### 3.8 查证的结果（2026-11-13，MySQL 9.7 官方文档加本机实测）

- **`WAIT_FOR_EXECUTED_GTID_SET(集合, 超时)`**：返回 0 是追上，1 是超时，其他失败报错。超时的单位是秒，实测接受小数（0.1 约 100 毫秒）。**超时为 0 表示一直等下去**，不是立即返回，所以 `store.WaitReplica` 拒绝不大于 0 的超时。它只看这台服务器上已经应用了哪些 GTID，不管复制线程是开着还是停着：线程停着时就是等到超时。
- **复制账号的认证**：MySQL 9 的默认插件是 `caching_sha2_password`。连接不是 TLS 时，从库必须指定 `GET_SOURCE_PUBLIC_KEY = 1` 或 `SOURCE_PUBLIC_KEY_PATH`，主库才会给出 RSA 公钥。本机用前者。公钥是从连接上要来的，没有校验主库的身份，生产环境应当用 TLS 加证书校验。
- **制造延迟**：`SOURCE_DELAY` 的单位是整数秒，改它要先停 SQL 线程。e2e 里直接停、启 SQL 线程更好控制：停着就是延迟无限大，启动就是追上。
- **`super_read_only` 不能写在 compose 的启动参数里**：官方镜像首次启动要写系统表和 root 密码，会失败。改为复制建立后由脚本 `SET PERSIST`。代价是容器首次启动到脚本跑完之间从库可写。

### 3.9 实现中的调整

- **占用已被认领时，展示读改读主库**。原来从库查不到行、闸门里有占用时，直接从占用合成一个 `CREATING` 的订单。从库落后时，主库上已经待支付的订单会被答成 `CREATING`，状态往回退。认领发生在写订单行之前，所以“已认领”说明主库上可能已经有行，这时读一次主库；未认领说明落库还没开始，照旧合成。这样从库“缺一行”在任何情况下都不会给出错误的答案，剩下的局限只有一种：标记过期之后，从库里**有**这一行但状态是旧的。
- **记 GTID 只在确实写了数据之后做**。条件更新没有生效（被别人抢先）的事务不记：抢先的一方自己会记。
- **sweeper 查从库用一半的 slot 时限**。从库挂起时不能把整个时限耗光，否则退回主库时已经没有时间，兜底任务会跟着从库一起停摆。
- **`service.New` 改为返回错误**：读模式要读从库而没有配置从库或标记时拒绝启动。

### 3.10 结果（2026-11-13）

端到端用例（`test/e2e/replica_lag_test.go`）在真实的主从上跑，用停掉从库的 SQL 线程制造延迟，两个分片各跑一遍：

- **复制停着时下单**：能在正常时限内看到待支付，取消后立刻查到已取消，标记过期后仍然不是 404。`window` 和 `gtid` 都成立。
- **从库里有旧行、主库上已取消、标记已过期**：
  - `gtid` 模式读到已取消，那次查询耗时 104 到 115 毫秒，就是等满 `ORDER_READ_GTID_WAIT` 后退回主库。
  - `window` 模式读到的是旧的待支付，耗时约 5 毫秒。这是它的已知局限，用例把它记录下来而不是判为失败。
- **恢复复制后**查询正常。

`make e2e` 默认用 `gtid` 模式，`ORDER_READ_MODE=window`、`primary` 也能跑；`primary` 下延迟用例跳过。

定量的对比（不同延迟下读主库的比例、对落库吞吐的影响）没有做：现在没有指标可以统计读走了哪里，本机的吞吐测量在 1b 已经证明不可靠。挪到阶段 3 有了指标之后。

## 4. 步骤三：非分片键查询（CDC 加商家索引表）

状态：主人已确认（2026-11-13）。决定和备选方案见 ADR-0014。

目标是阶段计划里的验收项：商家维度的查询走索引表，不扫全部分片，同步延迟可观测。

### 4.1 问题和整体结构

订单按 `user_id` 分片。“某个商家的订单列表”没有分片键，只能 8 张表全扫一遍再归并。做法是另存一份按 `merchant_id` 分片的数据，专门回答这个查询，它和订单表之间靠 binlog 同步：

```
order 主库 ──复制──> order 从库 ──binlog──> cdc ──> Kafka: cdc.order.orders ──> orderindex ──> merchant_index_db_{0,1}
                                                                                    ↑
                                              gateway: GET /merchants/{id}/orders ──┘
```

- **`services/cdc`**（新）：伪装成从库读 binlog，把 `orders_*` 表的行变更发到 Kafka。它不知道下游拿这些变更做什么。一个进程里每个源库一条流水线，和 order 里每库一个 outbox 中继是同样的结构。
- **`services/orderindex`**（新）：消费变更，写索引表；提供 `ListMerchantOrders`（gRPC）。
- **gateway**：新增 `GET /api/v1/merchants/{merchant_id}/orders`。

为什么不让 order 服务在写订单时顺手写索引表（双写），也不直接用现有的 `OrderEvent`：见 ADR-0014。一句话：双写跨库，没有事务保证；`OrderEvent` 能做到，但它只包含发布方想到要发的内容，而 binlog 是“库里实际发生了什么”，不依赖业务代码配合，后面的归档、对账、人工修数都能被它看到。这一步的学习目标也是 CDC 本身。

### 4.2 前置：数据模型里要有商家

现在没有商家的概念。要加三处，都是共享部分的改动，在主线串行完成：

1. **inventory**：`sku_stock` 加 `merchant_id BIGINT NOT NULL`（存量行填 1）。SKU 属于哪个商家定下来之后不改。`reservation` 头上加 `merchant_id`（可空，“先释放后预占”留下的行没有商家），使重复的 Reserve 返回同样的结果。两个 `ALTER` 各占一个迁移版本，单条 DDL 本身是原子的，中途被杀可以重跑。
2. **proto**：`ReserveResponse` 加 `merchant_id`。
3. **order**：`orders_N` 加 `merchant_id BIGINT NULL` 和 `version BIGINT NOT NULL DEFAULT 0`（`version` 的用途见 4.6）。`CREATING → PENDING_PAYMENT` 的那条更新（现在写总金额的地方）同时写入 `merchant_id`。

**一个订单只属于一个商家。** Reserve 发现订单里的 SKU 属于不同商家时拒绝（`FAILED_PRECONDITION`，reason=`MIXED_MERCHANTS`），订单走现有的创建失败路径。真实的电商在结算页就把购物车按商家拆成多个订单，上面再挂一个交易单；这里不做拆单，只保证订单模型是“拆完之后”的样子。

这样选的原因在同步这一侧：`merchant_id` 在 `orders` 行上，每条行变更自己就带着路由到索引分片所需的全部信息。如果允许多商家，商家只出现在 `order_items` 上，而状态变更只改 `orders` 行，消费者拿到一条“订单变成已支付”时不知道该更新哪些商家的索引，只能回查源库或者自己维护一张订单到商家的映射，两种都把顺序和幂等问题变复杂了。

由此有三个结论：

- `merchant_id` 为空的订单（还在 `CREATING`，或预占前就失败）不进索引。商家不需要看到没创建成功的订单。
- `merchant_id` 写入后不变，所以索引行不会从一个索引分片搬到另一个。索引的分片键如果可变，一次更新就要变成“旧分片删、新分片插”，两步不在一个事务里。
- 只需要同步 `orders_*`，不需要 `order_items_*`。

**order 的迁移要可重入。** 8 张表各一条 `ALTER`，中途被杀会留下改了一半的状态，而 MySQL 没有 `ADD COLUMN IF NOT EXISTS`。两列放在同一条 `ALTER` 里（每张表原子），每条前面查 `information_schema` 判断是否已经加过。具体写法（goose 的 SQL 迁移里用预处理语句，还是改用 Go 迁移）实现时定，并用“杀在中间再重跑”验证。不采用直接改 `00001` 重建库的办法：分片后的表结构变更本身是要练的内容。

### 4.3 从哪里读 binlog：从库

本机实测（2026-11-13）：主库和从库都是 `log_bin=ON`、`log_replica_updates=ON`、ROW 格式，binlog 保留 30 天（集群上 2026-11-22 起是 1 天，见 `deploy/charts/mysql/values.yaml` 的 `binlogExpireLogsSeconds`）。从库的 binlog 里是带着主库 GTID 的同一批事务。

**从从库读**，DSN 可配，能指回主库。理由：

1. **异步复制下，主库宕机时可能有已提交但从库没收到的事务。** 从主库读的 CDC 会把这些事务发给下游；切到从库之后它们在新主库上不存在，索引里就多了源库没有的订单。从从库读，下游看到的永远不超过从库已有的，提升这个从库后两边一致。
2. 位点用 GTID 集合记，不用文件名加偏移，所以它不绑定某一台机器，源可以在主库和从库之间换。
3. 不占主库的连接和网络。这一点是次要的，dump 线程本身很轻。

代价是同步延迟叠加了复制延迟，从库停了 CDC 也跟着停。

需要改的配置：order 的四个实例和 `mysql` 都加 `--binlog-row-metadata=FULL`（现在是 `MINIMAL`），原因见 4.8。CDC 的账号（`REPLICATION SLAVE`、`REPLICATION CLIENT`、对 order 库的 `SELECT`）由复制脚本在主库上创建，靠复制到达从库。伪装成从库要有自己的 server-id，用 1011、1021，登记到 `versions.md`。

### 4.4 变更消息

- **topic**：`cdc.order.orders`。8 张 `orders_N` 合成一个逻辑表，消息里带 slot。只捕获表名匹配 `^orders_\d+$` 的行事件，其他表和 DDL 只记日志。
- **key**：`order_id`。同一个订单的变更进同一个分区。
- **格式**：protobuf（新文件 `api/proto/oppenheimer/cdc/v1/change.proto`）。

```
RowChange {
  source        string   // 流水线名，如 "order-0"
  table         string   // 逻辑表名 "orders"
  slot          int32
  op            enum     // INSERT, UPDATE, DELETE, READ（全量阶段读到的行）
  before, after map<string, Value>   // 列名到值；INSERT 和 READ 没有 before，DELETE 没有 after
  gtid          string   // 所在事务，排查用
  commit_micros int64    // 事务在主库提交的时间（GTID 事件里的 original_commit_timestamp），算延迟用
}
Value { oneof: null, int64, string, bytes }   // DATETIME 以字符串原样传递，由下游解析
```

消息按列名携带值，CDC 不认识 `orders` 表的任何一列，换一张表不用改代码。

- **topic 开启压缩保留**（`cleanup.policy=compact`）。每个订单至少留着最新的一条，以后新增一个下游（例如 ES）可以从 topic 的开头消费出全量，不用再对源库做一次全量读。

### 4.5 位点和断点续传

- **位点是 GTID 集合**，只在事务边界（XID 事件）推进，重启不会从事务中间开始。
- **存在 Kafka 里**：一个压缩的 topic `cdc.checkpoint`，key 是流水线名。CDC 的源是只读的从库，没法把位点写回源库；另找一个 MySQL 存又多一个依赖，而 Kafka 本来就必须可用。
- **先确认消息落盘，再推进位点。** 每隔一小段时间（默认 1 秒）：等到目前为止发出的消息全部得到确认，再把“最后一个完整发出的事务”对应的 GTID 集合写进位点 topic。崩溃后从位点重读，最多重发一个间隔内的事务，下游靠 4.6 的版本号去重。这是至少一次。
- **发送失败不跳过**。生产者开幂等和 `acks=all`，分区内保序。遇到重试也解决不了的错误，进程退出，重启后从位点再来。
- **位点在源库上已经被清掉**（`gtid_purged` 里有位点之后的事务）时，CDC 拒绝启动并报错，由人决定是否重做全量（4.7）。自动重做会把“binlog 保留期配短了”这种问题盖住。
- **同时只应有一个实例**读同一个源。两个实例同时跑不会出错（下游幂等），只是每条变更发两遍。这一步靠部署保证单实例，不加选主。

为什么不用 Kafka 事务把“发消息”和“写位点”做成原子的：能做，franz-go 支持。但下游无论如何要幂等（它自己的消费位移和写库也不是原子的），有了幂等，上游的恰好一次没有额外收益，只多了事务的开销和超时要处理。

### 4.6 顺序和幂等：行版本号

消费者要保证两件事：同一个订单的变更不乱序应用；重复的消息不出错。

分区内有序能保证正常情况下的顺序，但挡不住**重放**：CDC 从位点重启后，把已经发过的 `v3, v4, v5` 又发了一遍，消费者已经应用到 `v5`，再按顺序应用就是先退回 `v3` 再回到 `v5`。最终结果对，中间有一段读到的是旧状态。全量和增量衔接的地方（4.7）也是同样的问题。

所以每条变更要带一个能比较新旧的版本，消费者只接受更新的。版本从哪里来，有两种：

| | 从日志位置派生（GTID 的事务号） | 行上的 `version` 列 |
|---|---|---|
| 业务代码 | 不用改 | 每条更新 `orders` 的语句都要 `version = version + 1` |
| 会不会漏 | 不会 | 新写一条更新忘了加，这次变更就被索引丢掉 |
| 换主库之后 | 新主库的事务号从另一个序列开始，和旧的不可比 | 不受影响 |
| 全量读到的行 | 行里没有位置，只能用“全量开始时的位置”代替，而且全量必须是一个精确对应某个位置的一致性快照（要短暂加全局读锁） | 行自己带着版本，全量可以是普通的分批读，不需要一致性快照 |

**采用行上的 `version` 列。** 它让“全量加增量”和“换源”两个最容易出错的地方变得简单：任何来源的行映像，版本高的赢。它的弱点（忘了加）用 CDC 自己来补：binlog 是 `FULL` 行映像，更新事件里有改之前和改之后的整行，CDC 发现一条更新前后 `version` 相同就记错误日志并计数，测试里断言这个计数为 0。`orders` 上现在有 5 条更新语句，都在 `store.go` 里。

索引表的写入：

```sql
INSERT INTO merchant_orders_K (merchant_id, order_id, ..., src_version) VALUES (...) AS new
ON DUPLICATE KEY UPDATE
  status      = IF(new.src_version > src_version, new.status, status),
  ...
  src_version = IF(new.src_version > src_version, new.src_version, src_version);  -- 必须放在最后
```

`ON DUPLICATE KEY UPDATE` 的赋值从左到右执行，后面的表达式读到的是前面已经改过的值。`src_version` 如果先赋值，后面每一列的比较都变成“新版本大于新版本”，永远为假，行就只有版本号在涨。这一点要有测试钉住。

有了版本，应用变更就是可交换的：乱序、重复都收敛到版本最高的那个映像。按 `order_id` 分区仍然保留，它让正常情况下不产生无用的写。

**DELETE** 这一步不处理：CDC 照常发布，索引的消费者忽略并计数。现在没有任何路径删除订单；步骤五的归档会删热库的行，那时再决定索引里保留还是删除（删除没有“更高的版本”，要用墓碑）。

### 4.7 全量加增量的初始化

位点 topic 里没有这条流水线的记录时做全量：

1. 在源上读出当前的 `gtid_executed`，记为 G，连同“全量进行中”写进位点。
2. 逐张 `orders_N` 按主键分批读（`WHERE order_id > ? ORDER BY order_id LIMIT n`），每行发一条 `op=READ` 的消息。每发完一批，把“读到哪张表的哪个主键”写进位点，中断后从那里继续。
3. 全部读完后，从 G 开始读 binlog，转入增量。

读 G 和分批读必须在同一台机器上。正确性的论证：G 之前提交的状态，分批读一定看得到；G 之后提交的任何变更都在 binlog 里 G 的后面，增量阶段会发出来。分批读期间行被改了、新行插在已经读过的位置之后，都属于后一种。全量读到的映像可能比增量里的某条新，也可能旧，版本号保证留下的是最新的。

所以这里不需要一致性快照，不需要全局读锁，也没有长事务。代价是 binlog 必须保留到全量读完（本机是默认的 30 天；集群上 2026-11-22 起是 1 天，全量读要在 1 天之内读完）。

重做全量是一个显式的命令行参数：清掉这条流水线的位点再启动。下游不用清，重复的映像会被版本号挡掉。

### 4.8 表结构变更

行事件里只有按位置排列的值，没有列名。列名的来源有两种：去库里查当前的表结构，或者让 MySQL 把列名写进 binlog。前一种有一个时间差的问题：CDC 在追旧日志时查到的是“现在”的结构，和产生那条日志时的结构可能不一样（Debezium 为此专门维护一个表结构历史的 topic）。`binlog_row_metadata=FULL` 让每个 TABLE_MAP 事件带上当时的列名，CDC 不用查库，也就没有这个时间差。

约定：

- **加列**：新列自动出现在消息里。消费者忽略不认识的列。
- **删列或改名**：消费者需要的列缺失时，这条消息是毒消息，消费停住并报错，不跳过。所以删列要按“先让所有消费者不再依赖它，再改表”的顺序做。
- 8 张表的 DDL 不是同时完成的，中间一段时间不同 slot 的消息列不一样。按列名取值的消费者不受影响。

go-mysql 的 `replication` 包能否取到这些列名，动工时第一件事是写一个小程序验证；取不到的话退回“查库加 DDL 事件触发刷新”，并把时间差作为已知局限写下来。

### 4.9 索引表和查询

- **库**：`merchant_index_db_0`、`merchant_index_db_1`，都放在现有的 `mysql` 实例上（本机内存不够再加实例，分库的路由逻辑不受影响）。4 个 slot，`slot = merchant_id & 3`，`db = slot % 2`，表名 `merchant_orders_{slot}`。布局定义在 `pkg/sharding`，和订单的布局并列。
- **表**：

```sql
CREATE TABLE merchant_orders_K (
    merchant_id   BIGINT      NOT NULL,
    order_id      BIGINT      NOT NULL,
    user_id       BIGINT      NOT NULL,
    status        TINYINT     NOT NULL,
    total_amount  BIGINT      NOT NULL,
    currency      CHAR(3)     NOT NULL,
    created_at    DATETIME(6) NOT NULL,   -- 订单的创建时间
    paid_at       DATETIME(6) NULL,
    src_version   BIGINT      NOT NULL,
    synced_at     DATETIME(6) NOT NULL,   -- 本行最后一次被同步写入的时间
    PRIMARY KEY (merchant_id, order_id),
    KEY idx_merchant_status (merchant_id, status, order_id)
);
```

- **带上列表页要显示的列**，不只存订单号。只存订单号的话，列表的每一行都要按订单号回到订单分片再读一次（一页 20 条就是分散在各分片上的 20 次点查），而且没法按状态筛选。代价是这些列有同步延迟，见 4.10。订单详情仍然走现有的 `GetOrder`。
- **分页用订单号做游标**。订单号的高位是毫秒时间戳，按订单号倒序就是按创建时间倒序：`WHERE merchant_id = ? AND order_id < ? ORDER BY order_id DESC LIMIT n`，直接走主键，翻到多深都是一次范围扫描。不同节点的时钟有偏差，同一毫秒内的先后也不严格，对列表页足够。
- **接口**：`GET /api/v1/merchants/{merchant_id}/orders?status=&cursor=&limit=`，规范先行。项目里没有鉴权，路径里的商家号直接信任，和现有的用户接口一致。

### 4.10 同步延迟：怎么看，怎么应对

**怎么看。** 每条消息带着事务在主库的提交时间。CDC 发出时算一次“捕获延迟”，消费者写库时算一次“端到端延迟”，各自每 10 秒输出一行汇总日志（条数、最大、平均）。加上 Kafka 消费组的积压条数。e2e 里量一次“下单到出现在商家列表”的耗时。指标和告警等阶段 3 有了 OpenTelemetry 再接，和步骤二的读模式对比一样。

已知的不足：没有写入时算不出延迟，“没有变更”和“同步卡住了”在日志上分不开，要靠消费组积压和 CDC 进程的存活来区分。完整的做法是在源库上定时写心跳行，放到阶段 3。

**怎么应对。** 和 ADR-0013 的原则相同，按用途划分：

- 索引只用于展示列表。列表里的状态可能是旧的，新订单可能晚一点出现。商家不是这些订单的写入方，不存在“读己之写”的预期。
- 任何要做决定的操作（以后的发货、商家退款）都按订单号回到订单分片的主库重新读状态，不用索引里的状态做前提。
- 点进详情走 `GetOrder`，看到的是源库的状态。
- 不做“列表页回查源库刷新状态”。它把每次列表查询变回多分片点查，索引表带状态列就没有意义了。

### 4.11 测试和实现顺序

### 4.12 主人确认过的决定

1. **一个订单只属于一个商家**，多商家的订单在预占时被拒绝（4.2）。这改变了现有行为：`make seed` 的三个 SKU 会归到同一个商家，现有用例不受影响。
2. **版本用行上的 `version` 列**，为此改 `orders` 的 5 条更新语句（4.6）。备选是从 GTID 派生，不改业务代码，但全量和换主库更复杂。
3. **CDC 从从库读**（4.3）。
4. **新增两个服务** `cdc` 和 `orderindex`，而不是把消费者和查询放进 order 服务（4.1）。
5. **延迟只做到日志加 e2e 测量**，指标留到阶段 3（4.10）。
6. **两个可选项不做**（4.11）。

### 4.13 实现中的发现（2026-11-13）

**查证的结果**（go-mysql v1.16.0 对本机的 MySQL 9.7.4）：

- `binlog_row_metadata=FULL` 下，`RowsEvent.Table.ColumnNameString()` 能拿到列名，4.8 的做法成立，不需要退路。
- 行里的值：整数列是 Go 的整数类型，`CHAR`、`VARCHAR` 是字符串，`DATETIME(6)` 是 `2026-06-01 12:00:00.123456` 这样的字符串，NULL 是 `nil`。`BINARY` 列也以字符串返回（内容是原始字节），要靠 TABLE_MAP 里的列类型和字符集区分它和字符列。
- GTID 事件里有微秒精度的 `original_commit_timestamp`；XID 事件带着“到此为止”的 GTID 集合，可以直接当位点。
- 从库的 `gtid_executed` 里有两个 uuid：主库的事务，加上从库自己的 5 个本地事务（初始化时写的）。这正是 4.6 里“事务号只在同一个 uuid 内可比”的情况，用行版本号就不用处理它。

**步骤二留下的一个缺陷：容器重建后复制起不来。** 给 MySQL 加 `--binlog-row-metadata` 要重建容器，重建后两个从库的复制线程都启动失败（错误 1872）。原因是从库没有设 `--relay-log`，中继日志的文件名默认取主机名，而容器的主机名是容器 ID，每次重建都变；复制元数据里记着旧文件名，新实例找不到。`make down` 再 `make up` 同样会触发，步骤二验证时没有走过这条路径。MySQL 启动日志里其实有一条警告说的就是这件事。

修了两处：compose 里给从库固定 `--relay-log=relay-bin`；复制脚本在 `START REPLICA` 失败时执行 `RESET REPLICA ALL` 再重新配置。重新配置不丢也不重复数据，因为用的是 GTID 自动定位：位置不来自复制元数据，而来自从库自己的 `gtid_executed`，主库按它补发。修完后核对过主从的 GTID 集合一致，又做了一次 `make down`、`make up`，复制自己恢复。

**`sku_stock.merchant_id` 带默认值 1。** 设计里写的是存量行填 1。实现时保留了列的默认值：本项目没有创建 SKU 的接口，SKU 由脚本、压测和十几处测试直接插入，不关心商家的地方可以不写这一列。代价是忘了写商家不会报错。

**多商家的订单失败在落库之后，不在受理时。** 受理（`SubmitOrder`）只看 Redis 里的库存闸门，那里没有商家信息，所以多商家的订单会被受理、返回 `creating`，随后在预占时被拒绝，订单变为 `failed`，原因码 `MIXED_MERCHANTS`，闸门里的占用由 failed 事件归还。和“闸门有货而 MySQL 没货”走的是同一条路径。要在受理时就拒绝，得在装载闸门时把商家也放进 Redis，现在没有做。

**列表查询固定了索引（`FORCE INDEX`）。** 4.9 写的是“直接走主键”。orderindex 的子 Agent 实测优化器两个方向都选错过：带状态筛选时选了主键倒序扫、边扫边过滤，状态稀少时要扫完这个商家的全部订单；不带状态时有一次选了 `idx_merchant_status` 再排序。两条查询的形状是固定的，所以各自指定索引，测试里用 `EXPLAIN` 断言没有 filesort。

**缺列时怎么“停住”。** `kafkax` 对普通错误是重试若干次后进死信、分区继续，没有“停住”的选项。orderindex 把重试次数设成无限：表结构对不上和写库失败都原地重试（退避封顶 5 秒），不提交位移、不进死信，修好后从这条消息继续。只有消息本身反序列化不了才进死信。

**步骤五要先定的一件事：压缩的 topic 和 DELETE。** 现在 DELETE 是一条 `op=DELETE` 的普通消息，压缩后它会成为这个 key 留下的唯一记录，新下游从头消费时看不到被删的订单曾经存在；改成墓碑又会让现有下游收不到“删除”。归档会删热库的行，动工前要定。

**全量和增量对同一行必须给出相同的映像，有两处天然不同。** 都是 cdc 的子 Agent 实现时发现并处理的，有测试钉住：

- `BINARY(n)` 列：MySQL 写 binlog 时去掉尾部的 `0x00`，`SELECT` 返回的却是补满 n 字节的值。`request_hash` 恰好以 `0x00` 结尾的订单，两条路径会给出不同的值。CDC 按 TABLE_MAP 里的列长度补齐。
- `FLOAT` 列：binlog 里是 32 位，直接转成 64 位和 `SELECT` 的文本结果对不上。订单表没有浮点列，也对齐了。

`ENUM`、`SET`、`BIT`、`JSON` 两条路径的表示不同（例如 binlog 里 `ENUM` 是序号），没有处理，订单表里没有这些类型。

**CDC 的几条约束，设计里原来没有写：**

- 源的 DSN 必须指向一个固定的实例，不能是负载均衡或虚拟地址。4.7 的论证要求“读 G”和“分批读”在同一台机器上。
- 主键必须是整数且不被更新。主键被更新时消息的 key 是新主键，旧主键没有删除消息，下游会留下一行孤儿。
- 行被删除后用同一个主键再插入，版本从 0 重新开始，下游会把新行当成旧映像丢掉。现在没有删除订单的路径，步骤五归档时要处理（和上面的 DELETE 问题一起）。
- 一条流水线出错会让整个进程退出（`app.Run` 遇到任一组件失败就全停），另一条流水线跟着重启，靠位点续上。
- 带全量游标的位点在续传前、以及全量做完转入增量前，各检查一次 G 之后的日志有没有被清掉。全量可能做很久。
- 遇到不完整的行映像（`binlog_row_image` 不是 `FULL`）、拿不到列名、主键列不存在，都报错退出，不跳过。
- 超过 Kafka 消息上限的行会让流水线反复失败，没有出口。订单行很小，不会遇到。

**4.4 说压缩的 topic “每个订单至少留着最新的一条”，不总是成立。** 重放期间（崩溃后重启，或重做全量后从 G 读 binlog），某个 key 的最后一条可能是较旧的版本，要等 CDC 追平才是最新的。恰好在这段时间从头消费的新下游先拿到旧映像，随后被后续消息修正；它同样要按行版本号比较。

**端口。** orderindex 是 HTTP 8084、gRPC 9084，cdc 是 HTTP 8085（只有健康检查）。

**这一步的三个并行任务没有用 worktree。** 主线的共享改动没有提交（提交要主人发话），worktree 里看不到。三个任务各自只改一个互不重叠的目录，直接在主工作目录里做，只允许在自己的模块目录里运行构建和测试。

### 4.14 结果（2026-11-13）

`make lint test e2e` 通过，`make chaos` 两次 PASS（chaos 和 bench 不启动 CDC 和 orderindex，它们验证的是商家和行版本号的改动没有破坏原有的一致性）。

e2e 新增 5 个用例（`test/e2e/merchant_index_test.go`）：

- 同一个商家的三个订单（支付、取消、待支付）出现在商家列表里，状态跟上，按状态筛选正确。
- 用 `limit=2` 翻页走完 5 个订单，不重不漏，订单号严格递减。
- 两个商家互相看不到对方的订单。
- 多商家的订单被受理后变为失败，原因是 `MIXED_MERCHANTS`，两个 SKU 的库存都还回去，两个商家的列表里都没有它。失败原因是直接读订单表断言的，`GET /orders/{id}` 的响应里没有这个字段。
- 直接读订单表和索引表，同一个商家的订单号集合相同，状态、金额、版本逐个相等。

**同步延迟**：从下单请求返回到订单出现在商家列表里，几次运行量到 50 到 260 毫秒，每 50 毫秒轮询一次。这个数包含了订单落库、主从复制、CDC、Kafka 和写索引，是本机空闲时的值，不代表有压力时的表现。

**对账**：`test/load` 的 verify 加了第 20 项“商家索引与订单表一致”，报告缺失、多余、不一致和放错 slot 的行。它要用 `-merchant-index-dsns` 传入索引库才检查，不传就跳过。chaos 和 bench 现在不传。以后要在压测后检查它，得先等索引追上：`wait-quiet` 不看 CDC 和 orderindex 的积压，紧接着对账会误报缺失。

4.11 列的 e2e 场景里有两个没有放进 e2e：“先有订单再第一次启动 CDC”和“杀掉 CDC 再启动后一致”。e2e 的服务由脚本按固定顺序启动，用例控制不了进程。这两个场景由 cdc 模块的集成测试覆盖（全量、全量中途停止后续传、优雅停止和模拟崩溃后从位点重启），用的是临时库里的表，不是真实的订单流量。把 CDC 和 orderindex 加进 chaos 的击杀名单是更完整的验证，没有做。

## 5. 步骤四：跨分片查询、造数、扩容演练

状态：主人已确认（2026-11-14）。扩容的决定和备选方案见 ADR-0015。

这一步有三件事，按依赖顺序做：先定哪些查询支持（5.1、5.2），再灌数据（5.3），最后在有数据、有流量的情况下把 2 个库扩成 4 个（5.4 到 5.8）。

### 5.1 查询按“落在几个分片上”分类

| 查询 | 落在哪 | 结论 |
|---|---|---|
| 按订单号查详情、支付、取消 | 一个 slot（基因） | 已支持 |
| 按用户加幂等键查 | 一个 slot | 已支持 |
| 按用户列出订单（分页、按状态筛选） | 一个 slot | 这一步新增，见 5.2 |
| 按商家列出订单 | 索引表的一个 slot | 步骤三已支持 |
| 后台扫描（超时关单、卡单兜底） | 逐个 slot | 明确豁免的全分片扫描，每个 slot 有时限 |
| 不带用户、不带商家的列表（全站最近订单、按状态或时间筛全部订单） | 全部 slot | 在线不支持 |
| 全局聚合（订单总数、某天的成交额、按状态计数） | 全部 slot | 在线不支持 |
| 跨用户的连接、按金额排序的全局榜单 | 全部 slot | 在线不支持 |

“在线不支持”的意思是 gateway 和 order 不提供这样的接口，不是做不到。它们的归宿是另一份按别的维度组织的数据：

- **换一个分片键的索引表**。商家维度已经这么做了。再有新的固定维度（比如按 SKU 查订单），做法相同：CDC 的 topic 上再挂一个消费者。
- **离线或分析型存储**。聚合和任意条件的筛选交给数仓或 OLAP 库，数据同样从 CDC 的 topic 来。本项目不搭，只在这里写明出口。
- **运营后台偶尔要看“全站最近订单”**。可以接受慢，用散发加归并（下面一段）就够了，不值得为它建索引表。

**为什么跨分片分页不能直接做。** 要第 `p` 页、每页 `n` 条、全局按时间倒序。每个分片各自的第 `p` 页合起来不是全局的第 `p` 页：全局的前 `p × n` 条可能全部来自同一个分片。所以用偏移量时，每个分片都要返回自己的前 `p × n` 条，协调方归并后丢掉前面的。8 个 slot、翻到第 1000 页、每页 20 条，是取回 16 万行只为了显示 20 行，而且每个分片自己也要扫过这 2 万行。

三种改法：

1. **禁止跳页，改用游标**。请求带上一页最后一条的排序键（订单号），每个分片执行 `order_id < 游标 ORDER BY order_id DESC LIMIT n`，协调方做 k 路归并取前 `n` 条。每个分片每次只出 `n` 行，翻多深代价都一样。代价是只能“下一页”，不能跳到第 500 页。
2. **二次查询法**。保留跳页：第一次每个分片查 `OFFSET (p × n) / 分片数`，取各分片返回的最小排序键，第二次用这个下界重新查，算出全局偏移量。两次往返，仍然要在分片内跳过偏移量，只是省掉了网络传输。实现复杂，只在排序键分布均匀时划算。
3. **不做**。把查询收窄到带分片键，或者交给上面说的索引表、离线存储。

本项目选 1 用于“单个分片内的分页”（用户列表、商家列表），选 3 用于其余。散发加归并只在造数工具的查询测试里实现一次，用来量出偏移量和游标两种写法在灌数之后的差距（5.3），不做成对外接口。

**跨分片聚合**同理：`COUNT`、`SUM` 可以每个分片各算一次再相加，`AVG` 要拆成 `SUM` 和 `COUNT`，`COUNT(DISTINCT)`、中位数、`TOP N` 不能由分片结果直接合成。在线路径上不做。

### 5.2 新增：按用户列出订单

- **接口**：`GET /api/v1/orders?status=&cursor=&limit=`，用户取自 `X-User-Id`，和现有的用户接口一致。规范先行。形状和商家列表一致：按订单号倒序，`cursor` 是不透明的游标（内容是上一页最后一个订单号），返回 `next_cursor`。gRPC 是订单服务的 `ListUserOrders`，返回的行只有列表页要显示的字段，不带明细。
- **路由**：`slot = user_id & 7`，只查一个 slot，不经过索引表，没有 CDC 的同步延迟。
- **索引**：现有的 `idx_orders_user_created (user_id, created_at)` 配不上订单号游标（InnoDB 的二级索引末尾隐含主键，它实际是 `(user_id, created_at, order_id)`，按 `order_id` 排序用不上）。新增 `idx_orders_user (user_id, order_id)`，删掉没有任何查询使用的 `idx_orders_user_created`。迁移沿用 00002 的做法：先查 `information_schema.statistics`，索引已在就跳过。
- **按状态筛选不另建索引**。一个用户的订单通常是几十到几千条，在 `(user_id, order_id)` 的范围里逐行回表过滤状态就行。商家不同：一个商家可以有上百万订单，所以索引表有 `(merchant_id, status, order_id)`。重度用户下这个选择的代价在 5.3 里量。
- **读哪里**：固定读主库，和读模式无关（实现时改的，原来打算走从库）。读己之写的标记是按订单打的（ADR-0013），列表是“这个用户的一组订单”：要读从库，得证明这个用户最近写过的每个订单都已经复制过去，而刚落库的新订单正是从库上没有、读的一方也不知道该去查哪个标记的那一行。按“不确定就退回主库”的原则读主库。查询只扫一个分片里 `idx_orders_user` 的一小段，主库多承担的代价不大。以后要分流，需要在写订单的每个地方按用户再打一份标记，没有做。
- **固定索引**：语句带 `FORCE INDEX (idx_orders_user)`。带状态筛选时优化器可能改选 `(status, expire_at)`，那样要扫全表这个状态的订单再排序。固定之后索引被删或改名时语句直接报错，不会悄悄变慢。
- **围栏期间**（5.6）：分片表不存在时接口返回 `Unavailable`，不是内部错误。
- **已知局限**：已受理但还没落库的订单（还在 Kafka 里排队）不在列表里。按订单号查详情时这种订单会从闸门读出 `CREATING`，列表不做这层合并。

订单状态只读不写，但属于订单查询路径，由 Fable 评审。

### 5.3 造数工具

目标：让表大到缓冲池装不下（order 的每个实例缓冲池不到 300 MB），再看分片是否均匀、各条查询路径的延迟。步骤五的归档也要用这批数据。

**形式**：`test/load` 新增子命令 `seed`，直接向主库写，不经过服务。经过服务的话每单要走 Kafka、Redis、三个服务，灌几百万单要几个小时，而且造不出过去的时间。

**先要解决的问题：订单号造不出 2026 年以前的时间。** 订单号的高 41 位是相对 `idgen.Epoch`（2026-01-01）的毫秒数，今天是 2026-11-14，往前只有十个半月。阶段计划要求“时间跨度覆盖数年”，步骤五按订单号里的时间判断冷热，所以订单号里的时间必须是真的。三个办法：

| 办法 | 做法 | 代价 |
|---|---|---|
| A. 把 Epoch 提前到 2020-01-01 | 改一个常量 | 本机和 CI 里已有的订单号按新 Epoch 解出来是 2020 年的；本机的开发库要清空重建。可用年限从 69 年变成从 2020 年起算的 69 年 |
| B. Epoch 不动，数据只铺满 2026 年至今 | 不改代码 | 只有十个半月，“完结超过 3 个月为冷”仍然能演示，但没有“数年” |
| C. Epoch 不动，往未来灌到 2029 年 | 归档工具加一个“把现在当作某个时刻”的参数 | 库里有创建时间在未来的订单，所有按 `created_at` 和 `expire_at` 判断的代码都可能被影响 |

建议 A。这是练习项目，没有不能丢的数据；“Epoch 一旦发了号就不能改”这条规则本身正好借这次变更写进考点（改了以后旧号的时间全部错位，新旧号之间不会重复，但顺序关系被破坏）。主人已同意清空本机的开发库（5.10）。

**数据的形状**

- 订单数默认 500 万，可调。按每行订单加两行明细估算，每个主库约 1.5 到 2 GB，从库同样大，另加 binlog。具体数字灌一次小样（10 万）后按实测换算，再决定默认值。
- 时间从（新的）Epoch 均匀铺到今天，按天分块。
- 只造终态订单：已支付约 70%、超时关闭约 20%、已取消约 8%、创建失败约 2%。不造 `CREATING` 和待支付的，否则超时关单的后台任务会接手这些订单，去释放并不存在的库存预占。
- 用户号从一个保留区间取（`2^40` 起），对账工具可以据此把造出来的订单和真实流量分开：跨服务的对账（订单对支付、订单对库存流水）跳过这个区间，订单自身的检查（明细金额之和等于订单金额、状态与 `paid_at` 相符）照常做。
- 用户和商家都按 Zipf 分布取，不是均匀的。均匀的用户号必然得到均匀的分片，量不出东西；真实系统里的不均匀来自少数重度用户和大商家。
- 行版本号、`merchant_id`、`expire_at`、`paid_at`、明细的单价快照都按真实流程会写出的值来填。
- 订单号用 `idgen` 配假时钟生成，节点号固定用 63（服务不会用到），保证和线上的号不重复、同一个 slot 内按时间递增（主键顺序插入，页不分裂）。

**写入方式**

- 每个 slot 一个协程，多行 `INSERT`（一批 1000 行订单加对应的明细，同一个事务）。
- 可中断续跑：生成是确定性的（随机数种子由全局种子、slot、日期算出），每完成一个“slot 加一天”的块，在同一个事务里往 `seed_progress` 表记一行。重跑时跳过记过的块。
- 可限速（每秒行数），默认不限。
- 写入会经过 binlog 流到从库和 CDC，再进商家索引表。不绕开：这正好是一次 CDC 增量同步的吞吐测试，把“灌入速率”和“索引追上要多久”一起记下来。从库延迟期间 e2e 之类的不要同时跑。

**灌完之后量什么**（`seed` 之外另一个子命令 `seed-report`，只读）

- 均匀度：每个 slot 的行数、每个库的数据和索引大小，最大值与最小值之比；商家索引的 4 个 slot 同样统计。预期订单分片比较均匀（重度用户被 8 个 slot 稀释），商家索引明显不均匀（最大的商家独占一个 slot 的大半）。后者是“按商家分片”的固有问题，结论写进文档，不在这一步解决。
- 查询延迟（p50、p99，各跑几千次，随机取参数）：按订单号查；用户列表第一页、重度用户的深页、带状态筛选；商家列表第一页、大商家的深页。
- 每条查询跑一次 `EXPLAIN`，确认走的是预期的索引、扫描行数和页大小同阶。这是阶段验收“不出现全分片扫描”的证据。
- 偏移量对游标：同一个深页分别用 `LIMIT n OFFSET m` 和游标查，单分片内比一次，8 个 slot 散发加归并再比一次（5.1）。

### 5.4 扩容：做什么，不做什么

把 2 个库扩成 4 个：slot 2、6 从库 0 搬到库 2，slot 3、7 从库 1 搬到库 3。slot 数不变，表不拆。映射规则还是 `db = slot % 库数`，只是库数从 2 变 4（2.1 的第 2 条）。

方法是 ADR-0012 里预告的“从库提升”：给每个旧主库挂一个新从库，追平后切断复制、提升为新主库，两边各删掉不属于自己的一半。数据搬迁由 MySQL 复制完成，应用不写一行搬数据的代码。备选方案（双写加回填、用现成的 CDC 搬、停机导出导入）的对比在 ADR-0015。

不做的：拆表（8 个 slot 变 16 个）、非成倍扩容、缩容、多个 order 实例下的滚动切换（阶段 2 上了 K8s 再验证，但这里的设计要保证那时是安全的，见 5.6）。

### 5.5 布局不能再是常量

ADR-0012 把库数写成常量，理由是“配置改了数据就找不到了”。扩容演练要求同一份代码既能跑 2 个库（CI 和 e2e 仍然如此），也能跑 4 个库，常量不够用了。改成：

- **库数等于 `MYSQL_DSNS` 的个数**，必须是 2 的幂且不超过 slot 数。`sharding.OrderDBs` 常量删除，`OrderLayout()` 改成接受库数。slot 数仍然是常量。
- **每个库里有一张 `shard_meta` 表**，一行：本库的序号、总库数、本库持有的 slot 列表。order 启动时逐库核对：DSN 列表里第 `i` 个库的 `shard_meta` 必须写着“我是 `i` 号库，共 `len(DSNS)` 个库”，不符就拒绝启动。空库（第一次启动）由迁移写入这一行。

这样 ADR-0012 担心的事被挡住了：把 DSN 的顺序写反、少写一个库、拿旧配置连上扩容后的库，都会在启动时失败，而不是悄悄把订单写到找不到的地方。`shard_meta` 只由迁移（首次）和扩容工具改。

映射本身不需要变成显式的表（2.2 末尾曾这样预告）。搬迁中的 slot 用下面的围栏表示成“暂时不可用”，不存在“一部分 slot 按旧规则、一部分按新规则”的中间状态。

### 5.6 切换的核心：改表名做围栏

切换时要保证一件事：**任何时刻，一个 slot 只有一个库接受写入。** 危险在于路由的切换不是瞬时的。order 重启需要时间；以后有多个实例时，滚动升级期间新旧两种路由并存，旧实例会把 slot 2 的订单继续写进库 0，新实例已经在写库 2，同一个订单在两边各有一个版本。

做法是在旧主库上把要搬走的表改名：

```sql
RENAME TABLE orders_2          TO moved_orders_2,
             order_items_2     TO moved_order_items_2,
             payment_results_2 TO moved_payment_results_2,
             orders_6          TO moved_orders_6, ...;
```

- 一条 `RENAME TABLE` 对所有表是原子的，只改元数据，和表多大没有关系。
- 它要拿元数据锁，会等这些表上正在进行的事务结束。所以这条语句提交的那一刻是一个精确的分界：之前的写入全部在它前面，之后任何按旧路由来的读写都得到“表不存在”（错误 1146），整个事务回滚，包括同一个事务里写 outbox 的那一行。
- 围栏在数据库里，不依赖每个应用实例都及时拿到新配置。旧实例只会报错，不会写错地方。
- 长事务会让改名一直等，并且把后面所有访问这些表的语句堵在它后面。执行前设 `lock_wait_timeout`（几秒），超时就放弃重试，不能无限等。

改名本身也会复制到新从库。新从库执行到这条改名对应的 GTID，就拥有了围栏之前的全部数据。

### 5.7 演练的步骤

工具是一个脚本 `scripts/expand.sh`，每个阶段一个子命令（`prepare`、`check`、`fence`、`wait`、`promote`、`replicas`、`verify`、`cleanup`，以及 `unfence`、`rollback`、`status`、`env`），可以单独重跑、检查中间状态。`cutover` 把 `fence`、`wait`、`promote` 连起来做，并在等待超出预算时自动撤掉围栏。compose 里用一个 profile 增加 4 个容器（两个新主库、各带一个从库），平时不启动。本机 32 GB 内存，order 的实例实测每个约 220 MB，够用。

1. **准备（`prepare`）**。启动 `mysql-order-2`、`mysql-order-3`，用 CLONE 插件从旧主库拷一份数据（实例是空的，CLONE 比导出导入快，而且 GTID 状态一起带过来），然后作为旧主库的从库开始复制，开 `super_read_only`。可以提前很久做，对线上没有影响。CLONE 插件在官方镜像里是否可用，动工时第一件事验证；不可用就退回 `mysqldump --single-transaction --source-data` 加 `gtid_purged`。
2. **切换前检查**。新从库的复制延迟接近 0；没有长事务；两个旧库的行数、`shard_meta` 和预期一致。
3. **立围栏（`cutover` 的第一步）**。在两个旧主库上各执行一次 5.6 的改名，记下执行后的 `@@gtid_executed`。从这一刻起，slot 2、3、6、7 不可读写，slot 0、1、4、5 不受影响。
4. **等三件事**：
   - 新从库执行到第 3 步记下的 GTID（`WAIT_FOR_EXECUTED_GTID_SET`，带超时）。
   - 旧库的 outbox 里，围栏之前写下的行都已发布。这些事件必须先由旧库的中继发完，否则同一个订单的事件会由新旧两个中继各发一部分，顺序没有保证。outbox 是每个库一张，没搬走的 slot 还在不停地写，所以不能等“没有未发布的行”（有流量时永远等不到）：围栏之后立刻记下 `MAX(id)` 作为水位，只等不超过水位的行发完。
   - 旧的两个 CDC 源的位点越过第 3 步的 GTID。原因见 5.8。
5. **提升**。在新实例上：`STOP REPLICA`、`RESET REPLICA ALL`、关 `super_read_only`；建库 `order_db_2`，把 `order_db_0.moved_orders_2` 等改名到 `order_db_2.orders_2`（同一个实例内跨库改名也只改元数据）；写 `shard_meta`（2 号库，共 4 个库，slot 2、6）；给 `cdc` 账号补上新库名的 `SELECT` 权限（拷贝来的授权只认旧库名）。旧库的 `shard_meta` 改成“共 4 个库”。新主库的从库不在这一步建：CLONE 要重启接收方，每个要 5 到 10 秒，放进窗口会把它拖长一倍。路由切完之后再用 `replicas` 子命令建。
6. **切路由**。用 4 个主库的 DSN 重启 order，先不带从库（读模式 `primary`）；新主库的从库建好后再带上 4 个从库重启一次，CDC 同时增加两个源 `order-2`、`order-3`。order 启动时的迁移在 `order_db_2` 上发现没有 goose 的版本表，会把所有迁移重跑一遍：建表是 `IF NOT EXISTS`，加列加索引先查后做，都会跳过，只新建一张空的 `outbox`。迁移可重入在这里是必须的，不是锦上添花。新库的中继叫 `order-2`、`order-3`。
7. **验证（`verify`）**。搬走的每张表在新旧两边一致。旧库的 `moved_*` 从围栏起不再变，但新库的表在切路由之后会继续被写，直接比行数和 `CHECKSUM TABLE` 只在切路由之前成立，而在窗口里做整表校验又会把窗口拖长。所以只比“围栏之后没有动过的行”，两边用同一个条件：订单表先在新库上取出围栏之后更新过的订单号，两边都排除；明细和支付结果写入后不再改，两边都只取创建时间早于围栏时刻的行。然后比较行数和行摘要的聚合值。被排除的行数要打印出来，它应当和切换后的流量相称。这样验证可以在流量恢复之后从容地做。另外`test/load verify` 通过；`seed-report` 显示 4 个库各有两个 slot。
8. **清理（`cleanup`）**，验证通过后才做，不可回退。旧库删除 `moved_*`；新实例删除整个 `order_db_0`（它带着 slot 0、4 的一份拷贝和一张旧 outbox）。表是独立表空间，`DROP` 后磁盘空间立刻归还；大表的 `DROP` 在线上会造成短暂的 I/O 抖动，这里只记录耗时。

**回退。** 第 6 步之前随时可以回退：在旧主库上把表名改回去，新实例丢弃。第 6 步之后新库上有了新的写入，旧库没有，改回表名会丢数据，只能向前修。真实系统里想保留回退的能力，要在切换后立刻建立反向复制（旧库作为新库的从库），本项目不做，写进考点。

**不可用窗口。** 第 3 步到第 6 步完成之间，被搬的 4 个 slot 不可用，预期是几秒到十几秒，演练时量出来。这期间：

- 已受理的订单在 Kafka 里排队，落库失败后重试，路由切换后落到新库。这是 1b 异步下单的结构带来的好处：削峰的队列顺便吸收了切换的停顿。前提是落库的消费者把“表不存在”当作可重试的错误，而不是毒消息，也不能把订单置为失败。读代码确认的结果见下面“窗口的时间预算”。
- 取消走 gRPC，这段时间返回错误，由调用方重试。支付结果走 Kafka（`payment.events`），同样靠消费者重试。
- 读：终态订单在缓存里的仍然读得到，其余返回 503。
- 背压和回收：排队时间变长，要确认窗口远小于回收的宽限期，否则已受理的订单会被当成孤儿回收（1b 的 ADR-0011）。

**窗口的时间预算（2026-11-14 读代码确认）。** `kafkax` 的消费者对普通错误原地重试，到 `MaxAttempts` 次后把消息送进死信，分区继续往下走。“表不存在”是普通错误，会重试，但重试有上限：

- 下单消息（`order.submit`）：10 次，退避合计约 21 秒。超过后消息进死信，订单最后由回收任务置为失败。数据一致，但用户的订单没了。（这是 1c 当时的状态。1d 步骤四之后落库的消费者对普通错误不设重试上限，分区停住等库恢复，见 ADR-0021；围栏窗口仍然按这里的预算控制在 15 秒以内。）
- 支付结果（`payment.events`）：原来是默认的 5 次，合计约 1.5 秒。超过后消息进死信，而这条消息是订单变成已支付的唯一途径，没有任务会重发（1b 设计文档里记过的缺口）。钱收了，订单却会超时关闭。**这不只是扩容的问题**：订单库任何超过 1.5 秒的不可用（比如以后的主从切换）都会触发。已改为无限重试，分区停住等库恢复；消息本身有问题的仍由 handler 标成 `Permanent` 直接进死信。
- 延迟关单消息：10 次约 20 秒，超过后由 sweeper 兜底，不受影响。

所以围栏窗口必须明显短于 21 秒。`expand.sh` 给第 3 步到第 5 步设一个总预算（默认 15 秒），第 4 步的等待超出预算就自动回退：把表名改回去，新实例保持从库身份继续追，稍后可以重试。回退在第 5 步之前始终是安全的。

**CDC 的两点确认。** 规则按表名整体匹配（`^orders_(\d+)$`），`moved_orders_2` 不匹配，被忽略；DDL 事件只当作事务边界。CDC 的位点存在 Kafka 里，给 cdc 的二进制加了 `-print-checkpoint <流水线名>`，打印已确认的 GTID 集合；第 4 步用 MySQL 的 `GTID_SUBSET(围栏的集合, 位点的集合)` 判断旧源是否已经越过围栏。

演练时用 `test/load` 以每秒几十单的速率持续下单，结束后对账，并统计窗口内的错误数和最长的下单耗时。

### 5.8 扩容对 CDC 和索引表的影响

- 旧源（`order-0`、`order-1`）会读到改名的 DDL，之后再也读不到 slot 2、6 的行事件。`moved_orders_2` 不匹配它订阅的表名，后面的 `DROP` 也一样，应当被忽略。CDC 对不认识的表和 DDL 事件的处理，动工时先读代码确认。
- 新源（`order-2`、`order-3`）没有位点，第一次启动做全量加增量（4.7），把 slot 2、6 的所有行重新发一遍。索引表靠行版本号去重（4.6），重发的行版本没有变高，全部被跳过。
- **行版本号放在行上，在这里起了作用。** 订单从库 0 搬到库 2，binlog 换了一份，GTID 的来源也换了。如果版本号是从日志位置派生的，换库之后新旧版本没法比较。放在行上的版本号跟着数据走，搬到哪里都连续。
- **为什么第 4 步要等旧 CDC 源追上。** 变更的 topic 是按订单号压缩的，压缩保留的是每个键位置最靠后的那条消息，不是版本最高的那条。如果旧源还没发完围栏之前的变更，新源就开始发更新的版本，topic 里就可能出现“新版本在前、旧版本在后”。索引表的消费者会正确地丢掉旧版本，但压缩之后留下来的是旧版本，以后从头重放 topic 会得到错的结果。让旧源先发完再放开新库的写入，就不会出现这种顺序。
- 索引表本身不扩容，它的分片键是商家，和订单库的布局无关。

### 5.9 测试与实现顺序

1. 主线（Fable）：`pkg/sharding` 的布局改动、`shard_meta` 的表结构和启动校验、00003 迁移（索引）。这些是共享部分，先串行完成。
2. 并行：
   - 用户列表（规范、gateway、order 的查询）：Opus 实现，Fable 评审。
   - `seed` 和 `seed-report`：Opus 或 Sonnet，只动 `test/load`。
   - compose 的扩容 profile 和 `scripts/expand.sh`：Sonnet 写，围栏、提升、清理这几段由 Fable 逐行评审。
3. Fable：确认并修正“表不存在”时落库消费者、gRPC 接口、CDC 的行为，补集成测试。
4. 灌数、出报告；在灌好的数据上做扩容演练；结果写回本节。

测试：

- `pkg/sharding`：库数为 1、2、4、8 时映射正确；从 2 到 4，每个旧库恰好搬走一半 slot，且只搬给一个新库。
- order 集成测试：`shard_meta` 不符时拒绝启动（序号错、总数错、空库正常初始化）；某个 slot 的表被改名后，落库消息被重试而不是丢弃，其他 slot 不受影响，表名改回后积压的消息落库成功。

- 扩容演练不进 CI（要 8 个 MySQL 实例），由 `make expand-drill` 在本机跑，结果记在文档里。CI 和 e2e 继续用 2 个库。

### 5.10 主人确认过的决定（2026-11-14）

1. **订单号的 Epoch 提前到 2020-01-01**，本机开发库清空重建（5.3 的办法 A）。
2. **切换用改表名做围栏**，接受被搬的 slot 有几秒的不可用（5.6、5.7）。

### 5.11 结果（2026-11-14）

**造数**

- 500 万订单、1000 万条明细，时间从 2020-01-01 到 2026-11-13，直接写两个主库，用时 2 分 57 秒，平均 2.8 万单/秒。开头是 8.6 万单/秒，表超过缓冲池之后降到 2 万多。
- 每个 slot 的订单表约 100 MB 数据加 80 MB 索引，明细表约 70 MB；扩容前每个库（4 个 slot）约 1 GB。
- 分片均匀度：订单行数最多的 slot 与最少的之比是 1.22，两个库之比 1.01。用户按 Zipf 分布，最重的用户有 5.4 万单（占 1%），被 8 个 slot 稀释之后影响不大。
- **商家索引追得很慢。** CDC 这一侧没有问题：500 万行的变更在灌数期间就全部发进了 Kafka；扩容后两个新源做全量，260 万行用了约 20 秒。慢的是索引的消费者：逐条写库、4 个分区串行，只有约 2000 行/秒，500 万行要 40 分钟以上。演练结束时还积压约 547 万条，约一个小时后才追平，商家索引这一半的报告是追平之后补量的（见下面“商家索引”一段）。消费者改成按批写是 1d 的事，和订单落库的吞吐问题是同一类。

**查询延迟**（2 个库时量的，每类 2000 次，随机参数）

| 查询 | p50 | p99 | 最大 |
|---|---|---|---|
| 按订单号查一行 | 0.23 ms | 0.46 ms | 0.98 ms |
| 用户列表第一页 | 0.34 ms | 4.4 ms | 21.7 ms |
| 用户列表带状态筛选 | 0.48 ms | 15.3 ms | 56.8 ms |
| 重度用户第 500 页（游标） | 0.21 ms | 1.0 ms | 6.8 ms |

每条查询的 `EXPLAIN` 都走预期的索引（主键或 `idx_orders_user`），列表是反向索引扫描，没有排序。带状态筛选的尾延迟明显更高：它在用户的索引范围里逐行回表过滤，要找的状态少见时回表的行多，又赶上页不在缓冲池里。5.2 里“不为状态另建索引”的决定在这个数据量下还成立，但代价是看得见的。`EXPLAIN` 的 `rows` 对重度用户没有参考价值（`ref` 访问给的是索引的平均基数，5 万单的用户也显示 7 行），“扫描行数与页大小同阶”要看实测延迟，不能看 `EXPLAIN`。

**商家索引**（追平后补量，索引里共 490.8 万行：创建失败的订单没有商家，不进索引）

| slot | 行数 | 数据 | 索引 |
|---|---|---|---|
| 0 | 57.7 万 | 100 MB | 24 MB |
| 1 | 119.3 万 | 200 MB | 49 MB |
| 2 | 119.1 万 | 203 MB | 47 MB |
| 3 | 194.7 万 | 321 MB | 79 MB |

- 最多的 slot 是最少的 3.37 倍，订单分片那边是 1.22 倍。原因和预期的一样：最大的商家一家就有 136 万单，占全部订单的 28%，独占 slot 3 的七成。按商家分片时，一个商家的数据不可拆，再怎么加 slot 也稀释不了它，只能把它单独放一个库，或者在商家之下再按时间拆。这里不解决。
- 查询本身不受影响：商家列表第一页 p50 0.21 ms、p99 0.29 ms；最大的商家翻到第 500 页（游标）p50 0.21 ms、p99 0.31 ms。都是主键 `(merchant_id, order_id)` 上的反向范围扫描，延迟和这个商家有多少订单无关。倾斜的代价在容量和迁移上，不在单次查询上。

**偏移量对游标**（第 500 页，每页 20 条）

| 场景 | 偏移量 p50 | 游标 p50 | 偏移量取回的行 | 游标取回的行 |
|---|---|---|---|---|
| 单个分片内，一个重度用户 | 5.2 ms | 0.37 ms | 20 | 20 |
| 8 个 slot 散发加归并 | 7.6 ms | 0.64 ms | 80000 | 160 |

单分片内偏移量慢 14 倍，是数据库自己扫过并丢掉前 9980 行的代价。散发时偏移量要从每个分片取回 1 万行，共 8 万行，只为显示 20 行；游标每个分片只取 20 行。页越深差距越大，游标的代价不随页码变化。

**扩容演练**

在 500 万单的数据上，压测工具以 20 个并发持续下单 150 秒（约 55 单/秒，一半支付、一半取消），中途做切换。

| 阶段 | 用时 |
|---|---|
| `prepare`：两个新实例各 CLONE 约 1 GB 并开始复制 | 28 秒 |
| `check`：行数比对等 | 约 30 秒 |
| 立围栏到新主库可写（数据库层面的窗口） | 7.5 秒 |
| 立围栏到 order 按 4 库路由恢复服务 | 9.3 秒 |
| `replicas`：给两个新主库各建一个从库 | 36 秒 |
| `cleanup`：每条 `DROP TABLE` | 约 0.1 秒 |

- 窗口里大部分时间花在等待的三项检查上（每项都要起一次容器内的客户端），真正的改名、提升、跨库改名都是毫秒级。order 重启只用了 0.3 秒。
- 期间受理的 8181 个订单全部落库，没有一个进死信；落库延迟 p99 是 1.8 秒，最长 8.5 秒（正好是在窗口里排队的那些）。轮询订单状态有 1289 次返回错误（被搬的 slot 上的读），压测工具重试后都拿到了结果。
- 对账（`load verify`，19 项）通过：4096 个已支付订单对应 4096 笔支付，库存和闸门平衡，死信为空。
- 搬走的 12 张表在新旧两边一致：每张订单表比较了 59 万到 68 万行，排除了围栏之后变动过的 600 多行。
- 切换后用 `ORDER_DBS=4 make run` 带 4 个从库、4 个 CDC 源重启，各服务没有 ERROR 日志。

**过程中发现并修掉的**

1. **支付结果的消费者只重试约 1.5 秒就进死信**（5.7），已改为无限重试。这是这一步最重要的发现，和扩容无关的订单库抖动同样会触发。
2. **第一版校验在流量恢复之后会误报。** 原来比行数和 `CHECKSUM TABLE`，新库一有写入就不等。改成只比围栏之后没动过的行（5.7 第 7 步）。改完后又报了三张明细表不一致，查明还是校验条件的问题：明细的 `created_at` 取的是订单的受理时间，围栏之前受理、切换之后才落库的订单，明细看起来是“围栏之前”的。明细改成和订单表共用同一份排除名单后通过。教训是校验条件必须建立在“这一列到底什么时候写、写的是什么”之上，不能看列名猜。
3. **等待 outbox 清空在有流量时永远等不到**，改成按水位等（5.7 第 4 步）。
4. **`cdc` 账号对新库名没有权限**，提升时补授权。
5. **迁移的续跑测试**假设只有两个版本，加了 00003 之后 goose 报“出现了比库里版本号更低的未执行迁移”。测试改成把之后的版本记录一起去掉。
6. 本机 MySQL 9.7 的 `explain_format` 是 `TREE`，没有分开的 `key` 列，测试里的 `EXPLAIN` 要写成 `EXPLAIN FORMAT=TRADITIONAL`。

**已知的局限，没有做**

- 造数工具的进度表（`seed_progress`）留在原来的库里，不跟着 slot 走，库数也算进了参数指纹。扩容之后不能再用原来的参数续灌（会被拒绝，不会写坏数据）。
- 两个旧库的围栏是先后立的，不是同一时刻。各自的 GTID 和水位分别记录，不影响正确性。
- `check` 要 30 秒，主要是在大表上数行数；它不在窗口里。
- CLONE 和复制是实例级的，新实例会带上旧实例里所有的库（包括 `e2e_*` 之类）。脚本只处理当前前缀的库，其余的拷贝留在新实例上。
- 多个 order 实例滚动切换没有验证（阶段 2）。
- CI 和 e2e 仍然只跑 2 个库；4 个库的布局只有本机演练和单元测试覆盖。

## 6. 步骤五：冷热分离与归档

状态：主人已确认（2026-11-14）。决定和备选方案见 ADR-0016。主人确认的四处：按订单号里的时间划分冷热（6.2）、冷库用压缩表加按年分区（6.5）、用户列表冷热归并且接口不变（6.6）、商家索引保留归档订单的行（6.7）。

目标是阶段计划里的验收项：归档后冷热数据总量与归档前一致，冷订单仍可查询。

### 6.1 问题和整体结构

订单表只增不删。本机造的 500 万单里，下单超过 90 天的约 480 万（每个 slot 约 96%），它们都已是终态，几乎没人再查，却占着热库的缓冲池、备份时间和扩容时要搬的数据量（步骤四的 CLONE 搬的大部分是它们）。归档是把它们搬到一个便宜的地方，热库只留近期的。

```
                         ┌── 热：order_db_0..N（按用户分片，主从）
order 服务 ── 读写 ──────┤
          └─ 只读 ───────┴── 冷：order_archive_db（一个库，压缩，按时间分区）
                                   ↑
archiver（一次性任务）：热库读 → 写冷库 → 校验 → 删热库
```

- **冷库**：独立的 DSN（`ARCHIVE_DSN`）。本机就放在现有的 `mysql` 实例上，库名 `order_archive_db`，不再多起一个容器。
- **archiver**：order 模块里的另一个可执行文件（`services/order/cmd/archiver`），跑完就退出。它和 order 服务共用 `store` 和 `sharding`，不放进服务进程：它是批处理，要限速、要能随时停，生命周期和在线服务不同，以后在 K8s 上是 CronJob。
- **order 服务**：多一条只读的冷库路径。不配 `ARCHIVE_DSN` 时行为和现在完全一样。

### 6.2 冷热怎么划分

**终态，并且订单号里的时间早于截止点（默认 90 天前）。**

- 终态是 `PAID`、`CANCELLED`、`CLOSED`、`FAILED`。终态订单的行不会再变（5 条更新语句都带非终态的前置条件）。
- 时间用订单号里的受理时间，不用 `updated_at`（完结时间）。本系统里订单从受理到终态最多隔一个支付时限，两者差几分钟；换来的是**只看订单号就知道它可能在哪**，读路径不用查任何元数据。扫描也因此是主键范围扫描（`order_id < 截止点对应的订单号`），不需要时间索引。
- 早于截止点但不是终态的订单（卡住的）留在热库，不归档。这种订单应该极少，archiver 报告它们的数量。

阶段计划里写的是“完结超过 3 个月”。按完结时间更贴近业务（有退款、售后的系统里，完结可能比下单晚几个月），代价是订单号不再能决定冷热，要么读路径先查热再查冷（对每个不存在的订单号都多一次冷库查询），要么维护一个水位。本系统没有会让完结时间远离下单时间的流程，所以建议按订单号。

**两个时间常量，保证读和归档对“哪些订单可能在冷库”的看法一致：**

- `MinHotAge = 30 天`，编译进代码的常量。读路径认为：订单号比它新的订单**一定不在冷库**。
- archiver 的 `-older-than` 默认 90 天，小于 `MinHotAge + 1 天` 时拒绝运行。多出的一天吸收时钟偏差。

常量而不是配置，是因为这两个数配反了的后果是“订单查不到”，和 ADR-0015 里库数配错是同一类问题；这里用不着一张元数据表，写死就行。

### 6.3 归档一批订单：先写冷，校验，再删热

冷热在两个库上，没有跨库事务（工程规范：不用 XA）。靠顺序和幂等：

1. **读**。在热库主库上按主键范围读一批终态订单（默认 500 个），连同它们的明细和支付结果记录。普通的快照读，不加锁。对每个订单算一个摘要（三张表的全部列，规范化后哈希）。
2. **写冷库**。一个事务里把三张表的行 upsert 进去（`INSERT ... ON DUPLICATE KEY UPDATE`，整行覆盖）。重复执行结果相同。
3. **校验冷库**。把刚写的行从冷库读回来，按同样的方式算摘要，和第 1 步的比。这一步验证的是“冷库里存下来的和读出来的一样”（字符集、截断、列对应关系）。
4. **删热库**。一个事务（`READ COMMITTED`）里：
   - `SELECT ... FROM orders_N WHERE order_id IN (这一批) FOR UPDATE`，按主键顺序加锁；
   - 在锁里重读这些订单的三张表，再算一次摘要；
   - 摘要和第 1 步相同的订单：删三张表的行。不同的或已经不是终态的（不应发生）：跳过，下一轮重新处理；
   - 提交。

**为什么第 4 步要在锁里重读。** 终态订单的 `orders` 行不变，但它的 `payment_results` 还可能增加：订单取消之后才到的支付成功结果，会插入一条“要求退款”的记录。这条插入不改 `orders` 行，行版本号不变，只比版本号发现不了。处理支付结果的事务第一步就是锁订单行（`LockOrder`），所以订单行锁就是这个订单三张表的互斥锁：archiver 拿到锁之后看到的内容，在它提交之前不会再变。锁里的摘要等于第 1 步的摘要，而第 1 步的摘要等于冷库的内容，所以删的那一刻热和冷相同。

**崩溃在任何一步之间**：第 2 步之后崩，订单在冷热两边各有一份，内容相同；重跑时再 upsert 一次、再删。不会出现两边都没有。

**死锁**。archiver 先一次拿齐这一批的订单行锁，再碰子表；处理支付结果的事务只锁一个订单行。属于这一批的订单，对方卡在第一步，手里什么都没有；不属于这一批的，archiver 不等它。用 `READ COMMITTED` 是为了删子表时不留间隙锁，免得挡住相邻订单的支付结果插入。

**不变量**（测试围绕它们写）：

1. 任何时刻，一个订单在热库、在冷库、或两边都有；不会两边都没有。两边都有时以热库为准：冷库那份的订单行与热库相同，但可能少了写冷之后才到的支付结果记录（见 6.13）。
2. 数据只从热到冷，不回流。冷库里的订单不再改。
3. 冷库里只有终态订单，订单号都早于 `now - MinHotAge`。
4. 订单号早于 `now - MinHotAge` 的订单不会被插入热库（见 6.6）。

### 6.4 任务的形态：分批、限速、可中断

- 逐 slot 处理，同一个库上的 slot 串行，不同的库并行。
- **不持久化进度。** 归档过的行已经从热库删掉，重跑时同样的扫描条件自然只看到剩下的。一次运行内部在内存里记着游标（上一批的最大订单号），避免反复扫过删除后还没被清理的记录。
- **限速有两层**：固定的速率上限（`-rate`，订单/秒）；每批删除之后等这个库的从库执行到主库当前的 GTID 再做下一批（复用步骤二的 `WaitReplica`），等超时就放慢。大批量删除最先压垮的是复制，这是拿复制延迟做反馈。
- 收到停止信号时做完当前这一批再退出。
- 结束时输出汇总：每个 slot 扫了多少、搬了多少、跳过多少（非终态、摘要不符）、用时。
- `-dry-run` 只数不搬。

### 6.5 冷库的表

三张表，列和热表一一对应，另加 `archived_at`。不按用户分片，一个库里一套：

```sql
CREATE TABLE orders_archive (
    ...与 orders_N 相同的列...,
    archived_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (order_id),
    KEY idx_user (user_id, order_id)
) ENGINE = InnoDB ROW_FORMAT = COMPRESSED KEY_BLOCK_SIZE = 8
PARTITION BY RANGE (order_id) (
    PARTITION p2020 VALUES LESS THAN (<2021-01-01 对应的订单号>),
    ...每年一个...
    PARTITION pmax  VALUES LESS THAN MAXVALUE
);
```

- **按订单号做 RANGE 分区，每年一个。** 订单号的高位是时间，所以按订单号分区就是按时间分区，而且分区键就是主键，不用为了分区把时间列塞进主键。好处在数据的最后一段生命周期：过了保存期限的整年数据用 `DROP PARTITION` 删掉，是元数据操作，不像热库那样逐行删再回收空间。按订单号点查会裁剪到一个分区；用户列表带游标时裁掉游标之后的分区（本机已验证这两条的执行计划，也验证了分区表可以用压缩行格式）。
- **不按用户分片。** 冷数据没有写入压力，查询量很小，分片解决的问题它没有。容量不够时按时间加库（新的年份放新的实例），不是按用户哈希。
- **少了两个索引**：`(user_id, idempotency_key)` 唯一键和 `(status, expire_at)`。后者是后台任务扫非终态用的。前者见 6.6；另外分区表的唯一键必须包含分区键，它本来也建不了。
- `payment_results_archive` 的主键改成 `(order_id, payment_id)`，同样是分区键的要求。
- **压缩用 `ROW_FORMAT=COMPRESSED`**（页在缓冲池里压缩和未压缩各存一份，写入慢，读多一次解压）。另一种是透明页压缩（`COMPRESSION='zstd'`），依赖文件系统打洞，容器的卷上不一定成立，不用。压缩比实测后写进结果。
- 冷库的迁移是 order 模块里的第二套迁移文件，分区边界由模板从 `idgen.Epoch` 算出来。archiver 和 order 服务启动时都会执行（同一把迁移锁）。

备选是不分区的一张压缩表，或者照热库的样子按 slot 拆 8 张。见 ADR-0016。

### 6.6 冷库对各条路径的影响

**按订单号查（`GetOrder`）**：先查热库（现有的全部逻辑不变）；热库主库确认没有、并且订单号早于 `now - MinHotAge` 时，再查冷库。

顺序必须是先热后冷。数据从热流向冷，而且写冷在删热之前：先查热没查到，说明要么不存在、要么已经删了，而删之前冷库一定已经有了。反过来先查冷再查热，会在“还没写冷”时查冷、“已经删热”后查热，两边都落空，把一个存在的订单说成不存在。

订单号新于 `MinHotAge` 的查不到就直接返回不存在，不碰冷库。所以热订单的读路径没有任何额外开销，冷订单多一次热库的主键查询（约 0.2 毫秒）。

**按用户列表**：两边各按同样的条件（`user_id`、状态、`order_id < 游标`）取 n+1 条，按订单号归并、去重，取前 n 条。游标还是订单号，接口不变。先查热再查冷，理由同上；一个订单两边都有时留热库那条。

每次列表都查冷库就失去了分离的意义，所以加一条判断：**热库这一页之后还有订单，而且这一页最后一条的订单号新于 `MinHotAge`，就不查冷库**。冷库里的订单都比它旧，挤不进这一页；热库后面还有，“有没有下一页”也已经确定。热库刚好一页就用完时仍然要查冷库：冷库里有没有更旧的订单决定了有没有下一页。活跃用户的头几页只走热库；翻到 30 天以前、或者近期订单不满一页的用户，才会查冷库。

这样做是精确的，但有一个要看数据的问题：近 30 天下单不满一页的用户是多数，他们的第一页都会碰冷库。常见的产品做法是把它变成接口上的区分（默认只列近期订单，“更早的订单”单独请求），用不精确换冷库的清静。建议先做精确的归并，量一下有多大比例的列表请求落到冷库，再决定要不要加开关。

**幂等键**：归档后 `(user_id, idempotency_key)` 的唯一约束对这个订单不再起作用，同一个幂等键在 90 天后重放会创建新订单。也就是幂等的有效期有上限，等于热数据的保留期。写进接口文档。

**落库（不变量 4）**：`order.submitted` 的消费者遇到受理时间早于 `now - MinHotAge` 的消息直接丢弃（记错误日志并计数），不插入。否则一条被重放的陈年消息会在热库里重新插入一个已经归档的订单号：行版本号从 0 开始，状态是创建失败，而且先查热库的读路径会返回它，盖住冷库里真正的订单。4.13 留下的“删除后同主键重插”就这样解决：不处理它，禁止它。正常情况下受理到落库只隔几秒，背压把排队限制在约 25 秒。

**支付结果**：这是唯一涉及钱的改动。现在订单不存在而支付成功时答复“要求退款”。归档后，一条针对已归档订单的支付结果（重复投递，或消费组位移被重置后重放）会因为热库查不到订单、也查不到当初的处理记录，而对一个正常付清的订单要求退款。改成：热库没有、订单号早于 `MinHotAge` 时查冷库，

- 冷库有这条 `payment_id` 的处理记录：重复投递，和热库里的处理一样，什么都不做；
- 冷库有订单、没有这条记录：订单是终态，按和热库相同的规则得出答复（支付失败则接受；支付成功则要求退款，订单已不可支付），发答复事件，**不写记录**。冷库不接受在线写入；答复只取决于不会再变的冷数据，重放时得出同样的答复，支付服务以第一次答复为准；
- 冷库也没有：现有的“订单不存在”逻辑；
- 冷库查询失败：返回错误，消费者原地重试（支付结果已是无限重试）。宁可堵住也不猜。

不依赖“Kafka 的保留期比 30 天短”这类巧合。

**后台任务**（sweeper、关单、回收）只看非终态，和归档的数据不相交，不用改。**查询缓存**只缓存终态订单，内容不变，不受影响。

### 6.7 CDC 和商家索引

归档在热库上是 DELETE，binlog 里有，CDC 会发出 `op=DELETE`、带着删除前的整行（`before`）。4.13 留下两个问题，这里定下来：

**DELETE 在压缩的 topic 里保持是一条普通消息，不改成墓碑。** 约定：`orders` 表的 DELETE 表示“这一行离开了热库”，`before` 是它的最终映像。订单在业务上从不删除，只会归档，所以这个约定没有歧义。压缩之后每个归档订单留下的就是这条带最终映像的消息，新下游从头消费仍能拿到全部订单；改成墓碑的话，归档订单会从 topic 里消失，而 CDC 的全量只读热库，新下游就再也看不到它们了。

**商家索引保留归档订单的行。** 索引表是一份独立的数据，带着展示列，商家列表不回源，所以订单归档后商家照样能列出它；点进详情走 `GET /orders/{id}`，由 6.6 的路径去冷库取。orderindex 对 DELETE 的处理从“忽略”改成“用 `before` 做一次带版本号的 upsert”：平时它是空操作（索引里已经是这个版本），在索引从头重建时它就是这个订单唯一的来源。

索引表自己也会越来越大（最大的商家占 28%），它的冷热分离是另一件事，这一步不做。另一个选择是归档时把索引行也删掉，商家列表只显示热订单：索引小了，但商家端看不到三个月前的订单，要再给冷库建商家维度的查询。

**归档对索引消费者的冲击**：480 万条 DELETE 会排在在线变更前面，而索引的消费者只有约 2000 行/秒（5.11，改成按批写挂在 1d）。归档期间商家索引的延迟会升到几十分钟。这一步如实测量并写进结果，archiver 的限速是眼下唯一的旋钮。

对账（`load verify` 第 20 项）改成拿索引和“热加冷”比。

### 6.8 空间回收

DELETE 之后 InnoDB 把页标成可复用，文件不会变小，表里留下大量半空的页。归档完成后对每张热表做一次重建（`OPTIMIZE TABLE`，InnoDB 上等价于 `ALTER TABLE ... FORCE`，在线 DDL）：

- 重建期间表可读写，开始和结束各需要一次短暂的元数据锁；有长事务时会堵住，并堵住它后面的所有语句（和步骤四改表名是同一个问题）。
- 需要额外的磁盘空间放新表。
- DDL 在从库上重放时同样要重建一遍，期间这个从库的复制延迟上升。
- 做成 archiver 的一个显式子命令（`-reclaim`），逐表串行，不自动跟在归档后面。

量三组数：归档前、归档后未回收、回收后，各自的表大小和 5.11 那几类查询的延迟。

不用逐行删除的做法是把热表也按时间分区、过期整区卸掉。它要求一个分区里的行全部可以走，而“卡住的非终态订单”会钉住整个分区；按用户分片的 8 张表再各自分区，表的数量和迁移的复杂度也上去了。写进 ADR 的备选。

### 6.9 和扩容的关系

冷库不按 slot 组织，扩容不影响它。archiver 通过 `sharding.Router` 找热表，和 order 一样受 `shard_meta` 校验。归档和扩容不要同时做：扩容的围栏会让 archiver 的语句失败（它会报错退出，重跑即可），而归档产生的大量删除会拖慢新从库追平。

### 6.10 测试

- **archiver 的集成测试**（`-race`，真实的两个库）：搬完后热冷的行数守恒、内容逐行相同；每一步之后中断再重跑，结果相同；归档进行中并发地对同一批订单投递“取消之后才到的支付成功”，结束后每条处理记录恰好在热或冷的一边，没有丢；非终态和不够旧的订单不动。
- **读路径**：归档前后 `GetOrder` 返回相同的内容；用户列表在三种页上都对（全在热、跨越冷热、全在冷），翻完不重不漏；在“已写冷、未删热”的状态下列表不出现重复。
- **支付结果**：对已归档的已支付订单重放它的支付结果，不产生退款答复；对已归档的已取消订单投递一笔新的支付成功，答复要求退款，重放时答复相同。
- **落库**：受理时间早于 `MinHotAge` 的消息被丢弃，热库没有新行。
- **orderindex**：DELETE 的 `before` 被当作映像应用；版本不高于现有行时不改。
- **e2e**：直接往热库插入几个一年前的终态订单，运行 archiver，再经 gateway 按订单号和按用户列表查到它们。e2e 的环境配上 `ARCHIVE_DSN`。
- **对账**：`load verify` 加一项“冷热不相交（归档结束后）、冷库只有够旧的终态订单、每个冷订单的明细齐全”。

### 6.11 实现顺序

1. 主线（Fable）：冷库的迁移、`MinHotAge`、archiver 的核心（6.3）、落库的拒绝、支付结果的冷库路径。这些直接关系到订单会不会丢、钱会不会退错。
2. 并行：
   - 读路径（`GetOrder` 的回退、用户列表的归并），Opus，Fable 评审；
   - orderindex 对 DELETE 的处理，Opus；
   - compose、脚本、Makefile、e2e 环境、`load verify` 和 `seed-report` 的冷库部分，Sonnet。
3. 在本机 500 万单上跑一次，量 6.8 的三组数、压缩比、归档的吞吐、期间的复制延迟和索引延迟，结果写回本文。

### 6.12 不在这一步做的

- 用 Merkle 树校验冷热一致：工具在 1d 才有，到时把归档加进它的对账对象。这一步用逐批的摘要和事后的全量比对。
- 归档到对象存储（Parquet）：只在 ADR 里做书面对比。
- 冷库的保存期限和到期删除（`DROP PARTITION`）：表结构为它留好了，不实现任务。
- 把冷订单恢复回热库：不提供。它正是不变量 2 和 4 要禁止的方向。
- 归档的指标和告警：阶段 3。

### 6.13 实现中的发现（2026-11-14）

**不变量 1 原来写的是“两边都有且内容相同”，不对。** 一个订单写进冷库之后、删热之前来了一笔支付结果，删除时锁内的摘要对不上，这个订单被跳过、留在热库，冷库里留下一份少一条支付结果记录的旧拷贝，直到下一次运行重新写冷再删。期间读路径都先查热库，不受影响；表述改成了“两边都有时以热库为准”。也因此冷库的写入只做加法（upsert，不删冷库里多出的子表行）：热库的子表只增不改，加法足够，而“先删再插”在两个归档任务并发时会删掉另一个刚写进去的记录。

**上线顺序是硬约束：先给所有 order 实例配上 `ARCHIVE_DSN`，再第一次运行归档。** 没配冷库的实例收到已归档订单的支付结果时走的还是“订单不存在”：往热库写一条没有订单的支付结果记录，并对一个付清的订单要求退款。归档任务检查不到别的进程有没有配。订单的查询同理（查不到）。

**两个归档任务同时运行会误报。** A 读了热库的旧内容，B 搬走了带新支付结果的版本，A 读回冷库比对时摘要不同，报错停下。不丢数据，但没有必要。加了互斥：归档任务启动时在冷库上取一把 `GET_LOCK`（会话锁，进程崩溃时自动释放），拿不到就退出。正确性不依赖这把锁。

**“写子表之前必须先锁订单行”现在是 store 包的一条约定。** 校验后删除靠它成立。删除时逐表核对删掉的行数等于锁内读到的行数，对不上就回滚报错，这是兜底，不是保证。以后新增写 `payment_results` 或 `order_items` 的路径都要先 `LockOrder`。

**一批的上限是 2000 个订单，不是随便多大。** MySQL 一条预处理语句最多 65535 个占位符，订单行 15 列；多行 INSERT 另按 1000 行切开，因为一个订单的明细行数不受批大小限制。一批会同时持有这么多订单行锁，这些订单上的支付结果要等这一批提交。

**列出可归档订单的语句固定走主键。** 条件里有状态，优化器可能改选 `(status, expire_at)` 再排序；归档把表删空的过程中统计信息一直在变。

**归档删除用 `READ COMMITTED` 有两个作用**，设计里只写了一个（不留间隙锁）：另一个是让锁内的普通读看到最新提交的内容。在 `REPEATABLE READ` 下，拿到锁之后读子表用的可能还是拿锁之前的快照，锁内重读就失去了意义。它要求 binlog 是 ROW 格式（本项目是）。

**读路径的三个小问题，没有改：**

- 查占用排在查冷库之前。已归档的订单如果在 Redis 里还留着占用，会被答成 `CREATING`。这要求库存的消费者卡住 30 天以上。
- `GetOrder` 查冷库没有自己的时限，冷库挂起时一次对旧订单号的查询会占到调用方的 deadline。列表有 3 秒的时限。
- 冷库的表不存在时，错误文案是“订单分片暂时不可用”。

**对已归档订单调用取消**：已取消的返回成功（和热库里重复取消一样），其他终态返回 `ORDER_NOT_CANCELLABLE`。写路径不需要知道冷库，是读回订单时经过了同一个“先热后冷”的出口。

**用户列表在冷库上不带游标时会探查全部 11 个分区。** 二级索引是分区本地的，条件里没有订单号的范围就没法裁剪。带游标时裁掉游标之后的年份。点查只落在一个分区。

**CDC 的 topic 不再是可以随时重建的缓存。** 归档订单在 topic 里只剩那条 DELETE，而 CDC 的全量只读热库。topic 被删掉重建、保留策略配错，归档订单对新下游来说就消失了，只能从冷库另做一次全量。`cdc.order.orders` 的压缩保留现在是数据约束，不是调优选项。另外，CDC 的全量和归档同时进行时，同一行的 `READ` 可能排在它的 DELETE 之后成为这个 key 的最后一条：对按版本号比较的下游无害，但“最后一条是 DELETE 就表示已归档”不能当判断依据。

**索引消费者的 `stale` 计数在归档期间会大量增长**：每条归档的 DELETE 平时都是空操作，算作 stale。看重放或乱序的程度时要扣掉新加的 `archived` 计数。

**没有 `before` 的 DELETE 会让索引的消费停住**，和没有 `after` 的 INSERT 一样。CDC 拒绝不完整的行映像，所以这只在 CDC 有缺陷时出现；跳过的话，索引重建时这个订单会悄悄丢掉。

**`load verify` 的第 4 到 15 项只读热库**，会把已归档的真实流量订单当成不存在。压测造的订单不到 30 天，不会被归档，所以现在不影响；长期运行的环境里对账要先限定时间范围，或者像第 20 项那样读“热加冷”。

**从库等待超时后不会主动放慢。** 6.4 写的是“等超时就放慢”，实现是等满时限（默认 30 秒）就继续下一批：这一批已经为从库等了这么久，再加别的退避没有依据。

**这一步的并行任务仍然没有用 worktree**，原因同前：主线的共享改动没有提交。五个任务各自限定了目录，order 模块里的两个任务分别只动 `internal/store`、`internal/archive`、`cmd/archiver` 和 `internal/service`。

### 6.14 结果（2026-11-14）

`make lint test e2e` 通过。e2e 新增一个用例（`test/e2e/archive_test.go`）：往热库直接插入一年前的 5 个终态订单和 1 个待支付订单，再正常下一单，运行归档任务；5 个终态订单进了冷库、另外两个留在热库，经网关按订单号查到的内容与归档前相同，按用户列表用 `limit=2` 翻到底拿到全部 7 个订单；再运行一次结果不变。`make chaos` 这次没有跑。

下面是在本机 4 个订单库、500 万造数订单上实际归档一次量到的（原始输出在 `tmp/archive/`，不入库）。

**归档**（默认参数：截止点 90 天，每批 500，不限速，每批删除后等从库）

- 搬走 4,820,905 个订单、9,642,408 条明细，用时 8 分 8 秒，约 9900 单/秒（4 个库并行，每个库约 2500 单/秒）。跳过 0，早于截止点的非终态订单 0。
- **守恒**：归档前热库有订单 5,008,181、明细 10,009,030、支付结果 4,096；归档后热库 187,276 + 冷库 4,820,905，明细 366,622 + 9,642,408，支付结果 4,096 条都在热库（造数的订单没有支付结果记录，它们全部属于近期的真实流量）。三张表都对得上。
- **对账**：`load verify` 第 21 项通过（冷库非终态 0、太新 0、冷热重复 0、缺明细 0、冷热两边的孤儿行都是 0），480 万行用时 84 秒；第 20 项通过（8181 个真实流量订单与索引一致）。商家索引仍是 490.8 万行，归档没有让它少一行。
- 几分钟后再跑一次，只归档了 23 个订单：这几分钟里刚越过 90 天界线的。
- **复制延迟**：每 10 秒采样一次，四个从库最大 1 秒。等从库追上的反馈起了作用，固定限速没有用上。
- **商家索引的积压**：归档期间涨到 266 万条，归档结束后约 5 分钟追平。比 6.7 估计的“几十分钟”好：归档的 DELETE 在索引里是空操作，消费者处理它们的速度约 4500 条/秒，是真正写入时的两倍多。期间在线订单的索引延迟最长约 13 分钟。

**热库的大小**（四个库的数据目录合计）

| 时刻 | 磁盘上 | 说明 |
|---|---|---|
| 归档前 | 2273 MB | 500.8 万订单 |
| 归档后、回收前 | 2273 MB | 行删了 96%，文件一个字节没小 |
| 回收后 | 217 MB | `archiver -reclaim`，24 张表共 8.6 秒，单表最长 1.6 秒 |

`information_schema` 里的 `data_length + index_length` 在回收前就已经降到 549 MB：purge 把整段空出来的区还给了表空间内部，但不还给文件系统。只看这个数会以为空间已经回来了。重建之所以只要几秒，是因为表里只剩 4% 的行；从库上重放同样快，没有量到延迟。

**冷库的大小**

| | 订单表 | 明细表 | 数据目录 |
|---|---|---|---|
| 归档刚结束 | 816 MB 数据 + 92 MB 索引 | 481 MB | 1490 MB |
| 重建全部分区之后 | 477 MB + 96 MB | 255 MB | 906 MB |

- **归档刚结束时冷库几乎没有压缩效果**：订单表的数据部分每行 169 字节，和热库归档前一样。原因是插入顺序。8 个 slot 分在 4 个库上并行归档，每个 slot 都从 2020 年往后搬，冷库的主键在同一段范围里被几路交错着插入，页不断从中间分裂，留下大量半满的页；压缩页分裂的代价比普通页还高。把分区重建一遍（`ALTER TABLE ... REBUILD PARTITION`，两张表共 150 秒）之后小了 39%。
- 重建之后（只算数据，不算索引）：订单每行 104 字节（热库 169，压缩比 1.6），明细每行 27.8 字节（热库 56.6，压缩比 2.0）。订单压得差是因为行里有 32 字节的请求哈希和幂等键，都是随机内容。
- 同样的 482 万订单在热库里占约 2190 MB，在冷库里占 906 MB，是 41%。省下来的不只来自压缩：热表有三个二级索引共约 134 字节/行，冷表只留一个，约 20 字节/行。**去掉用不上的索引省的空间和压缩差不多。**
- 重建冷库分区现在是手工执行的，没有做进归档任务。日常的增量归档只往最新的一两个分区追加，问题小得多；第一次大批量归档之后应当重建一次。

**查询延迟**（每类 2000 次，随机参数；毫秒，p50 / p99）

| 查询 | 归档前 | 归档后、回收前 | 回收后 |
|---|---|---|---|
| 按订单号查一行 | 0.18 / 0.34 | 0.19 / 0.31 | 0.20 / 0.34 |
| 用户列表第一页 | 0.22 / 0.82 | 0.20 / 0.29 | 0.22 / 0.30 |
| 用户列表带状态筛选 | 0.45 / 4.73 | 0.21 / 0.67 | 0.23 / 0.74 |
| 重度用户第 500 页（游标） | 0.19 / 0.32 | 0.22 / 0.52 | 0.19 / 0.25 |

- 点查没有变化：主键查找的代价只和树高有关，500 万行和 19 万行的差别在测量误差之内。**归档不会让本来就走主键的查询变快。**
- 变化在尾部：列表的 p99 从 0.82 降到 0.30，带状态筛选的从 4.73 降到 0.7 左右。归档前每个实例的缓冲池是 64 MB、数据约 560 MB，尾延迟来自读盘和筛选时回表的行数；归档后数据比缓冲池小，筛选要扫的行也少了。
- 回收前后几乎一样：空洞多的表对这几类查询没有可见的影响，回收换来的是磁盘空间，不是延迟。
- 归档刚结束、索引还在追积压时量过一次，热库各类查询的 p50 都在 0.45 毫秒左右，是机器忙造成的，不是归档的结果。上表是索引追平之后量的。

**冷库的查询**（重建之后；毫秒，p50 / p99）

| 查询 | 延迟 | 落在的分区 |
|---|---|---|
| 按订单号查一行 | 0.22 / 0.45 | 1 个 |
| 用户列表第一页（无游标） | 1.35 / 2.21 | 全部 11 个 |
| 用户列表带游标的一页 | 0.19 / 1.34 | 游标所在年份及更早的 |

点查和热库一样快（冷库和 inventory、payment、商家索引共用一个实例，缓冲池 128 MB）。无游标的列表慢 6 倍，是在 11 个分区的本地索引上各探查一次再归并的代价；分区按年而不是按月，就是为了让这个数不太大。

**没有做的**

- 归档任务按全局时间顺序写冷库（先把所有 slot 的 2020 年搬完再搬 2021 年），或者归档后自动重建涉及的分区，来消掉上面的碎片。
- `GetOrder` 查冷库的时限、冷库不可用时的降级（和 1d 的熔断降级一起）。
- 把 CDC、orderindex、归档任务加进 `scripts/chaos.sh`：在归档进行时杀进程的验证现在只有集成测试里的中断重跑。
- 用户列表落到冷库的比例没有量：需要真实的访问分布，本机没有。造数的用户里，近 30 天下单不满一页的占绝大多数，按 6.6 的规则他们的第一页都会查冷库。
- 限速和等从库那条路径没有自动化测试（测试环境没有真的从库），只有这次实际运行。
- 冷库的保存期限和到期删除、Merkle 校验、Parquet：见 6.12。
