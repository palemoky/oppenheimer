## 1. 动工前查到的事实（2026-11-17）

### 1.4 已经知道的数和没有回答的问题

- **集群上落库只有约 200 单/秒**，是本机（686 到 870）的四分之一，三档并发下都是平的（设计文档 2c 第 13 节）。线索：最忙的是订单库 0 的从库，约 1 核。没有查。这是 3b 要回答的第一个问题。
- 受理在默认背压下约 365 单/秒（等于落库速度加一个队列的量），关背压约 2000 到 2500 单/秒，那时节点 CPU 88%。
- **405 请求/秒时 gateway、order 的 CPU 已经到 71% 到 75%**（2c 是约 810 请求/秒才到）。中间多了 Istio 的边车、全量的链路导出、15 秒一次的指标导出，没有拆开量。
- 一次 gateway 到 order 的调用 6.5 毫秒里有 2.7 毫秒在边车和网络上（低负载的平均值）。
- 每个请求约落 1.2 个 span（尾部采样后）和 1.4 KB 日志：2000 请求/秒压一小时，Tempo 约 1.5 GB、Loki 约 1.4 GB，和 etcd 在同一块 60 GB 的盘上。
- Tempo 在不采样压测时内存到过 1.55 Gi（上限 2 Gi）；Collector gateway 的内存和吞吐成正比（405 请求/秒时多 100 Mi，requests 512 Mi）。
- 订单读闸门的 16 个名额在突发下会满，答 `429 READ_BUSY`；要不要调大等“不那么整齐的流量”再定。
- HPA 的阈值（gateway 每副本 180、order 100 请求/秒）是用 CPU 反推的初值，等这里重定。

### 1.5 限流会挡住压测

长期运行的那一套开着默认的限流：**每个客户端地址 200 请求/秒**（桶 400）、每个用户下单 5 次/秒、查库存每个 SKU 500 次/秒。入口的 Envoy 把 Mac mini 的地址写进 `X-Forwarded-For`，gateway 只信它，所以从一台机器发压，超过 200 请求/秒的部分全部是 `429 RATE_LIMITED`。本机的 bench 和集群的 bench、chaos 都是把限流整个关掉的。怎么处理是第 2 节第 3 项。

### 1.6 版本

k6 的最新正式版是 **v2.4.0**（2026-11-12 发布；另有 1.8.x 的维护线，最新 v1.8.3）。主会话 2026-11-17 在 GitHub 的发布页核对过。k6 没有 LTS，按规范用最新的正式版。装的时候登记到 `versions.md`。

没有查证的（装的时候对着官方文档确认，不凭记忆写脚本）：2.x 里各个 executor 的名字和参数有没有变；指标输出到 Prometheus remote write 和 OTLP 两种方式在 2.4 里各自的稳定级别；直接跑 TypeScript 的支持程度。

另有一项不需要选、但要写明结论的（计划里从 1a 推迟过来的）：**要不要从 OpenAPI 规范生成客户端。建议不生成。**

- k6 这边：对外只有 8 个接口，手写一个 `api.js` 模块大约一百行。能用的生成器（openapi-generator 的 k6 模板）产出的是一份脚本骨架而不是可以复用的客户端，还要引入 Java 或 Node 的工具链。
- `test/e2e` 这边：手写的请求和响应结构是对规范的**第二次独立解读**。服务端是从规范生成的，如果测试的客户端也从同一份规范生成，规范写错（比如字段名拼错、类型写成字符串）时两边会一起错，测试照样通过；现在这样，规范和手写的结构不一致时 e2e 会失败。这个好处比少写几十行结构体重要。
- 代价是规范改了要手工跟着改两处（e2e 和 k6）。规范里的字段不多，可以接受。

主人 2026-11-17 确认不生成。以后改主意的话，Go 这边用已经在工具链里的 `oapi-codegen` 生成客户端，不引入新东西。

## 3. 设计

### 3.1 总体的样子

```
Mac mini                                   集群
┌──────────────────────┐   HTTP    ┌─────────┐   ┌─────────┐   ┌──────────────┐
│ k6（场景脚本）        │ ───────► │ 入口     │──►│ gateway │──►│ order 等服务  │
│  ├ 订单号清单（文件）  │          │ Envoy    │   └─────────┘   └──────────────┘
│  └ 汇总 JSON          │          └─────────┘
│                      │  指标（remote write）   ┌────────────┐
│                      │ ─────────────────────► │ Prometheus │──► Grafana
└──────────────────────┘                        └────────────┘
MacBook：发起（ssh mini 跑 k6）、灌数和清理、对账、抓 pprof、写记录
```

- 脚本在仓库的 `test/k6/`，一个场景一个文件，公共的部分（接口封装、用户和 SKU 的选法、阈值、运行号）在 `test/k6/lib/`。MacBook 上 `make k6 SCENARIO=<名字>` 把脚本同步到 Mac mini 并在那里执行，结果拉回 `tmp/k6/<运行号>/`。
- 每次运行有一个运行号（时间加场景名），它出现在幂等键前缀、`X-Load-Run` 头、k6 指标的标签、结果目录名里，用它把客户端的数、服务端的日志和链路、写下的记录串起来。
- 开跑前的检查做成脚本（`scripts/cluster/loadtest.sh preflight`）：集群没有不正常的 Pod、消费延迟为 0、没有别的压测或 e2e 在跑、server 的盘够、限流和副本数是这一轮要的状态。不满足就不跑。

### 3.2 一轮压测的固定流程

1. 预检（上面那个脚本）。
2. 记下开始时刻和这一轮的条件（提交号、镜像 tag、副本数、限流、采样、数据量），写进结果目录。
3. 预热 1 到 2 分钟（不计入结果）：让连接池建满、缓存有内容、Go 的堆大小稳定下来。
4. 发压。期间在约定的时刻抓 pprof（CPU 30 秒、堆、goroutine），存进结果目录。
5. 停压，等系统静止（`load wait-quiet`：outbox 清空、消费延迟为 0、没有未完成的订单）。
6. 对账（`load verify` 对订单号清单，`make cluster-recon` 式的全量比对）。**对账不过的一轮，性能数字作废。**
7. 从 Prometheus 把这一轮的服务端数据取出来存档（各服务的 RED、CPU、MySQL、Redis、Kafka 的几条关键查询），和 k6 的汇总放在一起。大盘会过期，记录要自己带着数。

### 3.3 怎么判断“拐点”

阶梯加压：每一档保持 3 分钟，到达速率按上一档的 1.25 倍递增。出现下面任何一条，这一档就算过了拐点，拐点记作上一档：

- 受理（`POST /orders`）的 p99 超过 200 毫秒（`GOALS.md` 的目标）；
- 5xx 加超时超过 0.1%；
- `429 BACKLOGGED` 持续出现（背压在工作，说明落库跟不上了）；
- 消费延迟或 outbox 的积压在这一档里单调上涨，停不下来；
- k6 开始丢迭代（发压机自己不够了，这一档的数不可信，要先解决发压一侧）。

受理和落库分开找拐点：1b 的结构决定了受理的拐点远高于落库的（1.4 节），只报一个数会误导。

### 3.4 定位瓶颈的办法

拐点那一档，按 USE（每种资源的使用率、饱和度、错误）从外往里看，3a 的大盘和工具都已经有了：

| 看什么 | 从哪看 |
|---|---|
| 节点和容器的 CPU、节流（throttling）、内存 | 集群资源大盘；`container_cpu_cfs_throttled_periods_total` |
| 每一跳的耗时，哪一跳先变长 | 单服务大盘的 gRPC 耗时；网格大盘（边车上的耗时）；出问题的链路（尾部采样留着慢的） |
| 连接池有没有在排队 | MySQL、Redis 连接池的等待次数和等待时间 |
| MySQL：提交耗时、行锁等待、从库回放、慢查询 | 中间件大盘；`performance_schema`；慢查询日志 |
| Kafka：生产和消费的速率、延迟、每个分区是否均匀 | 中间件大盘 |
| Go：CPU 花在哪、GC 占比、锁竞争、goroutine 数 | pprof（CPU、堆、mutex、block）、运行时指标 |
| 磁盘：虚拟机盘的 fsync 耗时、IO 等待 | node-exporter；etcd 的 fsync 作为同一块盘的旁证 |

**三轮“压测、定位、优化、再压测”不预先定题目**，每一轮修的是上一轮量出来的第一个瓶颈。按现有的线索，候选是：落库这条链路（提交刷盘、`SUBMIT_CONCURRENCY`、从库单线程回放）、边车和链路导出的 CPU、读闸门的名额、连接池大小、HPA 的阈值。每一轮一份记录，放在 `docs/notes/3b-rounds/`：现象、证据（图和 pprof 的结论）、假设、改了什么、改完的数、没有解释的。涉及订单、库存、资金路径的改动由 Fable 写或评审。

### 3.5 长稳测试

拐点的 50% 上下，混合读写场景，4 小时。看的是斜率不是数值：每个服务的堆、goroutine 数、文件描述符、连接数在这 4 小时里是平的还是在涨；Redis 的键数和内存；Kafka 的磁盘；MySQL 的 undo 和临时表。结束后对账。4 小时大约 15 到 30 GB 的日志和链路，所以采样降到 10%（第 2 节第 8 项），开跑前清一次监控的盘或者确认余量。

### 3.6 容量结论要写成什么样

- 每个服务单副本的能力（在什么请求组合、什么延迟目标下），以及 1、2、4 个副本的扩容系数（2 个副本是不是 1.9 倍）。
- 整个系统在这套硬件上的上限和第一个瓶颈；瓶颈是硬件（虚拟机的盘、20 个 vCPU）还是软件。
- HPA 的新阈值和依据。
- `GOALS.md` 的目标量级修正：5000 QPS 的秒杀受理做不做得到、落库能到多少、1 亿数据量要不要做。

### 3.7 压完怎么对账

现有的两个工具都不能原样用在长期运行的那一套上，动手前读代码确认的（2026-11-17）：

- `load verify` 把订单库、预占、支付单**整表读进内存**再和账本比，它是为隔离环境写的（库里的数据全是这一轮产生的）。库里有 1000 万造数加历次压测的订单时，它读不动，也会把别的轮次的订单报成“没有对应的流程”。
- `load verify` 和 `recon` 都按 `user_id < 2^40` 排除造数的订单（造数在支付和库存里没有对应的行）。所以**压测的用户号必须低于 2^40**，否则压测的订单会被对账悄悄跳过，“对账通过”就是空话。用户号段因此定在 2^39 起。

每一轮压完，等系统静止之后做两层：

1. **全局的不变量，用 `recon` 的增量模式**（`-since` 取这一轮开始前几分钟）：订单对支付单、订单对预占、主从、订单对商家索引。它是为“系统运行中、数据量大”设计的（ADR-0022），按时间窗比，不读全表。集群上现在只有 chaos 在隔离的命名空间里跑它，要加一个对长期运行的那一套跑的入口（一个 Job，DSN 来自已有的 Secret）。
2. **这一轮自己的不变量，给 `load verify` 加一个限定范围的模式**：只读这一轮的 SKU（每轮的 SKU 号是新的）的库存行、预占和闸门，以及订单号清单里的订单（按主键点查）。检查：
   - 每个 SKU：`初始库存 = 可售 + 预占中 + 已售`，三项都不为负；闸门里的数和 MySQL 对得上。这就是零超卖。
   - 清单里每个被受理的订单：在库里，并且已经离开 `creating`；落库成功的订单数不超过库存。
   - 清单之外、但买了这一轮 SKU 的订单数（预占表按 SKU 有索引，查得出来）：应当是 0，不是 0 说明有受理了但客户端没收到响应的请求，数出来报告，不算错。

第 2 层涉及库存和订单状态的判断，由 Fable 写或逐行评审。

## 6. 实现中的发现和量到的数

### 不删压测的订单（2026-11-17，改了第 2 节第 4 项的后一半）

主人 2026-11-18 确认：不删。

主人确认的第 4 项原来写的是“事后按用户号段删订单、支付、索引、归档里的行”。动手前读表结构和 CDC 的代码，发现它和系统已有的约定冲突：

- **订单在业务上从不删除，订单表的 DELETE 只有一个含义：这一行被归档了**（设计文档 1c 的 6.7）。CDC 把 DELETE 连同删除前的映像发出去，商家索引收到后不删索引行，而是按“已归档”再写一遍。所以从热库删掉压测订单，商家索引里会多出同样数量的“已归档”订单，而冷库里并没有它们。
- 要删干净就得按顺序来：先删热库、等 CDC 追平、再删索引；变更 topic 是按键压缩的，里面留着的 DELETE 记录在索引重建时还会把这些订单带回来。再加上支付、库存预占、支付结果、outbox 几张表各自的关联，这是一个专门绕过系统约定的工具，写错的后果是对账出现解释不了的差异。
- 一轮阶梯压测是几十万单，整个 3b 下来可能和灌进去的 1000 万是一个量级。删这么多行本身就是对主库、从库回放和 CDC 的一次压测。

改成不删：

- **隔离仍然靠号段**（用户号从 2^39 起、SKU 从 7001 起、幂等键前缀）。对账、报表要排除或者只看压测数据时按号段过滤。
- **每一轮用新的一批 SKU 号**（7001 起，按运行递增），不需要把卖掉的库存复位。
- **数据量的增长记下来，不抹掉。** 每轮开跑前记各表的行数，写进这一轮的条件。新订单的号是按时间递增的，写入集中在索引的右端；表从 1000 万长到 2000 万，树高不变，缓冲池本来就放不下全表，对写路径的影响预计很小。这是推断，优化前后对比的两轮之间如果数据量差得多，结论里要写明。
- **要回到基准状态时从备份恢复**：灌完数做一次备份（恢复演练的脚本已经有），需要时恢复三个实例并让索引重建。它的耗时到时实测。

面试里这件事的说法：压测数据的清理为什么难（数据散在多个库、缓存、消息和下游的派生数据里，删除本身会触发同步链路），所以工业界要么用影子库表从一开始就隔离，要么不清理、用可丢弃的环境。

### 第 1 步：脚本、指标、对账工具（2026-11-17）

三样都不碰集群，各由一个子 Agent 在独立的 worktree 里写，主会话读 diff 后合并。

**k6 脚本**（`test/k6/`，Sonnet）。四个场景在本机用 Docker 镜像 `grafana/k6:2.4.0` 冒烟通过（`scripts/k6-local.sh <场景>`）：

| 场景 | 到达速率 | 受理数 | 受理 p99 | 说明 |
|---|---|---|---|---|
| order | 30/s | 450 | 5 毫秒 | 落库 450，支付 225，取消 90 |
| flash | 50/s | 874 | 7.5 毫秒 | 库存很大，没有触发库存不足 |
| mixed | 50/s | 108 | 10 毫秒 | 请求总数 1001 |
| ratelimit | 猛发组 200/s，正常组 50/s | 1486、1001 | 195、157 毫秒 | 猛发组 62.9% 被限流，正常组没有被限流 |

- 订单号清单的办法：受理时 `console.log` 一行 JSON，k6 用 `--console-output` 写文件，包装脚本用 `jq` 还原成 `orders.jsonl`。四个场景的行数都等于受理数。上千次/秒时的开销没有量。
- 幂等键是 `lt-<运行号>-<虚拟用户号>-<序号>`：只用序号的话不同虚拟用户之间会重复。
- 空闲的虚拟用户约 0.33 MB 一个，负载下没有量。
- **落库耗时的精度受轮询间隔限制**：量到的约 104 毫秒里有 100 毫秒是轮询间隔本身。落库耗时以服务端的指标为准。
- 没有验证到的：库存不足的 409、`BACKLOGGED`、`READ_BUSY`（冒烟里没有触发）；超时的错误码（1050 是凭记忆写的）；带 `Host` 头打集群入口。
- 限流冒烟里正常组的受理 p99 是 157 毫秒，比单独跑时高一个数量级。单次 20 秒、没有对照，不能下结论；集群上带对照（猛发组关掉）再量。

**Redis 命令耗时的指标**（`pkg/redisx/metrics.go`，Opus）：go-redis 的 Hook，记到 `db.client.operation.duration`（秒），和 MySQL 同名，`db.system.name=redis`。标签只有命令名（小写；管道是 `pipeline`，事务是 `multi`；超过 64 种归到 `_OTHER`）和 `error.type`（成功时不带；`timeout`、`canceled`、`pool_timeout`、`connection`、`redis_error`、`_OTHER`）。`redis.Nil` 和 `NOSCRIPT` 不算错误。稳定状态下每次约 150 纳秒、0 分配。

- **建连接时的握手命令被排除了**：go-redis 9.23 让 `HELLO`、`AUTH`、`CLIENT ...` 也经过 hook，不排除的话每建一个连接多记几条，而且 `CLIENT MAINT_NOTIFICATIONS` 在不支持它的 Redis 上每次都失败，错误率会一直不为零。
- Cluster 模式下 hook 加在 `ClusterClient` 上，重定向不会重复计数。这是读 go-redis 的源码加一个用单节点模拟的测试确认的；真实的 Cluster、Sentinel 测试因为本机没起那套环境被跳过了。
- 管道的 `error.type` 在两种模式下含义不同：单节点和 Sentinel 只算网络层的错误，Cluster 下第一条失败命令的错误也算。
- **分不出是哪一个 Redis**：一个服务连着闸门、缓存、限流三个 Redis，都记在同一组序列里。要区分得给 `redisx.Config` 加一个调用方给的固定名字当标签，还没有做。
- 和 `redisotel` 的 `db.client.connections.use_time`（毫秒、不分命令）有重叠，没有删它；大盘上用它近似命令耗时的图可以换成新的。

**`load verify` 的限定范围模式**（Opus 写，Fable 读过采集的代码）：`-scope-skus 7001,7002` 加 `-orders-jsonl <k6 的清单>`。`Check` 一行没有改，只改了“读什么”。

- 范围内的订单 = 清单里的订单号 ∪ 预占里买了这些 SKU 的订单 ∪ 按清单里的（用户号，幂等键）在订单库里找到的订单。第三项是实现时加的：没有它，“被回收后用同一个幂等键重新提交”的订单不在范围里。
- 订单、预占、支付单按主键或唯一键分批点查（每批 500）；闸门的占用不 SCAN，按订单号用管道查。
- 限定范围时跳过的检查：死信、库存服务日志、商家索引、冷库（第 18 到 21 条），它们由 `recon` 的增量模式覆盖或者没法按轮次分。
- 测试里有一组对照：同一个库，限定范围的检查通过，不限定范围的在四条上失败，说明范围外的数据确实在而且被挡在了外面；把一个 SKU 的已售数加 1，检查报库存不守恒。
- **它看不到的**：客户端没收到响应（不在清单里）、又在预占之前就失败的订单，因为订单明细没有按 SKU 的索引；它在闸门里留下的占用仍然会被第 11 条发现。第 17 条（outbox 为空）数的是全库，有别的流量时会误报。压测的订单必须只买这一轮的 SKU。

全量 `make lint test`：lint 0 issues；test 第一次有 1 项失败（`TestSweeperSlotTimeoutSkipsHungDB`，当时本机的六个服务也在跑），原样重跑全部通过。没有改 order 的代码，判断是负载下的偶发，没有证实。

### 第 2、3 步：3a 收尾、发压机和写入地址（2026-11-18）

3a 的最后一次数量完了（设计文档 3a 第 8 节最后一段），Grafana 的 requests 和 agent 的队列两件小事也做了。和压测有关的两条：

- **空转时链路的写入量是 0**，Tempo 和 Loki 的盘完全由流量决定。1.4 节“每个请求约 1.2 个 span 和 1.4 KB 日志”的折算不变。
- agent 的发送队列从 1000 批改成了 20 批：压测的日志量下 Collector gateway 一慢，`filelog` 就会停下来等，日志会滞后。压测时看 `otelcol_exporter_queue_size`。

**发压机（Mac mini）查到的事实**，`ssh mini` 现在能登录，k6 是 v2.4.0（`k6 version` 核对过）：

- **它现在走的是 Wi-Fi，有线口没有插线**（`route -n get` 入口地址走的是无线网卡，有线网卡的状态是 inactive）。1.2 节写的“发压机到入口走真实的千兆网络”现在不成立。从它到入口查一次库存是 11 到 15 毫秒，而服务端自己记的是几毫秒：客户端看到的延迟里大半是无线这一段，而且抖动会进尾部分位数。**量基线之前要插上网线**；在那之前脚本和工具可以照常验证，客户端的延迟不算数。
- 空闲 1 分钟就睡眠（`pmset` 的 `sleep 1`），2026-11-17 连不上多半是这个原因。没有免密的 sudo，改不了系统设置，运行 k6 时用 `caffeinate -i` 包住；长稳测试（4 小时）之前最好由主人把睡眠关掉。
- 默认的文件描述符上限是 256（硬上限不限，`kern.maxfilesperproc` 是 61440），跑 k6 之前要在同一个 shell 里调高。临时端口是 49152 到 65535，约 1.6 万个：k6 复用连接，够用；如果某个场景关掉了连接复用，这是上限。
- 入口的地址不应答 ping（MetalLB 二层模式下只有 Service 的端口通），用它判断连通性会误判，要用 HTTP。

**Prometheus 的写入地址**（第 2 节第 7 项）：入口上加了一条 `HTTPRoute`（`deploy/cluster/monitoring/prometheus-write-route.yaml`，`monitoring.sh kps` 会应用），`Host: prom-write.oppenheimer.test`，只放行 `POST /api/v1/write`，查询接口不对外（从 Mac mini 实测：写入口有应答，查询是 404）。没有鉴权，局域网里的设备都能写，是练习环境接受的代价。remote write 接收端 3a 时已经为 Tempo 打开过，不用改 Prometheus。

### 第 3 步的结果：运行入口和辅助脚本（2026-11-18）

两块各由一个 Sonnet 子 Agent 写，主会话读过后合并、在集群上复验。

**`make k6 SCENARIO=<场景>`**（`scripts/cluster/k6.sh`）：把 `test/k6/` 同步到 Mac mini，经 ssh 在那里原生运行 k6，结果拉回 `tmp/k6/<运行号>/`（结构和 `k6-local.sh` 一样，`conditions.txt` 里多了发压机的信息和走的是哪个网卡）。调高文件描述符上限、用 `caffeinate` 防睡眠、中断时把远端的 k6 一起停掉。

- **macOS 的“本地网络”权限**：brew 装的 k6 是临时签名的，第一次经 ssh 启动时访问不了任何局域网地址（全部超时，访问 127.0.0.1 正常，同一个会话里系统自带的 `curl` 也正常）。主人在 Mac mini 自己的终端里跑了一次 k6、在弹窗里点了允许之后，经 ssh 启动的也通了。重装 k6 或升级系统之后可能要再来一次。面试里可以讲的点：同一台机器上 `curl` 通而压测工具不通时，先想到的不该是网络。
- **指标用 remote write 写进 Prometheus**（`-o experimental-prometheus-rw`）。趋势类指标每个统计量一条序列（`k6_http_req_duration_p99` 这样的名字，带 `name`、`method`、`status`、`scenario`、`testid` 标签），不是直方图，所以不能跨运行再聚合分位数。一轮约 200 条序列。运行结束时 k6 写入 stale 标记，之后即时查询查不到，要用 `last_over_time(...[10m])` 或者范围查询。
- k6 2.4 的这个输出**设不了 Host 头**（配了 `K6_PROMETHEUS_RW_HEADERS_Host` 也被忽略，实测入口答 404），入口上那条路由因此改成不限 Host、只认 `POST /api/v1/write`。带业务主机名的请求仍然走业务的路由（实测 `Host: api.oppenheimer.test` 访问这个路径是 404）。
- 这个输出在 k6 2.4 里已经标了弃用（v3 移除，建议换 OpenTelemetry 输出）。Prometheus 的 OTLP 接收端 3a 时已经开着，以后换过去不用动集群。
- 冒烟（Wi-Fi 下，延迟不算数）：`order` 30 单/秒 20 秒，601 单全部受理并落库，清单 601 行；`mixed` 30 请求/秒，601 个请求 0 失败。

**`scripts/cluster/loadtest.sh`**（`make loadtest ARGS="..."`）：`preflight`、`conditions`、`skus`、`pin`/`unpin`、`seed-orders`、`wait-quiet`、`recon`、`verify`。后四个在集群里起一个一次性的 Pod（chaos 镜像），DSN 来自已有的 Secret。**`LOADTEST=1 make deploy`** 叠一层 values 把 gateway 的 `RATE_LIMIT_IP` 关掉。

### 第 4 步：灌数时主库被 OOMKilled（2026-11-18）

灌数的命令（参数的指纹记在库里的 `seed_progress`，**续跑必须原样**，只有 `-rate`、`-timeout`、`-progress` 可以变）：

```

```

第一次没有限速，带 `-timeout 30s` 试跑：约 4.3 万单/秒，24 秒灌进去 1064235 单，然后 **`mysql-order-0-0`（分片 0 的主库）撞到 1 Gi 的内存上限被 OOMKilled**，7 秒后重启完成。

- 数据没有受影响：崩溃恢复后两个分片主从的 `gtid_executed` 一致，`seed_progress` 的合计（513909 加 550326）等于工具报的数；没提交的事务回滚了，同样的命令可以接着灌。
- 另外三个订单库实例当时是 990 到 1014 Mi，也贴着上限。缓冲池是 512 MB，也就是**缓冲池之外还有 500 Mi 上下**：8 个 slot 并发、每个事务 1000 单加 2000 行明细，事务的 binlog 缓存、连接的缓冲区、`performance_schema` 加起来的。这部分是个绝对量，不随缓冲池按比例变，“缓冲池给上限的一半”在 1 Gi 这个量级下不安全。
- 没有限速是主会话的疏忽：1c 在本机灌的时候没有内存上限，集群上有。
- 处理（主人同意）：四个订单库实例的上限提到 2 Gi、缓冲池 1 G（`deploy/cluster/mysql/mysql-order-*.yaml`，滚动了一遍，1 分 40 秒，主从状态正常）；灌数加 `-rate 5000`。`mysql-main` 没有动（上限 1536 Mi、缓冲池 768 M，灌数期间在 986 Mi 上下），商家索引追数时看着它。
- 3c 要加的告警：容器内存接近上限、容器被 OOMKilled。这一次是从客户端的 `invalid connection` 才发现的。

**续灌和结果（2026-11-18，16:54 到 17:24 UTC）。** `-rate 5000` 续灌，29 分 45 秒写完剩下的 8935765 单，全程稳定在 5000 单/秒。

- 两个分片各 360 个块，5023016 加 4976984 正好 1000 万单；主从的 `gtid_executed` 一致；灌完时所有消费组的延迟是 0（商家索引的消费者在灌数期间最多积压约 3 万条，5000 单/秒跟得上）；`preflight` 通过。
- 数据目录：订单库的主库 3.4 GB、从库 4.3 GB（各 500 万单加 1000 万行明细，含 binlog），`mysql-main` 3.0 GB。两个 agent 节点的盘各剩 126 到 128 GB。
- **`mysql-main` 在灌数期间也被 OOMKilled 了一次**（约 17:00 UTC，上限 1536 Mi，商家索引追数时涨上去的；主会话看到它在 1530 Mi 时去请主人同意，等答复的几分钟里它被杀了）。主人同意后提到 2560 Mi、缓冲池 1 G，滚动 28 秒。
- **内存的账（灌完时在 `mysql-order-0-0` 上量的）**：

  | | MB |
  |---|---|
  | 容器的匿名内存（`memory.stat` 的 `anon`，也是进程的 `RssAnon`） | 1844 |
  | MySQL 自己记的（`performance_schema.memory_summary_global_by_event_name` 合计） | 1448 |
  | 其中缓冲池（配的是 1 G，实际 1047） | 1047 |
  | 其中 redo 的 log buffer | 64 |
  | 其中 `performance_schema` 自己的几张表 | 约 100 |
  | **MySQL 没有记、进程却占着的** | **约 400** |

  差的那 400 MB 推断是分配器留着的：镜像里的 `mysqld` 没有预加载 jemalloc 或 tcmalloc（`LD_PRELOAD` 是空的），用的是 glibc 的 malloc，大批量插入时申请过的内存释放后留在分配器手里，不还给系统。这是推断，没有换分配器做对照。所以**缓冲池之外要留的不是“一点余量”，而是固定开销约 400 MB 加分配器留着的约 400 MB**。上限 1 Gi 配 512 M 的缓冲池、上限 2 Gi 配 1 G 的缓冲池都算不过来：灌完之后四个订单库实例在 1854 到 1902 Mi（上限 2048），cgroup 的 `memory.events` 里 `max` 是 29 和 72（撞到过上限，靠回收文件缓存过去的），`oom_kill` 是 0。
- 没有做完的判断：分配器留着的这部分在之后的在线流量下会被重复利用还是继续涨，没有数据；压测时看 `container_memory_working_set_bytes` 和 `memory.events`。订单库的上限要不要再提，等主人定。
- 面试里这件事的说法：`innodb_buffer_pool_size` 不是 MySQL 的内存上限；容器里给 MySQL 定内存要算缓冲池、固定开销（log buffer、`performance_schema`、每个连接的缓冲区）和分配器的碎片三样；`kubectl top` 看到的数贴着上限时要分清是匿名内存还是文件缓存（`memory.stat`），后者能回收、前者不能；怎么确认是分配器的问题（进程的 RSS 减去 `performance_schema` 记的合计）。

### 第 4 步的后一半：备份和恢复的耗时，备份 Job 被 OOMKilled（2026-11-18）

灌完之后做一次手工备份（`make middleware-backup`），这是“回到基准状态”用的那一份：NAS 上 `mysql-order-0/20261118T173525Z`、`mysql-order-1/20261118T173606Z`、`mysql-main/20261118T173407Z`。定时备份只留最近 7 份，**要长期留着的话得在 NAS 上另存一份**（没有做）。

| 实例 | 数据 | 备份（mysqldump 加 zstd，从从库读） | 压缩后 | 恢复到临时实例 |
|---|---|---|---|---|
| `mysql-order-0` | 502 万单、1005 万行明细 | 29 秒 | 505 MB | 177 秒 |
| `mysql-order-1` | 498 万单 | 约 30 秒 | 501 MB | 没有做 |
| `mysql-main` | 库存、支付、1000 万行商家索引 | 约 20 秒 | 342 MB | 没有做 |

- 恢复演练（`make mysql-restore-drill RELEASE=mysql-order-0`）：恢复出来的 `gtid_executed` 和备份记录一致；订单、明细、支付结果、outbox、进度表共 16 张表的行数和 `CHECKSUM TABLE` 都和线上从库一致；只有 `idgen_worker`（节点号租约，一直在续租）对不上，是 2c 就知道的。2b 留下的“恢复耗时等有百万行再量”到这里算量了：**500 万单恢复约 3 分钟，是备份的 6 倍**（逻辑备份的恢复要重新建索引）。按这个比例，1 亿单的逻辑恢复是一小时的量级，那时该换物理备份。
- **备份 Job 第一次在两个订单库上都被 OOMKilled**（上限 256 Mi，开始十几秒就被杀；`mysql-main` 的成功了）。values 里的注释写的是“dump 是流式的，内存用量很小”，对进程本身是对的：重跑时看 `memory.stat`，`mysqldump` 加 `zstd` 的匿名内存只有 41 Mi。占内存的是**输出文件的页缓存**：备份写在 NFS 上，脏页和正在回写的页都记在这个容器的 cgroup 里（采到过 `file` 481 Mi、其中 `file_writeback` 213 Mi，峰值 526 Mi），NAS 收得没有 dump 产生得快，256 Mi 装不下。库里只有几万行时文件只有 1 MB，所以一直没有暴露。
- 处理：备份 Job 的内存提到 1 Gi（`deploy/charts/mysql/values.yaml`，只改了 CronJob，三个实例没有滚动），重跑成功。**这是把上限抬过了现在的数据量，不是修好了**：数据再大十倍，回写跟不上时还会撞。真正的修法是让写出去的数据不在页缓存里积压（例如输出经 `dd oflag=direct` 或者定期 `fsync`），没有做，记给阶段 4 的备份恢复实验。
- 面试里这件事的说法：容器的内存上限管的不只是进程的堆，写文件产生的脏页也算；本地盘上脏页回写得快看不出来，写到 NFS 这种慢的后端就会 OOM；“流式处理所以不占内存”要连输出端一起看。

### 第 6 步：阶梯加压和第一个瓶颈（2026-11-18）

记录在 [notes/3b-rounds/round-0-first-bottleneck.md](../notes/3b-rounds/round-0-first-bottleneck.md)，对账通过。结论：

- 普通下单场景，落库和受理的拐点都是 **125 单/秒**；落库的上限约 **143 单/秒**，之后背压把受理压在 130 到 170。
- 第一个瓶颈是**同步提交的刷盘**：落库一单要两次事务提交，提交的中位数 40 到 60 毫秒；虚拟盘每个节点每秒只能刷 400 多次，每次 5 毫秒上下；宿主机的 NVMe（970 EVO Plus，没有掉电保护）空闲时一次同步写就要 5.3 毫秒，虚拟机里 11 到 13 毫秒。从库延迟（最多 553 秒）是同一个原因。
- 受理跟着变慢是因为落库落后之后轮询把读路径和节点 CPU 打满（重试放大）。
- 入口 Envoy 的默认熔断上限（1024）在系统变慢时答了几十万个 `503 UO`，gateway 的指标里看不到。
- **支付出结果的上限是每秒约 17 笔**（payment 的 processor 一笔一个事务串行处理）。阶梯那一轮 43227 笔受理的支付里有 22351 笔因为排队超过 15 分钟、订单已被关单而退款。账是对的，对账通过。**基线“普通下单”那一轮的支付速率是 50 笔/秒，也在排队**，只是没有超过 15 分钟；以后的轮次支付要压在每秒 15 笔以下，或者先修它。
- 优化方案（七条）在记录的第 7 节，等主人定。夜里没有改业务代码。

### 第 5 步的对照：可观测的开销（2026-11-18）

同样的到达速率（普通下单 100 单/秒，支付比例调到 10%，避开支付那个每秒 17 笔的上限；每种设置先预热 40 秒再压 3 分钟），只换遥测的设置，每换一次六个服务滚动一遍。CPU 取后 150 秒的平均。

| 设置 | 请求/秒 | 业务容器的 CPU（核，六个服务合计） | 每个请求（毫核） | Collector gateway 加 Tempo（核） | 受理 p50 / p99（毫秒，客户端） |
|---|---|---|---|---|---|
| 全量导出加尾部采样（平时的配置） | 382 | 2.19 | 5.7 | 0.19 | 8.9 / 19.1 |
| 头部采样 10% | 376 | 1.85 | 4.9 | 0.05 | 8.0 / 18.3 |
| 不采链路（指标照常） | 385 | 1.92 | 5.0 | 0.04 | 8.3 / 18.6 |
| 链路和指标都不导出 | 410 | 2.02 | 4.9 | 0.04 | 8.4 / 19.8 |

- **全量导出链路的代价是业务容器 CPU 的 14% 上下**（每个请求 5.7 对 4.9 毫核），另加 Collector 和 Tempo 上的 0.15 核。头部采样 10% 就拿回了几乎全部，和完全不采没有可分辨的差别。
- 指标导出的开销量不出来：最后一行和第三行每个请求的 CPU 一样，在噪声里。
- 延迟没有差别。这个负载下 CPU 不紧，多花的 14% 不体现在延迟上；压到节点 CPU 九成以上时会。
- 所以 1.4 节那个问题（“405 请求/秒时 gateway、order 的 CPU 就到 70%”）的账：链路导出只占一成半，不是主要原因。边车在这一轮是 0.7 核，约为业务容器的三分之一；其余是业务容器自己，pprof 里花在网络读写的系统调用上。2c 到现在的变化里边车是更大的一块，没有做“有边车对没边车”的对照。
- 每种设置只跑了一轮、3 分钟，请求数因为轮询有 ±4% 的出入，所以上面的差别小于 5% 的都不能算数。全量那一轮用的是经历过阶梯加压的旧 Pod，另外三轮是刚滚动出来的新 Pod，内存没有可比性（505 Mi 对 280 到 310 Mi），没有列。
- 做完已恢复成平时的配置（`LOADTEST=1` 重新部署，采样器未设、导出地址在；`preflight` 核对过）。
- 四轮都对账通过（`recon` 差异 0，`verify` 四个 `PASS`）。支付压在每秒 10 笔时，受理的支付全部成功（1778、1846、1790、1801 笔，和已付的订单数逐一相等），和“支付出结果的上限约每秒 17 笔”的判断一致。
