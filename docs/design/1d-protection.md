# 1d 设计：限流、熔断、降级与对账

本文是阶段 1d 的实现规格。1c 之后系统的功能和数据布局已经齐了，1d 做的是让它在过载和依赖故障时表现得可预期，再加一个能定位数据差异的对账工具。

状态：第 1、2 节主人已确认（2026-11-14）：按五步的顺序做；落库用分区内按 key 并发；商家索引先复用并发消费，达不到 1 万行/秒再做按批写。其余各步在动工前细化。

## 1. 分六步走

每一步结束时系统都能运行，`make lint test e2e` 通过。

| 步骤 | 内容 | 对应阶段计划里的任务 |
|---|---|---|
| 一 | 把吞吐的欠账还掉：落库并发、轮询不再和落库抢连接、商家索引追得上、压测工具的开环模式 | 1b 压测遗留的落库性能问题、orderindex 按批写、开环模式 |
| 二 | 网关限流：令牌桶，按接口、按用户、按 IP；单机和 Redis 分布式两种 | 网关限流 |
| 三 | 服务侧保护：sentinel-go 的熔断、并发隔离、热点参数限流；全链路的超时预算和重试规范 | 服务侧保护、超时与重试规范、1b 遗留的小问题 |
| 四 | 降级预案和优雅启停：Redis 不可用、冷库不可用、从库落后、inventory 超时各自怎么退；摘流、排空、关闭顺序 | 降级预案、优雅启停 |
| 五 | 对账：`pkg/merkle`，用于订单对支付、订单对库存流水、Redis 对 MySQL，以及主从、CDC 索引、冷热归档 | 对账 |
| 六 | 埋点：OpenTelemetry 的链路和指标，贯穿 HTTP、gRPC、Kafka、MySQL、Redis | 埋点（ADR-0004） |

**为什么先还吞吐的欠账。** 限流的阈值、熔断的阈值、背压的队列长度都要对着“系统实际能处理多少”来定。现在落库只有约 400 单/秒，是串行造成的，不是资源用尽；在这个数上定下的阈值，落库改完就全部作废。另一个原因是测量工具：没有开环的压测，过载下的行为（限流该不该触发、触发后延迟是否稳住）量不出来，步骤二到四的验收都要靠它。

**为什么对账放最后。** 它和前四步没有依赖，放在哪里都行。放最后是因为前四步会改动消费者和降级路径，对账工具正好拿来验证这些改动之后数据仍然一致。

**步骤六是写完前五步的划分之后补上的**（2026-11-14）：阶段计划的 1d 清单里还有一项埋点，第一次划分时漏了。放在最后是因为它不改变行为，而且前五步新增的限流、熔断、并发消费都是需要埋点的地方，等它们定型后一次加完；后端（SkyWalking、指标存储）在阶段 3。主人已确认（2026-11-14）。

步骤三的两个 1b 遗留小问题（调用方取消被记成 ERROR、payment 启动时 Redis 不可用就启动失败）和 Guard 调用的超时，归到各自相关的步骤里（三、四、三）。

## 2. 步骤一：吞吐的欠账

决定和备选方案见 ADR-0017。

### 2.1 现状和目标

三个已经量到的问题（1b 设计文档 7.3.4、1c 设计文档 5.11）：

| 问题 | 现在 | 原因 |
|---|---|---|
| 落库吞吐 | 约 410 单/秒，MySQL 和 inventory 都很空闲 | 4 个分区，每个分区一条一条处理，每条约 10 毫秒（一次 Redis、一次 gRPC、两个事务） |
| 轮询拖垮落库 | 800 个用户每 50 毫秒轮询时，落库从 410 跌到 43 单/秒 | 非终态订单不缓存，`GetOrder` 先查 MySQL，和落库共用连接池 |
| 商家索引追不上 | 约 2000 行/秒写入，500 万行要 40 分钟 | 同样是分区内串行，每条一次写库 |

前两个和第三个是同一个原因：**消费者在一个分区内是串行的**，吞吐上限是“分区数 ÷ 单条耗时”，和下游有多少余量无关。

目标不是某个绝对数字（本机的吞吐测量受 OrbStack 端口转发干扰，结论要到阶段 2 的集群上才算数），而是三件可以在本机判断的事：

1. 落库吞吐随并发度上升，直到某个下游资源（连接池、inventory、MySQL）成为瓶颈，并且知道是哪一个。
2. 轮询的压力不再影响落库吞吐。
3. 商家索引的写入速度超过 CDC 的产出速度（归档时约 1 万条/秒）。

### 2.2 分区内按 key 并发消费

给 `pkg/kafkax` 的消费者加一个并发度（`ConsumerConfig.Concurrency`，默认 1，即现在的行为）。

```
                       ┌─ lane 0 ─ handler ─┐
拉取 → 分区的本地队列 → 分发（hash(key) % N）─┼─ lane 1 ─ handler ─┼→ 完成表 → 提交连续前缀
                       └─ lane N-1 ─ handler┘
```

**顺序。** 同一个 key 的消息总是进同一条 lane，lane 内串行。所以“同一个订单的消息按序处理”仍然成立，不同订单之间本来就没有顺序要求。这是并发消费能做而不出错的前提，也是它和“开一个协程池随便处理”的区别。

**位点提交。** Kafka 一个分区只有一个已提交位点，表示“这之前的都处理完了”。并发之后消息不按偏移量的顺序完成：偏移量 7 做完了而 5 还在重试，这时只能提交到 5，不能提交到 8，否则重启后 5 就丢了。做法是记录在途的偏移量，可提交的位点是“最小的未完成偏移量”；没有在途的消息时是“最后分发的偏移量加一”。

由此的后果：重启或再平衡后，7 会被重新处理一次。并发消费把“重复投递”从偶发变成了常态，handler 必须幂等。本项目的 handler 从 1b 起就按至少一次设计，这一条已经满足。

**一条消息卡住时。** 现在一条消息在原地重试，整个分区停住。并发之后只有它所在的 lane 停住，其他 lane 继续，但提交的位点被它拖着不动。不加限制的话，“已处理未提交”的跨度会无限增长，一次重启要重放全部。所以加一个窗口（默认 1024）：分发的偏移量超过最小未完成偏移量这么多时，停止分发，这个分区等它。到这一步行为和现在相同（分区停住），窗口只是让短暂的重试不拖住其他订单。

**重试、死信**的语义不变，都发生在 lane 内：原地重试期间这条 lane 不前进；进死信的消息算作完成。

**再平衡和停止。** 分区被收回时：停止分发，等各 lane 做完手上的那一条，提交连续前缀。前缀之后已经完成的消息会被新的持有者重新处理。强制取消时同现在一样立刻放弃。

**延迟消费者不允许并发**（`Concurrency > 1` 时构造函数报错）。延迟 topic 依赖“分区内按到期时间有序、队首没到期就等”，并发会破坏这个假设。

**哪些消费者开并发：**

| 消费者 | 并发度 | 理由 |
|---|---|---|
| order 的 `order.submit`（落库） | 8（可配） | 这一步的目标。key 是订单号，不同订单互不相干 |
| orderindex 的 `cdc.order.orders` | 16（可配） | key 是订单号；写入按行版本号幂等，乱序也收敛 |
| order 的支付结果、延迟关单 | 1 | 量小；延迟关单不允许 |
| inventory 的订单事件 | 1 | key 是订单号，但处理时锁的是 SKU 行：同一个 SKU 的不同订单并发处理只会在行锁上排队，还会让死锁重试变多。它也不是瓶颈 |
| payment 的订单事件 | 1 | 量小 |

落库并发 8、4 个分区，同时在途 32 个订单；每个订单库的连接池是 25，默认 2 个库共 50（本机扩容后是 4 个库共 100）。order 启动时比较这两个数，在途上限超过连接池总和时打一条警告。并发度上去之后瓶颈预计转到 inventory 的 `Reserve`（热门 SKU 的行锁）或订单库的连接池，实测后写进结果。

**核心代码归属**：分发、完成表、提交位点的计算是并发加一致性的代码（提交错了就是丢消息），由 Fable 编写，带 `-race` 的测试和并发场景的测试：乱序完成时提交的位点、卡住一条时窗口生效、再平衡时不提交未完成的、同一个 key 不并发。

### 2.3 落库并发之后要重看的地方

并发消费改变了落库路径上“同一时刻只有一条在处理”的假设。逐个检查：

- **`Claim` 的心跳和探测名额**（ADR-0011）：按消息独立，不依赖串行。
- **订单号的幂等**：同一个订单号的重复消息在同一条 lane 里串行，和现在一样。
- **同一个用户的不同订单**并发落库：`(user_id, idempotency_key)` 的唯一约束仍然由数据库保证；“幂等键过期后的重放”那条路径（`dropReplay`）读的是已提交的数据，两条重放并发时一条插入成功、另一条撞唯一键后走重放，结果相同。
- **`Reserve` 的并发**：inventory 里同一个 SKU 的并发预占靠行锁排队，1a 起就有并发测试。多个 SKU 的订单按固定顺序加锁，不死锁。
- **落库的重试上限**（10 次，约 26 秒）和回收宽限期的关系不变。

这些是读代码的结论，实现时用测试确认：现有的 `land_test.go` 用并发度大于 1 的消费者再跑一遍，加一个“同一批订单乱序、重复投递”的用例。

### 2.4 轮询先读闸门

`GetOrder` 对非终态订单现在的顺序是：读订单行（MySQL）→ 没有再读占用（Redis）→ 再读一次订单行确认。刚受理、还在排队的订单，每次轮询都要白读两次 MySQL。

改成先读占用：

1. 缓存命中（终态）：直接返回。不变。
2. 读占用：
   - **有，未认领**：落库还没开始，主库上不可能有行（落库流程先认领再插入）。直接合成 `CREATING` 返回，不读 MySQL。
   - **有，已认领**：行可能已经在主库。读主库，有就返回，没有就按占用合成。
   - **没有**：读订单行（按读模式走从库或主库）。没有的话由主库确认，再走冷库（1c 步骤五）。
   - **读占用失败**（Redis 不可用）：退回现在的顺序，先读订单行；行不存在时和现在一样返回不可用。Redis 故障不应该让已落库的订单也查不到。

排队中的订单轮询只打 Redis（一次 Lua，几十微秒）。已落库的非终态订单（待支付）多一次 Redis 读，仍然要读 MySQL：它的占用是“已认领”，要到终态才归还。这部分轮询量和落库不重叠（落库已经完成），而且步骤二的限流会按用户限制轮询的频率。

**为什么这样改是对的。** 现在“先读行、再读占用、再读行”的三步是为了排除一个竞争：两次读之间订单落库并走完终态、占用被归还。先读占用之后这个竞争不存在了：占用没有，只可能是从未受理、已被回收，或者已经走到终态；最后一种情况下行一定已经提交，随后那次主库读看得到。所以只需要读一次行。

未认领时直接返回 `CREATING` 可能比真实状态旧一瞬间（读完占用的下一刻落库开始了），这对展示读是可接受的，下一次轮询就会更新。

这段代码决定订单状态怎么答，由 Fable 编写或逐行评审。

### 2.5 商家索引的消费者

阶段计划里写的是“改成按批写”。这一步先不做批量，直接用 2.2 的并发消费（并发度 16）：

- 它和落库是同一个问题（分区内串行），用同一个机制解决，kafkax 只多一个概念。
- 按批写要给 kafkax 再加一种 handler（收一批消息），批内同一个订单的多个版本要先合并，一批里一条失败怎么办（整批重试，还是拆开）也要定。收益是每行的往返更少，上限比并发更高。
- 并发 16、4 个分区是 64 路同时写，按现在每路约 500 行/秒算是 3 万行/秒的量级，超过 CDC 的产出。实测达不到 1 万行/秒再做按批写。

这一条和阶段计划的写法不同，主人已确认。

### 2.6 压测工具的开环模式

现在的 `load run` 是闭环的：每个虚拟用户提交一单、轮询到终态、再提交下一单。系统变慢时请求也跟着变少，量不出过载；“只管提交”是用 1 毫秒的轮询超时凑出来的。

新增 `-mode open -rate N`：

- 按固定的时间表发请求（每秒 N 个，均匀间隔），不管上一个有没有返回。并发数不设上限会在系统卡住时耗尽本机的连接，所以设一个在途请求的上限，超过时这个时刻的请求记为“未发出”，单独计数，不悄悄跳过。
- **延迟从“计划发出的时刻”算起**，不是从实际发出的时刻。系统卡住 1 秒时，这 1 秒里本该发出的请求都在排队，它们的延迟要算上排队的时间；只从实际发出算，会把最坏的那些样本漏掉（协调遗漏）。
- 压测期间不轮询。结束后有一个收尾阶段，把已受理订单的最终状态查出来写进账本，`load verify` 照常能用。
- 报告：计划速率、实际发出速率、各类结果（受理、被背压拒绝、被限流、超时、未发出）的数量，受理延迟的分位数，落库延迟（从受理到订单行出现）的分位数。

闭环模式保留，默认仍是闭环。

### 2.7 改完之后重新设定的参数

- `ADMIT_MAX_QUEUE`（等待落库的订单数上限）：现在的默认值是按 400 单/秒定的。按实测的落库吞吐乘以“愿意让订单排多久”（现在是回收宽限期的一半，约 25 秒）重新算。
- 落库并发度和订单库连接池（`MYSQL_MAX_OPEN_CONNS`）的关系：在途的落库数不能长期超过连接池，否则落库自己在池上排队。
- 这些数写进结果，步骤二、三的阈值以它们为基础。

### 2.10 结果（2026-11-14）

`make lint test e2e` 通过，`make chaos` 两次 PASS（并发消费下 19 项对账全过；第 15 项“受理后被回收”一次 0、一次 70，和以前一样只出现在 order 被杀之后）。

下面的数都是 `scripts/bench.sh` 在本机量的：开环、每秒 3000 个下单请求、持续 20 秒，10 个 SKU，两个订单库、inventory、payment 都在同一个 MySQL 实例上。原始输出在 `tmp/1d/`，不入库。本机的绝对值不可靠（见 1b 设计文档 7.3.4），看的是相对变化和瓶颈的位置。

**落库吞吐对并发度**

| `SUBMIT_CONCURRENCY` | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| 落库（单/秒） | 316 | 448 | 569 | 642 | 686 |
| 受理（单/秒） | 804 | 974 | 1112 | 1219 | 1305 |
| 被背压拒绝的比例 | 73% | 68% | 63% | 59% | 57% |

并发生效了，但到 2.2 倍就平了，没有到“下游资源用尽”那种量级。平的时候四个服务的 CPU 都很空闲（order 约三分之一个核），只有 MySQL 容器用了约 1.1 到 1.3 个核。

**瓶颈在哪：让 MySQL 自己说。** 清空 `performance_schema` 的语句统计后跑一次并发度 16，按总耗时排：

| 语句 | 次数 | 平均 | 其中等锁 |
|---|---|---|---|
| inventory：`UPDATE sku_stock SET available = available - ? ...` | 24679 | 48.4 ms | 几乎全部（累计 1192 秒） |
| 订单库 0 的 `COMMIT` | 24625 | 7.0 ms | 0 |
| inventory 的 `COMMIT` | 24654 | 6.9 ms | 0 |
| 订单库 1 的 `COMMIT` | 24646 | 6.8 ms | 0 |
| 其余所有语句 | | 0.3 ms 以下 | 0 |

两件事叠在一起：

1. **热门 SKU 的行锁。** 预占在一个事务里扣 `sku_stock` 的可售数，这一行的锁要拿到事务提交。10 个 SKU、64 个在途订单，大家在这 10 行上排队。
2. **提交很慢。** 每次提交约 7 毫秒（`sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`，容器里的文件系统刷盘本来就慢），一个订单落库要提交三次。它又拉长了第 1 条里持锁的时间：一行每秒最多被扣一百多次。

做了两个对照，各自只解释一部分，和上面的结论一致：

| 条件 | 并发度 1 | 并发度 16 |
|---|---|---|
| 默认 | 316 | 686 |
| 放宽刷盘（`sync_binlog=0`、`innodb_flush_log_at_trx_commit=2`，量完改回） | 571 | 848 |
| 100 个 SKU | | 800 |

串行时刷盘是主要成本（放宽后快了 80%），并发之后它不再是唯一的限制。

**这一步达到了什么，没达到什么。** 2.1 定的第一个目标是“落库吞吐随并发度上升，直到某个下游资源成为瓶颈，并且知道是哪一个”：达到了，瓶颈是 inventory 里同一个 SKU 的扣减在 MySQL 里是串行的。没有达到的是数量级的提升：1b 留下的“落库 400 单/秒”现在是 640 到 820，原因不再是消费者的结构。

热门行的扣减是秒杀的老问题，闸门（Redis）解决了受理这一侧，落库这一侧每个订单仍然要在 MySQL 里扣一次。常见的做法：把一个 SKU 的库存拆成多行（分桶），不同订单扣不同的行；把短时间内对同一个 SKU 的多个预占合并成一次扣减（一个事务扣 n 件、写 n 条预占记录）；或者预占只写流水、可售数异步汇总。放在 1d 的哪一步做，等主人定。

**轮询压力下的落库**（并发度 8，每秒 2000 个下单请求，另一个进程对最近受理的 2000 个订单每秒查询约 4600 次）

| | 落库（单/秒） | 查询延迟 p50 / p99 |
|---|---|---|
| 没有查询压力 | 821 | |
| 有查询压力 | 617 | 1.8 / 7.3 ms |

有查询压力时落库是没有时的 75%。1b 的数是 410 对 43（约 10%），当时的轮询是每个虚拟用户 50 毫秒一次、800 个用户，约 1.6 万次/秒，压力比这次大，两个比值不能直接比。能确定的是：排队中的订单被查询时不再读 MySQL（`TestQueuedOrderIsAnsweredWithoutTheOrderDB` 把订单库关掉也能答），剩下的 25% 来自已落库、待支付的订单，它们仍然要读订单行。这部分留给步骤二按用户限制查询频率。

**商家索引**

只在测试库上量了（同一个 MySQL 实例，每库连接池 25）：在途写入从 4 路（相当于改动前）加到 64 路（并发度 16 × 4 个分区），写入从约 2000 行/秒到 7600 到 9000 行/秒，32 路之后就平了。瓶颈同样是每次提交的刷盘：一行一个事务，每次约 1.2 毫秒，靠组提交把多路的提交合在一起刷，合到头就是这个数。

它低于 2.5 定的门槛（1 万行/秒）。按约定应当接着做按批写：一个事务写多行，直接减少提交次数，正好针对这个瓶颈。在真实数据上的追平速度没有量（要重新造一批变更）。

**参数**

- `ADMIT_MAX_QUEUE` 保持 1 万：按 640 到 820 单/秒算是排 12 到 16 秒，比原来按 400 算的 25 秒更保守。热门 SKU 的问题处理之后再调。
- `SUBMIT_CONCURRENCY` 默认 8：从 8 到 16 只多 7%，而在途数（64）已经超过两个订单库的连接池总和（50）。
- `INDEX_CONCURRENCY` 默认 16。
- 共享 MySQL 实例的 `max_connections` 提到了 400：各服务的连接池加起来是 164，超过默认的 151，服务开着的时候跑测试会报 1040。

**实现中的发现**

- **并发之后，同一个幂等键的两个订单谁落库不再由受理的先后决定**（ADR-0017 后果一节）。
- **正常停止也会产生重复。** 测试里一次正常停止：处理了 923 条、提交了 661 条，重启后 262 条重做。停止时每条 lane 只做完手上的一条，前缀之后已完成的都要重来。这是设计内的行为，量出来比预想的多。
- **分 lane 的哈希不能用生产者分区的那个。** 一个分区里的 key 本来就是“哈希取模后相等”的一批，再用同一个哈希对 lane 数取模，lane 数和分区数有公因数时会挤进少数几条 lane。用了带随机种子的 `maphash`。
- **开环模式没有量落库延迟。** 网关的订单响应里没有落库时刻，压测期间又不轮询。报告里写明“未测”，落库吞吐仍从库里算。要量得在订单上暴露一个落库时间，或者等阶段 3 的指标。
- 每条语句执行前都有一次 `PREPARE`（上表之外，次数与执行数相同，每次约 0.04 毫秒）：驱动默认用服务端预处理、不缓存。耗时很小，但多一次往返；`interpolateParams` 可以去掉，没有做。
- 预热接口一次最多 100 个 SKU，压测脚本的 `BENCH_SKU_COUNT` 超过 100 会失败。

**没有做的**

- 热门 SKU 的扣减（上面）。
- 商家索引按批写（上面）。
- 商家索引在真实数据上的追平速度。
- 落库延迟的测量。
- `GetOrder` 对已落库、待支付订单的查询仍然读 MySQL。
