# 1d 设计：限流、熔断、降级与对账

本文是阶段 1d 的实现规格。1c 之后系统的功能和数据布局已经齐了，1d 做的是让它在过载和依赖故障时表现得可预期，再加一个能定位数据差异的对账工具。

状态：第 1、2 节主人已确认（2026-11-14）：按五步的顺序做；落库用分区内按 key 并发；商家索引先复用并发消费，达不到 1 万行/秒再做按批写。其余各步在动工前细化。

## 1. 分六步走

每一步结束时系统都能运行，`make lint test e2e` 通过。

| 步骤 | 内容 | 对应阶段计划里的任务 |
|---|---|---|
| 一 | 把吞吐的欠账还掉：落库并发、轮询不再和落库抢连接、商家索引追得上、压测工具的开环模式 | 1b 压测遗留的落库性能问题、orderindex 按批写、开环模式 |
| 二 | 网关限流：令牌桶，按接口、按用户、按 IP；单机和 Redis 分布式两种 | 网关限流 |
| 三 | 服务侧保护：sentinel-go 的熔断、并发隔离、热点参数限流；全链路的超时预算和重试规范 | 服务侧保护、超时与重试规范、1b 遗留的小问题 |
| 四 | 降级预案和优雅启停：Redis 不可用、冷库不可用、从库落后、inventory 超时各自怎么退；摘流、排空、关闭顺序 | 降级预案、优雅启停 |
| 五 | 对账：`pkg/merkle`，用于订单对支付、订单对库存流水、Redis 对 MySQL，以及主从、CDC 索引、冷热归档 | 对账 |
| 六 | 埋点：OpenTelemetry 的链路和指标，贯穿 HTTP、gRPC、Kafka、MySQL、Redis | 埋点（ADR-0004） |

**为什么先还吞吐的欠账。** 限流的阈值、熔断的阈值、背压的队列长度都要对着“系统实际能处理多少”来定。现在落库只有约 400 单/秒，是串行造成的，不是资源用尽；在这个数上定下的阈值，落库改完就全部作废。另一个原因是测量工具：没有开环的压测，过载下的行为（限流该不该触发、触发后延迟是否稳住）量不出来，步骤二到四的验收都要靠它。

**为什么对账放最后。** 它和前四步没有依赖，放在哪里都行。放最后是因为前四步会改动消费者和降级路径，对账工具正好拿来验证这些改动之后数据仍然一致。

**步骤六是写完前五步的划分之后补上的**（2026-11-14）：阶段计划的 1d 清单里还有一项埋点，第一次划分时漏了。放在最后是因为它不改变行为，而且前五步新增的限流、熔断、并发消费都是需要埋点的地方，等它们定型后一次加完；后端（SkyWalking、指标存储）在阶段 3。主人已确认（2026-11-14）。

步骤三的两个 1b 遗留小问题（调用方取消被记成 ERROR、payment 启动时 Redis 不可用就启动失败）和 Guard 调用的超时，归到各自相关的步骤里（三、四、三）。

## 2. 步骤一：吞吐的欠账

决定和备选方案见 ADR-0017。

### 2.1 现状和目标

三个已经量到的问题（1b 设计文档 7.3.4、1c 设计文档 5.11）：

| 问题 | 现在 | 原因 |
|---|---|---|
| 落库吞吐 | 约 410 单/秒，MySQL 和 inventory 都很空闲 | 4 个分区，每个分区一条一条处理，每条约 10 毫秒（一次 Redis、一次 gRPC、两个事务） |
| 轮询拖垮落库 | 800 个用户每 50 毫秒轮询时，落库从 410 跌到 43 单/秒 | 非终态订单不缓存，`GetOrder` 先查 MySQL，和落库共用连接池 |
| 商家索引追不上 | 约 2000 行/秒写入，500 万行要 40 分钟 | 同样是分区内串行，每条一次写库 |

前两个和第三个是同一个原因：**消费者在一个分区内是串行的**，吞吐上限是“分区数 ÷ 单条耗时”，和下游有多少余量无关。

目标不是某个绝对数字（本机的吞吐测量受 OrbStack 端口转发干扰，结论要到阶段 2 的集群上才算数），而是三件可以在本机判断的事：

1. 落库吞吐随并发度上升，直到某个下游资源（连接池、inventory、MySQL）成为瓶颈，并且知道是哪一个。
2. 轮询的压力不再影响落库吞吐。
3. 商家索引的写入速度超过 CDC 的产出速度（归档时约 1 万条/秒）。

### 2.2 分区内按 key 并发消费

给 `pkg/kafkax` 的消费者加一个并发度（`ConsumerConfig.Concurrency`，默认 1，即现在的行为）。

```
                       ┌─ lane 0 ─ handler ─┐
拉取 → 分区的本地队列 → 分发（hash(key) % N）─┼─ lane 1 ─ handler ─┼→ 完成表 → 提交连续前缀
                       └─ lane N-1 ─ handler┘
```

**顺序。** 同一个 key 的消息总是进同一条 lane，lane 内串行。所以“同一个订单的消息按序处理”仍然成立，不同订单之间本来就没有顺序要求。这是并发消费能做而不出错的前提，也是它和“开一个协程池随便处理”的区别。

**位点提交。** Kafka 一个分区只有一个已提交位点，表示“这之前的都处理完了”。并发之后消息不按偏移量的顺序完成：偏移量 7 做完了而 5 还在重试，这时只能提交到 5，不能提交到 8，否则重启后 5 就丢了。做法是记录在途的偏移量，可提交的位点是“最小的未完成偏移量”；没有在途的消息时是“最后分发的偏移量加一”。

由此的后果：重启或再平衡后，7 会被重新处理一次。并发消费把“重复投递”从偶发变成了常态，handler 必须幂等。本项目的 handler 从 1b 起就按至少一次设计，这一条已经满足。

**一条消息卡住时。** 现在一条消息在原地重试，整个分区停住。并发之后只有它所在的 lane 停住，其他 lane 继续，但提交的位点被它拖着不动。不加限制的话，“已处理未提交”的跨度会无限增长，一次重启要重放全部。所以加一个窗口（默认 1024）：分发的偏移量超过最小未完成偏移量这么多时，停止分发，这个分区等它。到这一步行为和现在相同（分区停住），窗口只是让短暂的重试不拖住其他订单。

**重试、死信**的语义不变，都发生在 lane 内：原地重试期间这条 lane 不前进；进死信的消息算作完成。

**再平衡和停止。** 分区被收回时：停止分发，等各 lane 做完手上的那一条，提交连续前缀。前缀之后已经完成的消息会被新的持有者重新处理。强制取消时同现在一样立刻放弃。

**延迟消费者不允许并发**（`Concurrency > 1` 时构造函数报错）。延迟 topic 依赖“分区内按到期时间有序、队首没到期就等”，并发会破坏这个假设。

**哪些消费者开并发：**

| 消费者 | 并发度 | 理由 |
|---|---|---|
| order 的 `order.submit`（落库） | 8（可配） | 这一步的目标。key 是订单号，不同订单互不相干 |
| orderindex 的 `cdc.order.orders` | 16（可配） | key 是订单号；写入按行版本号幂等，乱序也收敛 |
| order 的支付结果、延迟关单 | 1 | 量小；延迟关单不允许 |
| inventory 的订单事件 | 1 | key 是订单号，但处理时锁的是 SKU 行：同一个 SKU 的不同订单并发处理只会在行锁上排队，还会让死锁重试变多。它也不是瓶颈 |
| payment 的订单事件 | 1 | 量小 |

落库并发 8、4 个分区，同时在途 32 个订单；每个订单库的连接池是 25，默认 2 个库共 50（本机扩容后是 4 个库共 100）。order 启动时比较这两个数，在途上限超过连接池总和时打一条警告。并发度上去之后瓶颈预计转到 inventory 的 `Reserve`（热门 SKU 的行锁）或订单库的连接池，实测后写进结果。

**核心代码归属**：分发、完成表、提交位点的计算是并发加一致性的代码（提交错了就是丢消息），由 Fable 编写，带 `-race` 的测试和并发场景的测试：乱序完成时提交的位点、卡住一条时窗口生效、再平衡时不提交未完成的、同一个 key 不并发。

### 2.3 落库并发之后要重看的地方

并发消费改变了落库路径上“同一时刻只有一条在处理”的假设。逐个检查：

- **`Claim` 的心跳和探测名额**（ADR-0011）：按消息独立，不依赖串行。
- **订单号的幂等**：同一个订单号的重复消息在同一条 lane 里串行，和现在一样。
- **同一个用户的不同订单**并发落库：`(user_id, idempotency_key)` 的唯一约束仍然由数据库保证；“幂等键过期后的重放”那条路径（`dropReplay`）读的是已提交的数据，两条重放并发时一条插入成功、另一条撞唯一键后走重放，结果相同。
- **`Reserve` 的并发**：inventory 里同一个 SKU 的并发预占靠行锁排队，1a 起就有并发测试。多个 SKU 的订单按固定顺序加锁，不死锁。
- **落库的重试上限**（10 次，约 26 秒）和回收宽限期的关系不变。

这些是读代码的结论，实现时用测试确认：现有的 `land_test.go` 用并发度大于 1 的消费者再跑一遍，加一个“同一批订单乱序、重复投递”的用例。

### 2.4 轮询先读闸门

`GetOrder` 对非终态订单现在的顺序是：读订单行（MySQL）→ 没有再读占用（Redis）→ 再读一次订单行确认。刚受理、还在排队的订单，每次轮询都要白读两次 MySQL。

改成先读占用：

1. 缓存命中（终态）：直接返回。不变。
2. 读占用：
   - **有，未认领**：落库还没开始，主库上不可能有行（落库流程先认领再插入）。直接合成 `CREATING` 返回，不读 MySQL。
   - **有，已认领**：行可能已经在主库。读主库，有就返回，没有就按占用合成。
   - **没有**：读订单行（按读模式走从库或主库）。没有的话由主库确认，再走冷库（1c 步骤五）。
   - **读占用失败**（Redis 不可用）：退回现在的顺序，先读订单行；行不存在时和现在一样返回不可用。Redis 故障不应该让已落库的订单也查不到。

排队中的订单轮询只打 Redis（一次 Lua，几十微秒）。已落库的非终态订单（待支付）多一次 Redis 读，仍然要读 MySQL：它的占用是“已认领”，要到终态才归还。这部分轮询量和落库不重叠（落库已经完成），而且步骤二的限流会按用户限制轮询的频率。

**为什么这样改是对的。** 现在“先读行、再读占用、再读行”的三步是为了排除一个竞争：两次读之间订单落库并走完终态、占用被归还。先读占用之后这个竞争不存在了：占用没有，只可能是从未受理、已被回收，或者已经走到终态；最后一种情况下行一定已经提交，随后那次主库读看得到。所以只需要读一次行。

未认领时直接返回 `CREATING` 可能比真实状态旧一瞬间（读完占用的下一刻落库开始了），这对展示读是可接受的，下一次轮询就会更新。

这段代码决定订单状态怎么答，由 Fable 编写或逐行评审。

### 2.5 商家索引的消费者

阶段计划里写的是“改成按批写”。这一步先不做批量，直接用 2.2 的并发消费（并发度 16）：

- 它和落库是同一个问题（分区内串行），用同一个机制解决，kafkax 只多一个概念。
- 按批写要给 kafkax 再加一种 handler（收一批消息），批内同一个订单的多个版本要先合并，一批里一条失败怎么办（整批重试，还是拆开）也要定。收益是每行的往返更少，上限比并发更高。
- 并发 16、4 个分区是 64 路同时写，按现在每路约 500 行/秒算是 3 万行/秒的量级，超过 CDC 的产出。实测达不到 1 万行/秒再做按批写。

这一条和阶段计划的写法不同，主人已确认。

### 2.6 压测工具的开环模式

现在的 `load run` 是闭环的：每个虚拟用户提交一单、轮询到终态、再提交下一单。系统变慢时请求也跟着变少，量不出过载；“只管提交”是用 1 毫秒的轮询超时凑出来的。

新增 `-mode open -rate N`：

- 按固定的时间表发请求（每秒 N 个，均匀间隔），不管上一个有没有返回。并发数不设上限会在系统卡住时耗尽本机的连接，所以设一个在途请求的上限，超过时这个时刻的请求记为“未发出”，单独计数，不悄悄跳过。
- **延迟从“计划发出的时刻”算起**，不是从实际发出的时刻。系统卡住 1 秒时，这 1 秒里本该发出的请求都在排队，它们的延迟要算上排队的时间；只从实际发出算，会把最坏的那些样本漏掉（协调遗漏）。
- 压测期间不轮询。结束后有一个收尾阶段，把已受理订单的最终状态查出来写进账本，`load verify` 照常能用。
- 报告：计划速率、实际发出速率、各类结果（受理、被背压拒绝、被限流、超时、未发出）的数量，受理延迟的分位数，落库延迟（从受理到订单行出现）的分位数。

闭环模式保留，默认仍是闭环。

### 2.7 改完之后重新设定的参数

- `ADMIT_MAX_QUEUE`（等待落库的订单数上限）：现在的默认值是按 400 单/秒定的。按实测的落库吞吐乘以“愿意让订单排多久”（现在是回收宽限期的一半，约 25 秒）重新算。
- 落库并发度和订单库连接池（`MYSQL_MAX_OPEN_CONNS`）的关系：在途的落库数不能长期超过连接池，否则落库自己在池上排队。
- 这些数写进结果，步骤二、三的阈值以它们为基础。

### 2.10 结果（2026-11-14）

`make lint test e2e` 通过，`make chaos` 两次 PASS（并发消费下 19 项对账全过；第 15 项“受理后被回收”一次 0、一次 70，和以前一样只出现在 order 被杀之后）。

下面的数都是 `scripts/bench.sh` 在本机量的：开环、每秒 3000 个下单请求、持续 20 秒，10 个 SKU，两个订单库、inventory、payment 都在同一个 MySQL 实例上。原始输出在 `tmp/1d/`，不入库。本机的绝对值不可靠（见 1b 设计文档 7.3.4），看的是相对变化和瓶颈的位置。

**落库吞吐对并发度**

| `SUBMIT_CONCURRENCY` | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| 落库（单/秒） | 316 | 448 | 569 | 642 | 686 |
| 受理（单/秒） | 804 | 974 | 1112 | 1219 | 1305 |
| 被背压拒绝的比例 | 73% | 68% | 63% | 59% | 57% |

并发生效了，但到 2.2 倍就平了，没有到“下游资源用尽”那种量级。平的时候四个服务的 CPU 都很空闲（order 约三分之一个核），只有 MySQL 容器用了约 1.1 到 1.3 个核。

**瓶颈在哪：让 MySQL 自己说。** 清空 `performance_schema` 的语句统计后跑一次并发度 16，按总耗时排：

| 语句 | 次数 | 平均 | 其中等锁 |
|---|---|---|---|
| inventory：`UPDATE sku_stock SET available = available - ? ...` | 24679 | 48.4 ms | 几乎全部（累计 1192 秒） |
| 订单库 0 的 `COMMIT` | 24625 | 7.0 ms | 0 |
| inventory 的 `COMMIT` | 24654 | 6.9 ms | 0 |
| 订单库 1 的 `COMMIT` | 24646 | 6.8 ms | 0 |
| 其余所有语句 | | 0.3 ms 以下 | 0 |

两件事叠在一起：

1. **热门 SKU 的行锁。** 预占在一个事务里扣 `sku_stock` 的可售数，这一行的锁要拿到事务提交。10 个 SKU、64 个在途订单，大家在这 10 行上排队。
2. **提交很慢。** 每次提交约 7 毫秒（`sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`，容器里的文件系统刷盘本来就慢），一个订单落库要提交三次。它又拉长了第 1 条里持锁的时间：一行每秒最多被扣一百多次。

做了两个对照，各自只解释一部分，和上面的结论一致：

| 条件 | 并发度 1 | 并发度 16 |
|---|---|---|
| 默认 | 316 | 686 |
| 放宽刷盘（`sync_binlog=0`、`innodb_flush_log_at_trx_commit=2`，量完改回） | 571 | 848 |
| 100 个 SKU | | 800 |

串行时刷盘是主要成本（放宽后快了 80%），并发之后它不再是唯一的限制。

**这一步达到了什么，没达到什么。** 2.1 定的第一个目标是“落库吞吐随并发度上升，直到某个下游资源成为瓶颈，并且知道是哪一个”：达到了，瓶颈是 inventory 里同一个 SKU 的扣减在 MySQL 里是串行的。没有达到的是数量级的提升：1b 留下的“落库 400 单/秒”现在是 640 到 820，原因不再是消费者的结构。

热门行的扣减是秒杀的老问题，闸门（Redis）解决了受理这一侧，落库这一侧每个订单仍然要在 MySQL 里扣一次。常见的做法：把一个 SKU 的库存拆成多行（分桶），不同订单扣不同的行；把短时间内对同一个 SKU 的多个预占合并成一次扣减（一个事务扣 n 件、写 n 条预占记录）；或者预占只写流水、可售数异步汇总。放在 1d 的哪一步做，等主人定。

**轮询压力下的落库**（并发度 8，每秒 2000 个下单请求，另一个进程对最近受理的 2000 个订单每秒查询约 4600 次）

| | 落库（单/秒） | 查询延迟 p50 / p99 |
|---|---|---|
| 没有查询压力 | 821 | |
| 有查询压力 | 617 | 1.8 / 7.3 ms |

有查询压力时落库是没有时的 75%。1b 的数是 410 对 43（约 10%），当时的轮询是每个虚拟用户 50 毫秒一次、800 个用户，约 1.6 万次/秒，压力比这次大，两个比值不能直接比。能确定的是：排队中的订单被查询时不再读 MySQL（`TestQueuedOrderIsAnsweredWithoutTheOrderDB` 把订单库关掉也能答），剩下的 25% 来自已落库、待支付的订单，它们仍然要读订单行。这部分留给步骤二按用户限制查询频率。

**商家索引**

只在测试库上量了（同一个 MySQL 实例，每库连接池 25）：在途写入从 4 路（相当于改动前）加到 64 路（并发度 16 × 4 个分区），写入从约 2000 行/秒到 7600 到 9000 行/秒，32 路之后就平了。瓶颈同样是每次提交的刷盘：一行一个事务，每次约 1.2 毫秒，靠组提交把多路的提交合在一起刷，合到头就是这个数。

它低于 2.5 定的门槛（1 万行/秒）。按约定应当接着做按批写：一个事务写多行，直接减少提交次数，正好针对这个瓶颈。在真实数据上的追平速度没有量（要重新造一批变更）。

**参数**

- `ADMIT_MAX_QUEUE` 保持 1 万：按 640 到 820 单/秒算是排 12 到 16 秒，比原来按 400 算的 25 秒更保守。热门 SKU 的问题处理之后再调。
- `SUBMIT_CONCURRENCY` 默认 8：从 8 到 16 只多 7%，而在途数（64）已经超过两个订单库的连接池总和（50）。
- `INDEX_CONCURRENCY` 默认 16（之后改成按批写，换成了 `INDEX_MAX_BATCH`，见 2.11）。
- 共享 MySQL 实例的 `max_connections` 提到了 400：各服务的连接池加起来是 164，超过默认的 151，服务开着的时候跑测试会报 1040。

**实现中的发现**

- **并发之后，同一个幂等键的两个订单谁落库不再由受理的先后决定**（ADR-0017 后果一节）。
- **正常停止也会产生重复。** 测试里一次正常停止：处理了 923 条、提交了 661 条，重启后 262 条重做。停止时每条 lane 只做完手上的一条，前缀之后已完成的都要重来。这是设计内的行为，量出来比预想的多。
- **分 lane 的哈希不能用生产者分区的那个。** 一个分区里的 key 本来就是“哈希取模后相等”的一批，再用同一个哈希对 lane 数取模，lane 数和分区数有公因数时会挤进少数几条 lane。用了带随机种子的 `maphash`。
- **开环模式没有量落库延迟。** 网关的订单响应里没有落库时刻，压测期间又不轮询。报告里写明“未测”，落库吞吐仍从库里算。要量得在订单上暴露一个落库时间，或者等阶段 3 的指标。
- 每条语句执行前都有一次 `PREPARE`（上表之外，次数与执行数相同，每次约 0.04 毫秒）：驱动默认用服务端预处理、不缓存。耗时很小，但多一次往返；`interpolateParams` 可以去掉，没有做。
- 预热接口一次最多 100 个 SKU，压测脚本的 `BENCH_SKU_COUNT` 超过 100 会失败。

**没有做的**

- 热门 SKU 的扣减（上面）。
- 商家索引按批写（上面）。
- 商家索引在真实数据上的追平速度。
- 落库延迟的测量。
- `GetOrder` 对已落库、待支付订单的查询仍然读 MySQL。

### 2.11 商家索引按批写（步骤一的延续）

状态：主人已确认要做（2026-11-14）。决定记在 ADR-0017 的补充一节。

2.10 量到索引的写入在约 9000 行/秒见顶，瓶颈是一行一个事务、每个事务一次刷盘。按批写直接减少提交次数。

**kafkax 增加按批处理的消费者。**

```go
type BatchHandler func(ctx context.Context, msgs []Message) error

type BatchConsumerConfig struct {
    ConsumerConfig
    MaxBatch int // 一批最多多少条，默认 500
}
func NewBatchConsumer(ctx context.Context, cfg BatchConsumerConfig, handler BatchHandler) (*Consumer, error)
```

- **一批是一个分区里连续的一段。** worker 取本地队列里现成的记录，最多 `MaxBatch` 条，至少 1 条，交给 handler。不等凑满：没有积压时一批就是一条，延迟和现在一样；有积压时批自然变大。所以不需要“攒多久”这个参数。
- **成功**：整批完成，位点提交到这一批的最后一条。
- **失败**：handler 返回错误时，暂时性的错误先整批重试（共 3 次）；仍然失败，或者错误是 Permanent 的，这一批退回逐条处理：每条消息单独作为一条的批交给同一个 handler，走和普通消费者完全相同的重试和死信。这样一条坏消息不会让整批反复失败，也不需要 handler 自己报告“是哪一条”。第一版没有整批重试，任何错误都直接逐条：数据库抖一下，第一条重试到恢复之后其余几百条各自提交一次，正确但按批的意义就没有了（orderindex 的子 Agent 指出）。
- 批内按位点顺序排列，同一个 key 的多条消息保持先后。
- 和 `Concurrency` 互斥，延迟消费者不支持。按批已经把一个分区的写入合成了一次提交，再分 lane 并行只会让事务之间互相等。

**orderindex 改用按批的消费者。** 一批消息：

1. 逐条解码。解不了的（消息本身坏了）返回 Permanent 错误，触发上面的逐条回退，坏的那条进死信。
2. 同一个订单在一批里出现多次时只留版本最高的映像（带版本号的 upsert 本来也会收敛到它，先合并少写几行）。
3. 按索引的 slot 分组，每张索引表一条多行的 `INSERT ... AS new ON DUPLICATE KEY UPDATE`，版本比较的写法不变（版本列最后赋值）。同一个库上的几张表放在一个事务里。
4. 两个索引库是两个事务，不是原子的：一个成功一个失败时整批返回错误，重做时成功的那一半是空操作。
5. 统计（Changed、Stale 等）：多行 upsert 拿不到逐行的结果。用受影响行数区分不了“新插入”和“更新”的各自条数时，统计改成按批给出受影响的行数，Stale 用“写入的行数减去实际改变的行数”估算；具体做法实现时定，原则是不为了统计多读一次库。

目标：本机测试库上超过 2 万行/秒（一批 500 行、4 个分区）。`INDEX_CONCURRENCY` 这个刚加的配置随之去掉，换成 `INDEX_MAX_BATCH`（默认 500，上限 6553：一条语句最多 65535 个占位符、每行 10 列）；还设着旧变量时拒绝启动。

**结果**（2026-11-14，测试库，4 路并行模拟 4 个分区，每库连接池 8）：

| 每批行数 | 带 `-race` | 不带 `-race` |
|---|---|---|
| 1 | 1700 行/秒 | 2100 行/秒 |
| 50 | 3.3 万 | 4.6 万 |
| 500 | 4.8 万 | 7.9 万 |

比按 key 并发的上限（约 9000）高一个数量级。印证了瓶颈是提交次数：一批 500 行只提交一次。

实现时定下来的几点：

- **统计**：多行 upsert 分不出逐行的结果。精确的有 `written`（合并后实际写库的行数）、`merged`（批内被更高版本顶掉的映像）和原有的跳过、忽略、归档、延迟。`changed_est` 取每条语句“受影响行数”和“写入行数”中较小的一个，是实际改变行数的上界，没有重放时是精确的；`stale_est` 是剩下的。日志字段名带 `_est` 就是为了不让人把它当精确值。
- **每条语句里的行按主键排序**再写，不同分区的批并发写同一张表时加锁顺序一致，减少死锁。二级索引上的锁顺序仍然可能交叉，出现时整个事务回滚、作为可重试的错误返回；测试里没有出现过。
- 一个库只有一条语句时不开显式事务（自动提交），一条消息的批和原来一样是一次往返。两个索引库并行写。
- 每个索引库的连接池从 25 降到 10：同时在途的事务最多是每个分区一个。

kafkax 的按批消费由 Fable 写；orderindex 的改造派给 Opus。

## 3. 步骤一的延续：MySQL 侧的库存扣减改成异步

状态：主人已确认（2026-11-14）：先做方案 A，量完再决定要不要做方案 B；接受 3.4 的代价（MySQL 从阻止超卖变成发现超卖）。决定见 ADR-0018。

### 3.1 现在的问题

落库时 order 同步调 inventory 的 `Reserve`，它在一个事务里做三件事：

1. 插入预占记录（`reservation`、`reservation_item`）。这是幂等记录和流水，每个订单各写各的行。
2. `UPDATE sku_stock SET available = available - ?, reserved = reserved + ? WHERE sku_id = ? AND available >= ?`。**所有买这个 SKU 的订单都改同一行**，行锁要拿到事务提交。
3. 读这些 SKU 的价格和商家，返回给 order。

第 2 步是 2.10 量到的瓶颈：平均等锁 48 毫秒。支付后的确认、取消后的释放（由 inventory 消费订单事件来做）改的也是这一行，和预占抢同一把锁。

第 2 步在 1a 是防超卖的核心。1b 加了库存闸门之后，能不能卖是 Redis 里先判断的：闸门原子地扣可售、记占用，不会超卖。MySQL 这一步成了第二道检查，绝大多数时候只是在重复闸门已经做过的判断，却要每个订单串行地做一次。

### 3.2 两种做法

**方案 A：库内流水表，单个应用者合并更新。**

```
Reserve / Confirm / Release（各自的事务里）
    写预占记录、改预占状态          ← 和现在一样
    INSERT INTO stock_pending ...   ← 新：只记“这个 SKU 的三个数各要变多少”，不碰 sku_stock

应用者（inventory 里的一个后台任务）
    取一批 stock_pending → 按 SKU 求和 → 每个 SKU 一条 UPDATE sku_stock → 删掉这批 → 提交
```

热点行从“每个订单改一次”变成“每批改一次”。`Reserve` 仍然是同步的 gRPC，接口、幂等、价格快照、多商家检查都不变。

**方案 B：经 Kafka 异步，inventory 按批消费。** order 落库时不再调 `Reserve`：它自己读（缓存的）价格和商家，算出金额，订单直接进入待支付，同时发一条“请求预占”的事件；inventory 按批消费，一个事务里写一批订单的预占记录、每个 SKU 一条合并的更新。这是最常见的“Redis 预扣、消息队列异步落库”的形态，落库路径上少一次同步调用和一次提交，上限更高。

**建议 A。** 理由：

- **没应用的增量要能和计数在同一个快照里读到。** 闸门从 MySQL 装载（预热）时需要“真实的可售数”，等于 `sku_stock.available` 加上还没应用的增量。A 的增量在同一个库里，一次一致性读就能算准。B 的增量在 Kafka 里，装载的那一刻有多少还在路上是不知道的，装进闸门的数会偏大，这正是会造成超卖的方向。要补就得再维护一份“已发未应用”的账。
- **“应用一次且仅一次”需要“改计数”和“标记已应用”在一个事务里。** A 天然如此（更新和删除在同一个事务）。B 是至少一次投递，仍然要靠预占记录的唯一键去重，等于在消费端把 A 的事务再做一遍。
- **改动面。** A 只动 inventory 内部，order 和契约不变。B 要改 order 的落库流程（金额谁算、多商家谁查、预占失败怎么通知回来）、新增事件、改 1a 以来“预占成功才进入待支付”的语义。
- B 多出来的收益（落库少一次同步调用）在热点行解决之后才看得出值不值，可以等 A 做完再量。Kafka 已经承担了落库本身的异步，这里要解决的只是“计数那一行”。

### 3.3 方案 A 的细节

**表**

```sql
CREATE TABLE stock_pending (
    id           BIGINT NOT NULL AUTO_INCREMENT,
    sku_id       BIGINT NOT NULL,
    d_available  BIGINT NOT NULL,   -- 预占 -n，释放 +n，确认 0
    d_reserved   BIGINT NOT NULL,   -- 预占 +n，释放 -n，确认 -n
    d_sold       BIGINT NOT NULL,   -- 确认 +n
    order_id     BIGINT NOT NULL,   -- 排查用
    created_at   DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    KEY idx_stock_pending_sku (sku_id)
);
```

应用之后删除。它是一张队列表，不是流水；流水是 `reservation` 和 `reservation_item`，已经有了。

**写入方**。`Reserve`、确认、释放的事务里，原来调 `ReserveStock`、`ConfirmStock`、`ReleaseStock` 的地方改成插入一行 `stock_pending`。预占记录的状态机、唯一键互斥、空回滚都不变：它们保证每个订单的每次状态变化只发生一次，所以每个增量只会被写一次。

**应用者**。inventory 里的周期任务，每个实例各跑一个（实现时去掉了 leader 锁，见 3.7）：

```
BEGIN
SELECT id, sku_id, d_available, d_reserved, d_sold FROM stock_pending ORDER BY id LIMIT 1000 FOR UPDATE   -- READ COMMITTED
按 SKU 求和
对每个 SKU（按 sku_id 升序）:
    UPDATE sku_stock SET available = available + ?, reserved = reserved + ?, sold = sold + ? WHERE sku_id = ?
DELETE FROM stock_pending WHERE id IN (...)
COMMIT
```

有积压就连着做，空了就等一小段（默认 20 毫秒）。

- **为什么按 id 顺序、加普通的 `FOR UPDATE`，不用 `SKIP LOCKED`。** 同一个订单的增量有先后：先预占（`reserved +n`），后释放（`reserved -n`）。跳过被锁住的行会让后面的先应用，`reserved` 出现一瞬间的负数，撞上 CHECK 约束。按 id 顺序、不跳过，就不会。两个应用者同时跑时，后一个在行锁上等，等到之后这些行已经被删了，它读到的是后面的行，不会重复应用。
- **为什么不用“记一个已应用到哪个 id 的水位”。** 自增 id 的分配顺序和事务提交的顺序不一致：id 小的事务可能后提交，水位已经越过它，它就永远不被应用。这是用自增 id 做位点的经典错误。取“当前看得见的行”再删掉，没有这个问题。

**读“真实的数”**。凡是拿 `sku_stock` 的数去做判断的地方，都要加上没应用的增量，在一个一致性读里：

```sql
SELECT s.available + COALESCE(SUM(p.d_available), 0), s.reserved + COALESCE(SUM(p.d_reserved), 0), ...
FROM sku_stock s LEFT JOIN stock_pending p ON p.sku_id = s.sku_id WHERE s.sku_id = ? GROUP BY s.sku_id
```

- 闸门的预热（装载可售数）：必须用。
- 闸门和 MySQL 的对账（`reconcile`）：必须用。它比较的是 `available + reserved`，预占和释放不改变这个和，确认会。
- `GetStock`（展示，带缓存）：原计划直接读 `sku_stock`，实现时也改成了读真实的数（见 3.7）。

### 3.4 语义上变了什么（要主人知道的代价）

1. **“MySQL 没货”不再在预占时发现。** 现在闸门有货而 MySQL 没货时，`Reserve` 返回库存不足，订单创建失败。改了之后 `Reserve` 不看可售数，这种订单会成功。发现它的地方变成应用者：把增量加到 `sku_stock` 上时 `available` 会变负，被 CHECK 约束拒绝。这时应用者跳过这个 SKU 的全部增量（保持先后），记错误日志并计数，其他 SKU 照常；这个 SKU 的增量留在表里，直到人把库存对上。
   也就是：MySQL 这一侧从**阻止**超卖变成**发现**超卖。阻止超卖完全靠闸门。闸门出错的途径是它和 MySQL 对不上（有人直接改了 `sku_stock`、对账修正有缺陷、Redis 丢数据后装载错了），这些以前有 MySQL 兜底，以后没有。
2. **`sku_stock` 的三个数会落后**，量级是应用者的一轮（几十毫秒），积压时更久。恒等式 `available + reserved + sold = 入库总量` 在任何时刻仍然成立（每个增量自身三项之和为零）；“加上未应用的增量之后三个数都不为负”才是新的不变量。
3. **阶段计划里步骤四的降级预案“Redis 不可用时退回数据库扣减”要重新设计。** 没有闸门时 MySQL 必须同步地判断并扣减，那就得先把这个 SKU 的增量应用完，再走原来的条件更新。这一步的设计里要给它留出一个同步的 `Reserve` 模式，步骤四再接。

### 3.5 测试

- 并发预占同一个 SKU：不再有行锁等待；全部应用后 `sku_stock` 与逐个串行应用的结果相同。
- 应用者：按 SKU 合并；重复运行、两个同时运行，每个增量恰好应用一次；中途被杀（事务回滚）后重做，结果相同。
- 先预占后释放的订单，无论分在一批还是两批，`reserved` 从不为负。
- 预热和对账在有未应用增量时读到的是真实的数：预占之后、应用之前装载闸门，装进去的可售数已经扣掉了这笔预占。
- 超卖的发现：人为把 `sku_stock.available` 改小，预占照常成功，应用者跳过这个 SKU 并报错，其他 SKU 不受影响；把库存补上之后自动恢复。
- 现有的全部测试（1a 的并发扣减、空回滚、重复预占、1b 的事件消费和对账）在“应用者追平之后再断言”的前提下通过。
- 实测：同 2.10 的条件重跑落库吞吐对并发度，再看 `performance_schema` 里瓶颈移到了哪。

### 3.6 实现顺序

库存的扣减是这个系统里最核心的一致性代码，这一步的产品代码由 Fable 写：迁移、store 的三个写入点、应用者、读真实数的查询。测试的铺开（把现有测试改成先等应用者追平、新增并发和故障用例）派给 Opus，Fable 评审。`scripts/chaos.sh` 和 `load verify` 里读 `sku_stock` 的检查要改成先等增量应用完，派给 Sonnet。

### 3.7 实现中的调整（2026-11-14）

- **应用者不用 leader 锁，每个实例各跑一个。** `ApplyPending` 靠增量行上的行锁互斥：后到的等先到的提交，之后读到的是剩下的行。这样它不依赖 Redis，闸门所在的 Redis 不可用时 MySQL 的计数照常更新；也少了一个“锁丢了、两个同时跑”要论证的情形，因为两个同时跑本来就是对的。
- **应用者的事务用 `READ COMMITTED`。** `REPEATABLE READ` 下带 `LIMIT` 的加锁读在行数不足一批时会一直扫到索引末尾并锁住末尾的间隙，而所有新增量都插在末尾：预占、确认、释放会被应用者的事务挡到它提交。
- **`GetStock` 统一返回真实的数**，不分“做判断的读”和“展示的读”。多出来的是一次按 SKU 的索引求和，表很小。好处是只有一种读法，不会有人误用落后的那个；直接读 `sku_stock` 的只剩排查问题时的手工查询。
- **`SKIP LOCKED` 的害处是误报，不是算错。** 改坏验证时把 `FOR UPDATE` 换成 `SKIP LOCKED`，最终的数仍然正确：先后被打乱时某个数会短暂为负，CHECK 约束拒绝这次更新，应用者把这个 SKU 报成卡住，下一轮连同前面的增量一起应用就恢复了。但每一次都是一条“超卖”的错误日志。第一版的并发测试没有检查这一点（只看了最终的数和恒等式），改坏之后照样通过；补上“库存充足时应用者不应报告任何卡住的 SKU”之后才抓得到。
- **卡住的 SKU 平时要绕开。** 它的增量留在表头，不绕开的话会把每一批占满，别的 SKU 轮不到。应用者记着卡住的 SKU，平时的批次排除它们，每秒带上它们重试一次；看完整张表而它们不再出现时算恢复。
- **合计为零的批也执行更新。** 一批里同一个订单先预占后释放，三个增量加起来都是零。仍然执行这条更新并额外确认行存在，否则“SKU 不存在”的增量会被当成已应用而删掉。
- **停止时的顺序**：应用者最后停（gRPC 的预占、消费者的确认和释放收尾时还在写增量），停了之后再收一次尾。没应用完的增量留到下次启动也是对的，读库存的地方都会把它们加上。

### 3.8 测试铺开时的发现（2026-11-14）

inventory 的测试由 Opus 子 Agent 修正和铺开（只许改测试文件），发现并钉住了两个产品代码的缺陷，已修：

- **超卖时预热失败。** 真实可售数为负时原样传给闸门，闸门当作参数错误拒绝，对外成了“闸门不可用，请重试”，调用方会对一个数据问题无休止地重试。改成按 0 装载并记错误日志。
- **超卖时对账失效。** 修正偏差时把 MySQL 的可售数当上限传给闸门，为负时报错。闸门装多了导致超卖时，对账是唯一能把闸门收紧的机制，它恰好在这时不工作，闸门会继续卖。改成上限取 0，修正把闸门收到 0。

两个是同一个原因：3.4 写了“加上未应用的增量之后三个数都不为负才是新的不变量”，而超卖正是这个不变量不成立的时候，下游的读者没有为负数做准备。**一个值的取值范围变了，要把它所有的读者过一遍。**

由此定下的约定：inventory 的 `GetStock` 接口照实返回（超卖时 `available` 为负），它也给对账和排查用；面向买家的展示由 gateway 截到 0。

子 Agent 指出的设计问题，没有改，记在这里：

- **MySQL 一侧能不能发现短暂的超卖，取决于分批。** 一批之内的增量是先求和再更新的：预占超过了库存，但它的释放落在同一批里，合计不为负，就不会被报出来。分在两批里才会。所以“应用者发现超卖”对持续的超卖是确定的，对短暂的不确定。持续的超卖最终一定被发现；`load verify` 的第 22 项在静止后把关。
- **卡住的 SKU 恢复的条件是“表头那一批够扣”，不是“净额够”。** 重试时取的是最老的一批行；这个 SKU 在这一批里的合计为负就继续卡着，即使更后面的释放已经让净额够了。默认一批 1000 行，要一个 SKU 有上千行未应用的增量才会遇到，这时本来也需要人来看。
- **应用者会等还没提交的增量行。** `FOR UPDATE` 遇到别的事务刚插入、还没提交的行会等它提交。一个慢的预占事务会拖住这一批的应用。这同时也是先后不被打乱的原因，所以没有改；预占的事务只有几条语句。
- `Applier.Stuck()` 不是并发安全的，循环运行期间不能从别的 goroutine 调用。以后给监控用要加锁。
- order 的测试用假的 inventory，它仍然在可售数不够时拒绝预占。真实的 inventory 不再这样做。order 处理 `INSUFFICIENT_STOCK` 的代码作为防御保留，相关的测试注明了“这是防御用例，不代表系统现在的行为”。
- e2e 没有“闸门有货而 MySQL 没货”的用例：它要在共用的服务上人为制造闸门和 MySQL 的差，容易污染别的用例。这个行为由 inventory 的集成测试和 `load verify` 第 22 项的测试覆盖。

每个 inventory 测试结束时现在会自动把增量应用完（批大小故意取 3，让一个订单的预占和释放落在不同的批里），并断言没有意外卡住的 SKU、增量表为空、`sku_stock` 的三个数不为负且总量守恒。相当于给每个现有测试都加了一条“应用之后账是平的”。

### 3.9 结果（2026-11-14）

`make lint test e2e` 通过。`make chaos` 两次 PASS：22 项对账全过，其中第 22 项（库存增量都已应用）在静止后是 0 行，说明 inventory 被 `kill -9` 后重启的应用者把留下的增量接着应用完了。

落库吞吐，条件同 2.10（开环每秒 3000 个下单请求、20 秒、10 个 SKU、所有库在同一个 MySQL 实例上）：

| `SUBMIT_CONCURRENCY` | 1 | 8 | 16 | 32 |
|---|---|---|---|---|
| 改之前（2.10） | 316 | 642 | 686 | |
| 异步扣减之后 | 320 | 789 | 870 | 985 |
| 改之前，放宽刷盘 | 571 | | 848 | |
| 异步扣减之后，放宽刷盘 | | | 1064 | 1034 |

**热点行的锁没有了。** 并发度 16 时的语句统计里，`UPDATE sku_stock` 不在前十（改之前它平均 48 毫秒、累计等锁 1192 秒）。应用者的两条语句（取增量、删增量）共约 500 次，把三万次预占合并成了几百次更新。

**吞吐只涨了 23% 到 27%，因为下一个瓶颈紧跟在后面：提交。**

| 语句（并发度 16，正常刷盘） | 次数 | 平均 |
|---|---|---|
| inventory 的 `COMMIT` | 29972 | 9.1 ms |
| 订单库 0 的 `COMMIT` | 29950 | 8.9 ms |
| 订单库 1 的 `COMMIT` | 29457 | 8.9 ms |
| 其余每条语句 | | 0.5 ms 以下 |

一个订单落库要提交三次，共约 27 毫秒，几乎就是它在 MySQL 里的全部时间。每秒约 2600 次提交已经是这个实例（容器里的文件系统、`sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`）的上限，并发度从 16 加到 32，提交只是排得更久。

**放宽刷盘之后，MySQL 不再是瓶颈，但吞吐停在约 1050，原因没有找到。** 这时每次提交 1.3 到 1.7 毫秒，一个订单在 MySQL 里总共约 5.5 毫秒，采样时 MySQL 只有 7 个线程在运行、103 个连接里 2 个在执行。而 64 个在途、每秒 1055 单意味着每个订单在途约 60 毫秒。剩下的约 54 毫秒不在 MySQL 里，四个服务的 CPU 也都很空闲。可能是 1b 就怀疑过的本机网络问题（OrbStack 的端口转发在高包速率下丢包，一次重传约 200 毫秒；这几轮受理延迟的 p99 正好在 200 到 470 毫秒），也可能是 order 进程内的某处等待。没有链路追踪，分不出来。这是步骤六（埋点）要回答的问题，也是 1b 把吞吐结论挂到阶段 2 的原因。

**结论**

- 这一步消掉了一个真实的、会随 SKU 热度恶化的瓶颈：以前吞吐取决于有多少订单抢同一个 SKU（10 个 SKU 时 686，100 个时 800），现在与此无关。秒杀场景（所有人买同一个 SKU）受益最大，压测用的 10 个 SKU 低估了它。
- 本机在正常刷盘下的落库上限现在是提交次数决定的：每个订单三次。要再提高，得减少每个订单的提交次数。方案 B（inventory 按批消费，把它的那一次提交摊到几百个订单上）能去掉三次里的一次；订单库的两次（插入订单行、改成待支付）是另一个可以合并的地方。
- 落库吞吐从 1b 的约 400 到了 790（默认并发度 8），不是数量级。数量级的结论仍然要到阶段 2 的集群上、有链路追踪之后才能下。

**参数**：`ADMIT_MAX_QUEUE` 仍然保持 1 万（按 790 单/秒是排约 13 秒）。`SUBMIT_CONCURRENCY` 默认仍是 8。

**没有做的**

- 方案 B：主人决定先不做（2026-11-14）。剩下的时间花在哪还不清楚，等有了埋点（步骤六）或上了集群再判断它值不值。
- 放宽刷盘后那约 54 毫秒的去向。
- 应用延迟（增量从写入到被应用的时间）没有单独量；应用者每 10 秒的汇总日志里有 `max_age_ms`，压测里没有收集。
- `stock_pending` 的行数和最老一行的年龄应当有指标和告警（阶段 3）。
