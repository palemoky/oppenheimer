# 1d 设计：限流、熔断、降级与对账

本文是阶段 1d 的实现规格。1c 之后系统的功能和数据布局已经齐了，1d 做的是让它在过载和依赖故障时表现得可预期，再加一个能定位数据差异的对账工具。

状态：第 1、2 节主人已确认（2026-11-14）：按五步的顺序做；落库用分区内按 key 并发；商家索引先复用并发消费，达不到 1 万行/秒再做按批写。其余各步在动工前细化。

## 1. 分六步走

每一步结束时系统都能运行，`make lint test e2e` 通过。

| 步骤 | 内容 | 对应阶段计划里的任务 |
|---|---|---|
| 一 | 把吞吐的欠账还掉：落库并发、轮询不再和落库抢连接、商家索引追得上、压测工具的开环模式 | 1b 压测遗留的落库性能问题、orderindex 按批写、开环模式 |
| 二 | 网关限流：令牌桶，按接口、按用户、按 IP；单机和 Redis 分布式两种 | 网关限流 |
| 三 | 服务侧保护：sentinel-go 的熔断、并发隔离、热点参数限流；全链路的超时预算和重试规范 | 服务侧保护、超时与重试规范、1b 遗留的小问题 |
| 四 | 降级预案和优雅启停：Redis 不可用、冷库不可用、从库落后、inventory 超时各自怎么退；摘流、排空、关闭顺序 | 降级预案、优雅启停 |
| 五 | 对账：`pkg/merkle`，用于订单对支付、订单对库存流水、Redis 对 MySQL，以及主从、CDC 索引、冷热归档 | 对账 |
| 六 | 埋点：OpenTelemetry 的链路和指标，贯穿 HTTP、gRPC、Kafka、MySQL、Redis | 埋点（ADR-0004） |

**为什么先还吞吐的欠账。** 限流的阈值、熔断的阈值、背压的队列长度都要对着“系统实际能处理多少”来定。现在落库只有约 400 单/秒，是串行造成的，不是资源用尽；在这个数上定下的阈值，落库改完就全部作废。另一个原因是测量工具：没有开环的压测，过载下的行为（限流该不该触发、触发后延迟是否稳住）量不出来，步骤二到四的验收都要靠它。

**为什么对账放最后。** 它和前四步没有依赖，放在哪里都行。放最后是因为前四步会改动消费者和降级路径，对账工具正好拿来验证这些改动之后数据仍然一致。

**步骤六是写完前五步的划分之后补上的**（2026-11-14）：阶段计划的 1d 清单里还有一项埋点，第一次划分时漏了。放在最后是因为它不改变行为，而且前五步新增的限流、熔断、并发消费都是需要埋点的地方，等它们定型后一次加完；后端（SkyWalking、指标存储）在阶段 3。主人已确认（2026-11-14）。

步骤三的两个 1b 遗留小问题（调用方取消被记成 ERROR、payment 启动时 Redis 不可用就启动失败）和 Guard 调用的超时，归到各自相关的步骤里（三、四、三）。

## 2. 步骤一：吞吐的欠账

决定和备选方案见 ADR-0017。

### 2.1 现状和目标

三个已经量到的问题（1b 设计文档 7.3.4、1c 设计文档 5.11）：

| 问题 | 现在 | 原因 |
|---|---|---|
| 落库吞吐 | 约 410 单/秒，MySQL 和 inventory 都很空闲 | 4 个分区，每个分区一条一条处理，每条约 10 毫秒（一次 Redis、一次 gRPC、两个事务） |
| 轮询拖垮落库 | 800 个用户每 50 毫秒轮询时，落库从 410 跌到 43 单/秒 | 非终态订单不缓存，`GetOrder` 先查 MySQL，和落库共用连接池 |
| 商家索引追不上 | 约 2000 行/秒写入，500 万行要 40 分钟 | 同样是分区内串行，每条一次写库 |

前两个和第三个是同一个原因：**消费者在一个分区内是串行的**，吞吐上限是“分区数 ÷ 单条耗时”，和下游有多少余量无关。

目标不是某个绝对数字（本机的吞吐测量受 OrbStack 端口转发干扰，结论要到阶段 2 的集群上才算数），而是三件可以在本机判断的事：

1. 落库吞吐随并发度上升，直到某个下游资源（连接池、inventory、MySQL）成为瓶颈，并且知道是哪一个。
2. 轮询的压力不再影响落库吞吐。
3. 商家索引的写入速度超过 CDC 的产出速度（归档时约 1 万条/秒）。

### 2.2 分区内按 key 并发消费

给 `pkg/kafkax` 的消费者加一个并发度（`ConsumerConfig.Concurrency`，默认 1，即现在的行为）。

```
                       ┌─ lane 0 ─ handler ─┐
拉取 → 分区的本地队列 → 分发（hash(key) % N）─┼─ lane 1 ─ handler ─┼→ 完成表 → 提交连续前缀
                       └─ lane N-1 ─ handler┘
```

**顺序。** 同一个 key 的消息总是进同一条 lane，lane 内串行。所以“同一个订单的消息按序处理”仍然成立，不同订单之间本来就没有顺序要求。这是并发消费能做而不出错的前提，也是它和“开一个协程池随便处理”的区别。

**位点提交。** Kafka 一个分区只有一个已提交位点，表示“这之前的都处理完了”。并发之后消息不按偏移量的顺序完成：偏移量 7 做完了而 5 还在重试，这时只能提交到 5，不能提交到 8，否则重启后 5 就丢了。做法是记录在途的偏移量，可提交的位点是“最小的未完成偏移量”；没有在途的消息时是“最后分发的偏移量加一”。

由此的后果：重启或再平衡后，7 会被重新处理一次。并发消费把“重复投递”从偶发变成了常态，handler 必须幂等。本项目的 handler 从 1b 起就按至少一次设计，这一条已经满足。

**一条消息卡住时。** 现在一条消息在原地重试，整个分区停住。并发之后只有它所在的 lane 停住，其他 lane 继续，但提交的位点被它拖着不动。不加限制的话，“已处理未提交”的跨度会无限增长，一次重启要重放全部。所以加一个窗口（默认 1024）：分发的偏移量超过最小未完成偏移量这么多时，停止分发，这个分区等它。到这一步行为和现在相同（分区停住），窗口只是让短暂的重试不拖住其他订单。

**重试、死信**的语义不变，都发生在 lane 内：原地重试期间这条 lane 不前进；进死信的消息算作完成。

**再平衡和停止。** 分区被收回时：停止分发，等各 lane 做完手上的那一条，提交连续前缀。前缀之后已经完成的消息会被新的持有者重新处理。强制取消时同现在一样立刻放弃。

**延迟消费者不允许并发**（`Concurrency > 1` 时构造函数报错）。延迟 topic 依赖“分区内按到期时间有序、队首没到期就等”，并发会破坏这个假设。

**哪些消费者开并发：**

| 消费者 | 并发度 | 理由 |
|---|---|---|
| order 的 `order.submit`（落库） | 8（可配） | 这一步的目标。key 是订单号，不同订单互不相干 |
| orderindex 的 `cdc.order.orders` | 16（可配） | key 是订单号；写入按行版本号幂等，乱序也收敛 |
| order 的支付结果、延迟关单 | 1 | 量小；延迟关单不允许 |
| inventory 的订单事件 | 1 | key 是订单号，但处理时锁的是 SKU 行：同一个 SKU 的不同订单并发处理只会在行锁上排队，还会让死锁重试变多。它也不是瓶颈 |
| payment 的订单事件 | 1 | 量小 |

落库并发 8、4 个分区，同时在途 32 个订单；每个订单库的连接池是 25，默认 2 个库共 50（本机扩容后是 4 个库共 100）。order 启动时比较这两个数，在途上限超过连接池总和时打一条警告。并发度上去之后瓶颈预计转到 inventory 的 `Reserve`（热门 SKU 的行锁）或订单库的连接池，实测后写进结果。

**核心代码归属**：分发、完成表、提交位点的计算是并发加一致性的代码（提交错了就是丢消息），由 Fable 编写，带 `-race` 的测试和并发场景的测试：乱序完成时提交的位点、卡住一条时窗口生效、再平衡时不提交未完成的、同一个 key 不并发。

### 2.3 落库并发之后要重看的地方

并发消费改变了落库路径上“同一时刻只有一条在处理”的假设。逐个检查：

- **`Claim` 的心跳和探测名额**（ADR-0011）：按消息独立，不依赖串行。
- **订单号的幂等**：同一个订单号的重复消息在同一条 lane 里串行，和现在一样。
- **同一个用户的不同订单**并发落库：`(user_id, idempotency_key)` 的唯一约束仍然由数据库保证；“幂等键过期后的重放”那条路径（`dropReplay`）读的是已提交的数据，两条重放并发时一条插入成功、另一条撞唯一键后走重放，结果相同。
- **`Reserve` 的并发**：inventory 里同一个 SKU 的并发预占靠行锁排队，1a 起就有并发测试。多个 SKU 的订单按固定顺序加锁，不死锁。
- **落库的重试上限**（10 次，约 26 秒）和回收宽限期的关系不变。

这些是读代码的结论，实现时用测试确认：现有的 `land_test.go` 用并发度大于 1 的消费者再跑一遍，加一个“同一批订单乱序、重复投递”的用例。

### 2.4 轮询先读闸门

`GetOrder` 对非终态订单现在的顺序是：读订单行（MySQL）→ 没有再读占用（Redis）→ 再读一次订单行确认。刚受理、还在排队的订单，每次轮询都要白读两次 MySQL。

改成先读占用：

1. 缓存命中（终态）：直接返回。不变。
2. 读占用：
   - **有，未认领**：落库还没开始，主库上不可能有行（落库流程先认领再插入）。直接合成 `CREATING` 返回，不读 MySQL。
   - **有，已认领**：行可能已经在主库。读主库，有就返回，没有就按占用合成。
   - **没有**：读订单行（按读模式走从库或主库）。没有的话由主库确认，再走冷库（1c 步骤五）。
   - **读占用失败**（Redis 不可用）：退回现在的顺序，先读订单行；行不存在时和现在一样返回不可用。Redis 故障不应该让已落库的订单也查不到。

排队中的订单轮询只打 Redis（一次 Lua，几十微秒）。已落库的非终态订单（待支付）多一次 Redis 读，仍然要读 MySQL：它的占用是“已认领”，要到终态才归还。这部分轮询量和落库不重叠（落库已经完成），而且步骤二的限流会按用户限制轮询的频率。

**为什么这样改是对的。** 现在“先读行、再读占用、再读行”的三步是为了排除一个竞争：两次读之间订单落库并走完终态、占用被归还。先读占用之后这个竞争不存在了：占用没有，只可能是从未受理、已被回收，或者已经走到终态；最后一种情况下行一定已经提交，随后那次主库读看得到。所以只需要读一次行。

未认领时直接返回 `CREATING` 可能比真实状态旧一瞬间（读完占用的下一刻落库开始了），这对展示读是可接受的，下一次轮询就会更新。

这段代码决定订单状态怎么答，由 Fable 编写或逐行评审。

### 2.5 商家索引的消费者

阶段计划里写的是“改成按批写”。这一步先不做批量，直接用 2.2 的并发消费（并发度 16）：

- 它和落库是同一个问题（分区内串行），用同一个机制解决，kafkax 只多一个概念。
- 按批写要给 kafkax 再加一种 handler（收一批消息），批内同一个订单的多个版本要先合并，一批里一条失败怎么办（整批重试，还是拆开）也要定。收益是每行的往返更少，上限比并发更高。
- 并发 16、4 个分区是 64 路同时写，按现在每路约 500 行/秒算是 3 万行/秒的量级，超过 CDC 的产出。实测达不到 1 万行/秒再做按批写。

这一条和阶段计划的写法不同，主人已确认。

### 2.6 压测工具的开环模式

现在的 `load run` 是闭环的：每个虚拟用户提交一单、轮询到终态、再提交下一单。系统变慢时请求也跟着变少，量不出过载；“只管提交”是用 1 毫秒的轮询超时凑出来的。

新增 `-mode open -rate N`：

- 按固定的时间表发请求（每秒 N 个，均匀间隔），不管上一个有没有返回。并发数不设上限会在系统卡住时耗尽本机的连接，所以设一个在途请求的上限，超过时这个时刻的请求记为“未发出”，单独计数，不悄悄跳过。
- **延迟从“计划发出的时刻”算起**，不是从实际发出的时刻。系统卡住 1 秒时，这 1 秒里本该发出的请求都在排队，它们的延迟要算上排队的时间；只从实际发出算，会把最坏的那些样本漏掉（协调遗漏）。
- 压测期间不轮询。结束后有一个收尾阶段，把已受理订单的最终状态查出来写进账本，`load verify` 照常能用。
- 报告：计划速率、实际发出速率、各类结果（受理、被背压拒绝、被限流、超时、未发出）的数量，受理延迟的分位数，落库延迟（从受理到订单行出现）的分位数。

闭环模式保留，默认仍是闭环。

### 2.7 改完之后重新设定的参数

- `ADMIT_MAX_QUEUE`（等待落库的订单数上限）：现在的默认值是按 400 单/秒定的。按实测的落库吞吐乘以“愿意让订单排多久”（现在是回收宽限期的一半，约 25 秒）重新算。
- 落库并发度和订单库连接池（`MYSQL_MAX_OPEN_CONNS`）的关系：在途的落库数不能长期超过连接池，否则落库自己在池上排队。
- 这些数写进结果，步骤二、三的阈值以它们为基础。

### 2.10 结果（2026-11-14）

`make lint test e2e` 通过，`make chaos` 两次 PASS（并发消费下 19 项对账全过；第 15 项“受理后被回收”一次 0、一次 70，和以前一样只出现在 order 被杀之后）。

下面的数都是 `scripts/bench.sh` 在本机量的：开环、每秒 3000 个下单请求、持续 20 秒，10 个 SKU，两个订单库、inventory、payment 都在同一个 MySQL 实例上。原始输出在 `tmp/1d/`，不入库。本机的绝对值不可靠（见 1b 设计文档 7.3.4），看的是相对变化和瓶颈的位置。

**落库吞吐对并发度**

| `SUBMIT_CONCURRENCY` | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| 落库（单/秒） | 316 | 448 | 569 | 642 | 686 |
| 受理（单/秒） | 804 | 974 | 1112 | 1219 | 1305 |
| 被背压拒绝的比例 | 73% | 68% | 63% | 59% | 57% |

并发生效了，但到 2.2 倍就平了，没有到“下游资源用尽”那种量级。平的时候四个服务的 CPU 都很空闲（order 约三分之一个核），只有 MySQL 容器用了约 1.1 到 1.3 个核。

**瓶颈在哪：让 MySQL 自己说。** 清空 `performance_schema` 的语句统计后跑一次并发度 16，按总耗时排：

| 语句 | 次数 | 平均 | 其中等锁 |
|---|---|---|---|
| inventory：`UPDATE sku_stock SET available = available - ? ...` | 24679 | 48.4 ms | 几乎全部（累计 1192 秒） |
| 订单库 0 的 `COMMIT` | 24625 | 7.0 ms | 0 |
| inventory 的 `COMMIT` | 24654 | 6.9 ms | 0 |
| 订单库 1 的 `COMMIT` | 24646 | 6.8 ms | 0 |
| 其余所有语句 | | 0.3 ms 以下 | 0 |

两件事叠在一起：

1. **热门 SKU 的行锁。** 预占在一个事务里扣 `sku_stock` 的可售数，这一行的锁要拿到事务提交。10 个 SKU、64 个在途订单，大家在这 10 行上排队。
2. **提交很慢。** 每次提交约 7 毫秒（`sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`，容器里的文件系统刷盘本来就慢），一个订单落库要提交三次。它又拉长了第 1 条里持锁的时间：一行每秒最多被扣一百多次。

做了两个对照，各自只解释一部分，和上面的结论一致：

| 条件 | 并发度 1 | 并发度 16 |
|---|---|---|
| 默认 | 316 | 686 |
| 放宽刷盘（`sync_binlog=0`、`innodb_flush_log_at_trx_commit=2`，量完改回） | 571 | 848 |
| 100 个 SKU | | 800 |

串行时刷盘是主要成本（放宽后快了 80%），并发之后它不再是唯一的限制。

**这一步达到了什么，没达到什么。** 2.1 定的第一个目标是“落库吞吐随并发度上升，直到某个下游资源成为瓶颈，并且知道是哪一个”：达到了，瓶颈是 inventory 里同一个 SKU 的扣减在 MySQL 里是串行的。没有达到的是数量级的提升：1b 留下的“落库 400 单/秒”现在是 640 到 820，原因不再是消费者的结构。

热门行的扣减是秒杀的老问题，闸门（Redis）解决了受理这一侧，落库这一侧每个订单仍然要在 MySQL 里扣一次。常见的做法：把一个 SKU 的库存拆成多行（分桶），不同订单扣不同的行；把短时间内对同一个 SKU 的多个预占合并成一次扣减（一个事务扣 n 件、写 n 条预占记录）；或者预占只写流水、可售数异步汇总。放在 1d 的哪一步做，等主人定。

**轮询压力下的落库**（并发度 8，每秒 2000 个下单请求，另一个进程对最近受理的 2000 个订单每秒查询约 4600 次）

| | 落库（单/秒） | 查询延迟 p50 / p99 |
|---|---|---|
| 没有查询压力 | 821 | |
| 有查询压力 | 617 | 1.8 / 7.3 ms |

有查询压力时落库是没有时的 75%。1b 的数是 410 对 43（约 10%），当时的轮询是每个虚拟用户 50 毫秒一次、800 个用户，约 1.6 万次/秒，压力比这次大，两个比值不能直接比。能确定的是：排队中的订单被查询时不再读 MySQL（`TestQueuedOrderIsAnsweredWithoutTheOrderDB` 把订单库关掉也能答），剩下的 25% 来自已落库、待支付的订单，它们仍然要读订单行。这部分留给步骤二按用户限制查询频率。

**商家索引**

只在测试库上量了（同一个 MySQL 实例，每库连接池 25）：在途写入从 4 路（相当于改动前）加到 64 路（并发度 16 × 4 个分区），写入从约 2000 行/秒到 7600 到 9000 行/秒，32 路之后就平了。瓶颈同样是每次提交的刷盘：一行一个事务，每次约 1.2 毫秒，靠组提交把多路的提交合在一起刷，合到头就是这个数。

它低于 2.5 定的门槛（1 万行/秒）。按约定应当接着做按批写：一个事务写多行，直接减少提交次数，正好针对这个瓶颈。在真实数据上的追平速度没有量（要重新造一批变更）。

**参数**

- `ADMIT_MAX_QUEUE` 保持 1 万：按 640 到 820 单/秒算是排 12 到 16 秒，比原来按 400 算的 25 秒更保守。热门 SKU 的问题处理之后再调。
- `SUBMIT_CONCURRENCY` 默认 8：从 8 到 16 只多 7%，而在途数（64）已经超过两个订单库的连接池总和（50）。
- `INDEX_CONCURRENCY` 默认 16（之后改成按批写，换成了 `INDEX_MAX_BATCH`，见 2.11）。
- 共享 MySQL 实例的 `max_connections` 提到了 400：各服务的连接池加起来是 164，超过默认的 151，服务开着的时候跑测试会报 1040。

**实现中的发现**

- **并发之后，同一个幂等键的两个订单谁落库不再由受理的先后决定**（ADR-0017 后果一节）。
- **正常停止也会产生重复。** 测试里一次正常停止：处理了 923 条、提交了 661 条，重启后 262 条重做。停止时每条 lane 只做完手上的一条，前缀之后已完成的都要重来。这是设计内的行为，量出来比预想的多。
- **分 lane 的哈希不能用生产者分区的那个。** 一个分区里的 key 本来就是“哈希取模后相等”的一批，再用同一个哈希对 lane 数取模，lane 数和分区数有公因数时会挤进少数几条 lane。用了带随机种子的 `maphash`。
- **开环模式没有量落库延迟。** 网关的订单响应里没有落库时刻，压测期间又不轮询。报告里写明“未测”，落库吞吐仍从库里算。要量得在订单上暴露一个落库时间，或者等阶段 3 的指标。
- 每条语句执行前都有一次 `PREPARE`（上表之外，次数与执行数相同，每次约 0.04 毫秒）：驱动默认用服务端预处理、不缓存。耗时很小，但多一次往返；`interpolateParams` 可以去掉，没有做。
- 预热接口一次最多 100 个 SKU，压测脚本的 `BENCH_SKU_COUNT` 超过 100 会失败。

**没有做的**

- 热门 SKU 的扣减（上面）。
- 商家索引按批写（上面）。
- 商家索引在真实数据上的追平速度。
- 落库延迟的测量。
- `GetOrder` 对已落库、待支付订单的查询仍然读 MySQL。

### 2.11 商家索引按批写（步骤一的延续）

状态：主人已确认要做（2026-11-14）。决定记在 ADR-0017 的补充一节。

2.10 量到索引的写入在约 9000 行/秒见顶，瓶颈是一行一个事务、每个事务一次刷盘。按批写直接减少提交次数。

**kafkax 增加按批处理的消费者。**

```go
type BatchHandler func(ctx context.Context, msgs []Message) error

type BatchConsumerConfig struct {
    ConsumerConfig
    MaxBatch int // 一批最多多少条，默认 500
}
func NewBatchConsumer(ctx context.Context, cfg BatchConsumerConfig, handler BatchHandler) (*Consumer, error)
```

- **一批是一个分区里连续的一段。** worker 取本地队列里现成的记录，最多 `MaxBatch` 条，至少 1 条，交给 handler。不等凑满：没有积压时一批就是一条，延迟和现在一样；有积压时批自然变大。所以不需要“攒多久”这个参数。
- **成功**：整批完成，位点提交到这一批的最后一条。
- **失败**：handler 返回错误时，暂时性的错误先整批重试（共 3 次）；仍然失败，或者错误是 Permanent 的，这一批退回逐条处理：每条消息单独作为一条的批交给同一个 handler，走和普通消费者完全相同的重试和死信。这样一条坏消息不会让整批反复失败，也不需要 handler 自己报告“是哪一条”。第一版没有整批重试，任何错误都直接逐条：数据库抖一下，第一条重试到恢复之后其余几百条各自提交一次，正确但按批的意义就没有了（orderindex 的子 Agent 指出）。
- 批内按位点顺序排列，同一个 key 的多条消息保持先后。
- 和 `Concurrency` 互斥，延迟消费者不支持。按批已经把一个分区的写入合成了一次提交，再分 lane 并行只会让事务之间互相等。

**orderindex 改用按批的消费者。** 一批消息：

1. 逐条解码。解不了的（消息本身坏了）返回 Permanent 错误，触发上面的逐条回退，坏的那条进死信。
2. 同一个订单在一批里出现多次时只留版本最高的映像（带版本号的 upsert 本来也会收敛到它，先合并少写几行）。
3. 按索引的 slot 分组，每张索引表一条多行的 `INSERT ... AS new ON DUPLICATE KEY UPDATE`，版本比较的写法不变（版本列最后赋值）。同一个库上的几张表放在一个事务里。
4. 两个索引库是两个事务，不是原子的：一个成功一个失败时整批返回错误，重做时成功的那一半是空操作。
5. 统计（Changed、Stale 等）：多行 upsert 拿不到逐行的结果。用受影响行数区分不了“新插入”和“更新”的各自条数时，统计改成按批给出受影响的行数，Stale 用“写入的行数减去实际改变的行数”估算；具体做法实现时定，原则是不为了统计多读一次库。

目标：本机测试库上超过 2 万行/秒（一批 500 行、4 个分区）。`INDEX_CONCURRENCY` 这个刚加的配置随之去掉，换成 `INDEX_MAX_BATCH`（默认 500，上限 6553：一条语句最多 65535 个占位符、每行 10 列）；还设着旧变量时拒绝启动。

**结果**（2026-11-14，测试库，4 路并行模拟 4 个分区，每库连接池 8）：

| 每批行数 | 带 `-race` | 不带 `-race` |
|---|---|---|
| 1 | 1700 行/秒 | 2100 行/秒 |
| 50 | 3.3 万 | 4.6 万 |
| 500 | 4.8 万 | 7.9 万 |

比按 key 并发的上限（约 9000）高一个数量级。印证了瓶颈是提交次数：一批 500 行只提交一次。

实现时定下来的几点：

- **统计**：多行 upsert 分不出逐行的结果。精确的有 `written`（合并后实际写库的行数）、`merged`（批内被更高版本顶掉的映像）和原有的跳过、忽略、归档、延迟。`changed_est` 取每条语句“受影响行数”和“写入行数”中较小的一个，是实际改变行数的上界，没有重放时是精确的；`stale_est` 是剩下的。日志字段名带 `_est` 就是为了不让人把它当精确值。
- **每条语句里的行按主键排序**再写，不同分区的批并发写同一张表时加锁顺序一致，减少死锁。二级索引上的锁顺序仍然可能交叉，出现时整个事务回滚、作为可重试的错误返回；测试里没有出现过。
- 一个库只有一条语句时不开显式事务（自动提交），一条消息的批和原来一样是一次往返。两个索引库并行写。
- 每个索引库的连接池从 25 降到 10：同时在途的事务最多是每个分区一个。

kafkax 的按批消费由 Fable 写；orderindex 的改造派给 Opus。

## 3. 步骤一的延续：MySQL 侧的库存扣减改成异步

状态：主人已确认（2026-11-14）：先做方案 A，量完再决定要不要做方案 B；接受 3.4 的代价（MySQL 从阻止超卖变成发现超卖）。决定见 ADR-0018。

### 3.1 现在的问题

落库时 order 同步调 inventory 的 `Reserve`，它在一个事务里做三件事：

1. 插入预占记录（`reservation`、`reservation_item`）。这是幂等记录和流水，每个订单各写各的行。
2. `UPDATE sku_stock SET available = available - ?, reserved = reserved + ? WHERE sku_id = ? AND available >= ?`。**所有买这个 SKU 的订单都改同一行**，行锁要拿到事务提交。
3. 读这些 SKU 的价格和商家，返回给 order。

第 2 步是 2.10 量到的瓶颈：平均等锁 48 毫秒。支付后的确认、取消后的释放（由 inventory 消费订单事件来做）改的也是这一行，和预占抢同一把锁。

第 2 步在 1a 是防超卖的核心。1b 加了库存闸门之后，能不能卖是 Redis 里先判断的：闸门原子地扣可售、记占用，不会超卖。MySQL 这一步成了第二道检查，绝大多数时候只是在重复闸门已经做过的判断，却要每个订单串行地做一次。

### 3.2 两种做法

**方案 A：库内流水表，单个应用者合并更新。**

```
Reserve / Confirm / Release（各自的事务里）
    写预占记录、改预占状态          ← 和现在一样
    INSERT INTO stock_pending ...   ← 新：只记“这个 SKU 的三个数各要变多少”，不碰 sku_stock

应用者（inventory 里的一个后台任务）
    取一批 stock_pending → 按 SKU 求和 → 每个 SKU 一条 UPDATE sku_stock → 删掉这批 → 提交
```

热点行从“每个订单改一次”变成“每批改一次”。`Reserve` 仍然是同步的 gRPC，接口、幂等、价格快照、多商家检查都不变。

**方案 B：经 Kafka 异步，inventory 按批消费。** order 落库时不再调 `Reserve`：它自己读（缓存的）价格和商家，算出金额，订单直接进入待支付，同时发一条“请求预占”的事件；inventory 按批消费，一个事务里写一批订单的预占记录、每个 SKU 一条合并的更新。这是最常见的“Redis 预扣、消息队列异步落库”的形态，落库路径上少一次同步调用和一次提交，上限更高。

**建议 A。** 理由：

- **没应用的增量要能和计数在同一个快照里读到。** 闸门从 MySQL 装载（预热）时需要“真实的可售数”，等于 `sku_stock.available` 加上还没应用的增量。A 的增量在同一个库里，一次一致性读就能算准。B 的增量在 Kafka 里，装载的那一刻有多少还在路上是不知道的，装进闸门的数会偏大，这正是会造成超卖的方向。要补就得再维护一份“已发未应用”的账。
- **“应用一次且仅一次”需要“改计数”和“标记已应用”在一个事务里。** A 天然如此（更新和删除在同一个事务）。B 是至少一次投递，仍然要靠预占记录的唯一键去重，等于在消费端把 A 的事务再做一遍。
- **改动面。** A 只动 inventory 内部，order 和契约不变。B 要改 order 的落库流程（金额谁算、多商家谁查、预占失败怎么通知回来）、新增事件、改 1a 以来“预占成功才进入待支付”的语义。
- B 多出来的收益（落库少一次同步调用）在热点行解决之后才看得出值不值，可以等 A 做完再量。Kafka 已经承担了落库本身的异步，这里要解决的只是“计数那一行”。

### 3.3 方案 A 的细节

**表**

```sql
CREATE TABLE stock_pending (
    id           BIGINT NOT NULL AUTO_INCREMENT,
    sku_id       BIGINT NOT NULL,
    d_available  BIGINT NOT NULL,   -- 预占 -n，释放 +n，确认 0
    d_reserved   BIGINT NOT NULL,   -- 预占 +n，释放 -n，确认 -n
    d_sold       BIGINT NOT NULL,   -- 确认 +n
    order_id     BIGINT NOT NULL,   -- 排查用
    created_at   DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    KEY idx_stock_pending_sku (sku_id)
);
```

应用之后删除。它是一张队列表，不是流水；流水是 `reservation` 和 `reservation_item`，已经有了。

**写入方**。`Reserve`、确认、释放的事务里，原来调 `ReserveStock`、`ConfirmStock`、`ReleaseStock` 的地方改成插入一行 `stock_pending`。预占记录的状态机、唯一键互斥、空回滚都不变：它们保证每个订单的每次状态变化只发生一次，所以每个增量只会被写一次。

**应用者**。inventory 里的周期任务，每个实例各跑一个（实现时去掉了 leader 锁，见 3.7）：

```
BEGIN
SELECT id, sku_id, d_available, d_reserved, d_sold FROM stock_pending ORDER BY id LIMIT 1000 FOR UPDATE   -- READ COMMITTED
按 SKU 求和
对每个 SKU（按 sku_id 升序）:
    UPDATE sku_stock SET available = available + ?, reserved = reserved + ?, sold = sold + ? WHERE sku_id = ?
DELETE FROM stock_pending WHERE id IN (...)
COMMIT
```

有积压就连着做，空了就等一小段（默认 20 毫秒）。

- **为什么按 id 顺序、加普通的 `FOR UPDATE`，不用 `SKIP LOCKED`。** 同一个订单的增量有先后：先预占（`reserved +n`），后释放（`reserved -n`）。跳过被锁住的行会让后面的先应用，`reserved` 出现一瞬间的负数，撞上 CHECK 约束。按 id 顺序、不跳过能让这种情况少见，但**不能杜绝**（这句话原来写的是“就不会”，是错的，见 3.10）。两个应用者同时跑时，后一个在行锁上等，等到之后这些行已经被删了，它读到的是后面的行，不会重复应用。
- **为什么不用“记一个已应用到哪个 id 的水位”。** 自增 id 的分配顺序和事务提交的顺序不一致：id 小的事务可能后提交，水位已经越过它，它就永远不被应用。这是用自增 id 做位点的经典错误。取“当前看得见的行”再删掉，没有这个问题。

**读“真实的数”**。凡是拿 `sku_stock` 的数去做判断的地方，都要加上没应用的增量，在一个一致性读里：

```sql
SELECT s.available + COALESCE(SUM(p.d_available), 0), s.reserved + COALESCE(SUM(p.d_reserved), 0), ...
FROM sku_stock s LEFT JOIN stock_pending p ON p.sku_id = s.sku_id WHERE s.sku_id = ? GROUP BY s.sku_id
```

- 闸门的预热（装载可售数）：必须用。
- 闸门和 MySQL 的对账（`reconcile`）：必须用。它比较的是 `available + reserved`，预占和释放不改变这个和，确认会。
- `GetStock`（展示，带缓存）：原计划直接读 `sku_stock`，实现时也改成了读真实的数（见 3.7）。

### 3.4 语义上变了什么（要主人知道的代价）

1. **“MySQL 没货”不再在预占时发现。** 现在闸门有货而 MySQL 没货时，`Reserve` 返回库存不足，订单创建失败。改了之后 `Reserve` 不看可售数，这种订单会成功。发现它的地方变成应用者：把增量加到 `sku_stock` 上时 `available` 会变负，被 CHECK 约束拒绝。这时应用者跳过这个 SKU 的全部增量（保持先后），记错误日志并计数，其他 SKU 照常；这个 SKU 的增量留在表里，直到人把库存对上。
   也就是：MySQL 这一侧从**阻止**超卖变成**发现**超卖。阻止超卖完全靠闸门。闸门出错的途径是它和 MySQL 对不上（有人直接改了 `sku_stock`、对账修正有缺陷、Redis 丢数据后装载错了），这些以前有 MySQL 兜底，以后没有。
2. **`sku_stock` 的三个数会落后**，量级是应用者的一轮（几十毫秒），积压时更久。恒等式 `available + reserved + sold = 入库总量` 在任何时刻仍然成立（每个增量自身三项之和为零）；“加上未应用的增量之后三个数都不为负”才是新的不变量。
3. **阶段计划里步骤四的降级预案“Redis 不可用时退回数据库扣减”要重新设计。** 没有闸门时 MySQL 必须同步地判断并扣减，那就得先把这个 SKU 的增量应用完，再走原来的条件更新。这一步的设计里要给它留出一个同步的 `Reserve` 模式，步骤四再接。

### 3.5 测试

- 并发预占同一个 SKU：不再有行锁等待；全部应用后 `sku_stock` 与逐个串行应用的结果相同。
- 应用者：按 SKU 合并；重复运行、两个同时运行，每个增量恰好应用一次；中途被杀（事务回滚）后重做，结果相同。
- 先预占后释放的订单，无论分在一批还是两批，`reserved` 从不为负。
- 预热和对账在有未应用增量时读到的是真实的数：预占之后、应用之前装载闸门，装进去的可售数已经扣掉了这笔预占。
- 超卖的发现：人为把 `sku_stock.available` 改小，预占照常成功，应用者跳过这个 SKU 并报错，其他 SKU 不受影响；把库存补上之后自动恢复。
- 现有的全部测试（1a 的并发扣减、空回滚、重复预占、1b 的事件消费和对账）在“应用者追平之后再断言”的前提下通过。
- 实测：同 2.10 的条件重跑落库吞吐对并发度，再看 `performance_schema` 里瓶颈移到了哪。

### 3.6 实现顺序

库存的扣减是这个系统里最核心的一致性代码，这一步的产品代码由 Fable 写：迁移、store 的三个写入点、应用者、读真实数的查询。测试的铺开（把现有测试改成先等应用者追平、新增并发和故障用例）派给 Opus，Fable 评审。`scripts/chaos.sh` 和 `load verify` 里读 `sku_stock` 的检查要改成先等增量应用完，派给 Sonnet。

### 3.7 实现中的调整（2026-11-14）

- **应用者不用 leader 锁，每个实例各跑一个。** `ApplyPending` 靠增量行上的行锁互斥：后到的等先到的提交，之后读到的是剩下的行。这样它不依赖 Redis，闸门所在的 Redis 不可用时 MySQL 的计数照常更新；也少了一个“锁丢了、两个同时跑”要论证的情形，因为两个同时跑本来就是对的。
- **应用者的事务用 `READ COMMITTED`。** `REPEATABLE READ` 下带 `LIMIT` 的加锁读在行数不足一批时会一直扫到索引末尾并锁住末尾的间隙，而所有新增量都插在末尾：预占、确认、释放会被应用者的事务挡到它提交。
- **`GetStock` 统一返回真实的数**，不分“做判断的读”和“展示的读”。多出来的是一次按 SKU 的索引求和，表很小。好处是只有一种读法，不会有人误用落后的那个；直接读 `sku_stock` 的只剩排查问题时的手工查询。
- **`SKIP LOCKED` 的害处是误报，不是算错。** 改坏验证时把 `FOR UPDATE` 换成 `SKIP LOCKED`，最终的数仍然正确：先后被打乱时某个数会短暂为负，CHECK 约束拒绝这次更新，应用者把这个 SKU 报成卡住，下一轮连同前面的增量一起应用就恢复了。但每一次都是一条“超卖”的错误日志。第一版的并发测试没有检查这一点（只看了最终的数和恒等式），改坏之后照样通过；补上“库存充足时应用者不应报告任何卡住的 SKU”之后才抓得到。
- **卡住的 SKU 平时要绕开。** 它的增量留在表头，不绕开的话会把每一批占满，别的 SKU 轮不到。应用者记着卡住的 SKU，平时的批次排除它们，每秒带上它们重试一次；看完整张表而它们不再出现时算恢复。
- **合计为零的批也执行更新。** 一批里同一个订单先预占后释放，三个增量加起来都是零。仍然执行这条更新并额外确认行存在，否则“SKU 不存在”的增量会被当成已应用而删掉。
- **停止时的顺序**：应用者最后停（gRPC 的预占、消费者的确认和释放收尾时还在写增量），停了之后再收一次尾。没应用完的增量留到下次启动也是对的，读库存的地方都会把它们加上。

### 3.8 测试铺开时的发现（2026-11-14）

inventory 的测试由 Opus 子 Agent 修正和铺开（只许改测试文件），发现并钉住了两个产品代码的缺陷，已修：

- **超卖时预热失败。** 真实可售数为负时原样传给闸门，闸门当作参数错误拒绝，对外成了“闸门不可用，请重试”，调用方会对一个数据问题无休止地重试。改成按 0 装载并记错误日志。
- **超卖时对账失效。** 修正偏差时把 MySQL 的可售数当上限传给闸门，为负时报错。闸门装多了导致超卖时，对账是唯一能把闸门收紧的机制，它恰好在这时不工作，闸门会继续卖。改成上限取 0，修正把闸门收到 0。

两个是同一个原因：3.4 写了“加上未应用的增量之后三个数都不为负才是新的不变量”，而超卖正是这个不变量不成立的时候，下游的读者没有为负数做准备。**一个值的取值范围变了，要把它所有的读者过一遍。**

由此定下的约定：inventory 的 `GetStock` 接口照实返回（超卖时 `available` 为负），它也给对账和排查用；面向买家的展示由 gateway 截到 0。

子 Agent 指出的设计问题，没有改，记在这里：

- **MySQL 一侧能不能发现短暂的超卖，取决于分批。** 一批之内的增量是先求和再更新的：预占超过了库存，但它的释放落在同一批里，合计不为负，就不会被报出来。分在两批里才会。所以“应用者发现超卖”对持续的超卖是确定的，对短暂的不确定。持续的超卖最终一定被发现；`load verify` 的第 22 项在静止后把关。
- **卡住的 SKU 恢复的条件是“表头那一批够扣”，不是“净额够”。** 重试时取的是最老的一批行；这个 SKU 在这一批里的合计为负就继续卡着，即使更后面的释放已经让净额够了。默认一批 1000 行，要一个 SKU 有上千行未应用的增量才会遇到，这时本来也需要人来看。
- **应用者会等还没提交的增量行。** `FOR UPDATE` 遇到别的事务刚插入、还没提交的行会等它提交。一个慢的预占事务会拖住这一批的应用。这同时也是先后不被打乱的原因，所以没有改；预占的事务只有几条语句。
- `Applier.Stuck()` 不是并发安全的，循环运行期间不能从别的 goroutine 调用。以后给监控用要加锁。
- order 的测试用假的 inventory，它仍然在可售数不够时拒绝预占。真实的 inventory 不再这样做。order 处理 `INSUFFICIENT_STOCK` 的代码作为防御保留，相关的测试注明了“这是防御用例，不代表系统现在的行为”。
- e2e 没有“闸门有货而 MySQL 没货”的用例：它要在共用的服务上人为制造闸门和 MySQL 的差，容易污染别的用例。这个行为由 inventory 的集成测试和 `load verify` 第 22 项的测试覆盖。

每个 inventory 测试结束时现在会自动把增量应用完（批大小故意取 3，让一个订单的预占和释放落在不同的批里），并断言没有意外卡住的 SKU、增量表为空、`sku_stock` 的三个数不为负且总量守恒。相当于给每个现有测试都加了一条“应用之后账是平的”。

### 3.9 结果（2026-11-14）

`make lint test e2e` 通过。`make chaos` 两次 PASS：22 项对账全过，其中第 22 项（库存增量都已应用）在静止后是 0 行，说明 inventory 被 `kill -9` 后重启的应用者把留下的增量接着应用完了。

落库吞吐，条件同 2.10（开环每秒 3000 个下单请求、20 秒、10 个 SKU、所有库在同一个 MySQL 实例上）：

| `SUBMIT_CONCURRENCY` | 1 | 8 | 16 | 32 |
|---|---|---|---|---|
| 改之前（2.10） | 316 | 642 | 686 | |
| 异步扣减之后 | 320 | 789 | 870 | 985 |
| 改之前，放宽刷盘 | 571 | | 848 | |
| 异步扣减之后，放宽刷盘 | | | 1064 | 1034 |

**热点行的锁没有了。** 并发度 16 时的语句统计里，`UPDATE sku_stock` 不在前十（改之前它平均 48 毫秒、累计等锁 1192 秒）。应用者的两条语句（取增量、删增量）共约 500 次，把三万次预占合并成了几百次更新。

**吞吐只涨了 23% 到 27%，因为下一个瓶颈紧跟在后面：提交。**

| 语句（并发度 16，正常刷盘） | 次数 | 平均 |
|---|---|---|
| inventory 的 `COMMIT` | 29972 | 9.1 ms |
| 订单库 0 的 `COMMIT` | 29950 | 8.9 ms |
| 订单库 1 的 `COMMIT` | 29457 | 8.9 ms |
| 其余每条语句 | | 0.5 ms 以下 |

一个订单落库要提交三次，共约 27 毫秒，几乎就是它在 MySQL 里的全部时间。每秒约 2600 次提交已经是这个实例（容器里的文件系统、`sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`）的上限，并发度从 16 加到 32，提交只是排得更久。

**放宽刷盘之后，MySQL 不再是瓶颈，但吞吐停在约 1050，原因没有找到。** 这时每次提交 1.3 到 1.7 毫秒，一个订单在 MySQL 里总共约 5.5 毫秒，采样时 MySQL 只有 7 个线程在运行、103 个连接里 2 个在执行。而 64 个在途、每秒 1055 单意味着每个订单在途约 60 毫秒。剩下的约 54 毫秒不在 MySQL 里，四个服务的 CPU 也都很空闲。可能是 1b 就怀疑过的本机网络问题（OrbStack 的端口转发在高包速率下丢包，一次重传约 200 毫秒；这几轮受理延迟的 p99 正好在 200 到 470 毫秒），也可能是 order 进程内的某处等待。没有链路追踪，分不出来。这是步骤六（埋点）要回答的问题，也是 1b 把吞吐结论挂到阶段 2 的原因。

**结论**

- 这一步消掉了一个真实的、会随 SKU 热度恶化的瓶颈：以前吞吐取决于有多少订单抢同一个 SKU（10 个 SKU 时 686，100 个时 800），现在与此无关。秒杀场景（所有人买同一个 SKU）受益最大，压测用的 10 个 SKU 低估了它。
- 本机在正常刷盘下的落库上限现在是提交次数决定的：每个订单三次。要再提高，得减少每个订单的提交次数。方案 B（inventory 按批消费，把它的那一次提交摊到几百个订单上）能去掉三次里的一次；订单库的两次（插入订单行、改成待支付）是另一个可以合并的地方。
- 落库吞吐从 1b 的约 400 到了 790（默认并发度 8），不是数量级。数量级的结论仍然要到阶段 2 的集群上、有链路追踪之后才能下。

**参数**：`ADMIT_MAX_QUEUE` 仍然保持 1 万（按 790 单/秒是排约 13 秒）。`SUBMIT_CONCURRENCY` 默认仍是 8。

**没有做的**

- 方案 B：主人决定先不做（2026-11-14）。剩下的时间花在哪还不清楚，等有了埋点（步骤六）或上了集群再判断它值不值。
- 放宽刷盘后那约 54 毫秒的去向。
- 应用延迟（增量从写入到被应用的时间）没有单独量；应用者每 10 秒的汇总日志里有 `max_age_ms`，压测里没有收集。
- `stock_pending` 的行数和最老一行的年龄应当有指标和告警（阶段 3）。

### 3.10 CI 上抓到的设计漏洞：按 id 顺序加锁扫描不是快照（2026-11-14）

步骤二推送之后，CI 的 `TestConcurrentWritersAndAppliers` 失败了一次：库存充足，应用者却报告 SKU 卡住，“available +12, reserved -12 会让某个数变负”。日志里没有任何写入失败。也就是说，应用者取到的一批里有四个订单的释放，却没有它们的预占，而那些预占此时也还没有被应用。

3.3 里写的是“按 id 顺序、不跳过，就不会”。这个论断是错的。

**推断的机制**（本机没有复现：去掉修复后限制 CPU 连跑 40 遍都通过）：`SELECT ... ORDER BY id LIMIT n FOR UPDATE` 是一行一行加锁往前走的，中途会在别人锁着的行上等待。它不是一个瞬间的快照。一个较早分配了 id、较晚才插入并提交的预占，可以出现在扫描游标已经走过的位置后面；游标继续往前，取到这个订单后来写入的释放。这和 3.3 里特意警告过的“不能用自增 id 做水位，因为分配顺序不是提交顺序”是同一个原因，只是当时只想到了水位，没想到加锁扫描也有“已经走过的位置”。

后果是误报，不是算错：这一轮那个 SKU 被报成超卖并留下，下一轮它的预占排在表头，一起应用就恢复了。但每次都是一条“超卖”的错误日志，而这条日志是这个设计里发现真超卖的唯一途径，不能有假阳性。

**修法**：不再依赖先后。一个 SKU 这一批的合计被 CHECK 拒绝时：

1. 把这个 SKU 的**全部**未应用增量锁住、合计，再试一次。这一批里出现的释放，它的预占在这第二条语句开始之前就已提交，一定在里面。能应用就全部应用。
2. 还是被拒绝，用一次普通的一致性读算它的真实值（`sku_stock` 加全部增量）。普通的读是真正的快照，没有“游标后面”的问题。有负数才是真的对不上，报错并绕开；没有负数说明第二次扫描又遇到了同样的交错，这一轮推迟，不报错。

这样“报告超卖”的条件变成了“快照里的真实值为负”，和先后无关。顺带解决了 3.8 里记的另一个问题：卡住的 SKU 现在按全部增量的净额判断，净额够了就自己恢复，不再取决于表头那一批。

两个应用者现在可能互相死锁（一个拿着后面的行、回头锁同一个 SKU 更早的行，另一个相反），数据库回滚其中一个，应用者重试。

测试：新增一个确定性的用例（按“释放的 id 比预占小”的顺序写入，一批只取一行）直接走重算的路径；并发用例改成只断言“没有被报成真的对不上”。有修复时限制 CPU 连跑 80 遍通过。

**这次的教训有两条。** 一是论证“某种交错不会发生”时，要问清楚每条语句看到的到底是不是一个时间点的状态：一致性读是，加锁读不是。二是并发测试在本机通过不说明什么：这个测试在本机连跑过五遍、做过改坏验证，CI 第二次运行就失败了。CI 的机器更慢、别的包的测试同时在跑，交错的分布不一样。

## 4. 步骤二：网关限流

状态：主人已确认（2026-11-14）：按 IP 在进程内、按用户和接口在 Redis（4.4）；Redis 不可用时退回进程内的限流器（4.6）；限流状态放在 `redis-cache`（4.7）。决定和备选方案见 ADR-0019。

目标是阶段计划里的任务：令牌桶，按接口、按用户、按 IP；分布式限流用 Redis。对应的验收是“超出阈值的流量被拒绝而不是拖垮服务”。

### 4.1 它和已有的背压是什么关系

系统里已经有一处拒绝请求的地方：受理端的背压（ADR-0011），等待落库的订单太多时下单返回 429 `BACKLOGGED`。它保护的是落库这条管道，依据是系统自己的状态（队列有多长）。

限流保护的是别的东西，依据是请求的来源：

| | 背压 | 限流 |
|---|---|---|
| 问的问题 | 系统现在还吃得下吗 | 这个调用方是不是要得太多了 |
| 依据 | 队列长度 | 谁在调、调的哪个接口、多快 |
| 被拒绝的是谁 | 所有人，不分来源 | 超出配额的那个用户或地址 |
| 位置 | order 服务里 | 网关，最外层 |

只有背压时，一个用户用脚本每秒下 1000 单，会把队列占满，其他人全被拒绝：系统没垮，但不公平。只有限流时，每个人都守规矩但总量超过容量，系统照样被压垮。两个都要。

步骤一留下的一个具体问题也归限流解决：已落库、待支付的订单被轮询时仍然读 MySQL（2.10），要按用户限制查询的频率。

### 4.2 三个维度，各自防什么

| 维度 | 键 | 防什么 | 默认 |
|---|---|---|---|
| 按 IP | 客户端地址 | 没有身份的洪水：扫描、撞库、坏掉的客户端。在识别用户之前就拒绝，最便宜 | 每秒 200，桶 400 |
| 按用户 | 用户号加接口 | 一个用户占用过多：脚本刷单、过快的轮询 | 见下表 |
| 按接口 | 接口 | 这个接口的总量超过下游能承受的 | 默认不限，可配 |

按用户的默认值（每秒的速率 / 桶的容量）：

| 接口 | 默认 | 理由 |
|---|---|---|
| 下单 `createOrder` | 5 / 10 | 人不会每秒下 5 单；桶 10 容得下连点和重试 |
| 支付 `payOrder`、取消 `cancelOrder` | 5 / 10 | 同上 |
| 查订单 `getOrder` | 20 / 40 | 轮询。客户端每 100 毫秒查一次是 10 次/秒，留一倍 |
| 查支付 `getPayment` | 20 / 40 | 同上 |
| 订单列表 `listOrders`、商家列表 `listMerchantOrders` | 10 / 20 | 翻页 |
| 查库存 `getStock` | 50 / 100 | 商品页的展示读，有缓存 |

按 IP 的默认值比按用户的高得多：一个地址后面可能是一个公司或一个运营商的出口，按用户的限制已经管住了每个人。按接口的总量默认不设：下单的总量已经由背压按实际的落库能力管着，其他接口的容量要等有了指标（阶段 3）才定得出来；机制和配置在这一步做好。

用户身份取自 `X-User-Id` 请求头，和现在的 `requireUser` 一致。本项目没有做认证，这个头是可以伪造的；按用户限流在有真实认证之前挡不住故意换用户号的攻击者，那是按 IP 那一层要挡的。

### 4.3 算法：令牌桶

每个键一个桶：容量 `burst`，以每秒 `rate` 个的速度补充，一个请求取一个令牌，取不到就拒绝。状态只有两个数（令牌数、上次补充的时间），补充是在取的时候按流逝的时间算出来的，不需要后台任务。

选它的原因是它同时表达了两件事：长期的平均速率（`rate`）和允许的突发（`burst`）。用户连点两下、客户端超时后立刻重试，都是正常的突发，不应该被拒绝。几种算法的对比写在 ADR-0019。

被拒绝时能算出“再过多久会有一个令牌”，放进 `Retry-After` 响应头。

### 4.4 单机和分布式怎么分工

网关可以有多个实例。限流的状态放在哪里：

- **放在进程里**（单机）：没有网络往返，不依赖任何东西。N 个实例各限各的，实际的总限额是 N 倍，而且同一个用户的请求落在哪个实例是随机的。
- **放在 Redis 里**（分布式）：所有实例共用一份状态，限额精确。每个请求多一次 Redis 往返，Redis 不可用时要有对策。

建议按维度分：

- **按 IP：进程里。** 它是第一道闸，要在最前面、最便宜；N 倍的误差对“挡洪水”无所谓（限额本来就给得宽）；它不能依赖 Redis，否则打垮 Redis 就等于关掉了限流。
- **按用户和按接口：Redis。** 这两个要精确：用户的配额很小（每秒 5 次），N 倍的误差就是限了个寂寞；接口的总量保护的是下游，更要全局算。两个桶在**一个 Lua 脚本里一次判断**，一次往返：都有令牌才都扣，任何一个没有就都不扣（否则一个请求被接口总量拒绝了，却白白消耗了用户的配额）。

顺序：先 IP（进程里），再识别用户，再用户加接口（Redis），最后才是下游调用。被限流的请求不产生任何下游调用。

### 4.5 Redis 里的令牌桶

每个桶一个 hash：`tokens`、`ts`。脚本做的事：读出两个值 → 按流逝的时间补充（不超过容量）→ 够就扣 → 写回并设过期时间。Lua 脚本在 Redis 里是原子执行的，不会有两个请求同时读到同一个令牌。

- **时间用 Redis 的 `TIME`，不用网关传进去的时间。** 各个网关实例的时钟有偏差，用各自的时间去算“流逝了多久”，时钟快的实例会多补令牌。Redis 7 起脚本按效果复制，在脚本里调 `TIME` 是允许的（本机是 8.10）。
- **过期时间取“从空到满要多久”再加一点。** 过期的桶等于满桶，和它自然补满的结果一样，所以过期不改变行为，只是回收不活跃的键。
- 键：`rl:u:{用户号}:{接口}` 和 `rl:r:{接口}`。
- 网关调用带一个很短的时限（默认 20 毫秒）。

### 4.6 Redis 不可用时

三种选择：放行（限流消失）、拒绝（网关跟着 Redis 一起不可用）、退回进程内的限流器。

建议第三种：Redis 调用出错或超时，这一次请求改用进程内的同一套规则判断（每个实例各自的桶，限额不除以实例数，所以比正常时宽松）。这样限流的基础设施坏了，既不会把网关变成不可用，也不会完全没有限制。连续失败时不必每个请求都去撞一次 20 毫秒的超时：用一个简单的开关，失败后的一小段时间内（默认 1 秒）直接走进程内，到时再试一次 Redis。这其实就是一个最小的熔断器，步骤三会把它换成正式的。

### 4.7 用哪个 Redis

本机有两个实例：`redis`（库存闸门和锁，`noeviction`，开了 AOF）和 `redis-cache`（查询缓存，`allkeys-lru`，不持久化）。

建议用 `redis-cache`：

- 限流的状态丢了没关系（丢一个桶等于那个桶满了，宽松一次），不需要持久化；内存紧张时被淘汰也只是同样的后果。这正是缓存实例的特性。
- 闸门所在的实例是下单的命脉，不该让每一个请求（包括所有的查询）都去那里多一次往返。闸门实例上跑一个慢脚本会直接卡住下单。
- 网关因此新增一个依赖（它现在不连任何 Redis）。

### 4.8 进程内的令牌桶

同样的算法，状态在一个按键索引的表里。两个要处理的问题：

- **键是无界的。** 按 IP 的表会随见过的地址增长。给它一个容量上限（默认 10 万个键）和按最近使用淘汰；淘汰一个桶等于它满了。不活跃的键定期清掉。
- **并发。** 分片加锁（按键的哈希分成若干片，每片一把锁），不用一把大锁。

自己写而不用 `golang.org/x/time/rate`：它的 `Limiter` 是单个桶，按键管理、淘汰、和 Redis 版对齐的行为都要自己包一层，剩下的只有几十行算术。自己写的好处是进程内和 Redis 两个实现是同一个算法、过同一组测试，退回进程内时行为一致。

### 4.9 客户端地址从哪来

网关直接面向客户端时用连接的远端地址。前面有反向代理或负载均衡时，远端地址是代理的，真实地址在 `X-Forwarded-For` 里；但这个头是客户端可以随便写的，只有“来自受信任的代理”时才能信。配置项 `TRUSTED_PROXIES`（CIDR 列表，默认空）：远端地址在这个列表里才取 `X-Forwarded-For` 里最右边那个不属于受信任代理的地址，否则用远端地址。本机默认空；阶段 2 上了 Ingress 再配。

配错的两个方向都有后果：该信没信，所有请求都算在代理的地址上，一下就被限住；不该信却信了，攻击者每个请求写一个不同的地址，按 IP 的限流形同虚设，还会把表撑满（所以要有容量上限）。

### 4.10 对外的行为

- 被限流返回 429，原因码 `RATE_LIMITED`，和背压的 `BACKLOGGED` 区分开。客户端的处理不同：`BACKLOGGED` 是系统忙，所有人都该退避；`RATE_LIMITED` 是你自己太快了。
- 响应头 `Retry-After`（秒，向上取整，至少 1）。
- 响应体里说明是哪个维度（`ip`、`user`、`route`）。
- 先改 `api/openapi/gateway.yaml`（规范先行，ADR-0005）：每个接口加 429 的响应和 `Retry-After` 头的定义。
- 被限流的请求记一条日志太多：按维度和接口计数，周期性地汇总成一条（和别的服务的汇总日志一样）；指标等阶段 3。

### 4.11 配置

默认规则写在代码里（4.2 的表），用环境变量覆盖：

- `RATE_LIMIT`：`on`（默认）或 `off`。整体开关。
- `RATE_LIMIT_IP`：`速率/桶`，如 `200/400`；`off` 关闭这一维。
- `RATE_LIMIT_USER`：按接口覆盖，如 `createOrder=5/10,getOrder=20/40`；没写的用默认。`off` 关闭这一维。
- `RATE_LIMIT_ROUTE`：按接口的总量，如 `createOrder=3000/6000`；默认空（不限）。
- `RATE_LIMIT_REDIS_ADDR`：默认是缓存实例；空表示不用 Redis，全部在进程内。
- `TRUSTED_PROXIES`。

**现有的脚本要关掉一部分。** 压测、杀进程测试和 e2e 都是从本机一个地址、用很多用户号打网关：按 IP 的限流会把它们全部限住，按用户的限流会限住压测里高频的用户。`scripts/bench.sh` 和 `scripts/chaos.sh` 整体关闭限流（它们量的是别的东西）；`scripts/e2e.sh` 关掉按 IP 的，保留按用户的，并加专门的用例。`scripts/run-local.sh`（`make run`）用默认值。

### 4.12 测试

- **令牌桶的算法**（进程内和 Redis 两个实现过同一组表驱动的测试）：桶满时能连取 `burst` 个；之后按 `rate` 补充；长时间不用不会超过容量；`Retry-After` 的值正确；速率为零、桶为零等边界。进程内的用可注入的时钟；Redis 的用真实的 Redis，时间靠等待或者在测试里直接改桶的 `ts`。
- **并发**（`-race`）：N 个协程同时取同一个桶，取到的总数不超过 `burst + rate × 时长`，也不明显少于它。Redis 版用多个客户端并发。
- **两个桶的原子性**：用户的桶有令牌、接口的桶没有时，请求被拒绝且用户的桶没有被扣。
- **Redis 不可用**：关掉 Redis，请求仍然被处理，并且仍然受进程内的限额约束；恢复后回到 Redis。超时的那一次不会让请求等超过时限。
- **进程内的表**：超过容量时淘汰，淘汰后的键表现为满桶；并发读写不竞争。
- **客户端地址**：受信任代理的各种情况（没配、配了且来自代理、配了但不来自代理、多级代理、头里是伪造的地址）。
- **网关的中间件**：被限流的请求不调用下游；429 的响应体、原因码、`Retry-After`；三个维度各自触发；顺序是先 IP 后用户。
- **e2e**：一个用户快速下 30 单，前若干个被受理，之后的得到 429 `RATE_LIMITED`，等 `Retry-After` 之后又能下单；另一个用户同时下单不受影响。
- **开环压测**：`load` 已经把非 `BACKLOGGED` 的 429 归为 `rate_limited`。用少量用户号打高速率，看被限流的比例和受理延迟是否稳住。

### 4.15 实现中的发现（2026-11-14）

- **一个错的假设，被改坏验证纠正了。** 写 Redis 脚本时我认为 Lua 把数字转成字符串只保留 14 位有效数字，微秒时间戳（16 位）直接写进 hash 会丢掉最后两位，于是加了显式的整数格式化，并写了一个测试“钉住”它。改坏验证时去掉格式化，测试照样通过：Redis 把脚本里的数字参数写入时，对整数值本来就按整数格式化。Lua 自己的 `tostring` 确实只有 14 位，但走的不是那条路。格式化保留了（不依赖没写进文档的行为），那段测试和注释里的错误说法删掉了。
- **淘汰不需要“最近使用”的顺序。** 进程内的表满了要丢桶。一个已经补满的桶和一个不存在的桶没有任何区别，丢掉它不改变行为；所以先找补满的丢，找不到再随机丢一个。每个桶多记一个“什么时候补满”，换掉了一条每次请求都要挪动的链表。
- **一次调用里的几个桶可能在不同的分片上**，按分片号升序加锁，两个调用以相反的顺序列出同样的桶也不会死锁。
- **`Fallback` 一次失败就打开**，不数失败率：退回的代价只是限额变宽，不值得为了少退回几次去多等几个超时。调用方自己取消不算主限流器的故障。
- **Redis 版的脚本一次处理多个键，它们必须在同一个节点上。** 单实例和主从没有问题，Redis Cluster 下用不了（用户的桶和接口的桶没法靠哈希标签放进同一个槽）。到需要集群的时候，要么拆成两次调用并接受不原子，要么把接口的总量改成进程内按实例数均分。

### 4.16 做限流时发现的两个旧问题（2026-11-14）

网关的子 Agent 接 Redis 客户端时提醒了两件和限流无关、但影响面更大的事。核实之后都是真的。

**一、受理的 `Hold` 被 Redis 客户端重试时，订单会凭空消失（1b 起就有，已修）。**

go-redis 默认在读超时之后自动重试命令（最多 3 次），Lua 脚本也不例外。`Hold` 的脚本第一次已经在 Redis 里执行成功、只是回复没收到时，重试的那一次看到自己刚写下的幂等键，返回“重复”，带的订单号就是这次调用自己的。order 把它当成“这个幂等键以前受理过”：返回订单、**不发落库消息**。用户拿到 202，占用却等不到落库，宽限期一过被回收，之后查询是 404。

这是“受理后被回收”的一个来源，而且恰好在网络抖动时发生。本机的压测里一直能看到约 200 毫秒和 1 秒的网络停顿（1b 设计文档 7.3.4），1 秒的那种正好撞上 Redis 的读超时。

修法：闸门返回“重复”且订单号等于这次调用刚生成的订单号时，按受理成功处理、照常发消息。订单号由发号器保证每次调用都不同，所以相等只可能是自己的占用。没有去改“客户端不重试”：重试对连接断开这类错误是有用的，而且即使关掉，调用方自己重试时也是同样的情形。**让操作在语义上幂等，比指望它只被执行一次可靠。**

测试用一个每次都发同一个订单号的发号器构造出这个情形（`hold_retry_test.go`）；去掉修复后它失败。

其他脚本过了一遍：

| 脚本 | 执行两次的后果 |
|---|---|
| 闸门的认领、释放、装载 | 没有：设计时就是幂等的 |
| 闸门的修正（`Adjust`，加一个增量） | 多修一次。修正有上下限，多出来的部分之后几轮对账会反向修回（1b 设计时就接受了“多修一次”） |
| 分布式锁的加锁 | 第二次看到锁已被（自己）占着，返回“没拿到”。调用方以为没拿到，锁却要等过期才释放。只影响可用性：周期任务的 leader 晚一个租期才有人接 |
| 限流的令牌桶 | 多扣一个令牌。网关的客户端关掉了重试 |
| 缓存的解锁、读己之写的标记 | 没有 |

分布式锁那一条没有改，记在这里。

**这个改动的一个后果，CI 上才看到**：`pkg/lock` 的看门狗每 TTL/3 续期一次，续期的超时也是 TTL/3。这个超时以前同样不起作用。生效之后，测试里 300 毫秒的租期意味着每次续期只有 100 毫秒，CI 上连着几次超时，锁被判定丢失，`TestLockOutlivesAcquireContext` 失败。产品逻辑是按设计工作的（生产里租期是秒级），把测试的租期放宽到了 900 毫秒。**让一个一直没生效的超时开始生效，等于改了所有带时限的调用的行为**，这类改动要预期会有这种后果。

**二、`pkg/redisx` 开出的客户端不遵守 ctx 的截止时间（已修）。**

go-redis 默认不看调用方 ctx 的截止时间和取消，要开 `ContextTimeoutEnabled`。没开时，调用方给一次 Redis 调用设的时限不起作用，真正生效的只有客户端的读超时（1 秒）。限流的时限是 20 毫秒，不开的话 Redis 卡住时每个请求要等 1 秒才退回进程内。子 Agent 用一个只接受连接、从不回应的假服务器验证了这一点。

`redisx.Open` 现在开了这个选项，所有服务的 Redis 调用都开始遵守 ctx。全量测试、e2e 通过。这本来是步骤三（超时规范）要查的东西，提前碰到了。

**教训**：两个问题都出在“客户端库的默认行为”和“我们以为的行为”之间。命令会不会被重试、时限从哪里来，要去读客户端的源码确认，不能假设。

### 4.17 结果（2026-11-14）

`make lint test e2e` 通过（e2e 18 个用例），`make chaos` 一次 PASS（22 项；chaos 里网关关闭了限流）。

**e2e 的限流用例**（`test/e2e/ratelimit_test.go`，网关用默认的按用户限额，关掉按 IP 的）：一个用户在 9 毫秒内并发发出 30 个下单请求，受理 10 个，其余 20 个是 429 `RATE_LIMITED`，`Retry-After` 是 1 秒。等待之后恢复；同时另一个用户下单、这个用户查自己的订单都不受影响；被限流的请求用过的幂等键之后再提交，得到的是新受理的订单，说明它们没有走到下单逻辑。

**压测对比**（`BENCH_RATELIMIT=1 scripts/bench.sh`）：开环每秒 1000 个下单请求、20 秒，只用 20 个用户号。这些用户的配额合计是每秒 100 单，外加每人 10 个的桶。

| | 受理 | 受理速率 | 被限流 | 受理延迟 p50 / p99 | 落库 |
|---|---|---|---|---|---|
| 限流开（按用户 5/10） | 2180 | 109 单/秒 | 89.1% | 1.0 / 3.6 ms | 109 单/秒 |
| 限流关 | 20000 | 1000 单/秒 | 0 | 1.3 / 17.0 ms | 932 单/秒 |

- 受理数和算出来的一致：20 个用户 × （桶 10 + 每秒 5 × 20 秒）= 2200，实测 2180。
- 被拒绝的 89% 在网关就返回了，没有碰 order、闸门和 Kafka。受理延迟的 p99 从 17 毫秒降到 3.6 毫秒：被放进来的请求更少，后面更空。
- 这组数说明的是“一小撮用户打不满系统”。总量超过容量的情况仍然由背压处理（这一轮里背压拒绝是 0，因为每秒 1000 单在落库能力之内）。

**每个请求多出来的开销**没有单独量。限流开的那一轮里受理延迟的 p50 是 1.0 毫秒，关的那一轮是 1.3 毫秒，两轮的负载不同，不能直接相减；Redis 的一次脚本调用在本机是 0.1 到 0.3 毫秒的量级。

**没有做的**

- 按 IP 的限流和 Redis 不可用时的退回，只有网关的集成测试覆盖，没有在跑着的整套服务上验证（e2e 和压测都从本机一个地址发请求）。
- 按接口的总量没有默认值，也没有压测。
- 被限流的请求仍然每个记一条访问日志。洪水来时这会是下一个问题，可以对 429 采样。
- 维度（`ip`、`user`、`route`）只出现在错误信息的文字里。规范说客户端不应依赖文字，而现在只能这样区分；以后给错误体加一个结构化的字段。
- 调用方取消请求时，网关记一条 error 日志并返回 500 `CANCELLED`。这是原有的行为，归到步骤三（1b 遗留的小问题）。
- 限流的汇总日志间隔固定 10 秒。指标等阶段 3。

## 5. 步骤三：服务侧保护，超时与重试规范

状态：主人已确认（2026-11-14）：不用 sentinel-go；服务之间的熔断和并发隔离现在就用 Envoy，每个服务一个边车；保护范围是全部下游调用；客户端断开时 gateway 返回 499。决定和备选方案见 ADR-0020。

对应阶段计划里的三项：服务侧保护（熔断、并发隔离、热点参数限流）、超时与重试规范、1b 遗留的小问题。验收是“手动停掉 inventory，系统按预案降级而不是雪崩”里“不雪崩”的那一半；“按预案降级”是步骤四。

### 5.1 现在是什么样

调用链和每一跳上实际生效的时限：

```
客户端 ─HTTP→ gateway ─gRPC→ order ─gRPC→ inventory ─→ MySQL
                 │              ├─→ Redis（闸门、标记）
                 │              ├─→ MySQL（订单库、从库、冷库）
                 │              └─→ Kafka（发 order.submit）
                 ├─gRPC→ payment ─gRPC→ order
                 ├─gRPC→ inventory
                 └─gRPC→ orderindex ─→ MySQL
```

| 位置 | 现在的时限 | 说明 |
|---|---|---|
| gateway 每个请求 | 5 秒 | 中间件设的截止时间，经 gRPC 传到下游的每一跳 |
| gRPC 客户端 | 3 秒 | 只在调用方没带截止时间时才加（`grpcx.Dial`）；从 gateway 进来的请求都带着 5 秒，所以它不起作用 |
| order 的 `SubmitOrder` | 3 秒 | 发 Kafka 消息的时限 |
| order 的读己之写标记 | 500 毫秒 | 步骤二之前不生效（Redis 客户端不看 ctx），现在生效了 |
| Kafka 消费者处理一条消息 | 5 到 10 秒 | 各服务自己设 |
| MySQL | 没有单独的 | 只有连接超时 5 秒；语句靠 ctx |
| Redis | 读写各 1 秒 | 加上 ctx |

三个问题：

1. **没有预算，只有一个总数。** 5 秒从入口一路传下去，中间哪一跳都可以把它用完。order 等 inventory 等满 5 秒时，gateway 也刚好超时，谁都来不及做任何补救，客户端等了 5 秒拿到一个 504。
2. **一个下游变慢，会拖住调用它的每一个请求。** inventory 卡住时，gateway 上每个查库存的请求都要等 5 秒才放手，这期间它们占着协程和连接；下单的落库也每条等 10 秒。没有任何机制在“已经知道它坏了”之后少发几个请求过去。
3. **没有按参数的保护。** 一个热门 SKU 的库存查询、一个大商家的订单列表，可以把整个接口的容量占满。步骤二的限流是按用户和接口的，看不到“这个 SKU”。

### 5.2 放在哪一层：进程里，还是独立的代理

阶段计划写的是 sentinel-go。查证的结果（2026-11-14）：它最新的正式版 v1.0.4 发布于 2021 年 12 月，之后五年没有正式版；在 Go 1.27 下能跑，但会带进 18 个较旧的间接依赖。主人不想引入停更的库。

还在维护的 Go 库（failsafe-go v0.9.8、sony/gobreaker v2.4.0、cep21/circuit v4.2.0）能做熔断和并发隔离，都没有热点参数限流。

主人提出：生产里这类保护经常不在业务进程里，而是一个独立的、和语言无关的组件。确实如此，业界有两种形态：

- **进程里的库**：Java 的 Sentinel、Resilience4j、Hystrix，.NET 的 Polly。判断发生在调用方进程里，能看到业务含义。
- **独立的代理**：服务网格的边车（Envoy、Linkerd 的代理）和入口网关（Nginx、APISIX、Kong、Envoy）。服务之间的调用都经过它，保护写在代理的配置里，业务代码不用改，所有语言一套做法。

**决定：服务之间的熔断和并发隔离用 Envoy**，现在就在 compose 里起一个；到阶段 2 上 K8s 时，同一份配置的内容照搬成边车或网格。

代理看不到、仍然要在进程里做的：

| 事情 | 为什么代理做不了 |
|---|---|
| 时限逐跳收紧（5.6） | 只有应用知道上游还剩多少时间、愿意给下一跳多少 |
| order 里展示读和落库对数据库连接的隔离（5.7） | 不是 RPC，是进程内部对一个连接池的争用 |
| 冷库的时限和并发上限（5.7） | 同上，走的是 MySQL 协议 |
| 热点参数限流（5.8） | 可以在代理里按请求头、路径做，但要再起一个限流服务；步骤二的网关已经有按键的令牌桶，直接复用 |
| 取消和超时的错误映射（5.9） | 应用自己的日志和状态码 |
| 降级逻辑（步骤四） | 熔断之后退回哪里是业务决定 |
| Kafka 消费者的重试 | 不经过代理 |

### 5.3 Envoy 能做什么：查证的结果

版本：v1.40.2（2026-10-27 发布，官方发布页查证；Envoy 没有 LTS，同时维护最近四个小版本）。下面每一条都是在本机用它的镜像加一个可控的 gRPC 上游实际跑出来的，不是照文档抄的。探测用的程序和配置没有入库。

| 要的东西 | Envoy 里的机制 | 实测 |
|---|---|---|
| 并发隔离 | 集群的 `circuit_breakers`（名字叫熔断，实际是上限）：`max_requests` 是同时在途的请求数 | 上限 128、发 400 个慢请求：恰好 128 个通过，其余在几毫秒内返回 `UNAVAILABLE`（`reset reason: overflow`），尾部带 `x-envoy-overloaded: true`。计在统计项 `upstream_rq_active_overflow` 上（HTTP/2 下超的是在途请求数；`upstream_rq_pending_overflow` 是排队溢出，这里一直是 0） |
| 熔断：下游报错 | `outlier_detection`：连续 N 次 5xx 把这个实例摘掉一段时间 | 上游连续 5 次返回 `INTERNAL` 或 `UNAVAILABLE` 后被摘除，之后的请求 0.2 毫秒返回 `UNAVAILABLE`（`no healthy upstream`）；5 秒后放回 |
| 熔断：下游进程没了 | 同上，连接失败也算 | 杀掉上游，5 次连接失败后摘除；上游重启后约 5 秒恢复 |
| 业务错误不触发熔断 | gRPC 状态码按对应的 HTTP 状态归类 | 连续 50 次 `NOT_FOUND`：原样返回，不摘除 |
| 熔断：下游变慢 | 路由的固定超时（`timeout`）到了算一次网关错误 | 见下面的三个坑 |
| 超时 | 路由的 `timeout`；或者按调用方的 `grpc-timeout` 头（`max_stream_duration`） | 都生效 |
| 多出来的一跳 | | 本机 p50 约 0.5 到 1.3 毫秒 |

**三个不查就会踩的坑：**

1. **每个服务只有一个实例时，默认配置下摘除不生效。** 两个默认值挡着：`max_ejection_percent` 默认 10%（一个实例的 10% 是 0 个）；健康实例低于 50% 时进入“恐慌模式”，无视摘除照常转发。要设 `max_ejection_percent: 100` 和 `healthy_panic_threshold: 0`。这两个默认值是为“很多实例里坏了几个”设计的，那种情况下宁可继续往坏实例发也不要把流量全压到剩下的几个上；只有一个实例时，摘除就是熔断，要的正是全部拒绝。
2. **慢下游只有路由的固定超时能熔断。** 试了三种：只靠调用方自己的截止时间，Envoy 看到的是调用方主动断开，不算上游的错，30 个请求每个都等满 300 毫秒，不摘除。让 Envoy 按调用方的 `grpc-timeout` 头提前一点超时（`max_stream_duration`），超时生效了，但同样不计入摘除。只有路由上写死的 `timeout` 到期才算一次网关错误，连续 5 次后摘除，之后快速失败。
3. **`split_external_local_origin_errors` 不能开。** 它把“代理自己产生的错误”（超时、连接失败）和“上游返回的错误”分开统计。开着的时候，30 次连续的路由超时一次都没有触发摘除；关掉之后 5 次就摘除了。

**和进程里的熔断器相比少了什么**：它按“连续失败次数”判断，没有错误比例和慢调用比例（按比例的检测要多个实例互相比较）；没有“半开时只放一个探测请求”，到时间就整个放回，还坏的话再连续失败 5 次才再次摘除，而且摘除时间逐次加长（基数乘以被摘除的次数，有上限）。对“一个下游整体坏了”这种情况够用；对“偶尔失败、错误率 30%”这种情况不敏感。

**超时到期时调用方看到的是 `UNAVAILABLE`**（`upstream request timeout`），不是 `DEADLINE_EXCEEDED`：Envoy 的 504 映射成 gRPC 的不可用。调用方区分“下游超时”和“下游不可用”时不能只看状态码。

### 5.4 拓扑：每个服务一个边车

每个服务旁边一个 Envoy 容器（主人确认，2026-11-14：比“一个容器、按调用边分集群”多四个容器，换来和 K8s 里一样的形态，阶段 2 可以直接照搬）。一次调用经过两个代理：

```
调用方进程 ──→ 调用方的边车（出站）──→ 被调用方的边车（入站）──→ 被调用方进程
              熔断、并发上限、路由超时        入站的并发上限
```

| 边车 | 出站（它的服务要调用谁） | 入站 |
|---|---|---|
| `envoy-gateway` | order、inventory、payment、orderindex | 没有：客户端直接访问 gateway 的 HTTP 端口，gateway 自己就是入口 |
| `envoy-order` | inventory | 有 |
| `envoy-payment` | order | 有 |
| `envoy-inventory` | 没有 | 有 |
| `envoy-orderindex` | 没有 | 有 |

cdc 没有 gRPC 调用，不需要边车。

- **出站在调用方的边车上。** 每个调用方对每个下游有自己的集群、自己的并发额度和摘除统计：gateway 查库存把它对 inventory 的额度用完，不影响 order 落库时的预占。这就是服务网格里“目标规则作用在客户端边车”的做法。
- **入站在被调用方的边车上。** 只做一件事：这个服务总共同时处理多少请求的上限（它对自己的保护，不管请求来自谁）。入站不做摘除：后面只有本机的一个进程。
- **端口。** 每个边车的入站监听 15001（只在容器网络里，别的边车用容器名访问它）。出站监听发布到宿主机的回环地址，给本机的服务进程用：

| 服务 | 环境变量 | 指向 |
|---|---|---|
| gateway | `ORDER_ADDR`、`INVENTORY_ADDR`、`PAYMENT_ADDR`、`ORDERINDEX_ADDR` | `envoy-gateway` 的 15081、15082、15083、15084 |
| order | `INVENTORY_ADDR` | `envoy-order` 的 15182 |
| payment | `ORDER_ADDR` | `envoy-payment` 的 15281 |

  管理端口各自发布到 19901 到 19905，只绑本机。
- 服务在宿主机上运行（`make run` 起的是二进制），边车在容器里：入站把请求转给 `host.docker.internal` 上的服务端口，compose 里加 `extra_hosts` 让它在 Linux（CI）上也能解析。到了 K8s，边车和服务在同一个 Pod 里，这个地址换成 `127.0.0.1`。
- 服务怎么用上它：各服务本来就从环境变量读下游地址。`scripts/run-local.sh` 把它们指到自己边车的出站端口；不设时仍然直连，按模块的测试（`make test`）不受影响，也不需要 Envoy。
- 边车放在 `make up` 里，不放 `make up-core`：e2e、chaos、bench、`make run` 需要它们，CI 的按模块测试不需要。
- 配置是静态的 YAML，每个边车一个文件，放在 `deploy/envoy/`，入库。`make envoy-validate` 用 Envoy 自己的校验模式逐个检查。
- 管理端口用来看每个集群的在途数、溢出次数、摘除次数，测试和排查都靠它。

一次调用多经过两个代理，本机每个约 0.5 到 1.3 毫秒（5.3），合计约 1 到 2.5 毫秒。

### 5.5 Envoy 的参数

每条边：

出站（调用方的边车上，每个下游一个集群）：

| 参数 | 值 | 理由 |
|---|---|---|
| `max_requests`（同时在途） | gateway → order 512；其余 128 | 5.1 的问题 2：给每条边的资源占用封顶 |
| `max_pending_requests`、`max_connections` | 与 `max_requests` 相称 | HTTP/2 下一条连接跑很多流，连接数给得小 |
| `max_retries` | 0 | 同步链路不重试（5.6） |
| 路由的 `timeout` | gateway → 各下游 3 秒；order → inventory、payment → order 1 秒 | 这一跳的预算；也是慢下游能被熔断的唯一途径（5.3 的坑 2） |
| 连续失败几次摘除 | 5 | 上游报错、连接失败、路由超时都算 |
| 摘除多久 | 5 秒，上限也是 5 秒 | 摘除时间是基数乘以被摘除的次数（实测第二次是 10 秒），默认的上限按文档是 300 秒；杀进程测试里服务被反复杀，不想让恢复时间越来越长 |
| `max_ejection_percent` | 100 | 坑 1 |
| `healthy_panic_threshold` | 0 | 坑 1 |

入站（被调用方的边车上）：

| 参数 | 值 | 理由 |
|---|---|---|
| `max_requests` | order 1024；inventory、payment、orderindex 各 512 | 这个服务总共愿意同时处理多少。比任何一个调用方的出站额度都大，正常情况下先触发的是出站的上限 |
| 路由的 `timeout` | 不设 | 时限由调用方那一侧决定，入站再设一个只会多一个要对齐的数 |
| 摘除 | 不做 | 后面只有本机的一个进程 |

调用方看到的：并发超限和被摘除都是 `UNAVAILABLE`，立刻返回；gateway 映射成 503。

### 5.6 超时预算和重试规范（进程里）

**超时**的规则：

1. 总时限只在入口设一次（gateway 的 5 秒），经 ctx 往下传。
2. 每一跳给它调用的下一跳单独设一个更短的时限，从上游剩下的时间里取，不超过它。上一跳在下一跳超时之后还有时间处理。
3. 没有上游截止时间的调用（消费者、周期任务）自己设总时限，规则同上。

| 调用 | 时限 | 在哪设 |
|---|---|---|
| gateway → 任一下游 | 上游剩余时间，最多 3 秒 | Envoy 的路由超时 3 秒；进程里 3.5 秒兜底 |
| order → inventory（Reserve、WarmUp） | 1 秒 | Envoy 1 秒；进程里 1.5 秒兜底 |
| payment → order（查订单） | 1 秒 | Envoy 1 秒；进程里 1.5 秒兜底 |
| order → Redis（闸门的 Hold、Claim 等） | 300 毫秒 | 进程里 |
| order → 冷库 | 1 秒 | 进程里。1c 留下的：`GetOrder` 查冷库没有自己的时限 |
| order → 从库 | 上游剩余时间，最多 500 毫秒 | 进程里。超时退回主库 |
| 周期任务的 Guard（leader 锁） | 1 秒 | 进程里。1b 留下的 |

两处都设是有意的，但**两处不是同一个数**：表里的时限写在 Envoy 的路由上，是这一跳真正的预算；进程里的时限比它长 500 毫秒（`grpcx.SidecarMargin`），只做兜底，保证边车不在（直连）或者边车自己卡住时调用方仍然会放手。

第一版设计写的是“两处同一个数”，这是错的，gateway 的子 Agent 指出、也和 5.3 的实测吻合：进程里的计时器先启动，两个数相等时总是调用方先放手，边车看到的是“调用方断开”，不计入异常检测，慢下游永远不会被摘除。必须让边车先超时。由此的一个后果：下游超时时，调用方正常看到的是边车返回的 `UNAVAILABLE`（gateway 映射成 503），只有边车不在时才是进程里的 `DEADLINE_EXCEEDED`（504）。

`grpcx.Dial` 增加 `WithHopTimeout` 选项；“没带截止时间就加 3 秒”的兜底保留。

**重试**。现在系统里的重试：

| 位置 | 重试什么 | 现状 |
|---|---|---|
| Kafka 消费者 | 一条消息处理失败 | 原地重试，指数退避，幂等由 handler 保证 |
| 数据库事务 | 死锁、锁等待超时 | `pkg/retry`，带抖动 |
| Redis 客户端 | 连接错误、读超时 | go-redis 自动重试 3 次（步骤二查明的） |
| gRPC 调用、gateway、Envoy | 无 | 不重试 |

规则，写进 AGENTS.md 的工程规范：

1. 只重试幂等的操作。不幂等的要么先改成幂等（步骤二的 `Hold`），要么不重试。
2. 一条调用链上只有一层重试。每层都重试 3 次，三层就是 27 次，下游刚恢复就被重试的洪水再次打垮。本项目的选择：同步调用链上不重试（进程里不重试，Envoy 的 `max_retries` 为 0），由客户端带幂等键重试；异步的由消费者重试。
3. 退避加抖动，否则同时失败的请求会同时重试。
4. 重试要有上限，耗尽之后的去向要明确（死信、返回错误、留给周期任务）。

这一步要改的：`kafkax` 消费者的退避现在是固定翻倍，没有抖动，加上。

### 5.7 进程内部的隔离：数据库连接

- **order 的展示读对订单库的并发上限**：每个库 16（连接池 25，给落库留 9 个）。`GetOrder` 和列表读订单库之前先取一个名额，取不到立刻返回“资源耗尽”。步骤一量到查询会挤占落库（2.10）；步骤二按用户限了查询的频率，这里限的是查询总共能占多少连接。
- **冷库**：并发上限 8（连接池 10），时限 1 秒。冷库卡住时旧订单的查询最多占 8 个协程、各等 1 秒，不影响别的。冷库没有熔断器（它走 MySQL 协议，不经过 Envoy）；时限加并发上限已经把它能占用的资源封了顶，不值得为它单独写一个熔断器。

实现是一个带上限的信号量，放在 `pkg` 里，十几行。

### 5.8 热点参数限流

在 gateway，复用步骤二的 `ratelimit.Local`（每个键一个令牌桶，有容量上限和淘汰）：

| 接口 | 参数 | 默认 |
|---|---|---|
| 查库存 `getStock` | 路径里的 `sku_id` | 每个 SKU 每秒 500，桶 1000 |
| 商家订单列表 `listMerchantOrders` | 路径里的 `merchant_id` | 每个商家每秒 50，桶 100 |

和步骤二的“按接口”不同：那是一个接口一个桶，这里是这个接口下每个参数值一个桶。可以给个别参数值单独设阈值（比如某个大促的 SKU）。状态在进程里：热点保护要的是“别让一个 SKU 把这个实例占满”，不需要跨实例精确。

被拒绝时沿用 429 `RATE_LIMITED`，维度是 `hot`。配置 `RATE_LIMIT_HOT`，格式同步骤二。

下单按 SKU 的热点限流不做：闸门已经按 SKU 的库存原子地放行，卖完了的请求在闸门就返回了。

### 5.9 1b 遗留的小问题

- **调用方取消被记成 ERROR、返回 `Internal`。** order 的 `internal()` 不看错误是不是来自调用方的 ctx；payment 同样。改成：调用方取消返回 `Canceled`、不记 ERROR；到了截止时间返回 `DeadlineExceeded`、记 WARN。
- **gateway 对客户端主动断开返回 500 并记 ERROR**：改成 499（Nginx 的约定，不是标准状态码）并记 INFO。主人已确认。
- **周期任务的 Guard 调用没有单独的时限**：`worker.Loop` 调 `Guard.Allow` 时加 1 秒的时限。
- “payment 启动时 Redis 不可用就启动失败”归步骤四。

### 5.10 测试

- **Envoy 的配置**：`make envoy-validate`。
- **经边车的故障用例**（e2e 的环境，服务经边车互相调用）：
  - 用 `kill -STOP` 让 inventory 挂住（进程在、不响应）：查库存的请求先是各等 3 秒返回 503，连续 5 次之后毫秒级返回 503；`kill -CONT` 之后约 5 秒恢复。期间下单的受理和查订单不受影响。
  - 杀掉 inventory：查库存快速返回 503；下单照常受理（它只碰闸门）；inventory 重启后，排队的订单落库。
  - 从 Envoy 的管理端口读统计，断言摘除确实发生过、并发溢出为 0。
- **并发上限**：对一条边发超过上限的慢请求，多出来的立刻被拒（用 Envoy 的统计核对数字）。
- **进程里的**（带 `-race`）：按方法的时限生效且不超过上游剩余的时间；每一跳的时限都短于上一跳的（把配置里的数排出来检查，并且和 Envoy 配置文件里的路由超时一致）；信号量满了立刻拒绝、释放后恢复；热点参数不同的值互不影响；取消之后 order 和 payment 的日志里没有 ERROR、返回码是 `Canceled`；gateway 对客户端断开返回 499。
- **`scripts/chaos.sh`**：服务经 Envoy 互相调用，随机击杀照常通过对账。
- **压测**：开环打查库存，中途挂住 inventory，对比经 Envoy 和直连两种情况下别的接口的延迟；再量一次 Envoy 这一跳给下单延迟加了多少。

### 5.11 实现顺序

1. 主线（Fable）：五个边车的配置文件和 compose、`make envoy-validate`（配置里的每个数都对应 5.5 的一行）；`grpcx` 的按方法时限；信号量；`worker` 的 Guard 时限；取消的错误映射；`kafkax` 退避的抖动。

3. 实测并写回本文。

### 5.12 不在这一步做的

- 把步骤二的网关限流挪到 Envoy：它已经用 Go 做完了，而且按用户、按接口的判断要懂业务。阶段 2 上 Ingress 时，按 IP 的那一层可以挪到入口代理。

### 5.13 实现中的发现（2026-11-14）

**第一版设计里“进程里的时限和边车的超时是同一个数”是错的**，见 5.6。gateway 的子 Agent 指出：进程里的计时器先启动，两数相等时总是调用方先放手，边车看到的是调用方断开，不计入异常检测。这和 5.3 的实测是同一件事，设计时没有把两处连起来。改成边车的数是预算、进程里的比它长 500 毫秒。

**并发超限计在 `upstream_rq_active_overflow` 上**，不是 `upstream_rq_pending_overflow`。HTTP/2 下一条连接跑很多流，超的是在途请求数，不是排队数。第一版的文档和任务说明里写错了，故障注入的脚本第一次运行就因为断言了错的统计项而失败。

**一个没有解释的现象。** 故障注入里“杀掉 inventory 再重启”的场景，紧跟在“挂住”的场景后面跑时，重启后约 30 毫秒查库存就成功了，而此时统计里 `ejections_active` 仍是 1，按理要等 5 秒的摘除期；单独跑这个场景时是预期的 5.5 秒。可能是同一个实例在上一次摘除之后的某种提前放回，也可能是统计滞后。断言写的是“20 秒内恢复”，两种情况都满足。

**order 里按跳时限带出来的问题：**

- **闸门调用的时限是 300 毫秒，比原来实际生效的 1 秒（Redis 客户端的读超时）紧得多。** 一次 TCP 重传（约 200 毫秒）之内能过，连丢两个包或者突发时等连接池就会超。超时的下单返回 503，客户端带同一个幂等键重试。压测时要看“hold outcome unknown”这条 WARN 的数量。
- **Hold 超时之后的清理和 Hold 本身可能乱序，留下一个没有落库消息的占用**（原来就有，时限收紧后更容易出现）。Hold 的包丢了在重传，而清理（`ReturnIfUnclaimed`）走另一条连接先到了 Redis：清理看到“没有占用”，随后 Hold 执行成功，占用和幂等键都留下了，却没有人发落库消息。用户在宽限期内重试会看到一个不会落库的 `CREATING`，直到回收任务把它收走。修法要改闸门：清理时写一个短期的“已放弃”标记，Hold 看到它就不再占用。没有做，记在这里。
- **预热（WarmUp）被这一跳的 1 秒封顶了**，它自己原来的时限是 3 秒。冷启动时一次装载多个 SKU 是否够用，没有量过。
- **落库时的预占（Reserve）最多等 1 秒**，原来可以等到消费者的 10 秒。库存异步扣减之后预占不再等行锁，正常是几毫秒；超时按“结果未知”原地重试。

**展示读的并发上限只限主库，不限从库。** 上限的目的是给写路径留主库的连接，从库的连接池不参与写。从库读超时（500 毫秒）后退回主库，退回的那次读占主库的名额，所以坏掉的从库不会把主库的查询推过上限。名额满时客户端看到 429，原因码 `READ_BUSY`，没有 `Retry-After`。

**取消和超时的判断依据是 ctx 的状态，不是错误的类型。** 驱动在超时后返回的错误五花八门：Redis 客户端返回网络层的 `i/o timeout`，MySQL 驱动在连接被关掉时返回 `invalid connection`。所以每个按跳的时限都用带原因的超时（`context.WithTimeoutCause`），事后看 `context.Cause` 是不是这一跳自己的时限；请求自己的 ctx 出了错则以它为准。三种情况对外分别是 `Canceled`（不记日志）、`DeadlineExceeded`（WARN）、`Unavailable`（WARN）。

**order 返回的取消错误必须还能解包出 `context.Canceled`。** 查询缓存把同一个订单的并发回源合并成一次；发起回源的那个调用被取消时，搭便车的调用靠 `errors.Is(err, context.Canceled)` 认出“这是别人的取消”而自己重新回源。只返回一个普通的 gRPC 状态错误，它们会把别人的取消当成自己的结果。

**没有改的：**

- `pkg/grpcx` 的服务端日志拦截器对 `DeadlineExceeded` 和 `Unavailable` 仍然记 ERROR。服务自己不再为调用方超时记 ERROR 了，但拦截器每个请求还会补一条。按错误级别告警时调用方超时仍然会响。
- gateway 的热点限流：`RATE_LIMIT_HOT=off` 不取消 `RATE_LIMIT_HOT_ITEMS` 里的单独阈值。
- gateway 路径里的 ID 接受 `007`、`+7`，比规范宽松；热点限流按解析后的整数计数，不能靠改写法绕过。
- 客户端在请求体还没读完时断开，gateway 返回的仍然是 400。

### 5.14 结果（2026-11-14）

`make lint test e2e` 通过（e2e 18 个用例，服务之间经边车）。`make chaos` 一次 PASS（22 项，服务经边车，被杀的服务会被调用方的边车摘除 5 秒；对账不受影响）。`make envoy-validate` 进了 CI。

**故障注入**（`make fault`，`scripts/fault.sh`；服务经边车，gateway 关闭限流）

| 场景 | 结果 |
|---|---|
| A 基线 | 查库存 p50 1 毫秒；下一单并落库 |
| B inventory 挂住（`kill -STOP`） | 查库存前 5 次各约 3 秒返回 503，之后 7 次在 1 到 2 毫秒返回 503；摘除 1 次。期间查订单 20 次全部 200、延迟和基线一样；新订单被受理（202）。`kill -CONT` 之后 5.5 秒恢复；挂住期间受理的订单在恢复后落库 |
| C inventory 被杀（`kill -9`） | 12 次查询最长 5 毫秒，全部 503；摘除 1 次；重启后恢复 |
| D 并发上限（同时 300 个请求，上限 128） | 恰好 172 个被立刻拒绝（503，不到 500 毫秒），128 个在途；没有一个等满 5 秒；查订单不受影响 |

**边车加了多少延迟**（`BENCH_SIDECAR=1 scripts/bench.sh`：开环每秒 500 单、20 秒，经边车和直连各一轮）

| | 受理延迟 p50 | 受理延迟 p99 | 落库 |
|---|---|---|---|
| 经边车 | 1.67 ms | 17.2 ms | 490 单/秒 |
| 直连 | 0.99 ms | 2.4 ms | 493 单/秒 |
| 差 | +0.69 ms | +14.8 ms | 持平 |

受理这条路径（gateway → order）经过两个代理。中位数多 0.7 毫秒，和 5.3 里单个代理 0.5 到 1.3 毫秒的量级一致；尾部多了约 15 毫秒，是这一步最明显的代价。本机的容器网络本来就有偶发的停顿（1b 设计文档 7.3.4），请求多经过两次容器边界，撞上的机会更多；到了 K8s，边车和服务在同一个 Pod 里走回环，这个数要重新量。落库吞吐没有变化：每秒 500 单在落库能力之内，瓶颈不在这一跳。

**没有做的**

- 按错误比例和慢调用比例的熔断，半开时的单个探测：Envoy 在单实例下没有（5.3）。
- 5.13 里记的几项：受理超时后清理和受理乱序留下的占用；gRPC 日志拦截器对超时仍记 ERROR；预热被 1 秒封顶是否够用。
- 展示读的并发上限、冷库的上限和时限、取消的映射，只有按模块的集成测试，没有在跑着的整套服务上压到上限。
- `make fault` 没有进 CI（耗时，而且对机器的时序敏感）。
- Envoy 的访问日志和链路追踪没有开；现在排查只能看 `/stats`。

## 6. 步骤四：降级预案和优雅启停

状态：主人已确认（2026-11-14）：闸门的 Redis 不可用时拒绝下单、不退回数据库扣减（6.4）；开关在进程内、运行中可改（6.9）；熔断器自己写（6.3）；落库健康（6.5）和列表的部分结果（6.8）都做。决定和备选方案见 ADR-0021。

对应阶段计划里的三项：降级预案、优雅启停、payment 启动时 Redis 不可用。验收是“手动停掉 Redis 或 inventory，系统按预案降级而不是雪崩”里“按预案降级”的那一半。

步骤三解决的是“一个依赖坏了，别把调用方拖死”：时限、并发上限、熔断。这一步回答接下来的问题：依赖坏着的这段时间里，每个接口对用户是什么表现，已经受理的订单会怎样，依赖恢复后要不要人管。

### 6.1 现在是什么样

下面每一条都是读代码得出的，没有实测；6.12 的故障场景会把它们逐条跑出来。

**闸门所在的 Redis（`redis`）不可用**

| 路径 | 现在的表现 | 问题 |
|---|---|---|
| 下单受理 | `Hold` 等满 300 毫秒，再花最多 300 毫秒尝试撤销，返回 503 | 结果是对的，但每个请求都要等满时限 |
| 落库（已受理、还在排队的订单） | `Claim` 失败，重试 10 次（约 26 秒）后进死信 | **订单丢失**：占用还在 Redis 里，Redis 恢复后被回收任务归还，用户拿到过 202，之后查询是 404 |
| 查订单 | 读占用等满 300 毫秒，退回只读订单行；行不存在时 503 | 每次查询多 300 毫秒 |
| 取消、支付结果 | 不依赖 Redis（读己之写的标记写不进去只记日志） | 无 |
| inventory 处理订单事件 | MySQL 一步已提交，闸门一步失败，重试 60 次（约 5 分钟）后进死信 | 超过 5 分钟后占用没人归还，对账看不出来，要人工重放 |
| 周期任务的 leader 锁 | `FailOpen`：每个实例都跑 | 每一轮先等锁调用失败，中继从每 100 毫秒一轮变成约每秒一轮 |
| 启动 | order、inventory、payment 都启动失败（`redisx.Open` 会 PING） | Redis 故障期间重启或发布的实例起不来，连不依赖 Redis 的查询和支付结果也跟着没了 |

**其他依赖**

| 依赖 | 现在的表现 | 问题 |
|---|---|---|
| 缓存的 Redis（`redis-cache`） | 查询直接回源，限流退回进程内 | 每次查询先在 Redis 上失败一次才回源；order 配了独立的缓存地址时启动失败 |
| 订单库的从库挂起 | 每次展示读等 500 毫秒后改读主库 | 每个请求都付一次超时；启动时连不上从库，order 启动失败 |
| 订单库的从库落后 | `gtid` 模式下带标记的读各等 100 毫秒再读主库；标记过期（1 分钟）后读到旧数据 | 没有任何东西在看延迟（ADR-0013 留下的） |
| 冷库 | 旧订单的查询 1 秒超时，并发上限 8；用户列表需要冷库的那一页整页失败 | 每个请求都付 1 秒；启动时连不上冷库，order 启动失败 |
| inventory | 边车在连续 5 次失败后快速失败。查库存 503；下单照常受理，落库时预占失败，重试约 26 秒后进死信，订单由 sweeper 置为失败 | **受理了落不了库的订单**：背压要等约 30 秒才开始拒绝，这期间受理的订单要么失败、要么排队超过宽限期被回收 |
| Kafka、订单库主库 | 受理和写入失败 | 硬依赖，没有可退的地方，靠它们自己的高可用（阶段 2） |

**启停**

- 停止：按启动的相反顺序，总时限 20 秒。gRPC 先把健康状态置为不可用再等在途调用；消费者等在途的 handler、提交位点；中继最后发一轮。顺序在 1b 已经理过，这一步不改。
- 没有“摘流”这个阶段：收到 SIGTERM 立刻停止接新请求。多实例时，负载均衡还没来得及知道这个实例要走，仍然发过来的请求会被拒绝。
- 只有 `/healthz`，进程活着就返回 200，分不出“活着”和“可以接流量”。

### 6.2 原则

1. **不受理落不了库的订单。** 用户拿到 202 之后订单消失或者必然失败，比一开始就拿到 503 糟糕：前者用户以为下单成功了。受理之前就知道落不了库（闸门不可用、落库在持续失败），直接拒绝。
2. **依赖不可用时消息留在分区里等，不进死信。** 死信只收“这条消息本身有问题”的。依赖坏了把消息送进死信，等于把一次会自己恢复的故障变成要人工处理的数据问题。
3. **坏掉的依赖只付一次超时。** 连续失败之后的一段时间内不再去问它，直接走降级的那条路。服务之间的调用由边车做（步骤三），边车看不到的（Redis、MySQL）在进程里做。
4. **可选的依赖不能挡住启动。** 运行中坏了能降级的东西，启动时坏着也应该能起来。
5. **降级的结果要么精确、要么明说不完整。** 不悄悄返回可能有错的数据。
6. **自动降级和人工开关走同一条路。** 人工关掉一个功能，等于把它的熔断器强制打开；这样降级路径平时也有人走，不会到用的时候才发现是坏的。

### 6.3 进程里的熔断器：`pkg/breaker`

步骤三里服务之间的熔断交给了 Envoy。Redis 和 MySQL 不走 gRPC，边车看不到，要在进程里做。步骤二的 `ratelimit.Fallback` 里已经有一个最小的（出错即打开，过一秒再试），这里把它做成一个正式的、可以复用的。

三个状态：

```
        连续失败 N 次                 冷却时间到
关闭 ───────────────→ 打开 ───────────────→ 半开
 ↑                      ↑                     │
 │                      └──── 探测失败 ───────┤
 └──────────────────── 探测成功 ──────────────┘
```

- **关闭**：放行，数连续失败的次数，成功一次清零。
- **打开**：不放行，调用方立刻拿到 `ErrOpen` 去走降级。
- **半开**：只放一个请求去探测，其余仍然不放行。探测成功回到关闭，失败回到打开。

默认连续 5 次、冷却 5 秒，和边车的摘除参数一致。

按连续失败而不是错误比例：这里保护的依赖坏起来是整体坏（Redis 连不上、MySQL 挂起），连续失败几毫秒到几秒内就能数到；按比例要维护滑动窗口，对付的是“30% 的请求失败”这种情况，这里没有遇到。以后需要再加。

**什么算失败**由调用方告诉它：依赖返回的错误和这一跳的超时算；调用方自己取消或者上游的截止时间到了不算（那是调用方的事，和步骤三判断取消的规则相同）；业务结果（库存不足、订单不存在）不算。

半开时只放一个探测，是 Envoy 的摘除没有的（它到时间整个放回）。对 Redis 这种“恢复的一瞬间所有等着的请求一起涌上去”的依赖有用。

### 6.4 闸门的 Redis 不可用

这是这一步最主要的取舍。阶段计划里写的是“Redis 不可用时退回数据库扣减并收紧限流”。建议不这么做，改成：**拒绝新的下单，其余照常，已受理的订单等 Redis 恢复后继续落库。**

**为什么不退回数据库扣减。**

1. **扣减有了两个权威，切回来才是难点。** 退回数据库期间卖掉的数量，闸门不知道。Redis 恢复后闸门里的数是旧的，必须先按 MySQL 重新装载才能再用；而恢复的 Redis 里可能还留着故障前受理、没落库的占用，重新装载时要把它们算进去。这一段做错的后果是超卖。
2. **“Redis 不可用”是每个实例各自的判断。** 一个实例连不上 Redis（网络分区），别的实例正常：前者在 MySQL 里同步扣减，后者继续用闸门受理，同一份库存卖两次。要避免就得有一个所有实例一致的模式开关，切换时还要围栏；这是另一个一致性问题，而我们除了 MySQL 没有能做这件事的存储。
3. **MySQL 已经不阻止超卖了**（ADR-0018）。库存扣减改成异步之后，MySQL 一侧只负责发现超卖。退回数据库扣减要恢复同步的条件更新，还要先把没应用的增量应用完，等于把 1a 的路径重新接回来并长期维护。
4. **退回的那条路容量很小。** 同步扣减是 1a 的吞吐（每秒几百单，热门 SKU 上是行锁排队）。秒杀流量下即使退回成功，绝大部分请求还是要被限流拒绝。
5. **让闸门高可用是更直接的办法。** Redis 的主从加自动切换（阶段 2、阶段 4）把不可用的时间压到秒到十几秒；这段时间拒绝下单，切换完成后自动恢复。为十几秒的窗口维护第二条扣减路径不划算。

真实系统里两种做法都有。有独立的降级扣减路径的，通常有一个配置中心下发的全局开关和一套切换预案（先停受理、排空、切模式、重新预热），是人工操作的，不是自动的。它作为备选方案记在 ADR-0021 里。

**各条路径的表现：**

| 路径 | Redis 不可用时 |
|---|---|
| 下单受理 | 闸门的熔断器打开后立刻返回 503，原因码 `STOCK_GATE_UNAVAILABLE`，带 `Retry-After`。打开之前的几个请求各等一次 300 毫秒。服务之间传的不是 gRPC 的 `UNAVAILABLE`，见 6.16 |
| 已受理、在排队的订单 | 留在 Kafka 里。落库的消费者停在 `Claim` 上重试，不进死信 |
| 查订单 | 已落库的照常返回（熔断器打开后不再等 300 毫秒）；没落库的返回 503（分不清是在排队还是不存在） |
| 取消、支付、支付结果、关单 | 照常 |
| 查库存 | 照常（读 MySQL 和缓存） |
| inventory 处理订单事件 | MySQL 一步照常，闸门一步重试到 Redis 恢复，不进死信 |
| 闸门对账 | 不跑（它的正确性依赖互斥，宁可不跑） |
| 其余周期任务 | 每个实例都跑；锁调用失败后的一段时间内不再问锁，不拖慢每一轮 |

**恢复。** 不需要人管，顺序是：

1. 半开的探测成功，熔断器关闭，受理恢复。
2. 落库的消费者在下一次重试（最多 5 秒后）认领成功，排队的订单开始落库。落库时已经过了支付时限的直接置为失败（1b 已有）。
3. **回收任务在闸门恢复后的半个宽限期内不回收。** 回收任务按“受理了多久还没被认领”判断孤儿，故障期间这个时钟一直在走，而消费者一直认领不了。不等这一下，Redis 一恢复，回收任务会和消费者抢着处理排队的订单，抢赢了订单就没了。队列长度上限 1 万、落库每秒 600 到 800 单，半个宽限期（30 秒）够排空。
4. inventory 的消费者把欠着的结清和归还补上；对账恢复。

**Redis 重启后数据丢了**是另一件事：占用和幂等键都没了，已受理的订单认领不到。这要靠持久化配置缩小窗口，留给阶段 4 的故障实验（1b 设计文档 6.6 已经写明）。

### 6.5 不受理落不了库的订单：落库健康

inventory 不可用或者订单库的某个主库不可用时，受理这一侧（只碰 Redis 和 Kafka）什么都不知道，照常返回 202。背压的三项检查都要等排队超过 `ADMIT_MAX_WAIT`（30 秒）才触发；ADR-0011 的后果一节也记着“消费者活着但落不了库”的情形没有处理。

做法：order 的每个订单库一个熔断器，由落库的结果喂它。

- 落库的一次处理因为依赖不可用而失败（预占调不通、订单库写不进去）算一次失败；处理完成（包括业务上被拒绝、订单置为失败）算成功。
- 某个库的熔断器打开时，订单号落在这个库的下单请求在 `Hold` 之前就返回 503，原因码 `ORDER_LANDING_UNAVAILABLE`。
- inventory 坏了，所有库的落库都失败，全部打开；一个订单库坏了，只有它的用户受影响。
- 半开的探测不用另外发：落库的消费者本来就在重试排队的消息，重试成功就是探测成功。**没有排队的消息时**（空闲），半开状态放一个下单请求进来当探测。

这是每个实例自己的判断：没有分到分区的实例看不到落库的结果，它的熔断器不会打开，那时兜底的仍然是闸门里的背压（所有实例共用）。

**落库的重试次数。** 现在是 10 次后进死信，再由 sweeper 把订单置为失败。改成不设上限，理由是原则 2。不设上限不等于永远重试，每条消息都有终点，不需要死信来收尾：

- 认领不了（闸门不可用）：闸门恢复后认领成功，继续落库；这时已经过了支付时限的直接置为失败。占用如果已经被回收，认领不到，消息被丢弃。
- 订单行已经写进去、一直预占不了的：sweeper 在创建超时（1 分钟）后把它置为失败，消费者下一次重试看到订单已是终态，直接结束。
- 认领了、订单行写不进去（订单库不可用）：订单库恢复后写入成功。原来的做法下这种消息进了死信，占用已认领却没有订单行，回收任务不会自动归还（不知道 MySQL 里有没有预占），用户看到的是 `CREATING` 持续到支付时限的两倍，然后报出来等人工处理。

消息本身有问题的仍然由 handler 标成 `Permanent` 直接进死信。inventory 和 payment 消费订单事件的消费者同样改成不设上限（order 消费支付结果的在 1c 已经改了）。代价：一条 handler 没识别出来的坏消息会一直挡住它的分区，要靠消费积压的告警发现（阶段 3）。

**inventory 短暂抖动和长时间不可用用同一套处理。** 抖动几秒：排队的订单重试几次后落库，用户没有感觉；受理在连续 5 次失败后拒绝几秒。不可用几分钟：受理一直拒绝；故障前已经受理的订单，写了订单行的由 sweeper 置为失败，没写的被回收。

### 6.6 缓存的 Redis 不可用

`pkg/cache` 里加熔断器：打开期间读和写都跳过 Redis，直接回源。order 的订单缓存、inventory 的库存缓存都经过它，不用各改一遍。

回源的压力由步骤三的并发上限挡住（每个订单库 16 个展示读），超出的返回 429。计划里说的“收紧限流”在这里指的就是这个上限：缓存没了，能打到数据库的查询数不变，多出来的被拒绝。

### 6.7 从库挂起或落后

每个从库一个健康标记，由一个后台探测维护（每秒一次）：

1. 在主库上读当前的 GTID 集合。
2. 在从库上 `WAIT_FOR_EXECUTED_GTID_SET(这个集合, 最大延迟)`。
3. 在最大延迟内追上了：健康。没追上、查询出错或超时：不健康。

不健康时，这个库的展示读直接读主库，不再去试从库；sweeper 的扫描同样。连续两次探测通过才恢复，避免在阈值附近来回切。请求路径上读从库出错时也立刻标记为不健康，不等下一次探测。

不用 `SHOW REPLICA STATUS` 里的 `Seconds_Behind_Source`：它是用从库正在回放的事件的时间戳算的，IO 线程断了或者落后时它是 0 或 NULL，看上去一切正常。上面的探测量的是“主库刚才的位置，从库多久能追上”，就是读者真正关心的那个量，而且复用了读己之写已有的机制。

最大延迟默认 1 秒，必须小于 `window` 模式下 pin 的时长（3 秒）：延迟超过 pin 的时长，`window` 模式就会读到自己刚写的数据的旧版本。

从库不健康期间，展示读全部落到主库，仍然受每个库 16 个的并发上限约束。

启动时从库连不上：不阻止启动，标记为不健康，探测通过后自动用上。

### 6.8 冷库不可用

- **启动**：连不上不阻止启动。建表（迁移）在后台重试到成功；成功之前冷库的查询立刻返回不可用。
- **运行中**：加熔断器。打开后旧订单的查询立刻返回 503（现在每个请求等 1 秒）。近 30 天的订单号不查冷库，完全不受影响（1c 已有）。
- **按用户列出订单**：现在需要冷库的那一页整页失败。改成返回精确的前一段：订单号晚于冷热分界（`MinHotAge`，30 天）的行不可能在冷库里，这一段只看热库就是精确的。返回这一段，带上游标和一个新字段 `archive_unavailable = true`；客户端可以显示“更早的订单暂时无法查看”，之后用游标接着取。这一段为空时（已经翻到 30 天之前了）返回 503。
  - 要改 proto 和 OpenAPI 规范（各加一个布尔字段）。
- 针对已归档订单的支付结果要查冷库（1c 步骤五）。这种消息只会是陈年消息的重放；冷库不可用时它会挡住所在的分区，直到冷库恢复。不处理，记在这里。

### 6.9 非核心功能的开关：`pkg/degrade`

每个服务一组有名字的开关，每个开关两个取值：`auto`（功能开着，是否降级由熔断器或探测决定，默认）、`off`（强制降级）。第一版设计还有一个 `on`（强制不降级），实现时去掉了：它要求每个调用点多一条绕过熔断器的路径，而“依赖坏着却强制去用”没有实际用处。

| 服务 | 开关 | 关掉之后 |
|---|---|---|
| order | `admission` | 拒绝新的下单（503）。用于维护窗口和演练 |
| order | `cache` | 查询不经过缓存 |
| order | `replica_read` | 展示读只读主库 |
| order | `archive_read` | 不查冷库，表现同 6.8 |
| inventory | `cache` | 查库存不经过缓存 |
| gateway | `merchant_orders`、`user_orders`、`stock_query` | 对应的接口返回 503，原因码 `FEATURE_DISABLED` |

- 初始值从环境变量 `DEGRADE` 读（例如 `DEGRADE=archive_read=off,cache=off`）。名字写错拒绝启动。
- gateway 只有一个对外的端口，开关的接口没有鉴权，不能挂在上面：gateway 另开一个只在本机监听的管理端口。
- 运行中通过服务内部的 HTTP 端口（和 `/healthz` 同一个，不经过 gateway）查看和修改：`GET /degrade` 列出每个开关的取值和当前实际状态（包括熔断器是开是关、从库是否健康）；`PUT /degrade/{name}` 修改。
- 只在这个进程里生效，不持久化，重启后回到环境变量的值。多实例时要逐个改。阶段 2 上了 K8s 之后，持久的配置走 ConfigMap，这个接口留作应急。

`GET /degrade` 在有指标之前也是唯一能看到“现在哪些东西降级了”的地方，故障注入的脚本靠它做断言。

### 6.10 启动：哪些依赖必须在

| 依赖 | 启动时不可用 | 理由 |
|---|---|---|
| 自己的主库、Kafka | 启动失败 | 没有它们什么都做不了 |
| 闸门的 Redis（order、inventory） | 启动，受理处于降级状态 | Redis 故障期间重启的实例要能回来承担查询、支付结果、订单事件 |
| 锁的 Redis（payment） | 启动，锁按 `FailOpen` 放行 | 1b 留下的问题：运行中能放行，启动时却不行 |
| 缓存的 Redis、从库、冷库 | 启动，对应功能降级 | 可选依赖 |
| 下游的 gRPC 服务 | 启动 | 连接本来就是惰性的 |

`redisx` 增加一个不因为 PING 失败而返回错误的打开方式：记一条 WARN，返回客户端，连接池在后台建。

### 6.11 优雅启停

停止的顺序不改。增加三样东西，都在 `pkg/app` 里：

**就绪和存活分开。**

- `/healthz`（存活）：进程能响应就是 200。和现在一样。
- `/readyz`（就绪）：所有组件都启动之后才是 200；开始停止的那一刻起变成 503。gRPC 的健康检查服务跟着它走。
- **依赖降级不影响就绪。** 闸门的 Redis 坏了，所有实例会同时变成未就绪，负载均衡把它们全部摘掉，本来还能提供的查询和支付也没了。就绪只回答“这个进程能不能接请求”；依赖的状态在 `/degrade` 里看。

**摘流的等待（`DRAIN_DELAY`）。** 收到 SIGTERM 之后：

1. 就绪变成 503，gRPC 健康状态变成不可用。**继续正常处理请求。**
2. 等 `DRAIN_DELAY`。
3. 再按现在的顺序停止各组件。

为什么要等：K8s 里“给进程发 SIGTERM”和“把这个实例从服务的端点里摘掉”是同时发生的两件事，后者要经过端点控制器、各节点上的代理才生效，通常要几秒。进程收到信号就立刻关监听，这几秒里发过来的请求会被拒绝。等的这一段就是留给负载均衡的。

本机默认 0：每个服务只有一个实例，没有别处可去，等只是让重启变慢。阶段 2 设成比端点传播时间长一点（5 到 10 秒），并且 `DRAIN_DELAY` 加停止时限（20 秒）要小于 `terminationGracePeriodSeconds`。

**第二次信号立刻退出。** 现在停止过程中再按 Ctrl-C 没有反应，要等满 20 秒。改成第二次信号取消组件的 ctx，立刻放弃。

**没做的**：零失败的滚动发布要有两个以上实例和一个会看就绪状态的负载均衡，留给阶段 2 验证（阶段 2 的计划里已经有“探针与优雅启停配合”）。边车和服务谁先退出的问题也在那时处理。

### 6.12 测试

**按模块的测试**

- `pkg/breaker`：状态转换；半开时并发 100 个请求只有 1 个被放行；调用方取消不计入失败；带 `-race`。用 `testing/synctest` 控制时间。
- `pkg/app`：就绪的时序（启动完成前 503、收到信号后 503 而请求仍被处理、等待结束后才停止）；第二次信号立刻退出。
- `pkg/degrade`：三个取值和熔断器状态的组合；HTTP 接口。
- `pkg/cache`：Redis 不可用时只有前几次调用碰 Redis。
- order：闸门熔断器打开时受理立刻返回、不调用 `Hold`；落库在闸门不可用时一直重试、恢复后落库且只有一个订单；落库健康打开时受理被拒绝、落库成功后恢复；回收任务在恢复后的等待期内不回收；sweeper 把订单置为失败之后落库的重试结束；从库探测的三种结果；冷库启动时不可用、之后恢复；列表在冷库不可用时返回的前一段是精确的。
- inventory：闸门不可用时订单事件一直重试，恢复后占用被归还，恒等式成立。
- payment：Redis 不可用时能启动。

**故障注入**（`make fault` 增加场景，都是带流量的）

| 场景 | 预期 |
|---|---|
| F 暂停闸门的 Redis（`docker pause`）30 秒 | 受理在几次之后毫秒级返回 503；已落库的订单查询照常；暂停前受理的订单在恢复后全部落库，没有被回收的，死信为空；`load verify` 通过 |
| G 停掉闸门的 Redis（`docker stop`）再启动 | 同上（连接被拒绝而不是超时） |
| H 停掉缓存的 Redis | 查询全部成功，延迟在熔断器打开后回到接近基线 |
| I 从库停止回放（`STOP REPLICA SQL_THREAD`） | 2 秒内 `/degrade` 显示从库不健康；之后读到的都是最新数据；恢复回放后自动用回从库 |
| J 暂停一个从库 | 查询全部成功；探测发现之后延迟回到基线 |
| K 冷库地址指向一个不通的端口启动 order | 能启动；近期订单的查询和下单正常；旧订单号的查询立刻 503；用户列表返回近期的一段并带 `archive_unavailable` |
| L inventory 挂住，同时持续下单 | 受理在几次之后返回 503，不再出现“202 之后失败”；恢复后受理自动恢复 |
| M 带流量给 order 发 SIGTERM 再启动 | 在时限内退出，退出码 0；没有孤儿占用；`load verify` 通过 |
| N Redis 停着时启动 payment 和 order | 都能启动；order 的查询正常，下单 503 |

冷库在本机和 inventory、payment 的库是同一个 MySQL 实例，不能单独停，所以场景 K 用不通的地址；运行中挂起的情况由按模块的测试覆盖。

### 6.13 实现顺序

1. 主线（Fable）：`pkg/breaker`、`pkg/degrade`、`pkg/app` 的就绪和摘流、`redisx` 的惰性打开、`pkg/cache` 的熔断器、`lock.FailOpen` 的冷却；proto 和 OpenAPI 的新字段；order 里和订单状态有关的部分（闸门熔断器接入受理和落库、落库健康、落库重试不设上限、回收任务的等待）。
2. 并行：order 的读路径（从库探测、冷库的启动和熔断、列表的部分结果、sweeper 跳过不健康的从库；Opus，Fable 评审）；inventory 和 payment（启动、消费者重试、开关；Opus，inventory 的由 Fable 评审）；gateway（开关、新原因码的映射、`Retry-After`、就绪；Opus）；故障注入的场景和 e2e（Sonnet）。

### 6.16 实现中的发现（2026-11-14）

**降级的拒绝不能用 gRPC 的 `UNAVAILABLE`。** 设计时只想了“对客户端返回 503”，没有想服务之间用什么状态码。步骤三的边车把 `UNAVAILABLE` 算作被调用方的一次失败，连续 5 次就把它整个摘掉 5 秒（5.3）。闸门的 Redis 坏了，下单请求全部被 order 拒绝；如果拒绝用的是 `UNAVAILABLE`，秒杀流量下连续 5 个下单请求之后 gateway 的边车就把 order 摘掉，查询、取消、支付跟着全部快速失败。“拒绝下单、其余照常”变成了全挂，而且是保护机制自己造成的。这个问题在这一步之前就存在：`Hold` 超时本来就返回 `UNAVAILABLE`。

做法：区分“这个服务不行了”和“这个服务是好的，它的一个依赖不行了”。后一种用 `errx.Degraded`：gRPC 状态码是 `FAILED_PRECONDITION`（边车归为 4xx，不计入摘除），带一个降级原因码；gateway 按原因码而不是状态码把它映射成 503 加 `Retry-After`。order 的主库连不上、内部错误仍然是 `UNAVAILABLE` 和 `INTERNAL`，这时被摘掉是对的。payment 调 order 失败时原来回 `UNAVAILABLE`，同样改成降级错误（`ORDER_UNAVAILABLE`），否则 order 坏了会连累 payment 被 gateway 摘掉。

边车把 `FAILED_PRECONDITION` 归为 4xx 是按 Envoy 的 gRPC 状态码映射推断的（5.3 实测过的只有 `NOT_FOUND` 不触发摘除），要由故障注入的场景 F 证实：闸门不可用、持续下单的同时，查订单全部成功，gateway 边车上 order 的摘除次数是 0。

**落库健康的探测结果不一定回得来。** 半开时放进去的那个订单，落库的结果由消费者报告；多实例时它所在的分区可能在别的实例上，这个实例永远等不到结果，熔断器会一直停在半开，每个冷却时间只放一个订单。做法：探测的消息发出去之后，一个冷却时间内没有失败报上来就当它成功。失败会把熔断器重新打开，那之后“当它成功”不再起作用（熔断器给每次放行记了一个代号，状态变过之后旧的结果作废）。第一版用定时器实现，改成了在下一次受理时顺带检查：没有新的下单请求时，停在半开也没有影响，不需要一个后台的定时器。

**什么算“落库成功”要收紧。** 第一版设计写的是“处理完成算成功”。但库存服务坏着的时候，被 sweeper 置为失败的订单，它的消息下一次重试会正常结束（看到终态，什么都不做）。把这个算成成功，熔断器会被错误地关上，受理重新放开，新订单接着失败。改成只有这一次处理真的调用了库存服务并得到回答（预占成功或业务上拒绝）才报告成功；什么依赖都没碰就结束的不报告。

**闸门的故障不记到落库健康上。** 落库时认领失败（Redis 不可用）不算落库失败：闸门有自己的熔断器，受理那一侧已经会因为它拒绝。两个都记的话，对外的原因码取决于哪个先检查，而且 Redis 恢复后落库健康还要多等一次探测。

**回收任务的等待有两个来源。** 设计里只写了“闸门恢复后的半个宽限期内不回收”，由闸门的熔断器恢复的时刻触发。但熔断器是被调用喂出来的：一个只跑周期任务、没有受理和落库流量的实例，回收任务每 10 秒才访问一次 Redis，短于 50 秒的故障数不到连续 5 次，熔断器不会打开。所以回收任务另外记着自己上一轮列占用是否失败，失败之后第一次成功的那一轮同样开始等待。两个来源都是本进程的见闻：消费者在别的实例上、而只有那个实例连不上 Redis 时，回收任务所在的实例看不到，不会等。

**Redis 恢复后读己之写的标记有一段空白。** 故障期间的写入没能打上标记（打标记失败不阻止写入，1c 的决定）。Redis 恢复后，这些订单的展示读会被当成“没有标记”而去读从库。做法：闸门的熔断器恢复后的一段时间内（标记的最长保留时间）展示读一律读主库。

**“最大延迟小于 pin 的时长”不够。** order 读路径的子 Agent 指出：探测每秒一次，延迟在两次探测之间还会继续涨，被发现时最坏已经是“最大延迟加一个探测间隔”。启动时的校验改成 `ORDER_READ_MAX_LAG + 探测间隔 < ORDER_READ_PIN_TTL`（默认 1 秒 + 1 秒 < 3 秒）。

**不设重试上限之后，“数据本身不对”的错误必须标出来。** inventory 和 payment 的子 Agent 逐个检查了两个消费者返回的普通错误，找出几种重试永远不会成功的。以前它们最多挡住分区 5 分钟（inventory）或 1.5 秒（payment）后进死信，现在会永久挡住。inventory 的两种（预占的状态值不认识、已预占却没有明细）已经改成直接进死信。没改的见 6.17。

**从库健康和设计的几处差异**（子 Agent 的选择，评审后保留）：

- 闸门恢复后不信任标记的时长按读模式取：`window` 模式只用 pin，等 pin 的时长（3 秒）；`gtid` 模式等标记的保留时间（1 分钟）。也就是 `gtid` 模式下闸门每恢复一次，有 1 分钟展示读全部落到主库，受每库 16 个的并发上限约束。
- `gtid` 模式下等从库追上的那次调用出错，也立刻把从库标成不健康（设计只写了读从库出错）。MySQL 明确答复的错误（比如标记里的位置格式不对）除外，那不是从库的问题。
- 初始状态是不健康：刚启动的实例在连续两次探测通过之前（约 1 到 2 秒）展示读全部读主库。
- 支付结果路径查冷库不看 `archive_read` 开关：开关管的是展示读，人工关掉它不应该挡住支付结果的分区。这条路径经过冷库的熔断器，并且每次查询有了 1 秒的时限（原来会在热库的事务里一直等到事件的 10 秒时限）。

**列表降级时总是带游标。** 冷库不可用时返回的那一段后面还有没有订单，没有冷库就不知道，所以不能说“没有更多了”。客户端接着取：冷库恢复了是正常的一页（可能为空），没恢复是 503 `ARCHIVE_UNAVAILABLE`。

**gateway 的开关在单独的管理端口上**（`ADMIN_ADDR`，默认 `127.0.0.1:8089`）。其他服务的内部端口本来就不对外；gateway 的 HTTP 端口是对外的，没有鉴权的开关接口不能挂在上面。就绪探测 `/readyz` 两个端口都有：负载均衡要打对外的那个。开关的判断排在所有限流之前，被关掉的请求不消耗用户的配额。

### 6.17 没有做的

- **闸门的 Lua 脚本运行时出错和“Redis 连不上”分不开。** inventory 把闸门的错误一概当作可重试。Redis 里的数据损坏（占用的结构不对）时脚本会报错，这条消息会一直重试、挡住分区。要区分得改 `pkg/stockgate`。
- **payment 读支付单时的扫描错误**（列里有不该有的 NULL）同样会一直重试。
- 上面两种都只在数据损坏时出现，现在只能靠日志里持续重试的 WARN 发现，阶段 3 有了消费积压的告警之后才有保障。
- **inventory 进程里的闸门调用没有熔断器。** Redis 坏着时每次预热都要等一次超时。现在靠 order 那边的熔断器打开后不再发预热来兜底。
- **`Retry-After` 固定 5 秒。** 人工关掉的开关可能关几个小时，所有客户端每 5 秒来一次；下游熔断器的冷却时间改了，gateway 也不知道。
- **标记和闸门共用一个熔断器。** 它们现在在同一个 Redis 上；以后把标记挪到别的实例，要拆开。
- **缓存没开时不登记 `cache` 开关**，这时 `DEGRADE=cache=off` 会让服务拒绝启动。给所有服务统一下发同一份 `DEGRADE` 时要注意。
- 探测间隔没有做成环境变量（固定 1 秒）。
- 6.15 里列的各项。

- 6.16 的推断证实了：降级的拒绝用 `FAILED_PRECONDITION`，边车不计入摘除（F、G 里摘除 0，查询全部成功）。

**故障注入发现并修掉的一个问题：缓存的 Redis 挂住时，熔断器打开之前的每个请求多等约 1 到 2 秒。** 缓存的读没有自己的时限，等的是客户端的读超时（1 秒）；熔断器要数到连续 5 次才打开。给进入缓存时的那一次读加了 200 毫秒的时限，复测最大延迟从约 1030 毫秒降到约 210 毫秒。闸门的调用在步骤三就有 300 毫秒的时限，缓存漏了。

**场景没有覆盖到的**

- F、G 里“已受理、未落库”的订单是先让 inventory 挂住造出来的：它们在 Redis 暂停之前已经被认领、写了订单行，Redis 暂停期间卡在预占上。“Redis 暂停时还没被认领的订单，恢复后被认领并落库”这条路径只有按模块的测试覆盖（`TestLandingWaitsForGate`）。回收任务在恢复后的等待同样只有按模块的测试。
- 从库的探测量的是 GTID 位置。主库没有新写入时，停了回放的从库不会被判为不健康（也没有东西会读旧）。场景 I 要在停止回放后写一笔才触发。
- 冷库在运行中挂起（不是启动时就不通）只有按模块的测试。
- `DRAIN_DELAY` 在单实例下验证不了，只有 `pkg/app` 的测试。场景 M 验证的是停止的顺序和在途订单不丢。

## 7. 步骤五：对账

状态：主人已确认（2026-11-14），7.14 的四项都按建议。决定和备选方案见 ADR-0022。

对应阶段计划里的“对账：基于 Merkle Tree 定位差异”。验收是“对账任务能发现并定位人为制造的数据差异”。

### 7.1 现在是什么样

系统里已经有三处在做“两份数据对不对得上”：

| 在哪 | 比的是什么 | 做法 | 局限 |
|---|---|---|---|
| inventory 的 `reconcile` | 闸门（Redis）和 MySQL 的库存数，按 SKU | 每 5 秒逐个 SKU 比，连续 3 轮偏差相同才修 | 无。SKU 只有几个到几千个，逐个比就是对的做法 |
| `load verify` 的 22 项 | 订单、支付单、预占、闸门、商家索引、冷库 | 把相关的表整个读进内存再比 | 第 4 到 15、20 项排除了造数的订单（`notSeeded`），因为 500 万行读不进来；它是压测之后用的，前提是系统静止 |
| 归档任务 | 每批订单在热库和冷库的摘要 | 写冷库后读回比对，再删热库 | 只管它正在搬的这一批，搬完之后冷库坏了没有人发现 |

缺的是一个能在**数据量大、系统在运行**的时候跑的对账：500 万订单对商家索引、主库对从库、订单对支付单，现在都没有办法比。

### 7.2 这件事难在哪

两份各 500 万行的数据，绝大多数是一样的，要找出不一样的那几行。直接的办法是两边都按主键顺序读出来，归并着比。它的代价和差异多少无关：每次都要把两边的每一行传到对账工具里。本机实测（冷库 `orders_archive`，482 万行，6 列）：读出来是 276 MB，7.3 秒。

Merkle 树的想法是先比摘要、只在摘要不同的地方往下看。但摘要本身要扫全表才能算出来，所以它省的不是扫描，是**传输和比较**；省不省得下来取决于摘要在哪里算：

- 对账工具把行读过来再算摘要：扫描、传输一样没少，比归并多做了一次哈希。**没有任何好处。**
- 数据库自己算，只把摘要传出来：扫描还在，传输从 276 MB 变成几千行摘要。本机实测同一张表按 18.6 小时一个桶聚合，出 3115 个桶，8.5 秒（同一张表只做 `COUNT(*)` 是 3.1 秒，差的 5 秒是每行一次 SHA-256）。

所以在本机上（工具和数据库在同一台机器，传输几乎不要钱）两种办法时间差不多，Merkle 的好处要到工具和数据库之间隔着网络、或者一份数据有多个副本要两两比的时候才显出来。这一点 7.12 要量出来写清楚，不预设结论。

### 7.3 树的形状：按订单号的二进制位分层

所有要比的数据都能用订单号做键（订单、明细、支付单、预占、索引行，每一行都属于一个订单）。订单号是 `41 位毫秒时间 | 6 位机器 | 10 位序号 | 6 位基因`，时间在最高位。

**树是订单号上的一棵基数树**：一个节点是订单号的一个前缀，也就是订单号上一段连续的区间；`shift` 位以下的位被抹掉，每往下一层多看 4 位（16 叉）。

| shift | 一个节点覆盖的时间 |
|---|---|
| 48 | 18.6 小时 |
| 44 | 70 分钟 |
| 40 | 4.4 分钟 |
| 36 | 16 秒 |
| 32 | 1 秒 |

选它而不是“按订单号的哈希分桶”，有三个原因：

1. **每个节点是主键上的一段区间。** 数据库用一次主键范围扫描就能算出任何一个节点的摘要、读出任何一个节点里的行。按哈希分桶的话，取一个桶的行要扫全表。
2. **旧数据的节点不再变。** 新订单只落在最右边的几个节点里。水位线（7.6）就是“右边的若干节点不比”，存下来的旧节点摘要可以一直用。
3. 冷库按订单号分区，范围条件能裁掉分区。

代价是节点大小不均：造的 500 万单摊在近 7 年里，一分钟不到 2 单；压测时一秒 800 单，差四个数量级。固定大小的叶子要么在旧数据上碎成几百万个只有一两行的桶（传摘要不比传行省），要么在新数据上一个桶几百万行。所以**树不定深度**：一个摘要不同的节点，行数不超过阈值（默认 2000）就逐行比，超过就再分 16 份接着比。稀的地方停得早，密的地方走得深。

### 7.4 摘要：行哈希的和

**行哈希。** 两边的行先各自投影成同样的一组列（7.7），拼成一个规范的字符串，取 SHA-256 的前 128 位：

```
SHA2(CONCAT_WS('|', order_id, user_id, COALESCE(merchant_id, '~'), status, total_amount, version), 256)
```

投影里只放整数和状态码，不放时间和浮点（两边精度、时区一不一样就白比了）；`NULL` 写成一个不会和数字混淆的标记，因为 `CONCAT_WS` 会跳过 `NULL`，`(1, NULL, 2)` 和 `(1, 2, NULL)` 会拼成同一个串。

**节点的摘要是它下面所有行哈希的和**（两个 64 位的和，各自对 2^64 取模），外加行数。SQL 里是：

```sql
SELECT order_id >> ? AS node, COUNT(*),
       SUM(CAST(CONV(SUBSTRING(h, 1, 16), 16, 10) AS UNSIGNED)),
       SUM(CAST(CONV(SUBSTRING(h, 17, 16), 16, 10) AS UNSIGNED))
FROM (SELECT order_id, SHA2(...) AS h FROM orders_3 WHERE order_id >= ? AND order_id < ?) x
GROUP BY node
```

MySQL 对无符号 64 位整数求和返回精确的 DECIMAL，取模在工具里做。已在本机的 MySQL 9.7 上跑通（顺带发现 9.7 已经没有 `MD5()` 函数）。

用“和”而不是教科书上的“父节点 = H(子节点的哈希拼起来)”，是这个设计里最要紧的一点：

1. **和与顺序无关。** 数据库按什么顺序扫、分几次扫，结果一样。
2. **和可以跨分片相加。** 两边的分片方式不同：订单按用户分在 4 个库 8 个 slot 里，商家索引按商家分在 2 个库 4 个 slot 里，冷库不分片，支付单只有一个库。同一个节点（同一段订单号）的摘要，一边是 8 张表各算一次加起来，另一边是 4 张表加起来；“热库加冷库”也只是再加一项。用 H(子节点) 做不到这一点，它要求两边的行先凑到一起排好序。
3. **任何一层的节点都能直接算**，不需要先有它的子节点。所以可以从上往下、只在不同的地方才向数据库要下一层。
4. **可以增量维护**：加一行就加上它的哈希，删一行就减掉。（这一步没有用到，见 7.13。）

和 XOR 比：XOR 下同一行出现两次会互相抵消，和不会（行数也能发现，但两道保险好过一道）。

放弃的是教科书 Merkle 树的防篡改性质：行哈希的和不抗有意构造的碰撞，也给不出“某一行确实在树里”的证明。对账面对的是程序缺陷和运维失误，不是攻击者；128 位下偶然碰撞的概率可以忽略。这一点和区块链、证书透明度用 Merkle 树的目的不同，ADR-0022 里展开。

### 7.5 比对的过程

```
比较(区间, shift):
    两边各自取出这个区间里、按 shift 分组的节点摘要（每张分片表一条聚合语句，结果按节点相加）
    对每个两边摘要不同的节点（含一边有、一边没有）:
        两边行数都不超过阈值 → 记入“待逐行比”
        否则               → 比较(这个节点的区间, shift - 4)
逐行比: 两边各读出这些区间里的行（投影后的列），按键归并，得到 只在左、只在右、两边不同 三类
复查:   等一小段时间，把这些键在两边各重读一次，仍然不同的才报告（7.6）
```

**第一遍在哪一层开始。** 从根（一个节点）开始的话，每下一层都要把不同的区间重扫一遍；差异分散时，上面几层每层都近似一次全表扫描。所以第一遍直接在 shift 48 上聚合：一次全表扫描，7 年的数据约 3000 个节点，之后只对不同的节点往下走。这相当于树的上面几层在内存里（`pkg/merkle` 的 `Tree`），下面的层按需向数据库要。

**没有订单号索引的一侧。** 商家索引的主键是 `(merchant_id, order_id)`，按订单号的范围取数是全表扫描。这一侧第一遍照常（本来就是全表扫描，本机一张 205 万行的索引表 3 秒）；往下走时不能一个节点一条语句，要把同一层所有不同的节点合成一条语句（`WHERE order_id >> ? IN (...)`），一层一次全表扫描。数据源自己声明“按订单号的范围扫描有没有索引”，比对过程据此选择做法。

**只读从库。** 订单库的扫描默认连从库（本机每个订单库都有一个），冷库、索引库、支付库、库存库没有从库，直接读。第一遍按订单号分段执行（每段一条语句），不在一个库上开一个几十秒的长查询。

### 7.6 数据在变怎么办

两边不是同一时刻读的，在途的变化会被看成差异。三层处理：

1. **水位线。** 只比订单号里的时间早于 `now - settle` 的订单，默认 30 分钟（支付时限 15 分钟的两倍）。过了这个时间的订单绝大多数已经是终态，不再变。水位线是订单号上的一个上界，纯计算，两边用同一个数。
2. **复查。** 水位线以内仍然有会变的行（刚关单、索引还没追上、归档正在搬）。逐行比出来的差异不直接报告：等一段时间（默认 5 秒）把这些键在两边重读，**两次结果相同的才算差异**。这和库存对账“连续几轮偏差相同才修”是同一个道理。
3. **主从对比时先等从库追上**（读主库的 GTID 位置，在从库上等到它，再开始扫）。**没有做**：水位线以内的行很少再变，从库落后的那几行由复查过滤，实测没有出现需要它的情况。记在 7.16。

没有用一致性快照：`START TRANSACTION WITH CONSISTENT SNAPSHOT` 只管一个库，对不上两个库的同一时刻。pt-table-checksum 的办法（让校验语句本身经复制在从库上重放，天然在同一个位置上执行）要求语句格式的 binlog，CDC 需要行格式，用不了。

### 7.7 比哪几对，各自怎么投影

每一对是“左边一组数据源、右边一组数据源、一个投影”。键都以订单号开头。

| 名字 | 左 | 右 | 键 | 比的列 | 说明 |
|---|---|---|---|---|---|
| `replica` | 订单主库的 `orders_N`、`order_items_N`、`payment_results_N` | 对应的从库 | 各表主键 | 除时间外的全部列 | 每个库各比各的，三张表各一棵树 |
| `index` | 热库 `orders_N` 加冷库 `orders_archive`，`merchant_id` 非空的 | `merchant_orders_N` | 订单号 | `merchant_id`、`user_id`、`status`、`total_amount`、版本号 | 取代 `load verify` 第 20 项在大数据量下的位置；500 万行全量 |
| `payment` | 状态是 `PAID` 的订单 | 状态是 `SUCCEEDED` 的支付单 | 订单号 | `payment_id`、金额、币种 | 对应第 7、8 项：付清的订单恰好有一笔金额相同的成功支付，反过来也是 |
| `stock` | 状态是 `PENDING_PAYMENT`、`PAID` 的订单的明细 | 状态是 `RESERVED`、`CONFIRMED` 的预占的明细 | 订单号加 SKU | 数量、单价、占用状态（占着或已售） | 对应第 4 到 6 项。两边都把“已释放”投影成“没有这一行”，这样没预占过就失败的订单不会被报成差异 |
| `archive` | 热库加冷库的三张表 | 之前存下来的一棵树（文件） | 各表主键 | 除时间、`archived_at` 外的全部列 | 归档是搬家，“热加冷”这个集合在归档前后应当不变。归档前存一棵树，归档后再比 |

说明：

- `payment` 和 `stock` 的右边没有造数的订单（造数工具只写订单库和索引），所以这两对排除用户号在 2^40 以上的订单，和 `load verify` 一样。`replica`、`index`、`archive` 是全量。
- `archive` 的右边是文件，只有节点摘要、没有行，所以只能定位到节点（一段时间里的若干订单），不能定位到行。要定位到行得有另一份数据：有商家的订单可以再跑 `index`。这是它和其他几对的区别，照实写进输出。
- 投影把“两边结构不同”变成“两边是同一个集合”。写投影就是把不变式写出来，例如 `payment` 的投影说的是“`PAID` 的订单和 `SUCCEEDED` 的支付单一一对应，支付单号和金额相同”。不变式写错，对账就会漏报或误报，这部分由 Fable 写。

**不用这个工具比的：闸门（Redis）和 MySQL 的库存。** 阶段计划把它列在对账对象里，这里不做，理由：键是 SKU，只有几个到几千个，逐个比的代价本来就小；数一直在变，没有“已经定下来”的那一段，水位线用不上；它现在的做法（逐个比、连续几轮相同才修）是对的。给它套一棵树只是为了用而用。

### 7.8 输出和修复

输出是一份报告（文本和 JSON）：每一对的行数、根摘要、扫描和传输的量、每一层比了多少节点、三类差异各多少条和具体的键及两边的值（有上限）。有差异时退出码非零。

修复分情况，**默认只报告**：

| 对 | 以谁为准 | 修复 |
|---|---|---|
| `index` | 订单库（索引是派生数据） | `-repair`：缺的行和不同的行按订单库的映像重写，多出来的行删除。只对复查后仍然不同的键做，逐行、带“订单库此刻的版本号不低于索引里的”这个条件 |
| `replica` | 主库 | 不自动修。从库被改坏说明有人绕过了 `super_read_only`，或者复制出了问题；正确的处理是查原因、重建从库 |
| `payment`、`stock` | 没有哪一边天然是对的 | 不自动修。涉及钱和库存，报告给人 |
| `archive` | 无 | 不自动修。从备份或 binlog 找回 |

### 7.9 放在哪

- **`pkg/merkle`**（纯计算，不碰数据库）：`Digest`（行数加 128 位的和，加、减、相等）、`RowHash`（规范编码加 SHA-256，和 SQL 的表达式逐位一致，有测试对着真实的 MySQL 核对）、`Tree`（稀疏的基数树：按节点存摘要，合并另一棵树，加减一行，求根）、`Diff`（自上而下，只进入摘要不同的节点，统计比了多少节点）、序列化。
- **`services/recon`**（新模块，一个批处理命令 `cmd/recon`）：数据源（生成聚合语句和范围读取语句、跨分片相加、分段、限速）、五对的投影、比对和复查、报告、索引的修复。它要连所有服务的库，不属于任何一个服务；阶段 2 里它是一个 CronJob。
- `make recon`、`scripts/recon.sh`（按本机的库数拼 DSN，和 `archive.sh` 一样）。

### 7.10 和 `load verify` 的关系

不合并，也不替换。`load verify` 是压测之后、系统静止时的全面检查，带客户端账本，22 项里大多数（账本对服务端、死信、日志、闸门）不是“两份数据比对”。`recon` 是系统运行中、对全量数据的比对，只做五对。重叠的是第 20 项（商家索引）：`load verify` 里保留（它在 chaos 之后只看新订单，快），`recon index` 管全量。

`scripts/chaos.sh` 在 `load verify` 之后加跑一次 `recon`（`payment`、`stock`，不设水位线，因为这时系统是静止的），两套检查互相印证；`recon` 有差异时 chaos 判失败。chaos 的环境没有从库和商家索引，`replica`、`index` 不跑。

### 7.11 测试

- `pkg/merkle`：`Digest` 的加减和交换律；`RowHash` 对 `NULL` 位置的区分；`Tree` 的合并等于逐行加入；`Diff` 找出的节点恰好是被改动的行所在的节点、相同的两棵树只比一个节点；序列化往返；一棵随机树随机改 k 行的性质测试。
- `RowHash` 和 SQL 表达式的一致性：往测试库插一批行（含 `NULL`、负数、最大值），库里算的摘要和 Go 算的相同。
- `services/recon`（集成测试，`testdb`）：每一对各造一份一致的数据，确认无差异；再逐个制造差异（删一行、多一行、改金额、改状态、改版本号、同一行在两个 slot 里各有一份），确认报告的键恰好是被改的那些，没有多也没有少。
- 变动中的数据：比对过程中另一个协程持续改水位线以内的行，确认复查把它们滤掉；改完不改回去的那一行仍被报告。
- 没有订单号索引的一侧走合并下钻的路径，结果和有索引的一侧相同。
- 索引的修复：修完再比是干净的；修复期间订单库的行又变了（版本号更高）时不会把索引写回旧值。

### 7.12 实测结果（2026-11-14）

本机，订单库 4 个（各带一个从库），工具和数据库在同一台机器上。原始输出在 `tmp/recon/`。

**`index` 这一对，两侧各 490.8 万行**（左边 8 张热表加冷库，右边 4 张索引表）：

| 差异 | 做法 | 第一遍 | 逐行比 | 读回的行（每侧） | 传回的量 | 合计（不含复查） |
|---|---|---|---|---|---|---|
| 0 | 树 | 4.8 秒 | 无 | 0 | 约 1.7 万个摘要 | 4.8 秒 |
| 0 | 全量归并 | 无 | 7.8 秒 | 490.8 万 | 545 MB | 7.8 秒 |
| 1 行 | 树 | 4.7 秒 | 0.27 秒 | 1495 | 0.17 MB | 5.0 秒 |
| 93 行，散布 | 树 | 4.7 秒 | 1.9 秒 | 14.1 万 | 15.7 MB | 6.6 秒 |
| 9612 行，散布（0.2%） | 树 | 4.8 秒 | 5.9 秒 | 464 万 | 516 MB | 10.7 秒 |

全量归并的代价与差异数无关，一直是 7.8 秒、545 MB。复查另加等待的 5 秒和重读（9612 个订单约 2.4 秒，索引表每 1000 个订单号一次全表扫描）。

读法：

1. **没有差异时树是归并的六成时间，传输是它的三千分之一。** 时间上差得不多，因为两边都要扫全表，而且树那边每行多算一次 SHA-256；本机没有网络，传输省下来的不显眼。
2. **交叉点取决于差异落在多少个节点里，不是差异有多少行。** 第一遍在 18.6 小时一个节点的层上，一共 3231 个非空节点，每个约 1500 行，不超过阈值（2000），所以摘要不同的节点整个读回来。9612 行散布的差异打中了其中 3053 个，等于把 95% 的行又读了一遍，比归并慢。按这个数推，均匀散布的差异超过约 2000 行（万分之四）树就不如归并。
3. **真实的故障很少均匀散布。** 消费者漏了一段时间、一次发布写坏了一批，差异集中在几个节点里；那时的代价接近“1 行”那一行。均匀散布的大量差异意味着整份数据要重建，那时不该用对账去找。
4. 把阈值调小能让树在散布的差异下少读一些行，但商家索引没有订单号的索引，每往下一层是 4 张表各一次全表扫描（约 3 秒），不划算。两侧都有索引时可以调小。

**其他几对**（两侧相同时只有第一遍）：`replica` 三张表（18.7 万订单、36.7 万明细）共 0.26 秒；`payment`、`stock` 各 4096 行，约 15 毫秒；`archive` 的三棵树（500.8 万订单、1000.9 万明细）存快照 11 秒，文件 276 KB。

**行哈希的代价**（冷库 482 万行，单条语句）：只 `COUNT(*)` 3.1 秒，`CRC32` 聚合 5.0 秒，SHA-256 聚合 8.5 秒。

**修复**：1 行 0.35 秒，93 行 1.2 秒，9612 行 41 秒（每个订单约 4 毫秒，主要是在 8 张热表和冷库里逐个按主键重读订单行）。三轮修完再比都是干净的。

**验收的演练**（在本机开发库上各制造一处差异，查完改回）：

| 对 | 制造的差异 | 工具报告的 |
|---|---|---|
| `index` | 索引里 1 行、93 行、9612 行的金额加 1 | 每一行都报成 `mismatch`，数量恰好；`-repair` 修好 |
| `payment` | 一笔支付单的金额加 1 | 那个订单 `mismatch`，两边的金额 12900 对 12901。4096 行都在同一个 18.6 小时的节点里，往下走到 16 秒的节点（约 390 行）才逐行比 |
| `stock` | 一个已确认的预占改成已释放 | 那个订单的明细 `only_left`（订单付清了，预占没了） |
| `archive` | 存快照，归档 20717 个订单（80 天以前的），再比 | 三棵树的根都没变 |
| `archive` | 再把冷库里一个订单的金额加 1 | `archive/orders` 报出 1 个节点（2025-04-14 22:23 到 04-15 17:02，1566 行），另外两棵树不变 |
| `replica` | 没有在开发库上做（要关掉从库的 `super_read_only`） | 集成测试覆盖：缺行、多行、改金额、改状态、改版本号 |

`make lint test e2e` 通过（e2e 18 个）。`make chaos` 一次 PASS（19 次击杀，`load verify` 和 `recon` 都通过）。

### 7.13 不在这一步做的

- 增量维护的树（写入时或经 CDC 更新节点摘要，对账时不扫全表）。这是把每次对账的扫描也省掉的办法，也是 Cassandra 之外很多系统的做法；它要一张持久的摘要表和一条保证不丢更新的路径，本身又是一份要对账的派生数据。记在 ADR 里。
- 定时调度：阶段 2（CronJob）。指标和告警：步骤六、阶段 3。
- `payment`、`stock` 的自动修复。
- 闸门和 MySQL 的库存（7.7 末尾）。
- 归档任务里自动存树、自动比：先做成手工的两步，脚本里给出用法。

### 7.14 主人定的（2026-11-14，四项都按建议）

1. **摘要在哪里算**：数据库里聚合、只传摘要（7.2、7.4，建议）；还是工具把行读过来自己算（实现简单、不依赖 SQL 表达式和 Go 的编码逐位一致，但那样 Merkle 相对归并没有任何优势，只剩演示树的结构）。
2. **节点摘要用行哈希的和，每一层都是**（7.4，建议）；还是教科书式的父节点 = H(子节点)。后者做不到跨分片相加和按需计算，只能配合“工具读行自己算”。
3. **闸门和 MySQL 的库存不纳入**，维持现有的 `reconcile`（7.7 末尾，建议）；还是按阶段计划的原文也接进来。
4. **修复的范围**：只有商家索引可以 `-repair`，其余只报告（7.8，建议）；还是全部只报告。

### 7.15 实现中的发现（2026-11-14）

- **MySQL 9.7 没有 `MD5()`。** 设计前的探测发现的，行哈希用 `SHA2`。
- **按订单号删索引行是带锁的全表扫描。** 修复的第一版对每个订单在 4 张索引表上各发一条 `DELETE ... WHERE order_id = ?`。索引表的主键是 `(merchant_id, order_id)`，这条语句扫全表，`REPEATABLE READ` 下给扫过的每一行加锁，CDC 的消费者在这期间写不进这张表。改成两步：先用不加锁的读找出这些订单号现有的索引行（一批 1000 个订单号一次全表扫描），再按主键逐行删。
- **全量归并的第一版不公平。** 它按 18.6 小时一个节点、一张表一条语句地读，4096 行的 `payment` 发了 2.9 万条语句。改成和第一遍一样按 198 天分段。拿来做对比的基线要先确认它自己没有被写慢。
- **两侧是同样的多份时不报重复。** 主库上的重复行被原样复制到从库，两侧摘要相同，树看不到；全量模式为了和树的结果一致也不报。所以 `replica` 发现不了主库自己的重复，要靠 `index`、`payment` 这类对面不会重复的对。
- **和文件比没有复查。** `archive` 的右边是存下来的树，没有行可以重读，在途的变化没有地方过滤。所以它的热库读主库（别的对读从库），并且存快照和比对都要在归档任务不在跑的时候做：热库和冷库不是同一时刻扫的，两次扫描之间被搬走的订单会被数两次或一次都没数到。
- **取订单号的范围用 `ORDER BY ... LIMIT 1`，不用 `MIN`/`MAX`，也不带过滤条件。** `stock` 的数据源是连接，`MIN`/`MAX` 会把整个连接算一遍。代价是分段的范围比实际数据宽，多发几条读不到行的语句。
- **修复时先读热库再读冷库。** 归档是先写冷库再删热库，这个顺序下正在被搬的订单至少在一边读得到，不会被当成“订单库里没有”而删掉索引行。
- 修复的写入条件是“新版本号不低于索引里的”，所以索引里的版本号比订单库还高时修不动，留在报告的“未修好”里，要人看。

### 7.16 没有做的

- 主从对比前等从库追上 GTID 位置（7.6 第 3 条）。
- 商家索引表没有以订单号开头的索引：往下每一层、复查每 1000 个订单号、修复每 1000 个订单号，都是 4 张表各一次全表扫描。给 `merchant_orders_N` 加 `KEY (order_id)` 可以全部变成按索引取，代价是索引写入变慢（现在按批写 4.8 万行/秒），没有量过，没有加。
- `archive` 只能定位到节点；归档任务没有自动存树、自动比，现在是手工的三步（`recon -pairs archive -snapshot-out F`，归档，`recon -pairs archive -against F`）。
- 复查只看第一次报出来的行，复查时才出现的不一致要等下一次运行。
- 修复在版本相同时也会刷新 `synced_at`，报告里的写入次数会包含内容没变的行。
- `replica` 没有在开发库上演练；`-mode full` 不支持 `archive`。
- 7.13 列的那些（增量维护的树、定时调度、指标）。增量对账后来用窗口的下界做了，见 7.17；它不需要维护任何状态。

### 7.17 增量对账：窗口的下界（2026-11-14 补）

前面的实现只有上界（水位线），每次都从最早的订单比到水位线。主人提出对账通常只比新数据和变化的数据、按业务需要每小时或每天跑，全量不必每次做。这个设想是对的，补了下界。

**做法。** `-since 26h` 表示只比订单号里的时间在最近 26 小时以内的订单，和 `-settle` 合起来是一个窗口 `[now - since, now - settle)`。下界和上界一样是订单号上的一个数，两侧每条语句都带。能这样做是因为树按订单号的区间分层（7.3）：一个时间窗口就是主键上的一段，有订单号索引的表只扫这一段。按哈希分桶的树做不到，每个桶里新旧数据都有。

**窗口由时间决定，不由树决定。** 树解决的是“在给定范围里怎么少传数据就找到不同的行”，范围取多大是另一个旋钮。两者配合得上是分桶键选得巧，不是 Merkle 树自带的性质。

**为什么“新数据”就够了。** 订单受理后一个支付时限内到终态，之后不再变；所以按订单号的窗口基本覆盖了“发生变化的数据”。同步出的错（消息丢了、消费者有缺陷）发生在写入的时候，一个时间段比过一次相等，以后不用再比。

**它发现不了什么。** 窗口之前的数据后来被改坏（手工改库、归档搬坏、存储损坏）没有任何信号，只有全量扫描能发现。所以全量不能取消，只能降低频率。建议的搭配：

| 频率 | 参数 | 管什么 |
|---|---|---|
| 每小时 | `-since 3h` | 同步出错，尽早发现 |
| 每天 | `-since 50h` | 同上，窗口重叠一天，覆盖晚到的变化 |
| 每周或每月 | 不带 `-since` | 旧数据的事后损坏 |

窗口要互相重叠（`since` 取运行间隔的两倍以上）。工具不记“上次比到哪”：重叠的窗口不依赖上一次运行成功，漏跑一次也不会留下没比过的时间段；代价是每段数据被比两三次。

**实测**（本机，同 7.12 的数据）：

| 范围 | `index` 的行数 | `index` 耗时 | `replica` 三张表合计 |
|---|---|---|---|
| 全量 | 490.8 万 | 4.7 秒 | 0.24 秒 |
| `-since 720h`（30 天） | 6.6 万 | 0.29 秒 | 0.10 秒 |
| `-since 26h` | 9221 | 0.27 秒 | 0.03 秒 |

`index` 在窗口很小时仍要 0.27 秒：商家索引没有订单号的索引，窗口条件只能在全表扫描里过滤，省掉的是每行的 SHA-256，不是扫描。这是 7.16 里“加 `KEY (order_id)`”那一条的又一个理由；表再大一两个数量级时应当加。

**限制。** `archive` 不支持下界（存下来的树覆盖到它的上界为止的全部数据）。分段取范围的语句也带上了窗口，有下界时不会为窗口之前的几年各发一条读不到行的语句。

**关于把哈希存下来。** 讨论过三种，都没有做：

- 应用在终态时算行哈希写进一列：省每行的 SHA-256，但哈希成了行的一份拷贝，有人直接改了金额而哈希没跟着变时，两边存的哈希仍然相等，对账恰好漏掉这种差异。不要这样做。
- 用生成列（`STORED`）存行哈希：哈希永远跟着行走，没有上面的问题；但一列只对应一个投影，五对的投影各不相同。数据到几十亿行、SHA-256 的代价显眼时可以给 `replica` 这类同构的对用。
- 存节点摘要（比过的旧时间段不再重扫）：和下界是同一个取舍，下界不需要存任何东西。


## 8. 步骤六：埋点

状态：主人已确认（2026-11-14），8.14 的四项都按建议。决定和理由见 ADR-0023。

对应阶段计划里的“埋点（OpenTelemetry SDK，见 ADR-0004）：链路贯穿 HTTP、gRPC、Kafka、MySQL、Redis；指标含 QPS、延迟、错误率和业务指标；日志带 trace id”。

### 8.1 现在是什么样

- 仓库里没有任何 OpenTelemetry 代码。日志是 `slog` 的 JSON，只带 `service`，不带 trace id；非测试代码里 95 处日志带了 ctx（`InfoContext` 这一类），84 处没带。
- 到现在为止所有的“量”都是临时的：压测工具自己的统计、`performance_schema`、脚本里数日志。前五步里明确挂到这一步的有：
  - 3.9 的悬案：放宽刷盘后落库停在约 1050 单/秒，每个订单在途约 60 毫秒，其中约 54 毫秒不在 MySQL 里，分不出是本机网络还是 order 进程内的等待。
  - 读走了主库、从库、冷库还是缓存的比例（1c 步骤二挪出来的定量对比）。
  - 降级开关和熔断器的状态（现在只有日志和 `GET /degrade`）。
  - 消费者什么时候分到分区、排查恢复耗时只能靠推断（1c 步骤一评审的遗留）。
- 好的一面：所有客户端的构造都集中在 `pkg/`（`grpcx.Listen`、`grpcx.Dial`、`kafkax` 的生产者和消费者、`mysqlx.Open`、`redisx.Open`），例外只有 gateway 的限流自己建了一个 Redis 客户端、cdc 自己开了一个 `sql.DB`。接入点很少。

### 8.2 边界：这一步只做“产生”，不做“用”

这一步让每个进程产生链路、指标和带 trace id 的日志，并且在本机能看到。Collector 的部署、SkyWalking、大盘、告警、SLO、尾部采样都在阶段 3。

划在这里的理由：埋点是代码的一部分，后端是部署的一部分。但完全不接后端有两个问题：一是 3.9 的悬案要真的看到一条链路才能回答；二是按这个项目的教训，没有跑过的东西不算数，埋点写完却从来没有被任何后端收过，到阶段 3 才发现属性名不对、链路断在哪一跳，返工更贵。所以本机接一个最轻的后端（8.9），只用来看。

### 8.3 装配：`pkg/otelx`

一个新包，做三件事：

1. `Setup(ctx, service) (shutdown func(context.Context) error, err error)`：建 `TracerProvider` 和 `MeterProvider`，设成全局的，设全局的传播器（W3C `traceparent` 加 `baggage`）。资源属性是 `service.name`、`service.instance.id`（主机名加进程号）、`service.version`（构建信息里的提交号）。
2. 导出只用 OTLP（gRPC），地址和采样全部用 OTel 规范里的标准环境变量（`OTEL_EXPORTER_OTLP_ENDPOINT`、`OTEL_TRACES_SAMPLER`、`OTEL_TRACES_SAMPLER_ARG`），不自己发明变量名。到了阶段 2、3，改部署清单里的环境变量就能指向 Collector。
3. `shutdown` 在所有组件停止之后调用，把缓冲里的 span 和最后一次指标发出去，时限 5 秒。

**没配地址时的行为**：仍然建 `TracerProvider`，只是不挂导出器。span 照常产生、照常有 trace id，日志里就有 trace id 可以串起来；不往任何地方发。`make test`、e2e、chaos 默认都是这个状态。指标没有读取器时各个仪表是空操作。

**后端不在时不能影响服务**（要有测试）：OTLP 导出器建连接是惰性的，不挡启动；批处理的队列满了就丢 span，不阻塞业务 goroutine；`shutdown` 有时限。可观测性是可选依赖，和 6.10 的规则一致。

**为什么用全局的 provider**：`otelgrpc`、`redisotel`、`otelsql` 默认都读全局的，`pkg/` 里各个构造函数不用多一个参数。代价是测试里换 provider 是进程级的状态，所以埋点的测试各自放在单独的测试文件里、用 `TestMain` 设一次，不和 `t.Parallel()` 的业务测试混用。

版本（2026-11-14 从 Go 模块代理查的，引入时登记到 `versions.md`）：`go.opentelemetry.io/otel` 和 SDK v1.47.0；contrib 的 `otelgrpc`、`runtime` v0.72.0（起草时还列了 `otelgin`，后来没有用，见 8.4）；`redis/go-redis/extra/redisotel/v9` v9.23.0（和 go-redis 同版本号）；`XSAM/otelsql` v0.44.0。

### 8.4 链路：每一跳怎么接

| 跳 | 做法 | 要注意的 |
|---|---|---|
| HTTP 入口（gateway） | gateway 自己的中间件（`traceEntry`），span 名用路由模板（`POST /api/v1/orders`，不是带订单号的路径），没匹配到路由的叫 `GET unmatched`。`/healthz`、`/readyz` 不经过这个 gin 引擎 | gateway 是对外的入口：外面带进来的 `traceparent` 不当成父 span，只记成 link（否则任何人都能把自己的 span 接到我们的链路上、或者用采样位强制我们全量采样）。响应里加 `X-Trace-Id`，压测工具和排查时用它找链路 |
| gRPC | `otelgrpc` 的 stats handler，加在 `grpcx.Listen` 和 `grpcx.Dial` 里（v0.72 已经没有拦截器的接法，只有 `NewServerHandler`、`NewClientHandler`）。过滤健康检查 | 中间隔着两个 Envoy 边车。边车没有配链路追踪时把 `traceparent`、`tracestate`、`baggage` 原样转发（2026-11-14 实测：自己起一个 gRPC 服务端打印收到的元数据，经 gateway 和 inventory 两个边车调用，三个头都在，只多出 `x-request-id` 和 `x-forwarded-proto`）。边车自己出 span 是阶段 3 的事 |
| Kafka 生产 | `kafkax.Producer.Send` 里把 ctx 的链路上下文写进消息的 header，每条消息一个 PRODUCER span | 自己写，不用 franz-go 的 `kotel` 插件，理由见下 |
| Kafka 消费 | `kafkax` 的消费者在调用 handler 之前从 header 里取出上下文，**每一次尝试**一个 CONSUMER span，属性里带第几次尝试和消息在 Kafka 里排了多久 | 见 8.5 |
| outbox | 表加一列存 `traceparent`，`outbox.Add` 从 ctx 写入，中继发布时放进消息的 header | 见 8.6 |
| MySQL | `mysqlx` 里用 `otelsql.OpenDB(connector)` 代替 `sql.OpenDB`，每条语句一个 span | 语句文本记进 span（全部是 `?` 占位符，不含参数值）。关掉 `Ping`、`rows.Next`、`reset_session` 这些噪音；**没有父 span 的语句不产生 span**（中继、sweeper、应用者这些后台循环每秒都在查，全是孤立的根 span），用 `otelsql` 的 `SpanFilter` 实现。span 名是 `mysql` 加语句的第一个词或操作名（`mysql SELECT`、`mysql commit`） |
| Redis | `redisx` 里对客户端调 `redisotel.InstrumentTracing`。gateway 限流的客户端改成也走这里 | 不记命令文本：key 里有用户号和幂等键，Lua 脚本很长。span 名就是命令名（`evalsha`、`get`）。`redisotel` 的过滤器拿不到 ctx，“没有父 span 就不出 span”做不到在它那一层，改由采样器做：`otelx` 在环境变量选出的采样器外面包一层，没有父 span 的 CLIENT span 一律丢弃（所以采样器的环境变量是 `otelx` 自己解析的，SDK 只在没有显式传采样器时才读） |

**HTTP 入口为什么没有用 `otelgin`**（起草时写的是用它，实现后去掉了）。读它 v0.72.0 的源码，有四处和这里的要求对不上，而且都没有选项可以改：没有“公共入口”的选项，外面带来的 `traceparent` 一律当成父 span；它的指标带 `server.port` 标签，值取自请求的 Host 头，客户端随便写一个端口就多一条时间序列；`client.address` 用 gin 的 `ClientIP()`，默认信任所有代理；所有 5xx 和所有被取消的请求都标成 Error，降级的 503 和客户端断开的 499 也在内。把这四处都绕开之后它只剩“建一个 span”，所以改成自己建，一共几十行。降级响应靠 `writeDegraded` 在 gin 的 context 里设的一个键来认，不靠状态码猜（下游真的不可用时也是 503，那个要标 Error）。

**Kafka 为什么自己写。** `kotel` 是挂在 franz-go 客户端上的钩子，它的 span 对应“消息进了客户端缓冲”和“消息出了缓冲”。而我们关心的处理过程在 `kafkax` 自己的代码里：消息按 key 分到各条 lane、排队、重试、按批、延迟消息等到期。这些 `kotel` 看不到，处理的 span 无论如何都要自己建。传播本身只是把一个 `map[string]string` 交给传播器，`kafkax.Record` 和 `kafkax.Message` 的 header 正好是这个类型，自己写大约几十行，而且能控制 8.5 的那些选择。

**业务代码不手工建 span。** 一次落库里的查占用、预占、写库都已经是客户端 span 了。客户端 span 覆盖不到的只有“等待”，最主要的一处是 `kafkax` 消费者里消息从拉到进程里到 handler 开始之间的排队（按 key 分 lane、等窗口），它记成 CONSUMER span 上的两个属性和两个直方图：`kafkax.queue_ms` 是进程内的排队，`kafkax.delivery_ms` 是从写入 Kafka 算起的总等待，两者的差就是消息在 broker 和网络上的时间。3.9 的 54 毫秒如果在进程里，要么在这里，要么在 span 之间的空隙里。

起草时还列了 `pkg/bulkhead` 的排队和 `pkg/cache` 合并回源的等待，实现时去掉了：舱壁不排队（满了立刻拒绝）；缓存的等待两端都有 Redis 的 span，空隙就是它，另有 `cache.requests` 的 `coalesced` 计数。

**span 上放什么属性。** `order_id`、`user_id` 可以放在 span 上（链路里高基数没有代价，而且按订单号找链路是最常用的入口），由 order、payment、inventory 的入口处各加一行。它们**绝不能**出现在指标的标签里（8.8）。

**什么算错误。** 和 `grpcx.isServerFault` 同一条规则：只有服务端故障才把 span 标成 Error。库存不足、限流的 429、降级的 `errx.Degraded` 是正常结果，不标 Error，原因码记成属性。否则阶段 3 的“错误率”会被业务拒绝淹没。

### 8.5 异步的一跳：父子还是 link

同步调用没有疑问，下游的 span 是上游的子 span。消息队列的一跳有两种接法：

- **父子**：消费者的 span 接在生产者的 span 下面，受理和落库在同一条链路里。看一条链路就能看到一个订单从 HTTP 到落库的全过程，中间在 Kafka 里排了多久是两个 span 之间的空隙。
- **link**：消费者开一条新的链路，只带一个指向生产者 span 的引用。每条链路都短、都很快结束，但要看全过程得在后端里跳转。

规范对这件事没有强制，常见的建议是“一条消息对应一次处理”用父子，“一批消息一次处理”只能用 link（一个 span 只能有一个父）。

建议按“是不是同一个业务动作的延续”来分：

| 消息 | 接法 | 理由 |
|---|---|---|
| 受理到落库（`OrderSubmitted`） | 父子 | 客户端在轮询等结果，这就是一次下单。3.9 的问题正是要在一条链路里看到受理、排队、落库各占多少 |
| 订单事件、支付结果（经 outbox） | 父子 | 同一个订单状态推进的后续 |
| 延迟关单（`OrderCloseDue`） | link | 它在支付时限之后才触发（默认 15 分钟）。给一条早就结束的链路在 15 分钟后再添 span，后端按“链路已结束”做的处理（尾部采样、聚合）都会出错 |
| 按批消费（orderindex） | 批一个 span，link 到各条消息（上限 32 个） | 一个 span 只能有一个父。实际上这些消息来自 CDC，本来就不带上下文 |
| 进死信 | 原样带着 header | 死信里的消息还能找回它的链路 |

**重试时每次尝试一个 span，不是整条消息一个 span。** 步骤四之后消费者对普通错误不设重试上限，依赖坏着时一条消息可以重试几分钟。span 要结束了才会被导出，整条消息一个 span 的话，分区停住的那段时间里什么也看不到，恰好是最需要看的时候。

CDC 的一跳不传递：binlog 里没有地方放上下文（除非给每张表加一列），orderindex 的链路从它自己的消费开始。

### 8.6 outbox：链路要过一张表

order 的订单事件和 payment 的支付结果都是先写进 `outbox` 表、由后台的中继读出来再发到 Kafka。中继是个定时循环，它发消息时的 ctx 和当初写这一行的请求毫无关系。不处理的话，链路在这里断开：下单的链路到“写库”为止，支付、完结各是孤立的链路。

做法是给 `outbox` 加一列 `trace_context VARCHAR(64) NULL`（`traceparent` 固定 55 个字符），`outbox.Add` 从 ctx 里取、和业务变更在同一个事务里写入，中继发布时原样放进消息的 header。消费者看到的父 span 是写 outbox 的那个 span，中继的延迟表现为空隙。中继自己那一轮的扫描和发送不属于任何订单的链路。

代价：

- 一次表结构变更。order 每个库一张、payment 一张，`outbox.Schema` 和两个服务的迁移各加一个文件（order 的 `00004`、payment 的 `00003`）。表很小（发布后定期清理），加一个可空的列是 INSTANT 的。MySQL 没有 `ADD COLUMN IF NOT EXISTS`，迁移里先查 `information_schema` 再决定要不要 `ALTER`（和 order 的 `00002`、`00003` 同一个写法），中途被杀后可以重跑。原来“迁移文件里的建表语句和 `outbox.Schema` 逐字一致”的测试改成比数据库里实际的表结构（`SHOW CREATE TABLE`），两个服务各一个。
- 每行多 55 个字节，未采样的也要写（采样位在里面，下游要靠它知道“不采样”）。可以只在采样时写、`NULL` 表示没有上下文，那样下游会各自重新做采样决定，1% 采样时会多出一批只有后半段的链路。建议都写。

不加这一列的替代办法是靠 span 上的 `order_id` 属性在后端里搜，能找到同一个订单的几条链路，但它们之间没有先后和因果关系，也没法自动算“从下单到完结”的耗时。

### 8.7 采样

头部采样，`ParentBased(TraceIDRatioBased(r))`：gateway 在入口按比例决定，决定写在 `traceparent` 的标志位里，后面每一跳（包括经过 Kafka 和 outbox 的）都跟着这个决定，一条链路要么完整要么没有。

- 本机 `make run` 默认 100%；`bench.sh` 默认 1%，可以用环境变量改；e2e、chaos 没有后端，采样多少都不导出。
- 量级：落库约 1000 单/秒时，一个订单的 span 数先估 30 到 50 个（实测后改），全量就是每秒几万个 span。全量采样只适合看单个请求，不适合压测。
- “只留出错的和慢的”是尾部采样，要等一条链路的 span 到齐才能决定，只能在 Collector 里做，是阶段 3 的事。头部采样的缺点（出错的那条恰好没采到）到那时再解决。

没被采样的请求仍然有 trace id、仍然传播，只是不记录属性、不导出。这部分的开销要量（8.11）。

### 8.8 指标

用 OTel 的指标 API，经 OTLP 推到和链路同一个地址（ADR-0004：服务统一用 OTLP 上报）。本机每 10 秒导出一次。

**自动得到的**：gRPC 服务端和客户端的请求数、耗时、状态码（`otelgrpc`）；HTTP 的（gateway 的中间件自己记 `http.server.request.duration`，标签只有方法、路由模板、状态码）；数据库连接池（`otelsql.RegisterDBStatsMetrics`：在用、空闲、等待次数、等待时长）；Redis 连接池（`redisotel.InstrumentMetrics`）；Go 运行时（goroutine 数、堆、GC）。这些已经覆盖了 QPS、延迟、错误率。

**自己加的**，按“前五步每一层保护都要能看到它有没有在动”来列：

| 在哪 | 指标 | 标签 |
|---|---|---|
| gateway | 限流判定次数；限流退回进程内的次数；降级响应数 | 规则（ip、user、route、hot）、结果；原因码 |
| order 受理 | 受理结果数；闸门里未认领的占用数（背压看的就是它） | 结果（受理、库存不足、限购、背压、闸门不可用、落库不健康、重复） |
| order 落库 | 落库结果数；从受理到落库完成的耗时；状态迁移数；回收任务回收的订单数 | 结果和原因；起止状态 |
| order 读 | 读请求数 | 来源（缓存、从库、主库、冷库）、读模式 |
| inventory | 预占、释放、扣减的件数；`stock_pending` 的积压行数；应用者每批的行数和耗时；发现超卖的次数；闸门对账修正的次数 | 无（不按 SKU） |
| payment | 支付结果数、退款数 | 结果 |
| `kafkax` | handler 耗时；重试次数；进死信数；进程内排队时长；在途数；暂停的分区数；分区的消费延迟（拉取时拿到的高水位减去下一个要处理的位点） | topic、消费组、结果 |
| `outbox` | 发布条数；从写入到发布的延迟 | 中继名 |
| `breaker`、`degrade`、`bulkhead` | 熔断器状态和状态变化次数；开关状态；舱壁的在用数、拒绝数（舱壁本身没有名字，由 order 登记） | 名字 |
| `cache` | 命中、未命中、回源、合并回源 | 缓存名 |
| cdc、orderindex | 事件数；最后一个事件的提交时间到现在的延迟；每批的行数和写库耗时 | 无 |

**标签的规则**：只能是有限的枚举（结果、原因码、规则名、topic）。订单号、用户号、SKU、IP、trace id 一律不进标签。指标的每一种标签组合都是一条独立的时间序列，在进程里和后端里各占一份内存；按用户号打标签，序列数就等于用户数。这条写进 AGENTS.md。阶段计划里说的“库存扣减数”因此是总数，不分 SKU。

**直方图的桶**：SDK 默认的边界是给秒级的 HTTP 请求定的，Redis 一次调用不到 1 毫秒，全落在第一个桶里。用 View 给耗时类的仪表统一设一组从 0.5 毫秒到 10 秒的边界。不用指数直方图：阶段 3 的后端对它的支持要另外验证，现在不引入这个变数。

消费延迟在阶段 3 还会由 Kafka 的 exporter 提供一份。进程里的这份便宜（拉取的响应里本来就带高水位），而且消费者进程挂了时它会消失，两份互相印证。

### 8.9 日志

`logx.New` 返回的 handler 包一层：记录带的 ctx 里有 span 时，加上 `trace_id` 和 `span_id` 两个字段。只有带 ctx 的调用（`InfoContext` 这一类）才有；所以要把那 84 处不带 ctx 的日志里“当时手边有 ctx”的改成带 ctx 的，并在 golangci-lint 里打开 `sloglint` 的对应检查，以后新写的不会漏。启动阶段和后台循环里确实没有请求 ctx 的不动。

日志不走 OTLP，仍然是标准输出上的 JSON，阶段 3 由 Loki 收。和 ADR-0004 一致。

顺带补上 1c 步骤一评审的遗留：消费者分到分区、失去分区时记一条日志。

### 8.11 测试和验收

按模块的测试（用 SDK 自带的内存导出器和手动读取器，进 CI）：

- `otelx`：没配地址时不导出但 span 有 id；配了一个连不上的地址时 `Setup` 立刻返回、业务调用不变慢、`shutdown` 在时限内返回。
- `logx`：ctx 里有 span 时日志带 `trace_id`、`span_id`，没有时不带。
- `grpcx`：客户端和服务端的 span 在同一条链路里；健康检查不产生 span。
- `kafkax`：生产到消费是父子；重试时每次尝试一个 span；延迟消息是 link；按批消费带 link；死信保留 header；指标里的计数对得上。
- `outbox`：`Add` 时的链路上下文，经过表和中继，到消费者手里是同一个 trace id；`Add` 时没有 span 则写 `NULL`、消息不带 header。
- `mysqlx`、`redisx`：有父 span 时出子 span，没有父 span 时不出。

端到端（进 CI）：e2e 的测试进程里起一个很小的 OTLP 接收端（实现 `TraceService` 的 `Export`，几十行），服务把链路发给它。一个用例：下一单并支付，断言同一个 trace id 下出现了 gateway、order、inventory、payment 四个服务的 span，并且有 HTTP、gRPC、Kafka、MySQL、Redis 五种。这就是阶段计划里“链路贯穿”的验收。

实测（不进 CI，结果写进本节末尾）：

1. **开销**：`bench.sh` 在四种配置下的落库吞吐和受理延迟（p50、p99）：埋点之前的提交、采样 0、采样 1%、采样 100%。不预设通过线，量出来再说。
2. **回答 3.9**：放宽刷盘、并发度 16，采样 1%，从链路里看那 54 毫秒在哪。
3. **边车**：经过 Envoy 时 `traceparent` 原样到达下游（实现的第一步就做，它决定 gRPC 这一跳的做法成不成立）。
4. `make fault` 的场景里，熔断器、开关、限流的指标和实际发生的事对得上（抽两三个场景看）。
5. 后端容器停掉时服务照常，内存不涨。

### 8.15 实现中的发现（2026-11-14）

- **HTTP 入口没有用 `otelgin`**，原因在 8.4。
- **支付结果的链路要自己开头。** e2e 第一次跑出来，支付结果的链路是从“中继发消息”那一刻才开始的：出结果的是 payment 的后台处理器，ctx 里没有 span，`outbox.Add` 存不下上下文。现在处理器在出结果的地方开一条链路（`payment.complete`），写 outbox 的事务在它下面，经两次 outbox 一直连到 inventory。这是业务代码里唯一手工建 span 的地方，规则是：后台循环里的一步如果是一个业务动作的起点，就在那里开头。它和用户发起支付的那次请求是两条链路；真实系统里这一步是支付渠道的回调，本来就是新请求。
- **一个订单是三条链路，不是一条**：下单（HTTP 到落库，约 70 个 span，gateway、order、inventory）、发起支付（gateway、payment、order，没有 Kafka）、支付结果（payment、order、inventory）。延迟关单是第四条，用 link 指回下单。它们靠 span 上的 `app.order_id` 关联。ADR-0023 里“一条下单的链路会持续到支付完结”的担心因此不成立。
- **写测试时查出的两个缺陷**（都已修）：降级开关的指标先报后改，两个并发的 `SetMode` 会让指标和实际状态相反，一直错到下一次改动（并发用例约 300 次里失败 1 次；改成在同一把锁里改值和报指标）。MySQL 的 span 名按空格取第一个词，多行语句的名字带着换行，以注释开头的叫 `mysql /*`（改成只认十来个动词，其余叫 `mysql query`）。
- **`redisotel` 默认给每个 span 记调用位置**，每条命令一次 `runtime.Caller`，位置总是落在我们自己的封装里。已关掉。
- **lint 的 `contextcheck`** 会沿着调用链报“记指标时没有用调用方的 ctx”。状态变化发生在不带 ctx 的方法里（熔断器的 `Allow`、开关的 `SetMode`），指标的 ctx 只用来带 baggage 和 exemplar，这里用不到；在这几个函数上标了 `nolint` 并写明原因。
- 刚受理、还没落库的订单在响应里 `unit_price` 是 0：它从闸门的占用合成，只有商品和数量，价格在预占时才有。不是缺陷，记在这里免得再查一次。

### 8.16 实测结果（2026-11-14）

**链路贯穿**（进了 e2e，`TestTraceSpansAllServices`）：测试进程里起一个 OTLP 接收端，下一单并支付，断言下单那条链路里有 gateway、order、inventory，有 HTTP、gRPC、Kafka 的生产和消费、MySQL、Redis 各种 span，除根之外每个 span 的父都在这条链路里，`process order.submit` 的父是 `send order.submit`；支付结果那条链路从 `payment.complete` 经 order 到 inventory。经过 Envoy 边车没有断。

**开销**（`scripts/bench.sh`，开环每秒 2000 个下单请求、20 秒、落库并发度 16，每种配置 3 次；原始输出在 `tmp/bench/otel-overhead/`）：

| 配置 | 落库吞吐（单/秒），3 次 | 受理 p50（毫秒） |
|---|---|---|
| 不导出，采样器 `always_off` | 736、751、611\* | 6.2 到 7.6 |
| 不导出，默认采样（span 照常记录，不发） | 623\*、725\*、726 | 6.2 到 7.5 |
| 导出，采样 1% | 793、728、737 | 5.8 到 7.4 |
| 导出，采样 100% | 562\*、687、553\* | 8.5 到 9.4 |

带 \* 的那几次出现了落库重试（见下一条），不能用来比。没有重试的几次里，前三种配置分不出差别（725 到 793，在这台机器的波动之内）；全量采样只有一次没有重试，687，比前三种低约 7%，受理的 p50 多约 2 毫秒。四个服务的 CPU 用量在四种配置下几乎一样（order 都是约 26 秒）。结论：**1% 采样的开销量不出来；全量采样有可见的代价，只适合看单个请求。** 基线用的是 `always_off` 而不是埋点之前的二进制，它仍然包含传播和生成 trace id 的开销，所以这里量到的是“记录和导出”的代价，不是埋点的全部代价。

全量采样压测一轮之后，`otel-lgtm` 容器的内存是 1.26 到 1.33 GiB，上限 1.5 GiB：全量采样加长时间压测会把它撑爆。

**过载时闸门的调用会成批超时**（不是埋点引起的：`always_off` 的一次也出现了）。12 次运行里 5 次：认领占用的 Redis 调用超过 300 毫秒的时限，闸门的熔断器打开，之后的几百条消息在熔断期间被拒绝、重试（每次 378 到 751 次重试，集中在一两秒里）。订单没有丢，但那一轮的落库吞吐低 15% 到 25%。这是步骤三、四的保护在过载下的实际表现，以前没有注意到，因为没有 `kafkax.consumer.retries` 这个数。原因没有查：可能是下面说的网络停顿打在了 Redis 的连接上。

**回答 3.9：那 54 毫秒在哪。** 放宽刷盘（`sync_binlog=0`、`innodb_flush_log_at_trx_commit=2`，量完已改回）、采样 2%，取 120 条落库的链路，同时读 MySQL 自己的语句统计：

| 一次落库（`process order.submit`）里 | p50（毫秒） | 平均 | 最大 |
|---|---|---|---|
| 整个 handler | 26.8 | 55.3 | 632 |
| 调 inventory 的 `Reserve`（客户端看到的） | 14.9 | 26.4 | 423 |
| 其中 inventory 服务端 | 9.8 | 21.4 | 419 |
| order 自己的 MySQL 语句（不含提交） | 8.1 | 22.0 | 219 |
| order 的提交（两次） | 1.6 | 3.9 | 110 |
| Redis | 0.6 | 0.8 | 5.5 |
| 没有被任何子 span 覆盖的时间 | 0.15 | 2.2 | 204 |

- **不在 order 进程里。** handler 的时间几乎全部被子 span 覆盖，没覆盖的中位数是 0.15 毫秒。3.9 猜的“order 进程内的某处等待”不存在。
- **不是一个 54 毫秒，是一个 27 毫秒的中位数加一条长尾。** 平均值被少数几百毫秒的调用拉到 55。64 个在途除以平均 55 毫秒约等于每秒 1160 单，和 3.9 的 1050 对得上。
- **长尾是 200 毫秒的整数倍**：最大值是 219、419、423 这样的数。这是 TCP 重传的特征（丢一个包，等约 200 毫秒重发），和 1b 起就怀疑的本机容器网络丢包一致。它打在谁身上是随机的，所以“语句”“提交”“Reserve”的最大值都是这种数。
- **中位数的 27 毫秒花在往返次数上。** MySQL 自己统计的语句执行时间是每条 0.2 到 0.5 毫秒、提交 1.5 毫秒，而客户端看到的是每条 1 毫秒上下。一次落库在 order 里有 18 个子 span，inventory 里还有十来条语句，每次往返经过容器的端口转发多出大半毫秒；`Reserve` 这一跳经过两个边车另外多 5 毫秒（客户端 14.9、服务端 9.8）。

所以 MySQL 不再是瓶颈之后，剩下的是**往返的次数乘以这台机器上每次往返的代价，再加上偶发的 200 毫秒重传**。前一半在集群上会小得多（同机房的往返是几十微秒），后一半是 OrbStack 的问题。这支持 1b 把吞吐结论挂到阶段 2 的决定；也说明方案 B（经 Kafka、order 不再同步调 `Reserve`，3.9 末尾）在本机上能省掉的是那 15 毫秒，在集群上未必值得。

刷盘严格时（默认）同样的拆法：handler 的 p50 是 51 毫秒，其中 order 的两次提交 18、`Reserve` 21（里面一次提交约 9）、order 的语句 8。MySQL 自己统计的提交是每次 10.2 毫秒，和链路里的数一致；而单个连接串行提交只要 1.3 毫秒（300 个小事务 0.39 秒），所以那 10 毫秒是每秒两千多次提交并发时排队等刷盘的时间。

另一个顺带看到的数：过载（每秒 2000 个请求，落库只有 700 多）时，消息从写入 Kafka 到开始处理的中位数是 1.7 到 10 秒，其中大部分是进程内的排队（`kafkax.queue_ms`），不是在 broker 上。这是背压放进来的积压，符合设计。
