## 1. 动工前查到的事实（2026-11-24）

### 1.1 现在有什么

- 场景 8 个：4a 的 3 个，这次补了 5 个（都是 Chaos Mesh 的、第一档）。第一档现在 7 个，第二档 1 个。
- 新补的 5 个**都没有在集群上跑过**，答案文件里的“证据”是按设计推的。其中 3 个用到了 4a 冒烟没有覆盖的写法或者量级。
- 注入方式里 `istio`、`script` 两种还没有样例场景，脚本里对应的路径一次都没有走过。
- 故障开关只有 `f01` 一个。计划里“Go 代码缺陷”八类还差七类。
- `chaos-run.sh` 的三处改动（压测不满 30 分钟不让注入、逐行对账放后台、不通过时拦住下一次注入）这次写了，没有对着集群跑过（第 1.4 节）。

### 1.2 和计划的前提不一样的两件事

1. **`s002` 上次已经是“不给宽限期”的删法。** 计划里写“`s002` 是正常的 TERM，另加一个 `pod-kill` 加 `gracePeriod: 0` 的硬杀场景”。查集群上的 CRD（`kubectl explain podchaos.spec.gracePeriod`）：`gracePeriod` 的默认值就是 0，`s002` 的清单没有写这个字段，所以它本来就是立刻删。
   - 4a 走通时“没有失败”的解释（进程收到 TERM，优雅停止把请求做完了）是推断，现在看站不住。更可能的原因：Pod 从 API 里一删，端点立刻从各个调用方的边车里撤掉，而在途的请求只有几毫秒长。进程实际收到的是什么信号、排空的 5 秒走没走，没有看。
   - 后果一：计划里那个新场景照原样写出来和 `s002` 没有区别。硬杀改用了 `container-kill`（对容器里的进程直接发 KILL，Pod 不换、容器原地重启），更贴近崩溃和 OOM。
   - 后果二：`s002` 现在不是名副其实的“正常下线”的对照。要它是，得把 `gracePeriod` 写成 45（等于 Pod 的 `terminationGracePeriodSeconds`）。主人上次定的是“`s002` 不改注入方式”，但那是在“它是正常的 TERM”这个前提下定的，所以放回待定项（第 2 节第 1 项）。
2. **`istio` 这种注入方式按 4a 的设计走不通。** 设计 4a 的 3.5 写的是“apply 一个带故障注入的 VirtualService，恢复时删掉”。但五个服务各自已经有一个同名 host 的 VirtualService（`deploy/cluster/mesh/*.yaml`，超时和不重试都写在上面）。对网格内部的流量，同一个 host 的多个 VirtualService 不会合并，后加的那个要么不生效，要么把原来的超时顶掉。**这是按 Istio 文档的理解，没有实测。**
   - 两条路：改现有的 VirtualService（给某条路由加 `fault`，恢复时改回去；用 `script` 方式做），或者用 EnvoyFilter 给调用方的边车插故障过滤器（不碰现有的路由）。前一条简单，但“恢复”是把一个长期存在的对象改回原样，改错了影响的是平时的流量治理；后一条不碰原来的东西，但 EnvoyFilter 的写法和 Istio 版本绑得紧。
   - 定哪一条要先在 `oppenheimer-e2e` 里各试一次（第 3 节的 B1）。

### 1.4 这次改的脚本，和知道的问题

改了什么（`scripts/cluster/chaos-run.sh` 的头部有完整的说明）：

- **注入前多两道闸**：稳态的压测跑不满 30 分钟拒绝（`SKIP_WARMUP=1` 跳过，会记在这次运行的状态里）；前面的运行有没看过的对账不通过也拒绝。
- **恢复时对账分两段**：前台只查三个常驻核对的指标（越过结束时刻、没有不一致），过了就可以开始下一个实验；逐行对账放到后台，结果晚几分钟写进运行目录，`make chaos-status` 看。不通过时弹一条 macOS 的通知（只有运行号），并且拦住下一次注入，直到 `make chaos-recon-ack RUN=<运行号>`。第三档、指标那一段没过、或者给了 `WAIT_RECON=1` 时逐行对账仍然在前台等。
- 这些只用桩走过逻辑（假的 `kubectl`、可控退出码的 `recon-check.sh`），**没有对着集群跑过**。

知道的问题（子 Agent 提的，主会话认为成立；都先接受）：

1. **后台的逐行对账会被下一个实验“污染”。** 它比的是 `[开始, 结束)` 这段时间里的订单，但读的是现在的库。上一个窗口里下的订单如果在下一个实验期间被写坏，差异会记在上一个运行名下。这不是误报（数据确实不一致，确实该有人看），是归属会错：看到后台对账不通过时，要同时怀疑当时正在做的那个实验。
2. **“拦住下一次注入”是事后的。** 逐行对账出结果时下一个实验可能已经开始了，拦住的是再下一个。
3. **对盲测是一点泄漏。** 拦注入的提示会说出“上一个运行的对账没过”，等于告诉主人上一个故障伤到了数据。数据不一致比盲测要紧，照实说。
4. **压测中途死了，那道 30 分钟的闸看不出来**（它只看启动时刻）。后面紧跟着的稳态检查里“负载”那一项会拦住。
5. **后台进程在本机。** 它被杀、机器睡眠或者重启，结果就是“没有结论”，会拦注入；集群里那个对账的 Job 可能其实跑完了，要手工 `make recon-check ROWS_ONLY=1 FROM=... TO=...` 再跑一次。总闸（`recover --all`）不会停掉还在后台的逐行对账。

## 2. 主人确认的八项（都按建议）

| # | 要定的事 | 建议 |
|---|---|---|
| 1 | `s002` 要不要把 `gracePeriod` 写成 45，做成真的“正常下线” | 改。池里有一个“什么都没坏”的对照是上次定的目的，现在的写法达不到（它是立刻删，只是碰巧没有失败）。改了之后“正常下线”和“进程突然没了”各有一个场景，对比才有意义 |
| 2 | 新场景进盲测的池之前要不要先试一次 | 要。每个新场景先在 `oppenheimer-e2e` 里由主会话跑一次（不盲），核对三件事：注入生效、到时恢复、答案文件里的证据和实际对得上。过了才在 `scenario.yaml` 里标成能盲测（加一个字段，`blind` 只从标了的里面抽）。理由：盲测时场景写错了，浪费的是主人的一次练习，而且事后分不清是没查出来还是根本没注入上 |
| 3 | 实验的顺序 | 按第 3 节的六批。原则：先外部的、自己会恢复的，再代码缺陷，再中间件，最后是可能丢数据的和叠加的 |
| 4 | 七个故障点怎么写 | 按设计 4a 的分工：每个故障点一个独立任务，派给 Opus 在各自的 worktree 里并行写，主会话逐个评审（查“不露痕迹”的规则、查没有碰资金、库存扣减、订单状态机）。放在哪个服务的哪个接缝由主会话定，记在 `chaos/scenarios/` 里。主人不读这些代码。七个任务是一次集中的 token 开销，所以先问一句 |
| 5 | 故障开关只对注入那一刻的副本生效，怎么办 | 接受，不改机制。五个服务现在都是固定的 2 个副本（gateway、order 有 HPA，上限是 2；另外三个没有 HPA），不会扩出新副本；实验期间不发布。Pod 自己重启（比如被 OOM 杀掉）时开关会复位，这一点挡不住。`recover` 时多打一行“注入时的 Pod 和现在的 Pod 是不是同一批”，不是的话在复盘草稿里标出来。panic 那一类本来就要走 `FAULT_FILE`，不受这个限制 |
| 6 | 盲测的“同意”按什么粒度给 | 沿用 4a 定的按池同意，再加一条：每次坐下来做实验时主人说一句今天的池（比如“今天第一档”），当天在池里抽几个都算。命令由主人自己敲。第三档每个单独问 |
| 7 | 一次实验做多久算超时 | 盲测时从注入起 30 分钟没有定位就停，揭晓、复盘。验收标准是“常见故障 15 分钟内定位”，30 分钟还没有头绪时继续耗下去学不到更多，不如看答案 |
| 8 | Agent 的诊断由什么触发 | 两路都留。有告警响的，Alertmanager 自己触发（现在就是这样）；没有告警的场景（不少故障本来就不该响告警），主人开始排查的同时由主会话手动问一次，问题只写症状，不写背景（上次定的）。高峰价时段手动问要加 `-force`，尽量把实验排在低谷 |

## 3. 六批

每一批开始前，要动集群和发压的具体做法先登记到计划文件，等主人同意。下面写的是每一批做什么、要备什么。

| 批 | 做什么 | 在哪 | 发压 | 盲测 |
|---|---|---|---|---|
| B0 | 不动集群的准备：脚本的三处改动、补第一档的场景、这份设计 | 本机 | 否 | |
| B1 | 把没有跑过的东西在 e2e 里跑一遍 | `oppenheimer-e2e` | 否 | 否 |
| B2 | 第一档：杀 Pod、CPU 和内存压力、网络延迟和丢包、DNS | `oppenheimer` | 稳态 | 是 |
| B3 | Go 代码缺陷八类 | `oppenheimer` | 稳态；开头有一次阶梯 | 是 |

| B5 | MySQL、Redis、Kafka | `oppenheimer`；写坏数据的在 e2e | 稳态；第三档用带账本的 | 第一、二档是 |

**B0（这次做了的）。** 见 `PROGRESS.md`。

**B1：e2e 里跑通。** 不发压，不碰长期运行的那一套。起一套 `E2E_KEEP=1 make cluster-e2e`，然后：

- `make chaos-blind POOL=1 DRY_RUN=1`；再 `CHAOS_NS=oppenheimer-e2e` 真的盲测一次（验“终端不打印内容”和抽取，主会话看得到内容没关系）。
- 新补的 5 个场景各跑一次，核对第 2 节第 2 项说的三件事。e2e 里没有稳态的压测，要用 `--skip-warmup` 和 `CHAOS_STEADY_SKIP`；看不出对业务的影响，只验注入本身。
- 硬杀的三种写法（`container-kill`、`pod-kill` 加 `gracePeriod: 0`、`gracePeriod: 45`）各一次，看进程收到什么信号、退出码、事件里写什么。这同时回答第 1.2 节第 1 件事里“没有看”的那些。
- Istio 故障注入的两条路各试一次（第 1.2 节第 2 件事），定用哪条。
- 新的 `recover` 编排（逐行对账在后台、不通过时拦注入、确认之后放行）走一遍。
- 做完删掉 e2e 那一套。

**B2：第一档。** 这是主人的第一批盲测。稳态的压测先跑 30 分钟。一次坐下来做两三个，每个：注入 → 主人和 Agent 各自排查 → 恢复 → 揭晓 → 复盘。计划清单里对应：“随机杀业务 Pod”“Pod CPU 打满、内存压力直到 OOM”“网络延迟、丢包”“DNS 故障”。

**B3：Go 代码缺陷。** 先做三件准备，再做实验：

1. 七个故障点（第 2 节第 4 项）。写完、评审完，带故障代码的镜像重新构建、滚动更新一次（和 4a 那次一样，开关全关）。
2. 打开 mutex、block 采样（`DEBUG_MUTEX_FRACTION`、`DEBUG_BLOCK_RATE`，会重启 Pod），打开前后各跑一次 3b 的 mixed 阶梯，比吞吐和 p99。这一轮连接数会过 200，顺带看 `MALLOC_ARENA_MAX=4`。量完决定采样率留多少。
3. panic 那一类要的 `FAULT_FILE`：一个可以不存在的 Secret 挂进五个服务（Deployment 的定义要改一次，会滚动）。

然后这八类按第二档盲测。“数据竞争导致错误数据”例外：只写坏派生数据，只在 `oppenheimer-e2e` 里做（设计 4a 第 2 节第 9 项），不盲。排查工具（`go tool trace`、core dump 加 delve）是主人手工练的，哪个场景适合练哪个，复盘时主会话指出来。

**B4：服务之间。** 用 B1 定下来的那条路。“下游变慢引发的级联”要验的是不雪崩：边车的超时、并发上限、摘除在真的慢下游面前是不是像 1d 设计的那样动作。“网络分区”分两种：服务和数据库之间（NetworkChaos 的目标在别的命名空间，写法要先试）、节点之间（B6）。

**B5：中间件。** 这一批的场景大多是 `script` 方式：往库里放数据、开一个不提交的事务、跑一条慢语句。

- 第一、二档（可以盲）：慢查询、死锁、锁等待和长事务、从库延迟、连接池耗尽、大事务造成延迟；Redis 的大 key、热 key、慢命令、内存打满；Kafka 的积压和重平衡。
- 第三档（每个单独登记、单独同意，不盲，用带账本的 `make loadtest`，结束后 `load verify` 加逐行对账都过了才算）：MySQL 主库宕机和切换、磁盘写满；Redis 主节点宕机、整体不可用；Kafka broker 宕机。
- 会改表结构或者往业务表里塞脏数据的（“缺索引”“统计信息过期”）在 `oppenheimer-e2e` 里做，或者只动为实验单独建的表。动手前逐个定。
- 做“主库宕机”之前先读 inventory 在主库不在时返回什么（第 1.3 节），有问题先修。

**B6：集群和叠加。** 关节点（宿主机上 `vm.sh`）、驱逐、控制面不可用、时钟偏移；秒杀期间叠加、发布期间叠加、两个故障同时。都是第三档或者接近第三档，逐个登记。叠加的实验要脚本支持同时有两个进行中的运行，现在不支持（一次只有一个），到时再改。

## 4. 一次实验从头到尾

1. **前置**（每天一次）：`make down`（本机是发压机）；确认没有告警在响、没有上一次没看过的对账结果（脚本会拦）；备 SKU；`make chaos-steady ARGS=start`，等 30 分钟。
2. **假设**：第一、二档盲测时主人不知道内容，写不了具体的假设。改成注入前写一句通用的：现在哪些指标是基线、如果坏了最先看哪里。场景自己的“预期”在答案文件里，复盘时对照。第三档不盲，注入前写完整的假设。
3. **注入**：主人敲 `! make chaos-blind POOL=<池>`，记下运行号和摘要。
4. **排查**：主人只用监控、日志、链路、kubectl、pprof；记时间线和走过的弯路（哪怕只是几行）。Agent 同时诊断（第 2 节第 8 项）。主会话在这段时间不提示。主人要查资料、问概念可以问主会话，问“是不是 X”不答。
5. **止血**：主人说出结论和止血的办法之后，`make chaos-recover`。结论不对也恢复（30 分钟的上限，第 2 节第 7 项）。
6. **数据检查**：三个常驻核对过了就可以开始下一个；逐行对账在后台，出了差异会拦住下一次注入。
7. **揭晓和复盘**：`make chaos-reveal` 生成草稿。主人填时间线和弯路；主会话填“假设和实际的差距”、Agent 的表现（对的、错的、缺什么工具或知识）、改进项。改进项当场能做的做掉（补告警、补 runbook），要改代码或架构的登记到计划文件。
8. **顺带**：对照第 5 节，这个实验该触发的告警响了没有。

一个第一档的实验从注入到复盘写完，估计 40 到 60 分钟：排查最多 30 分钟，恢复和等核对约 8 分钟，复盘 15 分钟上下。一次坐下来做两到三个。

## 7. B1 的结果（2026-11-24 12:50 到 13:05 UTC；主人同意后做的；只动了 `oppenheimer-e2e`）

做了：`E2E_KEEP=1 make cluster-e2e`（通过）→ 逐个试 → `services.sh e2e-down`。长期运行的那一套没有被注入，结束时没有告警在响。没有发压。

| 试的事 | 结果 |
|---|---|
| 删 Pod 的宽限期 | 45 秒是名副其实的正常下线（Pod 在 Terminating 里约 10 秒，就绪探针先返回 503）；0 是 3 秒内 Pod 从 API 里消失，没有排空。第 1.2 节的判断成立 |
| 进程被直接杀掉（`container-kill`） | 能用。退出码 137，不是 OOMKilled，容器原地重启，Pod 不换 |
| CPU 压力 | 能用。没有 CPU limit 的业务容器，几个 worker 就多占几个核，所在的节点从 7% 到 47% |
| 内存超过 limit | 能用。整个容器被杀（OOMKilled）。**只杀一次**：容器重启后 Chaos Mesh 不再注入 |
| 网络延迟、丢包 | 注入成功。对业务的影响要有负载才量得出 |
| DNS | **DNSChaos 对业务容器注入不了**：它要进容器改 `resolv.conf`，业务镜像是 distroless，辅助程序报找不到文件。4a 的冒烟是对 busybox 的探测 Pod 做的，所以当时是通过的。改用 NetworkChaos 挡住 Pod 到集群 DNS 的包，在 Pod 里核对过解析确实失败。代价是粒度变粗：那个 Pod 里所有域名都解析不了 |
| 盲测（`blind`） | 真的跑了一次，终端上只有运行号和摘要，没有场景的任何内容。`reveal` 核对摘要、生成草稿正常（草稿是试跑的，删了） |
| 对账的闸 | 用假的“不通过”试：`status` 报出来，注入被拒，`recon-ack` 之后放行。真的后台逐行对账没有跑（e2e 里没有常驻核对） |
| Istio 的故障注入 | **没有试成。** 主会话的探测请求被 gateway 的鉴权挡在 401，没有走到下游，两种写法都看不出效果。挪到 B4 开始之前 |

- 第一档里 5 个场景标成了能盲测。丢包和 DNS 两个注入是验过的，但它们的效果要有负载、而且其中一个要半小时以上才看得出，第一次由主会话带着做（不盲），先不进池。

## 8. Go 故障点（2026-11-24；六个 Opus 子 Agent 各在一个 worktree 里写，主会话读了每一个的故障代码后合进工作区）

写了六类：内存泄漏、锁竞争、CPU、死锁、连接泄漏、panic。各自在哪个服务、是什么写法，在 `chaos/scenarios/NOTES.md`。数据竞争那一类（只在 e2e 里做）还没有写。

主会话评审时查的：名字、注释、文件名里没有露痕迹的词；对 `pkg/fault` 的调用只有一行登记和一次 `On()`；没有碰下单提交、支付、库存的预占确认释放、订单状态的变更；开关关着时走的是原来的代码。六个都符合。有一个离状态机最近，单独说明：连接泄漏放在“兜底扫描到期订单”读从库的那一步，改的只是这次读怎么拿连接，扫描结果怎么用、订单怎么关没有动；从库的连接池耗尽后扫描会失败几轮，随后自动改读主库，后果是关单的兜底路径晚几十秒（主路径是延迟消息，不受影响）。

子 Agent 报的、主会话认为成立的问题：

1. **有三个在稳态的压测下症状可能太弱**（都是估的，没有量）：内存泄漏每小时只涨十几兆；锁竞争的 p99 只到两三倍；CPU 只多零点几个核。带负载试一次再决定是调压测的配比、和别的故障叠加，还是接受它们是“要看剖析才发现”的场景。
2. **死锁多久撞上波动很大**，30 分钟里可能一次都不发生。
3. **panic 那个现有的告警基本看不见**：消费者“最老一条消息等了多久”每次重启都从零算，不会响，约 20 分钟后才有一条别的告警。这是真实的监控盲区，做到这个实验时补。
4. **连接池的指标分不出主库池和从库池**（标签只有库名，两个池的库名一样）。不属于故障实验，是平时的可观测缺口，登记到计划里。
5. order 模块的 `internal/service` 测试在几个 Agent 同时跑的时候要 12 分钟以上，超过 `go test` 默认的 10 分钟。单独跑的耗时见 `PROGRESS.md` 这次的验证结果。
