# ADR-0029：服务之间的流量治理迁到 Istio，用边车模式

- 状态：已采纳
- 日期：2026-11-15

## 背景

服务之间的熔断、并发上限、路由超时从 1d 起放在每个服务自己的 Envoy 边车上（ADR-0020）。2c 把这些边车原样搬进了 Pod：配置是手写的静态 YAML，下游的端点靠 headless Service 加 DNS 发现（设计文档 2c 第 6 节）。当时就定了分两步：2c 先手写，把端点怎么传到代理、摘流要等多久亲手量一遍；2d 换成服务网格，因为真实环境里几乎没有人手写边车的配置。

设计和调研在设计文档 [2d-mesh.md](../design/2d-mesh.md)。

## 决定

主人 2026-11-15 确认，八项都按设计文档第 2 节的建议：

1. **Istio，边车模式。** 每个有 gRPC 的业务 Pod 注入一个 `istio-proxy`，配置由 istiod 经 xDS 下发。1d 的每条调用边改写成 `VirtualService`（超时、不重试）、`DestinationRule`（并发上限、摘除）、`Sidecar`（入站上限、可见范围）。
2. **版本 1.32.0。** chart 和 istioctl 取自 GitHub 的发布包。
3. **到 MySQL、Redis、Kafka 的流量不过边车**，出站按端口排除。
4. **入站只接管 gRPC 端口。** HTTP 端口（探针、管理端口、gateway 的 8080）不过边车。
5. **摘除时间不再固定成 5 秒**，接受它随被摘除的次数加长，不用 EnvoyFilter。实测后再回头看。
6. **本机和 CI 保留手写的边车。** 同一跳的超时写在两份配置和 Go 的常量里，由测试核对三处一致。
7. **不停机地切换**，按调用关系的拓扑序，调用方先切。
8. **加 mTLS 严格模式和按身份的访问控制**；Argo CD、cert-manager、灰度发布这次不做。

不变的：保护仍然在代理上而不在进程里；每个调用方对每个下游各有额度；同步链上不重试；进程里的时限等于边车的预算加 `grpcx.SidecarMargin`，边车先超时。

## 理由

- **边车模式和 1d 的拓扑一一对应。** 出站的保护在调用方的代理上，是“迁移”而不是重新设计，1d 的每个实测结论都有一个可以直接对照的位置。面试里问服务网格，默认说的也是这个形态。
- **1.32 的 Envoy 分支（v1.40）和 1d 实测时的版本相同。** 三个坑是在这个版本上量出来的，换一个 Envoy 版本就要多怀疑一层。按版本规则它也是当前最新的正式稳定版（Istio 没有 LTS）。代价是它才发布 6 天。
- **中间件不过边车**：它们的熔断在进程里（`pkg/breaker`），对端没有边车所以没有 mTLS；过边车多一跳，并且引入“空闲的长连接被代理掐掉”这类问题，换来的只有指标，而指标系统要到阶段 3 才有。
- **只接管 gRPC 端口**：入口的 Envoy 到 gateway 这一跳如果过边车，gateway 看到的对端地址是边车的本地地址，受信任代理的判断失效，按 IP 的限流会把所有客户端算成一个。保持和 1d、2c 相同的形态，变量少一个。
- **不用 EnvoyFilter**：它直接改 istiod 生成的 Envoy 配置，和 Istio 的内部结构绑着，升级时容易悄悄失效。为一个“恢复时间可能变长”的问题引入它，要先有数据说明值得。
- **默认的重试必须关。** Istio 默认对 `connect-failure,refused-stream,unavailable,cancelled` 重试 2 次。`unavailable` 是按 gRPC 状态码判断的，下游已经执行了一半再返回 `UNAVAILABLE` 的写请求会被再发两次，而且一条链上每一跳都这样重试。在网格的默认配置和每条路由上各关一次。

## 备选方案

- **ambient 模式**（每个节点一个四层的 ztunnel，七层功能由 waypoint 代理提供）。省内存，没有注入，是 Istio 现在主推的方向。没选：超时、摘除、并发上限都落到被调用方一侧的 waypoint 上，“每个调用方各有额度”要换一种表达；这是另一个设计，不是迁移。边车模式做完之后可以单独做一次对照。
- **Linkerd。** 更轻。它的代理不是 Envoy，1d 的实测全部作废；熔断的模型也不同（按失败累积）。
- **继续手写。** 配置和代码对得上、行为都量过，但服务一多就不可维护，端点靠 DNS 传得慢，没有 mTLS。
- **1.31.4。** 更成熟的补丁版本，Envoy 是 v1.39。
- **本机也不用边车，保护只在集群上测。** CI 没有集群，熔断和并发上限就没有自动化的验证了。

## 后果

- 多一个常驻的控制面（istiod）。**它不在的时候**，已经在跑的边车用最后一份配置继续工作，但端点变化推不下去；注入 webhook 的失败策略是 `Fail`，业务命名空间里建不出新 Pod，滚动发布和 HPA 扩容都会卡住。只跑一个副本是内存决定的，这个代价要在阶段 4 的故障实验里量。
- 进程不再知道边车的存在（透明拦截），下游地址写的是 Service 名。排查“请求去了哪”要看边车实际拿到的配置（`istioctl proxy-config`），不能只看进程的配置。
- Service 的端口名成了行为的一部分：gRPC 端口不叫 `grpc`（或没有 `appProtocol`）就会被当成 TCP，按连接做负载均衡，不报错。
- 同一个超时写在两份配置里（本机的 Envoy YAML、集群的 `VirtualService`），靠测试守着。并发上限和摘除参数两边没有自动比对。
- 摘除时间随次数加长，被反复重启的服务恢复得越来越慢，直到健康一段时间后次数降回去。
- 每个 Pod 的边车比手写时重（多一个 pilot-agent 进程和整套动态配置），HPA 按整个 Pod 的 requests 算利用率，扩容点会移动。
- 服务之间有了 mTLS 和身份，每个服务要有自己的 ServiceAccount。

实测的结果、和 1d 不一致的地方记在设计文档 2d 的“实现中的发现”里。ADR-0020 加一段补充指向本文。
