# ADR-0014：商家维度查询用自研的 Go CDC 同步到索引表，从从库读，靠行版本号做幂等

- 状态：已采纳
- 日期：2026-11-13
- 相关：ADR-0002、ADR-0008、ADR-0012、ADR-0013；设计文档 [1c-sharding.md](../design/1c-sharding.md) 第 4 节

## 背景

订单按 `user_id` 分片后，按商家查订单没有分片键，只能扫全部分片。要另存一份按商家分片的数据，并决定它怎么和订单表保持同步。

本机的资源是一个约束：compose 已经有 9 个容器，order 的 MySQL 实例为了放得下已经把缓冲池调到 64 MB。

## 决定

1. **同步走 binlog**，不走应用层双写，也不走现有的 `OrderEvent`。
2. **CDC 用 Go 自己写**，基于 go-mysql 的 `replication` 包，不用 Canal 或 Debezium。
3. **从从库读 binlog**，位点记 GTID 集合，存在 Kafka 的压缩 topic 里。
4. **至少一次投递，下游靠行上的 `version` 列做幂等和定序**。`orders` 表加 `version`，每次更新加一；索引表只接受版本更高的映像。
5. **全量是普通的分批读**，不取一致性快照；它和增量的衔接靠版本号保证正确。
6. **列名取自 binlog**（`binlog_row_metadata=FULL`），CDC 不查库里的表结构。
7. **一个订单只属于一个商家**，`merchant_id` 写在 `orders` 行上，多商家的订单在预占时被拒绝。
8. 索引表带上列表页要显示的列（状态、金额、时间），只用于展示；做决定的读回到订单分片的主库。

## 考虑过的方案

**怎么同步**

- **应用层双写**（order 写完订单再写索引）。两个库之间没有事务，写完一个崩溃就不一致，还要另做补偿。业务代码每多一条写路径就要记得再写一次索引。
- **消费现有的 `OrderEvent`**（outbox 发到 Kafka 的业务事件）。在这个项目里行得通，也是不少系统的做法：事件和状态变更在同一个事务里，不会丢。区别在于事件是发布方决定发什么、什么时候发，绕过业务代码的变更（人工修数、以后的归档任务、忘了发事件的新写路径）它看不到；binlog 记的是库里实际发生的事。另外事件要带上索引需要的所有字段，等于让上游为某一个下游改事件格式。这一步的学习目标是 CDC，所以选 binlog；实际工作里两者都要会评估。
- **用 CDC 替换 outbox 的轮询中继**（阶段计划里的可选项）。这是 Debezium 的 outbox 模式：业务仍然在事务里写 outbox 表，但由 CDC 读 binlog 来发，不再轮询。好处是没有轮询间隔带来的延迟，也没有“扫未发布的行”对库的压力；1b 记录的“轮询拖垮落库”正是这个问题。代价是发布依赖 binlog 的保留和 CDC 的位点，outbox 表变成只写不读，清理要另外做。这一步只做书面对比，不实现。

**用什么读 binlog**

| | 自研（go-mysql） | Canal | Debezium |
|---|---|---|---|
| 运行形态 | 一个 Go 进程 | Java 服务端，高可用依赖 ZooKeeper | Kafka Connect 上的连接器（JVM），或独立的 Debezium Server |
| 内存 | 几十 MB | 约 1 GB | 约 1 GB，另加 Connect |
| 位点 | 自己管，这里存 Kafka | ZooKeeper 或本地文件 | Connect 的 offset topic |
| 全量 | 自己写 | 不带，要配合别的工具 | 自带，支持不加锁的增量快照（DBLog 的水位线算法） |
| 表结构变更 | 自己处理 | 内置一个表结构的时序库 | 表结构历史 topic |
| 成熟度 | 边界情况要自己踩 | 国内用得多，近年更新慢 | 事实标准，覆盖的情况最全 |

选自研有两个原因：一是内存，两个 JVM 方案都放不进本机；二是位点、全量衔接、表结构、顺序这些问题正是计划里要回答的，用现成的工具等于把答案藏在配置项后面。生产环境里没有特别的理由应该用 Debezium，自研要自己承担数据类型、DDL、主从切换的各种边界情况。

go-mysql 里还有一层更高的 `canal` 包，带全量（调 mysqldump）和表结构查询。不用它：它依赖本机装 mysqldump，表结构靠查库（有时间差的问题），位点的存取方式也和这里的设计不一样。

**从主库还是从库读**

- **主库**。延迟最低。但异步复制下主库宕机时，CDC 可能已经把从库没收到的事务发给了下游，切换后下游比新主库多出数据，而且没有办法自动发现。
- **从库**（采用）。下游不会超前于从库。代价是延迟叠加复制延迟。

**版本从哪里来**

- **GTID 的事务号**。不用改业务代码，也不可能漏。但它只在同一个主库产生的事务之间可比，换主库后要另加一个纪元；全量读到的行没有自己的位置，全量必须是精确对应某个 GTID 位置的一致性快照（短暂的全局读锁加一个长事务）。
- **`updated_at`**。现成的列，但它是语句执行时的墙上时钟，不保证递增（时钟回拨、同一微秒）。
- **触发器维护的 `version`**。不会漏，但把逻辑藏进了库里，也给以后的在线改表工具添麻烦。
- **业务代码维护的 `version`**（采用）。任何来源的行映像都能直接比较，全量和换源都不用特殊处理。会漏的风险由 CDC 检查更新事件前后的 `version` 是否变化来发现。

**位点存哪里**

- **源库的一张表**。位点和数据在一起，最直观。源是只读的从库，写不进去。
- **另一个 MySQL 库或 Redis**。多一个依赖；Redis 那个实例是闸门用的，位点丢了就要重做全量，不该和它放在一起。
- **本地文件**。进程换一台机器就丢了，阶段 2 上集群后不可用。
- **Kafka 的压缩 topic**（采用）。CDC 本来就离不开 Kafka。

**允许一个订单有多个商家**。现有接口不用加限制。但商家只出现在订单项上，订单状态变更的行事件里没有，消费者要回查源库或自己维护映射。真实系统在下单前拆单，订单模型本身就是单商家的。

## 后果

- 新增两个服务（`cdc`、`orderindex`）、两个 topic、两个索引库。`make run` 和 e2e 要多起两个进程。
- `orders` 上所有更新都要给 `version` 加一。漏掉的后果是索引停在旧状态，靠 CDC 的检测和对账工具发现，不会自动修复。
- 索引是最终一致的，延迟等于复制延迟加 CDC 和消费的延迟。从库停止时索引也停止更新。
- 现在的延迟只能从日志里看，没有写入时无法区分“没有变更”和“卡住了”。阶段 3 接入指标并在源库加心跳后补上。
- 只跑一个 CDC 实例，它挂掉期间索引不更新，重启后从位点追上。高可用（选主）没有做。
- **行版本号的正确性依赖“CDC 的源就是将来被提升的那个从库”。** 异步复制下主库宕机可能丢掉最后几个事务。如果 CDC 读的是主库（或一个没被提升的从库），它可能已经把旧主库上的版本 3（比如已支付）发给了下游，而这个事务在新主库上不存在；新主库上同一个订单会再长出一个内容不同的版本 3（比如已关闭），下游按“版本更大才接受”把它当成重复丢掉，索引停在一个源库里不存在的状态上，直到这个订单下一次更新。从被提升的从库读就没有这个问题：下游见过的版本都在这个从库上，提升后继续往上长。所以决定 3 和决定 4 是配套的，一个分片有多个从库时，切换后要对没被提升的那些源重做全量。这是 orderindex 的子 Agent 评审时指出的。
- 主库切换没有演练过，要等阶段 4 做故障切换时验证上面这一条。
- 一条缺列的消息会让它所在分区的全部订单停止同步（四分之一的订单），只能从日志和消费组积压发现。这是“不跳过”的代价；积压告警和跳过某个位点的操作手册放到阶段 3。
- DELETE 没有处理。步骤五的归档会删除热库的行，那时要决定索引的行为。
- 应当重新评估的情况：要同步的表变多、出现需要关联多张表才能生成的下游数据、或者需要不停机的大表全量，这时自研的成本会超过换用 Debezium。
