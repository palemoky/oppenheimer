# ADR-0028：发号器的节点号从 MySQL 租，唯一性靠互不重叠的时间区间

- 状态：已采纳
- 日期：2026-11-15

## 背景

`pkg/idgen` 的订单号和支付单号是“41 位毫秒时间、6 位节点号、10 位序列号、6 位基因”。唯一性的前提是同一个服务里没有两个进程同时用同一个节点号。到阶段 2b 为止每个服务只有一个进程，节点号靠环境变量 `WORKER_ID` 手工写死。

阶段 2c 要让 order 和 payment 各跑多个副本。一个 Deployment 的所有 Pod 环境变量相同，两个副本会用同一个节点号，同一毫秒里各自从序列号 0 发号，必然重号（设计文档 2c 的第 1 节、第 5 节）。

## 决定

没有设置 `WORKER_ID` 时，进程启动时从本服务的 MySQL 主库里租一个节点号（表 `idgen_worker`，64 行，一行一个号），每 10 秒续租一次，租期 30 秒，退出时让出。order 的表在第一个订单库，payment 的在 `payment_db`。设置了 `WORKER_ID` 就固定用它，不碰数据库（本机和 CI 的现状不变）。

**唯一性不靠“同一时刻只有一个持有者”，而靠给每一任持有者划一段互不重叠的毫秒区间：**

- 表里每个节点号有一个上界 `last_ms`：历任持有者可能用到的最大毫秒时间。
- 持有者每次续租把上界抬到“自己的时钟加一个租期”。数据库确认写入之后它才用到那么远；发号时毫秒时间超过已确认的上界就拒绝（`ErrLeaseExpired`）。
- 下一任用一条条件更新（`WHERE worker_id = ? AND expires_at < NOW(3)`，影响一行才算租到）接手，租到之后读出上一任留下的上界，只发比它大的毫秒。上一任这时已经不是持有者，续租的条件（`owner = ?`）不成立，再也抬不动上界。

上一任发的号都在上界以内，下一任发的都在上界以外，中间隔着数据库里的一次条件更新。

实现在 `pkg/idgen/lease.go`（逻辑）和 `lease_sql.go`（MySQL 上的三条语句），各服务装配时调用 `idgen.Open`。

## 理由

- **不比较两台机器的时钟。** 常见的租约写法是“持有者在本地判断租约还有没有效，过期前停手”，它的正确性依赖持有者的时钟走得不比数据库慢、进程不会在“判断有效”和“使用”之间卡住。这里把这个依赖去掉了：一个持有者卡住一分钟后醒来、接着发号，它用的毫秒时间超过了自己确认过的上界，会被拒绝；它的时钟要是慢了，发出来的号仍然落在自己的区间里，和接手的人不重叠。测试里专门有“上一任在被接手之后还在发号”“两边的时钟差 20 秒”的用例。租期和续租间隔只影响可用性，不影响唯一性。
- **过期与否只由数据库的时钟判断**（`NOW(3)`），所有进程看到的是同一个钟。
- **保住了 Deployment。** 滚动发布可以先起新的再停旧的（新旧各占一个号），节点失联后控制器会在别处建新的 Pod。这两点是 2c 的验收项和阶段 4 的实验对象。
- **没有引入新的组件，没有新的硬依赖。** order 启动时本来就要连订单库做迁移。
- **学习价值。** “节点号怎么分配”是分布式 ID 的标准问题（美团 Leaf 用 ZooKeeper 的顺序节点，百度 uid-generator 用数据库表），绕过去就少了这一课。

## 备选方案

- **StatefulSet 的序号当节点号。** 不用写代码，Kubernetes 保证同一个序号同一时刻最多一个 Pod。没选：它把无状态的服务变成了有身份的，滚动发布只能原地一个一个换，节点失联时 Pod 停在 Terminating、不会在别处重建，要人工强制删除。主人最初倾向这个方案，讨论后确认它不是生产里无状态服务的常见做法（2026-11-15）。
- **从 Redis 租**（`SET NX` 加过期时间）。闸门那套 Redis 是异步复制加 Sentinel，故障切换会丢最近的写入，丢的可能正是“谁租到了”。MySQL 的主从切换是人工的、有“等从库追平”这一步。
- **用 Kubernetes 的 Lease 对象**（存在 etcd 里）。服务要有访问 API 的权限，控制面不可用时不能启动新副本。
- **号段模式**（每个进程从数据库领一段连续的号）。没有节点号的问题，但号里就没有时间了，而冷热归档按订单号里的时间划分（ADR-0016），分片靠号里的基因。
- **节点号取 Pod IP 的低位。** 6 位只有 64 个值，Pod 网段是 /16，会撞。
- **把租约表放进服务的迁移文件。** order 的迁移是按分片渲染、每个订单库都跑一遍的，而这张表只应该在一个库里。所以由 `idgen.NewSQLLeaseStore` 自己建（`CREATE TABLE IF NOT EXISTS` 加 `INSERT IGNORE`），这是对“表由迁移建”的一处偏离。

## 后果

- **order 的受理多了一个失败原因。** 第一个订单库不可用超过约 20 秒（租期减续租间隔）之后，这个进程不能发号，所有用户的下单都被拒绝，按降级处理（`ORDER_LANDING_UNAVAILABLE`，网关返回 503）。此前订单库 0 不可用只影响落在它上面的一半用户（落库健康按库判断，ADR-0021），**现在会影响全部**。这是把租约放在一个库里的代价；可以接受的理由是受理本来就不应当在订单库故障时继续堆积，但它确实扩大了故障面，阶段 4 做“一个订单主库不可用”的实验时要把它算进预期。恢复是自动的：数据库回来后的第一次续租成功，发号就恢复。
- **payment 的租约过期时 `Pay` 返回的是内部错误**，不是降级。payment 的库是它唯一的存储，库不可用时它的每个接口本来就都是内部错误，没有单独处理。
- **租约被别人租走是致命错误**：续租发现自己不是持有者时，发号永久停止，租约组件报错，进程退出并由 Kubernetes 重启，重启后重新租。正常情况下不会发生（持有者只要还在续租，别人就租不走）；会发生的情形是进程卡住超过一个租期。
- **主库故障切换可能丢掉最后一次续租。** 异步复制下，新主库上的上界可能比持有者手里的小一个续租间隔。为此接手的人从“上界加 10 秒（一个续租间隔）”之后才开始发号。丢得更多（复制落后超过 10 秒时主库故障）就没有保证，这和那种情况下订单数据本身会丢是同一个问题，阶段 4 做主库故障切换时一起看。
- **崩溃的进程占着的号要过 30 秒才能被别人租走。** 数据库按“过期最久的优先”给号，64 个号里几乎总有闲置的，所以新进程不用等。反复崩溃重启的 Pod 每次占一个新的号，重启有退避，占不满。
- **64 是 order、payment 各自副本数的硬上限**，用完时启动失败并报 `no free worker id`。
- **一个号的上界远在将来**（某个持有者的时钟曾经快了很多）时，接手的进程不在它上面等，放回去换一个。这个号要等真实时间追上才会再被用到。
- 没有做的：租约状态的指标（当前的节点号、距离上界还有多久）；`idgen_worker` 表不在备份演练的比对范围里（它是运行状态，恢复出来的旧值是安全的：上界只会偏小一个备份周期之前的值，而那时的持有者早已不在。**这句是推断，没有验证**）。
- 重新评估的条件：需要的副本数接近 64；或者服务拆到没有自己的 MySQL。
