# ADR-0010：查询缓存用旁路模式，只缓存不会再变或旧了也无所谓的数据

- 状态：已采纳
- 日期：2026-11-12

## 背景

1b 步骤三之后，下单的压力被闸门和 Kafka 挡在数据库前面，但查询没有：库存查询和订单查询每次都读 MySQL。

- 秒杀页面反复刷新库存，所有用户读同一个 SKU。
- 异步下单让客户端必须轮询订单状态，一次下单带来多次查询。

约束：

- 订单状态关系到用户会不会重复支付、重复下单，不能长时间给出旧状态。
- 库存每秒被扣减很多次。
- 缓存和数据库之间没有事务，任何方案都有不一致的窗口，只能选窗口的大小和后果。
- 闸门所在的 Redis 配置为 `noeviction`。

## 决定

1. **旁路缓存（cache-aside）**：读时未命中则回源并写入。
2. **只缓存两类数据：不会再变的，和旧了也无所谓的**。因此没有任何写时失效的逻辑。
   - 不会再变的（终态订单）：长 TTL。
   - 一直在变但只用于展示的（库存数量）：短 TTL（1 秒），写时不删。
   - 会变而且旧值有后果的（创建中、待支付的订单，支付单）：不缓存。
3. **穿透用空值缓存，击穿用进程内 singleflight 加 Redis 互斥，雪崩用 TTL 抖动加故障时回源**。
4. **缓存用独立的 Redis 实例**，淘汰策略 `allkeys-lru`，不持久化。

实现细节见 [设计文档 7.2](../design/1b-high-concurrency.md)。

## 备选方案

- **待支付订单也缓存，短 TTL 加“先更新数据库再删缓存”**。支付页反复读取待支付订单时能少读库。没选：缓存和数据库之间没有事务，删除一定有窗口（读到旧行后在删除之后才写入；提交后删除前崩溃），后果是用户付完款仍看到“待支付”，最长一个 TTL。省下的只是一次主键查询，不值得。这也让决策路径（payment 核对订单）可以放心读缓存，不用给接口加“是否允许读缓存”的开关。
- **写时更新缓存（而不是删除）**。没选：同上，而且两个写并发时缓存可能停在较旧的值。
- **读写穿透（由缓存层代理所有读写）**。没选：状态转换依赖数据库的条件更新和同事务的 outbox，不可能交给缓存层。
- **库存写入时删除缓存**。没选：秒杀时每秒扣减很多次，每次都删，缓存永远是冷的。
- **逻辑过期**（过期后返回旧值，后台重建）。不阻塞，适合库存。没选：库存的 TTL 只有 1 秒，互斥重建加有上限的等待已经够用。
- **布隆过滤器防穿透**。没选：订单号持续新增，过滤器要持续维护；SKU 数量少，空值缓存足够。
- **本地内存缓存（进程内）**。最快，不依赖 Redis。没选：本阶段先不做多级缓存。因为缓存的数据都不需要失效，以后加一层本地缓存没有障碍。

## 后果

好处：

- 热点库存查询每个 SKU 每秒只回源一次；终态订单的查询不再读库。
- 缓存出错或被清空都不影响正确性，只影响性能。

代价：

- 非终态订单的查询仍然读库。下单后的轮询、支付页的刷新没有被缓存挡住。
- 库存展示最多滞后约 1 秒。
- 多一个 Redis 实例要部署和监控。
- Redis 不可用时所有查询直接落到数据库，在 1d 的限流和熔断完成之前没有保护。

应当重新评估的情况：

- 压测显示非终态订单的查询成了数据库的瓶颈。这时再考虑缓存待支付订单，并接受它的不一致窗口。
- 订单增加了“已支付”之后的状态（发货、退款），终态的定义变了，`PAID` 不能再无条件缓存。
- 需要订单列表查询。列表的缓存和失效是另一个问题。
