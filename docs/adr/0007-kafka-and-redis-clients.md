# ADR-0007：Kafka 客户端用 franz-go，Redis 客户端用 go-redis

- 状态：已采纳
- 日期：2026-11-11

## 背景

1b 引入 Kafka 和 Redis，需要各选一个 Go 客户端。约束：

- 镜像要交叉编译到 `linux/amd64`，最好不依赖 cgo。
- 需要精确控制消费位点的提交时机（处理成功后才提交）和再平衡时的行为，这是“至少一次”语义的基础。
- 学习价值优先：客户端不应把这些机制藏起来。

## 决定

- **Kafka：`github.com/twmb/franz-go` v1.22.3**，管理接口用同仓库的 `pkg/kadm` v1.20.0。
- **Redis：`github.com/redis/go-redis/v9` v9.23.0**。

两者都只在 `pkg/kafkax`、`pkg/redisx` 和少数公共库里直接使用，服务代码通过这些封装访问。

## 备选方案

Kafka：

- **`confluent-kafka-go`**：基于 librdkafka，功能最全、最成熟。依赖 cgo，交叉编译和精简镜像都麻烦，调试时进不到 C 代码里。
- **`IBM/sarama`**：老牌纯 Go 客户端，资料多。接口历史包袱重，消费者组的再平衡处理容易写错，新协议特性跟进慢。
- **`segmentio/kafka-go`**：接口最简单。对位点提交和再平衡的控制较粗，幂等生产者和事务支持不完整。

选 franz-go 的原因：纯 Go；对协议的支持最完整（幂等生产者、事务、增量再平衡）；位点提交、分区暂停与恢复、再平衡回调都有明确的接口，适合自己实现“处理成功再提交”和延迟消费。

Redis：

- **`rueidis`**：性能更好，自带客户端缓存。接口风格特殊，资料少。
- **`go-redis`**：官方维护，事实标准，面试和实际工作中最常见。

Redis 客户端不是瓶颈所在，选最通用的。

## 后果

- franz-go 的接口偏底层，“处理成功再提交”“失败重试”“死信”要自己在 `pkg/kafkax` 里实现一遍。这是代价，也是目的。
- 如果目标岗位明确使用 sarama 或 confluent 客户端，可以只替换 `pkg/kafkax` 的实现，服务代码不用改。

## 补充（2026-11-15）：不用静态成员

评估过给消费者设 `group.instance.id`（取 Pod 名）。结论是不用，实测和理由在设计文档 2c 第 13 节的第七步：

- 现状已经够好：滚动发布时每个分区只停 0.5 到 3.2 秒（增量再平衡加主动离组），停顿的上限是心跳间隔，不是会话超时。
- franz-go 的静态成员关闭时不离组。Deployment 的新 Pod 是新名字，旧成员的分区要等会话超时才交出去，滚动发布反而变慢。
- 它只对“同名的成员在会话超时内回来”有用（容器原地重启、StatefulSet），前者少见，后者我们不用。

放弃的是：进程被杀后原地重启时省掉约 10 秒的等待。
