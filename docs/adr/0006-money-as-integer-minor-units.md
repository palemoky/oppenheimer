# ADR-0006：金额用最小货币单位的整数表示

- 状态：已采纳
- 日期：2026-11-11

本文是补记。这个决定在 1a 动工时就已经执行（`AGENTS.md` 的“金额用整数分，不用浮点”），当时没有写下理由。

## 背景

订单、支付、库存三个服务都要存储、传输和比较金额。金额的表示方式一旦落进表结构、proto 和对外接口，之后改动要同时迁移三处，属于难以回头的决定。

可选的表示有三类：

- 浮点数（`float64`、MySQL 的 `DOUBLE`）。
- 定点小数（MySQL 的 `DECIMAL(p,s)`，Go 里用第三方 decimal 库）。
- 最小货币单位的整数（人民币为分，`int64`、`BIGINT`）。

浮点数直接排除：二进制浮点不能精确表示 0.1，累加会产生误差，金额判等不可靠。真正需要取舍的是后两者，`DECIMAL` 本身是精确的，用它存金额并不算错。

约束：

- 语言是 Go，服务间用 gRPC，对外用 JSON。
- 当前业务只有下单、支付、退款，金额运算只有“单价 × 数量”和求和。
- 订单服务要校验支付金额与订单金额相等，不等则退款（`AMOUNT_MISMATCH`）。

## 决定

金额在存储、服务间传输、对外接口三层都用**最小货币单位的整数**，并且**必须和币种一起出现**。

- **表结构**：`BIGINT` 加 `CHAR(3)` 的币种列，金额列有 `CHECK (amount >= 0)`。
- **proto**：`oppenheimer.common.v1.Money{int64 amount; string currency}`，币种用 ISO 4217 代码。
- **对外 JSON**：`{"amount":1999,"currency":"CNY"}`。
- **运算**：乘法和求和都检查 `int64` 溢出，溢出按内部错误处理（`services/order/internal/service/service.go` 的 `priceItems`）。不同币种的金额不能相加或比较。
- **“分”只是人民币下的说法**，准确的含义是该币种的最小单位。每个币种的小数位数不同（日元 0 位，人民币 2 位，科威特第纳尔 3 位），展示时按币种换算，存储和计算时不关心。

## 备选方案

**`DECIMAL` 加 Go 的 decimal 库（如 `shopspring/decimal`）**，没有选它的原因：

- **Go 没有原生的 decimal 类型**。`DECIMAL` 列读进 Go 只能落到 `string`、`float64`（精度当场丢失）或第三方类型。整数则从数据库到 proto 到 JSON 全程是同一个原生类型，没有转换环节可以出错。
- **proto 没有 decimal 类型**。只能用 `string` 或自定义 message，每个服务都要自己解析和校验。
- **JSON 里的小数有歧义**。`19.99` 会被很多客户端（尤其是 JavaScript）解析成双精度浮点，精度问题从服务端转移到了客户端；用字符串 `"19.99"` 可以避免，但又多了一层解析。
- **判等有陷阱**。`19.9` 和 `19.90` 数值相等但 scale 不同，有的库和序列化格式会把它们当成不同的值。金额校验是整数判等时没有这个问题。
- **性能和内存**：decimal 运算是堆上的大数运算，整数是一条机器指令。在本项目的量级上这不是决定性因素，只是顺带的好处。

**`DECIMAL` 存储，但应用层换算成整数**：两种表示并存，换算点多，没有任何好处。

## 后果

好处：

- 金额的加减和比较都是精确的整数运算，结果在所有语言和平台上一致。
- 三层用同一种表示，没有类型转换。
- 与主流支付接口的惯例一致（Stripe、支付宝、微信支付都用最小货币单位的整数），以后对接真实支付渠道不需要换算。

代价和要注意的地方：

- **除法和比例运算必须显式定舍入规则**。折扣、税、分摊都会产生不足 1 分的余数。例如 100 分摊给 3 个商品，必须做成 33 + 33 + 34，把余数明确分给某一项，保证各项之和等于总额，否则会凭空多出或丢掉 1 分。目前没有这类运算，引入时要单独设计并测试“分摊后求和等于原值”这条不变量。
- **表达不了小于最小单位的金额**。汇率、利率、按量计费的单价（如每次 0.0015 元）不能用分表示。
- **金额离开币种没有意义**。`1999` 可能是 19.99 元，也可能是 1999 日元。所有携带金额的结构都必须带币种。
- **溢出要显式检查**。`int64` 最大约 9.2 × 10^18 分，单笔金额不可能达到，但恶意或错误的输入可以让乘法溢出，所以运算处必须检查。
- **直接看数据库不直观**。`1999` 要心算成 19.99 元，排查问题时注意单位。

出现以下情况时重新评估：

- **引入促销分摊、税费或多币种换算**。做法是在计算层引入 decimal 做中间运算，按明确的舍入规则落到整数最小单位后再入库，存储和接口的表示不变。
- **需要亚分精度的计价**（按量计费、利息）。可以对这类字段单独改用更小的单位（厘、百万分之一元）或 `DECIMAL`，不影响订单和支付金额。
