# ADR-0019：网关用令牌桶限流，按 IP 在进程内、按用户和接口在 Redis 里

- 状态：已采纳
- 日期：2026-11-14
- 相关：ADR-0011（背压）、ADR-0005（规范先行）；设计文档 [1d-protection.md](../design/1d-protection.md) 第 4 节

## 背景

系统唯一会主动拒绝请求的地方是受理端的背压（ADR-0011），它依据的是队列长度，不分来源。一个用户用脚本占满队列，其他人全被拒绝；过快的轮询会和落库抢订单库（1d 步骤一量到，有查询压力时落库只有平时的 75%）。需要在最外层按“谁在调、调什么、多快”来限制。

## 决定

1. **算法用令牌桶**，每个键一个桶，参数是速率和容量。
2. **三个维度**：按 IP、按用户加接口、按接口。
3. **按 IP 的状态在网关进程里；按用户和按接口的状态在 Redis 里**，后两个在一个 Lua 脚本里一次判断，都通过才都扣。
4. **Redis 里的桶用 Redis 自己的时间**，键带过期时间。
5. **Redis 不可用时退回进程内的同一套规则**，不放行也不拒绝；失败后的一小段时间内不再尝试 Redis。
6. **限流的状态放在缓存实例**（`redis-cache`），不放在闸门所在的实例。
7. 被限流返回 429、原因码 `RATE_LIMITED`、带 `Retry-After`，与背压的 `BACKLOGGED` 区分。
8. 进程内的令牌桶自己实现，和 Redis 版同一个算法、同一组测试。
9. 客户端地址只在远端属于 `TRUSTED_PROXIES` 时才取 `X-Forwarded-For`。

## 理由

**为什么是令牌桶。**

| 算法 | 做法 | 问题 |
|---|---|---|
| 固定窗口计数 | 每个时间窗口一个计数器，到窗口边界清零 | 边界上能通过两倍：上一个窗口的最后一刻和下一个窗口的第一刻各打满一次 |
| 滑动窗口日志 | 记下每个请求的时间戳，数最近一个窗口内的 | 精确，但每个键要存和限额一样多的时间戳 |
| 滑动窗口计数 | 当前窗口的计数加上一个窗口的计数按比例折算 | 近似，够用；不能表达“平时慢、允许偶尔突发” |
| 漏桶 | 请求进队列，以固定速率流出 | 输出平滑，但突发要排队等，增加延迟；网关不适合替客户端排队 |
| 令牌桶 | 以固定速率攒令牌，有令牌就过，最多攒到容量 | 允许不超过容量的突发 |

用户连点、超时后立刻重试、页面同时发几个请求，都是正常的突发，应当放过；持续超过速率的才拒绝。令牌桶用两个参数把这两件事分开表达，状态只有两个数。漏桶当计量器用（不排队，只判断）时和令牌桶等价，GCRA 是它只存一个时间戳的写法；选令牌桶是因为它最容易讲清楚，也最容易算出 `Retry-After`。

**为什么按维度分开放。** 进程内和 Redis 各有一个别人没有的性质：进程内的不依赖任何东西，Redis 里的是精确的。按 IP 是第一道闸，必须在 Redis 坏掉时还在，而它的限额本来就宽，实例数倍的误差无所谓。按用户的配额很小，实例数倍的误差就等于没有；按接口的总量保护的是下游，必须全局算。

**为什么两个桶要在一个脚本里。** 分两次调用时，用户的桶扣了、接口的桶拒绝了，这个请求没被处理却消耗了用户的配额；两次调用之间还可能插进别的请求。一个脚本里先都看一遍、都够再都扣，是原子的，也只有一次往返。

**为什么 Redis 坏了要退回进程内。** 放行等于“限流在最需要的时候消失”：Redis 往往是被流量打垮的。拒绝等于给网关加了一个单点。退回进程内，限额变宽（每个实例各算各的）但没有消失，网关也不受 Redis 牵连。

**为什么用缓存实例。** 限流状态的全部要求是“快、丢了无所谓”。闸门实例的要求是“不能丢、不能慢”，把每个请求都加到它上面是在拿下单的可用性换限流的一点点精确。

## 备选方案

- **全部在进程里。** 最简单、没有依赖。多实例下按用户的限额不准；只有一个网关实例时和现在的方案等价。本机就是一个实例，但这一步要学的正是多实例时怎么办。
- **全部在 Redis 里。** 一套实现。按 IP 的限流会依赖 Redis，洪水来时每个请求一次往返，Redis 先垮。
- **在网关前面的代理上限流**（Nginx 的 `limit_req`、Envoy 的本地和全局限流）。生产上很常见，按 IP 的那一层放在那里更合适。本项目没有这一层，阶段 2 上 Ingress 时可以把按 IP 的挪过去；按用户、按接口的需要懂业务（用户是谁、接口是哪个），留在网关。
- **用 `golang.org/x/time/rate`。** 它是单个桶，按键管理和淘汰要自己写；和 Redis 版的行为对齐靠不了它。
- **用 sentinel-go 做网关限流。** 它是步骤三要引入的，侧重熔断和热点参数。它的集群限流需要单独的 token server。这一步先把算法自己做一遍。
- **把限额除以实例数、全部在进程里。** 实例数变化时要重新配，流量在实例间不均匀时不准。
- **Redis 用时间戳由网关传入。** 少一次 `TIME` 调用。各实例时钟不一致时补充速率会偏。

## 后果

- 网关新增一个依赖（缓存 Redis）和每个请求一次往返（本机约 0.1 到 0.3 毫秒）。
- 多了一种 429。客户端要区分 `RATE_LIMITED`（自己太快）和 `BACKLOGGED`（系统忙）。
- 压测、杀进程测试、e2e 都是从一个地址用很多用户号发请求，默认的限流会把它们限住，这些脚本要显式地关掉相应的维度。忘了关时现象是“吞吐突然上不去”，容易误判成性能问题。
- 按用户限流建立在可以伪造的 `X-User-Id` 上，在有认证之前只对守规矩的客户端有效。
- 限额是静态配置，改它要重启网关。
- Redis 不可用期间，按用户和按接口的限额实际放大到实例数倍。

## 补充：Redis Cluster 下按桶逐个调用（2026-11-15）

阶段 2b 把限流的桶放到了 Redis Cluster 上（设计文档 2b 第 4 节）。原来的做法是一次请求的几个桶（按接口、按用户）在同一个脚本里处理，要么各扣一个令牌，要么一个都不扣。Cluster 下一个脚本只能访问同一个槽里的键，这几个桶的键名不同，落在不同的槽。

决定：客户端是 Cluster 时，每个桶单独调用一次脚本，按调用方给的顺序，遇到第一个拒绝就停（`pkg/ratelimit` 的 `Redis`，按客户端的类型自动选择）。单节点和主从下行为不变。

放弃了什么：

- **“一个都不扣”的保证。** 前面的桶放行并扣了令牌，后面的桶拒绝时，前面的令牌白扣。限流因此在拒绝时略微偏严，不会偏松。
- **一次往返。** 变成最多“桶的个数”次，目前是 2 次。Redis 的时限（默认 20 毫秒）是整次判断的，不是每次调用的。

没有选的做法：

- **用 hash tag 把几个桶绑到同一个槽。** 做不到：同一个用户的桶要被他所有的请求共用，键名不能跟着某一次请求的接口变。
- **限流不上 Cluster，和库存闸门共用主从那一套。** 违背上面“用哪个 Redis”的决定：限流的流量不能压到闸门的 Redis 上。
- **先只读地检查所有桶，都够再逐个扣。** 检查和扣之间不是原子的，并发下照样会出现白扣，还多一倍往返。
