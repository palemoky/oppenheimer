# ADR-0008：用本地消息表（outbox）加 Kafka 做服务间的最终一致

- 状态：已采纳
- 日期：2026-11-11

## 背景

服务完成一次状态变更后往往要通知别的服务：订单支付成功要让库存确认预占，支付出了结果要让订单推进状态。“改自己的库”和“通知别人”不在同一个事务里，中间任何一步失败都会留下不一致。

1a 的做法是每个服务在自己的表里放一个标志位（`orders.stock_settled`、`payments.notified`），先在线同步调用一次，失败了由后台任务扫描标志位重试。它是正确的，但有三个问题：

- 每种通知都要单独设计标志位、扫描索引和重试逻辑，三个服务写了三套。
- 发布方必须知道订阅方是谁、怎么调用。新增一个关心“订单已支付”的服务要改订单服务。
- 在线路径上有对下游的同步调用，下游慢会拖慢上游。

不使用 XA 这类跨库分布式事务是项目的既定约束（见 `AGENTS.md`）。

## 决定

采用 **outbox 模式**：

1. 业务变更和“要发布的事件”在同一个本地事务里写入。事件写进本库的 `outbox` 表。
2. 每个服务有一个中继（relay），把 `outbox` 里未发布的行发到 Kafka，发送成功后标记。
3. 订阅方从 Kafka 消费，按至少一次投递来设计，自己保证幂等。
4. 中继靠轮询 `outbox` 表发现新消息，事务提交后在进程内主动唤醒一次以降低延迟。

消费端幂等一律用**业务唯一键**实现（预占记录以 `order_id` 为主键、支付结果以 `payment_id` 为主键、状态转换带前置条件），不建通用的去重表。

细节见 `docs/design/1b-high-concurrency.md`。

## 备选方案

- **先提交事务，再直接发 Kafka**：提交后、发送前进程崩溃，事件就丢了。只能再加一个补偿扫描，又回到了标志位方案。
- **先发 Kafka，再提交事务**：事务回滚的话，等于通知了一件没发生的事。
- **事务消息（RocketMQ 的做法）**：先发“半消息”，本地事务提交后再确认，broker 会回查未确认的消息。不需要 outbox 表和中继，但需要消息中间件支持，Kafka 没有这个能力（Kafka 的事务解决的是“消费、处理、再生产”的原子性，不是数据库和消息之间的）。
- **CDC（读 binlog 发事件）**：不用轮询，延迟更低，业务代码甚至不用写 outbox。需要额外部署和运维一套 CDC。1c 会实现 CDC，届时可以用它替换轮询中继做对比。
- **通用去重表（消费者记录处理过的事件 id）**：对没有天然业务键的消费逻辑是必须的。目前每个消费逻辑都有业务键，再加去重表是多一次写入和一张要清理的表。出现没有业务键的消费逻辑时再引入。
- **Saga 编排器**：由一个中心服务驱动各步骤并在失败时调用补偿。流程多、步骤长时更清晰。现在的流程只有两三步，各服务订阅事件各自反应（协同式 Saga）就够了。

## 后果

好处：

- “状态变了”和“事件会发出去”由本地事务保证原子，不再有需要逐个论证的窗口。
- 发布方不知道也不关心谁在订阅。
- 在线路径不再同步调用下游做结清，下游不可用只会让事件积压，不影响上游。
- 无法处理的消息进死信 topic，等价于 1a 里“保持未结清等人工介入”，但有了统一的位置。

代价：

- 一致性从“在线调用成功时立即一致”变为**始终最终一致**。订单已支付到库存显示已售之间有一小段延迟，读接口和测试都要接受这一点。
- 每次状态变更多写一行 outbox，多一个中继组件，表需要定期清理。
- 中继靠轮询，空闲时也在查库。
- 事件一旦发布就是契约，改动要考虑兼容。
- 至少一次投递把幂等的责任交给了每个消费者，漏掉一个就是重复扣减或重复退款。

重新评估的时机：1c 实现 CDC 之后，对比两种中继方式；出现需要多步补偿、各步有先后依赖的流程时，评估编排式 Saga。
