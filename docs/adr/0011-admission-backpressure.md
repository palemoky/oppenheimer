# ADR-0011：异步下单的受理端按队列长度做背压

- 状态：已采纳
- 日期：2026-11-12
- 相关：设计文档 [1b-high-concurrency.md](../design/1b-high-concurrency.md) 6.4、6.4.1、7.3.4

## 背景

1b 的下单分两段：网关受理（Redis 闸门预扣，返回 202），order 消费 Kafka 消息落库。中间的队列就是闸门里“已受理、未认领”的占用。回收任务把超过宽限期（默认 1 分钟）仍未认领的占用当成孤儿还掉，因为它分不清“消息没发出去”和“消息排在很后面”。

步骤四的压测里，受理约 4900 单/秒，落库约 400 单/秒。30 秒的峰值排出约 5 分钟的积压，排在后面的订单还没落库就被回收：用户拿到 202，之后查询是 404。

## 决定

闸门的 `Hold` 脚本在库存和限购检查之后、任何修改之前增加两项检查，任何一项不满足就拒绝受理，返回 `RESOURCE_EXHAUSTED`（HTTP 429，原因码 `BACKLOGGED`）：

1. 未认领的占用数达到 `ADMIT_MAX_QUEUE`（默认 1 万，约等于本机落库吞吐乘以 25 秒）。
2. 排队超过 `ADMIT_MAX_WAIT`（默认宽限期的一半）的占用多于 `ADMIT_MAX_STALE`（默认 100）个。

3. （2026-11-13 补充）落库已经超过 `ADMIT_MAX_WAIT` 没有动静时，未认领的占用数超过 `ADMIT_MAX_STALE`。“动静”由 `Claim` 记下的心跳（`gate:claim_at`）判断，占用不存在的 `Claim` 也算。

### 为什么补第 3 条

评审发现第 2 条在落库完全停住时会失效。它数的是“排队超时的占用”，而回收任务会在宽限期后把这些占用还掉，计数随之降回阈值以下，受理重新打开。新受理的订单再排到超时、再被回收，如此循环：消费者停多久，用户就持续拿到 202 然后订单消失。问题在于背压的信号存放在会被回收任务清掉的数据里。

第 3 条的信号是消费者自己留下的，回收任务碰不到。落库没有动静时只放进最多 `ADMIT_MAX_STALE` 个订单作为探测：消费者活着就会认领它们并刷新心跳，之后恢复正常；消费者停着，每个宽限期最多损失这么多订单。这和熔断器的半开状态是同一个思路，区别是不需要单独的状态，心跳的新旧就是状态。

## 考虑过的方案

- **只看最老订单的排队时长**（第一版的做法）。压测证明不够：最老的订单排到阈值时，后面已经排了几分钟的量。它衡量的是过去的等待，新订单的等待取决于队列长度除以处理速率（利特尔定律）。保留它，是用来发现“队列不动了”（落库停住）。
- **按认领速率自适应**（等待 = 长度 / 最近的认领速率）。更准，但冷启动时速率为零、速率抖动、要多维护一组计数器。现在落库吞吐稳定，静态上限够用，代价是落库吞吐变化时要手动调。
- **让宽限期跟着积压变长，或者回收前检查消费进度**。前者把“孤儿多久被发现”变成了不确定的值；后者要在占用里记下消息的位点，回收时查询消费者组，改动大，而且积压本身仍然无限增长。
- **按 Kafka 消费积压（lag）限流**。要在受理路径上查询 Kafka 或定期采样，引入新的依赖；lag 是条数，换算成时间仍要知道速率。闸门里的队列和回收任务看的是同一个东西，用它最直接，而且检查和写入在一个脚本里原子完成。
- **触发后锁存，直到有 `Claim` 才解除**（针对第 3 条要解决的问题）。锁存之后如果 Kafka 里已经没有待消费的消息，就没有 `Claim` 来解除，受理永久关闭；给锁存加过期时间又回到了周期性放行。要补上探测名额才完整，那就是一个显式的三态熔断器，比比较一个时间戳复杂。
- **消费者定时写心跳，不依赖 `Claim`**。信号更准，空闲之后的第一批订单不会被限制在探测名额内。但要在 `kafkax` 的消费循环里开口子，而且“在轮询”不等于“在落库”。探测名额只影响空闲后最初的几十毫秒，先不做。
- **在网关排队而不是拒绝**。只是把队列从 Kafka 挪到内存，请求挂着还占连接。秒杀场景下明确告诉用户稍后重试更好。

## 后果

- 已受理的订单在落库正常时不会再被回收。压测验证：同样的负载，受理 3.2 万、落库 3.2 万，零回收，积压 25 秒排空。
- 峰值期间一部分用户会收到 429。这是削峰本来的含义：系统只接它处理得了的量。
- `ADMIT_MAX_QUEUE` 和落库吞吐绑定，落库优化（1d）之后要重新设定。
- 消费者完全停住超过宽限期时，已经在队列里的订单仍会被回收，这是 6.4 设计内的结果。停住期间每个宽限期还会再损失最多 `ADMIT_MAX_STALE` 个探测订单。
- 空闲超过 `ADMIT_MAX_WAIT` 之后的突发流量，在消费者认领第一个订单之前只能放进 `ADMIT_MAX_STALE` 个，其余收到 429。这段时间是消费一条消息的延迟，通常几十毫秒。
- **第 3 条只管“完全停住”，管不了“活着但落不了库”**。心跳说明的是消费者在取消息，不是订单在写进数据库。下面几种情况心跳一直是新的，第 2 条触发、回收、重新放行的循环仍会出现，只是慢一些：
  - 多个分区里只有一部分停住，其余分区的认领让心跳保持新鲜（心跳是全局一个，不分分区）。
  - 落库极慢，每个 `ADMIT_MAX_WAIT` 内仍有一两次认领。
  - 认领成功但随后写库失败（MySQL 不可用），消息重试后进死信，下一条消息照样认领。

  要覆盖它们，信号得改成“最近是否有订单被回收”或按分区统计，留到 1d 做落库优化和对账时一并处理。
- 探测名额实际是 `ADMIT_MAX_STALE + 1`：判断用的是“超过”，这样取 0 时仍能放进一个探测订单，不会因为没有心跳而永远关闭。
- `ADMIT_MAX_STALE` 有了两个含义：容忍的排队超时个数，和落库没有动静时的探测名额。两者都是“愿意拿去冒险的订单数”，暂时共用一个值。
