# ADR-0015：成倍扩容用从库提升，切换时改表名做围栏；库数由配置决定并由库内元数据校验

- 状态：已采纳
- 日期：2026-11-14
- 相关：ADR-0012（本文修改其中第 4 条）、ADR-0013、ADR-0014；设计文档 [1c-sharding.md](../design/1c-sharding.md) 第 5 节

## 背景

ADR-0012 定了 8 个 slot、2 个库、`db = slot % 库数`，并预告成倍扩容可以用“从库提升为新主库、两边各删一半”来做。1c 步骤四要把这件事实际做一遍：在有数据、有流量的情况下从 2 个库扩到 4 个。

要回答三个问题：数据怎么搬；切换的那一刻怎么保证一个 slot 只有一个库在接受写入；同一份代码怎么既能跑 2 个库也能跑 4 个库，而不重新引入 ADR-0012 想避免的“改个配置数据就找不到了”。

## 决定

1. **数据靠 MySQL 复制搬。** 每个旧主库挂一个新从库，追平后切断复制并提升。应用不写搬数据的代码。
2. **切换时在旧主库上把要搬走的表改名（`orders_2` 改为 `moved_orders_2`），作为围栏。** 改名是原子的、只改元数据，它提交的那一刻就是新旧归属的分界。之后按旧路由来的读写得到“表不存在”，不会写到错的库。
3. **放开新库的写入之前等三件事**：新库执行到围栏的 GTID；旧库的 outbox 发完；旧的 CDC 源越过围栏的 GTID。
4. **库数等于 `MYSQL_DSNS` 的个数**，不再是常量（修改 ADR-0012 第 4 条）。slot 数仍是常量。
5. **每个库有一张 `shard_meta` 表**，记录本库的序号、总库数和持有的 slot。order 启动时逐库核对，不符就拒绝启动。
6. **映射规则不变**，仍然是取模，不引入显式的 slot 到库的映射表。搬迁中的 slot 表现为暂时不可用。
7. **接受被搬的 slot 有几秒到十几秒不可读写。** 已受理的订单在 Kafka 里等，切换后落库。

## 备选方案

- **双写加回填。** 应用同时写新旧两个库，后台把历史数据补到新库，校验一致后把读切过去，再停掉旧库的写。不需要数据库层面的复制，可以用于任意的重新分片（不限于成倍）。代价是双写不是原子的，两边会不一致，要靠对账修；回填和在线写入会更新同一行，要处理先后（本项目有行版本号，能做）；应用里长期带着一套迁移期的代码。成倍扩容用不着这么重。
- **用现成的 CDC 搬。** 步骤三的 CDC 已经能把订单的变更按行版本号幂等地发出来，再写一个消费者落到新库就是一条在线迁移的管道，同样不限于成倍扩容，拆表（8 个 slot 变 16 个）时也能用。没选是因为这一次是整表搬，MySQL 自己的复制更快、更省事，还顺带保证了事务边界。拆表时应当重新考虑这个方案。
- **停机导出导入。** 最简单，停机时间和数据量成正比。
- **先停 order 再切，不立围栏。** 单实例下是对的：进程没了自然没有写入。多实例滚动升级时，新旧两种路由并存，旧实例会把搬走的 slot 继续写进旧库。围栏的成本只是一条 `RENAME TABLE`，没有理由留着这个隐患。
- **在应用里给 slot 加“冻结”状态**（路由表带版本，切换时先把 slot 标成只读，所有实例确认后再切）。这是不停机切换的常见做法，需要一个配置中心和“所有实例都已生效”的确认机制。本项目现在没有配置中心；改表名在数据库这一层达到了同样的互斥，而且不依赖每个实例都听话。
- **库数保持常量，扩容时改代码重新发布。** 那样 CI 和 e2e 也得跟着跑 4 个库（多 4 个 MySQL 容器），或者为演练维护一个分支。
- **显式的 slot 到库的映射表**（配置或存在库里）。能表达“只搬一个 slot”这种非成倍的布局。现在的需求用不上，多一份要保持一致的状态；`shard_meta` 已经记下了每个库实际持有哪些 slot，以后要改成显式映射，数据是现成的。

## 后果

- 扩容的数据搬迁量和停顿都可以预先算出来：每个旧库搬走一半，停顿与数据量无关，取决于复制延迟、outbox 和 CDC 追上的时间。
- 切换期间被搬的 slot 上的请求会失败。落库的消费者必须把“表不存在”当作可重试的错误；这一点成了正确性的一部分，要有测试守着。
- 切换完成（新库开始接受写入）之后不能回退，只能向前修。想保留回退要在切换后立刻建反向复制，没有做。
- 迁移必须可重入：新库是从旧库的拷贝改出来的，没有 goose 的版本记录，所有迁移会在它上面重跑一遍。
- 提升出来的新主库上，库名和它的序号对不上（拷贝来的是 `order_db_0`）。靠同实例内跨库的 `RENAME TABLE` 把表挪进 `order_db_2`，再删掉旧库名下剩下的东西。
- 新库在 CDC 看来是一个全新的源，要做一次全量。行版本号在行上而不是从日志位置派生（ADR-0014），所以换了库之后版本仍然可比，重发的行被下游跳过。
- 配置错误（DSN 顺序、个数）从“悄悄写错地方”变成“启动失败”。`shard_meta` 是新增的、必须和实际数据保持一致的状态，只允许迁移和扩容工具改它。
- 只支持成倍扩容，8 个 slot 最多 8 个库，与 ADR-0012 相同。
- 多个 order 实例滚动切换时的表现（旧实例对被搬的 slot 报错，直到被替换）在阶段 2 验证。
