# ADR-0017：消费者在分区内按 key 并发，提交连续前缀

- 状态：已采纳
- 日期：2026-11-14
- 相关：ADR-0007、ADR-0008、ADR-0011；设计文档 [1d-protection.md](../design/1d-protection.md) 第 2 节

## 背景

`pkg/kafkax` 的消费者一个分区一个 worker，一条处理完才取下一条。吞吐上限是“分区数 ÷ 单条耗时”。订单落库每条约 10 毫秒、4 个分区，上限约 400 单/秒，此时 MySQL 和 inventory 都很空闲；商家索引的消费者同样的结构，约 2000 行/秒，一次归档要追几十分钟。

瓶颈不在任何资源上，在消费的结构上。

## 决定

1. **`ConsumerConfig.Concurrency`**：一个分区内开 N 条 lane，消息按 `hash(key) % N` 分到 lane，lane 内串行。默认 1，行为与现在相同。
2. **提交的位点是最小的未完成偏移量**（没有在途消息时是最后分发的偏移量加一）。不提交任何“前面还有没做完的”偏移量。
3. **在途窗口**：分发的偏移量领先最小未完成偏移量超过窗口（默认 1024）时停止分发。
4. 重试和死信在 lane 内进行，语义不变。延迟消费者不允许并发。
5. 只给 key 之间确实互不相干的消费者开：order 的落库、orderindex。inventory 不开。
6. 商家索引先用并发消费，不做按批写；达不到目标再做。

## 理由

**为什么不直接加分区。** 加分区是 Kafka 自己的并行手段，不用写代码，而且能把负载分到多个实例上。但它解决的是另一个层面的问题：

- 分区数是 topic 的属性，只能加不能减，加了之后 key 到分区的映射会变，同一个订单的新旧消息可能落在不同分区、被不同的 worker 并发处理。本项目的 handler 不依赖顺序，能承受，但这是一次性的、不可逆的运维操作。
- 要把 400 提到几千，需要几十个分区；每个分区都有 broker 上的开销，消费者组的再平衡也随分区数变慢。
- 分区数应当由“要分给多少个实例”决定，而单个实例内部的并行度由“下游能承受多少并发”决定。把两件事绑在一个数上，调其中一个就动了另一个。

本机只有一个 order 实例，缺的是实例内的并行度。到阶段 2 有多个实例时，分区数按实例数来定，两者相乘。

**为什么按 key 分 lane，而不是协程池。** 协程池里同一个订单的两条消息可能同时被处理，每个 handler 都得自己处理并发（现在靠行锁能扛住，但延迟关单、取消和落库之间的先后就全交给数据库了）。按 key 分 lane 保留了“同一个 key 串行”这条现在所有 handler 都默认的前提，改动只在消费者内部。

**为什么提交连续前缀。** Kafka 的位点是一个数，不是一个集合。提交 8 的含义是“0 到 7 都处理完了”。乱序完成时只有连续的前缀能这样说。代价是前缀之后已完成的消息在重启后会重做，这要求 handler 幂等，本项目从 1b 起就是这样设计的。

**为什么要窗口。** 没有窗口时，一条卡住的消息会让“已处理未提交”的部分无限增长：其他 lane 一直在处理，位点一直提交不了，重启后全部重放，内存里的完成表也无限长。窗口把最坏情况限定为重放 1024 条，并在超过后让分区停住，和现在“一条卡住、分区停住”的行为一致。

## 备选方案

- **加分区。** 见上。
- **不分 lane 的协程池加连续前缀提交。** 实现少一步分发，吞吐一样。丢掉了同 key 串行。
- **按批处理**（handler 一次收一批，自己决定怎么并行或合并成一条多行语句）。对“写一行”类的消费者上限最高（商家索引一条多行 upsert 能写几百行）。对落库没有用：落库的耗时在每个订单各自的 Redis、gRPC 和事务上，合不成一条语句。要给 kafkax 增加第二种 handler，批内的部分失败和同 key 多版本的合并都要定义。留作商家索引达不到目标时的下一步。
- **落库不走消费者，受理时直接异步写库。** 回到了 1a 的结构，丢掉了削峰。
- **用现成的并行消费库**（Confluent 的 parallel consumer 只有 Java）。Go 生态里没有被广泛使用的等价物；这段逻辑也是要学的内容。

## 后果

- 重复投递变得常见：每次重启、每次再平衡，窗口内已完成的消息都可能重做。幂等从“应对偶发”变成“每次部署都在用”。
- 消费延迟（lag）的含义变了：已提交位点可能落后于实际处理进度最多一个窗口。按 lag 告警时要留出这个余量。
- 一个分区同时占用的下游资源从 1 变成 N。并发度要和连接池、下游的并发限制一起定，不能单独调大。
- 同一个 key 的顺序保证依赖 key 选得对。新增消费者开并发之前要确认：它处理一条消息时碰的数据，是否只属于这个 key。inventory 是反例（key 是订单，碰的是 SKU）。
- 一条 lane 被一条慢消息拖住时，哈希到同一条 lane 的其他订单也在等，不只是它自己。落库的重试上限约 26 秒，并发度 8 时这个分区约八分之一的订单的落库会被拉长到这个量级（仍在回收宽限期之内）。并发度越大，受连累的比例越小。
- **不同 key 之间原来“碰巧有”的先后没有了。** 例子：同一个用户用同一个幂等键先后受理了两个订单（幂等键在 Redis 里过期后的重放），落库时靠数据库的唯一键只留一个。以前两条消息在同一个分区时，按位点一定是先受理的那个赢；并发之后谁先插入谁赢，先受理的那个订单号可能变成不存在。跨分区时以前就是这样，所以不是新的行为，只是从少见变成了常见。两种结果都满足“一个幂等键只有一个订单”。
