# ADR-0021：闸门不可用时拒绝下单而不退回数据库扣减；依赖不可用时消息不进死信；就绪和存活分开

- 状态：已采纳
- 日期：2026-11-14

## 背景

1d 步骤三之后，一个依赖坏了不会再把调用方拖死（时限、并发上限、Envoy 的熔断）。但依赖坏着的时候系统怎么表现，没有设计过，读代码得出的现状有几个问题（设计文档 1d 的 6.1）：

- 闸门所在的 Redis 不可用超过约 26 秒，已受理、还在排队的订单进死信，Redis 恢复后占用被回收，订单消失。
- inventory 不可用时受理照常返回 202，这些订单随后失败或被回收；背压要约 30 秒才开始拒绝。
- Redis、从库、冷库任何一个在启动时连不上，order 就起不来，尽管运行中它们坏了都能降级。
- Redis 和 MySQL 不经过边车，坏掉时每个请求都要先等满一次超时。
- 没有摘流：收到 SIGTERM 立刻停止接新请求；只有存活探测，没有就绪探测。

阶段计划里这一项原来写的是“Redis 不可用时退回数据库扣减并收紧限流”。

## 决定

1. **闸门的 Redis 不可用时，拒绝新的下单，其余接口照常。** 不退回数据库扣减。已受理的订单留在 Kafka 里，Redis 恢复后继续落库。
2. **不受理落不了库的订单。** order 按订单库记录落库是否在持续失败（inventory 调不通、订单库写不进去），是的话在受理时就拒绝。
3. **依赖不可用时消息留在分区里重试，不进死信。** 落库、订单事件的消费者对普通错误不设重试上限；死信只收 handler 明确标成 `Permanent` 的消息。
4. **边车看不到的依赖在进程里熔断**（`pkg/breaker`：连续失败打开、冷却后半开、半开只放一个探测），用于闸门、缓存、冷库。从库用主动探测（主库的 GTID 位置，从库在限定时间内能否追上）。
5. **可选依赖不挡启动。** 启动失败只因为自己的主库和 Kafka。
6. **非核心功能有开关**（`pkg/degrade`），和自动降级走同一条代码路径；通过服务内部的端口在运行中修改，只在本进程生效。
7. **就绪和存活分开，依赖降级不影响就绪。** 停止时先变成未就绪，等 `DRAIN_DELAY`，再停各组件。

## 理由

**为什么不退回数据库扣减。** 见设计文档 6.4，要点：

- 退回期间闸门里的数是旧的，切回来要重新装载，还要处理恢复的 Redis 里残留的占用，做错就是超卖。
- “Redis 不可用”是每个实例各自的判断，部分实例退回、部分不退回时同一份库存卖两次；要一致就需要一个全局的模式开关和围栏。
- ADR-0018 之后 MySQL 不再阻止超卖，退回要把同步扣减重新接回来。
- 同步扣减的容量是每秒几百单，秒杀时绝大多数请求仍然被拒绝。
- Redis 的主从切换能把不可用压到十几秒以内，为这个窗口维护第二条扣减路径不划算。

**为什么消息不进死信。** 死信的用处是把坏消息挪开，让分区继续。依赖不可用时每条消息都会失败，挪开一条没有用，后面的照样失败；全部挪进死信之后，一次会自己恢复的故障变成了要人逐条重放的数据问题，而重放之前的这段时间数据是不一致的（闸门里的占用没人归还）。落库的消息不需要死信收尾：订单行写进去的由 sweeper 置为失败，没写进去的占用会被回收，两种情况下重试都会自己结束。

**为什么依赖降级不影响就绪。** 共享的依赖坏了，所有实例同时未就绪，负载均衡把它们全部摘掉，本来还能提供的功能也没了。就绪只表达这个进程自己的状态。

**为什么按连续失败熔断。** 这些依赖坏起来是整体坏，连续失败很快就能数到；和 Envoy 的判断方式一致。按比例的判断要滑动窗口，针对的是部分失败，现在没有遇到。

## 备选方案

- **自动退回数据库扣减**（原计划）。上面的前两个问题没有便宜的解法。
- **人工的全局开关切到数据库扣减。** 切换预案：停受理、等队列排空、把模式写进 MySQL（所有实例轮询，带版本号）、inventory 的 `Reserve` 改成先应用增量再做条件更新；切回时先按 MySQL 重新装载闸门再放开。能解决一致性问题，适合 Redis 长时间（小时级）不可用。要多维护一条扣减路径和一套切换流程，这个项目里 Redis 长时间不可用不是要演练的场景。主人想做的话可以作为单独的一步。
- **消费者按错误类型决定是否计入重试次数**（给 `kafkax` 加一种“依赖不可用”的错误标记）。能保留“没识别出来的坏消息最终进死信”这层保护。但要枚举哪些错误算依赖不可用（驱动、Redis、gRPC 各有各的错误），漏掉一种就是把一条正常的消息送进死信；涉及资金和库存的消息宁可挡住分区。handler 已经把消息本身的问题标成 `Permanent` 了，反过来分类更安全。
- **熔断器用现成的库**（failsafe-go、gobreaker）。功能更全（错误比例、慢调用）。这里需要的只有连续失败和半开的单个探测，约 150 行；状态机本身是面试考点，自己写一遍有价值。
- **从库延迟看 `Seconds_Behind_Source`。** IO 线程断开或落后时它不反映真实延迟。
- **就绪探测检查依赖。** 见理由。
- **开关放在 Redis 或 MySQL 里全局生效。** 开关要在依赖坏掉时用，不能依赖 Redis；放 MySQL 要轮询。本机单实例用不上，阶段 2 有 ConfigMap。

## 后果

- **闸门的 Redis 是下单的单点。** 它不可用期间完全不能下单。可用性要靠 Redis 自己的高可用（阶段 2）。
- **Redis 故障超过半个宽限期（30 秒）时，故障前排队的订单仍然可能赶不上**：恢复后落库的消费者和回收任务有一段等待，但支付时限是从受理时算的，故障时间会吃掉支付窗口；超过支付时限的直接失败。
- **一条没被识别的坏消息会一直挡住它的分区。** 只能靠消费积压的告警发现（阶段 3）。在那之前要看日志里持续重试的 WARN。
- **落库健康是每个实例自己的判断。** 没有分到分区的实例不会拒绝受理，兜底的是闸门里的背压。
- **降级状态现在只能从日志和 `GET /degrade` 看到**，没有指标和告警（步骤六、阶段 3）。
- **开关不持久、不全局。** 重启后回到环境变量的值，多实例要逐个改。
- **`DRAIN_DELAY` 本机是 0。** 摘流的等待在单实例下验证不了，阶段 2 才能看到效果。
- 阶段计划里“Redis 不可用时退回数据库扣减”这一条改为“拒绝下单”，ADR-0018 后果一节里预留的同步 `Reserve` 模式不做。

## 补充（2026-11-14）：闸门的熔断器要失败持续 1 秒才打开，查询读闸门有单独的份额

压测加指标之后发现两件事（设计文档 1d 的 8.18）：

- 查询（客户端轮询）把闸门的 Redis 连接池占满，别的调用在池子上排队超时，被算成闸门的失败。
- 一次约 300 毫秒的停顿让在途的十几个调用同时失败，“连续 5 次”一下就满足，熔断器打开 5 秒，落库跟着停 5 秒。

改动：

1. 展示读读闸门占用之前先占名额（`READ_GATE_MAX_CONCURRENCY`，默认 16），占不到就只读订单行，不经过熔断器。闸门的连接池可配置（`REDIS_POOL_SIZE`），默认 128。
2. `pkg/breaker` 增加可选的 `MinFailureSpan`：连续失败达到次数之外，还要持续这么久才打开。闸门的熔断器用 1 秒，其他熔断器不变。

理由：熔断器要回答的是“依赖是不是坏了”。本地排队造成的超时和一次性的抖动都不是，把它们算进去，保护机制自己就成了故障的放大器。代价是 Redis 真的不可用时，熔断器晚 1 秒打开，这 1 秒里每个调用各自等满 300 毫秒的时限。

没有选的做法：把冷却从 5 秒缩短（仍然会打开，只是每次停得短一些）；改成按一段时间里的错误比例熔断（更准，但要维护滑动窗口，现在的问题用一个时间条件就够）。
