# ADR-0013：读写分离按“展示读走从库”划分，读己之写用写前标记加 GTID 等待

- 状态：已采纳
- 日期：2026-11-13
- 相关：ADR-0002、ADR-0012；设计文档 [1c-sharding.md](../design/1c-sharding.md) 第 3 节

## 背景

1c 的步骤二给每个订单分片加一个从库。从库是异步复制的，读它可能读到旧数据。要决定两件事：哪些读可以走从库；用户刚写完就读时怎么保证看到自己的写。

订单的查询有一个特殊之处：订单落库前靠 Redis 里的占用合成，走到终态后占用被归还。从库落后时，一个已经完结的订单会既没有占用、从库里也没有行，查询返回 404。所以这里读到旧数据不只是“晚一点看到”，而是“订单消失”。

## 决定

1. **按用途划分，而不是按语句类型**。只用来展示的读（对外的 `GetOrder`）和只用来找候选的扫描（sweeper）走从库。结果会成为某个决定或某次写的前提的读，全部走主库。`store` 用不同的方法名区分，不做透明路由。
2. **读己之写靠写的一方留标记**。写之前在 Redis 里给订单打标记，`GetOrder` 读从库前先看标记，没有标记才直接读从库。
3. **两种标记都实现，用配置切换**：固定时间窗口内读主库（`window`）；记下提交后的 GTID 集合，读的时候在从库上等它追上，超时读主库（`gtid`）。另有 `primary` 模式一律读主库，作为对照和退路。
4. **任何不确定都退回主库**：从库出错、等待超时、读标记失败。
5. **“订单不存在”只由主库说了算**：从库和闸门里都找不到时，再读一次主库才能答 404。标记只负责状态的新旧，不负责订单是否存在。
6. **GTID 标记只往前更新**：连同主库的时间一起记，Redis 里只接受更晚读到的那个，防止交错的两次写用旧位置盖掉新位置。

## 考虑过的方案

- **透明的读写分离**（中间件或驱动层按 `SELECT` 和非 `SELECT` 路由）。应用代码不用改，但事务里的读、写后马上的读、用来做决定的读都会被送到从库，要再用注解或提示一条条拉回来。哪些读能容忍旧数据是业务知识，放在方法名上比放在路由规则里清楚。
- **只用时间窗口**。实现最简单，也是很多系统的做法。问题是窗口靠猜，延迟超过窗口就失效，而延迟变大恰恰是出故障的时候。保留它是为了对比。
- **把 GTID 交给客户端**（写的响应里带回位置，读的时候带上）。服务端不用存任何状态，也不依赖 Redis。但要改对外接口，而且订单的状态变更有一半不是用户的请求触发的（落库、支付结果、超时关单），客户端拿不到那些写的位置。
- **按用户而不是按订单打标记**。一个标记能覆盖这个用户的所有订单，对以后的订单列表有用。现在只有按订单号的查询，按订单更精确，读主库的范围更小。做列表时再评估。
- **提交之后再打标记**。少一次 Redis 写（`gtid` 模式下只写一次）。但“已提交、标记未写”时崩溃会留下一个没有标记保护的订单。写前标记把这个缺口换成了“写失败时白打一次标记”。
- **用 `session_track_gtids` 取本次事务的 GTID**。比读整个 `gtid_executed` 精确，也省一次查询。go-sql-driver/mysql v1.10.1 没有暴露应答里的会话状态，要换驱动或改驱动，不值得。
- **半同步复制**。它解决的是主库宕机时不丢已提交的事务，不解决读到旧数据：从库收到日志不等于已经应用。

## 后果

- 每次订单写入多一次 Redis 写；`gtid` 模式再多一次主库查询和一次 Redis 写。落库是当前的吞吐瓶颈，代价要实测后写进笔记。
- 读己之写依赖 Redis。Redis 不可用时读全部退回主库，主库的读压力回到分离之前。
- 写的一方打标记失败时仍然继续写，这时随后的读可能是旧的。这是有意的：不让 Redis 的抖动拒绝业务写入。
- 标记过期之后从库仍然落后，读到的还是旧数据。`gtid` 模式下标记保留 1 分钟，延迟超过 1 分钟才会出现；这种程度的延迟应当由监控发现并把读切回主库（1d 的降级）。
- sweeper 读从库后，超时关单的兜底会晚一个复制延迟。主路径是延迟消息，影响小。
