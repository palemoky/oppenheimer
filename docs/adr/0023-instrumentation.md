# ADR-0023：埋点的几个取舍：链路过 outbox 靠表里的一列，异步一跳以父子为主，指标走 OTLP

- 状态：已采纳
- 日期：2026-11-14

## 背景

ADR-0004 定了“业务代码只依赖 OpenTelemetry，统一用 OTLP 上报”，没有定怎么埋。1d 步骤六动工时有四件事要定（设计文档 1d 第 8 节）：本机用什么看；链路怎么穿过 outbox 表；经过 Kafka 的一跳，消费者和生产者的 span 是什么关系；指标怎么导出。

动手前验证过一件事：服务之间隔着两个 Envoy 边车，边车没有配链路追踪时 `traceparent`、`tracestate`、`baggage` 原样到达下游（实测，只多出 `x-request-id` 和 `x-forwarded-proto`）。所以 gRPC 这一跳不需要边车配合。

## 决定

1. **链路上下文过 outbox 靠表里的一列。** `outbox` 加 `trace_context VARCHAR(64) NULL`，`outbox.Add` 在业务事务里写入 ctx 的 `traceparent`，中继发布时放进消息的 header。没有采样的也写。
2. **异步一跳按“是不是同一个业务动作的延续”选父子或 link。** 受理到落库、订单事件、支付结果用父子；延迟关单和按批消费用 link。重试时每次尝试一个 span。
3. **指标用 OTel 的指标 API，经 OTLP 推**，和链路同一个地址。不开 `/metrics`。
4. **本机的后端是 `grafana/otel-lgtm`**，放在 compose 的 `obs` profile 里，只用来看。没有配 OTLP 地址时服务照常产生 span（日志里有 trace id），不导出。
5. **Kafka 的传播和消费 span 写在 `kafkax` 里**，不用 franz-go 的 `kotel` 插件。
6. **指标的标签只能是有限的枚举**；订单号、用户号、SKU 只能放在 span 上。
7. **gateway 不信任外面带进来的 `traceparent`**，只记成 link；响应里返回 `X-Trace-Id`。入口的 span 由 gateway 自己的中间件建，没有用 `otelgin`（它没有公共入口的选项，指标带着取自 Host 头的端口，把降级的 503 和客户端断开都标成 Error；见设计文档 1d 的 8.4）。

## 理由

**outbox 加列。** 中继是后台循环，它发消息时的 ctx 和写这一行的请求没有关系；上下文只能跟着数据走，而数据在表里。替代办法是靠 span 上的 `order_id` 在后端里搜，能把同一个订单的几条链路找出来，但它们之间没有因果，也算不出从下单到完结的耗时。没有采样的也写，是因为采样位就在 `traceparent` 里：不写的话下游会各自重新抽签，低采样率下多出一批只有后半段的链路。

**父子为主。** 规范不强制。父子的好处是一条链路就是一个订单的全过程，在 Kafka 里排了多久是两个 span 之间的空隙，这正是 3.9 的悬案（落库时每个订单约 54 毫秒不在 MySQL 里）要看的。link 的好处是每条链路都短。延迟关单用 link，是因为它在支付时限之后才触发，给一条早已结束的链路再添 span，后端按“链路已结束”做的处理（尾部采样、聚合）都会出错。按批消费只能用 link：一个 span 只有一个父。

**每次尝试一个 span。** ADR-0021 之后消费者对普通错误不设重试上限。span 结束了才导出，整条消息一个 span 的话，分区停住的那段时间里什么也看不到。

**OTLP 推。** 和 ADR-0004 一致，链路和指标走同一条路，到集群上只改环境变量。`/metrics` 的好处是不起后端也能 `curl` 看一眼，代价是两条导出路径，阶段 3 要么改回来、要么改写 ADR-0004。

**不用 `kotel`。** 它的钩子对应“消息进出客户端的缓冲”，而处理过程（按 key 分 lane、排队、重试、按批、延迟等到期）在 `kafkax` 里，处理的 span 无论如何要自己建；传播只是把 header 交给传播器，几十行。

**标签的规则。** 指标的每种标签组合是一条独立的时间序列，进程里和后端里各占一份内存；按用户号打标签，序列数等于用户数。链路没有这个问题，每个 span 是独立的记录。

## 备选方案

- 不改 outbox 表、所有消息一律 link、指标用 Prometheus exporter 拉、本机只起 Jaeger 或不接后端：见设计文档 1d 的 8.14，主人都选了建议的一项。
- 本机直接接 SkyWalking：OAP 加 BanyanDB 太重，而且“OTLP 链路在 SkyWalking 里够不够用”是 ADR-0004 留给阶段 3a 的验证项。

## 后果

- `outbox` 的表结构变了，order 每个库、payment 各一个迁移。MySQL 没有 `ADD COLUMN IF NOT EXISTS`，迁移里先查 `information_schema` 再加列，可以重跑。
- 没有父 span 的 CLIENT span 由采样器丢弃（后台循环访问 Redis、MySQL 不产生孤立的链路）。代价是采样器的环境变量由 `otelx` 自己解析，只认规范里的六个名字。
- 一个订单实际上是三条链路（下单到落库、发起支付、支付结果），靠 span 上的订单号关联：发起支付是另一个 HTTP 请求，支付结果由 payment 的后台处理器产生、在那里开头（`payment.complete`）。起草时担心的“下单的链路会持续到支付完结”没有发生。
- 头部采样会漏掉没被抽中的出错请求。尾部采样在 Collector 里做，阶段 3。
- CDC 的一跳不传递，商家索引的链路从 orderindex 的消费开始。
- 埋点的开销要实测，结果在设计文档 1d 的第 8 节末尾。
