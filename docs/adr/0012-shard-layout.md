# ADR-0012：订单分片布局为 8 个逻辑分片、2 个库，表名带全局分片号

- 状态：已采纳
- 日期：2026-11-13
- 相关：ADR-0002；设计文档 [1c-sharding.md](../design/1c-sharding.md) 第 2 节

## 背景

ADR-0002 定了应用层分片、以 `user_id` 为分片键、订单号里嵌入用户的分片基因，留下分片数和映射规则到 1c 再定。idgen 在 1a 就把 `user_id` 的低 6 位放在订单号的最低 6 位，所以对任何不超过 64 的 2 的幂 N，`order_id % N == user_id % N`。

## 决定

1. **8 个逻辑分片（slot）**：`slot = user_id & 7`，订单号同理。
2. **2 个物理库**：`db = slot % 2`。
3. **每个 slot 一组表**：`orders_{slot}`、`order_items_{slot}`、`payment_results_{slot}`，slot 号是全局的。每个库一张 `outbox`。
4. **slot 数和库数是常量**，不做成运行时配置。
5. **只拆 order**。payment、inventory 保持单库。

## 考虑过的方案

- **按库内表号命名**（每个库都是 `orders_0` 到 `orders_3`）。更常见，但表的身份依赖它在哪个库，搬 slot 时要改名，而且路由要分两步算（先库后表）。全局编号下路由只算一次 slot，slot 在哪个库是另一张映射，扩容只改映射。
- **区间映射 `db = slot / 4`**。扩容到 4 个库时旧库要重新编号，或者每个旧库同时拆给两个新库。取模映射下成倍扩容每个旧库只拆给一个新库，编号不变，可以用“从库提升为新主库、两边各删一半”的方式迁移。
- **一致性哈希**。适合节点频繁增减、数据可以重算的缓存。订单数据迁移代价高，扩容是计划内的低频操作，成倍扩容配合固定的 slot 数更简单，搬迁量可以精确算出来。代价是每次扩容都得翻倍。
- **直接按 64 个 slot**。以后不用再拆表，但现在每个库 32 组表，测试和本机运行的建表开销、表数量都偏大。8 个起步，需要时按基因再拆一次（`orders_k` 拆成 `k` 和 `k + 8`），只涉及一张表内的行。
- **slot 数可配置**。配置改了数据就找不到了，改它本质上是一次数据迁移，不应该是一次重启就能做的事。
- **payment 也分库**。支付单的数据量和订单同阶，真实系统里也会拆。但 1c 要学的路由、非分片键查询、扩容、归档在 order 上都能覆盖，再拆 payment 只是重复劳动，还会让本机要跑的 MySQL 实例翻倍。

## 后果

- 按用户、按订单号的读写都只落在一个 slot，不需要全分片扫描。
- 不能跨 slot 开事务。现有的事务都以一个订单为中心，天然在一个 slot 内；`store.Tx` 拒绝操作其他 slot 的订单，把这条约束变成运行时检查。
- 后台扫描（超时关单、卡单兜底）要逐个 slot 扫。这是明确豁免的全分片扫描。
- 每个库一个 outbox 中继，中继名必须不同，否则 event-id 冲突。
- 扩容只能成倍。8 个 slot 最多支撑 8 个库，再多要先拆表。
- 迁移历史压缩成一个文件，旧的 `order_db` 废弃。
