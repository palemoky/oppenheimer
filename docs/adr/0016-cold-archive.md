# ADR-0016：冷订单按订单号里的时间归档到独立的压缩库，先写冷、校验、再删热

- 状态：已采纳
- 日期：2026-11-14
- 相关：ADR-0012、ADR-0014（本文定下其中留下的 DELETE 问题）、ADR-0015；设计文档 [1c-sharding.md](../design/1c-sharding.md) 第 6 节

## 背景

订单表只增不删。本机 500 万单里约 96% 下单超过 90 天，全是终态，几乎不再被访问，却和热数据挤在同一批表里：占缓冲池，拖长备份和扩容（步骤四 CLONE 搬的主要是它们）。1c 的最后一步要把它们搬出去，同时保证搬的过程不丢订单、搬完之后还能查到。

要回答的问题：哪些订单算冷；搬的过程中冷热在两个库上，怎么不靠分布式事务保证不丢不重；读路径怎么知道去哪找；热库上的删除对 CDC 和商家索引意味着什么。

## 决定

1. **冷的定义：终态，并且订单号里的受理时间早于截止点（默认 90 天）。** 不用完结时间。
2. **读路径靠一个编译期常量 `MinHotAge`（30 天）判断要不要查冷库**：订单号比它新的一定不在冷库。archiver 的截止点不得小于 `MinHotAge + 1 天`。没有水位表，没有路由元数据。
3. **搬一批的顺序：读热、upsert 进冷、从冷读回校验、锁住热库的订单行重读并比对、删热。** 订单行锁是一个订单三张表的互斥锁。任何一步之后崩溃都只会留下“两边都有”，重跑收敛。
4. **读一律先热后冷。**
5. **冷库是一个独立的库，不按用户分片；表用压缩行格式，按订单号做 RANGE 分区（每年一个）。**
6. **archiver 是 order 模块里独立的一次性任务**，不持久化进度，限速以复制延迟为反馈。
7. **数据只从热到冷。** 落库拒绝受理时间早于 `MinHotAge` 的消息，冷订单不恢复回热库。同一个订单号因此不会在热库里出现第二次。
8. **针对已归档订单的支付结果，从冷库的内容推出答复，不写冷库。**
9. **CDC 的 DELETE 保持为带 `before` 的普通消息**，约定它表示“离开热库”；**商家索引保留归档订单的行**，orderindex 把 DELETE 的 `before` 当作映像做带版本号的 upsert。
10. **归档后幂等键的唯一约束失效**，幂等的有效期以热数据的保留期为上限。

## 理由

**为什么按订单号里的时间。** 冷热的判断如果只依赖订单号，读路径就是纯计算。按完结时间划分更贴近业务，但订单号无法推出完结时间，读路径要么对每个没查到的订单号都去冷库再查一次，要么维护一个各方都要读的水位。本系统的订单从受理到终态最多一个支付时限，两种时间差几分钟，没有理由付这个代价。有退款和售后的系统里结论会不同：那里应该按完结时间，并接受读路径的元数据。

**为什么常量而不是水位。** 水位（“早于 W 的已经归档完”）能让冷订单的读直接去冷库，省掉一次热库查询。但读水位和读数据之间有窗口：读到旧水位、去热库查、行刚被删掉，于是把存在的订单说成不存在。要补上就得在热库落空后再查一次冷库，最后还是“先热后冷”，水位只剩下优化的作用。冷订单的访问量本来就小，这一次多出来的主键查询约 0.2 毫秒，不值得为它引入一份要保持一致的状态。

**为什么不用分布式事务也安全。** 写冷库是幂等的 upsert，删热库以“锁内重读的内容与冷库相同”为前提。两步之间失败的结果是重复，不是丢失；重复由下一次运行消除。这和 outbox 的思路相同：把跨库的原子性换成“可重复执行的步骤加一个确定的顺序”。

**为什么冷库不分片但要分区。** 分片解决的是写入和容量在多台机器上的分摊，冷数据没有写入压力。分区解决的是另一件事：按时间整段地管理数据。到了保存期限的一年数据，`DROP PARTITION` 是一次元数据操作；而这次归档在热库上不得不逐行删再重建表，正好是对照。订单号的高位是时间，分区键就是主键，分区的常见代价（唯一键必须包含分区键）在这里几乎不用付。

**为什么商家索引保留。** 索引带着展示列，是一份能独立回答“这个商家有哪些订单”的数据。源库的行搬走不改变这个事实。删掉索引行换来的是索引变小，付出的是商家端看不到旧订单，或者要给冷库再建一套商家维度的查询。索引自己的冷热分离应当按它自己的访问模式单独做。

**为什么 DELETE 不改成墓碑。** 墓碑的语义是“这个 key 不存在了，可以清掉”。归档的订单仍然存在。保留带 `before` 的消息，压缩的 topic 仍然是“每个订单的最新映像”，新下游可以只靠它建出全量。

## 备选方案

- **按完结时间划分冷热。** 见上。
- **水位路由。** 见上。
- **不分区的一张压缩表。** 最简单，这一步的全部功能都能实现。少的是保存期限到了之后的整段删除，以及一个把“分区”和“分片”放在一起比较的实例。
- **冷库照热库的样子按 slot 拆 8 张表。** 归档变成同构的表对表拷贝，用户列表在冷热两边的路由完全一样。但它把一个不需要分片的库分了片，扩容时冷库也要跟着搬。
- **热表也按时间分区，过期整区卸掉，不逐行删。** 这是日志类数据的标准做法，没有删除的开销，也没有空间回收的问题。订单不适合：归档的条件里有状态，一个卡住的非终态订单会钉住整个分区；整区卸掉之前还是得先把数据拷到冷库并校验。8 张分片表各自再分区，迁移和扩容脚本都要跟着变复杂。
- **归档到对象存储（Parquet）。** 列式压缩比远高于 InnoDB 的页压缩，存储便宜一个数量级，适合给分析用。不适合这里的查询：按订单号点查要么全扫、要么另建一份“订单号到文件”的索引，延迟是百毫秒到秒级；“冷订单仍可查”就得另做一条慢路径并在接口上体现出来。合理的组合是两层：近几年的冷数据放压缩的 MySQL 供在线查，更老的再转成 Parquet 只供离线。本项目只做第一层。
- **用 pt-archiver 之类的现成工具。** 它做的就是分批拷贝加删除，带复制延迟检查。不用的原因和 ADR-0002 一样：要学的是它内部的那几步。另外它不知道“订单行锁保护三张表”这个约定，逐表归档时会漏掉 6.3 里的并发插入。
- **用 CDC 搬（消费变更流写冷库）。** 冷库会变成热库的一个延迟副本，但它不知道什么时候可以删热，删除仍然要一个带校验的任务来做；而且冷库会收到全部在线变更，不再是“写一次就不动”的数据。
- **删热库时不重读，只比行版本号。** 行版本号只覆盖 `orders` 行。订单取消后才到的支付结果只插入 `payment_results`，不动订单行，会在拷贝之后、删除之前溜进来并被一起删掉。
- **归档订单的支付结果写回热库的 `payment_results`。** 能保留去重记录，但热库里会留下订单已经不在的孤儿行，archiver 还得再处理它们。答复既然完全由不变的冷数据决定，重新推一遍就够了。

## 后果

- order 服务多一个只读依赖。冷库不可用时：热订单的读写不受影响；冷订单的查询失败；针对旧订单号的支付结果会原地重试并堵住它所在的分区，直到冷库恢复。最后一点是有意的。
- 用户列表在近期订单不满一页时会查冷库，这样的用户是多数。实测比例之后可能需要在接口上把“更早的订单”分出去。
- 幂等键超过保留期后失效，是对外行为的变化，要写进接口文档。
- `MinHotAge` 一旦有数据归档就不能调大（调大会让读路径不去冷库找已经归档的、较新的订单）。调小是安全的。
- 归档产生的 DELETE 会经过 CDC 压到商家索引的消费者上，在它改成按批写之前，一次大规模归档会让索引延迟几十分钟。
- 热库的空间要靠重建表才能还给操作系统，重建在主从上各做一遍。
- 冷库的表结构要跟着热表演进：热表加列时冷库也要加，否则 archiver 的校验会失败（这是期望的失败方式）。
- **上线顺序是硬约束**：先给所有 order 实例配上冷库，再第一次运行归档。没配冷库的实例会把已归档订单的支付结果当成“订单不存在”而要求退款，归档任务检查不到这一点。
- `cdc.order.orders` 的压缩保留从调优选项变成了数据约束：归档订单在这个 topic 里只剩那条 DELETE，topic 丢了，新下游只能从冷库另做全量。
- 以后新增写 `payment_results` 或 `order_items` 的路径，必须先锁订单行。校验后删除靠这条约定成立。

## 实测（2026-11-14，设计文档 6.14）

- 482 万订单 8 分 8 秒搬完，从库延迟最大 1 秒，行数守恒，对账通过。
- 热库的磁盘占用在删除后不变（2273 MB），重建表后是 217 MB。
- 冷库在大批量归档刚结束时几乎没有压缩效果：多个 slot 并行归档使主键交错插入，页大量分裂。重建分区后是 906 MB，为同样数据在热库里的 41%，其中压缩和去掉两个二级索引各贡献约一半。
- 按主键的点查在归档前后没有变化；改善的是尾延迟（数据重新小于缓冲池）。
