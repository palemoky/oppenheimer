# ADR-0018：MySQL 侧的库存计数改为异步合并更新，闸门是防超卖的唯一关口

- 状态：已采纳
- 日期：2026-11-14
- 相关：ADR-0009、ADR-0011、ADR-0017；设计文档 [1d-protection.md](../design/1d-protection.md) 第 3 节

## 背景

1d 步骤一给落库开了分区内并发之后，落库吞吐从约 320 升到约 690 单/秒就不再上升。`performance_schema` 显示时间花在 inventory 预占时的 `UPDATE sku_stock ... WHERE sku_id = ?` 上：平均 48 毫秒，几乎全是等行锁。买同一个 SKU 的所有订单改同一行，行锁拿到事务提交，而每次提交约 7 毫秒。确认和释放改的也是这一行。

能不能卖在 1b 之后是 Redis 里的库存闸门先判断的。MySQL 的这次条件更新是第二道检查。

## 决定

1. **预占、确认、释放不再直接改 `sku_stock`**，改为在同一个事务里往 `stock_pending` 插入一行增量。预占记录（`reservation`、`reservation_item`）和它的状态机不变。
2. **一个后台应用者**按 id 顺序取一批增量，按 SKU 求和，每个 SKU 一条更新，同一个事务里删掉这批增量。
3. **防超卖只靠闸门。** MySQL 一侧不再在预占时检查可售数；应用增量会让某个数变负时，跳过那个 SKU 并报错。
4. **读真实的数要加上未应用的增量**，在一个一致性读里：闸门的预热和对账必须这样读。
5. `Reserve` 保持同步的 gRPC，契约不变。

## 理由

**为什么可以去掉 MySQL 的同步检查。** 它重复的是闸门已经原子地做过的判断。两处都检查的价值在于闸门出错时有兜底，代价是每个订单在最热的那一行上串行一次。兜底没有消失，只是从“当场拒绝”变成“事后发现”：应用者的 CHECK 约束、闸门和 MySQL 的周期对账、阶段 1d 步骤五的对账工具。

**为什么增量放在库里的一张表，而不是 Kafka。** 见设计文档 3.2。核心是两点：未应用的增量必须能和计数在同一个快照里读到，否则装载闸门时会装多；“改计数”和“标记已应用”必须在一个事务里，否则要另做去重。

**为什么合并而不是分桶。** 把一个 SKU 的库存拆成 N 行也能消掉热点，而且保留同步检查。但“某个桶没货、别的桶有货”要处理（换桶、借调），可售数的读取变成求和，桶数要按热度定。它适合 MySQL 仍然是防超卖关口的系统。这里关口已经在 Redis，没有理由再为第二道检查付这些复杂度。

## 备选方案

- **经 Kafka 异步、inventory 按批消费，order 落库时不调 `Reserve`。** 上限更高，改动面大得多，装载闸门时的真实可售数算不准。见设计文档 3.2 的方案 B。热点行解决之后如果同步的 `Reserve` 成为下一个瓶颈，再考虑。
- **分桶。** 见上。
- **在 `Reserve` 里把多个并发请求合并成一次更新**（请求在服务里排队，攒一小批后一个事务处理）。也能消掉热点，同步语义不变。但一个事务里混着多个订单，其中一个失败要么整批回滚、要么逐个处理，gRPC 的每个调用还各自有时限；确认和释放走的是事件消费，要另做一套。
- **缩短持锁时间**（放宽刷盘、把更新放在事务的最后一步）。放宽刷盘实测只把并发度 16 的吞吐从 686 提到 848，而且是拿持久性换的。
- **什么都不做，靠多个 SKU 分散。** 压测里 SKU 从 10 个加到 100 个，吞吐从 686 到 800。秒杀恰恰是所有人买同一个 SKU。

## 后果

- **MySQL 从阻止超卖变成发现超卖。** 闸门和 MySQL 对不上时（有人直接改库、Redis 丢数据后装载有误、对账修正有缺陷），以前是订单创建失败，以后是订单成功、应用者报错。这是这个决定最大的代价。
- `sku_stock` 的数落后一个应用周期。任何用它做判断的新代码都必须读“加上未应用增量”的值；直接读只能用于展示。
- 多了一个必须活着的后台任务。它停了，计数不再更新，增量表无限增长，预热和对账靠求和仍然正确但会越来越慢。需要监控增量表的行数和最老一行的年龄（阶段 3）。
- “Redis 不可用时退回数据库扣减”的降级预案（步骤四）不能直接用原来的条件更新，要先把增量应用完。
- 对账的恒等式不变（`available + reserved` 对闸门的 `avail + held`），但两边都要用包含未应用增量的值。
- 测试里凡是在预占、确认、释放之后立刻断言 `sku_stock` 的地方，都要先等应用者追平。
- **应用者不能假设增量按先后到来**（2026-11-14 补充，设计文档 3.10）。按 id 顺序加锁扫描不是快照，一个订单的释放可能先于它的预占被取到。一批的合计被 CHECK 拒绝时，改用这个 SKU 全部未应用增量的合计；仍然不行再用一致性读判断真实值是否为负，为负才算对不上。“发现超卖”的判据是快照里的真实值，不是某一批加不加得上。
