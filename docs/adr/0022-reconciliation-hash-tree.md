# ADR-0022：对账用订单号上的基数哈希树，摘要是行哈希的和，在数据库里算

- 状态：已采纳
- 日期：2026-11-14

## 背景

系统里有几份应当一致的数据：订单主库和从库、订单和商家索引、订单和支付单、订单和库存预占、归档前后的“热库加冷库”。现有的检查（`load verify`）把表整个读进内存，500 万行的造数订单被排除在外，而且要求系统静止。阶段计划要求做一个基于 Merkle 树的对账工具，并说明它在什么数据量和差异率下才有优势。

动手前在本机量了两个数（冷库 `orders_archive`，482 万行，投影 6 列）：把行读到客户端是 276 MB、7.3 秒；在数据库里按桶聚合 SHA-256 是 3115 行结果、8.5 秒。

## 决定

1. **树是订单号上的基数树。** 节点是订单号的一个前缀，即主键上的一段连续区间，每层 16 叉。订单号的高位是时间，所以节点也是一段时间。
2. **节点的摘要是它下面所有行哈希的和（128 位，取模）加行数，每一层都是。** 行哈希是投影列的规范字符串的 SHA-256 前 128 位。
3. **摘要在数据库里用聚合语句算**，工具只收摘要；只有摘要不同、行数又少的节点才把行读出来逐行比。
4. **树不定深度**：摘要不同的节点行数超过阈值就再分，否则逐行比。第一遍直接在 18.6 小时一个节点的那一层聚合。
5. **变动中的数据靠水位线加复查**，不用快照。对账的范围是订单号上的一个窗口：上界是水位线，下界可选（2026-11-14 补），带下界的是增量对账，不带的是全量。
6. **闸门（Redis）和 MySQL 的库存不用这个工具**，维持按 SKU 逐个比的 `reconcile`。
7. **只有商家索引可以自动修复**，其余只报告。

## 理由

**为什么在数据库里算。** Merkle 树省的是传输和比较，不省扫描：摘要要读过每一行才算得出来。如果工具把行读过来再算，传输已经花掉了，再建树只是多做一次哈希，比“两边读出来归并”更慢。只有摘要在数据所在的地方算、在网络上只走摘要，树才有意义。Dynamo、Cassandra 的反熵修复就是这个结构：每个副本在本地建树，副本之间只交换树。

**为什么是和，不是 H(子节点)。** 教科书的 Merkle 树里父节点是子节点哈希拼接后的哈希，它保证的是防篡改：改任何一片叶子，根一定变，而且可以给出一条从叶子到根的路径证明某片叶子在树里。代价是摘要和结构绑死：必须先有子节点才能算父节点，两边的数据必须按同样的方式切分。

这里两边的切分方式不同（订单按用户分 8 个 slot，索引按商家分 4 个 slot，冷库不分片）。用和做摘要，同一段订单号的摘要可以由各分片各算各的再相加，“热库加冷库”只是多加一项；任何一层的节点都能用一条范围聚合语句直接得到，不需要先算它的子节点；加一行、删一行是加减一个数。这三条都是对账需要的，防篡改和包含证明都不是：对手是程序缺陷和运维失误，不是会构造碰撞的攻击者。

和 XOR（pt-table-checksum 的 `BIT_XOR`）相比，和不会让出现两次的同一行互相抵消。

**为什么按订单号的区间，不按哈希分桶。** 节点是主键区间，取一个节点的摘要或行是范围扫描；按哈希分桶则每取一个桶都是全表扫描。旧数据的节点不再变化，水位线就是订单号的一个上界。代价是节点大小随下单速度变化，相差几个数量级，所以树不能定深度。

**为什么不用快照。** 一致性快照只在一个库内有效；主从之间靠“校验语句随复制重放”对齐的办法要求语句格式的 binlog，而 CDC 需要行格式。水位线挡掉绝大部分在途数据，剩下的靠复查：两次读到同样的差异才算。

**为什么库存不纳入。** 键只有 SKU 那么多，逐个比的代价本来就小；数值持续变化，没有可以划水位线的“已定型”部分。

**为什么增量对账用窗口的下界，不存摘要。** 通常的对账只比新数据（T+1 的日切对账就是这样），全量是偶尔做的兜底。树按订单号的区间分层，时间窗口就是主键上的一段，加一个下界就得到增量对账，不需要存任何状态，也不依赖上一次运行成功（窗口互相重叠）。它发现不了窗口之前的数据后来被改坏，那要靠定期的全量。把行哈希存进表里的两种办法和它们的问题见设计文档 7.17。

## 放弃的方案

- **两边全读出来归并。** 最简单，代价与差异多少无关。保留为工具的一个模式，用作性能对比的基线；在工具和数据库同机、差异很多时它可能更快，实测后写进设计文档 7.12。
- **工具读行、自己建教科书式的 Merkle 树。** 见上，没有收益。
- **固定深度、固定大小的叶子。** 数据密度不均时，要么叶子多到传摘要和传行一样贵，要么单个叶子大到下钻等于全表。
- **从根开始逐层向数据库要。** 差异分散时每一层都近似一次全表扫描。改为第一遍直接在较细的一层聚合。
- **增量维护的树**（写入路径或 CDC 更新摘要表，对账时不扫全表）。能把扫描也省掉，但摘要表本身是又一份要保证不丢更新的派生数据。本项目的数据量下一次全扫是几秒到几十秒，不值得。数据到几十亿行、对账要每小时跑的时候应当重新评估。
- **CRC32 做行哈希。** 快（实测 5.0 秒对 8.5 秒），但只有 32 位，一行改动恰好不被发现的概率是四十亿分之一，乘以几百万行和反复运行后不能忽略。

## 后果

- 两边的行哈希必须逐位一致：SQL 的表达式和 Go 的 `RowHash` 是同一个规范的两份实现，靠对着真实 MySQL 的测试守住。投影里只放整数和状态码。
- 每次对账仍是每张表一次全表扫描，跑在从库上；没有从库的库（冷库、索引库、支付库、库存库）直接承受这次扫描。
- 没有订单号索引的表（商家索引）每下一层是一次全表扫描，差异分散且密集的区域下钻会慢。
- 归档的前后对比，右边是存下来的树，只能定位到节点。
- 行哈希的和不抗有意构造的碰撞。如果以后对账要面对不可信的一方（例如和外部支付渠道对账），需要重新选摘要。
- 名字仍叫 `pkg/merkle`，但它不是教科书意义上的 Merkle 树，包的文档里要写明。
