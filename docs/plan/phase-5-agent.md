# 阶段 5：诊断 Agent

**目标**：把诊断 Agent 从最小版本做成效果可量化的完整版本，用阶段 4 的故障场景评测。
**设备**：Mac mini（运行 Agent）、Ubuntu（集群）
**技术**：Go + Claude API（工具调用）。动工前先查最新的 Claude API 和 Agent SDK 文档，不凭记忆写。

## 时间线

Agent 的开发分散在三个阶段：

| 阶段 | 做什么 |
|---|---|
| 3d | 最小版本：主循环、Prometheus、Loki 和 Kubernetes 三个只读工具、webhook 触发、报告、留痕 |
| 4 | 跟着每次故障实验一起跑，与主人的排查结果对比，边用边改 |
| 5（本阶段） | 正式的评测体系、补全工具、系统化迭代 |

进入本阶段时应该已经有：一个能跑的 Agent、几十次真实故障下的运行记录、一批带标注的复盘。

## 设计要点

- **触发**：Alertmanager webhook，也支持命令行手动提问。
- **工具（全部只读）**：
  - Prometheus：PromQL 即时与范围查询（3d 已有）
  - Loki：日志查询（3d 已有）
  - Tempo：按 trace id 取链路、TraceQL 搜慢链路和错误链路、service graph 看拓扑（ADR-0024，原计划是 SkyWalking）
  - Kubernetes：get、describe、events、logs（3d 已有，从本阶段提前）
  - Go 运行时：抓取并解读 pprof（goroutine、heap、mutex、block、cpu；阶段 4 已有，从本阶段提前）
  - MySQL：复制状态、慢查询、锁等待、死锁日志
  - Redis：slowlog、大 key 扫描结果、内存与集群状态
  - Kafka：消费延迟、分区与 ISR 状态
  - 知识：runbook 与历史复盘检索
- **输出**：根因判断、证据链（每条结论附查询和结果）、置信度、建议的处置步骤。
- **安全边界**：Agent 不直接执行变更。处置动作只给建议，后续若加自动修复，必须走人工确认。

## 任务

### 5a 评测

- [ ] 把阶段 4 的故障场景整理成评测集：注入清单 + 标准根因 + 关键证据（来自复盘模板的标注栏）
- [ ] 评测流水线：自动注入故障 → 等待告警 → Agent 诊断 → 判分 → 恢复环境
- [ ] 指标：根因命中率、定位耗时、工具调用次数、费用、报告中无法溯源的结论比例
- [ ] 用阶段 4 结束时的 Agent 版本跑出基线成绩

### 5b 补全与迭代

- [ ] 补全上面列出的其余工具（阶段 4 中已按需加过的，在这里整理和补测试）
- [ ] 接入 runbook 和历史复盘检索
  - 检索这一层（生成向量、召回一批再重排的接口、离线评测）按“可以给别的内容用”来设计，放在公共的位置：阶段 11 的推荐召回会接着用，只换索引（2026-11-18 加，见阶段 11 计划的“和诊断 Agent 复用的部分”）。文档只有几十到几百篇，先比较关键词检索、逐个算向量相似度和两者混合，不为了复用提前上近似最近邻索引
- [ ] 提示词与工具设计迭代，每次改动跑评测对比
- [ ] 模型分层：简单查询用小模型，推理用大模型，比较成本与效果
  - [ ] 封闭式判断交给专门的决策模型的对比实验（2026-11-15 加，主人提出）。候选是 Google 的 Gemini Decision 1（`gemini-decision-1`，2026-11-11 发布）：只做是或否、多选一、按量表打分，输出各选项的概率、不生成文字，只收输入的费用。它不能做主循环（不生成文字，官方介绍里没有工具调用），主循环保持 Claude。在下面三个位置各自和“Claude 的小模型加结构化输出”做同一件事，在评测集上比命中率、费用、延迟：
    - 评测的判分器（5a）：Agent 的结论和标准根因是不是同一个，报告里的结论有没有证据支撑
    - 裁剪工具输出：一段日志或一组指标和当前的怀疑有没有关系，只把相关的交给主模型
    - 告警分诊：属于哪一类（MySQL、Redis、Kafka、Go 运行时、Kubernetes），值不值得跑一次完整的诊断
  - 动工前先重新读官方文档：接口和价格发布不久，可能已经变了。它的延迟和校准数据是 Google 自己报的
  - 判分器先被评测：用它判分之前，拿一批人工标注的结果核对它和人的一致率；它给的概率准不准（说 0.9 的把握是不是真的九成对）也用这批数据核对
  - 接不接由这组实验的数据决定；接的话多一个供应商，密钥、留痕和费用统计都要各加一套
- [ ] 多 Agent 方案试验（按领域拆分子 Agent）并与单 Agent 对比
- [ ] 留出一批 Agent 没见过的新故障做最终测试，防止对评测集过拟合

### 5c 可选

- [ ] 带人工确认的处置动作（重启、扩容、切流）
- [ ] 做成 MCP server，让 Claude Code 等客户端直接使用这些诊断工具

## 验收标准

- 评测集上的根因命中率有明确数字，且相对基线有可解释的提升。
- 报告里的每条结论都能追溯到真实的查询结果。
- 没见过的新故障上也有可用的表现。

## 面试考点

Agent 循环与工具调用机制；工具设计原则；上下文管理；Agent 评测方法；幻觉的控制与证据溯源；单 Agent 与多 Agent 的取舍；成本与延迟优化（缓存、模型分层、把封闭式判断从生成式模型里拆出去）；用模型判分时判分器本身怎么验证（和人工标注的一致率、置信度的校准）；Agent 的权限与安全边界；MCP。
