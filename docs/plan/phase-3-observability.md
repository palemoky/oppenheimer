## 面试考点

OpenTelemetry 的架构（API、SDK、Collector、OTLP）与上下文传播；Collector 的 agent 加 gateway 两层部署各自做什么、`memory_limiter` 为什么放最前；推和拉两种采集方式怎么发现“对方挂了”；日志的 `trace_id` 为什么不做 Loki 的标签（结构化元数据）；多目标模式的 exporter 里 `up` 和 `mysql_up` 的区别；pprof 端点为什么不能挂在对外或 Service 暴露的端口上；原因码答错会把排查引向哪里（展示读名额满了答成“闸门不可用”，设计文档 3a 第 8 节）；头部采样和尾部采样各自在哪里做决定、各自的代价（实测：出错的链路头部 10% 只留下 10%，尾部全留，代价是服务全量导出和 Collector 的内存）；尾部采样之后从 span 算出来的指标为什么是偏的；网格指标的标签在源头裁和在 Prometheus 里裁的区别；埋点把正常的返回值记成错误的例子（`driver.ErrSkip`，设计文档 3a 第 8 节第 4 步）；Collector 停机时三种信号各丢什么、为什么（累计值的指标补得回来，链路补不回来，日志看 agent 会不会停下来等）；Collector 的 `batch` 处理器为什么会切断反压、批次没有上限会撞上哪些限额（Loki 的突发量、gRPC 的 4 MiB）；复制停了的时候 `Seconds_Behind_Source` 是 `NULL`，按延迟写的告警不响；怎么验证监控本身是对的（制造已知数量的失败再对数；同样是 503，响应标志 `UO`、`UT`、`UH` 才分得出原因）；尾部采样之后 exemplar 为什么大半跳不到链路；HPA 的自定义指标是怎么取到的（Resource、Pods、External 三类指标，聚合 API，KEDA 只提供数、改副本数的仍是 HPA 控制器）；HPA 有多个指标时取最大值，有一个取不到时不缩容但还能扩容（实测）；按请求速率伸缩为什么不比按 CPU 快（`rate` 的窗口）以及它好在哪里；指标后端挂了伸缩会怎样、怎么发现（`ScaledObject` 的 `READY` 看不出来）；同一个 Deployment 不能有两个 HPA；指标、日志、链路各自解决什么问题；Prometheus 拉模型、数据模型、PromQL、直方图与分位数；链路追踪的上下文传播与采样；SLI、SLO、错误预算；告警疲劳与如何设计好告警；压测方法论与常见瓶颈；Go 性能分析（pprof、trace、GC 调优）。

3b 第 1 轮补的（[记录](../notes/3b-rounds/round-1-replica-flush-and-payment.md)、ADR-0032）：`innodb_flush_log_at_trx_commit` 和 `sync_binlog` 各取值在进程崩溃、节点掉电时分别丢什么；从库为什么可以比主库放松、放松之后掉电为什么要重建而不能看“复制还在跑”（数据和 binlog 各丢各的，其中一种不报错）；这类设置为什么要跟着角色走而不是跟着序号（提升之后带着放松的设置当主库）；CDC 用 GTID 集合做位点时从库的 binlog 丢一截或者从库重建为什么不影响它；串行循环的吞吐上限是“1 ÷ 单次提交的耗时”，和负载无关，所以平时看不出来；把串行改成并发为什么能提高吞吐（并发的提交被组提交合进同一次刷盘）以及它和“几笔合进一个事务”的取舍（失败的隔离）；后台循环“取满一批就接着跑”时怎么避免整批失败变成死循环；另开的 goroutine 里的 panic 不会被外层的 recover 接住；量“排队等了多久”的直方图和量“一次调用多久”的直方图为什么不能用同一组桶。

3b 第 2 轮补的（[记录](../notes/3b-rounds/round-2-concurrency-and-consumers.md)、ADR-0033）：组提交在并发低的时候为什么攒不起来（一次刷盘带走的是刷盘期间到达的提交，要看的是同一时刻有几个事务在提交，不是线程数）；做贵的改动之前先做不改代码的对照；下游欠着活时上游量到的数是虚高的；幂等的“依据”和“捷径”要分开（订单库的唯一键是依据，Redis 里的键是让重放不碰数据库就得到答案的捷径，捷径可以过期）；带 TTL 的键放进 `noeviction` 的 Redis 就是一条容量公式（速率 × TTL × 单个大小），TTL 该按“客户端还会重试多久”定；两个各自配置、但有先后关系的时限（幂等键的 TTL 和支付时限）要在启动时互相校验；Redis 写满时“写不进”会连带挡住回收和锁，比拒绝新请求更糟。

3b 第 3 轮补的（[记录](../notes/3b-rounds/round-3-overload-behavior.md)、ADR-0034）：拒绝请求时为什么必须给 `Retry-After`（不给的话拒绝只是把一个慢请求换成很多个快请求）；轮询为什么也是一种重试放大（等待的订单越多查询越多，是正反馈，退避只能压低增益）；入口的并发上限怎么定、怎么读（在途请求数 = 到达速率 × 耗时）；HTTP/1.1 的上游里 Envoy 的连接上限和排队上限各管什么，冷的连接池为什么不能把排队收得太紧；利特尔定律用在背压上（限制等待时间只能靠限制队列长度，上限 = 最慢分片的处理速率 × 允许的等待，换环境要重算）；按“已经等了多久”触发的保护为什么管不了已经放进来的量；`noeviction` 的 Redis 写满时最先坏的是什么、为什么在水位上拒绝新工作而不是换淘汰策略；水位检查放在进程里采样和放进 Lua 脚本的取舍；被动喂结果的熔断器，“连续 N 次失败”为什么要和调用方的并发度比（并发 192 时一次停顿就是上百次失败，要加持续时间的条件）；令牌桶的 Redis 实现退回进程内时限额为什么会变宽（两边各有一个满的桶），端到端测试怎么因此偶发失败；按请求速率伸缩隐含“每个请求一样贵”的假设，CPU requests 远低于实际用量时按百分比的 HPA 会发生什么。时限按调用所在的路径定而不是按调用边定（同步路径按“用户等不等得起”，异步路径按“区分慢和坏”）；按实例摘除为什么救不了共享依赖的慢、反而把慢放大成断；Envoy 的摘除只有“连续 N 次”时，为什么只能靠时限盖住依赖的正常长尾；同一个下游怎么按 gRPC 方法分路由和时限（`VirtualService` 按 `uri` 匹配、第一条匹配的生效）。
