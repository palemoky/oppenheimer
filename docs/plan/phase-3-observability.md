  - 混合读写和秒杀的阶梯（2026-11-21，[记录](../notes/3b-rounds/round-4-mixed-and-flash-ladders.md)）：混合读写的拐点是 1907 请求/秒（其中下单 148 单/秒），到顶的是节点的 CPU；秒杀售罄之后 4000 请求/秒很轻，拐点在 4000 到 8000 之间（入口和 gateway 的 CPU）；有货的秒杀 500 次/秒就把入口打满（等落库的订单的轮询）。两轮对账通过。还没做：空表对照、扩容系数、弹性测试和重定 HPA、长稳
  - 空表对照（2026-11-21，[记录](../notes/3b-rounds/round-5-empty-table-comparison.md)）：不是一轮优化，是给前面几轮的结论排除一个变量。做法是把长期运行的那一套临时指到同一批实例上的空库（`loadtest.sh empty-up`、`empty-down`）。结论：这套负载下数据量不是变量
  - 扩容系数（2026-11-21，[记录](../notes/3b-rounds/round-6-scaling-factor.md)）：五个服务一起钉到 1、2、4 个副本，各跑普通下单 100 单/秒和混合读写的阶梯，三组对账通过。节点不变时加副本不加能力：1 个和 2 个副本的拐点都是 1907 请求/秒，4 个副本降到 1526；同样的请求量 2 个副本比 1 个多用三成半到五成的 CPU。发现入口的连接上限会被空闲连接占满（4 个 gateway 副本时在途 82 个请求就占满 1024 条连接）。单个服务的上限量不出来（先到顶的是节点）。主人 2026-11-22 定了三件事（都按记录第 6 节的建议）：入口的 `maxConnections` 调到 4096 并加 30 秒的上游空闲超时；gateway、order 的 HPA 上限从 4 收到 3，**弹性测试改成“验证扩容时不丢请求”，不再量“扩容跟不跟得上”**（扩完不会变快）；order 的连接池从 50 收到 40（按“HPA 上限加滚动多出的 1 个”倒推）。改完用 4 个副本重跑了阶梯（记录第 7 节）：1907 档入口的 `503 UO` 归零，4 个副本的拐点仍是 1526
  - 读从库的模式对比（2026-11-22，[记录](../notes/3b-rounds/round-7-read-modes.md)）：2 个副本上同一个阶梯跑 `primary`、`window`、`gtid` 三组，对账通过。读从库把七成多的订单读分到从库、主库 CPU 降三分之一，但 CPU 原样出现在从库上（主从在同一批节点），三组的拐点都是 1907；`gtid` 比 `window` 多用 14% 的数据库 CPU。集群上的默认值不改（`primary`）。连接池 40 在 2 个副本上够用
  - 定 CPU requests、重定 HPA 的阈值、弹性测试（2026-11-22，[记录](../notes/3b-rounds/round-8-cpu-requests.md)）：六个服务的 requests 改成 2 个副本、混合读写拐点八成时的实测用量（原来只有实际的两到三成），两个节点放得下 3 个副本；`perReplica` 重定（gateway 500、order 220）。弹性测试通过：600 升到 1221 请求/秒，gateway、order 各从 2 扩到 3，69 万个请求 0 失败，落库不受影响。重跑阶梯拐点仍是 1907，但只调了服务没调中间件，节点满时中间件的 CPU 权重变小：拐点上限流 Redis 的超时多五倍，过载时入口多拒一个数量级。主人同日定了中间件也按实测调（记录第 6 节）：按原数调滚动会放不下，所有 requests 统一乘 0.9；HPA 的上限收到 2（这两个节点上伸缩实际关着）。重跑阶梯：入口过载时的误拒和限流 Redis 的超时回到改之前，服务等 MySQL 的时间和拐点以上的落库延迟没有回来（每组一次，原因没有验证），拐点仍是 1907。顺带修了 Strimzi 的 operator 从 2026-11-20 起调和失败的问题（集群域名探测错，已写死）。还没做：长稳
- [x] 长稳测试：中等负载持续数小时，观察内存泄漏、goroutine 泄漏
  - 2026-11-22，[记录](../notes/3b-rounds/round-9-soak.md)：普通下单 125 单/秒 4 小时（180 万单），延迟、goroutine、连接数、CPU 全程是平的，对账通过；闸门 Redis 在幂等键的 TTL（1 小时）处走平，停在上限的 24%；受理队列的上限没有碰到。**找到的问题是磁盘没有稳态**：binlog 保留 30 天、Kafka 保留 7 天都是没配过的默认值，125 单/秒下 agent-2 每小时少 4.4 GiB。主人同日定了按建议改，已生效：binlog 1 天、Kafka 24 小时、死信 7 天（记录 3.4 节）；改完没有再跑长稳验证。跑的是普通下单而不是设计 3.5 写的混合读写（原因在记录第 1 节）。没有走平、4 小时不够下结论的：gateway 的堆（每个 Pod 每小时约 1.5 MiB）。
- [x] 容量结论：当前硬件下各服务的单副本能力与扩容系数（单副本能力按原样的问法量不出来，先到顶的是节点：改成写“每个请求的 CPU 开销”和“水平扩容在这套硬件上没有收益”，见扩容系数的记录第 3.4 节）

## 3c SLO 与告警

设计文档 [3c-slo-alerting.md](../design/3c-slo-alerting.md)（主人 2026-11-22 确认，十项都按建议）。

- [ ] 补 SLI 缺的指标（2026-11-22 加）：支付出结果到订单变成已支付的时延（order）、outbox 里等了多久（`pkg/outbox`）、消费者手里最老的未处理消息的年龄（`pkg/kafkax`）
- [ ] 常驻的低速探针（2026-11-22 加）：平时没有流量，SLO 算不出来；每秒约 1 单，带支付和查询，从入口进来
- [ ] `recon` 做成 CronJob（2026-11-22 加）：有差异时 Job 失败，按它报对账差异
- [ ] 定义 SLI 和 SLO：下单可用性、下单延迟、落库时延、支付回调处理时延（7 天窗口；429 不算坏）
- [ ] 错误预算与多窗口燃烧率告警
- [ ] 基础设施告警：节点、Pod 重启、磁盘、主从延迟、Kafka 消费积压、Redis 内存、`Kafka` 资源的 `Ready` 条件（Strimzi 的 operator 调和失败过两天没人发现，见 3b 的 round-8 记录第 6.3 节）；Kafka 的保留期 2026-11-22 起是 24 小时，消费积压的告警要按“最老的未消费消息的年龄”设，远早于 24 小时；闸门 Redis 是 `noeviction`，内存到上限的七成就要报（round-9 记录第 2.2、3.3 节）
- [ ] 业务告警：下单成功率骤降、对账差异、库存异常
- [ ] Alertmanager 路由、分组、抑制、静默；通知渠道（webhook，为阶段 6 的 Agent 留接口）
- [ ] 每条告警配一份 runbook（`docs/runbooks/`）：我们自己写的规则每条一份（相关的几条可以共用），chart 自带的沿用上游的链接
- [ ] 告警质量检查：人为触发每条告警，确认能响且不误报（规则的单元测试进 CI；集群上逐条触发，要用的故障注入动手前登记在这里；上线后放几天看误报）
- CDC 源库心跳**不做**（2026-11-22，主人确认）：它要解决的是“源库空闲时 `cdc_lag_ms` 不可信”，常驻探针让两个订单分片一直有写入；主从的告警按运行状态和延迟写三条，不依赖心跳

## 3d 最小诊断 Agent

提前做一个最小版本，让它跟着阶段 4 的每次故障实验一起跑、一起迭代，而不是等实验全做完再开始。完整设计见 [phase-6-agent.md](phase-6-agent.md)。

动工前先查最新的 Claude API 和 Agent SDK 文档。

- [ ] Agent 主循环（Go + Claude API 工具调用）：多轮推理、终止条件、步数与费用上限
- [ ] 三个只读工具：Prometheus 查询（PromQL 即时与范围）、Loki 日志查询、Kubernetes（get、describe、events、logs）
  - Kubernetes 工具从阶段 6 提前到这里（2026-11-15）：阶段 4 的故障里有一大类是 Pod 被杀、OOM、节点失联、调度不上，只有指标和日志时 Agent 只能从数据的缺口去猜
  - 用 client-go，单独的 ServiceAccount，只给 get、list、watch；不给 exec、不给任何写权限，权限写在清单里入库
- [ ] 工具输出的裁剪，控制上下文长度
- [ ] 触发方式：Alertmanager webhook 和命令行手动提问
- [ ] 输出 Markdown 报告：根因判断、证据（每条结论附查询和结果）、置信度
- [ ] 全过程留痕：每次运行的工具调用、token 用量、耗时落盘，可回放
- [ ] 用 3c 里人为触发告警的场景试跑几次，确认链路通

这一版不追求准确率，目标是把骨架和留痕做好，阶段 4 开始就能积累真实运行记录。

## 验收标准

- 任意一个慢请求，能从大盘下钻到链路再到日志，定位到具体的服务和调用。
- 有书面的压测基线和容量结论，`docs/GOALS.md` 里的目标量级据此修正。
- 每条告警都被真实触发验证过，并有对应 runbook。
- 告警触发后，最小 Agent 能自动产出一份带证据的报告，运行记录可回放。

## 面试考点

OpenTelemetry 的架构（API、SDK、Collector、OTLP）与上下文传播；Collector 的 agent 加 gateway 两层部署各自做什么、`memory_limiter` 为什么放最前；推和拉两种采集方式怎么发现“对方挂了”；日志的 `trace_id` 为什么不做 Loki 的标签（结构化元数据）；多目标模式的 exporter 里 `up` 和 `mysql_up` 的区别；pprof 端点为什么不能挂在对外或 Service 暴露的端口上；原因码答错会把排查引向哪里（展示读名额满了答成“闸门不可用”，设计文档 3a 第 8 节）；头部采样和尾部采样各自在哪里做决定、各自的代价（实测：出错的链路头部 10% 只留下 10%，尾部全留，代价是服务全量导出和 Collector 的内存）；尾部采样之后从 span 算出来的指标为什么是偏的；网格指标的标签在源头裁和在 Prometheus 里裁的区别；埋点把正常的返回值记成错误的例子（`driver.ErrSkip`，设计文档 3a 第 8 节第 4 步）；Collector 停机时三种信号各丢什么、为什么（累计值的指标补得回来，链路补不回来，日志看 agent 会不会停下来等）；Collector 的 `batch` 处理器为什么会切断反压、批次没有上限会撞上哪些限额（Loki 的突发量、gRPC 的 4 MiB）；复制停了的时候 `Seconds_Behind_Source` 是 `NULL`，按延迟写的告警不响；怎么验证监控本身是对的（制造已知数量的失败再对数；同样是 503，响应标志 `UO`、`UT`、`UH` 才分得出原因）；尾部采样之后 exemplar 为什么大半跳不到链路；HPA 的自定义指标是怎么取到的（Resource、Pods、External 三类指标，聚合 API，KEDA 只提供数、改副本数的仍是 HPA 控制器）；HPA 有多个指标时取最大值，有一个取不到时不缩容但还能扩容（实测）；按请求速率伸缩为什么不比按 CPU 快（`rate` 的窗口）以及它好在哪里；指标后端挂了伸缩会怎样、怎么发现（`ScaledObject` 的 `READY` 看不出来）；同一个 Deployment 不能有两个 HPA；指标、日志、链路各自解决什么问题；Prometheus 拉模型、数据模型、PromQL、直方图与分位数；链路追踪的上下文传播与采样；SLI、SLO、错误预算；告警疲劳与如何设计好告警；压测方法论与常见瓶颈；Go 性能分析（pprof、trace、GC 调优）。

3b 第 1 轮补的（[记录](../notes/3b-rounds/round-1-replica-flush-and-payment.md)、ADR-0032）：`innodb_flush_log_at_trx_commit` 和 `sync_binlog` 各取值在进程崩溃、节点掉电时分别丢什么；从库为什么可以比主库放松、放松之后掉电为什么要重建而不能看“复制还在跑”（数据和 binlog 各丢各的，其中一种不报错）；这类设置为什么要跟着角色走而不是跟着序号（提升之后带着放松的设置当主库）；CDC 用 GTID 集合做位点时从库的 binlog 丢一截或者从库重建为什么不影响它；串行循环的吞吐上限是“1 ÷ 单次提交的耗时”，和负载无关，所以平时看不出来；把串行改成并发为什么能提高吞吐（并发的提交被组提交合进同一次刷盘）以及它和“几笔合进一个事务”的取舍（失败的隔离）；后台循环“取满一批就接着跑”时怎么避免整批失败变成死循环；另开的 goroutine 里的 panic 不会被外层的 recover 接住；量“排队等了多久”的直方图和量“一次调用多久”的直方图为什么不能用同一组桶。

3b 第 2 轮补的（[记录](../notes/3b-rounds/round-2-concurrency-and-consumers.md)、ADR-0033）：组提交在并发低的时候为什么攒不起来（一次刷盘带走的是刷盘期间到达的提交，要看的是同一时刻有几个事务在提交，不是线程数）；做贵的改动之前先做不改代码的对照；下游欠着活时上游量到的数是虚高的；幂等的“依据”和“捷径”要分开（订单库的唯一键是依据，Redis 里的键是让重放不碰数据库就得到答案的捷径，捷径可以过期）；带 TTL 的键放进 `noeviction` 的 Redis 就是一条容量公式（速率 × TTL × 单个大小），TTL 该按“客户端还会重试多久”定；两个各自配置、但有先后关系的时限（幂等键的 TTL 和支付时限）要在启动时互相校验；Redis 写满时“写不进”会连带挡住回收和锁，比拒绝新请求更糟。

3b 第 3 轮补的（[记录](../notes/3b-rounds/round-3-overload-behavior.md)、ADR-0034）：拒绝请求时为什么必须给 `Retry-After`（不给的话拒绝只是把一个慢请求换成很多个快请求）；轮询为什么也是一种重试放大（等待的订单越多查询越多，是正反馈，退避只能压低增益）；入口的并发上限怎么定、怎么读（在途请求数 = 到达速率 × 耗时）；HTTP/1.1 的上游里 Envoy 的连接上限和排队上限各管什么，冷的连接池为什么不能把排队收得太紧；利特尔定律用在背压上（限制等待时间只能靠限制队列长度，上限 = 最慢分片的处理速率 × 允许的等待，换环境要重算）；按“已经等了多久”触发的保护为什么管不了已经放进来的量；`noeviction` 的 Redis 写满时最先坏的是什么、为什么在水位上拒绝新工作而不是换淘汰策略；水位检查放在进程里采样和放进 Lua 脚本的取舍；被动喂结果的熔断器，“连续 N 次失败”为什么要和调用方的并发度比（并发 192 时一次停顿就是上百次失败，要加持续时间的条件）；令牌桶的 Redis 实现退回进程内时限额为什么会变宽（两边各有一个满的桶），端到端测试怎么因此偶发失败；按请求速率伸缩隐含“每个请求一样贵”的假设，CPU requests 远低于实际用量时按百分比的 HPA 会发生什么。时限按调用所在的路径定而不是按调用边定（同步路径按“用户等不等得起”，异步路径按“区分慢和坏”）；按实例摘除为什么救不了共享依赖的慢、反而把慢放大成断；Envoy 的摘除只有“连续 N 次”时，为什么只能靠时限盖住依赖的正常长尾；同一个下游怎么按 gRPC 方法分路由和时限（`VirtualService` 按 `uri` 匹配、第一条匹配的生效）。

3b 扩容系数和读模式对比补的（[扩容系数](../notes/3b-rounds/round-6-scaling-factor.md)第 8 节、[读模式](../notes/3b-rounds/round-7-read-modes.md)第 5 节）：加副本什么时候加能力（副本带来新的 CPU，或者单个进程有瓶颈）；扩容系数为什么可以小于 1；按 Pod 配的上限总量随副本数漂；Envoy 的三个熔断上限各数什么（在途请求、连接、排队），连接数为什么不能当并发上限；修掉“提前拒绝”不等于提高能力；读写分离省的是主库不是系统；读己之写的固定窗口和按 GTID 等待各自的保证和代价；满载时 p99 自己的波动有多大、两组的差别怎么才算数。

3b 混合读写和秒杀的阶梯补的（[记录](../notes/3b-rounds/round-4-mixed-and-flash-ladders.md)）：容量为什么要按场景给、每个场景先到顶的是什么（盘、节点 CPU、入口）；秒杀为什么有货时比售罄时难得多（削峰压平了写入，没有压平“等结果”的读）；舱壁触发时为什么被调用方看不到错误、该看哪个指标；进程内限流的限额为什么随副本数变；依赖 Redis 的限流为什么在最忙的时候最松；同一个瓶颈资源被几种事务共用时，“某个环节的上限”为什么不是一个固定的数。

3b 空表对照补的（[记录](../notes/3b-rounds/round-5-empty-table-comparison.md)）：数据量大了哪些访问会变慢、哪些不会（按递增主键插入、读最新的数据、按索引取第一页只碰 B+ 树的右边缘；随机读旧数据、深翻页、备份和重建才跟着总量走）；B+ 树多一层的代价要看那一页在不在缓冲池里；对照实验怎么只动一个变量（同一套服务换一份数据，而不是另起一套环境）；为什么 A、B 之外要有 A'（p99 自己的波动可以有一倍）；“没有量出差别”的结论要写明负载没有碰什么；查询缓存只存终态订单时，轮询新订单的负载为什么全是未命中。

3b 容量结论补的（[记录](../notes/3b-capacity.md)第 10 节）：“能扛多少 QPS”为什么要先问请求的组合和持续多久；“单个服务能扛多少”什么时候答不了、用每个请求的 CPU 开销代替时它随什么变；秒杀的到达速率和受理速率为什么是两个数；容量的三条公式（吞吐看瓶颈资源的速率，内存看速率 × TTL × 单个大小，磁盘看写入速率 × 保留期 × 副本数）；两个瓶颈离得很近时推开一个能换来多少；瓶颈是硬件还是软件怎么答。

3b 长稳补的（[记录](../notes/3b-rounds/round-9-soak.md)第 5 节）：长稳找的是“没有稳态的东西”，看斜率不看数值；短的压测为什么量不出磁盘的问题；压缩保留和按时间保留的 topic 各由什么决定大小；保留期的下限由什么定（CDC 断点续传、消费者停机再回来）。

3b 定 CPU requests 和弹性测试补的（[记录](../notes/3b-rounds/round-8-cpu-requests.md)第 7 节）：requests 的三个用处（调度器记账、HPA 百分比的分母、节点满了之后分 CPU 的权重），它不是预留也不是上限；只调一部分 Pod 的 requests 为什么会改变所有 Pod 的相对权重（服务调准、中间件不动，过载时等于让服务优先于数据库）；全部按实测写时调度器为什么会拒绝再扩一个副本；HPA 用请求速率和 CPU 两个信号各自防什么；Istio 的边车资源注解为什么要三项一起写；扩容期间不丢请求靠哪几件事；滚动更新为什么要占容量（`maxSurge`）；控制器调和失败而它管的东西照常运行时怎么发现。
