# 阶段 1：Go 订单系统

**目标**：实现分布式高并发订单系统，重点是高并发下的数据一致性。
**设备**：MacBook（docker compose）
**原则**：先做对，再做快。每个子阶段结束时系统都能运行，并且一致性测试通过。

## 1a 正确性：单库跑通主流程

用最简单的架构把业务做对，作为后面所有改造的对照基线。

设计规格见 [design/1a-order-flow.md](../design/1a-order-flow.md)。

基础（主会话串行完成）：

- [x] 接口契约：`api/proto/oppenheimer/{inventory,order,payment}/v1/`
- [x] 数据模型：各服务 `migrations/00001_init.sql`，每个服务独立的库
- [x] `pkg/idgen`：雪花算法变体，低 6 位为分片基因，处理时钟回拨
- [x] `pkg/errx`：gRPC 状态码加原因码的错误约定
- [x] `pkg/mysqlx`：连接池、事务、迁移、错误分类
- [x] `pkg/grpcx`：服务端（日志、panic 恢复、健康检查、优雅停止）与客户端（默认超时）
- [x] `pkg/testdb`：每个测试一个隔离的库；CI 增加 MySQL 服务
- [x] 设计文档

服务（派给子 Agent 在各自的 worktree 并行实现，主会话评审后合并）：

- [x] inventory：Reserve、Confirm、Release（含空回滚与防悬挂）、GetStock
- [x] order：CreateOrder（幂等、可推进）、GetOrder、CancelOrder、HandlePaymentResult、结清与后台任务

集成（主会话）：

- [x] 合并四个服务，`make lint test` 通过

- [x] 端到端测试：主流程、并发抢购零超卖、幂等、超时关单、支付与取消并发
- [x] 把 1a 的面试考点整理到 [notes/1a-consistency.md](../notes/1a-consistency.md)
- [x] 推送并确认 CI 通过，合并到 `main`（PR #2，新增的 MySQL 集成测试和端到端任务首次运行即通过）

**验收**：并发测试在 `-race` 下稳定通过；重复请求、重复回调不产生副作用。

**面试考点**：超卖的几种解法与对比（悲观锁、乐观锁、条件更新）；幂等的实现方式；状态机为什么要带前置条件；雪花算法与时钟回拨。

## 1c 分库分表与主从

- [ ] 分片方案设计并写 ADR：分片键、2 库 × 4 表、订单号嵌入用户分片基因（见 ADR-0002）
- [ ] 应用层分片路由（`pkg/sharding`）：按用户查、按订单号查都能直接定位分片
- [ ] 非分片键查询（商家维度等）：基于 binlog 的 CDC 同步到按商家分片的异构索引表
  - CDC 服务用 Go 实现（go-mysql 库伪装成从库读 binlog），写入 Kafka 再由消费者落索引表；动工时写 ADR，与 Canal、Debezium 对比
  - 位点管理与断点续传、全量加增量的初始化、表结构变更的处理
  - 顺序与幂等：同一订单的变更按序应用，消费重复不出错
  - 同步延迟监控，以及延迟期间查询结果不一致的应对
  - 可选：用同一套 CDC 替换 1b 里 outbox 的轮询中继，对比两种方式
  - 可选：同步一份到 Elasticsearch 做多条件搜索（内存占用大，视资源决定）
- [ ] compose 里搭 2 个分片，每个一主一从（GTID 复制）
- [ ] 读写分离，以及主从延迟下的读己之写（强制走主、或按 GTID 等待）
- [ ] 跨分片的分页与聚合查询如何处理（先明确哪些不支持）
- [ ] 扩容方案设计：一致性哈希或成倍扩容，写文档并做一次演练
- [ ] 造数工具：灌入大量订单（时间跨度覆盖数年），验证分片均匀度和查询性能
- [ ] 冷热分离与归档（灌数之后做）
  - 冷热划分规则：按订单终态加时间（例如完结超过 3 个月为冷），写 ADR
  - 归档任务：分批、限速、可中断续跑，先写冷库、校验一致后再删热库，全程不长时间持锁
  - 冷存储选型：独立的归档 MySQL 实例（压缩表）起步；对比归档到对象存储（Parquet）的方案
  - 查询路由：订单号里带时间，可据此直接判断查热库还是冷库；跨冷热的列表查询如何分页
  - 归档前后对比热表的大小与查询性能
  - 归档数据校验复用 1d 的 Merkle 对比工具
  - 大表删除后的空间回收

**验收**：所有查询路径不出现全分片扫描（明确豁免的除外）；人为制造主从延迟时，用户下单后立刻查询仍能看到订单；商家维度查询走索引表且同步延迟可观测；归档后冷热数据总量与归档前一致，冷订单仍可查询。

**面试考点**：分片键怎么选；基因法；非分片键查询；binlog 格式与 CDC 原理、位点与顺序保证；分布式 ID；主从延迟的成因与应对；扩容与数据迁移；冷热分离与归档方案；什么时候不该分库分表。

## 1d 限流、熔断、降级与对账

- [ ] 网关限流：令牌桶，支持按接口、按用户、按 IP；分布式限流用 Redis
- [ ] 服务侧保护：sentinel-go 做熔断、并发隔离、热点参数限流
- [ ] 降级预案：Redis 不可用时退回数据库扣减并收紧限流；库存服务超时的快速失败；非核心功能开关
- [ ] 超时与重试规范：全链路超时预算、重试只用于幂等接口、退避与抖动
- [ ] 优雅启停：摘流、排空、关闭顺序
- [ ] 对账：基于 Merkle Tree 定位差异（`pkg/merkle`），动工时写 ADR
  - 对账对象：订单与支付单、订单与库存流水、Redis 库存与 MySQL 库存；同一工具复用于主从一致性、CDC 索引表、冷热归档的校验
  - 规范化：两侧结构不同的数据先各自投影成相同的元组（如订单号、金额、状态）再算哈希
  - 分桶：叶子是一个桶（按时间窗口，或按订单号哈希），桶哈希用与顺序无关、可增量更新的方式聚合行哈希
  - 比对：从根向下只展开哈希不同的子树，定位到差异桶后再逐行比对
  - 处理变动中的数据：只对超过水位线（如 10 分钟前）的数据对账，或用一致性快照
  - 差异输出与修复流程；与全量逐行比对做性能对比，说明 Merkle 方案在什么数据量和差异率下才有优势
- [ ] 埋点（OpenTelemetry SDK，见 ADR-0004）：链路贯穿 HTTP、gRPC、Kafka、MySQL、Redis；指标含 QPS、延迟、错误率和业务指标（下单成功数、库存扣减数）；日志带 trace id

**验收**：超出阈值的流量被拒绝而不是拖垮服务；手动停掉 Redis 或 inventory，系统按预案降级而不是雪崩；对账任务能发现并定位人为制造的数据差异。

**面试考点**：限流算法对比（固定窗口、滑动窗口、漏桶、令牌桶）；熔断器状态机；降级与熔断的区别；重试风暴；雪崩的传导过程；Merkle Tree 原理与在反熵、数据校验中的应用；对账系统设计。
