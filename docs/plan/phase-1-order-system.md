# 阶段 1：Go 订单系统

**目标**：实现分布式高并发订单系统，重点是高并发下的数据一致性。
**设备**：MacBook（docker compose）
**原则**：先做对，再做快。每个子阶段结束时系统都能运行，并且一致性测试通过。

**面试考点**：为什么不用 XA 或 2PC；outbox 与事务消息的对比；Kafka 的投递语义、顺序性、重平衡、消息积压处理；Redis 与 MySQL 双写不一致的窗口和兜底；背压的信号不能放在会被别的任务清掉的数据里（回收任务抹掉排队超时的计数，受理周期性重开），用消费者的心跳加探测名额解决，与熔断器半开状态的关系（ADR-0011）；Saga 与 TCC 的区别；延迟消息的实现方案；分布式锁的正确实现、锁过期与续期、Redlock 争议、fencing token、什么时候不该用锁。

步骤三实现中遇到的考点（细节在设计文档第 6 节）：

- Lua 脚本为什么能代替锁；脚本里“先做完所有检查再做所有修改”为什么不需要回滚；Redis Cluster 对多 key 脚本的限制和应对。
- 两个存储之间没有事务时怎么定操作顺序：让 Redis 变小的先做 Redis，让 Redis 变大的后做 Redis，中间状态只会少卖不会多放。
- 受理路径为什么不用 outbox，换来的不一致窗口是什么，怎么收敛（孤儿占用的回收）。
- “回收”和“落库”为什么必须互斥，只靠宽限期为什么不够（消费积压）；用一次原子的认领解决。
- 发送失败不等于没发出去：受理方失败后为什么不能无条件归还占用。
- 归还的幂等靠什么（占用记录以订单号为主键，存在才归还）；为什么占用不能设过期时间。
- 对账为什么用增量修正而不是覆盖；为什么要连续几轮相同才修；汇总量对账发现不了哪类偏差。
- 异步下单后“读己之写”怎么办（落库前的查询从占用合成）；消费积压超过支付时限的订单怎么处理。
- 延迟队列的饥饿问题：一个按时间排序的列表里混入长期不出队的元素，会挡住后面的元素。

步骤四设计中的考点（细节在设计文档第 7 节和 ADR-0010）：

- 分布式锁不可用时放行还是停下：取决于任务的正确性是否依赖互斥。不依赖的任务如果跟着锁一起停，等于凭空多了一个单点。
- 让多个 outbox 中继并存的两种做法：选主，或 `FOR UPDATE SKIP LOCKED`；后者为什么会丢掉分区内的顺序。
- 什么数据适合缓存：不会再变的，和旧了也无所谓的。会变而且旧值有后果的数据，缓存它就必须回答失效的窗口有多大。
- “先更新数据库再删缓存”为什么优于先删再更新和更新缓存；它剩下的两个窗口；延迟双删、消费事件删除、订阅 binlog 删除各自盖住哪一个。本项目没有采用，原因见 ADR-0010。
- 高频写的数据（库存）为什么写时不删缓存，只靠短 TTL。
- 穿透、击穿、雪崩各自的成因和处理；空值缓存和“数据正在创建中”的冲突；布隆过滤器和逻辑过期各适合什么场景。
- 缓存和不可淘汰的数据（库存闸门、锁）为什么不能放在同一个 Redis 实例里。
- 压测对比同步接口和异步接口的吞吐时，为什么要分别报告受理吞吐和落库吞吐。

步骤四实现和杀进程测试中遇到的考点（细节在设计文档 7.1、7.3.4）：

- 消费者被 `kill -9` 后分区要停多久：会话超时、心跳间隔的含义和取值；静态成员（`group.instance.id`）解决什么、代价是什么；为什么重启的新实例也要等旧成员被踢掉。
- 各种超时之间的约束：回收宽限期要大于“会话超时加重启耗时”；消费者的重试预算要盖得住依赖方的一次重启。超时不是各自拍脑袋定的。
- 一致性检查全部通过不等于系统可用：少卖、订单被回收都不违反任何一条不变量，要看比例才发现得了。
- 分布式锁只防崩溃不防卡住：持有者卡在任务里时看门狗照常续期。
- 5xx 不等于没执行；客户端放弃的请求，服务端可能已经执行了。对账要按幂等键去找。
- 突发流量下的冷连接池：新连接没有往返时间样本，丢包要等 1 秒的初始重传超时；为什么秒杀前要预热连接池、为什么固定大小的池比按需新建更稳。惊群：同一个 SKU 的预热用 `singleflight` 合并。
- 削峰的队列也要有上限：受理远快于落库时，积压超过回收宽限期，已受理的订单会被当成孤儿回收。背压为什么要按队列长度（利特尔定律）而不是按最老订单的排队时长；静态上限与按速率自适应的取舍；削峰的拒绝为什么用 429 而不是 503。

  - 冷热划分规则：按订单终态加时间（例如完结超过 3 个月为冷），写 ADR
  - 归档任务：分批、限速、可中断续跑，先写冷库、校验一致后再删热库，全程不长时间持锁
  - 冷存储选型：独立的归档 MySQL 实例（压缩表）起步；对比归档到对象存储（Parquet）的方案
  - 查询路由：订单号里带时间，可据此直接判断查热库还是冷库；跨冷热的列表查询如何分页
  - 归档前后对比热表的大小与查询性能
  - 归档数据校验复用 1d 的 Merkle 对比工具
  - 大表删除后的空间回收

**验收**：所有查询路径不出现全分片扫描（明确豁免的除外）；人为制造主从延迟时，用户下单后立刻查询仍能看到订单；商家维度查询走索引表且同步延迟可观测；归档后冷热数据总量与归档前一致，冷订单仍可查询。

**面试考点**：分片键怎么选；基因法；分片后 outbox 每库一个中继、中继名不同否则 event-id 冲突；CHECK 约束名库级唯一；分片后主键只在分片内唯一，依赖全局唯一的防御检查会失效；多实例同时启动时的迁移互斥（`GET_LOCK` 会话锁与锁表加租约的对比）、MySQL 的 DDL 隐式提交与迁移的可重入；分库后连接池预算怎么算（每库一个池，对照 `max_connections`）；后台扫描按分片设超时，一个库挂起不拖住其他库；非分片键查询；binlog 格式与 CDC 原理、位点与顺序保证；分布式 ID；主从延迟的成因与应对；读写分离按用途划分而不是按语句类型（展示读走从库，做决定的读走主库）；读己之写的三种做法（固定窗口、GTID 等待、客户端带位置）和各自的失效条件；为什么标记要在写之前打；“不存在”只由主库确认；`WAIT_FOR_EXECUTED_GTID_SET` 的超时为 0 是无限等待；半同步复制解决的是不丢数据而不是读到旧数据；为什么索引表用 CDC 而不是双写或业务事件；CDC 从主库读还是从库读（异步复制下主库宕机，下游可能比新主库多出数据）；位点为什么记 GTID 集合而不是文件名加偏移；位点为什么要在消息确认之后才推进，为什么只在事务边界推进；至少一次投递下靠行版本号做幂等和定序，版本从日志位置派生和放在行上的对比；`ON DUPLICATE KEY UPDATE` 的赋值从左到右执行，版本列必须最后赋值；全量加增量怎么衔接，有行版本号时为什么不需要一致性快照；`binlog_row_metadata=FULL` 和“查库得到的是现在的表结构”的时间差；索引的分片键必须不可变；索引表只存主键回表还是带上展示列；用订单号做游标的深分页；`ADD COLUMN` 没有 `IF NOT EXISTS` 时多张分片表的迁移怎么做到可重入；中继日志文件名默认取主机名，容器重建后复制起不来，用 GTID 自动定位时重置复制元数据为什么是安全的；跨分片分页为什么不能直接做（偏移量下每个分片都要返回前 p×n 条）、游标分页和二次查询法；跨分片聚合哪些能由分片结果合成；库数做成配置之后怎么防止配错（库内的身份元数据，启动时核对）；成倍扩容的几种做法（从库提升、双写加回填、用 CDC 搬、停机导出导入）；切换时怎么保证一个分片只有一个库在写（改表名做围栏，为什么围栏要放在数据库里而不是依赖每个实例拿到新配置）；`RENAME TABLE` 的原子性和元数据锁，长事务会堵住改名和它后面的所有语句；切换窗口的时间预算从哪里来（消费者的重试上限）；消费者重试耗尽进死信，对“唯一途径”的消息意味着丢数据；outbox 每库一张时怎么判断“搬走的分片的事件发完了”（水位）；在线校验怎么排除切换后的新写入，校验条件为什么不能看列名猜；雪花 ID 的 Epoch 为什么不能改；CLONE 插件；跨库 `RENAME TABLE` 只改元数据；MySQL 没有 `RENAME DATABASE`；扩容与数据迁移；冷热分离与归档方案；什么时候不该分库分表。

## 1d 限流、熔断、降级与对账

- [ ] 网关限流：令牌桶，支持按接口、按用户、按 IP；分布式限流用 Redis
- [ ] 服务侧保护：sentinel-go 做熔断、并发隔离、热点参数限流
- [ ] 降级预案：Redis 不可用时退回数据库扣减并收紧限流；库存服务超时的快速失败；非核心功能开关
- [ ] 超时与重试规范：全链路超时预算、重试只用于幂等接口、退避与抖动
- [ ] 优雅启停：摘流、排空、关闭顺序
- [ ] orderindex 的消费者逐条写库、分区内串行，只有约 2000 行/秒，500 万行的变更要追 40 分钟以上（设计文档 1c 的 5.11）。改成按批写
- [ ] 1b 压测遗留的落库性能问题（设计文档 7.3.4）：落库在 4 个分区上串行，约 400 单/秒（加分区，或分区内按订单号并发）；轮询非终态订单先查 MySQL，和落库抢连接池（先读闸门，有未认领的占用就直接返回 `CREATING`）。改完后按落库吞吐重新设定 `ADMIT_MAX_QUEUE`
- [ ] 压测工具 `test/load` 增加真正的开环模式（按固定速率提交、不轮询），替换现在用 1 毫秒轮询超时凑出的近似
- [ ] 1b 遗留的小问题：调用方取消被 order、payment 记成 ERROR 和 `Internal`；payment 启动时 Redis 不可用会启动失败；Guard 调用没有单独的超时（设计文档 7.1、7.3.4）
- [ ] 对账：基于 Merkle Tree 定位差异（`pkg/merkle`），动工时写 ADR
  - 对账对象：订单与支付单、订单与库存流水、Redis 库存与 MySQL 库存；同一工具复用于主从一致性、CDC 索引表、冷热归档的校验
  - 规范化：两侧结构不同的数据先各自投影成相同的元组（如订单号、金额、状态）再算哈希
  - 分桶：叶子是一个桶（按时间窗口，或按订单号哈希），桶哈希用与顺序无关、可增量更新的方式聚合行哈希
  - 比对：从根向下只展开哈希不同的子树，定位到差异桶后再逐行比对
  - 处理变动中的数据：只对超过水位线（如 10 分钟前）的数据对账，或用一致性快照
  - 差异输出与修复流程；与全量逐行比对做性能对比，说明 Merkle 方案在什么数据量和差异率下才有优势
- [ ] 埋点（OpenTelemetry SDK，见 ADR-0004）：链路贯穿 HTTP、gRPC、Kafka、MySQL、Redis；指标含 QPS、延迟、错误率和业务指标（下单成功数、库存扣减数）；日志带 trace id

**验收**：超出阈值的流量被拒绝而不是拖垮服务；手动停掉 Redis 或 inventory，系统按预案降级而不是雪崩；对账任务能发现并定位人为制造的数据差异。

**面试考点**：限流算法对比（固定窗口、滑动窗口、漏桶、令牌桶）；熔断器状态机；降级与熔断的区别；重试风暴；雪崩的传导过程；Merkle Tree 原理与在反熵、数据校验中的应用；对账系统设计。
