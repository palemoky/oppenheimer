# 阶段 4：故障注入与复盘

**目标**：在可控条件下把系统弄坏，练习发现、定位、止血、修复的完整过程，并用结果反过来改进监控、预案和架构。
**设备**：Ubuntu（集群）、Mac mini（实验期间持续施压）

## 实验方法

每次实验遵循同一流程，记录用 [`docs/postmortems/TEMPLATE.md`](../postmortems/TEMPLATE.md)：

1. **假设**：写下预期，系统会怎样、哪条告警会响、多久恢复。
2. **稳态**：实验前后台持续压测，确认指标处于基线。
3. **注入**：尽量由脚本随机挑选场景，让主人在不知道故障内容的情况下排查（盲测）。
4. **排查**：只靠监控、日志、链路和 kubectl，记录时间线和走过的弯路。
5. **恢复**：止血与根治分开记录。
6. **复盘**：假设与实际的差距，产出改进项（补告警、补 runbook、改代码、改架构），并跟踪到完成。

每个实验的注入清单和真实根因要按固定格式存档，阶段 6 会用作 Agent 的评测集。

**Agent 同步参与**：阶段 3d 的最小诊断 Agent 在每次实验中与主人同时排查，各自独立得出结论。复盘时对比两者，记录 Agent 错在哪、缺什么工具或知识，当场或攒一批后改进。它的运行记录是阶段 6 评测的原始素材。

## 面试考点

4a 装 Chaos Mesh 补的（[设计 4a](../design/4a-chaos-prep.md) 第 6 节“第 1 步”）：Chaos Mesh 的几类故障各自在哪一层动手（NetworkChaos 是目标 Pod 网络命名空间里的 tc/netem 和 iptables，所以延迟加在出方向、一来一回是两倍；StressChaos 是往目标容器的 cgroup 里放 stress-ng；IOChaos 是把卷换成一层 FUSE；TimeChaos 是 ptrace 进去改 vDSO 里取时间的函数，所以只对注入时已经在跑的进程、经过 vDSO 取时间的进程有效；DNSChaos 是把 Pod 的 DNS 指到它自己的 DNS 服务）；`chaos-daemon` 为什么要特权、生产里这意味着什么（它能进任何 Pod 的命名空间，装它等于多了一个能动所有业务的入口，要配命名空间过滤、RBAC、审计）；为什么默认谁都不能被注入（`enableFilterNamespace` 加注解）；冒烟为什么要先验“没开的时候不生效”；验证一类故障要量“生效、到时恢复、留下什么痕迹”三件事。

4a“Agent 看不到注入工具”补的（[设计 4a](../design/4a-chaos-prep.md) 第 6 节“第 5 步”）：Kubernetes 的 RBAC 为什么只有允许没有拒绝、想“除了某个命名空间都能读”时有哪几条路（逐个命名空间绑定、准入策略、分集群）各自的代价；权限的粒度到不了时在应用层拦，要说清楚它防的是谁（无意读到，还是存心绕过）；为什么“拒绝”本身是信息泄漏、返回要做成和不存在一样（和登录接口不区分“用户不存在”“密码错”是同一个道理）；按结果筛标签挡不住聚合查询，多租户的 Prometheus、Loki 是怎么做的（在查询进后端之前改写选择器强加租户标签，如 prom-label-proxy，或者干脆分租户存）。

4a 故障开关补的（[设计 4a](../design/4a-chaos-prep.md) 第 3.3 节和第 6 节、[ADR-0041](../adr/0041-two-fault-injection-paths.md)）：哪些故障从外面造不出来、只能预埋；Go 的构建标签怎么用（`//go:build` 写错了会被当成普通注释，文件就进了平时的构建）、怎么证明一段代码没有进二进制（`go tool nm`，以及这种检查为什么要“反过来确认一次”防止空转）；为什么不靠“常量为 false 的分支会被编译器删掉”；故障开关为什么必须自己会关（ttl）；带缓冲和不带缓冲的 channel 在“先返回、后台还在跑”这种写法里差在哪；shell 里 `pipefail` 加 `grep -q` 的 SIGPIPE 陷阱。

4b 补场景时补的（[设计 4b](../design/4b-experiments.md) 第 1.2 节；都还没有在集群上验证，B1 做完回来改）：Kubernetes 删 Pod 时宽限期是 0 意味着什么（对象立刻从 API 里消失，端点立刻撤掉，kubelet 再去杀容器）、为什么“立刻删”对调用方反而可能没有影响、它和“进程被 KILL”差在哪（前者端点先撤，后者端点还在、要靠探针或者边车的摘除发现）；优雅下线的几段时间怎么配（排空的延迟、停止的时限、`terminationGracePeriodSeconds`）；容器的 CPU 用量和进程自己报的 CPU 对不上说明什么（同一个 cgroup 里有别的进程）；没有 CPU limit 的容器被抢时按什么分（`cpu.weight`，来自 requests）；cgroup v2 下容器超过内存 limit 时杀的是一个进程还是一组（`memory.oom.group`）；丢包为什么表现成“p50 不变、p99 跳到 200 毫秒的台阶上”（TCP 重传的最小超时）而延迟表现成整体平移；DNS 故障为什么不是一下子出现的（连接池里已有的连接不用再解析，要等连接到期）、连接的寿命和空闲超时各自起什么作用；Istio 里同一个 host 写两个 VirtualService 会怎样。

4b 量采样开销、带负载试第二档时补的（[设计 4b](../design/4b-experiments.md) 第 8 节“2026-11-27”）：Go 的 mutex 剖析和 block 剖析各记的是什么（mutex 记在放锁一方的调用栈上、量的是别人等它的时间；block 记在等的一方，channel、`select`、锁都算）、采样率的两个参数是什么意思、常开的开销实测有多大；这两种剖析和 heap 的 `inuse` 一样是从进程启动起累计的，看“现在”要隔一段时间抓两次做差值；一把罩住 I/O 的全局锁什么时候才成为问题（占用率 = 到达速率 × 锁里的时间，低于一两成时延迟上看不出来，锁里的 I/O 一慢就翻脸）；内存泄漏为什么看容器内存看不出来、要看存活堆和两次 heap 剖析的差值；“每个请求里编译正则”这一类问题的特征（CPU 和分配速率涨、堆的目标不涨）；做前后对照的压测时怎么被上一轮留下的延迟任务骗到（15 分钟后到期的关单叠在下一轮上），为什么每一组只跑一次时只能说“没有超出波动的差别”；虚拟机的盘在线扩容的三层（宿主机上 qcow2 的虚拟大小、分区表、文件系统）各用什么命令、为什么要求要扩的分区是盘上最后一个。

混沌工程的原则；Go 的 goroutine 泄漏、内存泄漏、死锁的成因与 pprof 排查方法；GMP 调度与 GC 原理；MySQL 慢查询优化、索引失效场景、InnoDB 锁（行锁、间隙锁、临键锁）与死锁分析；Redis 大 key 与热 key 的发现和治理；MySQL 主从切换的数据安全（半同步、GTID）；Redis 故障转移期间的数据丢失窗口与脑裂；Kafka 的 ISR、acks、不丢消息的完整条件；CAP 在这些实验里的具体表现；线上故障排查的思路与真实案例（这一阶段的复盘就是案例）。

叠加场景试出来的（2026-11-27，数在 `chaos/scenarios/s016/truth.md`，主人盲测之前不读那个文件）：临界区里包了一次网络往返时吞吐上限是多少（1 / 锁里一次的时间）、为什么平时看不出来而依赖慢几毫秒就放大十倍；排队来自到达的随机性而不是平均速率（同样的平均速率，等间隔到达不排队，随机到达排队：压测工具的到达模型会不会把问题藏起来）；“依赖慢了 5 毫秒”为什么解释不了 p99 慢了 90 毫秒，怎么用链路上“服务端 span 开始到第一个子 span 之间的空白”和 mutex 剖析的差值分清“依赖慢”和“等锁”；累计的剖析为什么要做差值。测试里记并发峰值为什么不能“读到比自己小再 Store”（丢更新，后到的小值盖掉大值），原子变量上求最大值要用 CAS 循环。

Istio 故障注入试出来的（2026-11-27，[设计 4b 第 9 节](../design/4b-experiments.md)）：同一个 host 写两个 VirtualService 实测是先建的生效、后加的被忽略；Envoy 的 HTTP 过滤器链的顺序意味着什么（故障过滤器在 `router` 前面，所以注入的延迟不计入路由的超时，注入的中断不经过上游、不触发摘除）；所以“用 Istio 注入延迟来验超时和熔断”验到的是调用方进程自己的时限，不是网格的；改一个长期存在的对象再改回去和新建一个带标签的对象再删掉，哪种恢复更可靠。闸门 Redis 的 20 次超时查出来的：AOF 重写收尾时主线程会停几百毫秒（和 fork 的那一下是两回事）；客户端的时限和依赖的“正常的停顿”挨得太近时，表现是偶发的、成簇的、两个副本同时的超时；怎么从“两个调用方同时超时”推到“问题在被调用的一方”；指标 30 秒一个点看不到 400 毫秒的停顿，要靠日志的时间戳和 Redis 自己的延迟监控。

写 B4 的场景时碰到的（2026-11-27，都还没有在集群上验）：按地址过滤的网络故障该写 Service 的 ClusterIP 还是 Pod 的地址（包离开 Pod 时目的地址还是 ClusterIP，DNAT 在节点上由 kube-proxy 做；headless 的 Service 没有 ClusterIP，客户端直接连 Pod）；主动的健康检查和被动的摘除各自看的是什么（探针来自节点；摘除看的是调用方实际拿到的结果）；连接被拒绝和包被丢弃对客户端是两回事（前者立刻失败，后者要等到时限，时限没设好的地方就是挂住）；摘除时间为什么随次数加长、全部端点都被摘除时返回什么（恐慌阈值）。

写 B5 的场景时碰到的（2026-11-28，都还没有在集群上验）：`kubectl exec` 起的进程怎么才能在 exec 结束之后留下来（脱离标准输入输出、`nohup`），为什么故障注入不该挂在操作的人的终端上；容器里没有 `ps`、`kill` 不到进程时怎么让一个任务停下（停止文件、截止时刻、在数据库里 `KILL` 连接）；客户端超时断开之后，MySQL 里那条语句还在不在（等行锁、等元数据锁的线程不一定马上知道客户端走了，它持有的锁也就还在）；元数据锁的排队规则（一个排他的请求在等，后面的共享请求全部排在它后面：所以“对一张有长事务的表做 DDL”会让这张表整个不可用，而长事务本身什么都没挡）；可重复读下 `ORDER BY ... LIMIT ... FOR UPDATE` 扫到索引末尾时会锁住末尾之后的间隙、挡住插入；InnoDB 死锁时选哪一方回滚；延迟复制（`SOURCE_DELAY`）和“从库跟不上”在 `SHOW REPLICA STATUS` 上怎么分；`SET GLOBAL` 和 `SET PERSIST` 的区别、怎么查一个变量是谁在什么时候在线改的（`performance_schema.variables_info`）；`max_connections` 调小之后为什么不是立刻出事；Redis 单线程下一条慢命令挡住的是谁、集群里为什么只有一部分键受影响；读一个大 key 时内存花在哪几处（服务端的应答缓冲、客户端攒应答）；Kafka 的配额按什么维度算（客户端号、每个 broker 各算各的）、被限速的消费者自己看起来为什么一切正常；拿线上的消费者组名起一个命令行消费者会发生什么。
