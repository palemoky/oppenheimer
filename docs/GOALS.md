# 项目目标

## 背景

仓库主人正在准备 Go 和 Agent 开发方向的面试，需要在高并发、分布式、稳定性这些日常业务开发接触不到的场景里积累真实经验。本项目用家里的设备搭一套接近工业级的订单系统，把这些场景亲手做一遍、坏一遍、修一遍。

## 核心目标

1. **高并发下的数据一致性**：用 Go 实现分布式订单系统，做对防超卖、幂等、分布式事务、状态机、对账。
2. **Kubernetes 生态**：用 K8s 部署和运行整套系统，熟悉调度、网络、存储、发布、弹性伸缩和常用生态组件。
3. **可观测与稳定性**：指标、日志、链路齐全，有压测基线、SLO 和告警。
4. **故障能力**：主动注入故障，练习定位、排查、修复，并通过复盘改进监控和恢复手段。
5. **Agent 开发**：开发诊断 Agent，在告警触发时自动收集证据并给出根因判断，效果可量化评测。
6. **业务扩展**：优惠券、风控，练习更复杂的业务一致性和实时决策。
7. **Rust（可选）**：在压测证明的热点位置用 Rust 重写，积累 Rust 经验。

## 要模拟的工业级要素

Kubernetes、Kafka、Prometheus、OpenTelemetry（链路后端用 Tempo，见 ADR-0024）、分库分表、主从与集群架构、限流、熔断、降级、故障注入。

## 每个阶段的产出标准

一个阶段算完成，需要同时具备：

- 能运行的代码和部署清单
- 验收标准全部通过（定义在各阶段计划文件里）
- 关键决策有 ADR
- 「面试考点」一节整理完，主人能脱稿讲清楚：问题是什么、方案是什么、为什么不用别的方案、踩了什么坑

## 非目标

- 不做前端界面，接口用 k6、curl、测试脚本驱动。
- 不追求业务功能完整（没有商品管理、物流、售后等）。
- 不接真实支付，支付服务是模拟的。
- 不上公有云，全部跑在自有设备上。
- 不追求生产级安全加固，但密钥不入库这类基本要求要守。

## 目标量级（用于指导设计，阶段 3 压测后修正）

| 指标 | 目标 |
|---|---|
| 下单接口峰值 | 5000 QPS（秒杀场景） |
| 下单 P99 延迟 | < 200ms（异步下单的受理响应） |
| 订单数据量 | 灌入 1 亿级，验证分片方案 |
| 库存一致性 | 任何压测和故障场景下零超卖 |
| 订单与库存、支付对账 | 最终一致，差异可被对账任务发现 |

这些数字受家用硬件限制，是初始假设，不是承诺。
