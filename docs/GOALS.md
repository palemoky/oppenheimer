# 项目目标

## 背景

仓库主人正在准备 Go 和 Agent 开发方向的面试，需要在高并发、分布式、稳定性这些日常业务开发接触不到的场景里积累真实经验。本项目用家里的设备搭一套接近工业级的订单系统，把这些场景亲手做一遍、坏一遍、修一遍。

## 核心目标

1. **高并发下的数据一致性**：用 Go 实现分布式订单系统，做对防超卖、幂等、分布式事务、状态机、对账。
2. **Kubernetes 生态**：用 K8s 部署和运行整套系统，熟悉调度、网络、存储、发布、弹性伸缩和常用生态组件。
3. **可观测与稳定性**：指标、日志、链路齐全，有压测基线、SLO 和告警。
4. **故障能力**：主动注入故障，练习定位、排查、修复，并通过复盘改进监控和恢复手段。
5. **Agent 开发**：开发诊断 Agent，在告警触发时自动收集证据并给出根因判断，效果可量化评测。
6. **业务扩展**：优惠券、风控，练习更复杂的业务一致性和实时决策。
7. **Rust（可选）**：在压测证明的热点位置用 Rust 重写，积累 Rust 经验。
8. **LBS 与推荐（可选）**：现实系统里常见的两个业务方向。LBS 练空间索引、高频位置写入和就近派单；推荐练召回与排序的在线链路、实时特征和向量检索。只做工程部分，数据是模拟的。

## 要模拟的工业级要素

Kubernetes、Kafka、Prometheus、OpenTelemetry（链路后端用 Tempo，见 ADR-0024）、分库分表、主从与集群架构、限流、熔断、降级、故障注入。

## 每个阶段的产出标准

一个阶段算完成，需要同时具备：

- 能运行的代码和部署清单
- 验收标准全部通过（定义在各阶段计划文件里）
- 关键决策有 ADR
- 「面试考点」一节整理完，主人能脱稿讲清楚：问题是什么、方案是什么、为什么不用别的方案、踩了什么坑

## 非目标

- 不做前端界面，接口用 k6、curl、测试脚本驱动。
- 不追求业务功能完整（没有商品管理、物流、售后等）。
- 不接真实支付，支付服务是模拟的。
- 不上公有云，全部跑在自有设备上。
- 不追求生产级安全加固，但密钥不入库这类基本要求要守。

## 目标量级（2026-11-22 按阶段 3 的压测修正）

依据是 [容量结论](notes/3b-capacity.md)，数只对当时的硬件和配置成立（那份文档的第 2 节）。

| 指标 | 最初的假设 | 量到的 | 修正后的目标 |
|---|---|---|---|
| 秒杀的到达速率 | 5000 QPS | 售罄之后 4000 请求/秒很轻，约 8000 已过拐点；5000 没有直接量 | 售罄之后 4000 请求/秒不出错、不超时 |
| 下单的受理和落库 | 没有单独写，含在上一条里 | 持续 125 到 150 单/秒（带支付和取消），只下单不支付 287 单/秒；先到顶的是盘的同步刷盘 | 持续 125 单/秒，过载时由背压拒绝（`429` 带 `Retry-After`），已受理的订单不丢 |
| 读多写少的混合流量 | 没有写 | 拐点 1907 请求/秒，先到顶的是两个工作节点的 CPU | 1500 请求/秒（拐点的八成）下各接口 P99 < 100ms |
| 下单 P99 延迟 | < 200ms（异步下单的受理响应） | 125 单/秒时 45ms；混合读写的拐点上 94 到 191ms | < 200ms，在上面几条的速率以内 |
| 订单数据量 | 灌入 1 亿级，验证分片方案 | 灌了 1000 万；现有的负载下数据量不是变量 | 停在 1000 万，1 亿不做（主人 2026-11-22 定；理由在容量结论第 8 节） |
| 库存一致性 | 任何压测和故障场景下零超卖 | 阶段 3 对账过的每一轮都是零超卖 | 不变 |
| 订单与库存、支付对账 | 最终一致，差异可被对账任务发现 | 每一轮差异 0 | 不变 |

最初的“5000 QPS”把到达和受理说成了一件事，所以拆成前两行：到达几千由入口和 gateway 的 CPU 决定，受理由落库决定，两者差一个数量级以上。

这些数字受家用硬件限制（一块消费级 NVMe、两个 8 vCPU 的工作节点）。写入的拐点主人 2026-11-21 定了不再往上推；换硬件或者改了配置之后要重量。
