# s005 的答案

## 标准根因

order 的一个副本的业务容器里被放进了占 CPU 的进程（Chaos Mesh 的 StressChaos：3 个 worker，各占满一个核，跑在目标容器的 cgroup 里）。
order 自己的进程没有问题，是同一个容器里的“邻居”在抢 CPU。业务容器没有 CPU limit（只有 requests），所以多出来的三个核是从节点上拿的，
同一个节点上别的 Pod 也会被挤。

## 定位必需的关键证据

- 这个 Pod 的**容器** CPU 用量（cAdvisor 的 `container_cpu_usage_seconds_total`）多了约 3 个核，
  而**进程**自己报的 CPU（Go 运行时的指标、`process_cpu_seconds_total`）没有相应地涨：两个数对不上，多出来的不是这个 Go 进程用的。
- 只有一个副本这样，另一个副本同样的流量下 CPU 正常；请求量没有变。
- 对这个 Pod 抓 CPU 剖析：热点和平时一样，没有哪个函数突然占了大头。GC 的次数、堆的大小也没有变。
- 这个副本（以及同节点上别的 Pod）的延迟尾部变差，调度延迟（goroutine 等着被调度的时间）上升；节点的 CPU 使用率上去了。
- 开始和结束都是一瞬间的，没有发布，没有重启。

## 容易误判成的原因

- 代码里的死循环或者 GC 压力（CPU 剖析里没有，进程自己的 CPU 没涨）。
- 流量上涨或者热点（请求速率没变，另一个副本正常）。
- 节点上别的 Pod 在抢（方向反了：多出来的用量就记在这个容器名下）。
- 需要扩容（HPA 的上限就是 2 个副本；而且这不是负载造成的）。

## 备注

Agent 看不到容器里的进程列表，它能拿到的最强的证据是“容器的 CPU”和“进程的 CPU”对不上，加上 CPU 剖析是干净的。
人可以 `kubectl debug` 或者到节点上看进程，那就直接看到了（盲测时这算正常的排查手段）。

上面的证据是按设计推的，没有量过。冒烟（设计 4a 第 6 节）是在一个有 CPU limit 的探测 Pod 上做的；
对没有 limit 的业务容器，3 个 worker 会不会把节点挤到触发 `NodeCPUHigh`、对延迟的影响有多大，第一次真跑时核对。
三个节点的 CPU 余量不一样，抽到哪个副本结果可能差不少。
