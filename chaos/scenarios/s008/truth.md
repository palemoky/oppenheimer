# s008 的答案

## 标准根因

orderindex 的 Pod 里，数据库的域名（`mysql-main-primary.mysql.svc`）解析失败（Chaos Mesh 的 DNSChaos，`error`）。
数据库本身是好的，网络也是通的。**已经建好的连接不受影响**，只有新建连接时才要解析域名，所以故障不是一下子出现的：
连接池里的连接到了寿命（30 分钟）或者空闲太久（5 分钟）被关掉，补新连接的时候失败，能用的连接越来越少，错误越来越多。

## 定位必需的关键证据

- orderindex 的日志里数据库的错误是**建连接阶段**的解析失败（`lookup mysql-main-primary.mysql.svc...: ` 加 DNS 的错误，
  不是 `connection refused`、不是超时、不是 SQL 的错误）。
- 错误是逐渐增多的，不是某一刻突然全部失败；连接池里打开的连接数一路往下掉。
- 同样连这个数据库的别的服务（inventory、payment）完全正常；`mysql-main` 自己的指标正常，`MySQLDown` 没有响。
- 只有这一个域名解析不了：orderindex 到 Kafka、到别的服务都正常；集群的 DNS（CoreDNS）没有问题，别的 Pod 解析同一个名字是好的。
- 后果：商家索引的消费者停住（写不进去就原地重试，不进死信），`DerivedDataLagging`、`ConsumerBlocked` 可能响；
  商家订单列表的查询开始失败。订单、支付、库存的主流程不受影响。
- 结束也是自己好的：duration 到了之后新建连接成功，消费者追上，没有重启。

## 容易误判成的原因

- MySQL 主库出了问题或者连接数满了（别的服务连同一个库是好的）。
- orderindex 的连接泄漏、连接池耗尽（池里的连接是在变少，不是被占满；错误是解析失败，不是等连接超时）。
- 集群的 DNS 整体故障（只有这个 Pod、这个名字）。
- 网络分区（已有的连接一直能用；到别的目标都通）。
- Kafka 的问题或者消费者的 bug（积压是数据库写不进去造成的后果）。

## 备注

时长取 35 分钟是因为连接的寿命是 30 分钟（`pkg/mysqlx` 的默认值）：要保证每条连接在窗口里至少到期一次。
故障多快显现取决于注入的时刻离各条连接建立的时刻多远，可能头十几分钟什么都看不出来。这正是 DNS 故障在真实系统里的样子。

没有核实的（第一次用之前在 `oppenheimer-e2e` 里试，或者第一次做不盲）：

- 模式能不能把 Go 解析器实际发出的每一种写法都挡住（带搜索域展开的三种，加上不展开的原样）。
  这个集群的上游 DNS 对不存在的名字会返回假地址（设计 4a 第 6 节“第 1 步”），漏掉一种写法的话现象会变成“连到一个假地址上超时”。
- orderindex 的连接池大小和寿命是不是用的默认值。
- 消费者在这期间的行为是不是“停住等”，以及查询的失败经 gateway 出去是 503 还是别的。
