# s021 的答案

## 标准根因

order 的所有 Pod 到订单库 0 的主库（`mysql-order-0-primary.mysql.svc`）之间的网络不通（Chaos Mesh 的 NetworkChaos，partition，包被丢弃）。
订单库 0 自己是好的，别的客户端都连得上。和“一个分片不通”不同的是：order 的节点号租约放在订单库 0 上（ADR-0028），续租不上约 20 秒后，
**所有用户**的下单都发不了订单号，受理被拒绝，不只是订单库 0 的用户。

## 定位必需的关键证据

- 下单：注入后约 20 秒起全部用户得到 503、原因码 `ORDER_LANDING_UNAVAILABLE`（发号被拒绝和落库不可用用的是同一个原因码）；探针的下单同样失败。
- 把两种原因分开的证据：`breaker_state{breaker="landing-db-0"}` 打开、`landing-db-1` 没有打开，但订单库 1 的用户同样被拒绝；
  order 的日志里有续租失败的 WARN（每秒重试一次）和租约过期的拒绝；订单库 1 上已经受理的订单照常落库。
- 读：订单库 0 的用户的订单列表、查订单等满时限后失败；订单库 1 的用户的读按设计不受影响（连带影响同 s020 的备注）。
- 库一侧正常：`mysql_up` 1、复制正常、没有慢查询；`MySQLDown` 不响。order 到订单库 0 主库的连接池占满，日志是超时不是拒绝。
- 订单库 0 的 outbox 中继、落库和支付结果的消费者、兜底扫描的表现同 s020；订单库 1 的照常。
- 恢复是 duration 到时发生的；续租成功后发号自动恢复，没有进程退出（租约没有被别人租走）。

## 容易误判成的原因

- 两个订单库都坏了（订单库 1 完全正常，它上面的落库在继续）。
- 订单库 0 挂了、要切换（它是好的，别的客户端连得上）。
- 闸门 Redis 或者 Kafka 的问题（原因码不是 `STOCK_GATE_UNAVAILABLE`，闸门的调用正常）。
- 只看落库熔断器就下结论“只有一半用户受影响”（另一半是被发号挡住的）。
- order 的 Pod 有问题、去重启它（重启后新进程要从订单库 0 租节点号，租不到，起不来或者不 Ready，更糟）。

## 备注

- 都是按代码和 ADR-0028 推的，没有在集群上跑过。要核对的：从注入到全部拒绝是不是约 20 秒（租约 30 秒、续租间隔 10 秒）；
  恢复后多久发号恢复；探针的告警（`ProbeFailing`）和下单可用性的告警各自多久响。
- s020 备注里那处可能的设计问题（读请求的错误让调用方的边车把整个 order 摘掉）在这里同样会出现，先做 s020，那边有了结论再做这个。
- “重启 order 会更糟”是推的（新进程启动要租节点号）：盲测时如果主人或者 Agent 选了重启，复盘里记下实际发生了什么。
- 数据上要验的同 s020：恢复后三个常驻核对和逐行对账没有差异。第一次做时恢复加 `WAIT_RECON=1`。
- 会响 critical 的告警，会发到 Telegram、触发集群里的 Agent 诊断。
