# s018 的答案

## 标准根因

order 两个副本里的一个，发往调用方（gateway、payment）的包被加了 4 秒延迟（Chaos Mesh 的 NetworkChaos，delay，只对着调用方的地址）。
这个副本本身是好的：探针通过、一直 Ready、处理请求的速度正常、落库的消费者照常工作；只是调用方在路由的时限（gateway 3 秒、payment 1 秒）里等不到它的响应。
对应真实世界里“一个副本坏了一半，健康检查看不出来”（坏的网卡、单向的网络问题、一台慢的节点）。

## 定位必需的关键证据

- 经过 order 的接口（下单、查订单、订单列表、发起支付）成簇地出 504（发起支付是带原因码的 503），每一簇持续约 3 秒，簇与簇之间的间隔越来越长；
  别的接口（查库存、商家列表）不变。
- 调用方的边车在摘除 order 的一个端点：`envoy_cluster_outlier_detection_ejections_enforced_total` 在 gateway（和 payment）到 order 的出站 cluster 上一次次地涨，
  `MeshEndpointEjected` 响；每次摘除的时间比上一次长 5 秒（5、10、15…），所以间隔越来越长。
- 失败只落在一个端点上：出错的请求在链路里要么没有 order 的服务端 span，要么服务端 span 是正常结束的（几毫秒），而 gateway 的客户端 span 是 3 秒超时；
  把服务端 span 按 Pod 分开，慢的全是同一个 Pod 的调用方一侧。
- 那个 order 副本自己的指标全部正常：服务端量到的耗时没有变、CPU 没有涨、没有重启、Ready；它的落库和后台任务照常。另一个副本接走了大部分请求，请求数明显多。
- 恢复是 duration 到时发生的，没有发布或者重启。

## 容易误判成的原因

- order 的库慢了或者闸门 Redis 慢了（order 服务端量到的耗时没有变，两个副本都一样）。
- order 的一个副本过载或者卡住（它的 CPU、goroutine、服务端耗时都正常；卡住的话探针会失败）。
- gateway 的问题（gateway 的两个副本一样地在摘除同一个 order 端点；它调别的下游是好的）。
- 上一次发布留下的问题、Pod 在重启（没有重启，没有发布）。
- 摘除本身是故障（摘除是保护在起作用：没有它，一半的请求会一直等满 3 秒）。

## 备注

- 都是按设计推的，没有在集群上跑过。要核对的：
  - `target` 加 `direction: to` 的 delay 是不是真的只影响到调用方 Pod 的包（探针不失败、副本不掉 Ready）；4 秒的延迟下已有的 HTTP/2 连接会不会被重置、新建连接（mTLS 握手几个来回）要多久。
  - 每一簇失败的大小：摘除期满后那个端点回来，要再攒够连续 5 次 5xx 才再次被摘，每次要等满 3 秒；边车默认的负载均衡是按在途请求数挑少的，慢的端点分到的应当不到一半。
  - 错误的总量够不够让入口的 5xx 告警或者下单的 SLO 告警响：估计头一两分钟密、之后稀，10 分钟平均在百分之几，可能只有 `MeshEndpointEjected`（warning）。
  - 超时的下单里“其实受理成功”的那些：响应慢了但请求做完了，订单会落库；压测的客户端不重试，它们到支付时限后关单。逐行对账应当没有差异（第一次做时恢复加 `WAIT_RECON=1`）。
- 随机挑到的那个副本是不是后台任务的 leader 没有关系：到库、到 Redis、到 Kafka 的流量不受影响。
- **e2e 实测（2026-11-27 13:26 到 13:31 UTC，`r20261127-132653-e8c9`，没有负载，手工发请求）**：注入生效，`target` 加 `direction: to` 的延迟只影响到调用方的包：
  所有 Pod 一直 Ready、没有重启。落到那个副本上的请求等满 3.009 秒后失败，**gateway 回的是 503（边车的路由超时在 gRPC 上是 `UNAVAILABLE`），不是上面写的 504**；
  一分半钟里摘除 6 次，簇与簇的间隔约 15 到 20 秒（流量很稀，没有看到间隔明显加长）。撤掉后恢复。带负载的表现还没有量。
- **带负载实测（2026-11-27 14:52:36 UTC 注入，15:01:22 恢复，`r20261127-145236-6b85`，稳态 570 请求/秒，不盲）。比上面推的重得多，而且不衰减，上面“一簇一簇、间隔越来越长”的说法按这里的改：**
  - 整个 9 分钟里经过 order 的接口**稳定约 30% 失败**：下单 202 每秒 22.7、503 每秒 10；查订单 200 每秒 70、503 每秒 30；订单列表 28 比 12；发起支付 6 比 2.1。
    p99 是 3005 毫秒（发起支付 1012 毫秒，payment 到 order 的时限是 1 秒）。查库存、商家列表不变。
  - 摘除在发生但挡不住：每个 gateway 副本对 order 每 15 秒摘除一次（2 分钟 8 次），每个 payment 副本 2 分钟约 7 次，**间隔始终不变，摘除时间没有加长**。
    猜的原因（没有核实）：Envoy 的摘除倍数在端点没被摘除的每个检查周期（1 秒）减一，端点每次回来要挨几秒才再被摘，倍数回到 1，所以永远是 5 秒。
  - 边车的指标：来源一侧到 order 的 `response_flags="UT"`、`grpc_response_status="14"`，gateway 每秒约 50、payment 每秒约 2.4；目的地一侧是 `DR`。
    慢的那个副本在目的地一侧仍然每秒收到约 20 个请求，另一个约 130 个。
  - 告警：`MeshEndpointEjected` 2 分钟内；`SLOOrderPayAvailabilityBurnFast` 约 4 分钟；`IngressGateway5xxHigh`、`SLOOrderCreateAvailabilityBurnFast` 约 6 分钟（后三个是 critical）。
  - order 的受理结果里多出 `order_queue_unavailable`（每秒 0.4 到 0.8）和 `stock_gate_unavailable`（每秒 0.5 到 0.7），平时是 0；闸门和 Kafka 是好的。没有解释，
    猜是调用方 3 秒超时取消请求时打断了那个副本上在途的操作。落库从每秒 33 降到 24.5。
  - 所有 Pod 一直 Ready、没有重启。恢复后 336 秒回到稳态，三个常驻核对和逐行对账差异 0。
  - **这是个真的问题，不只是场景的症状**：一个“活着但对调用方慢”的副本，现在的摘除参数（连续 5 次、5 秒起）圈不住它，三成的下单一直失败到它恢复。登记到计划文件，等主人定。
