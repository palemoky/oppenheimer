# s007 的答案

## 标准根因

inventory 的所有 Pod 出站的网络包被随机丢掉约 10%（Chaos Mesh 的 NetworkChaos，`loss`，相关性 25%）：网络层的故障，
服务、数据库、Redis 本身都是好的。丢的包靠 TCP 重传补回来，所以大部分请求只是变慢，少数慢到超过这一跳的时限。

## 定位必需的关键证据

- inventory 经手的延迟分布变成“大部分正常，一小部分慢很多”：p50 几乎不变，p99 和最大值跳到 200 毫秒以上的台阶上
  （TCP 重传的最小等待约 200 毫秒，连着丢就翻倍）。和 s003 那种“整体平移”不一样。
- 慢的不挑接口、不挑下游：inventory 调 MySQL、调 Redis、发 Kafka、回给调用方的响应都受影响（出站的包都可能丢，响应也是出站）。
  MySQL 和 Redis 自己量的执行时间没有变。
- 只有 inventory 这样；它的 CPU、GC、goroutine 数没有异常。
- 调用方（gateway、order）到 inventory 的调用有零星的超时（路由上 1 秒或 3 秒的预算），边车可能摘除端点，
  `MeshEndpointEjected` 可能响：这是结果，不是原因。
- 节点或者 Pod 网卡的重传计数上升（如果有采集；Agent 的工具里不一定看得到）。
- 预占超时的订单走了补偿：对账（recon-check）是 0，库存没有超卖，可能有暂时卡着的预占随后被清掉。

## 容易误判成的原因

- MySQL 或者 Redis 变慢（服务端的执行时间没有变）。
- inventory 的代码退化、锁竞争、GC 停顿（CPU 和运行时指标正常；mutex、block 剖析里没有东西）。
- 网格的熔断或者并发上限（摘除是超时造成的后果）。
- 某一个节点的网络问题（inventory 的两个副本在哪个节点都一样）。

## 备注

丢的是 Pod 出方向的包（Chaos Mesh 默认的方向）。10% 是起步值：太小看不出来，太大会让预占大面积超时。
上面的证据是按设计推的，没有量过；经边车的 gRPC 这条路上 NetworkChaos 的效果在冒烟里也没有量过（只量了不过边车的 HTTP 端口）。
这个场景会让“预占的结果不明”（请求超时了，但库存其实扣了）大量出现，是对补偿和对账的一次真考验：
第一次做不盲，恢复后等逐行对账过了再继续。

B1（2026-11-24，`oppenheimer-e2e`，没有负载）试过：注入成功，目标 Pod 旁边的 `PodNetworkChaos` 里是 `netem loss 10% correlation 25%`。对延迟和预占的影响没有量（没有负载），所以上面“第一次做不盲、等逐行对账过了再继续”仍然成立：**第一次在长期运行的那一套上用它时，恢复加 `WAIT_RECON=1`**。
