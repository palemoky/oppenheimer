# s027 的答案

## 标准根因

订单库 0 的主库上有人在跑很大的事务（脚本造的，对应“清理历史数据、回填一列时一条语句改了几百万行”）：在一个单独的库 `tmp_report` 里，一条 `INSERT ... SELECT` 写入 200 万行，两分钟后一条 `DELETE` 全部删掉，一共两轮。
每个事务的 binlog 约 450 MB（行格式，整行映像）。大事务提交时要把这 450 MB 一次写进 binlog，这期间别的事务的提交排在它后面；
从库要把整个事务收完、再应用完，才轮到后面的事务，于是落后几十秒；CDC 读的是从库的 binlog，跟着晚。

## 定位必需的关键证据

- 症状是间歇的，四次（两次插入、两次删除），每次之后自己恢复：订单库 0 的从库落后出现尖峰，CDC 订单库 0 流水线的延迟同时出现尖峰；主库上提交的延迟同一时刻有一个短的停顿（落在订单库 0 的用户的落库延迟尖峰）。
- binlog 文件的大小：主库上出现远大于平时的 binlog 文件，或者短时间内连着滚动了几个（`SHOW BINARY LOGS`）；`mysqlbinlog` 或者 `SHOW BINLOG EVENTS` 看得到一个事务里几万个行事件，表是 `tmp_report.daily_orders`。
- 从库上 `performance_schema.replication_applier_status_by_worker` 的 `LAST_APPLIED_TRANSACTION` 的开始和结束时间差几十秒；尖峰期间 `Seconds_Behind_Source` 先涨后落。
- 主库上多了一个库 `tmp_report`，里面一张表；`processlist` 在那几十秒里有一条 root@127.0.0.1 的 `INSERT ... SELECT` 或者 `DELETE`。
- 主库的 `Binlog_cache_disk_use` 涨了（事务的 binlog 缓存放不下，落到了临时文件）。

## 容易误判成的原因

- 从库性能不够、盘慢（平时不落后，只在那四个时刻；每次都对应主库上一个大事务）。
- 网络抖动（IO 线程收得不慢，慢在应用）。
- 订单写入突增（订单的写入量没有变）。
- 和 s026（延迟复制）混：那个是一条平线、`SQL_Delay` 不是 0；这个是尖峰。

## 备注

- **全部是推的，没有在集群上跑过；尖峰有多高没有把握**（200 万行在这套硬件上从库要应用多久没有量过）。太矮的话加行数（`CX_BIG_ROWS`），但盘要跟着算。脚本在本机用 2 万行验过：建库、插入、复制到从库、撤销时删库。
- **第一次先用 20 万行、不带负载试**：CDC（自己写的，读 binlog）碰到一个几百 MB 的事务时内存怎么涨没有看过。它不认识这张表、会跳过这些事件，但事件还是要从从库收下来。
- 不碰业务表、不改表结构；多出来的是一个库和约 1.8 GB 的 binlog（主从各一份，一天后过期）。盘不够不做。
- 没有预期的告警：从库落后要超过 30 秒持续 5 分钟才响，尖峰多半够不着。是间歇类的场景，盲测时难度高，要不要配 `report` 试过再定。
