# s015 的答案

## 标准根因

orderindex 的 CDC 消费者在一批消息多于 32 条时，把反序列化（`proto.Unmarshal`）按 32 条一块分给几个 goroutine 并行做，
并且顺带“按 key 收拢”：`cdc.order.orders` 的 key 是订单号，同一个分区里同一个 key 后到的那条是最新的映像，
所以每个 key 在结果切片 `latest` 里只占一个位置，每个 goroutine 解出一条就直接 `latest[at[i]] = ch`，
指望“后面的覆盖前面的”。

这个指望只在一个 goroutine 里成立。同一个订单的两次变更落在两块里时，两个 goroutine 没有任何同步地写同一个位置（数据竞争），
谁后写谁留下，和消息的先后无关。典型的是旧的那条在前一块的末尾、新的那条在后一块的开头：后一块一开始就写了新的，
前一块解完它前面的三十来条才写旧的，旧映像盖掉新映像。交给 `Apply` 的这个订单只剩旧版本，新版本已经不在这一批里，
`Apply` 的“批内按版本合并”也救不了（它只能在交给它的消息里挑）。索引里这一行停在旧版本上：

- 旧的那条是刚下单的 INSERT（`merchant_id` 还是 NULL）时，这个订单根本不进索引，商家的订单列表里少了它；
- 旧的那条是待支付、新的是已支付时，索引里这一行的 `status`、`paid_at`、`src_version` 都是旧的。

写进去的是一个真实的旧映像（主键、商家、版本号、各列来自同一条消息），不是拼出来的值，版本号只会偏低不会偏高，
所以按版本号的 upsert 以后照常接受更新的映像：这个订单再变一次（付款、到期关单、归档）就自己好了，不再变的就一直错下去。
位点照常提交，没有报错，也没有日志。

代码：`services/orderindex/internal/indexer/unmarshal_compact.go` 的 `unmarshalChanges`（`latest[at[i]] = ch` 那一行），
由 `indexer.go` 里 `Handler` 调用；开关 `f08`。

## 定位必需的关键证据

- 现象只是数据不对，没有任何错误：商家订单列表里少了一些订单，或者订单的状态比订单库旧（订单库是已支付，列表里还是待支付）。
  orderindex 不重启、不报错，消费组没有积压（追赶完以后），CDC 正常，接口延迟正常。
- 逐行对账（recon 的 merchant index 那一对）有差异：索引里缺行，或者同一个订单 `src_version` 比订单库的 `version` 低、
  `status` 不同；没有“多出来的行”，也没有版本比订单库高的行。变更核对（recon-changes 的 index 目标）对这些订单报 `lagging`（不是 `mismatch`）：
  同一个版本上两边内容总是一致的，只是索引停在旧版本上。
- 出错的订单集中在一段时间里：都是积压追赶的那几十秒里有过两次以上变更的订单（下单后马上预占、或者下单后很快付款的）；
  追赶结束之后新来的订单全部正常，开关一直开着也不再出错。把出错订单的几条变更在 topic 里的位点找出来，同一个分区、相隔几条，
  正好跨过 32 的整数倍的边界（一批的起点不知道的话，至少是“同一批里”）。
- 积压的时候 orderindex 的批内合并（`Apply` 的 Merged，日志 reporter 里的计数）几乎是 0，而平时积压追赶时它不是 0：
  同一个订单的多条在进 `Apply` 之前就被收拢掉了。这是唯一一个从外面看得到的“代码走了另一条路”的迹象。
- 代码层面：读 `unmarshal_compact.go`，或者用带 `-race -tags faults` 的构建跑一批两块长、同一个 key 跨块的消息，
  race detector 指着 `latest[at[i]] = ch`。

## 容易误判成的原因

- 索引“落后”（CDC 慢、消费者慢、积压没追完）：落后会随时间自己追上，这里追赶早就结束了、消费组没有积压，这些行还是旧的，
  要等那个订单下一次变更才会好。变更核对报的 `lagging` 字面上像“没追上”，其实是“永远追不上”。
- 消息丢了（Kafka 丢数据、压缩把新版本删了、位点提交跳过了一段）：topic 里新版本的消息都在，位点是连续提交的；
  关掉开关重放那一段（或者重置消费组位点）就全对了。
- CDC 漏发或者发错了映像：recon-changes 和 orderindex 读的是同一个 topic，变更核对能核对新版本，说明消息是在的；
  坏的是 orderindex 自己的处理。
- 重启 cdc 造成的：重启只是制造了积压（注入的一部分），CDC 追赶本身不会改数据；
  积压追赶在开关关着时也照样有，那时索引是对的。
- 多分区并发写、版本比较的 SQL 写错了（`>` 写成了 `>=` 之类）：索引里没有任何一行的版本比订单库高，
  坏的行是一个完整的旧映像，问题出在写库之前，不在 SQL。
- 商家索引的分片路由错了：没有落错分片、落错商家的行（逐行对账没有“多出来的行”）。

## 备注

- **触发条件**（按代码推的，没有在集群上量过）：一批多于 32 条（只在积压追赶、从头重建时出现；稳态 mixed 每个分区每秒几十条、
  写一批十几毫秒，一批只有一两条），并且同一个订单有两条落在不同的块里、两个块真的同时在跑（GOMAXPROCS 大于 1，或者等于 1 时
  调度器先跑后起的那个 goroutine，结果一样）。本机的测试里，“旧的在前一块末尾、新的在后一块开头”这种排法 200 次里 200 次留下旧的。
  一批 500 条（16 块）里同一个订单的两条相隔只有几条时，跨块的概率大约是“相隔条数 / 32”，所以一次几十秒的追赶会写坏几十到几百个订单，
  不是全部。
- **怎么制造积压**：开关只经管理端口打开时，重启 orderindex 会把开关复位，所以重启的是 cdc：cdc 停的那段时间变更在 binlog 里攒着，
  起来后按位点追赶，一下子发出一大段，orderindex 每个分区一批几百条。重启 cdc 的停顿多长、追赶时一批到底多大没有量过。
  也可以走 FAULT_FILE（同 s014）再滚动重启 orderindex，重启和再平衡期间同样会积压。
- **e2e 里告警大概不会响**：`DerivedDataLagging` 等派生数据的告警规则写死了 `k8s_namespace_name="oppenheimer"`，所以 `expected_alerts` 是空的。
  recon-changes 有没有部署在 oppenheimer-e2e 里没有核实；没有的话 `lagging` 的计数也看不到，只能靠逐行对账。
- **对账能不能发现**：逐行对账比的列是 `merchant_id`、`user_id`、`status`、`total_amount`、`version`，缺行和版本低都会被发现。
  `chaos-run.sh recover` 收尾的 `recon-check` 用的是 `APP_NAMESPACE`（默认 oppenheimer），不跟 `CHAOS_NS`，
  在 e2e 上做时要显式设成 oppenheimer-e2e，否则核对的是另一套（没有核实 recon 的 Job 在 e2e 里是否可用）。
- **能不能修好**：recon 的 `-repair` 按订单库此刻的映像修，条件是“订单库的版本不低于索引里的”，这里索引的版本只会偏低，
  所以都能修（缺的行会被插进去）。关掉开关后重放 topic 的那一段也能修（新版本的 `src_version` 更高）；
  开关开着时重放本身就是积压，会再写坏一批。不需要重建索引。
- **统计会变**：开关开着、批多于 32 条时，交给 `Apply` 的条数变少，`Merged`、`Stale` 和延迟的样本数都偏小；这不是有意加的痕迹。
- 已知的另一处不严谨（不是这个场景要考的）：即使串行地“按 key 留最后一条”，在 CDC 全量和增量交叠时，后到的不一定是版本最高的；
  原来的写法让 `Apply` 按版本挑，没有这个问题。
- **2026-11-26 在 oppenheimer-e2e 里试过两轮**（带故障代码的构建，e2e 的 chaos 那一套发压）：把 cdc 缩到 0、发 90 秒压（约 3400 单）、再恢复 cdc，
  逐行对账分别查出 875 和 945 处差异（缺行 176/173，版本低 699/772，多出来的行 0），约占这段订单的四分之一，比上面估的多；
  第二轮装了 recon-changes，`lagging` 正好 945、`mismatch` 0，日志是 `derived version 1 < change version 2`。带 `-repair` 的对账两轮都全部修好。
  滚动重启 cdc 的停顿只有几秒，攒不出这么多积压，试的时候用的是缩到 0 再恢复。上面“没有量过”“没有核实”的几条里，
  触发、对账能发现、能修好、`lagging` 不是 `mismatch` 这四条到这里算核实了；告警在 e2e 里不响没有变。
