# s020 的答案

## 标准根因

order 的所有 Pod 到订单库 1 的主库（`mysql-order-1-primary.mysql.svc`）之间的网络不通（Chaos Mesh 的 NetworkChaos，partition，包被丢弃）。
订单库 1 自己是好的：复制、CDC、exporter、对账都连得上，`mysql_up` 是 1；到订单库 0、到两个从库、到闸门 Redis、到 Kafka 都通。
只有“order 到这一个主库”这一条路断了，连接是挂住的（不是被拒绝），每个操作都要等到各自的时限。

## 定位必需的关键证据

- 失败按用户分成两半：落在订单库 1 的用户（`user_id & 7` 是奇数的 slot）下单、查订单、订单列表出问题，落在订单库 0 的用户按设计应当不受影响
  （实际受不受连带影响是这个场景要验的，见备注）。
- 下单：头十几秒照常 202（受理不碰订单库），之后订单库 1 的用户得到 503、原因码 `ORDER_LANDING_UNAVAILABLE`，立刻返回；
  `breaker_state{breaker="landing-db-1"}` 打开而 `landing-db-0` 没有，`OrderLandingBreakerOpen`（critical）响。
- 读：订单库 1 的用户的订单列表等满 3 秒后失败，查订单（不在缓存里、已经落库的）同样；order 到库的耗时指标上，订单库 1 主库池的调用全是超时，
  连接池（`db_role="primary"` 的那个库）占满、等待数上涨；订单库 0 的池正常。
- 库一侧什么都看不出来：`mysql_up` 1、复制正常、没有慢查询，只是来自 order 的连接没有新的语句、写入量掉下去。**`MySQLDown` 不响**。
- 后台：订单库 1 的 outbox 中继每轮报错（`outbox_relay_delay` 上涨）、落库和支付结果的消费者在重试（最老待处理的消息的年龄一直涨）、
  兜底扫描在订单库 1 的 slot 上每轮超时跳过；订单库 0 的照常。
- order 的日志里是对同一个地址的超时（`i/o timeout`、`context deadline exceeded`），不是 `connection refused`，也不是 MySQL 返回的错误码。
- 恢复是 duration 到时发生的，没有发布、重启或者主从切换。

## 容易误判成的原因

- 订单库 1 挂了或者要做主从切换（它是好的，别的客户端都连得上；这时切换是错的处置，还会把 CDC 的源换掉）。
- 订单库 1 慢查询、锁等待（库上没有慢查询，没有锁等待；语句根本没有到库）。
- order 的连接池配小了（池是被挂住的连接占满的，是结果）。
- order 整个坏了（一半用户是好的；闸门、Kafka、另一个库都正常）。
- 落库熔断器、摘除是故障本身（是保护）。

## 备注

- 都是按代码和 1d 的设计推的，没有在集群上跑过。**读代码时看到的一处可能的设计问题，这个场景要验**：
  订单库 1 的读请求挂住后，order 返回的是 `UNAVAILABLE`（列表自己的 3 秒时限到期，`errDependencyTimeout`）或者被边车的 3 秒路由超时截成 504，
  这两种在 gateway 的边车那里都算这个 order 端点的 5xx。两个 order 副本都连着同一个坏了的库，所以两个都会攒够连续 5 次、一起被摘除，
  那时**订单库 0 的用户也拿到 503**：一个分片的主库不通，变成整个 order 对 gateway 时断时续。`AGENTS.md` 的规则是“依赖坏了返回降级错误，不返回 `UNAVAILABLE`”，
  这里主库算不算“依赖”在 orderindex 那一次判断过（只有一个库的服务，库不通就是整个不可用），但 order 有两个分片，情况不一样。
  要看的：两个副本是不是真的被摘、订单库 0 的用户的失败率；展示读的并发上限（每库 16）是不是先把大部分读挡成了不算 5xx 的拒绝，从而连不成 5 次。
  成立的话是要回到主人那里定的改动（对分片主库不通的读返回带原因码的降级错误，或者别的办法），记到计划里。
- 订单库 1 不带节点号的租约（租约在订单库 0），所以发号不受影响；订单库 0 不通是另一个场景（s021）。
- 写到一半挂住的事务：提交的应答丢了的那些，库里可能已经提交，消费者重试时靠幂等（订单号、状态前置条件）兜住。恢复后三个常驻核对和逐行对账应当没有差异，**这是数据上要验的**。
- 已受理、没落库的占用约 60 到 70 秒后被回收，对应的消息之后被丢弃；延迟关单的消费者重试 10 次（约 20 秒）后进死信，`ConsumerDeadLettered` 可能响。
- 会响 critical 的告警，会发到 Telegram、触发集群里的 Agent 诊断。
