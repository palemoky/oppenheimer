# s002 的答案

## 标准根因

inventory 的一个副本被外部删掉了（Chaos Mesh 的 PodChaos，`pod-kill`，同一时刻只删一个；`gracePeriod` 没有写，默认是 0，
即从 API 里立刻删掉这个 Pod）。Deployment 随后补上一个新 Pod。**对业务没有影响**：没有失败的请求，没有告警。
这个场景的答案就是“有一个 Pod 被换掉了，但没有出事”。

## 定位必需的关键证据

- inventory 的一个 Pod 在注入时刻被终止（事件里有 `Killing`，没有 OOMKilled，没有探针失败，没有节点事件），随后出现一个新的 Pod，
  Pod 名和创建时间都变了；Deployment 的副本数一直是期望值，没有发布（ReplicaSet 没有新版本）。
- gateway 的 5xx 是 0，探针没有失败，没有告警响也没有进 pending；inventory 另一个副本的指标没有异常。新 Pod 约 30 秒内就绪。
- 业务数据没有差异：库存的对账（recon-check）是 0。

## 容易误判成的原因

- 硬要找出一个“故障”：把稳态的压测、设计好的 429、对账的 Job 这些背景当成异常。
- 内存不足被杀（没有 OOMKilled 的退出原因）。
- 一次发布或者滚动重启（没有新的 ReplicaSet，镜像没变）。
- 节点故障（同一个节点上的别的 Pod 没有受影响）。
- inventory 自己崩溃（容器的重启次数没有增加：被换掉的是整个 Pod，不是容器重启）。

## 备注

删的是哪一个副本由 Chaos Mesh 随机选。

量到的（2026-11-24，稳态 570 请求/秒）：gateway 的 5xx 是 0，探针没有失败，没有告警；新 Pod 3 秒后调度、约 30 秒就绪。

**为什么没有失败，没有查清。** 4a 走通时写的解释是“`pod-kill` 发的是正常的 TERM，优雅停止把在途的请求做完了”，那是推断。
之后查了集群上的 CRD：`gracePeriod` 默认是 0，也就是这次删除本来就没有给宽限期。没有失败更可能是因为 Pod 从 API 里一删掉，
端点就立刻从各个调用方的边车里撤了，而在途的请求只有几毫秒长；进程到底收到的是 TERM 还是 KILL、排空的那 5 秒走没走，没有看。
要把它做成名副其实的“正常下线”的对照（滚动发布、节点排空），应当把 `gracePeriod` 写成 45（和 Pod 的 `terminationGracePeriodSeconds` 一样）；
改不改等主人定（设计 4b 的待定项）。“进程突然没了”是 s004。
