# s004 的答案

## 标准根因

order 的一个副本的业务容器被从外面直接杀掉（Chaos Mesh 的 PodChaos，`container-kill`：对容器里的进程发 KILL）。
进程没有收到 TERM，没有排空：它手上在途的请求全部断掉，Kafka 的消费者没有主动退组，节点号的租约没有主动还。
kubelet 随后在**同一个 Pod** 里把容器重新拉起来。

## 定位必需的关键证据

- order 的一个 Pod 的业务容器 `restartCount` 加了 1，Pod 名和 Pod 的创建时间没有变（和 s002 那种“Pod 被删、换了一个新的”不一样）；
  上一次退出的原因是被信号杀掉（退出码 137），**不是** OOMKilled，内存在被杀之前离 limit 很远。
- 被杀之前这个进程没有任何异常：日志里没有 panic、没有收到停止信号后排空的那几行（正常下线会打），最后一行日志和被杀之间没有征兆。
- gateway 到 order 的调用在那一刻有一小簇失败（在途的那些），集中在这一个端点上；边车可能摘除它几秒。另一个副本一直正常。
- 这个副本原来消费的分区停一小段（没有主动退组，要等会话超时才重新分配），之后追上。
- 业务数据没有差异（recon-check 是 0）：已经受理（202）而没有落库的订单由另一个副本或者重启后的进程接着做。

## 容易误判成的原因

- 内存不足被杀（退出码同样是 137，但没有 OOMKilled 的标记，内存曲线是平的）。
- 程序自己崩溃（没有 panic 的栈；Go 的 panic 退出码是 2，不是 137）。
- 存活探针失败被 kubelet 重启（没有 `Unhealthy` 的事件）。
- 节点的问题（同一个节点上别的 Pod 没有事，边车容器也没有重启）。
- 一次发布（镜像和 ReplicaSet 都没有变）。

## 备注

原来计划的写法是 `pod-kill` 加 `gracePeriod: 0`。查集群上的 CRD：`gracePeriod` 的默认值就是 0，那种写法是“Pod 立刻从 API 里消失”，端点也立刻撤掉。
要模拟“进程突然没了”（崩溃、OOM、掉电），`container-kill` 更贴近：进程直接收到 KILL，Pod 和端点都还在。

B1（2026-11-24，`oppenheimer-e2e`，没有负载）试过：业务容器 `restartCount` 0 → 1，上一次退出 `reason: Error`、`exitCode: 137`（不是 OOMKilled）；Pod 名不变，另一个副本和边车没有动；
事件里只有重新拉起的 `Pulled`、`Created`、`Started`，**没有 `Killing`**；清单不用写 `duration`（一次性的）。约 1 秒后容器就重新起来了。
没有量的（要有负载）：在途请求断了多少、边车摘不摘、消费的分区停多久。
